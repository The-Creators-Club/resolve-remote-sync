# Extract of inventory section 08

## Items

### 08-001: When the YouTube part is off for a site, no editor's computer downloads from YouTube, prepares to, or opens or fetches downloaded clips.
- Where: youtube / Where a download runs, and saying so
- What: The YouTube part is one of the parts a site switches on or off; it is off in the product as the vendor ships it. When it is off, or when the app on an editor's computer cannot tell whether it is on, the computer behaves as if it were off: it installs and updates nothing needed for downloading, it answers any request to download with "the YouTube downloader is off for this site, or switched off in config", and a request to show or fetch a downloaded clip is answered "the YouTube downloader is not enabled for this site". The computer notices the part being switched on within about 15 minutes, without the app being restarted.

### 08-002: The owner of a computer can stop that one computer from ever downloading YouTube clips, while still opening and fetching clips others downloaded.
- Where: youtube / Where a download runs, and saying so
- What: A per-computer setting, on by default, decides whether this computer may run YouTube downloads itself. Turned off, the computer never downloads, installs nothing for downloading, and is reported as "local YouTube downloads are switched off in config"; jobs then run on the server. Showing a downloaded clip in its folder and fetching a server-downloaded clip to this computer still work. A value that is neither on nor off counts as on.

### 08-003: A site can separately allow getting past YouTube's own blocks with a signed-in YouTube session; it is off unless the site turns it on.
- Where: youtube / Signing in to YouTube
- What: Whether editors' computers may download with a signed-in YouTube session is its own site switch, off in the product as shipped. While it is off, no signed-in session is ever used for a download (even one saved on the computer from before), the sign-in action is not offered to the editor, and saving a session is refused with "signing in to YouTube for downloads is not enabled for this site. Ask your administrator". Turning it on also lets the computer use the extra help needed to answer YouTube's in-page challenges.
- Flag: dormant

### 08-004: When the YouTube page starts a download, the editor's own computer runs it if it can; otherwise the server does, without a word to the editor.
- Where: youtube / Where a download runs, and saying so
- What: The YouTube page, open in the editor's browser, asks the app on the same computer whether it can download, and waits at most about one second for the answer. If the app does not answer, or answers no, the job runs on the server and the editor is told nothing. The computer answers no, with the first reason that applies, in this order:
  - the YouTube part is off, or this computer is switched off for downloads: "the YouTube downloader is off for this site, or switched off in config";
  - the computer has no server address or credential set: "this computer has no dashboard URL or token configured";
  - nobody is signed in on the computer: "nobody is signed in on this computer";
  - the computer's sign-in is not valid: "this computer has no valid sign-in token: sign in again from the tray";
  - the signed-in editor has not accepted the YouTube terms on this computer (08-033): "the YouTube terms have not been accepted on this computer: " followed by where to accept them;
  - the download tool on this computer is not ready: the reason it is not, or "the downloader is not ready on this computer";
  - the computer has no video tool to join the separate picture and sound YouTube serves: "this computer cannot merge downloaded video and audio";
  - the project drive is known to be absent: "this computer's project tree isn't mounted right now, so there is nowhere to download into". When the computer cannot tell whether the drive is there, it does not refuse on that ground.
  A download tool that is old and could not update itself does not refuse the job; it is passed back as a warning (08-031). The answer also tells the page the qualities this computer will download (480p, 720p, 1080p), the free space on the drive that holds the projects, the computer's name and the signed-in editor.

### 08-005: A computer runs one YouTube job at a time, and what it downloads, where to and how is always decided by the job on the server.
- Where: youtube / One job, one computer
- What: The page only tells the computer which job to run. The clips, their addresses, the quality, the destination folder and the naming all come from the job as the server holds it, so nothing on the page can make a computer download something else or write somewhere else. A second job started while one is running is refused with "this computer is already downloading job N". Only one computer can hold a job at a time; another computer of the same editor already holding it gets the server's own sentence followed by ", so this computer left it alone." If the computer cannot start the download it answers "the download thread could not be started" (and the server runs the job).

### 08-006: An editor can stop a download running on their own computer; the server then finishes the clips that were not done.
- Where: youtube / Jobs on the page: queue, retry, cancel
- What: Stopping a local download ends it at once, including any merge or conversion under way, and deletes the half-made files of the clip in flight. The answer is "Stopped. The server will download the clips this computer did not finish." or, with nothing running, "There was no download running on this computer." The job then shows as handed back with the reason "You stopped this download on this computer. The server will download the clips this computer did not finish." The server takes the unfinished clips over on its own after a short while; stopping on the computer does not tell the server anything directly. Quitting the app also stops a download in flight; the half-made files it leaves are cleared at the next attempt at that clip.

### 08-007: While a job runs on an editor's computer, the page and the tray show its progress; after it ends, the page can still learn how it ended.
- Where: youtube / Progress
- What: Shown for the job: its title (the search's folder name, or the project), the clip in flight, how many clips are done, failed and in total, the last file that landed, and a phase: "starting", "downloading" or "converting" while it runs; afterwards "cancelled" (the editor stopped it), "handed back" (with the reason) or "finished". For the clip in flight: percent done with one decimal, speed such as "4.2 MB/s" (decimal units; KB/s below 1 MB/s, B/s below 1 KB/s), and seconds left on that clip (not on the whole job). Anything unknown is shown as unknown rather than zero. After the job ends, the last job this computer ran stays readable until the app restarts, so a page that looks after the end learns how it ended. The tray carries a progress line from the same figures.

### 08-008: A computer without enough free space leaves the job to the server and says why.
- Where: youtube / Choosing the destination and checking space
- What: Before taking a job, the computer needs at least 5 GB free plus the app's general safety margin for free space. With less, the job goes to the server with the reason "This computer has X GB free and this download needs about Y GB, so the server is downloading it instead." (decimal GB, one decimal place).

### 08-009: When the computer cannot or may not take a job, the page is told why it went to the server.
- Where: youtube / Where a download runs, and saying so
- What: If the computer's own check fails at the moment the job starts: "This computer cannot download right now: <reason>. The server is downloading these clips." When the server refuses to let this computer take the job for a reason about this computer, the page shows one of these, each ending "The server is downloading these clips.":
  - the server has no record that the editor accepted the YouTube terms: "The dashboard has no record of you accepting the YouTube download terms, so this computer did not download. Read the notice at the top of this page and press Accept."
  - the computer's download tool is older than the minimum the server asks for: "This computer's downloader (<version, or 'version unknown'>) is older than the <minimum> the server asks for, so it did not download."
  - the server does not accept the computer's sign-in: "The dashboard does not accept this computer's sign-in, so it did not download."
  - the app is out of step with the server on how clips are named or how credits are written (an out-of-date app): "This computer names downloaded clips differently from the server, so it did not download. ... Updating the companion fixes it." or "This computer writes clip credits in a different format from the server, so it did not download. ... Updating the companion fixes it."
  - the quality is one this computer does not download: "This computer does not download <quality> clips, so it did not download."
  No reason is shown when the job is already finished, cancelled, meant for the server, taken by another editor's computer, lost to another computer at the same moment, or when the server is unreachable or answers with an error: the server simply runs it. The computer asks once and does not try again.

### 08-010: If the computer drops out partway, the server takes the rest of the job over by itself.
- Where: youtube / One job, one computer
- What: While a computer holds a job it keeps telling the server it is still working, about every 30 seconds unless the server asks for another pace. If those reports stop (the computer is switched off, loses its network, or the app quits), the server takes the job back after a while and downloads whatever is missing. A network outage of up to about a minute does not lose the job. If the server says the job is no longer this computer's, the computer stops at once, deletes the half-made clip and says nothing to the editor. If the server stops accepting the computer's sign-in mid-job: "The dashboard no longer accepts this computer's sign-in, so it stopped downloading. The server is downloading the rest of these clips." If the computer cannot get the job's details from the server, the job ends on the computer with nothing shown, and the server finishes it.
- Flag: undetermined: how long the server waits before taking a silent computer's job back

### 08-011: Editors' computers download only 480p, 720p and 1080p; higher qualities, "best" and audio-only always run on the server.
- Where: youtube / Where a download runs, and saying so
- What: A job asking for 1440p, 2160p, best or audio only is handed back by the computer with "Only the server downloads <quality> clips, so this computer handed the job back. The server is downloading them."

### 08-012: A computer only downloads into a project it actually has.
- Where: youtube / Choosing the destination and checking space
- What: The job names its project. The project name is compared ignoring letter case and treating both slash directions alike. An editor's computer downloads only into a project it syncs; a computer set to sync nothing downloads only into a project whose folder already exists on it under the exact spelling. Otherwise the job goes to the server with one of: "The download did not say which project it belongs to, so this computer handed it back. ..."; "This computer has no folder for <project>, so it handed the download back. ..."; "This computer could not check whether it syncs <project>, so it handed the download back. ..."; "This computer does not sync <project>, so it handed the download back. ...".

### 08-013: Clips land in the right project folder on each computer, and never in a made-up folder when the project drive is missing.
- Where: youtube / Choosing the destination and checking space
- What: The destination the job gives is a place inside the shared project tree; each computer puts it under its own copy of the tree, wherever that is on that computer. A destination that would lead outside the tree is refused. Right before writing, the computer checks again that the project drive is really connected (on macOS, that it is mounted at the right place, so a folder is never created on the computer's own disk in its stead). Hand-back reasons, each followed by "The server is downloading these clips." or similar: "This computer could not work out where these clips belong on its own disk, so it handed the job back."; "This computer's project drive is not connected, so it handed the job back."; "This computer could not create the folder these clips go in, so it handed the job back."

### 08-014: Clips in a job download one after another, with a short pause between them.
- Where: youtube / How YouTube throttles and refuses
- What: A computer downloads one clip at a time, waiting about 3 seconds between clips (the server can set another pause), so the studio does not look to YouTube like a burst of traffic. A clip without a video id is skipped and nobody is told. A link to a playlist never becomes many downloads: only the one video is taken. Each clip may take at most 2 hours including joining picture and sound; beyond that it is stopped and fails with "the download did not finish within 2h and was killed".

### 08-015: Only YouTube addresses are ever downloaded.
- Where: youtube / Rights and terms
- What: A clip whose address is not a web address on YouTube (youtube.com, music.youtube.com, youtube-nocookie.com, youtu.be, or YouTube's video servers on googlevideo.com) is refused and reported failed: "the download URL was not a YouTube URL, so this computer refused it".

### 08-016: When YouTube cuts a stream short, the clip is tried once more at the next lower quality.
- Where: youtube / How YouTube throttles and refuses
- What: Fact about YouTube: it sometimes ends a stream before all of it has arrived, and the download reports that more was expected and it gave up. When that happens the half-made files are deleted and the clip is tried once more one step lower (1080p to 720p, 720p to 480p; 480p has nothing lower and fails). A clip saved this way carries the note "<quality> stream truncated by YouTube, fell back to <lower>".

### 08-017: A clip that fails is reported with its reason, its leftovers can never be taken for the clip, and the server tries it again.
- Where: youtube / Jobs on the page: queue, retry, cancel
- What: Each clip is shown as downloading, then done (with its file name, any notes, and the title and channel from YouTube) or failed (with the reason). The reason is the last 400 characters of what the download said, or "the download failed and the downloader said nothing". A download that claims success but leaves no file fails with "the downloader reported success but left no output file". Anything a failed attempt made is renamed so it is never mistaken for the clip and never uploaded by the sync; its half-made files are deleted. The server retries failed clips itself.

### 08-018: What a downloaded clip is: a single MP4 file, H.264 picture and AAC sound where YouTube offers them, credits written into it, and dated the day it was downloaded.
- Where: youtube / Files Resolve can decode
- What: At 1080p and below the download prefers H.264 picture with AAC sound, then H.264 with any sound, then any picture of that height or lower; picture and sound are joined into one MP4 file. Written into the file: the channel (also as the artist), the video's address (also as the comment), the channel's address, the uploader, the chapters and YouTube's own details. The file's date is the day it was downloaded, not YouTube's upload date, so the sync treats it as new and uploads it in the normal way.

### 08-019: The quality choices for a YouTube download.
- Where: youtube / Files Resolve can decode
- What: Best, 2160p, 1440p, 1080p, 720p, 480p, and audio only (the best sound, AAC preferred). The preference for H.264 and AAC holds only at 1080p and below. When "best" has to step down, the next step is 1080p. Editors' computers take 480p to 1080p only (08-011).

### 08-020: Downloaded clips are named the same way wherever they were downloaded.
- Where: youtube / File names and what a file carries
- What: A clip is named "<uploader> - <title> [<video id>]" with its file type. The uploader is cut to 60 bytes and the title to 140 bytes, counting bytes rather than letters, so that long Chinese or other non-Latin titles still fit the 255-byte name limit that Windows and macOS impose. A computer and the server name a clip identically; a computer that would name differently does not download (08-009).

### 08-021: Every downloaded clip has a credits record beside it.
- Where: youtube / File names and what a file carries
- What: Beside each clip is a small record of its credits, in this order: channel (or the uploader when there is no channel), channel address (or the uploader's address), uploader, video address, title, video id, upload date and duration. It is written in readable text that keeps non-Latin characters as they are. If the credits cannot be written at the time, what is needed to write them is kept so they can be made later; if it could not be gathered at all, the clip has no credits record.

### 08-022: Downloads try without a YouTube account first, and fall back to the signed-in session only when YouTube asks for one.
- Where: youtube / How YouTube throttles and refuses
- What: Facts about YouTube: it sometimes refuses a download with a bot check ("confirm you're not a bot"), and it sometimes flags a signed-in account so that its downloads fail with "the page needs to be reloaded". Behaviour, within one job:
  - Every job starts without the signed-in session.
  - A bot check, when a signed-in session is saved: the clip is tried once with the session. If that works, the rest of the job's clips try the session first, and the clip is noted "downloaded with the signed-in YouTube session (the anonymous attempt was bot-checked)".
  - Trying the session first and getting the account flag: the clip is tried once without the session; if that works, the rest of the job goes back to trying without it first.
  - Both refused, in either order: the clip fails with "both download paths are blocked on this computer: YouTube is asking the anonymous one to confirm it is not a bot, and it is refusing the signed-in session as well. Export a fresh cookies file from a different signed-in YouTube session, or let the server download this job."
  Only a clip that landed through the signed-in session is noted. The next job starts without the session again.

### 08-023: The health of the editor's signed-in YouTube session is judged from real downloads and shown to them.
- Where: youtube / Signing in to YouTube
- What: The states, checked in this order:
  - none: no session saved, or the site does not allow signed-in downloads;
  - stale: a real download with the session was refused with any of "cookies are no longer valid", "sign in to confirm you're not a bot", "sign in to confirm your age", "this video may be inappropriate for some users", "please sign in to view this video", "login required" or "the page needs to be reloaded". The reason shown for the last is "YouTube is refusing your signed-in session (the page needs to be reloaded). Downloads are continuing without it."; for the others, YouTube's own phrase. A stale state more than 7 days old is marked as aged. It is recorded at most once per job;
  - expired: the sign-in in the saved session has run out ("the login cookies in the file have expired");
  - ok: otherwise. A download that succeeds with a stale session puts it back to ok ("a download succeeded with the signed-in session").
- Flag: undetermined: where and with what words the tray shows this state (outside this section)

### 08-024: A computer that keeps failing clips the same way stops and gives the rest to the server.
- Where: youtube / Jobs on the page: queue, retry, cancel
- What: When 3 clips in a row fail in the same way (the same error once video ids, file names and numbers are ignored), the computer stops before the next clip and hands the rest back: "<N> clips in a row failed the same way on this computer (<the error, shortened>), so it stopped at clip <i> of <total> and handed the rest back. The server is downloading them." A clip that succeeds starts the count again. The count is a per-computer setting (default 3); 0 or less turns the stop off.

### 08-025: When YouTube's answers suggest the download tool is out of date, the computer looks for a newer one at once.
- Where: youtube / Keeping the downloader working
- What: Fact about YouTube: it changes often in ways that break downloading tools, and the first signs are refusals such as "requested format is not available" or "HTTP Error 403". When a clip fails with either, the computer checks for and takes a newer download tool straight away, at most once per job.

### 08-026: A clip YouTube served in a form Resolve handles badly is converted on the editor's computer into one it edits smoothly.
- Where: youtube / Files Resolve can decode
- What: After a clip lands, the computer reads what is inside it (giving up after 2 minutes; with no way to read it, the clip is delivered unchecked and nobody is told). It converts when the picture is not H.264, the frame rate varies (the average and the nominal rate differ by more than 1 %), or there is sound that is not AAC. When the file could not be read, it converts both picture and sound to be safe. A file with no picture needs nothing. The result is H.264 at a quality indistinguishable from the download, high profile, 8-bit 4:2:0, at a constant frame rate, keeping its colour description; sound is AAC at 320 kbps; whatever was already fine is copied untouched; the credits written into the file are kept; the file starts playing without having to be read to the end. While converting, progress shows "converting", and the original is kept out of the sync and out of Resolve. A conversion may take up to 3 hours: "the conversion did not finish within 3h and was killed". Stopping the job mid-conversion deletes the half-made result and leaves the unconverted download to be cleared later.

### 08-027: If Resolve is holding the clip open when its conversion finishes, the converted clip is still delivered and the editor is told what happened.
- Where: youtube / Files Resolve can decode
- What: Fact about Windows: a file open in Resolve cannot be replaced. Outcomes, each a note on the clip:
  - the converted clip takes the clip's name and the original is removed;
  - the name is held: the old file is kept under an "original" name and the note says "original was in use, kept as <name>"; it is removed at the next attempt at that clip, and any size still held is reported then;
  - even that fails: the converted clip is saved as "<title>.converted [<id>]" and the note says "converted, but <name> was in use: saved as <new name>";
  - nothing can be put in place: the clip fails with "Edit-ready conversion failed: converted, but neither <name> nor its converted copy could be renamed into place";
  - the original cannot be removed after a few tries over about two seconds: "the pre-conversion download could not be removed (<size>, kept as <name>); it syncs nowhere and can be deleted".
  Sizes in notes read "N.N GB", "N MB" or "N bytes".

### 08-028: When conversion fails, the clip either fails with the reason or is kept as downloaded, depending on why.
- Where: youtube / Files Resolve can decode
- What: The conversion fails after the file was read and needed converting: the clip fails with "Edit-ready conversion failed: <the last 500 characters of the error>". The file could not be read and the safety conversion failed: kept as downloaded, noted "could not probe the codecs and the safety conversion failed; kept as downloaded". The video tool disappeared during the job: kept as downloaded, noted "could not convert (no video tool); kept as downloaded".

### 08-029: A local download only ever cleans up after its own clip.
- Where: youtube / Files Resolve can decode
- What: On a failure, stop, cancel or loss of the job, and before a lower-quality retry, the computer deletes only the half-made files of the clip concerned; it never sweeps the folder. Leftovers of a failed attempt are kept under a "failed" name. Nothing a download leaves behind is ever uploaded by the sync or filed into Resolve as a clip.

### 08-030: The download tool on each editor's computer is installed and kept current on its own.
- Where: youtube / Keeping the downloader working
- What: With the YouTube part on and the computer allowed to download, the app installs the download tool the first time it is needed and checks it about 30 seconds after the app starts and then once a day. With the part off it installs nothing and looks again every 15 minutes. After a failed check it tries again sooner (about 5 minutes, then longer each time, never beyond its normal wait). The tool always comes from its publisher's newest build, its checksum checked before it is used; a download that does not match is never run, and a failed install or update always leaves the previous tool in place. Installing needs the app's general free-space margin plus 60 MB free (if free space cannot be read, it goes ahead). The server can require a minimum version: an older tool is updated at once, and if the server cannot be reached a working tool is left alone. What the editor or the dashboard is told: "installed the downloader <version>"; "updated the downloader <old> -> <new>"; "the downloader <version> is current"; "the downloader <version> is the newest build (<N> days old; checked, nothing newer to take)"; "the downloader <version> was the newest build <N> h ago; next check after 20 h" (a successful check is not repeated for 20 hours); "no downloader on this computer and it could not be installed -- YouTube downloads stay on the server"; "the downloader <version> is older than the <minimum> the dashboard asks for and it could not update itself -- YouTube downloads stay on the server".

### 08-031: A download tool that could not update and is getting old is a warning, not a refusal.
- Where: youtube / Keeping the downloader working
- What: When the daily update could not run and the tool is older than a per-computer age limit (default 21 days), the computer still downloads but is marked stale: "the downloader <version> is <N> days old and it could not update itself -- YouTube downloads on this computer may start failing". This warning goes to the page with the computer's answer (08-004). Younger than the limit, a failed update only says "the downloader <version> (<N> days old); could not check for a newer build today, will try again on the next pass". Setting the age limit to 0 or less turns the computer's daily self-update off altogether.

### 08-032: An editor can use their own copy of the download tool instead of the one the app looks after.
- Where: youtube / Keeping the downloader working
- What: A per-computer setting names a download tool the editor manages. The app then only reads its version and never installs or updates anything over it. Messages: "the downloader is set to <path> but nothing runnable is there -- leaving it alone (nothing is installed over an override)"; "your own downloader at <path> is <version>, older than the <minimum> the dashboard asks for -- update it yourself, or clear the setting to let the companion manage one" (the computer does not download); "using your own downloader at <path> (<version>)".

### 08-033: Each editor accepts the YouTube terms on each computer before it downloads for them.
- Where: youtube / Rights and terms
- What: A notice titled "Accept YouTube Terms" carries four numbered statements: the editor confirms they have the right to use the material; they are responsible for YouTube's terms and copyright law; CC Sync grants no rights in downloaded material; their username, this computer's name, the clip and the time are recorded. It also says downloads are paced, may fail, and the feature may stop working. Accepting records the wording's version, the editor and the time on that computer: "Recorded. YouTube downloads can now run on this computer, for you." With nobody signed in: "sign in first -- the record has to say who accepted these terms". If it cannot be saved: "couldn't save that (<error>)". The acceptance counts only for the same editor and the same wording: a re-worded notice, another editor signing in, or a lost record all mean the terms must be accepted again before this computer downloads. The server keeps its own record of acceptance too (08-009).
- Flag: undetermined: where the notice is shown and what the control that accepts it is called

### 08-034: An editor can give their computer a signed-in YouTube session by choosing a cookies file exported from their browser.
- Where: youtube / Signing in to YouTube
- What: The file is checked before it is kept: it must be a cookies file in the common browser-export (Netscape) layout, otherwise "that is not a cookies file in Netscape format. Export it with a cookies-file browser extension, not Save As"; and it must hold at least two of YouTube's sign-in cookies, otherwise "those cookies are not from a signed-in YouTube session (no login cookies found). Sign in to YouTube in the browser first, then export". Other failures: "couldn't read that file (<error>)", "couldn't save the cookies (<error>)". On success it is stored so only the computer's own user can read it, the session is marked ok, and the editor reads "YouTube sign-in saved: your downloads can now reach age-restricted clips". A per-computer setting can name a different cookies file to use instead; if that file is not there, no session is used.
- Flag: several ways in: a chosen file, or the one-click browser sign-in (08-035)

### 08-035: An editor can sign in to YouTube with one click, in a browser window the app opens.
- Where: youtube / Signing in to YouTube
- What: The app opens a private browser window (1024 by 820) on Google's sign-in page, continuing to YouTube, using a sign-in profile of its own that is kept between sign-ins, with no first-run, default-browser, sync or translation prompts. Browsers it uses, in order: on Windows Microsoft Edge, Google Chrome, Brave; on macOS Google Chrome, Microsoft Edge, Brave, Chromium. Safari and Firefox are never used. None found: "no Chromium browser found (Microsoft Edge, Google Chrome or Brave). Install one, or use the cookies file instead". The editor is told "<browser> is opening. Sign in to YouTube in that window. Close the window to cancel.", then "waiting for you to finish signing in" every 5 seconds with the time spent and left, then "signed in, saving your session". Only the YouTube and Google sign-in is kept, marked as a live Google session not to be shared, and saved as in 08-034. A page reading "Signed in to YouTube. Closing this window..." shows for 2 seconds, and the browser is always closed at the end. Failures: the window must be reachable within 30 seconds ("<browser> started but its sign-in window never became reachable. Close any leftover windows and try again"); "the sign-in window opened but could not be inspected - try again"; the editor closed it: "the browser was closed before the sign-in finished - nothing saved"; 10 minutes without finishing: "the sign-in did not finish in time. Nothing was saved - try again"; "couldn't start <browser> (<error>)"; "couldn't create the sign-in profile folder (<error>)".
- Flag: several ways in: also a chosen cookies file (08-034)

### 08-036: Someone building the product can make the one-click sign-in use a particular browser.
- Where: youtube / Signing in to YouTube
- What: A browser named by the person building it is used first if it exists; otherwise it is ignored with a warning. A one-line description of which browser would be used is available for diagnosing.
- Flag: dev only

### 08-037: An editor can open the folder of a downloaded clip from the YouTube page.
- Where: youtube / Reaching the editor and Resolve
- What: The page names the clip by its place in the project tree, never by a full path; a place that leads outside the tree is refused. When the file is on this computer, the file manager opens with it selected: "Showing <name> in <folder>". When the file is not here but its folder is, the folder opens: "<name> is not on this computer - opened <folder> instead. YouTube originals only sync up, so a clip another editor downloaded, or one the server downloaded, stays on the NAS until you ask for it." When neither is here, nothing opens and the same explanation is given for the whole path. Windows opens Explorer and macOS opens Finder; an application or disk image is shown, never opened. On other systems: "opening a folder is only supported on Windows and macOS. The file is at <path>". On Windows a path containing a double quote cannot be shown.

### 08-038: An editor can fetch one server-downloaded clip down to their computer.
- Where: youtube / Reaching the editor and Resolve
- What: Already here: "<name> is on this computer". Otherwise the one file is copied down from the NAS's project folder, and the page asks again until it ends: "downloading <name> from the NAS" with progress, then "<name> is on this computer", or "the download finished but the file is not there - try again", or the reason it failed (for example the drive is not connected), or "the download failed".

### 08-039: YouTube clips that arrive in a project's folder are filed into the open Resolve project's bins by themselves.
- Where: youtube / Reaching the editor and Resolve
- What: For the project open in Resolve, the app looks in its YouTube folder: clips in a search's folder go to the bin Master > Youtube > <search>, and clips loose in the YouTube folder (from a pasted link) go to Master > Youtube. Only those two levels are looked at; a folder called Proxy (any case) and hidden folders are skipped. A clip counts when it is a video file (MP4, MOV, MKV, WebM or M4V), not hidden, and not an unfinished, temporary, converting or kept-original file; credits records are never filed. A clip is filed once it has stopped changing: at least 2 minutes old and unchanged since the last look. The app looks about once a minute, at once when the open project changes, and again straight away while there is more to file; it files a limited number per bin at a time. A clip already in the media pool (under this computer's spelling or the shared spelling) is not filed again, and filed clips are linked through the shared spelling so they are online on every computer. Nothing is remembered across restarts: a clip removed from the media pool while its file stays comes back after the app restarts. A clip that fails to file 3 times is given up on until the app restarts.

### 08-040: The YouTube folder used for a Resolve project is the one the server maps it to, or a careful guess.
- Where: youtube / Reaching the editor and Resolve
- What: The server's record of which folder belongs to which project (matched by name, ignoring case) wins. Without one, the app guesses the folder whose name shares the most words with the project's, and accepts the guess only if it has a YouTube folder. With no answer the editor is told the project has no folder (08-041).
- Flag: undetermined: whether the record of which folder belongs to which project can come from anywhere but the server

### 08-041: The editor and the dashboard are told what the YouTube filing is doing.
- Where: youtube / Reaching the editor and Resolve
- What: States, checked in this order, with the sentence shown:
  - switched off: "Filing YouTube clips into Resolve is switched off on this computer."
  - drive absent: "The sync drive is not available, so downloaded clips cannot be filed into Resolve."
  - paused: "Syncing is paused, so downloaded clips are waiting to go into Resolve."
  - Resolve closed (no project open, a project the app ignores, or Resolve not reachable): "Resolve is closed, so downloaded clips are waiting to go into it."
  - no project folder: "This Resolve project has no folder on the server yet, so downloaded clips cannot be filed into it. Ask your admin."
  - waiting for clips to settle, filing, nothing to do, idle: no sentence.
  With clips waiting, the sentence starts "<N> downloaded clip(s) is/are waiting. ". With clips given up on: "<N> downloaded clip(s) could not be filed into Resolve. CCSync tries them again the next time it starts." and " Last error: <error>". Also counted: clips waiting, filed and failed since the app started, when the last one was filed and into which bin. Error texts: "the import failed -- see the log", "the import returned nothing usable", Resolve's own message, or "the import was refused".

### 08-042: The owner of a computer can switch the YouTube filing off, and change how soon and how often it files.
- Where: youtube / Reaching the editor and Resolve
- What: Per-computer settings: filing on or off (default on); how often to look (default 60 seconds; 0 or less means 60); how old a clip must be before it is filed (default 2 minutes); how many failures before a clip is given up on (default 3). The filing has no tie to the site's YouTube switch.

### 08-043: The dashboard can see the state of each computer's download tool, and an editor is warned when their computer cannot install its video tools.
- Where: youtube / Keeping the downloader working
- What: Each computer tells the server its download tool's version, what was last done (installed, updated, checked), whether it is fine, whether it is stale, whether it is the newest, how many days old it is, the last message (up to 300 characters) and when it was checked; nothing until the first check has run. It also reports whether its video tools are installed, naming up to 4 that failed, the cause and how many tries in a row have failed. The video tools are kept installed on every computer even with the YouTube part off. When their install has failed twice or more in a row, the editor's settings show "This computer cannot install its video tools, so it will not make proxies or take shared media work", followed by ": <cause>" when known.

### 08-044: The music page names a track by its place in the library, and each computer finds it in its own copy of the library.
- Where: music / Sending to Resolve
- What: The music page, served from the server, never sends a full path. It names a track by the library and its place inside it (for example "Cinematic/Slow Build"). On an editor's computer the music library is the Assets > Music folder of the shared tree, unless a per-computer setting names another folder. A place that leads outside the library (a full path, a drive letter, a network path, a step up, or a link pointing outside) is refused. With no library folder on the computer, the page is told so.

### 08-045: An editor can send a track from the music page into Resolve in one of three ways.
- Where: music / Sending to Resolve
- What: The three actions:
  - into the bin: the track is imported only. Note "imported to the Music bin" or "already in the media pool (Music)", with the clip name.
  - place underneath: the track goes, sound only, at the playhead on the lowest audio track from A2 upward that is empty for the track's whole length from the playhead (A1 is kept for the dialogue and sync sound); if none is free, a new stereo track is added ("could not add an audio track" if that fails). Nothing else moves. Note "placed on A<n> at the playhead -- nothing moved" or the same with "(new track)". Needs an open timeline: "no timeline is open".
  - insert: the track goes at the playhead on a chosen audio track (A2 unless the page names one; added as a stereo track if missing), and every clip at or after the playhead on that track moves later by exactly the track's length. Needs an open timeline. Note "inserted at the playhead on A<n>, <k> clip(s) rippled later".
  An unknown action is refused ("unknown action '<x>'"), as is a track number that is not a number ("track must be a number, got <x>").

### 08-046: Every sent track goes into a Music bin once, and is linked so it is online on every computer.
- Where: music / Sending to Resolve
- What: If any clip anywhere in the media pool already points at the track (under this computer's spelling or the shared spelling), that clip is used again. Otherwise the track is imported into a bin named Music (found anywhere in the bin tree by name, or created at the top of the media pool) and, where it can be, re-pointed to the shared spelling so it is online on other computers. If Resolve refuses: "Resolve refused to import <name>".

### 08-047: An insert that would break the timeline is refused before anything changes, and one that fails partway is put back.
- Where: music / Sending to Resolve
- What: Refused before anything is touched:
  - the playhead is inside a clip on that track: "the playhead is inside a clip on A<n> (frame X to Y), so it cannot be rippled whole. Move the playhead to a cut, or razor the clip there first, or use 'place underneath'."
  - a clip that would move has no media of its own (a compound, Fusion or generator clip): "A<n> holds a clip with no media pool source (compound, fusion or generator) at frame X -- it cannot be safely re-appended. Use 'place underneath'."
  - a clip that would move is linked to picture: "A<n> is linked to video at frame X -- rippling it alone would desync sync sound. Use 'place underneath'."
  If it fails after clips were moved, whatever was placed is taken out and the moved clips are put back where they were: "insert failed; rolled back <restored>/<total> clip(s) on A<n>". Clips put back are placed fresh, so any settings made on them in the timeline are lost.

### 08-048: Placing a track never lands it somewhere other than the playhead or in a timeline the editor has just left.
- Where: music / Sending to Resolve
- What: If the editor switched timelines while the track was being placed: "the current timeline changed -- nothing was placed". If the track did not land exactly at the playhead it is taken out again: "placement failed on A<n> at frame X -- something already occupies that span, or the track is locked". The playhead is read from the timeline's current timecode (drop-frame timecode understood), or the timeline's start if that cannot be read. The track's length is its frame count, else its duration at the timeline's frame rate, else one second.

### 08-049: A track the editor's computer does not have yet is fetched from the NAS when sent.
- Where: music / Sending to Resolve
- What: Music is not synced to editors' computers. When a track sent to Resolve is missing, an editor's computer copies that one file down from the NAS's music library first. The page shows "syncing the track to this computer: <N>%" (or without a percentage when unknown) and sends the request again about every 1.5 seconds until it is there; when too many files are being fetched at once it is told to try again shortly. Failures: "couldn't sync the track from the NAS: <reason or 'the download failed'>". This does not happen on a computer set to sync nothing, or when the computer's music folder was set to another place by hand: there, and when the file is still not there after copying, the answer is "file not found at <path> - is the share mounted?".

### 08-050: When Resolve is not ready for a track, the music page is told why.
- Where: music / Sending to Resolve
- What: Messages:
  - Resolve is not running or still starting (the app checks without connecting, so as never to break Resolve's start-up): "could not reach DaVinci Resolve (<reason>). Is it running, with Preferences > System > General > External scripting = Local?"
  - no project open: "no project is open in Resolve (the Project Manager window counts as no project)".
  - Resolve took more than 90 seconds: "Resolve did not respond within 90s. It is usually busy, showing a dialog, or on the Project Manager window."
  - the app could not do the work at all: "could not start the Resolve work: <error>", or the reason it gave.
  A Resolve that hangs never freezes the app on the editor's computer: the request is abandoned after 90 seconds.

### 08-051: The music page can show which Resolve project and timeline a track would go into.
- Where: music / Sending to Resolve
- What: The page can ask for Resolve's state: the open project, and with a timeline open its name, frame rate, number of audio tracks and current timecode; or the same reasons as 08-050 when Resolve cannot answer. Answers are shared for 3 seconds, so many open pages asking at once cost Resolve one question.

### 08-052: An editor can show a music track in its folder from the music page.
- Where: music / Sending to Resolve
- What: Present: the file manager opens with it selected, "Showing <name> in <folder>". Missing but its folder is here: the folder opens, "<name> is not there - opened <folder> instead". Neither: "<path> is not on this computer - is the share mounted?". Same file manager behaviour as 08-037 (Explorer on Windows, Finder on macOS, applications and disk images shown, not opened; other systems told the path). If the file manager cannot be opened: "could not open the file manager -- see the companion's log".
- Flag: differs: unlike showing a YouTube clip, it works whatever the site's music switch says, and its wording differs

### 08-053: From the b-roll page an editor's computer can check Resolve, insert a clip range, and attach a proxy to a clip in the media pool, without the app ever freezing on Resolve.
- Where: broll / Sending a clip to Resolve
- What: These b-roll actions run under the same 90-second limit as sending music. Inserting a clip range appends it by default. Attaching an editing proxy finds the media pool clip whose file matches; if there is none: "that clip is not in this project's media pool"; the proxy is linked through the shared spelling where it can be; Resolve refusing with no reason of its own reads "Resolve refused the proxy".

### 08-054: An editor can drop audio files on the music page and their own computer analyses them and puts them into the library.
- Where: music / Adding tracks to the library
- What: The editor drops a batch of audio files on the music page; the batch is handed to the app on the same computer, which analyses each track for search and uploads it into the NAS's music library. A drop is flat: folders inside it are not kept. It runs on a laptop with no graphics card, and never pauses the making of proxies. Each track's progress reads: waiting, converting, analysing, analysed, uploading, in the library, or waiting for the studio's main computer. The rest (starting, stopping, resuming and the progress window) works as for b-roll footage brought in on an editor's computer.
- Flag: undetermined: the exact words each track's stage shows on the page

### 08-055: A dropped track that cannot be read or analysed fails with a plain reason.
- Where: music / Adding tracks to the library
- What: Reasons: "the source file is not on this computer any more"; "this file has no audio track that could be read"; "this file could not be read (<error>)"; "this file could not be converted to mp3: <error>"; "this track could not be analysed: <reason>"; "this file could not be decoded (<error>)"; "this file has no audio this computer could decode"; "the music model returned the wrong number of vectors for this file"; "the music model produced an unusable vector for this file"; "stopped" when the editor stops the batch or quits during analysis. Reading a file gives up after 2 minutes and analysing after 15 minutes.

### 08-056: Ogg Vorbis tracks enter the library as 320 kbps MP3.
- Where: music / Adding tracks to the library
- What: An Ogg Vorbis file is converted to MP3 at 320 kbps, keeping its tags, before it is analysed and uploaded; the conversion gives up after 15 minutes and fails when the result has no sound ("transcode produced a file with no audio"). Other audio enters as it is.

### 08-057: Only the server names a track in the library; when the library is busy, the track waits and is tried again.
- Where: music / Adding tracks to the library
- What: When the analysis is in, the server answers with the name the track will have in the library, and the file is uploaded under that name; when the upload finishes, the track is live. When the server says the library is not ready (busy, briefly unavailable, or two tracks wanting the same name), the track waits 5, 15, 30, 60, 120 then 300 seconds between tries, up to 6, showing "the library is not ready yet: <detail>"; its analysis is not redone unless the app restarted. Any other refusal, or tries run out: "the library would not take this track: <detail>". Upload failures: "the library did not name this track, so it could not be uploaded"; "the audio file is not on this computer any more, so it could not be uploaded"; "this computer could not queue the track for upload". Tempo, key and loudness are not worked out on the editor's computer; the studio's main computer adds them later.

### 08-058: A track an editor's computer cannot analyse stays on that computer, waiting for the studio's main computer, and is not put in the library.
- Where: music / Adding tracks to the library
- What: When the analysis cannot run on this computer at all, the track ends as waiting for the studio's main computer, with the reason; its file stays on the editor's computer and is not uploaded. If the computer cannot be used for analysis before the batch starts, the batch is not taken at all; if that check itself fails: "this computer could not be checked for the music indexing model".

### 08-059: Each dropped file is matched to its row on the page by its content first, then by name and size, then by name.
- Where: music / Adding tracks to the library
- What: Each row in the list the server holds for the batch is paired with at most one dropped file; a row with no match has no file on this computer. If the app restarts mid-batch, the track that was being analysed is analysed again.

### 08-060: The first music analysis on an editor's computer downloads the analysis model, with a progress window and a note when it is ready.
- Where: music / Adding tracks to the library
- What: The model is about 280 MB and is fetched once, from the vendor's release feed (or an address set for the site), only over a secure connection and only from hosts the build allows, then checked against the checksum the build carries. It needs its own size plus the app's general free-space margin free (an unmeasurable disk does not refuse). A tray notice appears when the download starts, a progress window names "the music indexing model" with percent, rate and time left, and "The music indexing model is ready. Indexing starts now." when it is done. A stopped download (quitting the app, cancelling the batch) resumes where it left off: "the download was stopped - it will resume where it left off". Refusals and failures:
  - "this build cannot run the music indexing model (<error>)";
  - "this build has no verified music indexing model to download yet: its checksum is still a placeholder";
  - "this fleet has no release feed configured, so the music indexing model cannot be downloaded. Set the dashboard's release feed URL and the tray will fetch it";
  - "refusing to download the music indexing model: <host> is not one of the hosts this build is allowed to fetch from";
  - "Not enough disk space for the music indexing model: needs about X GB free at <folder>, has Y GB. Free some space and try again";
  - "the music model download's checksum did not match - the file was deleted and will be fetched again";
  - "the music indexing model could not be downloaded: <error>";
  - loading: "the music indexing model is not downloaded on this computer yet", "the music indexing model's settings file is missing - it will be fetched again", "the music indexing model could not be loaded on this computer (<error>)", "the music indexing model's settings could not be read (<error>)".
  The page, the tray line and the tray notice give one short sentence when the computer cannot analyse music at all (the build cannot run the model, an unverified model, no release feed), and nothing when it can. The page can learn whether the model is already here and, if not, how much must be downloaded.

### 08-061: Music analysis keeps the editor's computer usable.
- Where: music / Adding tracks to the library
- What: Analysis uses a graphics card when the computer offers one, else the processor, and then only half the processor's cores. The model takes about 300 MB of memory, given back when the editor returns to the computer. Analysis listens to at most the first 2 hours of a track, judging it from up to twelve 10-second stretches spread across it (leaving out the first and last 2 %); a track of 10 seconds or less is judged whole. The duration recorded is what was heard, or the file's own figure when the track is longer than 2 hours. A waveform overview of 900 points, scaled to the track's own loudest moment, is made for the music page.
