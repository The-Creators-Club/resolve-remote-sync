# Extract of inventory section 02

## Items

### 02-001: Camera originals on an editor's computer go up to the server on their own, and nothing on the server is ever deleted or overwritten by an upload.
- Where: sync / What syncs where
- What: For every project ticked on a computer with the full mode, the camera video files in the project's folder are copied up to the same place on the server, at any depth. The kinds carried are the common camera and video files: Blackmagic RAW, QuickTime, MP4, MXF, AVI, AVCHD, Matroska, RED, Canon Cinema RAW Light, MPEG, Windows Media, WebM and Insta360 360 video, recognised whatever the letter case of the name.
  An upload never deletes anything on the server and never replaces a file that is already there: the first version of a file name to reach the server is the only one that ever will (see 02-033 for what the editor is told when a newer local version therefore stays behind).
  Never carried up: anything inside a folder named Proxy (any case, at any depth), the hidden extra files macOS writes beside each file on drives it did not format, empty (zero-byte) files, a file half-way through a move the product is making, and the working files a YouTube download leaves while it runs or after it fails.

### 02-002: A file that is still being copied in is not uploaded until it has sat untouched for two minutes.
- Where: sync / Clocks and file age
- What: A file whose last change is less than 2 minutes old is left for later, so a clip still being copied off a card or out of another program is never uploaded half-written. A file whose date is in the future on this computer's clock therefore waits until that time has passed (see 02-034).

### 02-003: A new clip dropped into a ticked project starts uploading about two minutes after it stops changing, without waiting for the regular sweep of projects.
- Where: sync / What syncs where
- What: The app watches the editor's project folders. When a camera video file appears, changes or is moved into a project ticked on this computer, it is uploaded on its own shortly after it settles: once nothing has happened to it for about 10 seconds, its size has stopped changing, and it is at least 2 minutes old. The regular sweep of every project still runs as well; this only makes new footage arrive sooner.
  - Only camera video files are sped up this way, even in an upload-only project; everything else waits for the regular sweep.
  - Up to 200 new files are waited on at once; more than that, and the extras simply go with the regular sweep. A file that has not settled after 30 minutes is likewise left to the regular sweep.
  - A failure here is never shown to the editor as an error (nobody is told; the regular sweep picks the file up). An admin can see, for each computer, whether this is switched on, how many times it has run, how many files it has carried, when it last ran and how long ago, how many files it last carried, and its last failure, so a computer where it has quietly stopped working can be spotted.
  - A per-computer setting, on by default; how long it waits for a file to settle is also a per-computer setting (about 10 seconds by default).
  - The editor's pause (02-025) pauses this too and forgets what it was waiting on; resuming starts it watching again.

### 02-004: In an upload-only project every kind of file goes up, not just video, and nothing comes down.
- Where: sync / Upload only
- What: For a project ticked as upload-only on a computer, every file in its folder is carried up, not only camera video. Still left out: anything inside a Proxy folder, those hidden macOS extra files, a file half-way through a move, YouTube download working files, the product's own recovery folder, unfinished and temporary files (names ending in temporary, lock or partial-download endings), operating-system litter (the Finder's and Explorer's hidden folder files) and the hidden bookkeeping that other sync tools keep in a folder. Nothing at all comes down for such a project: no proxies, no originals (a request for originals on it is refused, see 02-018). If the product cannot tell whether a project is upload-only, it uploads camera video only.

### 02-005: Proxies and the project's folder layout come down from the server to each editor's computer.
- Where: sync / What syncs where
- What: For every project ticked with the full mode, everything inside any folder named Proxy (at any depth, any case) is brought down from the server, and nothing else is brought down by this. Those hidden macOS extra files, the recovery folder, temporary, lock and partial files and half-moved files are never brought down even inside a Proxy folder. For clips downloaded from YouTube only their proxies come down, never the downloaded originals.
  The empty folder layout of the project on the server is also recreated on the editor's computer, so a team's prepared folders appear there before anything is in them. A folder whose name starts with a dot is never created.
  Proxies come down smallest first.

### 02-006: A proxy that is still being made on the server is not downloaded until it is two minutes old.
- Where: sync / Clocks and file age
- What: A proxy changed on the server less than 2 minutes ago is skipped and fetched later, so a proxy still being written is never brought down cut short. A per-computer setting, 2 minutes by default; zero turns the wait off.

### 02-007: A proxy removed on the server is removed from the editor's computer, but always into a recovery folder, never deleted.
- Where: sync / Deletions and removing a project
- What: The proxies on an editor's computer follow the server, so a proxy that is gone from the server goes from the computer too, and a changed one is replaced. Every file removed or replaced this way is moved into a hidden recovery folder at the top of the editor's synced tree, one dated folder per sync, keeping the project path and the file's own path inside it, so it can be recovered by hand. Nothing is deleted.
  When something has been moved there, the editor gets a notification naming the folder, at most once every 30 minutes. The recovery folder's size (file count and bytes, counting up to 50,000 files, measured at most every 15 minutes), where it is and how long files are kept there are reported to the dashboard.
  Removals are recorded in the transfer history as removals, never as downloads.
- Flag: undetermined: the exact wording of the notification is not given in this part.

### 02-008: The recovery folder empties itself by age, by size, and to keep the drive from filling.
- Where: sync / Deletions and removing a project
- What: After a sync, at most every so often, the oldest contents of the recovery folder are cleared: anything older than a set number of days, anything beyond a set total size, and as much as is needed to keep the drive above its free-space floor (more while proxy download is stopped because the drive was full, see 02-011). How often, how many days and how large are settings on the computer; their defaults and whether a person can change them are not given in this part.
- Flag: undetermined: the defaults of age, size and frequency.

### 02-009: Old proxies are cleared out a slice at a time, never more than 100 files or 20 GB in one go.
- Where: sync / Safety stops
- What: In one sync of a project at most 100 files and 20 GB are removed from an editor's computer. When that limit is reached the rest waits for the next sync, and the editor is told (as a calm state, not an error) how many files were transferred and that old files are being tidied in slices as a safety limit and it continues next time.

### 02-010: Proxy download stops by itself, and says so, when the server suddenly looks wrong; only a person restarts it, and uploads carry on.
- Where: sync / Safety stops
- What: Before and during each download the product checks that the server still looks like the studio's project tree, and counts how many local proxies a sync is about to remove. When the server does not look like the tree, or a sync would remove too many of the editor's proxies, proxy download stops and the app shows it as paused (not failed) with "STOPPED (safety):" followed by a sentence for the editor. Uploads of originals and the rest of syncing keep running. While stopped, nothing is downloaded or removed.
  Before stopping for removals, the product first asks whether the files were really deleted or only moved: a file still on the server at the same path (a proxy just re-rendered or replaced), a file elsewhere in the same project with the same name and size, a file the dashboard says now lives elsewhere, or one already carried to its new home (02-012), does not count as a deletion. If that check cannot be made, the files count as deletions.
  Only a person restarts proxy download: the editor from the app, or an admin from the dashboard for that computer (each such request takes effect once). The editor is then told proxy download resumed.
- Flag: several ways in: from the app on the editor's computer, and by an admin from the dashboard.

### 02-011: Downloads stop while the editor's drive is nearly full; uploads never do.
- Where: sync / Disk space
- What: Before each download the free space on the sync drive is measured. Below the free-space floor, proxy download pauses and the app shows "NOT DOWNLOADING (disk):" with the reason; originals download pauses with "NOT DOWNLOADING ORIGINALS (disk):" and the reason. Originals download also pauses when the whole batch of originals asked for would not fit while keeping the floor free, saying how much the originals need, how much the drive has to give, and how much it keeps free. Uploads are never paused for disk space. If the free space cannot be measured, nothing is paused.
- Flag: undetermined: the size of the floor and the level at which downloads resume.

### 02-012: A proxy moved by hand on the server is moved on the editor's computer too, not downloaded again.
- Where: proxies-and-file-moves / Moves made by hand on the NAS
- What: After a sync has removed proxies from an editor's computer, the product asks the dashboard where files of the same name and size now are on the server. For each one:
  - found in exactly one other place, in a project this computer syncs: the copy in the recovery folder is moved to that place (in the server's spelling of the path) instead of being downloaded again, and Resolve is told so its clips can be relinked. A file already at that place is never replaced; the copy stays in the recovery folder (with a warning when the two sizes differ). On a Mac a file that appears at the destination at the same moment is never overwritten;
  - found in one place, in a project this computer does not sync: stays in the recovery folder, but does not count as a deletion for the safety stop;
  - found in several places: nothing moves (an unclear answer is a refusal), and it does not count as a deletion;
  - found only where it was just removed from (the server's picture is out of date), or not found: stays in the recovery folder and counts as a deletion.
  A destination outside the editor's synced tree is refused. Names are compared in one Unicode spelling, so a Mac's file names match the server's. Up to 2,000 files are asked about after one sync; any beyond that, and every case where the dashboard cannot answer (no address, unreachable, a bad answer, or it has never finished looking over the tree), are treated as deletions. Nobody is told the outcome; it is only written to the app's log, including which projects the server could not read.

### 02-013: A computer can be set to download from a different server address than it uploads to.
- Where: sync / Speed and routes
- What: A per-computer setting, blank by default, gives downloads (proxies, originals and the server checks that go with them) their own address and folder on the server, for example a faster link used only for downloads. Uploads always use the normal address.
  - If that download address is plain unencrypted web traffic to a public internet address, it is not used (its password would cross the internet readable), and downloads use the normal address until it is made secure. Nobody is told except in the app's log.
  - If the download address does not answer, proxy download pauses with: "NOT DOWNLOADING (route): the server's download link did not answer, so proxy download is paused and nothing was changed here. It tries again next pass."
  - If the download address lists a project as empty while this computer holds proxies there (for example a sign-in page in front of it): "NOT DOWNLOADING (route): the server's download link listed {project} as empty while this computer holds {N} proxies there, so proxy download is paused and nothing was deleted. It tries again next pass."
  - Either way it tries again by itself and a change takes effect at the next sync.
- Flag: dormant

### 02-014: A project whose server path is malformed is not synced at all, by anything.
- Where: sync / Names
- What: Every project path the dashboard hands a computer is checked before anything is built from it. A path that is empty, starts at a drive root, names a drive letter, or contains an empty, "current folder" or "parent folder" part is refused, and that project is then left alone by every kind of transfer, consistently, rather than half-synced. A project marked inactive or with no path is skipped too. Nobody is told; it is only written to the app's log.

### 02-015: When an admin renames or moves a project on the server, every editor's copy follows by itself before anything else syncs.
- Where: sync / Project folders on an editor's computer
- What: Before any transfer, the app compares where each ticked project lives on this computer with where the dashboard now says it is. When they differ, the project was renamed or moved on the server, and the editor's folder is moved to match first, so nothing is ever uploaded back to the old place. Nothing needs remembering: a fresh install, an editor who was away through several renames, or an update all end up in the right place on the first check. Letter case and slash direction are ignored in this comparison.
  - Old folder gone and new one present: nothing is moved.
  - Neither present: nothing happens.
  - The new place already holds a synced copy of the project: the old folder is left where it is for a person to deal with, and syncing continues from the new one.
  - The new place exists but holds only empty folders: those are cleared and the move goes ahead.
  - The new place holds files but is not a synced copy: the move is refused (message in 02-016).
  - Moving to another drive: the folder is copied, put in place only when complete, and the old one removed only then; if it cannot all be removed it is left with a warning. A half-finished copy from a failed attempt is cleared on the next attempt. Empty parent folders left behind are not tidied.
  - A move that fails (on Windows usually because Resolve, Explorer or antivirus holds a file open): the project stops syncing, still pointing at its old place on purpose, because syncing from the wrong place would spread the whole project as deleted to the server and every editor. It retries by itself on every check.
  - If the admin undoes the rename or the editor re-ticks the project, it syncs again from where it is.
  - The target must lie inside the editor's synced tree, or nothing is moved.

### 02-016: What the editor is told when a project's folder follows a rename on the server.
- Where: sync / Project folders on an editor's computer
- What: The editor sees one of these sentences ({name} is the project's path):
  - moved and relinked: "Your admin renamed a project on the server. CC Sync moved your copy to match ({name}). Resolve was relinked."
  - moved, not yet relinked: "Your admin renamed a project on the server. CC Sync moved your copy to match ({name}). Resolve reconnects the clips next time you open that project."
  - move failed: "{name} is not syncing because CC Sync could not move its folder. Your files are safe where they are. Close it in Resolve and in Explorer, then it retries by itself."
  - new name taken: "{name} is not syncing because a folder with its new name is already on this computer. Your files are safe where they are. Move that other folder somewhere else, then it retries by itself."
  The last 20 such events are kept per computer, one per project, old place and outcome, so a project that fails every time does not crowd out real renames. When a pending relink later succeeds, its sentence changes to the relinked form.

### 02-017: Resolve's clips follow a renamed project, now or the next time that project is open.
- Where: proxies-and-file-moves / Relinking Resolve after a move
- What: When a project's folder has moved to follow a rename, the clips of the project open in Resolve are relinked from the old place to the new one. If Resolve is closed or open on another project, the relink waits and is tried again at most every 5 minutes, for up to 30 days, until it succeeds.

### 02-018: An editor can ask for the originals of chosen clips from inside Resolve.
- Where: resolve-on-the-editors-computer / Asking for originals from inside Resolve
- What: From Resolve's own menus an editor can ask to bring down, or stop bringing down, the originals of the clips chosen in the media pool, of a range of the timeline, of the clip under the playhead, or of the whole timeline. The app picks the request up within about 2 seconds.
  - Each clip is turned into its file. A multicam or compound clip has no file of its own and is turned into its angles' files only if the app has already seen it on a timeline in Resolve this session; otherwise it cannot be matched. A file path in the studio's drive form, or in the computer's own form (a Mac's mounted drive), both work.
  - Each file is matched to the ticked project that holds it. Files in no ticked project, and files that are not camera originals (proxies, unfinished, hidden or non-video files), are counted and reported, not asked for. Files in an upload-only project are sent so that the server's refusal reaches the editor.
  - The pick is recorded on the server for that project and this computer, and an accepted pick starts the download at once.
  - If the server cannot be reached or fails, the request is kept and tried again; parts already answered are not sent twice.
  - Limits: up to 10,000 clips in one request. A request not answered within 1 hour is dropped unanswered, and a malformed request is dropped unanswered; in both cases nobody is told.

### 02-019: What the editor is told after asking for originals from Resolve.
- Where: resolve-on-the-editors-computer / Asking for originals from inside Resolve
- What: One notification per request, built from these parts in this order:
  - each distinct refusal sentence from the server, word for word and first (for example the refusal of a pick in an upload-only project);
  - for any other refusal: "The server refused part of this request (HTTP {status})." or the same followed by the server's own reason;
  - when adding worked: "Bringing {N original(s)} to this computer ({size}). The tray shows progress." (the size is left out when the server gives none);
  - when removing worked: "Stopped bringing {N original(s)}. Files already on this computer stay.";
  - "{N clip(s)} could not be matched to a file (a multicam or compound clip this computer has not seen on a timeline yet).";
  - "{N clip(s)} is/are not in a project this computer syncs.";
  - "{N clip(s)} is/are not camera originals.";
  - with no refusal and no success it starts "Nothing was queued:" (or is just "Nothing was queued." when there is nothing else to say).

### 02-020: Originals an editor picked are brought down to their computer, without ever slowing uploads.
- Where: sync / What syncs where
- What: For each project ticked with the full mode, the server holds a list of originals picked for this computer (picked on the dashboard or from Resolve, 02-018). Those files are brought down; nothing else is.
  - An upload-only project brings nothing down even if originals are picked for it.
  - Up to 20,000 picked files per project; beyond that the first 20,000 are taken. A pick that names the same file twice (in any letter case or Unicode spelling) counts once.
  - Whatever is picked, only camera originals are ever fetched: never a hidden file, a file inside a Proxy folder, an unfinished or temporary file, a file half-way through a move, or a file that is not video.
  - A file already on this computer is never overwritten: at the same size it counts as here, at a different size it is left alone. Un-picking a file stops it coming but never deletes what is already down.
  - A picked file is looked for on the server in any letter case or Unicode spelling, and fetched in the server's spelling.
  - Bringing originals down runs alongside uploads and never holds them up.
  - A change to the picks is acted on promptly; otherwise the list is looked at about every 2 minutes. "Sync now" starts it at once. A picked file that was not on the server is looked for again after about 15 minutes.
  - Downloading is interrupted when a file in it is un-picked, and when any stop in 02-021 begins. A download that runs for an hour finishes the file in flight and carries on with the rest.
  - Files brought down this way are not sent back up.

### 02-021: What the editor sees while originals are coming down, or are not.
- Where: sync / Saying truthfully what the sync is doing
- What: The app shows, for originals coming down:
  - while working: "Bringing originals: {done} of {total}, {size} to go", with files in flight, files waiting, bytes, speed and time left, updated about every 2 seconds;
  - all present: "all {N} asked-for originals are here";
  - nothing to fetch because files are missing on the server: "{N} asked-for originals are not on the server";
  - finished: "brought {done} of {total} originals down";
  - paused (checked continually, so a download in progress stops within about a second): "NOT DOWNLOADING ORIGINALS: syncing is stopped on this computer" (a studio-wide or local stop), "NOT DOWNLOADING ORIGINALS: syncing is paused" (the editor's pause), "NOT DOWNLOADING ORIGINALS: the sync drive is not connected", "NOT DOWNLOADING ORIGINALS: {reason}" when the destination is refused by the same rules that guard b-roll fetches, and the disk messages of 02-011;
  - failed: that the server could not be listed to find the originals, that some originals did not arrive (with how many), or the transfer's own failure line.

### 02-022: Each kind of transfer tells the editor and the dashboard what it is doing, in the same terms.
- Where: sync / Saying truthfully what the sync is doing
- What: Uploading, downloading proxies and downloading originals each show, on the app and in what the computer reports to the dashboard: whether it is idle, working, failed or paused, and since when; files waiting and files in flight; the last failure, as a sentence; when it last finished cleanly; a one-line description of what it is doing; the project it is working on; bytes done and to do, speed and time left; and a row for each file in flight with its name, direction, bytes, percentage, speed and time left (and its project), refreshed about every 2 seconds.
  The dashboard marks a transfer as stuck when it says it is working but has moved nothing; a slow transfer that is still moving bytes is never called stuck.
  A transfer that cannot start, stop or report never takes the app down with it; the problem appears as its last failure.

### 02-023: An editor can make the app sync right now.
- Where: editor-app / The tray or menu-bar icon and its menu
- What: "Sync now" starts uploading, downloading proxies and checking for picked originals at once instead of waiting for the next time.

### 02-024: Each project gets a share of time in turn, and a large upload carries on in the background while the next project has its go.
- Where: sync / Stuck, slow and fair transfers
- What: Projects are synced one after another, each for up to about 10 minutes at a time (a per-computer setting, never less than 1 minute). When the time is up, files in flight finish, nothing new starts, and the editor is told how many files were transferred and that it paused at the project's time limit; the rest goes on the project's next turn. Uploads go newest file first.
  An upload still running when its project's time is up (10 seconds of grace) is not stopped, because an upload that is cut off cannot resume and would start again from nothing: it carries on in the background while other projects take their turn. The editor then sees "uploading {name} ({percent}%)" for one file or "uploading {N} file(s)" for several, and the upload still counts in the speed, time left and in keeping the computer awake. When it was handed over the editor sees that some files were transferred and the rest are still uploading in the background. A background upload that fails is never shown as an error; whatever did not land goes again on the next turn. On by default; a per-computer setting.
  Fixing media and gathering media into the project (actions elsewhere) always wait for their upload instead.

### 02-025: Signing out, quitting, updating or a studio-wide stop ends transfers calmly; an upload cut off this way starts again later.
- Where: sync / Uploads that cannot resume, shutdown and sleep
- What: Signing out, quitting the app, an update, a studio-wide stop or the editor's pause end every transfer in progress, including uploads carrying on in the background. This is shown calmly, as stopped mid-transfer or stopped before it started, never as a failure. An upload cut off this way starts again from the beginning the next time. A background upload in a project that is about to follow a rename on the server is ended first.

### 02-026: When the sync drive is missing, nothing syncs and the editor is told to plug it back in.
- Where: sync / The sync drive
- What: If the folder holding the editor's synced tree is not there (an external drive unplugged), no transfer starts at all, so nothing can ever be written to the computer's internal disk instead. The app shows "local root missing (drive disconnected?)" and warns once per disconnection: "If this is an external drive, plug it back in; syncing resumes on its own."

### 02-027: When the sync drive stops answering, the editor is told once, and told again when it is back.
- Where: sync / The sync drive
- What: Before the app starts watching the drive for new files, it checks that the drive answers within 5 seconds; a drive that hangs would otherwise freeze the app. While it does not answer, the app tries again after 1 minute, then less and less often, at most every 15 minutes, and uploads continue on their usual schedule meanwhile. The editor is told once each way:
  - "The sync drive isn't responding, so CCSync can't watch it for new files. Disconnect and reconnect the drive, or restart the computer. Everything else is still running."
  - "The sync drive is responding again. CCSync is watching it for new files."

### 02-028: A transfer that has stopped moving is ended and shown as failed, and the dashboard is told.
- Where: sync / Stuck, slow and fair transfers
- What: Transfers are watched about every 30 seconds.
  - One that has moved nothing (no bytes, no files) for 4 times the project time share or 15 minutes, whichever is longer (40 minutes with the 10-minute default), is ended and shown as failed with "made no progress for {N}s - killed".
  - One that has run more than twice the time share plus 5 minutes (25 minutes by default) and has moved nothing in the last minute or so is ended with "did not exit after {N}s - killed".
  - A transfer still moving bytes is never ended for taking long.
  The last such stop on a computer (which direction, how long, whether it was ended, when) is reported to the dashboard, without the sentence, until that direction next finishes cleanly or 24 hours pass, and it survives a restart of the app.

### 02-029: How a sync's ending is shown when it did not simply succeed.
- Where: sync / Saying truthfully what the sync is doing
- What: A clean ending shows how many files were transferred. A failure shows the most useful error line from the transfer, without generic notices, or that it ended with a failure code. Passing retries inside a successful sync are not shown. Running out of the project's time, reaching the removal limit, being stopped, or a safety stop are each shown as described in their own items, never as a failure.

### 02-030: Unfinished upload pieces left on the server are reported, never deleted.
- Where: sync / What is owed
- What: Partly uploaded files left in a project on the server (other than ones this computer is writing right now) are counted and reported for each computer: how many, their total size, and up to 20 examples. They are left in place deliberately; an admin removes them by hand to get the space back.

### 02-031: Proxies and originals keep the exact name they have, including full-width punctuation.
- Where: sync / Names
- What: File names cross in both directions exactly as written, including full-width punctuation such as a full-width question mark. A name holding a character Windows forbids fails visibly instead of being renamed. Names are matched without regard to letter case, and a Mac's file names (in the decomposed Unicode spelling) match the server's.

### 02-032: A project folder moved or renamed by the editor on their own computer is noticed and named, not followed.
- Where: sync / Project folders on an editor's computer
- What: The app remembers that each ticked project's folder was present. A folder never seen yet on this computer is an ordinary first state ("project dir not yet local: {path}"). A folder seen before and now gone is shown as a failure: "Your project folder for {name} is not where CCSync expects it. Did you rename or move it?", and when a folder carrying the same project's identity is found elsewhere among the projects, " It looks like it is at {path} now." Nothing is moved by the app. Up to 20 such folders are reported to the dashboard. It clears when the folder is back. If two folders claim the same project, the first found is taken.

### 02-033: The editor is told when a newer local version of a file will never upload because the server already has that name.
- Where: sync / What is owed
- What: Each project is checked for files that exist on both sides with the same name but a different size. Such a local file will never upload (02-001). It is reported with an example and the two ways out: rename the local file, or have an admin remove the server's copy. The app can list up to 20 such files with this computer's size (the server's size is not known). Projects no longer ticked, or whose folder is gone, drop out of the report.

### 02-034: Files dated in the future are reported, because they will not upload until that date.
- Where: sync / Clocks and file age
- What: A file the app would upload whose date is more than 5 minutes ahead of this computer's clock does not upload until then. These are reported with how many, examples, the earliest such date and when it was checked, with the advice that a few hours ahead clears by itself and further ahead needs the file's date reset.

### 02-035: Project folders on the computer that are in no sync plan are reported, never deleted.
- Where: sync / Project folders on an editor's computer
- What: Project folders on an editor's computer that are not ticked there are found and reported: how many, their total size, and up to 20 of them. Nothing syncs them and nothing deletes them. The check runs at most every 15 minutes and not at all while the computer's plan is empty or unknown (an empty plan is never a warning).

### 02-036: Before a project is removed from a computer, the product checks that removing it cannot lose work, and refuses on any doubt.
- Where: sync / Deletions and removing a project
- What: Removing a project's copy from a computer is only allowed when the product can show nothing would be lost. It checks:
  - files not yet on the server, counting files copied in moments ago and files dated in the future (up to 20 named);
  - files with the same name as the server's but a different size;
  - in an upload-only project, files edited here since they were uploaded (same size on the server but newer here);
  - files nothing would carry up (names the upload refuses, or unfinished download files), and future-dated files.
  Proxy folders, the recovery folder, operating-system litter, unfinished files and empty files are not counted. Any check that cannot be completed counts as "could not tell", and the copy is not deleted.

### 02-037: Every file copied up or down is recorded in the transfer history.
- Where: dashboard / Transfers and the queue
- What: Each file copied, in either direction, is reported to the dashboard with its project path, direction and time. Up to 200 files from one sync and 400 waiting to be reported are kept; beyond that some go unrecorded. Files moved into the recovery folder are recorded as removals.
