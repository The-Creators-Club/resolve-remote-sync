# Extract of inventory section 27

## Items

### 27-001: The owner can release a new version to the studio with one command, which checks everything first, updates the server, publishes the new app for editors, makes it the one offered, and updates the owner's own computer.
- Where: releases-and-updates / Making and publishing a release
- What: One release run, started by the owner at their own computer, does in order: the checks below; updates the studio's server and waits for it to come back reporting the new version (up to about a minute and a half; if it does not, the run stops and says to investigate before continuing); builds and tests the editor app; publishes the editor app and the installer to the studio's server and makes them the version offered to every computer; installs the new app on the owner's own computer; and finally checks that what is running here is what was released. Every line the run prints is labelled as coming from the release; a failure is printed in red with its reason, a warning in yellow. The run ends with a rollout line per platform: "N of M computers on <version>", how many are behind, and how many are refusing it. Options the owner can choose:
  - update only the server and stop;
  - release but leave the owner's own computer as it is ("Editors get the offer; this computer stays as it is");
  - skip the slower checks (the build's own checks still run);
  - re-create the server from scratch so deeper changes take effect;
  - also publish to the vendor's feed for customer sites (off by default; when off, the owner is told that customer sites do not have this build and given the exact way to send it there);
  - one line of "what changed" (see 27-011).
  The result is one of: done; refused or failed (nothing past that point happened); or published but held back (27-006).
- Flag: several ways in: the same publishing into one studio's server can also be done for a Mac build from a Mac, for the Mac installer from a Mac, and for any single already-built file by a separate publishing command (see 27-Q1).

### 27-002: A release refuses to start, before anything is changed, when something it needs is missing or wrong.
- Where: releases-and-updates / Making and publishing a release
- What: Refused before anything is deployed, each with a sentence saying what to do:
  - the secrets a release needs are not loaded in this window (it names the missing ones and says how to load them, and never to store them permanently in the system);
  - no server address, or no admin account to publish as ("this copy no longer has a server address or an admin account built in"); it then prints which server and admin it is releasing to;
  - the source has uncommitted changes ("a build with uncommitted changes must not reach the fleet"), listing each; the owner may override deliberately, and such a build is stamped as dirty (see 27-007);
  - the editor app's version, or the installer's version, is ALREADY published on the server ("bump the version"), because a second upload of the same version with different bytes would be refused;
  - no code-signing identity is set up, unless the owner has said an unsigned build is acceptable;
  - the release key's passphrase is wrong (asked once, hidden, before anything moves; see 27-016);
  - any of the automated checks fail;
  - the live server is older than the oldest server this editor app works with ("Deploy the server first"), unless the owner overrides, in which case the build is published but "held back there, never offered". If the server's version cannot be read, a note says the order was not checked.
  A note (never a refusal) reminds the owner when the release key has no recorded backup.

### 27-003: A release that stopped part way can be resumed from where it got to.
- Where: releases-and-updates / Making and publishing a release
- What: The release remembers after each step how far it got (checks, server, build, publish, made current, this computer) and what it made current. Resuming skips every step already done and says how far the last run got. Resuming with nothing recorded is refused ("run the release normally"); resuming when the version has changed since is refused ("that is a new release, not a resumption"). If the record cannot be written, the owner is warned that resuming will not work for this run. An installer already built is reused on resume only when it is newer than everything it is built from.

### 27-004: After a release, the owner is told whether this computer is really running what was released.
- Where: releases-and-updates / Pushing updates and seeing who has what
- What: The last step of a release installs the new editor app here and then compares source, build, installed copy and running program. The release FAILS (even though the build is already published and current for the fleet) when the installed version is wrong, no app is running, the running app is not the installed one, or a newer app is on disk than the one running; the message says the build is "PUBLISHED and CURRENT for the fleet but is NOT installed here". Other differences are reported as advice only.

### 27-005: The owner can ask, at any time and without changing anything, which build is actually running on this computer, on the server, and on every computer in the fleet.
- Where: releases-and-updates / Pushing updates and seeing who has what
- What: A read-only report, each line marked OK, DRIFT (something differs) or "?" (not checked, never shown as OK). It covers:
  - this computer: the version in the source, the built app (when, size, whether it was built with its checks, whether it is older than the source it came from), the installed app (and how its version was found), whether the app is running and is that installed copy, and whether it starts by itself at sign-in;
  - the server: its live version against the source, with what to do if it differs; which kind of NAS it is on;
  - signed in as an admin: how the server's code is being run; the current and all published Windows versions; whether the current build carries the release signature ("UNSIGNED: computers that verify will REFUSE it") and the operating system's code signature; the current installer; the Mac builds as advice;
  - rollout per platform: "N of M on <version>", each computer behind (person, computer, version, how long since last seen), how many went back to an older version, how many attempts failed, how long the version has been current, and each computer refusing it with its reason;
  - Timeline Cards (where the site has it): which change is live on the server and whether newer or uncommitted work exists that is not on the server ("THEY ARE NOT ON THE NAS. Commit them and release again"); no record of a deploy is "NOT CHECKED, not OK";
  - a verdict: OK when the installed version matches the source; otherwise "anything you 'verified' against this source has NOT been tested on this computer", with what to do.
  A follow mode re-reads every minute and prints one line per platform until "every computer that reports is on its platform's current build"; it ends if the admin session expires, after five failed reads in a row, or when the server gives no rollout numbers.
- Flag: several ways in: the rollout numbers also appear at the end of every release (27-001) and on the server's own update settings.

### 27-006: A new build can be published but held back, offered to nobody, and tried on one computer before it is offered to all.
- Where: releases-and-updates / Trying a build on one computer first
- What: A published build is either held back (stored, offered to nobody) or current (offered to every computer of that platform). When the server agrees to store a build but refuses to make it current, the owner is told both builds are "published and held back", and to push it to one computer, leave it running, then make it current from the server's update settings or resume the release. A Mac build published from a Mac gets the same advice. A newly current build is OFFERED to editors on their computer's next report, not forced.

### 27-007: A build with uncommitted changes can never be quietly made the version every computer is offered.
- Where: releases-and-updates / Making and publishing a release
- What: A build made from uncommitted work is stamped as dirty in its version. Releasing it at all needs a deliberate override; making it current needs a second, separate override, and without it the build is published held back. Publishing to customer sites refuses a dirty build outright unless overridden. The Mac installer warns "do not hand this installer to an editor" when the app inside it was dirty.

### 27-008: Nothing reaches editors or customers unless the automated checks passed on that exact change.
- Where: releases-and-updates / Making and publishing a release
- What: Every change is checked automatically on Windows and macOS (and nightly). A build made without running its own checks is accepted for publishing only when the automated checks passed on exactly that change, the change is clean, and it is part of the main line of work (a change removed from the main line after it passed is refused: "a rewrite can remove a change the checks went green on"). Every build must also start and pass its own self-test within three minutes before it can be published. A check that was skipped is not a pass. Each refusal can be overridden only by a deliberate, named choice.

### 27-009: Version numbers are three plain numbers; one version always means one set of bytes.
- Where: releases-and-updates / Version numbers
- What: An editor app version must be exactly three dot-separated numbers ("the server refuses to publish anything else"). The installer has one version that must agree everywhere it is stated, on Windows and macOS. Publishing a version that is already published with different bytes is refused (bump the version); publishing the identical bytes again is "already published and byte-identical: nothing to upload". A released server version is never rebuilt: a second build of the same version is refused ("Bump the version"). Versions are compared number by number.

### 27-010: Each build says which oldest server it works with, so a computer is not offered a build its server cannot support.
- Where: releases-and-updates / Offering an update to a computer
- What: An editor app build can name the oldest server version it needs. Releasing to a studio is refused while the studio's server is older (27-002). Publishing to customer sites is refused when the build needs a newer server than any server update in the feed, and the feed's daily freshness check (27-022) reports a current app that needs a newer server than the current server. Before this rule could be signed into what computers check, every computer had to be on a recent enough build; the release refuses to turn it on while any computer is behind, any platform's count is unreadable, or a platform has computers but no current build, naming each straggler.
- Flag: dormant: the ordering is checked by the vendor's own tools, but carrying it to customer sites and to editors' computers is off unless deliberately switched on for a release (see 27-Q3).

### 27-011: A release can carry one line of "what changed", shown to the editor in the update offer.
- Where: releases-and-updates / Offering an update to a computer
- What: The owner may give one line of notes; extra spaces are collapsed and it is cut to 300 characters. It is shown in the editor's update dialog as advice; it is not part of what the computer verifies before trusting the build.

### 27-012: Every build offered to a computer is signed with the vendor's offline release key, and a computer only trusts keys already present in the build it is running.
- Where: releases-and-updates / Signing and trust
- What: Each published package carries a signature over what it is: kind (editor app, installer, server update), platform, version, file name, checksum, size, its downgrade floor (27-013), when it was published, and whether the file itself carries an operating-system code signature; optionally the oldest server it needs and the processor it is for. The key that signs never leaves the owner's release computer and is never used by the automated builds. Computers trust only the public keys built into the version they are already running. So:
  - a build carrying no trusted key would refuse every update permanently: such a build is refused at release;
  - a build is refused when the key that will sign it is not among the keys built into it ("every editor would refuse the build you are about to publish");
  - the server refuses every publish until it is told the public key(s);
  - changing the key costs an overlap release: first a build that trusts both old and new keys, signed with the OLD key; only once that is everywhere can the new key sign. Publishing a build signed by a key the current build does not trust is refused unless overridden, with this explained ("the override does not perform a rotation").
  A build that names a processor is offered only to computers with that processor; otherwise to every computer of the platform.

### 27-013: Every build sets a downgrade floor, so no computer can be taken back below it.
- Where: releases-and-updates / Rolling back and withdrawing a build
- What: Each signed build names a minimum version; a computer raises its own floor when it sees one and never installs anything older. The floor normally trails the current build by a release and is tracked per kind and platform. Refused: a build with no floor ("any older signed build could then be made current by a replayed list or a compromised admin session"), unless deliberately allowed; a floor above the build's own version (the build would refuse itself and every corrected republish); a floor lower than one already published for that kind and platform; for apps and installers, a floor above the version currently offered. Republishing an older build above the floor is how a version is rolled back.

### 27-014: Builds that are not code-signed by the operating system's rules meet the operating system's warnings, and the release says so.
- Where: releases-and-updates / Facts about Windows, macOS and the NAS that bite an update
- What: Facts the release tells the owner and must respect:
  - Windows: an app without a valid code signature meets the SmartScreen warning on every fresh install and may be quarantined by antivirus. Making such a build current needs a deliberate override; the release prints a boxed "UNSIGNED BUILD" warning. Code signing uses a timestamp so signatures outlive the certificate.
  - macOS: an app without a Developer ID signature gets Gatekeeper's "cannot be opened because the developer cannot be verified". On Apple silicon an app with no signature at all is killed at launch, so that is refused. A signed but not notarised build is warned about. A single bare program cannot hold a notarisation ticket (only warned); the installer bundle must be signed throughout, and a nested unsigned or modified part, or a zip that broke the signature, is refused ("Do NOT publish it"). A Mac build that is not for Apple silicon is warned about.
  - A Mac installer handed over by hand (USB, AirDrop, copy) arrives quarantined and needs System Settings > Privacy & Security > "Open Anyway".
  - Each Windows program carries its file details: product name CC Sync, the vendor's legal entity as company and copyright holder, a description, and its version.

### 27-015: A Mac build is made and published separately, and the owner is told when Windows and Mac are out of step.
- Where: releases-and-updates / Making and publishing a release
- What: The Mac app and the Mac installer are built on a Mac. Until that happens, Mac editors stay on their old build. Every release compares the Mac version offered by the server with the source: "level with this source", a warning with what to run on the Mac, "no Mac app published yet", or "not checked". This never changes the release's result. Publishing from the Mac needs an admin's sign-in (27-018). After a Mac publish: Mac editors are offered (not pushed) the update on their next report. A Mac's installer download serves the published Mac installer; the older Terminal route to install still exists.

### 27-016: The release key is protected by a passphrase, can be backed up, and the dashboard asks the owner to confirm a backup exists.
- Where: releases-and-updates / Signing and trust
- What: The release key is a private key on the owner's release computer. The owner can: create one (never overwriting an existing one by accident: "overwriting it orphans every build the fleet was ever offered"; a forced replacement keeps the old one aside); protect it with a passphrase of at least 12 characters (typed twice; the protected copy is verified before the unprotected one is destroyed); see its public half and a short id; see every key a rotation in progress involves; check that it unlocks; and back it up to a file or print it. Backing up records when and where, and tells the owner to confirm "I have backed it up" on the dashboard. An unprotected key prints a warning every time it is used. A wrong passphrase or altered file: "cannot unlock: wrong passphrase, or the key file was altered". A damaged key: restore it from the offline backup. No key: how to create one. After creating a key the owner is told to protect it and to back it up now, with two offline copies and the passphrase written down elsewhere.

### 27-017: The owner's release secrets are kept encrypted for that one account on that computer and loaded into one window only.
- Where: accounts-privacy-legal / How secrets and keys are kept
- What: The secrets a release needs (the NAS admin password, the server's own secrets, an optional ingest secret) are stored encrypted so only the owner's account on that computer can read them, in a place only that account and the system can open. The owner saves them once (hidden typing; an existing value is kept on Enter, a blank optional value is never stored), loads them into one window when needed, or clears them. Loading also works out the public key(s) the server must trust from the release key, saying when a key rotation is under way. Only the names loaded are ever printed, never values. They are never set as permanent system-wide values.

### 27-018: Publishing into a studio's server needs an admin's sign-in, and passwords are only ever typed or piped, never put on a command line.
- Where: releases-and-updates / Making and publishing a release
- What: Every way of publishing into one server signs in as an admin first; a non-admin account is refused ("is not a dashboard admin"). The password is asked once with hidden typing, or read from one line of input; it is never accepted from the command line or the environment. An empty password is refused; a password or user name with a control character in it is refused, saying where ("retype it rather than pasting"); a paste wrapper the terminal added is removed. The upload is checked against the file's checksum before it is sent. Before signing in, the tool checks whether that version is already on the server and refuses if so. Nothing is published if the release key is missing. The answer names the build CURRENT or "held back (make it current from the server when ready)", and a read-back of the server's package list shows the row. No publishing call follows a redirect; an unreachable server is refused with "check it is up, then run again".

### 27-019: The vendor publishes builds for every customer site through one signed feed, which customer servers read.
- Where: releases-and-updates / Customer sites and the vendor's release feed
- What: The feed is a signed list of builds (server updates, editor apps and installers per platform, and large shared model files), with which version of each is current, the exact server image customers should run, and a recall list. Customer servers check the whole list's signature, and each build's, against the keys they trust. Rules when publishing:
  - a live feed that does not verify is refused ("either the feed was tampered with, or it was signed by a key this copy does not know"); a feed that cannot be read is refused rather than assumed empty; an absent feed is the first publish;
  - publishing never drops a build already published, except one deliberately recalled; anything that would is refused, listing it;
  - the list's timestamp never goes backwards; if the published one is more than a minute ahead of this computer's clock, the owner is warned to fix the clock;
  - making a build current needs: a named, clean change, the automated checks green on it, and that change on the main line ("REFUSED" otherwise);
  - a recalled version cannot be published again;
  - an upload that fails part way says the feed "may now be PARTIALLY updated; run again";
  - every build and the list are checked straight after signing.
  A large shared file (the music model) carries a checksum that the editor app compares with the one built into it.
- Flag: several ways in: the feed can be published from the studio release (27-001), from the newest green automated build (27-020), as part of a customer release (27-021), or by hand (see 27-Q2).

### 27-020: The vendor can publish the newest automatically built and checked editor app and installer to customer sites with one command.
- Where: releases-and-updates / Customer sites and the vendor's release feed
- What: For each of the Windows and Mac app and installer, takes the newest build that the automated system produced and checked on the main line, verifies the file against its own record, and publishes it to the feed. Refusals: the build's change is no longer on the main line; its checks did not pass; the file does not match its record; it is dirty; it was built untested and nothing vouches for it; it needs a newer server than any in the feed (unless overridden); its version is older than the newest in the feed (unless overridden). A build no longer available is skipped and said so. Already on the feed: "nothing to do", or the pointer is moved to it; it never moves the pointer BACK (rolling back is done by naming the version to make current). It can be narrowed to one kind or platform or one change, tried without publishing, and told to make the build current. At the end it says when customers get it: sites that follow "current" take it on their next check (daily, and about 10 seconds after their server restarts), subject to their own soak wait; sites set to "manual" need their admin to check for updates and publish. It prints a ready-to-run recall line for every build it published.

### 27-021: A customer release sends the server update, the editor apps and the installers out together, from one checked change, only after a day's trial in the studio and a second person's approval.
- Where: releases-and-updates / Customer sites and the vendor's release feed
- What: Refused, in order, unless every condition holds: the change is on the main line; all automated checks passed on it, including the server's own (a check that was skipped leaves the run green but "nothing has tested this server"); its server version is not older than the newest in the feed ("that is a rollback, not a release"); all builds for it exist; its version label is not already on another change ("a released label is never moved"); a second person's approval is required before the server image is released (if that approval step is not protected, refused); the studio's own server has run exactly this version and change for 24 hours (the first time it is seen the clock starts and the release is refused, saying "run again in 24 h"; later runs say how many hours remain; a different version or unknown change on the studio is refused). Then the server image is built, waited for (up to an hour) and approved, the server update is published and made current with the exact image, then the apps and installers. If the apps fail, the owner is told the server half is already out and how to send the rest. A fresh customer installation is pinned to the exact image released. A trial run checks everything and changes nothing.

### 27-022: The vendor is told every day when the customer feed has fallen behind.
- Where: releases-and-updates / Customer sites and the vendor's release feed
- What: A daily check reads the signed feed and reports it stale when: no server update is current; the current server is more than 3 releases behind the newest in the source (a different major or minor version always counts as far behind); the current server names no exact image; a current app needs a newer server than the current server; or the feed is more than 45 days old while a newer server exists. A feed that cannot be read or does not verify is "NOT CHECKED", never fresh, and counts as a failure.

### 27-023: A build that was offered can be recalled, with a reason every customer server shows beside it.
- Where: releases-and-updates / Rolling back and withdrawing a build
- What: Recalling a build needs a reason (refused without one: "every customer server shows it beside the withdrawn build"). The build is removed from the list and from being current. If it was current and nothing else is named current in the same act, the recall is refused unless the vendor deliberately leaves nothing current, because servers would otherwise take the highest remaining version, possibly a newer held-back one; the vendor is told to name the newest version below the withdrawn one. Making a version current again is a pointer move only; it is refused for a recalled build, for a version the feed does not carry (listing what it does carry), and for one signed by a key the current build does not trust.

### 27-024: Customer servers take their code updates as signed bundles, and every released server image has proved it boots.
- Where: releases-and-updates / The server updating itself
- What: A server update carries the server's code and the documents customers read on its help pages; a bundle that would leave the help page saying it is not installed, or the server with no code, is refused. A bundle made from uncommitted work is refused unless overridden. The bundle lists a checksum for every file and can be verified ("VERIFY OK" / "VERIFY FAILED"). If the studio's server runs from an image and is older than the source, a release explains how to update it over the air or roll back. Every server image released has started from empty with fresh secrets, answered its health check with the right version, and shown its set-up page, before it is released; released images are signed so anyone can verify them, and each customer installation is pinned to exact images.

### 27-025: Customers receive only components whose licences allow it, and every program carries the licence texts of what is inside it.
- Where: accounts-privacy-legal / Third-party licences and what customers receive
- What: Before release, every component in each thing conveyed to customers (the editor app on Windows and macOS, the server, and the optional YouTube add-on) is checked: copyleft (GPL, LGPL, AGPL, SSPL) or an unknown licence fails the release unless it has a recorded exception with a reason that applies to that product. Each program is also refused if it contains anything not on its approved list, any file nobody accounts for, or any component without its licence text inside the program. Each program carries one licence file listing its contents and every text (including the runtime it is built on); the installer carries everything the app carries. A customer-facing third-party notices document is generated from the same facts: issued by the vendor, stating CC Sync is proprietary under its licence and each component's own licence prevails; licences needing attention; components per part of the product; and the outside programs the installer fetches, with their versions and checksums. A hand-written part of it is kept as written.

### 27-026: An admin can hand heavy work to the fleet, follow it, see why it is waiting, and cancel or retry it from a command line.
- Where: fleet-jobs / Choosing who runs what
- What: Admin only ("a job is work on somebody else's computer"); same sign-in rules as 27-018. Paths are always a place (the editors' tree, the vault of transcripts and cut lists, or media) plus a path inside it; a full path, a drive letter, ".." or an empty path is refused.
  - Submit: a transcription (optionally also telling speakers apart; it needs a computer with that place, able to transcribe, with at least the stated graphics memory, default 6 GB), or a small proxy, an audio extract or a waveform for Timeline Cards (with where to write it and the name the page knows it by). Conforming a cut and editing in Resolve can never be submitted. Options: a priority; "now" (offered to every able computer at once, skipping the idle wait, cooldown and ranking grace); only on a named computer. The receipt says the job number, where it is, and a yes/no per computer with the reason.
  - List jobs (open by default, or queued, running, done, failed, abandoned; 50 by default) with attempts, the computer holding it and the last error.
  - Why: the summary, the reason, whether it is temporary ("the fleet will get to it"), and each computer's yes/no with its reason.
  - Cancel: "is over" at once, or "will stop on <computer>'s next report; it is not retried anywhere".
  - Retry: "is on the queue again as #M".
  - Queue: queued, running and pinned counts, oldest wait, per kind running against its limit ("AT THE LIMIT"), and whether the server itself takes jobs the fleet gives up on, or why not.
  - Watch: a line whenever state, computer or progress changes; on success the time taken, speed against real time, and the files written (up to 20) or "nothing to do, it was already made"; failed or abandoned shows the error; it gives up watching after an hour by default ("still <state>").
- Flag: several ways in: the same jobs are seen and acted on from the dashboard (see 27-Q4).

### 27-027: The dashboard can be installed on an Android phone as an app that opens it full screen.
- Where: dashboard / Phones and the installed app
- What: An Android app is made for one dashboard address; it opens that dashboard full screen in the phone's browser engine, with the dashboard's own name, colours, start page and icons. It sends no notifications and falls back to a browser tab if needed; it works on Android 5 and later. When the app is made, the owner is given its package id and its signing fingerprint, to enter in the dashboard's settings, and can check that the dashboard declares them. An app made without the studio's own signing key gets a throwaway test key, with the warning "Do not ship this app: its fingerprint changes on every build, and an app signed with a new key cannot update an installed one."

### 27-028: An admin can check whether a dashboard address lets a phone install the dashboard as an app.
- Where: dashboard / Phones and the installed app
- What: Given an address, it checks in order and stops at the first failure, one line each (OK, FAIL or SKIP): the address is secure (https; otherwise "no secure context: no offline worker, no install prompt, no Android app"); its certificate is accepted; the app description is readable signed out and has a start page and icons ("the browser will not offer to install it"); the offline worker is served and allowed; the Android declaration is readable (empty passes: "no Android package configured yet"); the address answers as the dashboard, with a version ("whatever is behind this address, it is not the dashboard"); every sign-in cookie is marked secure, else it names them and the fix. Ends "STOPPED at <check>. Fix that and run this again."

### 27-029: Every dashboard page works at phone and tablet width.
- Where: dashboard / Phones and the installed app
- What: Every page is measured at phone width (390 pixels) and tablet width (768). A page fails when it scrolls sideways as a whole or any part of it (other than a deliberately scrollable table or a form field) runs past the edge. A warning is raised when a button, link or field is smaller than 44 pixels either way, when a page has nothing to tap, or when any text is smaller than 12 pixels.
- Flag: dev only: this is a check the builders run against invented data, not something a person runs.

### 27-030: The installed Timeline Cards app opens with no network.
- Where: cards-editor / Working offline, connections and several devices
- What: Proven by a builders' test on a phone-sized screen. On the first online visit the installed app saves its landing page. With the server not answering at all, the saved episode picker appears within 10 seconds with its episodes listed; with the connection refused or the phone offline it appears within 2 seconds; opening from the home screen (with extra words in the address) finds it within 2 seconds. After an update from an older installed version, one online visit is enough for the next offline launch to show the picker. Opening an episode saves that episode's page; once a cut list has been downloaded to the device, the offline picker lists it and tapping it opens the episode offline.
- Flag: dev only: the test itself; the behaviour it proves is the product's.

### 27-031: Every icon of the product is drawn from one brand mark.
- Where: whole-product / Windows, text and names
- What: The tray icon, the program icons, the dashboard's browser icons, the phone home-screen icons (including ones a phone may crop to a shape) and the b-roll page's icon all come from one white brand mark. At small sizes the mark is made stronger so thin strokes stay visible. A check reports any icon that no longer matches the mark.

### 27-032: Heavy b-roll and music indexing can run on a separate machine with a graphics card, and it never starts spending on its own.
- Where: broll / Describing and indexing clips
- What: The indexing work (describing b-roll clips, transcribing them, analysing music, and working through the queue of music uploads) can run on a machine with a graphics card, apart from the server. Started with no instruction, it only prints how to use it, so nothing is spent by accident. Describing clips costs money for each call to the assistant. It refuses to start without its settings file ("mount one ... or say where it is") and without the library location. Only the music queue step may write to the library.

### 27-033: The vendor can measure how fast footage moves between an editor's computer and the NAS, for each kind of transfer, and whether the network path is direct.
- Where: sync / Speed and routes
- What: A measuring tool for the vendor. It makes test sets (a few large incompressible video-sized files; hundreds of small files in nested folders), then times each way of moving files, with each setting, for footage going up, proxies coming down and everything else both ways, plus the raw network ceiling, repeating each. Every timed transfer must move at least 99 % of the bytes or it is a failure; a sample of up to 3 files is re-checked at the destination. It never deletes anything outside its own scratch folders unless told to, and then warns for the whole run. Passwords never appear in its records. It reports, per kind of transfer, the fastest setting with caveats (not verified, measured on one machine only, repeats spread over more than six hours), and a comparison with a cloud service's advertised speed marked "INTERNAL ONLY, do not reproduce in customer-facing material". It also says whether the private network between the editor and the studio is direct or relayed; a relayed path is warned about, with "check UDP forwarding / NAT traversal before trusting any transfer numbers". A self-test runs the whole thing on one machine.
- Flag: dev only
