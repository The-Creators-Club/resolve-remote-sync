## dash-api-2
- Verdict: CONFIRMED
- Duplicate of: none
- Reasoning: I could not refute the permanence. `record_inventory_error` (db.py:8897) upserts only `walked_at` and `last_error` and deliberately does not touch `tree_sig`; the collector's phase 1 skips the whole walk when `sig == db.nas_inventory_sig(conn, pid)` (collector.py:1750), and `last_error` is cleared in exactly one place - the successful `replace_nas_media` upsert (db.py:8734, `last_error=NULL`). The contrast with the collapse-refusal path is what convinced me: that path documents "tree_sig is deliberately NOT updated on a refusal: the next cycle must walk again", and the error path has no such protection. `_dir_signature` is directory mtimes only, so a project whose contents are not changing (an archived project - the normal case) never produces a different signature, and `locate`'s new `COALESCE(s.last_error,'') = ''` filter plus `_unreadable_slugs` then excludes it for ever. There is no admin re-walk or `force=True` route to clear it (grepped). The morning's owner decision "CR-282A: `last_error` only, not the age of `walked_at`" is about NOT adding a staleness test and does not cover this, so the ledger does not dispose of it.
- Evidence: `record_inventory_error` writes no `tree_sig`; `nas_inventory_sig` reads `tree_sig` alone; `grep -rn "force=True|nas_inventory_sig"` over `dashboard/src` finds the collector's skip as the only caller and no forced refresh anywhere. Downstream effect checked on the companion side: `sync/lane_guard.py:791` discounts deletes by the locate probe's count, so a permanently empty answer puts the project back to "moved files read as deletions", i.e. the lane B breaker parks and only a human clears it - a bad state the user cannot clear, which is medium by the brief's guide.
- Fix note: the hunter's fix is right in direction but pick the version that cannot lie: nulling `tree_sig` in `record_inventory_error` forces exactly one re-walk and is the smaller change, but the collector's phase 1 would then also re-walk a project that is genuinely still unmounted every cycle (acceptable - it is 8 projects a cycle and the walk is cheap on a missing dir, which fails at `proj_dir.is_dir()` before any os.walk). The alternative (re-walk whenever `last_error` is set) has the same cost. Either way the fix touches `db.py` (`record_inventory_error`) and needs a test in the dashboard suite that records an error, runs a second collector cycle with an UNCHANGED signature, and asserts `last_error` is cleared; nothing today pins the current behaviour, so nothing breaks.
