# Whole-product audit 2026-11-10: performance, leaks, wasted work, deploy and streamlining

Read-only audit of four trees: CC Sync (`6b5c0c6`, companion 0.9.90 /
dashboard 0.7.79), the live Timeline Cards (`E:\Projects\Editing` `78f0bb0`),
the rebuilt Cards editor (branch `standalone-editor` `3dcf3b6`, another
session's worktree, a moving target) and the Footage Sorter
(`sorter-dashboard-module` `abe2539`). About 600,000 lines.

The owner asked for issues, inefficiencies, performance, memory leaks "from
every angle", then added code efficiency, deploy efficiency and streamlining.
Twelve earlier hunts looked for bugs; this one asked first what the product
costs to run, what grows without bound, and what could be removed.

**How it ran.** 41 Opus hunters, one territory each (36 territories, 5
cross-cutting lenses), under one brief (`audit-2026-11-10/HUNTER_BRIEF.md`,
roster in `TERRITORIES.md`). Every perf, leak and growth finding had to state
how often the code runs, how big n is, and the cost, measured where a probe
was possible. Raw reports and probe notes: `audit-2026-11-10/hunters/`; the
machine-readable merge: `audit-2026-11-10/results.json`; the one-line index of
every finding: `audit-2026-11-10/FINDINGS.md`. The 5-hour usage limit was hit
mid-run; 19 hunters were resumed from their own transcripts after the reset
and told to finish within 20 minutes, so their "Coverage note" sections are
longer than the first wave's.

**Nothing was changed by the audit itself.** A fix pass followed on 2026-11-11: twelve of the
fourteen highs and a first set of mediums, recorded finding by finding in
`audit-2026-11-10/FIXES.md` (KNOWN_BUGS CR-384). The text below is the audit as it was
written, before any fix.

## The highs

### Data safety: the field backup page can say "Safe to format" when it is not

**1. An unreadable card folder vanishes from the verdict (comp-field-1,
verified).** `sorter_cards.list_card` (`sorter_cards.py:405-409`) catches the
`OSError` from a folder it cannot read, logs at debug and continues; the
listing carries no "partial" marker and `field_mode.card_verdict` judges only
the files it was handed. A DJI card whose `101MEDIA` throws a read error is
judged on `100MEDIA` alone: "Safe to format: all 3 files are at home." The
drive scanner (`ledger_scan`) already returns an `unreadable` list for this
case; the card listing never got one. Fix: return `unreadable`, refuse
`safeToFormat` while it is non-empty. Small.

**2. The verdict only waits for file types on an allow-list (comp-field-2,
verified).** `field_mode.is_judged` (`field_mode.py:93-112`) returns False for
any extension not in `ORIGINAL_EXTS`. `.nev` (Nikon N-RAW), `.arx`, `.cine`,
`.crw`, `.erf`, `.rwl`, `.m2t`, `.mod`, `.vob` are on none of the lists, so a
card of N-RAW alone reads "Nothing on this card needs backing up". The
studio's own cameras (Blackmagic, Sony) are covered; a customer's may not be.
Fix: invert it, judge everything except a deny-list of sidecars, so an unknown
file makes the card unsafe. Small.

Related mediums from the same hunter, not verified except where noted:
- **comp-field-5 (verified):** yesterday's 0.9.90 fix reports cards in fixed
  readers (CFexpress B) to the sorter, but `card_copy._find_card`
  (`card_copy.py:465`), the field page's card list and its presence check
  still look at removable volumes only. The ingest job fails "card not found"
  and the field page can offer the card as a copy destination.
- **comp-field-10:** the built-in copier's "read back in full" re-reads the
  file through the OS cache, so it checks memory, not what reached the drive.
- **comp-field-8:** the drive-letter to physical-disk map is cached for the
  life of the process; after letters are reused, two partitions of one disk
  can count as two copies.

**3. The first verdict after a sync rewrites the local-copies file once per
file (comp-field-3, verified mechanism; timings are the hunter's).**
`LedgerView._raw` (`field_mode.py:737-751`) calls `LocalCopies.forget` per
lookup, and `forget` rewrites the whole jsonl atomically with fsync. 10.6 s
for a 500-file card, 28 s for 2,000, inside the page's poll handler, while
further polls queue behind it. comp-ui-1/2 and comp-field-4 are the same
area: 4.4 s per 2,000-file card every 20 s even without the rewrite. Fix:
collect and forget once; index local copies by `(name, size)`.

### The one dashboard process

**4. A video seek keeps streaming the rest of the file after the browser has
gone (dash-mounts-1; hunter's probe, confirmed independently by the
editor-server hunter from the uvicorn source).** uvicorn drops a send after
disconnect without raising, and nothing in the `/cards` a2wsgi bridge or the
`/cards/edit` proxy listens for the disconnect. The probe: the client read
256 KiB of a 200 MB response and closed; the producer produced all 200 MB.
While scrubbing, each seek reads the rest of an hour-long proxy off the pool
and holds one of the engine's 24 workers for seconds, so the page's own polls
queue behind dead streams. The hunter also proved the fix (a GET-only
disconnect listener stopped the producer at 0.4 MiB).

**5. The Footage Sorter ledger leaks a SQLite connection per thread
(lens-sql-1 = sorter-py-1, verified).** `Ledger._rd` (`ledger.py:342-351`)
opens a reader per thread and appends it to `self._readers`, which only
`close()` empties. The engine starts a short-lived thread per ledger change
(`engine.py:808`), and the dashboard's worker threads are replaced after
idling. Measured: 200 threads = 200 open connections, 401 handles, +466 MB,
inside the process that hosts everything. Fix: a small pool, or close on
thread exit.

**6. Waveform peaks: an unbounded thread and a whole decoded clip in memory
per clip (cards-library-1, verified).** `_peaks_make`
(`library_engine.py:3319+`) reads the entire 8 kHz decode through
`communicate()` and widens it to int32: 307 MB for a 64-minute clip, 576 MB
for two hours, one thread per clip with no cap, in the dashboard process (the
mount sets no fleet, so peaks are always made locally). Opening an episode of
hour-long interviews with no peaks yet is the trigger. comp-jobs-1 is the
same recipe on the companion side (+288 MB per hour of audio). Fix: one
worker, decode in fixed chunks; the output bytes do not change.

Read with these three mediums, which make the same point: the dashboard has
**no memory limit and is the largest process in its container, so it is what
the kernel kills first** (lens-longrun-dashboard-3: about 2.6 GB at a busy
moment today, 8.8 GB at commercial scale, summed from measurements and
estimates). The contributors: the music text model holds about 560 MB for
the life of the process after one search (web-music-3); the music search
index is 27 KB per track resident and twice that on rebuild (web-music-4);
the b-roll semantic index peaks at three times its size on every rebuild
(web-broll-3); each Cards engine's publish ring keeps 32 full copies of every
card, 57 MB at 1,522 cards (cards-library-4).

### Timeline Cards

**7. The app-only auto-download runs in every browser (cards-page-b-1,
verified).** `15-offline.js` declares `function oflAutoOn()` twice (lines
2741 and 3237). The second wins by hoisting and has no `oflInApp()` test, so
"keep what is open" downloads the episode's media in every desktop and
Android browser, and the app's own off switch (`cards_auto_keep`) is ignored.
With cards-page-b-2 (the video line has no `held` check) it re-downloads
every video proxy every ten minutes. Fix: rename one function. Trivial.

**8. The Windows Cards app installs an unsigned exe from a vault folder
(cards-storydeck-1, verified).** `apps/windows/src/proxy.js:466` checks a
sha256 only if `latest.json` carries one (`if (mine.sha256 && ...)`), the hash
sits in the same file as the binary's name, and `main.js:160` runs the
download silently with `/S`. Anyone who can write
`<vault>/Apps/Timeline Cards/` chooses what the next editor to press INSTALL
runs. CC Sync's own channel was signed on 2026-08-17 for this reason; this is
a second, unsigned one beside it. Within a studio of trusted editors the
exposure is small; for a customer install it is the kind of thing a security
review stops on.

### The rebuilt editor (unreleased; findings against a tree that changed the same day)

**9. Exact-word find is quadratic in the episode's transcripts
(editor-features-b-1; hunter's probe on copies).** Each find re-walks the
episode once per document and once per result row and re-parses every
transcript: 1.5 s per keystroke at 100 transcripts, 24 s at 520, uncancelled,
on the shared Python worker.

**10. The transcript panel scans the whole word index per paragraph per
redraw (editor-features-a-1; hunter's probe).** 70 ms for a 267-paragraph
transcript, 255 ms for a three-hour one, on every find keystroke and edit,
against the editor's own PERF.md budget of 60 ms. Grouping words by paragraph
first brings it to 3-4 ms.

### Release and deploy

**11. "CI green" no longer covers the dashboard (deploy-release-2 =
tests-ci-6, verified).** The linux job in `ci.yml` has been `if: false` since
2026-11-10 by the owner's decision (its dashboard suite flaked under parallel
runs and was holding companion releases). A skipped job leaves the run green,
`release-dashboard.yml` runs no tests, and `tools/release_customers.py` still
publishes a dashboard bundle to every customer on "ci.yml green on this
commit". So nothing automated now runs the dashboard, server, tools or
web-app suites, or the CRLF, licence and notices gates, before a customer
release. tests-ci-7 has a lead on the flake itself: six dashboard tests sit
at exactly 10 s on CI, SQLite's busy timeout, which looks like a test's own
connection waiting on the app's startup writes.

**12. The Cards/Sorter deploy recipe deletes and recreates the app every time
(deploy-nas-1, verified in code, not run).** `install_dashboard_app.py:6122-
6131`: passing `--mode` sets `args.recreate = True`, and the comment there
says a manifest that already says `image` should NOT recreate on a routine
redeploy. The documented recipe passes `--mode image`, so every Cards or
Sorter deploy deletes the TrueNAS app and creates it again from whatever
image it is told, which is the only reason the live digest has to be read
off the NAS by hand and the only way a stale one rolls the dashboard back.
Without the flag the script takes the restart path (`:7189-7204`), which
keeps the container's current image. See "Deploying" below.

### Plausible, not reproduced

**13. A live stream can hold the only server-side YouTube worker
(web-ytdl-1).** Verified: `vendor/downloader.py` has no `is_live` test, no
match filter and no wall-clock limit, `/live/` links are accepted, and the
worker reads cancel only between clips. Not verified: that yt-dlp then
records until the stream ends in this configuration (it does by default).
The companion's executor has a 3-hour clip timeout; the server's twin has
none (web-ytdl-2).

**14. The local b-roll indexer probably fails on 1080p proxies (idx-1).**
Verified: `extract_frames` applies no scale, and proxies have been 1080p
since 2026-09-17. The hunter's arithmetic: about 2,040 image tokens per frame
instead of 1,024, so an 8- or 9-frame window passes the 16,384-token slot and
each such clip is marked `error`. No local run has happened since the proxy
change, and the model was not loaded to prove it. Scaling frames to 960 wide
at extraction fixes it either way.

## Where the product wastes the most, by theme

Ordered by what it would return for the effort. Ids are in `FINDINGS.md`.

### 1. Unchanged data is re-sent, re-written and re-computed on a timer

The largest single source of load in the fleet, found from both ends of the
same wire by different hunters:

- Every machine re-sends its unchanged manifest in full every 10 minutes, and
  one changed project re-sends all of them: 3.55 MB and about 40,000 rewritten
  server rows per resend at 10 ticked projects, about 510 MB a day per machine
  (comp-core-2). The dashboard deletes and rewrites those rows each time: 1.64
  MB of WAL per ticked project per resend, about 47 GB a day at 20 machines,
  and the rewrite stops the owed-files cache from ever hitting (dash-db-1).
- The walk that builds it spends 85% of its CPU constructing `pathlib`
  objects: 3.6 s per 50,000 files every 300 s on every machine; a `scandir`
  version gives the same totals in 0.47 s (comp-core-1).
- One byte over the 7 MiB budget strips the per-file lists from every
  project instead of enough of them, and a trimmed manifest is then never
  recognised as unchanged again (comp-core-3, comp-core-4, both bugs).
- The selection reply carries the whole fleet's project-roots map every 30 s
  with a fresh timestamp, so the companion's write-on-change check never
  matches and `selection.json` is rewritten on every fetch (dash-api-1).
- The collector's self-check costs 18 write transactions and 83 KB of WAL
  every 15 s with nothing changed, about 650 MB of WAL a day
  (dash-collector-1); `remoteneed` deletes and re-inserts every missing-files
  list every minute, about 1.6 GB a day at 10 incomplete pairs
  (dash-collector-3); a light report writes 28 KB of WAL, about 1.9 GB a day
  across four machines at the 5 s cadence (dash-api-5).
- The home page rebuilds the projects view 12 times a minute per open tab and
  `GET /` builds every view twice: 1,170 SQL statements per load
  (dash-web-2); at a 20-machine fill it took 2.8 s (dash-db-6).

One change covers most of it: **send and store a content hash per project,
and skip the body when the hash matches**, on the report wire, the selection
reply and the collector's writers alike. The hunters proposed the same shape
independently in five reports.

### 2. One "is Resolve running" probe instead of nine

Nine call paths spawn `tasklist` (202 ms each, measured): 230-545 spawns an
hour on an idle Windows machine, 800-1,100 while syncing
(lens-longrun-companion-1, combining comp-jobs-2, comp-media-1,
comp-resolve-7 and a new one in the report path). The b-roll ingest runs it
before every extracted frame, so the probe costs 2.7 times the work it guards
(comp-media-1). An in-process Toolhelp snapshot measured 8.5 ms; cached for a
second or two it replaces all nine. On macOS the equivalent waste is
`diskutil` per mounted volume every 10 s from both sorter loops
(lens-longrun-companion-2) and `ioreg` on every report tick (comp-core-6).

Same family: an open `/music` tab relaunches the onefile companion exe as a
worker every 30 s for as long as the tab is open, Resolve running or not
(web-music-1 = comp-media-3; the hunter estimates 14 GB an hour of `%TEMP%`
writes).

### 3. Load on Resolve itself

Resolve's UI stalls while its scripting API is busy, so these cost the
editor directly:

- The media-tree refresh asks Resolve for every pool clip's proxy state every
  120 s, changed or not: about 5.5 s per 1,298 clips; at 20,000 clips the API
  would be busy most of the time (comp-resolve-1, the second figure
  estimated).
- Every bridge call opens a new `scriptapp()` connection, about 75 ms each:
  once a second from the Cards role, every 3 s from the watcher
  (comp-resolve-2). The relink path builds Resolve's full 60-key property
  dict two to four times per clip while a one-key reader already exists
  (comp-resolve-5).
- The watcher stats and realpaths every timeline clip every 3 s even when
  Resolve's answer came from its cache: 160 ms per poll at 2,000 clips on
  local disk (comp-resolve-3).
- Timeline Cards' agent runs a 1 Hz full sweep, about 1,350 calls into
  Resolve under the API lock the companion shares, with no page open and
  during playback (cards-resolve-3), and its 10 Hz loop serialises the whole
  680 KB state twice per tick, changed or not: 37 ms of CPU per second at 487
  cards (cards-resolve-2).

### 4. The dashboard's event loop and its one write lock

- About 45 `async def` UI routes write to SQLite on the event loop; a click
  while something else holds the write lock freezes every request for up to
  5 s (dash-web-1, measured 3.07 s).
- The report route holds the write lock across a walk of the Projects tree
  (dash-api-2).
- Five stacked `@app.middleware("http")` layers cut streaming throughput from
  693 to 294 MB/s for everything the dashboard serves (dash-web-4), and every
  signed-in request opens a fresh SQLite connection to check its session
  (dash-web-5).
- `docker stop` gives 10 s; the lifespan's steps run serially with about 20 s
  of waits ahead of the Node editor's stop, so the step that flushes open cut
  lists is the one that gets killed (lens-longrun-dashboard-1). The ytdl
  workers are never stopped and their ffmpeg and CLI children survive a
  self-restart into the next process (lens-longrun-dashboard-2).
- The checks panel shows `[ OK ]` for any kind evaluated once, ever, so a
  check that now fails every cycle still reads OK: the stored timestamps are
  never read (dash-collector-2). This breaks the product's own rule that an
  unverified check is NOT CHECKED.
- New footage can take 3.1 hours to show as "on the server" today and 15.6
  hours at 500 projects, because the 8-projects-per-cycle inventory window is
  spent on unchanged projects too (dash-collector-5).

### 5. Sync lanes

- Lane B still opens the full 16-connection SSH pool and lists the whole
  project on the NAS every pass; CR-381 cut that for lane A only
  (comp-sync-1).
- CR-381's "skip clean projects" memory survives an untick/re-tick and a
  full/upload-only switch, so lane A can skip files it has never looked at
  for up to two hours (comp-sync-2, a bug in a fix shipped this month).
- The "skipped, exists" alarm and the orphan `.partial` report keep only the
  last project scanned, so a clean project hides another's mismatches
  (comp-sync-3).
- Syncthing is polled with 3 + 2N REST calls every 15 s for the life of the
  process, including the expensive `/rest/db/status` per folder
  (comp-sync-5).

### 6. Footage Sorter

Move safety held up under review: renames refuse to replace, a cross-
filesystem move is refused rather than copied, every step is journaled,
nothing deletes a source (sorter-py). What needs work:

- A move run that raises leaves its plan "moving" for ever with no reconcile
  or rescan (sorter-py-2).
- Any ledger write makes every open page re-download the whole clip list, up
  to 2.7 MB gzip every 2 s with the Backups panel open, because the ETag
  changes with a counter rather than the content (sorter-page-1); each
  assign downloads the 2.9 MB manifest uncompressed and redraws every pane
  twice (sorter-page-3); two whole-table scans of `copies` per change, 1.7 s
  at 2M files (lens-sql-2).
- Thumbnail workers take a backfill job before waiting for a slot, so the
  thumbnail someone is looking at waits behind the backfill (sorter-py-5); a
  strip format change rebuilds about 25,000 strips over hours and deletes
  the old ones first (sorter-py-6).
- The page ships `dev-mock.js` to production, serves 606 KB of assets
  uncompressed with no version in their URLs, and about 81 visible strings
  contain an em dash (sorter-page-4, sorter-page-8: the owner's rule).
- The repo tracks 24 MB of creator-1's own state (manifest backups, executed
  move plans, a log, and a `settings.json` the hunter reports holds the
  owner's address and calendar ids) and pushes it to GitHub (sorter-node-6;
  the tracked files were confirmed, their contents were not opened).
- The sorter's docs still tell people to install the retired tray and start
  the old Node server, which would put a second card watcher beside the
  companion (sorter-node-1). `server.js` and `lib/` cannot be retired yet
  because 13 parity tests run the old JavaScript as their oracle, and that
  suite runs in no CI (sorter-node-2).

### 7. Timeline Cards (the live page)

- The edit view rebuilds every row with `innerHTML` on every new state
  version: 5,000 nodes and 1,000 canvases at 500 cards, 23 ms on the desktop
  and an estimated 90-140 ms on a phone (cards-page-a-1).
- The 1.67 MB page goes out in full on every load, gzipped again per request,
  with no ETag (cards-server-2).
- Offline: updating one episode's service worker deletes every other
  episode's offline shell (cards-page-b-3); a full-storage error while saving
  an offline edit is swallowed and the edit is reported as made
  (cards-page-b-5); downloaded media is never evicted (cards-page-b-4).
- Engines cannot be released, which is why the pool refuses a third episode.
  The hunter found a real stop is about ten lines: only the library sweep
  loop and the translator ignore the stop flag (cards-library-3), and each
  engine runs `LibraryEngine.__init__` twice, leaving an orphan translator
  thread (cards-library-2).
- The library reader holds one open transaction on Resolve's live project
  library for the life of the process; the same bug was fixed in
  `ProjectDatabase` on 2026-09-03 (cards-resolve-1). A library conform
  passes `allow_open=True`, switching off the writer's own lock check for the
  race it exists for (cards-resolve-5), and the database writer protects real
  libraries with a fixed list of five names (cards-resolve-6).
- Inside both native apps the page polls the NAS four times a second because
  a page served from 127.0.0.1 does not count as remote (cards-storydeck-2).
- While both pages exist, `/cards` and `/cards/edit` write the same cut-list
  files with no shared lock (editor-server-2, not reproduced).

### 8. AI cost

- The b-roll API path never hits the prompt cache: the 3k-token instruction
  block sits after the images (idx-3). Offline backfill does not use the
  Batch API, which is half price (idx-4). `max_tokens` 8000 is below a third
  of the archive's historical outputs, so a truncated answer costs two paid
  calls and then marks the clip `error` (idx-5).
- Story Deck's fan-out stages resend a 23k-token preamble uncached on every
  call: 75-85% of each stage's input (cards-storydeck-5).
- Every warm edit-chat turn re-sends a 46k-character digest of the cut list
  and the conversation keeps every copy (cards-server-1).
- Gear identify keeps every earlier photo in the conversation, so input grows
  quadratically over a 40-photo session (dash-mounts-3).
- The provider resolver probes every CLI below the one it picks, twice each,
  with no single-flight: eight lookups arriving together start 32 CLI
  processes (dash-ops-1). Nothing caps how many Claude Code CLI processes
  Cards starts inside the container (dash-mounts-4).
- In the rebuilt editor one queue of four Claude slots serves interactive and
  background work, and shorten's calls cannot be cancelled: a closed tab
  keeps Opus running for up to 15 minutes per call (editor-features-b-5/-6).

### 9. Disk growth

The disk lens built a table of everything the product writes, per machine
role (`hunters/lens-disk.md`). Thirty-odd items were already filed by
territory hunters; what has no retention at all, largest first:

- Clips fetched on demand from the b-roll archive and music library are
  never evicted from a remote editor's disk: an estimated 150 GB a year, with
  the whole archive as the ceiling (lens-disk-2).
- Pre-operation ZFS snapshots (`ccsync-pre-*`) never expire, so nothing
  deleted after one is ever freed (ops-server-1).
- Save-point exports of projects nobody edits any more are never swept:
  10-50 GB a year per editor on the system disk (lens-disk-1).
- Every force-kill of the companion leaves two 108 MB PyInstaller `_MEI`
  folders in `%TEMP%`; on the base rig every ship does it, about 26 GB a year
  (lens-disk-3). This machine already holds about 240 MB of them.
- Every OTA apply copies all three databases twice, including a 500 MB b-roll
  index it almost never migrates, and keeps eight: about 4.2 GB (dash-ops-2).
- Cut-list `.history` keeps full uncompressed copies without bound, about 75
  MB per cut list at 2,000 revisions (cards-resolve-9), and
  `timeline_plans.history.jsonl` appends the whole op list per revision:
  quadratic, never read (cards-library-5).
- Installer leftovers: 130 MB of downloads in `%TEMP%` per install and
  `.stale-<epoch>` companion copies at 48 MB each (ops-install-4, -9).

## Deploying

### Timeline Cards, the Sorter, and the dashboard (hunter `deploy-nas`)

Today a Cards-only deploy is the full dashboard deploy: about 31 SSH
connections, a snapshot, eight provisioning steps, both trees re-shipped, the
TrueNAS app deleted and created, a "health check FAILED" that is a fixed 10 s
sleep and one probe (deploy-nas-2), and in image mode a 150 s poll that can
only fail because it expects the repo's dashboard version, which an
image-mode deploy never ships (deploy-nas-3). Before it: the live digest and
the other tree's live commit read off the NAS by hand. "Restart to pick up
new vault data" runs all of that (deploy-nas-8).

What the hunter proposes, keeping snapshot-before-privileged and
stage-verify-swap:

| Case | Today | Proposed | Manual steps | SSH | Downtime (est.) |
|---|---|---|---|---|---|
| New image | recreate, digest and `site.toml` by hand | `image --to <digest>`: reads live state itself, refuses older than live, records the digest | 7 to 2 | 31 to 14 | unchanged, no false FAILED |
| Cards | full recipe, recreate, Sorter re-shipped | `cards [--commit <sha>]` | 5 to 2 | 31 to 7 | 1-3 min to 20-60 s |
| Sorter | same, plus the live Cards commit by hand | `sorter [--commit <sha>]` | 6 to 2 | 31 to 7 | 1-3 min to 20-60 s |
| Vault data | the full Cards recipe | `restart`, or close and reopen the episode | 5 to 1 | 31 to 2 | 1-3 min to under a minute, or none |

**What can be done today with no code change:** drop `--mode image` from the
Cards and Sorter recipes (high 12). That alone removes the recreate, the
digest lookup and the rollback trap. It has been read in the code, not run;
the first run should be a `--dry-run` to see "restarted container" in place
of "deleted app for re-create".

Also: the Cards recipe passes no Sorter commit, so it ships Sorter `master`
unpinned (deploy-nas-5); Cards ships 479 files where the mount needs about
160, including project working data (deploy-nas-7 = cards-storydeck-7);
`site.toml [stack] image` is stale right now (0.7.78 against 0.7.79 live).

The image itself is in good shape: the lockfile is the only input to the
108 MB venv layer, and a code-only update pulls about 3 MB. The OTA path is
the cheapest and safest deploy in the product. Neither should be touched.

### Companion and package releases (hunter `deploy-release`)

`ship.cmd` takes 27-29 minutes, of which 21.5 are the dashboard suite run
twice, the first time serially, and on the image-mode studio that first run
guards a deploy that does not happen (deploy-release-1). It then builds
locally a commit CI has already built, so one version number names two
different binaries and the studio soaks bytes no customer gets
(deploy-release-3). The CI pathway reaches the vendor feed in 9-12 minutes
with one prompt, but the studio then waits up to 24 hours for its daily poll
plus about 14 minutes per 50 MB from GitHub's CDN; the 1.2 s direct PUT
exists only as a helper outside the repo (deploy-release-4). A companion
ship needs six hand edits of version strings (deploy-release-5).

Proposed: one command, `release.py companion <version>`: bump every version
copy, push, wait on CI for that exact commit, publish with the existing
passphrase prompt and every existing refusal, optionally PUT the same
verified bytes to the studio, then upgrade this machine. `ship.cmd` becomes a
thin wrapper. Estimated: 27-29 minutes to 10-13, about 12 human actions to 3,
one binary per version everywhere. Its prerequisite is high 11: something
must run the dashboard suite before CI can vouch for a dashboard commit.

## Streamlining: duplication and dead code

The duplication lens diffed 14 pairs of twin files, built the import graph
of each Python package and scanned for unreferenced code
(`hunters/lens-dup.md`). The headline is that **there is very little dead
code to delete**: no unused Python modules, no unreferenced JS or CSS files,
no unread companion config keys, no unused dependencies, no dead routes,
about 320 lines of dead Python in total (lens-dup-7: the
`project_root_override` functions, and a `truenas_client.py` shim meant to
last one release that has been there since 2026-08-17). The savings are in
three places where the same thing exists twice:

- **The old Cards page has no retirement step.** After the flip to the
  rebuilt editor about 61,000 lines stay live (32,741 of page JS and 28,022
  of its tests), so every Cards feature exists twice. What blocks deleting
  it is that both native apps still load the old page (lens-dup-1). This is
  the largest streamlining item in the product, and it is a plan, not a
  patch.
- **The Windows and macOS installers** do the same steps twice and have
  drifted in seven ways, some of them bugs (macOS compares the installed
  companion by sha256, Windows by size and date; the Syncthing wait is 80 s
  on one and 10 s on the other). Moving the shared steps into companion
  subcommands, as `--setup-resolve-prefs` already is, would remove an
  estimated 1,400 lines (ops-install-2).
- **The sorter's old Node server** (`server.js` and `lib/`, about 7,200
  lines) is kept alive only as the oracle for 13 parity tests. Freezing its
  answers as saved expectations lets it retire and drops Node as a test
  requirement (sorter-node-2). Nothing starts the tray scripts, `mover.ps1`
  or the old ingest any more; they can move to `legacy\` now.

Twins that are deliberate and pinned by tests, and should stay as they are:
the vendored `broll_vlm` copies, `ed25519.py`, `webtheme.py`, and the two
telemetry tables.

Twins that have drifted, each with a consequence:
- `ffmpeg_tools.py`: the indexer's copy has no timeout on any of its ten
  ffmpeg and ffprobe calls, and no test checks that the shared frame-count
  helpers agree (lens-dup-4).
- The two YouTube downloaders: the server's conversion has no timeout and
  cannot be cancelled; the companion's has both (web-ytdl-2).
- The sorter's JS and Python disagree on what a duplicate is: the Node
  server calls any two equal-size files over 64 MiB identical; the Python
  compares every byte (sorter-node-3). The Python is right and is what ships.
- The Android app opens a new TLS connection per request where the Windows
  app reuses them (cards-storydeck-3).
- The test that keeps the companion's media recipes identical to Cards'
  compares against a hand-copied list, so it would not fail if the Cards
  side changed. They agree today (lens-dup-6).
- `ingest_batches.py` in b-roll and music has not drifted (11 functions
  identical) and fixes are copied across by hand; the two `ingest.js` files
  share only 29% and are not worth merging (web-music-9). The three
  `style.css` files share about 70% (web-broll-8).

Weight that ships and is never used:
- The companion build bundles all of onnxruntime: 306 `.py` files and 156
  submodules the code never imports (lens-dup-3), which adds to what every
  start extracts.
- The Cards deploy ships 479 files where the mount needs about 160, and the
  Story Deck screenshots are 46 MB in the tree and 78 MB in git history
  (deploy-nas-7, cards-storydeck-8).
- The rebuilt editor bundles all 17 features into one 1.29 MB file loaded up
  front, and its `dist/` carries 11.6 MB no browser downloads
  (editor-client-7).
- The footage-sorter repo tracks 23.6 MB of manifest backups, move plans and
  logs, against its own `.gitignore`; the lens reports they contain real
  interviewee names (lens-dup-2 = sorter-node-6).
- `bench/` cannot exercise the flags or the route the companion now uses,
  yet CI installs and tests it on every push (ops-server-8).
- Two dashboard tables, `lane_report_history` and `completion_history`, are
  written and pruned and never displayed (dash-db-5).

Large functions where a table would remove a class of bug: the Cards
`do_POST` dispatcher (the lens found `/api/fade` missing from the read-only
block list there, lens-dup-5), the dashboard's `api_report`, and the tray's
282-line `sync_guard`, rebuilt in full by two threads every 2 s (comp-app-4).

## What is already good (leave it alone)

Each report ends with a section on what is efficient and should not be
"optimised". The ones that matter most:

- The report route itself: 63 statements, one commit, about 6 ms (dash-api).
- Win32 handles in the tray are bounded on every path, including the error
  and menu-open paths: at most 24 cached icons, every menu destroyed in a
  `finally` (comp-ui). No GDI leak.
- Signature checks are cheap: 2.9 ms for the pure-Python ed25519 verify, 27
  ms to hash a 100 MB package; the supervisor wakes zero times at idle; logs
  rotate and crash files are capped at 20 (comp-core).
- Companion import takes 0.166 s; dashboard boot about 1 s
  (lens-longrun-companion, lens-longrun-dashboard).
- The Docker image's layer order and the OTA update path (deploy-nas).
- Sorter move safety (sorter-py), the Cards state poll and media serving on
  the Cards side of the bridge (cards-server), the editor server's own
  stream handling (editor-server), `tests_gate=ci` (deploy-release).
