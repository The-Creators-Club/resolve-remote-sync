# Extract of inventory section 18

## Items

### 18-001: An admin can see exactly which version of the server is running and where it came from.
- Where: releases-and-updates / Version numbers
- What: The server reports, to an admin and in its health information, the version it is running, the version it was installed with, whether the running version is an update taken on top of that installation (or a developer's working copy), and an identifier of the exact build it was made from. When the build cannot be identified (for example it was made from unfinished, uncommitted work) the identifier is shown as unknown, never guessed. Versions are compared number by number (a later number in any part is newer); a version that is not made of numbers and dots counts as older than every real version.

### 18-002: An admin sees which server updates are on offer, split by what taking each one involves.
- Where: releases-and-updates / The server updating itself
- What: The admin's update view lists, newest first, with size, publish date and notes:
  - updates the server can take by itself with one button;
  - updates that need the server's installation itself renewed from the NAS's own app manager (the admin is given the exact steps, see 18-014);
  - earlier versions, still newer than the installation, that the server can go back to.
  A version equal to the running one, or not newer than the installation, is not listed. The same view shows the progress or the last outcome of an update, the backups taken before updates (name, when, by which version, what they hold, total size), how much free space the server's data disk has (or that it cannot be measured), how many times the version on trial has failed to start, and what going back to the previous version would mean for the studio's data (safe, unknown, or that a backup must be restored with it).

### 18-003: An admin can update the server from the dashboard with one button, and is told plainly when it is refused.
- Where: releases-and-updates / The server updating itself
- What: Pressing update on an offered version starts it at once and the server restarts by itself for about ten seconds when it lands. It is refused, with the reason in words, when:
  - the version named is not a plain dotted version number;
  - this server was installed in a way that cannot update itself (the admin is told how this server is updated instead);
  - another update is already running ("Wait for it to finish or fail"), including when two admins press at the same moment: one update runs and the other is told;
  - that version is already running;
  - the version is not newer than the installation's own ("To go back, roll back instead");
  - the server has not checked the vendor's offer since it last started ("Run Check now first");
  - the update needs the installation renewed from the NAS's app manager instead;
  - YouTube downloads are in progress: "N YouTube job(s) are running: an update restarts the dashboard for about ten seconds and interrupts them. Wait, or apply again with force." Downloads waiting for review do not count. The admin can override with force;
  - the data disk is short of space: it needs at least four times the update's size plus twice the size of the studio's live data, plus 256 MiB. A disk whose free space cannot be measured is not refused;
  - the server cannot write where updates go.
  An admin's own update of a version also lifts any "do not take automatically" mark on that version (18-008).

### 18-004: While the server updates, the admin watches each step, refreshed every second.
- Where: releases-and-updates / The server updating itself
- What: The progress shows, in order: queued, downloading, checking, trying the new version against copies of the studio's data, backing up, switching over, restarting, then done; or failed with the reason. An update cut off by the server or the NAS restarting is shown afterwards as failed: "interrupted by a restart at step S". Nothing temporary from an update is left behind on the disk whatever happens.

### 18-005: A server update is checked and tried before it replaces anything, and a bad one changes nothing.
- Where: releases-and-updates / Signing and trust
- What: The update is downloaded only over a secure connection, is at most 256 MiB and must arrive within ten minutes, and must match exactly what the vendor signed; anything else is refused with the reason. Its contents are checked file by file against what the vendor listed; anything unsafe or unlisted refuses the whole update. The new version is then started against COPIES of the studio's data (within ten minutes) and must bring them up to date without error; if it cannot, the update is refused with the failed checks named and "Nothing was swapped". Only then does the server switch to it.

### 18-006: Before every server update the studio's data is backed up, and on a NAS that can do it a snapshot is taken.
- Where: server-install-and-running / Snapshots, restoring and the server's disk
- What: Just before switching versions, the studio's data (including the b-roll archive's and the music library's descriptions) is copied into a dated backup named for the update. Any part that cannot be copied is skipped and the backup says so; it never stops the update. On a NAS that offers snapshots, where the admin has given the server access and named what to snapshot, a snapshot named for the update and the time is also taken; otherwise the update notes that no snapshot was taken and why. Backups are kept newest first, at most 3 per update, at most 8 in total and at most 8 GiB in total; the newest backup is never deleted. The server always keeps the running version and the one it can go back to.

### 18-007: A server version that will not start properly is undone by itself after two tries.
- Where: releases-and-updates / Rolling back and withdrawing a build
- What: After a new version starts, the server waits about 45 seconds and then checks for up to another 45 seconds that it answers as that version. A version on trial that does not, or that has not got that far within ten minutes of starting, is restarted; after two failed starts in a row the server goes back by itself to the previous version (or to the installation's own) and records why ("X failed to reach a healthy boot N times", or that it was refused N times and why). The admin sees this in the update view, and that version is marked so the server never takes it again automatically. A healthy start clears the count. The server never goes back to a version that cannot understand the studio's data as it now stands: it stays on the new version, keeps its admin pages answering, and records "booting it would fail on every start. Restore the backup taken before this update and roll back from the dashboard, or deploy a newer image." A server version that can no longer be verified as signed by the vendor is never started.

### 18-008: An admin can roll the server back to an earlier version, restoring a backup with it when the data needs it.
- Where: releases-and-updates / Rolling back and withdrawing a build
- What: An admin can go back to the previous version, or name an earlier one still on the disk, or to the installation's own version when there is none; the server restarts. Refused when this server cannot update itself, while an update is running, when nothing has been taken on top of the installation ("this dashboard is already running the image's own code"), or when the named version is not on the disk. When the studio's data is newer than the earlier version understands, the rollback is refused unless the admin either chooses to restore the backup named in the message ("restore backup <name> alongside it"; the message warns that this takes today's reports back too) or explicitly acknowledges the risk. When it cannot be known whether the earlier version understands the data, the rollback is allowed and the answer is shown as unknown. A backup can only be restored as part of a rollback; a backup that does not exist or holds nothing in use is refused. A version rolled back from is marked "rolled back by <admin>" and is never taken again automatically, until an admin updates to it by hand.

### 18-009: A server whose installation is renewed past an update it had taken goes back to running the installation by itself.
- Where: releases-and-updates / The server updating itself
- What: When the NAS's installation is renewed to a version at or above an update the server had taken on top, the server stops using that update at its next start and runs the installation, recording "X is not newer than the image's own Y -- the image carries it", which the admin sees in the update view. It does not do this when the installation would not understand the studio's data as it now stands; it records the refusal instead.

### 18-010: The server says whether its information about vendor releases is current.
- Where: releases-and-updates / Customer sites and the vendor's release feed
- What: The server's health information says whether a vendor feed is set up, when it was last read and how many days ago, the last error, how many verified builds it carried, and whether it is stale. Stale means never checked, or not checked for more than 7 days. With no feed set up it says so and is never called stale. After the server restarts, nothing is offered from the feed until it has been checked again.

### 18-011: The server checks the vendor's release feed every day by itself, and an admin can check now.
- Where: releases-and-updates / Customer sites and the vendor's release feed
- What: The first check runs about ten seconds after the server starts, then once a day by default (the interval can be set by whoever installs the server, never under a minute). An admin can press Check now at any time and is shown what was published or made current by that check, what the vendor recalled, and which builds need a newer server. With no feed set up there are no checks and nothing reaches out to the internet; Check now and publishing from the feed answer that no feed is configured.

### 18-012: The server believes only a release feed the vendor signed, and refuses an old one played back.
- Where: releases-and-updates / Signing and trust
- What: The feed and every build in it must carry a valid vendor signature. The feed is fetched only over secure connections at every hop (a redirect to an insecure address is refused), sends no credential of any kind, and is limited in size. A feed older than the newest one the server has ever accepted is refused as "a possible replay of an old channel" and nothing changes. Builds without a valid signature, builds that claim a minimum version above their own, and builds the vendor has recalled are dropped. Builds the feed lists in a form this server cannot use are reported: the check still succeeds but its error reads "N record(s) in the channel are not offered here: ... The feed has to republish them." (up to five named). When the feed is held at an address whose signature cannot be found alongside it, the error explains why and suggests a plain address.

### 18-013: An admin chooses how much of the vendor's offer the server takes by itself.
- Where: releases-and-updates / Customer sites and the vendor's release feed
- What: Three settings, changeable by an admin at any time (the installer's choice is the starting value):
  - manual (the default): nothing is taken automatically; only an admin's publish button brings a build in;
  - stage: the build the vendor currently offers for each kind of app and each operating system is downloaded and kept, but not offered to the computers;
  - current: the same, and it is offered to the computers (made current), subject to the soak rule (18-024); the server also updates itself (18-016).
  The build the vendor offers is the one the vendor points at, or, with no pointer, the highest version. Anything else is refused as not one of the three settings.

### 18-014: When a server update needs the installation renewed, the admin is told exactly what to do on their kind of NAS.
- Where: releases-and-updates / Facts about Windows, macOS and the NAS that bite an update
- What: The same instruction appears on the update view, on the packages view, as a banner on the fleet view and in alert mail. When the vendor names an exact installation to use, the admin is told to edit the server's project in the NAS's own app manager (on Synology: the app manager's Project, then Edit; on TrueNAS: Apps, then Edit; otherwise the NAS's own app manager), to paste the exact references given, and warned that pressing Update or Build alone fetches the old pinned installation again. Otherwise they are told to press Build (Synology) or Update (TrueNAS) in the NAS's app manager. A banner appears when every server update on offer needs this (up to five versions named) and goes away when that is no longer so.

### 18-015: A vendor recall withdraws a build from the studio, whatever the admin's setting.
- Where: releases-and-updates / Rolling back and withdrawing a build
- What: Every build the vendor recalls stops being offered to the computers at the next check, under every setting including manual; the build stays on the shelf. A recalled build can never be made current again: "<kind> <version> was RECALLED by the vendor: <reason>. It cannot be made current. Roll the fleet back to a build that was not recalled." The feed view lists every recall, with reason and time, whether or not this studio ever had the build. Under the current setting, the vendor can also take the studio back to an earlier build by pointing at it again; that change is recorded in the admin history as made by the release feed.

### 18-016: Under the current setting, the server updates itself unattended, and says why when it does not.
- Where: releases-and-updates / The server updating itself
- What: After each check, the server takes the version the vendor offers for it, in the same way as the admin's button but never interrupting YouTube downloads. It does not, and shows one sentence why on its health view, when: this server cannot update itself (with how to update it instead); an update is already running; the newer version is not the one the vendor currently offers ("Update now" takes it by hand); it needs the installation renewed (with how); it already failed here ("will not be retried automatically"); an admin rolled back from it; it was taken before, would not start, and was undone; or it has not soaked: it must have been published by the vendor at least the soak time ago (30 minutes by default, none when the soak is off), and a build with no readable publish date is never taken while a soak is set. When it starts: "taking dashboard X now: this server restarts for about ten seconds when it lands." When refused: "dashboard X was not applied: <reason>".

### 18-017: An admin sees what the vendor offers and can bring one build onto the studio's shelf by hand.
- Where: releases-and-updates / Customer sites and the vendor's release feed
- What: The feed view shows whether a feed is set up and where, the setting in force, when it was last checked and the last error, builds available that the studio has not yet taken, builds where the vendor and the studio hold the same version with different contents (both short fingerprints shown), every recall, and the vendor's current server installation with the instruction for renewing it. An admin can publish one build from the feed onto the shelf, optionally making it current. Refused when: no feed is set up; the build is a server update ("applied, not published"); the server has not checked since it started ("run Check now first"); it is already on the shelf (or the same version from different contents: "The vendor has to publish this build under a new version number."); the download is not secure, does not match, fails, or is over 200 MiB or ten minutes; or the disk is short of space (18-019). The shelf records the admin as publisher (or the release feed, for automatic ones).

### 18-018: A companion build that needs a newer server is held back, and the admin is told the fleet is stuck until the server is updated.
- Where: releases-and-updates / Offering an update to a computer
- What: Such a build is brought onto the shelf but never offered to the computers; the check shows it as staged. The server raises a problem the admin sees: "A new CC Sync build for <platform> (<version>) is on offer but cannot be handed to the computers here: it needs dashboard X and this dashboard is Y. Until the dashboard is updated, every computer in the fleet stays on the build it has and this server reports them all as up to date." with the next step "update the DASHBOARD from the vendor feed. The companion build becomes available to the fleet straight after." It clears by itself once the check no longer finds it. Making such a build current by hand is refused: "<kind> <version> needs dashboard X and this dashboard is Y. Update the dashboard first, then make this build current." with no override.

### 18-019: Anything large written to the server's data disk is refused first when there is not room for it.
- Where: server-install-and-running / Snapshots, restoring and the server's disk
- What: Uploading a build, taking one from the feed and installing an assistant program are each refused when free space is below three times what they need plus 256 MiB (the 256 MiB floor applies even when the size is unknown). A disk whose space cannot be measured is never refused. The message: "not enough free space on the data volume: N MiB free, <what> needs about M MiB. Old builds are pruned on publish (current plus the two newest are kept); free some space and try again."

### 18-020: Every build the studio offers its computers is signed by the vendor, and the server cannot sign one itself.
- Where: releases-and-updates / Signing and trust
- What: Each build's description (its kind, operating system, version, file name, fingerprint, size, minimum version, publish date and whether the program itself is signed; for a companion also its processor type and the server version it needs) is covered by the vendor's signature, made away from the server. The server can check a signature but never make one. Several vendor keys may be trusted at once, so a key can be replaced over an overlap; each key is shown by a short identifier. With no key set up, every check fails ("no release public key is configured") and publishing is refused. Signature refusals say what was wrong: not readable, the wrong length, not signable, or "no configured release public key verifies this record". Two versions that cannot be compared are treated as a refusal, never as fine. A site whose release key the vendor holds is not asked to back that key up.

### 18-021: Putting a build on the shelf either succeeds whole or changes nothing.
- Where: releases-and-updates / Making and publishing a release
- What: The same rules apply however a build arrives (an admin's upload, the feed button, the feed's automatic setting, the release tools). Refused when its minimum version is above its own: the message explains that every computer that saw the offer would raise its lowest allowed version above the build and then refuse it, that nothing was published, and that it must be re-signed with a minimum at or below its version. Refused when the signature does not cover exactly what arrived: "release signature REJECTED (<detail>): nothing was published. The signature must cover this exact record: ...". The same version with the same contents is accepted with "already published at this version, with these exact bytes."; with different contents it is refused: "<kind> <version> for <platform> is already published on this server, from different bytes. Nothing on disk was replaced. Bump the version and rebuild, or delete the published record first if you meant to overwrite it." A shelf entry records the publisher, time, signature, minimum version, required server version, processor type, release notes (for display), and whether it was made from unfinished work (advisory; a mark the vendor's feed later says is clean is cleared, never set). The shelf keeps the current build plus the two newest for each kind and operating system; older ones are removed. A refused publish leaves nothing behind.

### 18-022: A build that is published but not yet allowed to be current is kept staged, and the publisher is told what to do next.
- Where: releases-and-updates / Trying a build on one computer first
- What: When publishing asks for the build to become current and that is refused, the build is still published but staged, with the note "published and STAGED: push it to one computer, let it soak, then MAKE CURRENT. <reason>". Making a build current is recorded in the admin history.

### 18-023: Making an unsigned build current needs the admin to type its version, because it stops every computer from updating.
- Where: releases-and-updates / Signing and trust
- What: "... has no release signature. Companions verify signatures, so making it current stops EVERY computer in the fleet from updating, silently." followed by "Publish the signed build from AVAILABLE FROM THE VENDOR instead." when a feed is set up (otherwise to republish it signed), and "To make it current anyway, type the version number (X) into the confirmation box."

### 18-024: A new companion build must soak on real computers before it is offered to the whole fleet.
- Where: releases-and-updates / Trying a build on one computer first
- What: However a build becomes current (button, rollback, publish, feed), a companion build is refused until it has soaked, with one of these reasons:
  - "no computer has reported X yet, so nothing has run it. Push it to one computer first, leave it for N min, then make it current."
  - "R of the M computers on X had to be rolled back off it by the crash-loop guard."
  - "M computers on X have reported C crash(es), and K of those computers have crashed since X started running there."
  - "C crash(es) are on record on the M computers on X and nothing says when they were written, so they cannot be told apart from this build's."
  - "no computer on X has reported its crash counter, so nothing here says the build stays up."
  - "M computers have been on X for T min; the soak is N min.", with "The C crash(es) on record there were all written before X started running, so none of them are its." when that is so.
  Wrapped as "<version> has not soaked yet: <reason> Make it current anyway by confirming the override." An admin can override only by typing the exact version ("to override the soak gate, type the version number (X) into the confirmation box. Nothing changed."). No soak is needed for a build that has been current before (going back), and, for the automatic paths only, for a build older than the current one (a vendor withdrawal) or a studio's very first build. The first-run set-up program's builds are not soaked. The soak is 30 minutes by default; an admin can change it, and 0 turns it off.

### 18-025: The server shows, in one place, how it and the studio's computers stand against what the vendor offers.
- Where: releases-and-updates / Pushing updates and seeing who has what
- What: Shown: the server's version, the version the vendor offers for it and whether it is behind; when the feed was last checked and the last reason the server did not update itself; and for each operating system, the build currently offered to the computers and when it was published here, the newest the vendor offers, whether the fleet is behind the vendor, how many computers there are and how many are on the current build, and one line per build computers are actually running (count, publish date, whether current), including builds this server never published. A blank means not checked, never up to date. Sentences shown: "A newer CC Sync build for <platform> (<v>) is on offer and the computers here are being offered <current>. Update the dashboard first: it is <D> and the vendor is offering <DV>."; "The vendor is offering <v> for <platform> and the computers here are being offered <current>."; "<n> of <total> <platform> computers are on <current>."; "This dashboard is <D> and the vendor is offering <DV>."

### 18-026: A studio can choose to let editors' computers take any newer build by themselves.
- Where: releases-and-updates / Pushing updates and seeing who has what
- What: A site setting lets the app on each editor's computer install a newer offered build unattended. Off unless the site turns it on.
- Flag: dormant

### 18-027: An admin can set up the studio's Android app so it opens without an address bar.
- Where: dashboard / Phones and the installed app
- What: An admin enters the Android app's package name and its certificate fingerprints (one per line) and saves both together; a mistake saves nothing and shows the error with the admin's typed text kept. Saved: "Saved. This site now serves an asset-links statement." or, when either part is missing, "Saved. Both a package name and at least one fingerprint are needed before this site serves a statement." The server then tells Android, openly and without sign-in, that the app may open the dashboard without an address bar. A Check button shows what the site is serving right now, the site's own address, and a link to Android's own checker for that address, which the admin opens themselves; the server never contacts it. No link is shown when the site's address is blank or not a web address. Without a correct statement the app still opens, but with an address bar, and nothing says why.

### 18-028: The Timeline Cards Windows and Android apps can check the server for a newer version and download it.
- Where: releases-and-updates / Offering an update to a computer
- What: The check needs the editor to be signed in. The builds are placed in the studio's Timeline Cards folder by the vendor's publishing; nothing is uploaded through the dashboard. With none placed, the app is told "no app builds have been published". Only a build listed as the newest for its platform can be downloaded; anything else is "no such app build", and a listed build missing from the folder is "that build is listed but missing". Nothing about this is kept by the device's browser between checks.

### 18-029: The assistant's work goes to the first service the studio has set up, unless an admin pins one.
- Where: whole-product / The assistant
- What: The studio may set up several assistant services, in a fixed order of preference shown in that order to the admin. By default the first one that is ready (a key entered, or a program installed and signed in) is used, and the reason given names those it was chosen ahead of. An admin can pin one service; a pinned service that is not ready is a refusal, never a quiet fallback: "<label> is pinned but not available. Nothing else will be used in its place: clear the pin to fall back to the chain." With none ready: "no provider has a working credential", or more precisely that a program was too slow to start ("the server is busy ... try again in a minute") or is not signed in ("An admin must sign it in again"), quoting the program's own words with any secret removed. Some services answer only YouTube search; the help says which.

### 18-030: The assistant can be paid per use with a key, or run by a program on the server signed in with a personal subscription; the second is off unless the studio allows it.
- Where: whole-product / The assistant
- What: Subscription programs are off for a site unless an admin ticks "Allow CLI providers"; while off they are never run and their rows say so. In builds made without them they are hidden entirely, and pinning one is refused. Shown with them: "Using a personal subscription to power a service may breach its terms: that is your decision, not ours. Neither CLI is shipped, bundled or updated by CC Sync. SET UP downloads the publisher's own build, from the publisher's own servers, at your click, and checks it against the publisher's own checksum. The API keys above are the supported path."
- Flag: dormant

### 18-031: An admin enters, replaces and removes the assistant services' keys, and a key is never shown back.
- Where: whole-product / The assistant
- What: A key is shown only as its first 3 and last 4 characters around an ellipsis (a short key as just an ellipsis); it never appears in a log, a public setting or an address. A key set by whoever installed the server always wins, is shown as "set by the deployment" and cannot be changed or saved over from the page ("a key saved here would never be used"). Typed keys are refused, without quoting them, when blank, over 512 characters, containing control characters ("paste it again"), or containing any space ("paste the key alone, with no 'Bearer' prefix"). Each service has help: what it is, what it costs, where to get a key, what a key begins with, and three steps.

### 18-032: An admin sees each assistant service's state and can test it.
- Where: whole-product / The assistant
- What: States shown: available, not configured, not installed, not signed in, disabled by site, unknown. Test makes one live check: for a key, "<label> accepted the key", "no key is configured", "the key was refused (HTTP 401/403)", another error code from the service, or that the service could not be reached from the server; within 20 seconds. For a subscription program: that it answered (with its version), not installed ("Click SET UP to install it from the publisher, or set the full path of a copy you installed yourself."), or "installed but not signed in. Click SET UP and finish the sign-in step, or run <login command> on this host." Checking that a subscription program is signed in makes one tiny real request charged to the subscription. A state can be up to ten minutes old; one not freshly checked is marked "(not re-checked since)" or "not re-probed". An admin can type the full path of a copy installed by hand, which then always wins.

### 18-033: An admin can install a subscription program on the server from the publisher, with a set-up wizard.
- Where: whole-product / The assistant
- What: Steps: notice, install, sign in, test. The notice, titled "This uses YOUR subscription, on a shared server", explains that every YouTube search by every editor is spent on the signed-in account, that this may breach the subscription's terms, that CC Sync ships nothing and downloads the publisher's own build only when INSTALL is clicked, and that a key is the supported alternative; the admin ticks "I understand this uses my own subscription for a shared server". The install fetches the publisher's latest build and refuses it unless it matches the publisher's own published checksum and size ("the publisher published no checksum ... this install cannot be verified and was not done"). Progress is shown in steps with a percentage. Refusals before anyone clicks: a server not running the operating system the wizard installs for, an unsupported processor, an unsupported variant of the system, a data folder the server cannot write, or too little space (18-019). Failures say "Nothing was installed" and leave any previous version working; an install cut off by a restart says so and invites a fresh start. One install at a time. An admin can remove an install, which also removes its sign-in (refused while it is installing).

### 18-034: An admin signs a subscription program in from the dashboard, without a terminal.
- Where: whole-product / The assistant
- What: The page shows a link (or a short code to type on the publisher's page); the admin signs in with the publisher and pastes the code back. A choice of signing in with a subscription or with pay-per-use billing is offered where the publisher has both. The sign-in gives up after 5 minutes ("the sign-in was not finished within 5 minutes and was stopped"); one sign-in at a time; the admin can cancel. Codes are refused when blank, over 512 characters or holding control characters, and are never stored or shown. Success is confirmed by asking the program, and the account is shown with its e-mail masked (first and last letter of the name, then the domain), plus plan and organisation where known. A sign-in survives the server restarting; a saved sign-in that has expired and cannot renew itself says "Sign in again". Sign out removes the stored sign-in. Signing in from the page needs the server's usual operating system; elsewhere the admin is told to run the program's own login. The program never sees the server's other secrets or keys.

### 18-035: The server can keep a wizard-installed subscription program up to date by itself.
- Where: whole-product / The assistant
- What: Only when the site allows subscription programs and turns this on, and only for a copy the wizard installed (never one at a typed path). It looks about five minutes after the server starts, then at most once a day, and installs only a strictly newer version, with the same checks as a manual install, never while another install runs. Its outcome is recorded but nobody is told.
- Flag: dormant

### 18-036: The studio's public website can ask the server to name a piece of gear from a phone photo.
- Where: whole-product / The assistant
- What: The website's gear page sends a photo (under about 2 MB) and the studio's list of gear categories (up to 40); the server answers with a suggested packing-list entry: name, category, weight in grams of one item, quantity (1 to 99), a one-line note and how confident it is (high, medium or low). It needs a code the server derives from its own secret, which changes when that secret is changed; a wrong code is refused. It always uses the subscription program and ignores the admin's choice, pin and switches; errors say it is not installed, not signed in, stopped, gave no usable answer, or did not answer within 120 seconds. Photos are handled one at a time; the first after an hour's quiet is slower.
- Flag: differs: unlike every other use of the assistant, it follows neither the admin's choice nor the site's switches.

### 18-037: A studio installs the server on its NAS by naming just two folders.
- Where: server-install-and-running / Installing on a NAS
- What: The admin names the shared folder holding the studio's tree (projects, the b-roll archive and the music library) and a folder for the server's own state; the server refuses to start without either, naming the missing one. No secrets are typed: the ones the server needs for itself are made at first start and kept. Site facts are entered in the dashboard's first-run wizard. The NAS account and group the server acts as can be set; they must be a real NAS account's, nothing sets them, and a mismatch is only warned about in the server's log, so nobody is told. Missing "Projects", "Assets", "Assets/B-roll Archive" and "Assets/Music" folders are created; existing ones are not touched. A required secret that is blank, a placeholder or too short stops the server from starting. Documents for customers (how it works, setting up an editor, the legal paperwork) come with the server.

### 18-038: The server is reachable only on the studio's own networks.
- Where: server-install-and-running / Connections and credentials
- What: The dashboard answers only on the network addresses it is set up for (the studio's network and its private network), never on every address. In the simplest installation it answers only on the NAS itself and is reached from elsewhere through the studio's private network once the server has been signed in to it.

### 18-039: Editors' direct file access to the NAS is by key only and locked to the studio's tree.
- Where: server-install-and-running / Connections and credentials
- What: Each editor gets an account that can only transfer files, cannot log in to a shell, starts in the studio's tree and cannot leave it; passwords are never accepted. Files they write can be changed by the other editors. New editors are picked up within about 30 seconds; accounts are never deleted by this. If the dashboard cannot be reached, nobody's access changes, but a key cannot be checked and the connection is refused.

### 18-040: The server can host Resolve's shared project library, and refuses Resolve's default password.
- Where: resolve-on-the-editors-computer / Project libraries and projects
- What: Optionally, the server runs the database Resolve uses for a shared project library, reachable only on the studio's network and private network. It refuses to start while its password is empty or Resolve's well-known default (it says to set a long random password, never the Resolve default), and resets an existing library's password to the one configured.

### 18-041: Server crash reports stay on the server.
- Where: accounts-privacy-legal / What the product records about a person
- What: When the server fails, its crash reports are written on the server only and sent nowhere.

### 18-042: The server keeps its YouTube downloader current by itself.
- Where: youtube / Keeping the downloader working
- What: Where YouTube downloads are switched on, the server fetches the newest downloader at each start without delaying the start; it takes effect at the following start. Where the extra anti-blocking help is switched on, it is installed at start with up to four tries over about a minute; a failure never stops the server, and its outcome is shown on the YouTube health view.

### 18-043: The server can publish itself over https on the private network.
- Where: server-install-and-running / Connections and credentials
- What: The simplest installation carries an option to publish the dashboard over https on the private network, but as shipped it has no effect.
- Flag: unreachable
