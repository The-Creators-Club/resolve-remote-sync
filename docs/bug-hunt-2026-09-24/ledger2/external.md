## bug-comp-resolve-4 (owed from c-resolve) - SyncEngine/ResolveEngine/LibraryEngine have no stop(), so a restarted Cards role leaves engine #1's threads running
- Status: FIXED (in the Timeline Cards repo)
- Verified as: on HEAD (`a10ea03`) none of the three classes defines `stop`; `SyncEngine.__getattr__` forwards `stop` to the `ResolveEngine` thread, which has none, so the companion's `getattr(engine, "stop", None)` in `timeline_cards_role._release_engine` gets None and does nothing. `ResolveEngine.run` is `while True`; `GoogleTranslator._worker` (built by every `LibraryEngine.__init__`) is `while True`; the AHK `KeyHelper` process is only stopped by nobody. So after a role restart engine #1 kept sweeping (taking the bridge's API lock every tick), holding an AHK process, and fetching translations into the episode cache beside engine #2. The new test's (a) fails on HEAD's code (run from a `git archive HEAD` copy in the scratchpad: `AttributeError: 'ResolveEngine' object has no attribute 'stop'`).
- Fix (all `E:\Projects\Editing\Resolve\MulticamPipeline\`):
  - `multicam_pipeline/cards/resolve_engine.py`: `ResolveEngine._cards_stopping` (class attr, so `object.__new__` spikes work; deliberately not `_stop`, which is `threading.Thread`'s own); `stop(timeout=None)` sets it and returns at once (joins only when given a timeout; answers whether the thread is gone); the old `run` body is now `_sweep_loop` with `while not self._cards_stopping`, and `run` calls it and, when stopped, `_let_go()` on the engine's own thread (stops the key helper, drops `_resolve`/`_project`/`_mp_objects`). The flag is checked between ticks, so an apply in progress (an edit's keystrokes, a conform, a release) always finishes; stopping the key helper from the caller's thread could land between two keystrokes, which is why it happens on the loop's thread. A never-started engine lets go immediately. A HELD project is left closed on purpose (reopening is what the hold forbids; a reload ends it). `SyncEngine.stop(timeout=None)` = `LibraryEngine.stop` + `res.stop(timeout)`.
  - `multicam_pipeline/cards/library_engine.py`: `LibraryEngine.stop()` sets `_lib_stopping` and stops the translator; `_src_worker` on a stopped engine drops queued CLIP jobs (and their `_src_jobs`/`_vid_jobs` marks) but still runs PINNED jobs, whose owner (the dashboard's executor) waits on them; the one ffmpeg already running finishes (the recipes are `.partial` + first-writer-wins). `ProjectAgentEngine.stop` (the dashboard's engine) overrides without calling super, so the dashboard's behaviour is unchanged and cards_pool's no-eviction rule still stands.
  - `multicam_pipeline/cards/translate.py`: `GoogleTranslator.stop()` clears the queue and wakes the worker, which saves unsaved drafts and returns; `get()` queues nothing after a stop.
  - `tests/test_bridge.py`: its golden method-hash check forbade any new method; added `ResolveEngine.run` to `CHANGED` and a new `ADDED` dict (`ResolveEngine.stop`, `_let_go`, `_sweep_loop`, `SyncEngine.stop`), asserted from both ends like `CHANGED`. The golden itself was NOT refreshed, because a refresh would also bake the other session's uncommitted `_apply_conform` change.
  - `tests/run_all.py`: registered `test_engine_stop.py` (and in the `fleet` group).
- Regression test: `E:\Projects\Editing\Resolve\MulticamPipeline\tests\test_engine_stop.py` (24 checks: every thread a running engine started ends and the bridge is never taken again; the key helper is stopped once, on the engine thread; a stop mid-apply lets the apply finish; stop before start; the translator flushes and stops queueing; the media queue drops clip jobs but runs a pin) - fails on HEAD because SyncEngine has no `stop`.
