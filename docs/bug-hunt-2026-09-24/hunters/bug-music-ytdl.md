## Findings

### bug-music-ytdl-1 - the "share vanished" guard runs AFTER the download phase has created the project folder, so it can never fire
- Severity: high
- Confidence: CONFIRMED
- Where: ytdl/web/ytdlweb/worker.py:1617-1619 (ensure_outdir), worker.py:1683 (tree_missing_note); ytdl/web/ytdlweb/routes_api.py:1650-1666 (tree_is_gone)
- What: `_phase_download` calls `ensure_outdir(outdir)`, which is `os.makedirs` on `<PROJECTS_ROOT>/<label>/Youtube/<term>`, before it asks `tree_missing_note(job)`. `tree_is_gone` answers "not gone" as soon as `<PROJECTS_ROOT>/<label>` is a directory, and ensure_outdir has just made one. So when the bind mount is gone and its mount point is an empty directory on the overlay, the guard added for CR-286M always answers False. `_no_room_note`'s tree check (worker.py:1567) is reached after the same makedirs, so it is defeated the same way.
- Failure scenario: the NAS dataset is unmounted (or the container starts before it) while the host has room. An editor presses DOWNLOAD. The worker creates the project tree in the container overlay, finds it "present", downloads every clip there, and `ledger_add` records each one at a NAS-relative path with no file behind it. From then on every search or paste of those ids across the fleet is skipped as "the fleet already has that video", and the files are lost on the next container recreate. This is the exact outcome CR-286M says it fixed. The overlay folder also stays behind, so the press-time `_refuse_if_the_tree_is_gone` is fooled on every later press too.
- Evidence: probe_tree.py: `tree_is_gone` = True on the empty mount point, then `worker.ensure_outdir(...)`, then `tree_is_gone` = False and `tree_missing_note` = None. The CR-286M test (`test_bug_hunt_2026_09_18_webapps_tools.py::test_a_vanished_share_stops_the_download_even_when_there_is_room`) calls `tree_is_gone` directly and never runs `_phase_download`, so it cannot see the ordering.
- Ledger: regression of CR-286M (ytdl-web-5, 2026-09-18)
- Suggested fix: in `_phase_download`, check `tree_missing_note(job)` before `ensure_outdir`/`_sweep_stale`, and before the reclaim, which also writes. Also make ensure_outdir refuse to create `<PROJECTS_ROOT>/<label>` itself: only create folders below an existing project folder. Add a test that drives `_phase_download` with the mount point empty.

### bug-music-ytdl-2 - a browser upload can take a filename a fleet batch has already promised, and the companion's upload then overwrites it
- Severity: high
- Confidence: CONFIRMED (server half read and traced; the overwrite follows from the companion's `rclone copyto` argv, which has no `--ignore-existing`)
- Where: music/web/musicweb/routes_ingest.py:377-379 (queue_one -> db.unique_dest -> shutil.move); music/web/musicweb/db.py:524-537 (unique_dest); music/web/musicweb/ingest_batches.py:226-280 (allocate_name); companion/src/ccsync_companion/broll_upload.py:180-190
- What: A fleet `result` sets a name for an item (`ingest_items.dest_name`, plus a `tracks` row) that stays reserved until the companion uploads the audio later from its UploadQueue. The upload can come minutes later, or hours later if uploads are paused. `allocate_name` checks new names against the disk, that reservation ledger and `tracks`. The browser drag-and-drop path uses `db.unique_dest`, which checks only the disk. So during that window a browser upload with the same name (a different recording, so neither duplicate check catches it) is written to the reserved name.
- Failure scenario: Editor A's companion posts the result for `theme.wav` (row written, upload queued). Editor B drops a different `theme.wav` in the music page, which runs queued ingest on the container. `unique_dest` finds no file, so B's audio is moved to `Music/theme.wav`, B gets a `queue_add` row, and the page says "queued". A's `rclone copyto` then overwrites the file. `mark_uploaded` checks the size against A's declared size, sees a match and marks it live. B's recording is gone from the library with no error anywhere, and B's pending queue row now points at A's audio (the drain will analyse it a second time under the same rel_path).
- Evidence: traced `queue_one` -> `unique_dest` (disk `exists()` only) against `write_item_result` -> `allocate_name(reserved=reserved_names(conn))` and `_track_state`. `build_upload_command` builds `rclone copyto <local> <remote>` with only tuning and transport flags.
- Ledger: new (related to the 2026-09-03 music-3 / 2026-09-18 music-3 reservation work, which covered only the fleet side)
- Suggested fix: make the browser path pick its name the way the fleet does. In `queue_one`, call `ingest_batches.allocate_name(c, staged.name, reserved=reserved_names(c))` (or give `unique_dest` the same reserved + `tracks` checks) under a process-wide lock around the allocate-and-move. On the companion, consider `--ignore-existing` plus a 409 on an unexpected size, so an upload fails instead of overwriting.

### bug-music-ytdl-3 - the first fleet drop into a new library refuses itself from item 2 onward
- Severity: medium
- Confidence: CONFIRMED
- Where: music/web/musicweb/config.py:539-560 (share_root_ready); music/web/musicweb/ingest_batches.py:249-251 (allocate_name gate)
- What: CR-262E's fix samples the 25 newest and 25 oldest `tracks` rows and calls the share "not mounted" when none of them is on disk. That only works if the library already held files before this drop. A fleet `result` writes the `tracks` row before its audio is uploaded (the companion's UploadQueue runs separately from the embedding). In a library whose only rows come from the drop in progress, both ends of the sample are unlanded rows.
- Failure scenario: A new customer (or a new music share) drops an album through the companion. Item 1's result writes its row (the table was empty, so the gate passes). Item 2's result reaches `allocate_name`, and `share_root_ready` finds one row with no file, returning "the music library ... is there but empty ... looks like a share that is not mounted". The server answers 503 `share_not_ready` for every item until item 1's upload lands. With uploads paused (the metered-connection control this feature offers), or with a slow first upload, each item uses up its retry budget (about six tries over twenty minutes, per CR-262E) and fails permanently. The message blames a mount that is fine.
- Evidence: probe_ready.py: an empty `tracks` table answers `(True, '')`. After inserting one unlanded row it answers `(False, 'the music library at ... is there but empty: none of the indexed tracks are visible ...')`.
- Ledger: related to CR-262E (regression-10, FIXED) - the fix does not cover a library made only of in-flight rows
- Suggested fix: leave out rows with an unlanded `ingest_items` entry (state `indexed`/`uploading`) when sampling, or treat "every sampled row belongs to an unfinished batch" as a first run. Better still, use a positive marker such as a `.ccsync-music-root` file created at deployment.

### bug-music-ytdl-4 - cancelling a batch strands every indexed-but-not-uploaded track as a permanent row with no audio
- Severity: medium
- Confidence: CONFIRMED
- Where: music/web/musicweb/ingest_batches.py:1252-1257 (release, cancelled branch); ingest_batches.py:1238-1242 (docstring); ingest_batches.py:568-571 (retry_failed moves only `failed`)
- What: `release(state='cancelled')` sets every item not in (`live`, `duplicate`, `skipped`, `cancelled`, `queued_for_base_rig`) to `cancelled`, which includes `indexed` and `uploading` items that already have a `tracks` row. The docstring says such a row stays "`indexed` rather than `live` - visible in the ledger, fixable by re-uploading", but the item becomes `cancelled`. `cancelled` is terminal, `retry_failed` only moves `failed` items, and nothing on the NAS ever deletes the row (`prune_missing` runs only from a manual base-rig `--prune`).
- Failure scenario: An editor cancels a 40-track drop halfway through, or the sweep finalises a cancelled batch whose machine went away (`expire_stale_leases` -> `release(cancelled)`). The tracks already embedded but not yet uploaded stay in `tracks` for good: they show in search, similar and browse, `/api/audio/{id}` answers 404 "file missing", they count in the percentiles, tags and debias axes (which the module header says a row must only do when it has something real), and they keep their filename in the collision set. The editor has no button that can remove or finish them.
- Evidence: read `release` SQL and `_check_transition` (`cancelled` is in ITEM_TERMINAL, so no later post can move the item). `grep "DELETE FROM tracks"` over music/ finds only `db.prune_missing`.
- Ledger: new
- Suggested fix: on a cancelled release, delete the `tracks` rows (windows, peaks and tags cascade) of items that are `indexed`/`uploading` and whose file is not on disk, and call `drop_proxy`. Alternatively, leave those items `indexed` so the docstring's promise holds, and let `retry_failed` pick them up.
