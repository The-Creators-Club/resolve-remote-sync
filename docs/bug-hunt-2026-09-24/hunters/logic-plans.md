## Findings

### logic-plans-1 - unticking a project a machine holds through the unassigned bucket is a no-op that says "changed", and the tray then removes it from the person's OTHER computers
- Severity: high
- Confidence: CONFIRMED
- Where: dashboard/src/ccsync_dashboard/db.py:6841 (remove_selection) with db.py:7327 (selections_for_machine); companion/src/ccsync_companion/selection.py:499 (untick widening)
- What: `remove_selection(machine=M)` materialises the bucket onto M and deletes M's row, but when that leaves M with ZERO own rows, `selections_for_machine` falls straight back to the bucket, which still holds the project. The bucket is never cleared once a person has machines, so any machine whose own plan is emptied re-inherits it. The companion's untick reads that post-delete view, sees the slug still listed, and widens to the person-wide DELETE - which also deletes the OTHER computer's own row, the exact comp-lane-c-2 outcome its docstring says it prevents.
- Failure scenario: admin ticks project B for a new editor before any companion reported (bucket row). LAP and DESK register; DESK gets its own plan [B, A]; LAP has none and inherits [B]. (a) Admin unticks B in the LAP column of the grid: DELETE returns changed=true, the JS shows the box empty, LAP keeps syncing B, and on reload the box is ticked again - it can never be cleared per machine. (b) Editor presses the tray's "Remove B from this machine" on LAP: machine-scoped DELETE, view still lists B, companion issues the person-wide DELETE, DESK's own B row is deleted and the enforce cycle unshares B from the desktop within 60 s, with nothing on DESK saying why. The same re-inheritance happens whenever any machine unticks its last own project, or receives a copy of an empty plan.
- Evidence: p1.py - after `remove_selection(c,"ed","pb",machine="LAP")` -> `removed: True`, `LAP after untick ['pb']`, rows `[('', 'pb'), ('DESK','pa'), ('DESK','pb')]`, `fetch_machine_selections` still `{'pb': [('ed','DESK'), ('ed','LAP')]}`. selection.py:499-508 then issues `_delete_selection(base)` (no machine), which `remove_selection(machine=None)` turns into `DELETE ... WHERE editor_username=? AND project_slug=?`.
- Ledger: new (the dash-core-1 fix recorded near KNOWN_BUGS line 1685 handles the "first own row" case only)
- Suggested fix: once a person has at least one registered machine, move (not copy) bucket rows onto every non-wired machine that is still inheriting and then delete the bucket, so an emptied plan means empty; or record an explicit "has a plan, possibly empty" flag per machine. Until then the companion must not widen when the dashboard's `changed` was true.

### logic-plans-2 - the project page's person-level mode buttons tick the project onto computers that never had it, with no confirm and no capacity check
- Severity: medium
- Confidence: CONFIRMED
- Where: dashboard/templates/partials/project_detail.html:90-101 -> ui.py:1413-1418 -> db.py:6791 (add_selection_for_person)
- What: [ SWITCH TO FULL SYNC ] / [ SWITCH TO UPLOAD ONLY ] post `?mode=` with no `machine`, which is `add_selection_for_person`: it writes the mode onto EVERY non-wired computer of the person, INSERTing a new row on each one that did not have the project. The button reads as "change this tick's mode", but it is also a tick-everywhere, and unlike the plain tick button it carries neither the UX-1 capacity `hx-confirm` nor a list of the machines it will touch. It also flattens a deliberate "mixed" plan.
- Failure scenario: an editor ticked project A upload-only on LAP only (to push a card dump up). The page shows [ SWITCH TO FULL SYNC ]. Pressing it switches LAP to full AND adds a new full tick on DESK, so the desktop starts downloading every proxy of A (possibly hundreds of GB) and the enforce cycle shares the folder with it - no warning at any point. In the reverse direction, SWITCH TO UPLOAD ONLY on a laptop-only tick silently adds an upload-only tick to the desktop, and on a "mixed" person it turns the full desktop into upload-only, stopping its downloads.
- Evidence: p2.py - LAP upload_only only; `add_selection_for_person(..., sync_mode="full")` -> `[('LAP','pa','full'), ('DESK','pa','full')]`.
- Ledger: new
- Suggested fix: a mode switch should only UPDATE existing rows (a helper that sets `sync_mode` where a row exists, per machine or for all of the person's existing rows) and never insert; if a person-level change is intended, give it the same named-machines confirm and capacity sentence the tick button has.

### logic-plans-3 - section 4b trashes a whole local folder, including files the NAS never received, and the trash is kept 14 days, not the "year" the design promises
- Severity: high
- Confidence: CONFIRMED
- Where: companion/src/ccsync_companion/file_moves.py:522-568 (apply_move, not-synced-here branch); docs/HAND_MOVES_ON_THE_SERVER.md:95 vs companion/src/ccsync_companion/sync/lane_guard.py:73
- What: when the destination project is not synced on this machine, `apply_move` does `src.replace(trash)` for the entire source path. For an `is_dir` move that folder can hold originals lane A has not uploaded yet (a card dump in progress, an upload-only ingest machine, a laptop that was offline): the server only moved what it had. Nothing checks for local-only files, and the answer is ok=True / "trashed locally". The design doc says such a copy is "trashed locally (recoverable for a year)"; `DEFAULT_TRASH_MAX_AGE_DAYS = 14`, and the size cap and disk-pressure rule can prune it sooner.
- Failure scenario: an editor ticked project X upload-only and is part-way through uploading a 300 GB card dump in `X/Card_07`. The owner drags `Card_07` on the NAS into project Y, which this laptop does not sync (hand-move detection or the MOVE button, is_dir command). The companion moves the whole local `Card_07` into `.ccsync-trash/<stamp>/...`; lane A never looks there, so the clips that had not been uploaded are on no server, and prune_trash deletes them after 14 days (earlier on a full disk). The project page shows this machine as done.
- Evidence: file_moves.py:534-568 has no check of what is under `src` against what the server holds; lane_guard.py:73 `DEFAULT_TRASH_MAX_AGE_DAYS = 14`; HAND_MOVES_ON_THE_SERVER.md:92-97.
- Ledger: new (res-fleet-3 introduced the branch; comp-sync-1 fixed only the empty-plan trigger)
- Suggested fix: for a folder, trash only the files the server's inventory already holds at the destination (or refuse with `retrying` and keep the lane A exclusion open while anything local-only is inside), and either keep 4b batches out of the age/size prune or correct the doc so the owner is not promised a year.

### logic-plans-4 - a file moved out of a borrowed (shared) folder never reaches the machines that borrow it
- Severity: medium
- Confidence: CONFIRMED
- Where: dashboard/src/ccsync_dashboard/db.py:5842 (file_move_target_machines); companion/src/ccsync_companion/manifest.py:173 (per-file lists only for `rel_to_slug`)
- What: move targets are (a) machines whose plan ticks the SOURCE project and (b) machines whose `editor_media` lists the file. A borrower machine ticks the borrower, not the lender, and its manifest builds per-file lists only for `sequencer.rel_to_slug` (selected projects, never borrowed lender rels), so it is in neither set. Yet it runs lane A over `Projects/<lender>/<sub>` (never deletes), which is exactly the case comp-sync-3's `recent_excludes` fix was written for - that fix can only act on a command the dashboard never sends. The same manifest rule means (b) also stops finding a machine 14 days after its editor unticks a project (per-file rows are no longer refreshed and are pruned at MEDIA_REPORT_MAX_AGE_DAYS), so the docstring's "an editor who unticked the project still has the copy" holds only for two weeks.
- Failure scenario: Project P borrows `Lender/Shared B-roll`. An editor on P drops `drone_04.mov` into that borrowed folder on their laptop; lane A uploads it to `Lender/Shared B-roll/drone_04.mov`. The owner moves it on the NAS into `Lender/Selects`. Every Lender machine is told; the P laptop is not, so its next borrowed lane A run uploads `drone_04.mov` back to `Shared B-roll`, and the owner sees the file return.
- Evidence: db.py:5864-5883 (only `fetch_machine_selections(...).get(from_slug)` plus `editor_media`); manifest.py:173-176 `include_files = selected_keys is not None and nfc_key(project_rel) in selected_keys`; app.py:4141-4149 `_selected_project_rels` returns `rel_to_slug` only; api.py:9617-9621 per-file rows written only when the lists are present.
- Ledger: related to comp-sync-3 (bug-hunt-2026-09-03), res-fleet-3
- Suggested fix: add every machine whose plan holds a borrower of `from_slug` (db.fetch_borrowers_by_lender, the same map the enforce cycle uses) when `from_rel` is under that link's `sub_rel`; and have the companion build per-file lists for borrowed subtrees too.

### logic-plans-5 - the companion's "the dashboard does not know this machine" untick fallback can never fire; an unknown hostname gets a silent 200 no-op
- Severity: low
- Confidence: CONFIRMED
- Where: companion/src/ccsync_companion/selection.py:490; dashboard/src/ccsync_dashboard/api.py:2653-2677
- What: `untick()` falls back to the person-wide DELETE only on HTTP 404 for the machine-scoped call, but `api_untick` never validates `?machine=` (unlike `api_tick`, which 404s an unknown computer); it deletes 0 rows and answers 200 with `changed=false`. The companion does not read `changed`, so it reports "unticked" and the tray goes on to remove the local copy while the tick still stands under the name the dashboard does know.
- Failure scenario: a renamed PC inside SYS-18a's deferred-adoption window (its plan rows are still under the old hostname). The editor presses "Remove X from this machine": machine-scoped DELETE under the new name removes nothing, the view (bucket only) does not list X, the tray says done and clears the local folder; when the rename is adopted a report or two later the old plan, still carrying X, comes back and X downloads again.
- Evidence: api.py:2663-2677 has no `machines_of` check (compare api.py:2606-2616); selection.py:487-516 ignores `view["changed"]`.
- Ledger: new
- Suggested fix: make `api_untick` 404 a `?machine=` the account has never reported, as the tick does, and have the companion treat `changed=false` with the slug absent as "nothing to untick here" rather than success before a local delete.
