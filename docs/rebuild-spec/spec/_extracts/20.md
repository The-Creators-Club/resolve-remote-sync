# Extract of inventory section 20

## Items

### 20-001: The server remembers each project: its name in the tree, where it lives, when it was first and last seen, whether it is active or archived, and the health of its sharing.
- Where: dashboard / Projects
- What: For every project the server keeps its short name, its label (the path under the projects folder, for example "2025/FF4/Nuclear"), its full folder location on the NAS, when it was first and last seen, whether it is active, and whether, when and by whom it was archived. It also keeps the health of the project's sharing to editors' computers: the state it is in, any error text (for example "folder marker missing"), when that was read, and how many files and bytes the NAS itself still has to receive from editors. An inactive project disappears from every list, queue and backlog. While a project's folder is still found on the NAS, its label, location and last-seen time stay current and it counts as active again, unless it was archived: an archived project stays inactive however often its folder is seen.

### 20-002: An admin can archive a project and bring it back; archiving deletes nothing.
- Where: dashboard / Projects
- What: Archiving takes the project out of every list and queue and records who archived it and when. Before confirming, the person is shown everyone who still has the project ticked on any of their computers. Nothing is deleted: the folder, its project marker, its files and every tick on it survive. Archiving a project that is already archived, or does not exist, is refused. Unarchiving makes the project active at once (not at the next check) and clears the archive record; it is refused for a project that is not archived. The list of archived projects is newest-archived first and shows, for each, how many different people still have it ticked.

### 20-003: A project whose folder disappears from the NAS's sharing is taken out of the lists, but never in the first 15 minutes and never in a mass.
- Where: dashboard / Projects
- What: A project newly created gets 15 minutes before its absence counts, so a project whose sharing has not been set up yet is not removed in the gap. If one check would take out more than a quarter of the active projects (or more than 2, whichever is larger), nothing is taken out at all, and an admin sees a banner with the time, the counts, the limit and up to 100 affected projects. Its wording says the sharing reported 0 of N folders and nothing is being taken out, when the sharing reported no folders at all; otherwise that it reported X of N folders and K project(s) are not being taken out. The banner stays until a later check comes in under the limit. A problem card ("too many projects would have been marked gone at once") is raised as well.

### 20-004: There is a way to take vanished projects out regardless of how many, but nothing can use it.
- Where: dashboard / Projects
- What: An override that would take out every vanished project even past the mass limit exists, but no person or part of the product can reach it.
- Flag: unreachable

### 20-005: A project can include a folder of another project; the server tracks each such link and shares only the ones that work.
- Where: sync / What syncs where
- What: A project can declare that it includes a folder belonging to another project. For each declared folder the server keeps the borrowing project, the folder as declared, the lending project and folder it resolved to, a status (working, missing, or another word with a detail) and when the link was first and last seen. The list is refreshed at every check; a link that survives keeps its first-seen time, and a borrower that no longer declares anything loses its links. A borrower whose declaration could not be read for one check keeps its links, so one bad read can never unshare a lent folder from every borrower's computers; links are dropped outright only when the borrower is both gone and inactive. The lending project's page lists only working links, and only working links are shared to computers. A file move inside a lent folder is also followed by the borrowers' computers, for links that are working or missing.

### 20-006: Each computer's sharing connection to the NAS belongs to a person only when its name is a known editor's sign-in name, and sharing is never changed automatically for one that belongs to nobody.
- Where: sync / Computers joining and changing
- What: The server knows every computer that has ever connected to the NAS's sharing: its name, which person it belongs to (or nobody), whether it is the server itself, when first and last seen, whether it is connected now, its last address and when it last connected. Connection status is refreshed at every check. A connection belongs to a person when its name, lowercased and trimmed, is a valid sign-in name of a known editor. A valid sign-in name starts with a lowercase letter followed by up to 31 more lowercase letters, digits, dots, underscores or hyphens. A name that looks like a raw device identifier, or is not a valid sign-in name, or is not a known editor, belongs to nobody, and the server never adds or removes sharing for it on its own. Which person a connection belongs to is worked out afresh each time, not remembered.

### 20-007: For every project shared to a computer, the server shows how complete that computer is and how fast it is catching up.
- Where: sync / Saying truthfully what the sync is doing
- What: For each project and computer currently shared, the server keeps the percentage complete (0 to 100), the files, bytes and deletions still needed, the project's total files and bytes, a download speed, and when this was last updated. The speed is averaged over recent readings so it does not jump about, and starts afresh when new work arrives. The project list shows every computer's completion under each active project, ordered by person and then computer name, with projects in label order. When a project stops being shared with a computer, its completion and missing-file details are removed at once, so a computer that no longer syncs a project stops showing as behind on it. Forgetting a computer's connection removes all of this for it.

### 20-008: The server keeps a history of each computer's completion on each project, recorded on meaningful change.
- Where: sync / Saying truthfully what the sync is doing
- What: A history point is written for a project on a computer the first time it is seen; when the whole-number percentage changes; when the files still needed go from none to some, or change by more than 10 percent; every 15 minutes while incomplete; and, while complete, at most every 6 hours. After 48 hours the history is thinned to one point per hour, and after 30 days it is forgotten.

### 20-009: For a computer that is behind on a project, the server lists the files it is still missing, with sizes.
- Where: sync / What is owed
- What: At most 500 file names are kept per project per computer; a list cut at that number is marked as cut. The list is cleared when the computer is complete on that project, and forgotten when it has not been refreshed for 7 days.

### 20-010: The server keeps a record of every sign-in name it has positive evidence is a real editor.
- Where: accounts-privacy-legal / Who may sign in
- What: A name becomes a known editor when an editor's computer reports under it, when a project is ticked for it, when it already had sharing at the first start, or when an admin approves a computer or creates the account; the record keeps when it was first recorded and how. Anyone with a tick, with a chosen place for their footage, or whose computer currently reports also counts as a known editor. Names are compared in lowercase, and anything that is not a valid sign-in name is ignored.

### 20-011: A removed person's computer cannot re-admit them by reporting; only an admin can.
- Where: accounts-privacy-legal / Suspending, disabling and removing a person
- What: Deleting a person leaves a permanent removal mark. Only an admin re-creating the account, approving the person's computer, or suspending the name lifts it. A computer that keeps reporting under the removed name never does.

### 20-012: An admin can suspend a person's access for the whole studio, with a reason, and lift it again with nothing lost.
- Where: accounts-privacy-legal / Suspending, disabling and removing a person
- What: A suspension records when, by whom and why (a reason of at most 255 characters). It is refused for an invalid sign-in name or for a name that is not a known editor. The person's ticks are untouched by suspending and by lifting, so lifting restores exactly what was ticked. Lifting is refused when the person is not suspended. Suspending also lifts any removal mark on the name. If the server cannot read its records because they are busy, it says so as an error rather than treating the person as not suspended, so a busy moment can never re-share a suspended person's folders.

### 20-013: An admin can cut off every sign-in a person's computers hold, at once and for good.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: Revoking a person makes every computer sign-in issued to them before that moment stop working. A later clock change on the server cannot bring old sign-ins back. When the revocation comes with removing the person, the removal mark is set and a later revocation never unsets it. When an admin re-admits the person, sign-ins from before the removal stay dead. The record of this is kept without the person's readable name.

### 20-014: A key a person's set-up sent for signing in to the NAS waits for an admin to approve or drop it.
- Where: accounts-privacy-legal / Who may sign in
- What: The set-up on an editor's computer can send the key that computer will use to sign in to the NAS before an admin has finished creating the account. The server keeps the sign-in name, the key's fingerprint, the key (at most 4096 characters), the computer it came from (at most 128 characters), when, and where it came from. Sending the same key again replaces the earlier entry. A waiting key grants nothing; it is a list, newest first, that an admin approves or drops.

### 20-015: An admin can give each person their own reporting key for their computers, see when each was last used, and revoke it.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: A personal reporting key is shown in full only at the moment it is made; the server keeps only enough to check it, so it can never show it again. For each key it keeps the person, a label (at most 64 characters), who made it and when, when it was last used, and when and by whom it was revoked. Making one is refused for an invalid sign-in name. A key that fails for any reason (wrong shape, unknown, wrong, revoked) fails the same way, without saying which. Revoking keeps the record, marked revoked; revoking twice does nothing. The list leaves revoked keys out unless asked, ordered by person and then newest. Revoked keys are forgotten 180 days after revocation; live keys never are.

### 20-016: An admin can see which kind of key each computer last reported with, and so which computers a revocation will stop.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: For each computer the server records whether it last reported with the studio-wide shared key or with a personal key, and which personal key. An admin is shown which computers will stop reporting when a given key is revoked, and how many computers are still on the shared key, listed as person/computer. Where it is not known, it shows "cannot tell", never "none".

### 20-017: A person can set a display name shown instead of their sign-in name, with exact rules and refusals.
- Where: accounts-privacy-legal / What the product records about a person
- What: A display name is only a label shown on screen; it is never used to identify anyone. It is tidied before saving: accented characters are stored in their composed form, the ends are trimmed and every run of spaces, tabs or line breaks becomes one space. It is refused with these exact sentences:
  - empty after tidying: "A name cannot be empty. To go back to your sign-in name, clear the box and save."
  - longer than 64 characters: "A name can be at most 64 characters."
  - containing any control, invisible (for example zero-width or right-to-left override), private-use or unassigned character: "A name cannot contain invisible or control characters."
  - equal, ignoring capitals and accent spelling, to another person's sign-in name or display name (any known editor, any account, anyone with a profile, or a configured admin): "Someone else already goes by that name. Pick another." A person's own sign-in name in any capitalisation is allowed.
  Two people can never claim the same name at the same instant. Clearing the box deletes the display name and the sign-in name shows again.

### 20-018: On sites that use the product's own sign-in, the server keeps each account's role, whether it is disabled, and whether its password must be changed.
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: Each account has a sign-in name, a password kept only in a form that cannot be read back, a role (admin or editor, nothing else), when it was created, a disabled flag and a "must change password" flag. Each account can also hold keys for signing in to the NAS, each with a fingerprint, when it was added and a label.
- Flag: undetermined: whether "must change password" is enforced anywhere

### 20-019: The server keeps a register of each person's computers, recognises a computer after it is renamed, and lists them oldest first.
- Where: dashboard / People and computers
- What: Each computer is known by its owner's sign-in name and its computer name, with its own lasting identity, its platform, its sharing connection, and when it was first and last seen. Every report creates the entry or updates its last-seen time; a report that leaves out the identity, platform or connection keeps the old values. A person's computers are listed oldest-registered first. The computer's own lasting identity lets the server recognise it under a new name; where two entries carry the same identity, the one heard from most recently is taken.

### 20-020: One sharing connection belongs to one computer: the computer reporting it takes it from any other.
- Where: sync / Computers joining and changing
- What: When a computer reports a sharing connection that another registered computer also holds, the other computer loses it and the reporting computer keeps it. The other computer's ticks are untouched.

### 20-021: A computer is shown as live when it reported in the last 5 minutes, and as lost after 7 days of silence, with the projects still ticked for it.
- Where: dashboard / Each computer's state
- What: A computer counts as live when its last report reached the server within the last 5 minutes by the server's own clock; an unreadable time is not live. A computer silent for 7 days is listed as lost, together with the projects still ticked for it.

### 20-022: When a computer is renamed, its plan and everything waiting for it follow it to the new name.
- Where: sync / Computers joining and changing
- What: When the server recognises a computer under a new name, its ticks, its chosen place for footage, its requested original files, its unanswered file moves and Resolve undo requests, and a waiting settings request all move to the new name, and the old entry is removed. What the computer last said it holds on disk and its transfers are not moved: they rebuild under the new name and the old ones are forgotten in time. The move is refused, with nothing changed, when the new name is already a registered computer of that person, so a clash of names can never destroy a plan. The one exception: when it is already confirmed to be the same computer (same lasting identity, old name quiet), it may take over an existing new-name entry that has no ticks and no chosen place of its own. A finished settings request at the new name gives way to a waiting one from the old name; a waiting one at the new name is kept.

### 20-023: Only a person's 20 most recently reporting computers keep their current state; older ones are dropped unless they still have ticks or a sharing connection.
- Where: dashboard / People and computers
- What: After every report, only the 20 computers of that person that reported most recently keep their latest-report details. An older computer loses them, and its register entry is removed too, unless it still has ticks of its own or still holds a sharing connection; then it is kept and shows as lost until someone presses Forget. Nobody is told this happened, beyond the computer showing as lost. Ticks are never deleted by this limit.

### 20-024: An admin can forget a computer, which clears everything the server holds about it now but keeps its history.
- Where: dashboard / People and computers
- What: Forgetting one computer removes its register entry, latest-report details, ticks, chosen place for footage, sync state, live transfers, its lists of what it holds on disk, its Resolve bin listing, its key record, its waiting file moves and Resolve undo requests, its b-roll stand-in records, its settings request, its requested original files and its diagnostics. The history of its sync state and its finished transfers is kept on purpose. The person's ticks that apply to any of their computers are not touched. Its sharing connection is removed from the NAS first. Forgetting is refused when no such computer is registered. Forgetting is not a ban: if the app is still running there, the computer registers again with its next report.

### 20-025: For each computer, the server shows what its last report said about it, and a report that says nothing about something does not erase what was known.
- Where: dashboard / Each computer's state
- What: Each computer's latest-report details include: the project folder the app detected, the Resolve project open, whether the report proved who sent it, when it arrived, the app's version, platform and processor type, whether the computer is wired to the server or an editing computer, connection counts (relayed and direct), leftover partial files and their size, the size and count of its trash, a counter of files skipped because they already existed (with the project it refers to), the disk-space floor it keeps, its proxy coverage (missing proxies, whether it is making proxies, how many are left), its free and total disk space, and how often it rotates between projects. A value like these is replaced only when a report carries a new one, so a report that is silent on it leaves the last known value. The open Resolve project and the detected project folder are updated by every report.

### 20-026: The safety conditions a computer reports clear themselves as soon as a report says they are over, and an unknown is never shown as "no".
- Where: sync / Saying truthfully what the sync is doing
- What: These conditions are rewritten (including back to nothing) by every report that carries them, and left alone by a report that does not: proxy downloading stopped by itself (with reason and time), a studio-wide or computer stop (with scope and reason), the computer's sharing not running (since when, how many times the app tried to restart it, last error), how many times the app has crashed and its newest crash report, folders being shared without the product's filters (count and names), the number of sharing conflicts, and transfers the app killed because they stalled (which direction, how long, when). A computer whose last report did not carry them answers "cannot tell" to questions such as "has its downloading stopped itself", never "no".

### 20-027: The server notices when a computer's clock is wrong.
- Where: sync / Clocks and file age
- What: Each report carries the computer's own time. The server keeps how far ahead or behind it is (ahead counts as positive) and flags a difference of more than 60 seconds. A computer time more than 7 days away from the server's is not trusted as a time, though how far off it is is still kept. An unreadable time is shown as unknown, never as "no difference".

### 20-028: A computer shows whether it is busy indexing b-roll or music, and the progress, and stops showing it as soon as it stops.
- Where: dashboard / Each computer's state
- What: Every report says whether a b-roll or music indexing batch is running on that computer; a report that does not mention it counts as not running. The batch, its state, done and total, failures, the clip or track being worked on, the percentage, the quality level (for b-roll) and any warning are replaced whenever the report carries them, so a report without a warning clears an old one.

### 20-029: For each computer the server shows why it is not syncing, in the app's own words, and how often its syncing has had to restart.
- Where: sync / Saying truthfully what the sync is doing
- What: The app's own reason for not syncing, its detail and since when; and how many times its syncing restarted in the last 24 hours, the last time and the last error. Cleared by the next report that says syncing is fine.

### 20-030: For each computer the server shows how its last update went, including an update it fled after crashing.
- Where: releases-and-updates / Pushing updates and seeing who has what
- What: The version it tried to install, how many attempts, the last error and when it last tried. The error "crash-looped" means the new version kept crashing and the computer went back to the one before, never that a download failed. The version it went back from is shown until the computer runs that version or a later one, then disappears on its own. When a computer goes back like this, any update pushed to it for that version is withdrawn, recorded as done by the system with the reason "crash-looped and rolled back". An update the computer refused on receipt is shown with the version, the reason and the time; nothing shown means it is not refusing.

### 20-031: The server records how long each computer has run its current app version.
- Where: releases-and-updates / Trying a build on one computer first
- What: When a computer first reports a version (or first reports at all), the server notes the time. This "running this version since" is what decides whether a new version has been tried long enough (see the soak rule).

### 20-032: For each computer the server shows the health of its Resolve: clips outside the tree, missing clips, stray project folders, and projects whose footage exists only on that computer.
- Where: resolve-on-the-editors-computer / Missing clips, relinking and refreshing
- What: Shown per computer: clips used from outside the shared tree, clips with a wrong drive or path start, missing clips, ignored clips, when Resolve was last scanned, stray project folders (count and size), project folders that were moved, bytes waiting in a folder for footage to be brought in, and the Resolve projects not currently open that hold clips found only on that computer (with counts, and when that was scanned). Also: whether the app is connected to Resolve, whether a project is open, how long and on what Resolve has been stuck, the missing clips, clips refused because their paths were outside the tree, proxies attached and proxy gaps, and stills. Each part is rewritten by every report that carries it, so a problem that is over clears.

### 20-033: For each computer the server shows whether its "Send to Resolve" receiver is working.
- Where: broll / Sending a clip to Resolve
- What: Whether it is on, whether it is listening, on which port, any error and since when. When nothing is known, it shows that the computer is too old to say, never that it is listening.

### 20-034: The server lists up to 20 undo records each computer holds for changes the app made in Resolve.
- Where: resolve-on-the-editors-computer / Fixing media: copying in, rehearsals and undo
- What: A report that does not include the list keeps the last one; a damaged list reads as empty.

### 20-035: For each computer the server knows what heavy work it can do and whether it is free now.
- Where: fleet-jobs / What a computer can honestly offer
- What: Kept per computer, replaced whole when reported and kept when not: whether it has a graphics card, its name and memory, a hardware video encoder, the video tools, speech-to-text and the assistant's tools being present (with a detail), which network drives it has (at most 16), processor count, how long it has been idle, its load, whether Resolve is running and which project, whether it takes shared work at all (yes unless said otherwise), which kinds of work it takes (empty means every kind), until when it is volunteering, and the state of its Timeline Cards link to Resolve (connected, state, timeline, version, since, a detail, when it last checked in). When the idle time is unknown the computer is treated as not idle; zero means someone is typing. A computer that never said what it can do is offered no work that needs anything.

### 20-036: A computer is either wired to the server or an editing computer; a person whose every computer is wired syncs nothing.
- Where: sync / Wired or remote
- What: The computer's latest report decides whether it is wired; failing that, the last thing it said alongside its disk lists; failing both, it is an editing computer. A person counts as wired-only when every known computer of theirs is wired; a person with no computers is not wired-only. Where the server needs "the" project folder or latest state of a person, it takes the most recently reported computer.

### 20-037: An admin can push an update to one computer, which takes it on its next report; an unanswered push expires after 14 days.
- Where: releases-and-updates / Pushing updates and seeing who has what
- What: The push records the version, when, by whom, and which version the computer was on, so the server can tell an upgrade from a rollback. The server may hold the push back and says why in one sentence; until it has decided, the computer is given no shared work, as it is about to change version. A push is cleared when taken. Unanswered for 14 days, it expires, recorded as done by the system with "not taken within 14 days". Before a second click, the admin sees what is already waiting for that computer (an update and its time, a resume request, a diagnostics request). Every push is recorded in the audit history. Refused when no such computer exists.

### 20-038: An admin can ask a computer to restart proxy downloading after it stopped itself; the request clears only when the computer reports downloading running again.
- Where: sync / Safety stops
- What: The request records when and by whom and is recorded in the audit history. It clears when the computer reports that downloading is no longer stopped, so it can never clear a later stop. Refused when no such computer exists.

### 20-039: An admin can ask a computer "why" and receive a diagnostics report from it; the server keeps a few recent reports per computer.
- Where: dashboard / Reports from computers
- What: The ask records when and by whom and is recorded in the audit history; the button shows it has been asked until the asked-for report arrives (not merely until the ask is sent). Each report keeps the person, the computer, what triggered it, the computer's time, when it arrived, and its text (up to 256 KB). Only the newest 5 per computer are kept, and any older than 30 days are forgotten. Lists are newest first, at most 200; a per-computer view shows each computer's newest report.

### 20-040: When a computer's report is turned away because the server cannot confirm who sent it, the admin sees when and why.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: Nothing else from the unconfirmed report is kept. The reason is at most 200 characters and only already-registered computers are marked; any accepted report clears the mark. Computers whose sign-in was made under a retired signing key are listed with the time (up to 200, newest kept) until they report on the current key.

### 20-041: Each tick records who made it, when, its place in the computer's order, and whether the project syncs fully or only uploads.
- Where: sync / A plan belongs to a computer
- What: A tick names the person, the computer (or none, for ticks made for the person rather than one computer), the project, its place in that computer's order of work, who made it and when, when it last changed, and its mode. There are two modes: full (originals go up, proxies and everything else come down) and upload only (originals go up and nothing comes down, and the project is not shared to that computer at all). Any other mode is refused with "unknown sync mode".

### 20-042: A computer syncs its own ticks; only a computer with no ticks of its own takes the ticks made for its person.
- Where: sync / A plan belongs to a computer
- What: Ticks made for a person without naming a computer apply to any of that person's computers that has no ticks of its own at all (in either mode). A wired computer syncs nothing, by its own ticks or otherwise. A person with no registered computer keeps such ticks, and still counts as having the project ticked. When an older app asks for its person's plan without naming its computer, it gets everything ticked on any of that person's computers (each project once, in the earliest position), so it syncs too much rather than too little. Where a person's computers disagree about a project's mode, that project shows as mixed for the person.

### 20-043: The admin's tick grid shows ticks that a wired computer holds, though such a computer never syncs them.
- Where: dashboard / Ticking and unticking
- What: A wired computer's own ticks still appear on the admin's grid and in the list of a computer's projects, while the computer's real plan and the sharing leave them out.
- Flag: differs: shown on the grid, left out of what actually syncs

### 20-044: Ticking a project for one computer never silently drops the ticks it was taking from its person.
- Where: sync / A plan belongs to a computer
- What: If the computer had no ticks of its own, it first receives its own copy of the person's ticks (keeping who ticked them and when), then the new project is added at the end of its order. Ticking a project already ticked in the other mode switches the mode and keeps its place in the order. The person is told whether anything changed.

### 20-045: Ticking a project for a person ticks it on every computer of theirs that is not wired.
- Where: sync / A plan belongs to a computer
- What: A person with no registered computer gets a tick their first computer will take. A person whose every computer is wired gets nothing.

### 20-046: Unticking a project for one computer leaves the person's other computers syncing it; unticking it for the person removes it everywhere.
- Where: sync / A plan belongs to a computer
- What: Unticking for a person (which is also what an older app's untick means) removes the project from every computer of theirs and from the person's own ticks. Unticking for one computer that was only taking the person's ticks first gives that computer, and every other non-wired computer of the person, its own copy of those ticks; then the project is removed from the person's ticks and from this computer only, so the others keep syncing it. An untick on a computer that never had the project changes nothing. Every untick also drops that computer's requests for original files in that project; files already downloaded stay where they are.

### 20-047: A person can copy one computer's plan onto another.
- Where: sync / A plan belongs to a computer
- What: The target's ticks are replaced by the source's: the same projects in the same modes, in the same order, recorded as made by the person copying. The target's requests for original files in projects the source does not have are dropped; the source's requests are not copied. Refused with "'<source>' is wired to the server: it works directly off the NAS and holds no plan, so there is nothing to copy from it" when the source is wired, and with "<source> has no projects ticked - copying it would empty <target>." when the source has nothing ticked (counting ticks it takes from its person).

### 20-048: Every tick and untick can be undone, including an untick of a project a computer was only taking from its person, and recent plan changes are listed.
- Where: dashboard / Ticking and unticking
- What: Before and after each change, the server notes where the project is ticked for the person and in which mode, naming each computer that held it, even by inheritance, so the change can be shown and undone. Ticks and unticks of the last hour are listed newest first (at most 200), each marked when it has since been undone.

### 20-049: Each computer, or a person as a whole, can have a chosen project that its new footage lands in.
- Where: sync / Project folders on an editor's computer
- What: A computer's own choice records who set it and when. A computer without its own choice uses its person's; asked about a person with neither, the server uses any of their computers' choices.

### 20-050: A Resolve project name is tied to a project in the tree once, permanently; only an admin can change or remove the tie.
- Where: resolve-on-the-editors-computer / Knowing which project is open
- What: Each Resolve project name (trimmed, capitals ignored) is tied to one tree project, recording whether it was matched automatically, by an editor or by an admin, who and when. The first tie wins and cannot be set again (two at the same moment cannot both win); only an admin may change or delete it. A person may make a first tie only for a Resolve project name one of their own computers has reported having open (an admin may tie any). Resolve project names that computers have reported and that have no tie are listed for an admin.

### 20-051: The product ties a Resolve project name to a tree project on its own only when exactly one project has that name and no unregistered folder rivals it.
- Where: resolve-on-the-editors-computer / Knowing which project is open

The studio grid shows, for each computer holding work: its kind, state, last sign of life, when its hold runs out, its percentage (unknown rather than 0 when not reported) and its file. The work page shows finished work for 24 hours; finished work is forgotten after 30 days; queued work never is.

### 20-093: Each kind of shared work has its own number of tries and its own studio-wide limit on how many run at once.
- Where: fleet-jobs / Failures, retries and the queue
- What:

| Kind | Shown as | Tries | At most running at once |
|---|---|---|---|
| Speech-to-text | (the name of the present speech-to-text tool, in capitals) | 3 | 2 |
| Small proxy | PROXY 480p | 3 | 4 |
| Sound taken out | AUDIO | 2 | 4 |
| Sound picture (waveform) | PEAKS | 2 | 4 |
| Camera card copy | CARD COPY | 2 | 4 |
| Drive copy | DRIVE COPY | 2 | 2 |

  Work of a kind the server does not know is accepted (3 tries, 4 at once, shown as its kind in capitals) but never given to any computer. The labels shown are the present build's; the rebuild should name speech-to-text in its own words.

### 20-094: Shared work moves from queued to taken to running to done; a computer that goes silent for 5 minutes loses it, and work that keeps failing is either taken over by the server or given up.
- Where: fleet-jobs / Failures, retries and the queue
- What: A computer takes queued work, and it shows as running from the computer's first sign of life. A hold runs out after 5 minutes without a sign of life; the work goes back to the queue with "the lease held by <person>/<computer> expired at <time>" (the rebuild may word this more plainly). Every failure and every lost hold uses up a try. A failure the computer says is not worth retrying ends as failed. When the tries are spent, a small proxy, a sound extraction or a sound picture is taken over by the server itself (holder shown as "(dashboard)"), never given back to the computers, and ends done or given up; any other kind is given up. Work the server has taken over does not count towards the studio-wide limit and resumes after the server restarts. A computer's report that it finished is accepted even after its hold ran out, as long as nobody else took the work. Finished states are done, failed and given up.
- Flag: differs: three media kinds fall back to the server, every other kind is simply given up

### 20-095: Work goes to computers highest priority first, then oldest, one piece per computer, and one kind's backlog never hides another's.
- Where: fleet-jobs / Choosing who runs what
- What: Waiting work not asked to stop is considered highest priority first, then oldest, looking at up to 200 per kind so a long queue of one kind cannot hide another. A computer gets a piece only if it is still waiting, has not been asked to stop, fewer than the kind's limit are running across the studio, and the computer still has what the work needs at that moment. A computer can narrow which kinds it takes, but never widen what it was offered. A computer holds at most one piece at a time. Each computer is told how much work is waiting, running and taken over by the server, and how old the oldest waiting piece is (empty, not zero, when nothing waits). Forced work and work for a chosen computer are kept as asked, even when the chosen computer is unknown. A computer's own list of kinds, when empty, means every kind.
- Flag: undetermined: the studio-wide limit can be overridden by a setting whose default is not given here

### 20-096: Work that needs something a computer lacks says exactly what is missing.
- Where: fleet-jobs / When a computer counts as free and able
- What: Messages: "this computer has no X mount" (a network drive it needs); "X is not available on this computer" or "X is set on this computer" (a yes/no need); "X is V, the job needs at least W" (an amount); "X is V, the job needs W" (anything else).

### 20-097: A computer whose work failed is rested for 2 minutes before it is given more.
- Where: fleet-jobs / Failures, retries and the queue
- What: After a failure worth retrying (not a cancellation), the computer is rested with "job #N (<kind>) failed here: <first 120 characters of the error>"; after losing a hold, with "job #N (<kind>) lost its lease here". A successful finish clears the rest.

### 20-098: Cancelling shared work ends waiting work at once and asks a computer to stop running work; nothing is forced to end behind a live process.
- Where: fleet-jobs / Stopping and cancelling
- What: Waiting work becomes failed at once with "cancelled by <who>" (an admin unless named). For work a computer holds, or the server has taken over, the request is recorded; the computer is told on its next report and the server's own worker checks it. If the holder then reports a failure, it ends with "cancelled: the holder reported a failure instead (...)"; if its hold runs out, "cancelled: the lease held by ... expired at ... without an answer". Cancelling finished or missing work does nothing.

### 20-099: A person can try finished work again, which makes a new piece of work and leaves the old one as it was.
- Where: fleet-jobs / Failures, retries and the queue
- What: The new piece has the same kind, files (with a pointer to the old one), needs, cost, priority, force and chosen computer. Refused with "job #N is <state> and has not finished, so there is nothing to try again yet. Cancel it first." or "job #M is already a new attempt at job #N and it is still on the queue."

### 20-100: An admin or the computer's owner can ask one computer to change whether it takes shared work and which kinds; whether it is wired or remote can never be asked for.
- Where: fleet-jobs / What a computer can honestly offer
- What: Only two settings can be asked for: whether the computer takes shared work, and which kinds (a list of kinds; naming every known kind means every kind). One request per computer; refused for an unregistered computer, and refused with "no computer setting to request" when it asks for nothing valid. A new ask while one waits is merged in, the newer value winning for each setting, and sent again. A finished request is replaced outright. States shown: waiting, applied or refused (from the computer's answer, recorded as done by the editor), withdrawn (by an admin, only while waiting) or expired (waiting for 14 days, recorded as done by the system with "not answered within 14 days"). An answer to an older request is ignored; an answer that is neither applied nor refused leaves the request waiting with an updated detail. Every step is recorded in the audit history.

### 20-101: Each computer reports which of its settings can be changed from afar, and its current values, so a person sees them before asking.
- Where: dashboard / Each computer's state
- What: Reported: which of the two settings it can accept (nothing means it cannot take a request), its volunteer minutes (0 to 100000), its sync-drive reminder minutes (0 to 100000), whether YouTube downloads, YouTube sign-in and the YouTube terms are on, off or unknown, its YouTube sign-in state, and which settings are waiting for the app to restart. A report without this keeps the last one. When it does not say what is waiting for a restart, that shows as "cannot tell", not "nothing waiting".

### 20-102: Each computer, and the site as a whole, can withhold four kinds of report, and what is withheld is deleted from the server and never shown as zero.
- Where: accounts-privacy-legal / What the product records about a person
- What: The four kinds are: the open Resolve project, the list of files the computer holds, the Resolve bin listing, and how long the computer has been idle. Withholding the Resolve project also withholds the bin listing. A computer withholds whatever it switched off itself plus whatever the site switched off; a report that does not repeat its own list keeps the last one. On withholding, and at every later report, the server deletes for that computer: for the Resolve project, the open project, the Resolve health details and the list of unopened projects, and the project names on its undo records (blanked, identifiers masked); for the file list, its file lists and totals, and also its missing and refused clip paths unless the Resolve project is also withheld; for the bin listing, its bin listings; for idle time, its idle time. Newly withholding any of the first three also deletes that computer's diagnostics. When the site switches a kind off, it is deleted for every computer, including ones known only from their file lists, and a newly withheld kind that diagnostics can contain deletes every diagnostics report. Switching a kind back on brings nothing back. Everywhere, a withheld kind reads as "not reported", never as zero or none.

### 20-103: The server records how each computer's report reached it: secure, plain on the studio network, or plain over the public internet.
- Where: server-install-and-running / Connections and credentials
- What: Recorded only when it changes; any other answer is refused.

### 20-104: The server records which licence each computer's editor accepted, and when.
- Where: accounts-privacy-legal / The licence a person accepts
- What: Version, time of acceptance and a fingerprint of the licence text, each up to 128 characters. A report without a version leaves it alone. Nothing recorded means "not reported", never "not accepted".

### 20-105: An admin can export everything the server holds about a person, with secrets left out.
- Where: accounts-privacy-legal / What the product records about a person
- What: The export covers the person's computers and their current state, ticks (including ones they made), preferences, sync state and transfers, file lists, bin listings, key records, file moves and Resolve undos sent to their computers, stand-ins, settings requests, requests for originals, their sharing connections (name and last address), safety-rule findings naming them; their identity (known-editor record and suspensions they made, profile, account with the password left out, NAS sign-in keys, waiting keys, reporting keys without their secret); their history (sync history, finished transfers, completion history, missing-file lists, diagnostics); and evidence (audit entries by them or about them, alerts, problems, shared work, file moves, Resolve name ties they set, builds they published without the signature, projects they archived, site settings they changed without the value). Something is about a person when it carries their name, starts with "name/", or names a computer only they use (a computer name shared with someone else does not count). Not included: sign-in sessions and sign-in attempts, YouTube download jobs, downloads and attestations, b-roll and music indexing batches, and client folders and their contents.

### 20-106: An admin can erase a person's history without removing the person.
- Where: accounts-privacy-legal / What the product records about a person
- What: Erasing deletes only the history: sync history, finished transfers, completion history, missing-file lists and diagnostics. Their current state, identity and the evidence stay.

### 20-107: An admin can delete a person: everything about them now goes, and what must stay as evidence is kept under a stand-in name.
- Where: accounts-privacy-legal / Suspending, disabling and removing a person
- What: Deleting gathers every computer name the person ever reported under, erases their history, forgets each of their registered computers, deletes everything kept per computer under their name (including ticks made for the person and computers that were never registered), their diagnostics, their sharing connections and completion records, their known-editor record and profile, and their membership of project groups; then it replaces their name in what remains. Their revoked reporting keys are deleted; live keys never are (they are revoked first).

### 20-108: A deleted person and their computers become the same stand-in name everywhere, for good.
- Where: accounts-privacy-legal / Suspending, disabling and removing a person
- What: A person becomes "deleted-user-" and a computer "deleted-machine-", each followed by 10 characters derived from the name with a site secret made once and never changed, so one person is always the same stand-in. Fields saying who did something are replaced exactly. Audit entries by the person are replaced, unless the person was an admin: those keep the name until they are forgotten at 180 days. Subjects are replaced only where a name stands (the name, "name/...", and the computer after "name/"); a bare computer name only on an entry already tied to the person. Free text (alert details, problem descriptions and advice, audit details) is rewritten only on entries tied to the person, whole names only and with exact capitals, so "alice-b", "alice.smith" and "Send a test email" survive deleting "alice" or "test". A computer name someone else also uses is never rewritten. The computers holding or chosen for shared work are rewritten. Where a renamed problem collides with an existing one, the newer is kept.

### 20-109: The server's set-up wizard remembers how far it got, so it survives a restart.
- Where: server-install-and-running / Installing on a NAS
- What: For each set-up task: its status (to do until changed), a detail, a time and whether it was skipped.

### 20-110: The server keeps every run of its mailed server check, the actions each offered, and the replies it acted on.
- Where: dashboard / Alerts by mail
- What: For each run: start, finish, status, the report, whether the mail went out, a detail, and a reply reference that can be checked but not read back, with its expiry. For each action a run offered: its number, what it does, why, its state (offered at first), the result, the reply that acted on it and when. For each reply mail handled (once per mail): when received, the sender, the run, the verdict and a detail.
- Flag: undetermined: whether any of this is ever forgotten (another note says 60 days; nothing here does it)

### 20-111: If the server is put back to an older version than its own records, it refuses to start and says which version to deploy.
- Where: releases-and-updates / The server updating itself
- What: The message says the records were written by a newer server than this one, gives both record versions, and tells the admin to deploy the matching or a newer server. An update of the records that was interrupted half way carries on from where it stopped at the next start.

### 20-112: When the server's records are busy, it says so rather than answering "nobody" or "nothing".
- Where: whole-product / Could not check, refusals and nothing silent
- What: For suspensions, archives, waiting keys, revocations and personal data, an empty answer is given only when the server is too old to hold that information; a busy or failing record store is reported as an error. So a busy moment can never re-share a suspended person's folders or bring back a revoked sign-in.

### 20-114: Lists the server keeps short by count rather than by age.
- Where: accounts-privacy-legal / What the product records about a person
