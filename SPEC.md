# Resolve Remote-Editor Sync System ("Creators Club Sync")

## Context

Remote editors will collaborate on the self-hosted Resolve Project Server (postgres:13 app on TrueNAS `192.168.0.102:5432`) over Tailscale. Blackmagic Cloud's media side must be replicated self-hosted, with three automatic behaviors:

1. **Proxies auto-download** to each editor's machine, recreating the server's folder tree exactly.
2. **Anything an editor adds to a timeline auto-uploads** to the *same relative folder* on the NAS (music in `Audio\Music` locally → `Audio\Music` on NAS), so every Resolve workstation picks it up. Editors sync their video *originals* up; the server syncs only *proxies* of video down.
3. **Popup warning** on the editor's machine when a timeline clip lives outside the synced project folder, with a one-click "move it to where it's syncable" fix.

Target: beat Blackmagic Cloud's observed ~60 mb/s up/down. User explicitly OK with A/B-testing different transfer services.

Canonical layout = existing template `Z:\Cablewrap\Projects\2025\FF4\Nuclear` (`AE/ Audio/ B-roll/ Interviewees/ Render in Place/ Subs/ Youtube/`), which already uses **per-folder `Proxy/` subfolders** — the exact convention Resolve + Blackmagic Proxy Generator auto-link from. ## Architecture

Three sync lanes with different directions, one policy:

| Lane | Content | Direction | Engine (initial pick, benchmarked in M3) |
|---|---|---|---|
| A: video originals | video files outside `Proxy/` dirs | editor → NAS only | rclone (SFTP, multi-stream) |
| B: proxies | `**/Proxy/**` | NAS → editors only | rclone (SFTP, multi-stream) |
| C: everything else | audio, GFX, AE, subs, docs, stills | bidirectional | Syncthing (event-driven, block-delta, versioning) |

Why split: no single tool expresses "video up-only, proxy down-only, rest both ways" in one folder. Syncthing `.stignore` can't upload a file type it ignores; rclone bisync is weak on conflicts. Splitting gives multi-stream bulk lanes (where speed matters) and battle-tested bidirectional sync for the small-file lane. Lanes are behind an adapter interface so the benchmark can swap engines per lane.

**Path canon:** one virtual drive letter on Windows — `P:`. Host/base rig: `P:` → `\\192.168.0.102\TheCreatorsPool\Creators_Club` (SMB). Editors (Win): `subst P: C:\Creators_Club` at login. Editors (Mac): local root on the editing SSD (`/Volumes/<Name>/Creators_Club`) + Resolve's **Mapped Mount** preference translating `P:\` to it — set automatically by `installer/macos_bootstrap.sh` (see flaw 7), with the companion still verifying it behaviourally by checking that timeline clip paths resolve. All DB-stored paths are `P:\Projects\...` → identical everywhere. `canonical_prefix` stays `P:\` on **every** machine including Macs: `companion/src/ccsync_companion/canon.py` compares and splits canonical strings with `ntpath` whatever the host is, translates them to `local_root/...` for any filesystem probe, and re-emits backslash spellings when writing paths back into Resolve — a `P:\Projects/2026/x.braw` produced by joining with the host separator would travel to every other machine in the fleet.

**Proxy generation:** **Blackmagic Proxy Generator on the base rig** watching `P:` (per-project watch folders). It natively handles BRAW (ffmpeg cannot decode .braw), is GPU-accelerated, preserves timecode, and writes to the in-place `Proxy/` subfolder convention — exactly what Resolve auto-links, and what the template tree already uses. Output: H.264 1080p (cross-platform safe; revisit H.265 later). NAS-side ffmpeg fallback container is a later nice-to-have for non-BRAW formats when the PC is off (PC has wake-on-LAN anyway).

**Resolve behavior:** editors run Playback → Proxy Handling → *Prefer Proxies* (original offline locally → proxy plays); host prefers camera originals. Auto-link requires same filename + timecode in the adjacent `Proxy/` folder — BPG guarantees this.

**Proxy relink (companion, added 2026-08-01):** auto-link only applies when the clip has NO proxy attached. A clip stores a second, independent `Proxy Media Path` beside its `File Path`, and an explicit stale value **beats** auto-link — Resolve never looks in the adjacent `Proxy/` folder. Projects built elsewhere therefore arrive carrying that machine's absolute proxy paths (a temp transfer drive, a local render-in-place folder, the base rig's legacy `T:`), which exist on no editor's machine: the proxy reads `Offline`, Resolve falls back to an original that lane A deliberately never downloaded, and the clip goes Media Offline next to a byte-perfect proxy. Note that `Reveal in Folder` and the Media Offline prompt both show the *original* path, so the clip looks correctly linked. `companion/src/ccsync_companion/proxy_relink.py` repoints such clips at the in-tree copy during the media-pool walk (every `media_tree_refresh_interval`), for in-tree originals only, only when a proxy is actually on disk, and always writing the canonical `P:\` spelling so the project stays portable. Repoint-only: it never copies, moves or deletes, and Resolve itself refuses a proxy whose timecode/frame count doesn't match. Off via `proxy_relink_enabled = false`.

**Shutdown warning (companion, added 2026-08-02):** rclone has no resume for SFTP uploads — `--partial-suffix` names the temp file, it does not checkpoint it — so a machine that goes away mid-upload restarts every in-flight file from zero on the next pass. On 2026-08-02 an editor switched off at 02:44 with three camera originals part-sent, discarding 19.3 GB of transfer with nothing on screen having suggested it was a bad moment. `companion/src/ccsync_companion/shutdown_guard.py` keeps a hidden top-level window whose `WM_QUERYENDSESSION` handler answers FALSE while a lane is syncing or has a queued backlog, with `ShutdownBlockReasonCreate` supplying the sentence Windows shows on its "this app is preventing you from shutting down" screen (how much is left, roughly how long). The editor always keeps *Shut down anyway*: this is a warning, not a lock. Two rules are load-bearing — it stays silent unless something is genuinely moving (paused and errored lanes don't count; a guard that cries wolf gets ignored on the night it's right), and every failure of the guard itself allows the shutdown, so a bug in here can never trap someone at their desk. "Genuinely moving" is enforced, not assumed (added 2026-08-03, B9): a lane only counts as busy while its progress fingerprint has changed within `keep_awake_stale_seconds` (default 180) and its peer isn't known-disconnected, and a `keep_awake_max_hold_seconds` ceiling (default 8 h) stands down a guard that has been blocking continuously — so a NAS that vanished overnight cannot hold "still syncing" forever with zero bytes in flight. Both keys tune the keep-awake below too; a bad value warns and falls back to the default rather than erroring, because a config error would stop syncing and disable the very guard being tuned. Covers shutdown/restart/log-off. Off via `shutdown_warning_enabled = false`. **macOS parity is deliberately reduced** (added 2026-08-03): nothing an unprivileged Mac app can do puts a sentence on the logout screen, so there is no shutdown-blocking screen there at all. Instead the darwin guard turns SIGTERM (logout, `launchctl bootout`) into the companion's normal graceful shutdown, and — best effort only, when pyobjc is present and nothing else owns the NSApplication delegate — answers `applicationShouldTerminate_` **once** per episode with `NSTerminateCancel` plus an `osascript` notification saying what is still moving; a second Quit inside the same episode always goes through.

**Keep-awake (companion, added 2026-08-02):** sleep sends no `WM_QUERYENDSESSION`, so the shutdown warning above never sees it — and idling into sleep is the likelier way an overnight upload dies. The same module holds `ES_CONTINUOUS | ES_SYSTEM_REQUIRED` via `SetThreadExecutionState` for exactly as long as a lane is busy, re-checked every 30 s, so the idle timer cannot sleep the machine out from under a transfer. `ES_DISPLAY_REQUIRED` is deliberately *not* set: the screen still blanks on schedule. Three constraints are easy to get wrong — the execution state is per-**thread** and dies with the thread that set it (so the polling loop must stay alive to hold it, and must release it on its own thread); `ES_CONTINUOUS` is what makes the request stick rather than nudging the idle timer once; and failing open means letting the machine sleep, because a guard bug that held the state forever would keep every editor's PC awake all night. It cannot stop a *deliberate* Start → Sleep or a closing laptop lid — nothing in user space can, and the shutdown guard covers the deliberate case. "Busy" is bounded by the same liveness rules as the shutdown warning (`keep_awake_stale_seconds` / `keep_awake_max_hold_seconds`, see above), so a wedged or disconnected lane cannot keep a PC awake indefinitely. On macOS this half is at **full** parity: a `caffeinate -i -w <our pid>` child (idle *system* sleep only, never `-d`) is held for exactly as long as a lane is busy, reaped when it isn't, and dies with the companion even if the companion is killed outright. Off via `keep_awake_while_syncing = false`.

### Shared asset libraries — the LUT library (added 2026-08-05)

Everything else in this system is per-project: a directory carrying a `.ccsync-project` marker gets a Syncthing folder, and an editor ticking it on the dashboard is what shares that folder with them. A **shared asset folder** is the other shape — one fleet-wide library, outside `Projects/`, that every editor gets automatically and nobody ticks. The LUT library (`P:\Assets\Luts`, Syncthing folder id `assets-luts`) is the first; the list lives in one place per component (`server/common.SHARED_ASSET_FOLDERS` and its two intentional copies), so a second library is a one-line change.

Three points where the project machinery would otherwise do the wrong thing to it, each handled explicitly: the collector's `_run_enforce` shares it with **every** mapped editor device (reading `selections` would find no rows and unshare it fleet-wide — the B16 failure by another route); `_ensure_ignores` repairs it with the **asset** `.stignore` (`build_asset_stignore_lines`, a different list — OS junk plus video as a blast-radius brake, and no Proxy patterns since there is no lane A/B under it), and getting that wrong makes the collector and companion rewrite the file at each other forever; and `_run_config` never gives it a `projects` row, so it cannot appear in the project list or anyone's tick UI. Editor side: `sync/shared_folders.py` reconciles it once per sequencer pass **before the selection check**, so an editor with zero projects ticked still gets it, and it is never part of the rotation.

**Resolve integration** is the half that makes it useful, and it is not filesystem trickery: Resolve has a supported list of extra LUT directories (Preferences → System → General → *LUT Locations*), so the library is added to it. Nothing is moved, renamed or linked, and Resolve's factory LUTs are untouched. That list has no scripting API but is plain text in the two preference files Resolve keeps — `Custom.LUT.Path.Count`/`.<n>` in `config.dat`, `CustomLutNum`/`CustomLutPath_<n>` in `.config.data` — which `companion/resolve_prefs.py` edits losslessly and atomically. The same two constraints as flaw 7's Mapped Mount apply and are enforced: **both files or neither** (the GUI form is what `config.dat` gets rebuilt from on the next launch), and **only while Resolve is quit** (it rewrites both from memory on exit, so an edit made with it running is silently discarded — the companion reports `resolve-running` and retries later rather than appearing to succeed). The location string is the canonical `P:\Assets\Luts` on every Windows machine — identical everywhere, which is what keeps an applied LUT resolvable on the next machine — and the real local path on macOS, which has no `P:`. Because an additional location is searched *in addition to* the factory directory, the library holds only LUTs Resolve does not already ship; copying factory LUTs in would show them twice.

The tray closes the loop the other way: a periodic scan of Resolve's own LUT folder (still the obvious place to drop a LUT) surfaces anything the library does not have as *"N LUTs only on this machine — share with the team"*, which copies them in after a confirmation naming what will be published. Matched by basename+size so a regrouped LUT is not offered forever; `.dctl` is deliberately excluded, since Resolve loads DCTLs only from its own `LUT/DCTL` directory and never from an additional location.

## Flaws / holes you asked me to flag

1. **Lag window**: editor adds video → other editors see it offline until upload + proxy-gen + proxy-download complete (minutes to hours for big files). Inherent to originals-up/proxies-down; companion tray shows queue so it's at least visible.
2. **Deletes & renames**: lane A never deletes on NAS (archival safety) — so folder reorganizations must happen **on the server side (host)** or stale copies accumulate; lane B mirrors server exactly (renames propagate down); lane C propagates deletes but server keeps versioned trash. This asymmetry is a rule editors must know.
3. **Same-name collisions**: two editors dropping different `track.mp3` into `Audio\Music` → Syncthing conflict-copies (surfaced in tray); on lane A skip-if-exists + warn.
4. **BRAW proxying depends on your PC being on** (BPG). WOL + optional NAS ffmpeg fallback mitigates.
5. **Postgres over WAN**: bin/timeline ops are latency-sensitive; fine on direct Tailscale, painful via DERP — the bootstrap must verify direct connectivity per editor.
6. **Shared upstream**: every editor's proxy download rides the HiNet upstream simultaneously; benchmark establishes the real ceiling.
7. **Mapped Mount on Mac has no scripting API — but it is not unscriptable** (revised 2026-08-03). Resolve exposes the preference nowhere in the API, and it never will be settable from the companion at runtime. It *is* settable from the installer: Resolve keeps it in two plain-text files under `~/Library/Preferences/Blackmagic Design/DaVinci Resolve/` — `config.dat` (`Site.<n>.FS.<i>.Root` / `.MappedRoot`) and `.config.data` (`IoFsMount_<i>` / `IoFsMappedMount_<i>`) — and `installer/macos_bootstrap.sh` edits **both** with an embedded python3 helper: losslessly (unknown keys, blank-line structure, spacing and line-ending style survive), atomically, after a timestamped backup of both files. Three constraints stay: the edit must happen **while Resolve is quit** (it rewrites `config.dat` from the GUI form on exit, so an edit made with Resolve running is thrown away — the helper refuses, exit 3); Resolve must have completed **one first run**, because first-launch onboarding regenerates the whole config and a missing `config.dat` therefore means "launch once, quit, re-run `--resolve-mapping-only`" rather than "invent one" (exit 4); and editing `config.dat` alone does nothing lasting, since the GUI form is what it gets rebuilt from. The companion still detects a wrong or missing mapping **behaviourally** — a timeline clip whose `P:\` path does not resolve under `local_root` raises the mapping warning — which is the only check that survives Resolve regenerating its own config. Manual GUI walkthrough retained as the fallback (`docs/EDITOR_SETUP.md` step 6), and `--skip-resolve-mapping` opts out entirely.
