# Extract of inventory section 24

## Items

### 24-001: Every clip in the b-roll archive ends up described shot by shot, so a person can search for what is in it and see it.
- Where: broll / Describing and indexing clips
- What: After indexing, each clip carries:
  - a list of shots, each with its start and end time in the clip, a short plain description (roughly 8 to 20 words, noun phrases), the things visible in it (with synonyms and broader terms, so "sedan" also finds "car" and "vehicle"), and any text on screen copied exactly in its original script with an English rendering beside it;
  - names of people, places and brands seen on screen, folded into the visible things in both the original script and English;
  - where the camera allows it, the setting and the camera's movement;
  - themes for the clip as a whole (free tags such as the subject matter);
  - picture-quality warnings from a fixed list of six: shaky, soft focus, overexposed, underexposed, noisy, rolling shutter;
  - a suggested category from the archive's category list, or none;
  - what spoken words were heard in it, with their times (see 24-012);
  - a record of which describer described it and when.
  A shot with no real visual content is labelled with one of exactly five words a person can search for: newsreader, title card, black frame, colour bars, station ident (a news anchor, presenter or talking head counts as newsreader; a test pattern as colour bars; a blank frame as black frame; a channel ident as station ident).
  Re-describing a clip replaces its whole previous description; it never mixes old and new shots.

### 24-002: Descriptions say only what can be seen, and give each distinct shot its own entry.
- Where: broll / Describing and indexing clips
- What: The describer is told to report strictly visible facts (it must not infer that traffic is congested from brake lights, or that a tunnel is a tunnel from lamps alone), to make one entry per distinct shot, and when in doubt to split. Every shot change in a clip is looked at, plus the very start and end, and no stretch of more than about 4 seconds goes unlooked at, so even a short shot gets seen. Adjacent entries that describe the same thing almost identically (most of their visible things in common and nearly the same wording) are joined into one entry covering both, so one continuous shot is not listed several times. Shot times come from the moments actually looked at, never from the describer's own guess.

### 24-003: The facts of each camera file are read and kept with the clip.
- Where: broll / Givens: browsers, cameras, files and Resolve
- What: For each clip the archive records its length, frame rate, width and height, codec, the date it was shot (taken from the date the camera or downloader wrote into the file), its frame count, its starting timecode and its bitrate. Facts about camera files that the product must respect:
  - a file's own claimed frame count is trusted only when it agrees with length times frame rate to within one frame or 1 percent, whichever is larger; otherwise the frame count is treated as unknown;
  - the starting timecode is taken from the file's own header first, then from a timecode track, then from any stream;
  - a timecode at 29.97 or 59.94 frames per second written with colons is really drop-frame and is shown with a semicolon before the frames, EXCEPT when the file carries a QuickTime timecode track, whose colons are a genuine non-drop timecode; a timecode that already has a semicolon, or is at any other rate, is kept as written;
  - file names in Chinese, Japanese or Korean must never break indexing, whatever language the computer is set to.

### 24-004: Which files in a footage folder count as clips.
- Where: broll / Bringing new footage in
- What: Every video file under a footage folder is found, at any depth: files ending in MOV, MP4, MXF, BRAW, AVI, MKV or M4V, in any letter case. Everything else is ignored. Skipped while looking: anything whose name starts with a dot, anything Windows marks hidden or system, the indexer's own working folder, and any folder the person has listed as excluded for that footage folder (whole subtree, letter case ignored; a pattern such as "anything/AE" matches an AE folder at any depth). Looking again later updates a known file's identity and size but never undoes what was already done to it, never forgets a file deleted from disk, and never drops a file that a newly widened exclusion now covers (those must be removed by hand). A file is recognised as the same clip by its content, so a renamed or moved copy is still known; a person can ask for every file's identity to be re-read rather than trusted.
- Flag: undetermined: whether a deleted file's clip should stay searchable; the present product keeps it until removed by hand.

### 24-005: A footage folder is either originals, or a shoot whose own proxies are the archive copy.
- Where: broll / How the archive is laid out
- What: The person setting up a footage folder says which of two kinds it is:
  - Originals (the default): the downloaded or camera file is the archive copy. A file inside a folder named proxy, proxies, optimized, optimised, transcode, transcodes, transcoded, lowres or low res written with an underscore (any depth, any case) is an editor's redundant encode: it is recorded and still copied to the archive, but never described.
  - The shoot's own proxies: the proxy files the shoot already made (inside such a folder) are what is archived and described; the camera originals beside them are recorded only, never described and never copied, and are remembered as each clip's true original (see 24-019).
  A clip's kind is decided when it is first seen and does not change on later looks.

### 24-006: Per footage folder, the person running indexing can switch off description, switch off transcription, cap clip length and name its archive folder.
- Where: broll / Describing and indexing clips
- What: Each footage folder has, besides its location and an optional free-text note:
  - Describe its clips (default on). Off: each clip still gets its preview, hover strip, poster and transcript, but nothing looks at its pictures and it costs nothing to describe; it rests as "kept, not described". Switching it back on later makes those clips get described on the next indexing run.
  - Transcribe its speech (default on). Off: no transcript is made for its clips.
  - Longest clip to index (default: no limit). A longer clip is not described or transcribed and is marked skipped with the reason "longer than <cap>s cap (<length>s) - not indexed", but is still copied to the archive.
  - Folders to leave out (default none).
  - The name its clips get in the archive, when it should differ from the folder's own name. Changing it after the archive was built moves nothing: the next archive build copies everything again under the new name and leaves the old copies.
  These are set by whoever runs indexing (the owner or an admin on the indexing computer). A mistake in them (an unknown kind, an exclusion list written as a single word) is refused with a message naming the setting.

### 24-007: A clip that cannot be indexed is parked with a reason a person can read, and nothing else is held up.
- Where: broll / Describing and indexing clips
- What: Each problem is kept against that clip only, and the run moves on:
  - no picture (sound only): "audio-only (no video stream) - transcript indexed, no visuals"; its speech is still transcribed and searchable, and it is still placed in the archive;
  - no length recorded in the file: told that nothing in it can be sampled and to rewrap the file and look again;
  - longer than the folder's cap (24-006);
  - unreadable: "file is truncated or incompletely downloaded" when the file was cut short, or "file is not valid media";
  - no picture could be taken from it: "no frames could be extracted - unreadable or truncated media";
  - its preview could not be made correctly (24-009);
  - the describer declined to describe it;
  - the describer's answer was unusable twice running;
  - it belongs to a footage folder that is no longer set up: "unknown share '<name>' (not in config)".
  A failure while transcribing or while preparing search never marks a clip as failed; it is only logged, and nobody is told.

### 24-008: An indexing run that hits an account-wide or machine-wide problem stops, leaves the queue untouched, and resumes where it stopped.
- Where: broll / Describing and indexing clips
- What: When describing fails for a reason every clip would share (out of credit, a missing or wrong key, a usage or rate limit, an overloaded service, a setting every request would repeat, or the computer's own describer not starting or not answering), the run stops at once without marking the clip it was on, and says "The queue is unchanged - fix the cause and re-run to resume" (or, for a limit, that it was reached after N clips and when it resets). Transient errors are retried for a while first. When running unattended overnight (24-025), a limit is waited out until the reset time the service names plus a minute (if that is no more than 6 hours away), otherwise 15 minutes at a time; after 6 hours of waiting with not one clip done, the run stops for good rather than sleeping on. A run that fails for another reason but did make progress tries again; one that made none stops and shows the end of what went wrong.

### 24-009: Each clip gets a browser preview that is checked to be complete before it counts.
- Where: broll / Previews made for the archive
- What: Every described clip gets a preview copy: 1080 lines high (never enlarged), H.264, always 8-bit so 10-bit camera footage plays in any browser, a keyframe every second so scrubbing is quick, AAC sound at 128 kbps, set up to start playing before it has fully downloaded, and carrying the source's timecode (with the drop-frame rule of 24-003). It is made on an NVIDIA graphics card when the computer has one, otherwise on the processor. Before it is accepted it is played through end to end: any decoding error, any difference from the source's frame count, or a length under 97 percent of the source's rejects it, and it is made once more the slower, surer way; if that is still wrong the clip is marked with the reason ("N decode errors", "X frames of the source's Y", or "truncated: Xs of Ys").

### 24-010: Each clip gets a hover-scrub strip and a poster picture.
- Where: broll / Previews made for the archive
- What: The hover strip has one picture every 2 seconds, 240 pixels wide, ten across, at most 240 pictures; a longer clip spaces them further apart so the whole clip still fits. The poster is the picture one tenth of the way into the clip, 640 pixels wide. Both are taken from the preview (or the original if there is no preview). The strip's layout is measured when made so the hover scrub lines up exactly.

### 24-011: Speech in a clip is transcribed so the archive can be searched by what is said.
- Where: broll / Describing and indexing clips
- What: Spoken words are turned into timed passages: neighbouring lines are joined while the pause between them is at most 1 second and the passage stays under 30 seconds. The language is detected on its own unless the person running indexing fixes one (for example Chinese). A file with no sound track gets an empty transcript and is not tried again. Transcription runs on a graphics card, shortest clips first, and reports how many hours of audio it faces and, at the end, how many times faster than real time it ran. Clips without a picture still get transcripts.
- Flag: differs: the bulk transcription the studio actually runs ignores a folder's "transcribe off" setting and the length cap, and always uses the graphics card; see 24-Q3.

### 24-012: Text that speech recognition invents is thrown away, and a transcript that is clearly noise is rejected whole.
- Where: broll / Describing and indexing clips
- What: Any passage containing a phrase that speech recognition is known to invent from silence or music is dropped: subtitle-credit and "please like and subscribe" lines in Chinese (both scripts, for example the subtitle-volunteer credit, subscribe, tip, reprint notices and one specific news-programme credit), and in English "subtitles by", "subtitled by", "thanks for watching", "thank you for watching", "please subscribe" and a subtitling website's name. What is left is rejected whole when it is empty (no speech), when one line makes up 60 percent or more of three or more lines (stuck repeating), when it has under 12 characters in all, or when the clip is over 2 minutes and the text averages under 8 characters a minute (noise, not speech). A rejected transcript is remembered as tried, so the clip is not transcribed again; the reason is only logged and nobody is told.

### 24-013: Search finds Chinese in either script and finds clips by meaning across languages.
- Where: broll / Search
- What: Everything searchable about a clip (each shot's description, visible things, setting, on-screen text and its English, and every spoken passage) is prepared so that: Chinese text can be found by keyword in Traditional (Taiwan) or Simplified script whichever was typed, with two-character words found as words; part of a Chinese word can be found by substring; English words match their other forms; and a search by meaning finds shots and speech in any of many languages even without the same words. A clip newly described, transcribed or removed shows in search straight away, with no restart.
- Flag: undetermined: if the Chinese-script or meaning-search preparation is missing on the indexing computer, keyword search falls back to the raw text and meaning search is simply absent; only a log says so.

### 24-014: The person running indexing chooses whether clips are described on the studio's own graphics card for free, or by the assistant for a fee.
- Where: broll / Describing and indexing clips
- What: Two ways to describe are offered: on the indexing computer's own graphics card (no per-clip cost; the default for a new set-up), or by the assistant over the internet (paid per clip; also needed for proposing categories, 24-021). With the assistant, the person can choose a faster, cheaper model or a slower, stronger one per run, or fix one in the settings. The owner judged the quality of the free local describer acceptable for the archive.
- Flag: several ways in: the choice is a setting on the indexing computer and can be overridden for one run.

### 24-015: The free local describer comes in two quality levels, Good and Best, chosen per site or per run.
- Where: broll / Describing and indexing clips
- What: Good needs an NVIDIA card with 8 GB of video memory (or an Apple Silicon Mac with 16 GB) and takes about 20 seconds per clip on a high-end gaming card; Best needs 12 GB (or 24 GB on Apple Silicon), reads on-screen text and vocabulary a little better, and is about twice as slow. The level is taken from, in order: the person's choice for this run; the indexing computer's own setting; the site's setting published by the dashboard (an admin's choice); otherwise Good. If the dashboard cannot be reached the site's setting is treated as unset, and only a log says so.
- Flag: undetermined: where on the dashboard an admin sets the site's level is not in this section.

### 24-016: The local describer downloads itself on first use, verified, resumable and then usable offline.
- Where: broll / Describing and indexing clips
- What: The first time, the describer and the chosen level's model are downloaded: about 3.3 GB for Good, about 6.2 GB for Best, plus the program itself (about 640 MB on Windows, about 11 MB on a Mac, about 33 MB on Linux). Every file is checked against a known fingerprint; a file that does not match is refused and fetched again ("Refusing to use this file. Re-run to retry the download."). An interrupted download picks up where it stopped. Once present, nothing is fetched again and it works with no internet. A person can fetch everything ahead of time; progress is shown per file in megabytes and percent, with the current speed available to show. It refuses a computer whose graphics card is too small (for example "Best needs 12 GB VRAM; this machine reports 10 GB", telling the person to choose Good or insist) or has none ("no GPU detected", suggesting the paid assistant instead or insisting) unless the person insists; an actual indexing run does not check. It runs on Windows with an NVIDIA card, on Apple Silicon Macs, and (untested) on Linux; any other system is refused.
- Flag: undetermined: AMD and Intel graphics cards are never detected, even where they could work.

### 24-017: A diagnostic report tells the person running indexing whether this computer can describe clips locally.
- Where: broll / Describing and indexing clips
- What: It shows which way of describing is set, the graphics card found and its memory (or "unified memory" on Apple Silicon, or none found), the recommended level (Best at 12 GB or more, or 24 GB on Apple Silicon; Good at 8 GB, or 16 GB; otherwise "none - search-only, or use the assistant"), the level that will be used, where the downloads are kept, whether the describer and model are downloaded yet and which version is present, and where the site's level is read from.

### 24-018: Paying for descriptions: the key is kept out of the settings file, and the run says whose credit it is spending.
- Where: broll / Describing and indexing clips
- What: The key for the paid assistant must come from the computer's environment or a separate key file; writing it into the indexer's settings is refused ("the API key belongs in the environment ... or in a file"). Each run starts by stating where the key came from and that it is billing that organisation's credit, or "NO API KEY" with the reason. A missing, unreadable or empty key stops the run with the queue intact (24-008).

### 24-019: How long and how much describing costs, in terms a person can plan with.
- Where: broll / Describing and indexing clips
- What: Every description is recorded with the clip, its length, the model, how much was sent and returned, how long it took, and an estimated cost (an estimate from list prices, never the billed amount; the free local describer counts as zero). A cost report gives, per model: calls, clips, minutes of footage, minutes of describing time, estimated cost, cost per minute and per hour of footage, speed against real time, and, given an archive size in hours, a forecast of cost and time to describe all of it. To bound cost on long clips, the person can cap how much of a long clip is looked at; the look is then spread evenly so the whole length is still covered.

### 24-020: Clips that already exist elsewhere in the archive can be found and set aside, never deleted.
- Where: broll / Bringing new footage in
- What: The person can ask for duplicates. By default each candidate is confirmed by comparing the whole file; a candidate whose file cannot be found is listed and left alone, and one that looked the same but is not is listed as distinct and left alone. Skipping the whole-file comparison prints a loud warning that a false match "can PERMANENTLY LOSE FOOTAGE" and the report says verification was off. The copy kept is the furthest-along one (filed into a category, then described, then with a preview, and so on), then the one with most shots described, then the oldest. Nothing changes until the person confirms; then the other copies are marked as duplicates of the kept one, are never described again, never copied to the archive and never shown in search, but are not deleted. Running it again is safe. The report gives counts ("N duplicate(s) to mark, N canonical copies kept, N collisions confirmed distinct (NOT marked), N file(s) missing (not marked)") and lists each group.

### 24-021: Categories for the archive: proposed by the assistant, approved by a person, then each clip filed under one by rules.
- Where: broll / How the archive is laid out
- What: The archive has a two-level category list (for example energy/nuclear), each with a short label and description. The assistant can propose one from all the themes seen so far, written as a document for a person to review (refused if nothing is described yet). An approved list is loaded into the archive; loading adds and updates but never removes a category. Each described clip is then filed under exactly one category by keyword rules: a rule word matches a whole word, or any word starting with it when it ends in a star, letter case ignored; the category matching most of the clip's themes wins, ties going to the narrower category. A clip inside a named person's folder under a folder called interview, interviews, interviewee or interviewees goes to the interviewee b-roll category when its themes mention an interview, talking head, testimony, conversation or speaking, or when nothing else matched. Clips matching nothing are tried against a few general fallback categories, then a default ("Unsorted"), else left uncategorised. A clip already filed keeps its category unless the person asks to re-file, which warns that it moves files in the shared archive. A dry run shows what would happen. The result reports how many were filed, how many by fallback and by the interviewee rule, how many stayed, how many matched nothing, and per category how many were filed against how many matched. The describer's own category suggestion is shown but does not decide the category.
- Flag: undetermined: whether anything still asks the assistant for a proposal.

### 24-022: Clips in an inbox folder are moved into their category's folder once described.
- Where: broll / How the archive is laid out
- What: Clips the person marked as in an inbox, once described and filed, are moved to the footage folder's subfolder for their category; a name already taken there gets _2, _3 and so on. A move to another drive copies, checks the size and only then removes the original; a size difference removes the copy and the clip is marked "sort failed" with the reason. A dry run lists the moves.

### 24-023: The shared archive on the NAS is built from the index, copying only what changed and never deleting.
- Where: broll / How the archive is laid out
- What: Described clips, clips kept without description, clips with a preview, and sound-only clips are placed in the archive (duplicates never). A downloaded clip not yet filed in a category waits until it is described, so it is not first placed under "uncategorised". Layout:
  - The studio's own shoots go under the studio's own folder, then the shoot's name, keeping the shoot's subfolders (leaving out any proxy level).
  - Everything else goes under a downloads folder by category, or an uncategorised folder.
  - Each clip has two places: its best media at the top (for an own shoot, the shoot's proxy; otherwise the original if it exists, else the preview), and the browser preview in a Proxy subfolder beside it. Poster and hover strip are copied too.
  - Names: forbidden Windows characters become underscores, trailing dots and spaces go, at most 90 characters, "untitled" if nothing is left. A clip's name, once given, is kept forever; a new clip whose name is taken in that folder (letter case and extension ignored) gets _2, _3 and so on. Names are decided from the index, never from what happens to be on disk.
  A plan is shown first (clips eligible, files and gigabytes to place, how many clips have no preview and so show "no preview" on the site, the first 12 paths); nothing is copied until the person confirms. A file is copied only when missing or different; a file deliberately repaired in place is left alone. Each copy is written aside and swapped in; the copy it replaces is kept in a trash folder in the archive, never emptied automatically. A failed file is reported and the rest continue. Progress shows gigabytes, speed and time left. Source footage is never touched and nothing at the destination is ever deleted; a renamed shoot or a re-filed clip leaves its old copies in place.

### 24-024: The archive remembers where each clip's true original lives, even with the drive unplugged.
- Where: broll / Previews standing in for originals
- What: For each clip the archive records its original file and its size: for a shoot archived as proxies, the camera file with the same name in the same folder (ignoring a proxy folder level, letter case ignored); otherwise the clip's own file. Where each footage folder lives is also recorded at the start of every indexing run so originals can be found later; a failure there is only logged. Working this out needs no drive to be connected. On request it also checks each original exists now and dates that check; one not found is counted, never recorded as gone. Report: "recorded N original path(s) of M; K unresolved", and with the check, how many were found and not found.

### 24-025: An indexing run can be left to work through the whole archive unattended, with limits the person sets.
- Where: broll / Describing and indexing clips
- What: The person running indexing can: describe at most N clips; stop starting new clips after a set clock time (clips under way finish; the rest stay queued); stop after a number of hours; limit a run to chosen footage folders (an unknown folder name is refused with the list of known ones); start a second run alongside a running one on later clips without overlap. On Windows a scheduled check every so often restarts an overnight run that has stopped while clips remain, and does nothing when the queue is empty. While it runs it shows how many clips are left, clips per minute, time to finish, and counts done, failed, skipped and not started.
- Flag: undetermined: the scheduled restart is written for one computer's fixed folders.

### 24-026: A morning report summarises an overnight indexing run and checks search quality.
- Where: broll / Describing and indexing clips
- What: It shows how much of the archive is described (out of all clips not skipped, with counts in each state), how many shots there are and how many have on-screen text, how many spoken passages and how many are ready for meaning search, how many shots got each no-visual-content label, how much describing was done, how many clips failed (the first ten named), free space on the indexing drive, and then runs the search-quality check of 24-031 against the studio's archive query set, beside the baseline before indexing.
- Flag: undetermined: written for one computer's fixed folders.

### 24-027: The archive can be re-pointed at footage that moved to a new folder, by matching content.
- Where: broll / How the archive is laid out
- What: After footage is moved, the person names the new folder; every video there is matched to known clips by content. For each match the furthest-along clip is pointed at the new place ("rematched", or "already correct"); other clips with the same content are "superseded". Nothing changes until the person confirms; superseded entries are deleted only if they also ask for that. A report lists rematched clips (old and new place), superseded duplicates ("NOT deleted - review these"), clips not found in the new folder (left untouched), and files in the new folder not in the archive (with the advice to index the new folder to add them).

### 24-028: A list of what to copy to the NAS can be produced for a first consolidation.
- Where: broll / Bringing new footage in
- What: Lists every clip to copy, leaving out confirmed duplicates and camera originals of proxy-archived shoots (counted as space saved), including clips that were skipped or failed. Clips from footage folders no longer set up are left out and counted. Files are not checked to exist. Output as a plain list of files, a Windows copy script (which refuses to run until the destination is set), or a list of relative paths for a Unix copy. Summary: "N file(s) to copy, N duplicate(s) skipped, N byte(s) saved".

### 24-029: The archive can be checked for source files that are damaged.
- Where: broll / How the archive is laid out
- What: Every clip's file is opened and tested; a missing one is "MISSING from disk", an unreadable one shows the first line of the error. The report says "N of M source files cannot be read as media. These are damaged in the archive itself - re-download or re-copy them." and lists each by footage folder with its size and reason.

### 24-030: Proxies missing from the studio's own shoots can be made in bulk before archiving.
- Where: broll / Previews made for the archive
- What: For a shoot's folder tree, every camera file without a proxy beside it (in a Proxy folder with the same name) gets one, made with the same settings as the editor's own proxies, carrying the source timecode, written aside and only then put in place, and checked as in 24-009. Leaves out folders that look like proxy folders, names starting with "@" or a dot, and excluded patterns; clips longer than a cap (default 5 minutes; 0 means none) are left out. A dry run is the default. Each clip's result (made, would make, unreadable, no length, no picture, over the cap, bad result, failed) is recorded and summarised. Source files are never moved, changed or deleted.
- Flag: differs: these proxies use the editor-proxy settings, not the browser-preview settings of 24-009; see 24-Q9.

### 24-031: The owner can measure how well b-roll search finds what it should, and how often it returns what it should not.
- Where: broll / Search
- What: The owner keeps a set of test searches. Each names the search words, and either the clips any of which should come back (by part of their path), or that nothing should come back (a guard against false hits), with optional tags. A check runs every search and reports: how many found an expected clip (as a fraction and percent), how many guards stayed clean, the hit rate per tag, each miss ("MISS ... N hits, none expected-matching") and each leak ("LEAK ... returned N hits (expected none)"). It can be run through the real search, choosing keyword, meaning or combined search and whether close spellings count, or as a plain keyword check straight on the index. Two or more indexes can be compared, listing each search whose result differs. A failed guard marks the check as failed.

### 24-032: The owner can measure how well a candidate describer describes clips, against the existing descriptions.
- Where: broll / Describing and indexing clips
- What: About 100 described clips are picked at random but balanced across four kinds (with on-screen text, with five or more shots, with at most two shots, any), and each candidate describer describes them. Each result is scored against the existing descriptions (a reference, not the truth): how well its shots line up in time, how much of the clip it covers, overlap of visible things and of key nouns, on-screen text exactly right, similar, and found where it exists and invented where none was, agreement on category, themes and quality warnings, and one overall agreement score. Reports give the totals, the same per kind, and the 20 clips that disagree most shown side by side; several runs can be compared in one table. A run records time per clip, memory used and speed, can be resumed, can skip a clip's remainder after a time limit, and the clip set can be carried to another computer (a Mac with a budget of memory picks the largest model that fits). On Windows an overnight run waits, for up to 8 hours, until the graphics card has about 6 GB free and Resolve is closed, then runs and reports; status can be checked while it runs.

### 24-033: A blind judging page lets a person score describers' output without knowing which is which.
- Where: broll / Describing and indexing clips
- What: A page that opens from disk (or through a small local server for browsers that refuse its pictures from disk) shows one clip at a time: its stills in a strip with timecodes, and one column per describer labelled A, B, C in a shuffled order this browser remembers, each listing shots (time, description, visible things, on-screen text and English), themes, quality warnings and category. Clicking a still enlarges it and highlights every shot in every column covering that moment (within 2 seconds); clicking again unpins. Hovering a shot highlights the stills it covers; clicking pins it. Under each column: an accuracy score 1 to 5 (click again to clear), a "best" choice, and flags "hallucinated", "missed the shot", "OCR wrong", "over-segmented". Once any vote is cast on a clip, the real names appear. A notes box per clip saves as you type. Keys: Right and Left arrows for next and previous clip, 1 to 5 to score the focused column, ignored while typing. Everything is kept in the browser and it reopens at the last clip. Votes can be exported to a file and imported back ("imported N verdict(s)" or "not valid JSON"). A summary shows per describer the mean score, how many scored, "best" picks and flag counts. Clips that disagree most come first by default. A written summary per describer and per kind, with all notes and how well the human scores agree with the automatic score, can be produced from the exported file.

### 24-034: Previews and hover strips made by earlier versions can be repaired in place.
- Where: broll / Previews made for the archive
- What: Three repairs for archive files made before the present preview rules: previews that are not H.264 or are 10-bit (and so will not play in a browser) are re-made, but only inside a Proxy folder; anything else is refused as "these are originals, not previews"; previews whose timecode differs from their original's are corrected without re-encoding, and the result is checked; hover strips without a recorded layout are rebuilt. Each shows what it would do first and acts only when confirmed; failures are counted. A preview re-made for playability is remembered as deliberately repaired so later archive builds leave it alone; a timecode correction is not, so the next archive build copies the uncorrected preview back over it (the corrected one goes to the archive's trash).
- Flag: dormant: one-off repairs for problems the present preview making no longer creates.

### 24-035: Indexing from a computer that sends results to the server, rather than writing the server's index directly, loses speech, search preparation and categories.
- Where: broll / Describing and indexing clips
- What: The indexing computer can send each clip's facts and description to the server over the network instead of writing the archive's index directly. Sent that way, transcripts, the Chinese-script and meaning-search preparation (24-013), loaded categories and removals do not reach the server: the indexing computer keeps them for itself and logs a warning per clip, and the transcript is counted as done so it is never sent later. Nobody else is told. Index upgrades and re-pointing (24-027) are refused in that way of working.
- Flag: differs: the two ways of storing results do not carry the same information; see 24-Q4.

### 24-036: The categories the studio files its b-roll under.
- Where: broll / How the archive is laid out
- What: The studio's shipped category rules cover 33 subject categories in groups: energy (nuclear, renewables, power and grid), environment (waste and recycling, pollution and climate, conservation and wildlife, coastal erosion), economy (industry and manufacturing, work and wages, retail and commerce, agriculture and fishing, cost of living and housing, finance and markets), society (government and politics, protest and activism, policing and crime, education, health and welfare, transport and road safety, indigenous affairs, gender and LGBT), culture (heritage and religion, food and drink, performance and music, digital and social media, animation and anime, media and broadcasting), leisure (esports and gaming, travel and tourism, sport and outdoors, animals and pets), security (military and defence, emergency and disaster), plus interviewee b-roll reached only through the interview-folder rule; five fallbacks (news broadcast, interviews, archival, public life, places) and the default "Unsorted".

### 24-037: Setting up an indexing computer refuses missing essentials by name and never guesses where tens of gigabytes go.
- Where: broll / Describing and indexing clips
- What: The working folder for previews, stills and transcripts must be named (it needs tens of gigabytes, so it is never guessed), as must the archive's index or the server to send to; transcription needs its speech recognition set up first. Each refusal names exactly what is missing and how to supply it.
