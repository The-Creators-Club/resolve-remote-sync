# The term review and the queue (ytdl/web)

Built 2026-08-30. The owner's ask, verbatim:

> youtube downloader should show a list of the search terms it is going to use
> (for chinese ones, it should show a translation in brackets). They begin all
> ticked and then you can untick individual ones or untick all, or tick all.
> there should also be a queue so you can queue up multiple searches.

Two additive features on the one phase machine in `ytdl/web/ytdlweb/worker.py`.
Neither changes the download half: `docs/YTDL_LOCAL_DOWNLOAD.md` (requester
first, the lease, the reclaim) and `docs/YTDL_RESILIENCE_PLAN.md` (the
3-refusals breaker, the cancel) describe exactly the behaviour they described
yesterday, and section 4 below says what was checked to keep it that way.

Schema: `migrations/012_terms_review_and_queue.sql`, `user_version` 12.

---

## 1. The term review

### The phase

```
queued -> generating_terms -> terms_review -> searching -> enriching ->
filtering -> ready_for_review -> downloading -> done | failed | cancelled
```

`terms_review` is a **no-op wait**, in the plainest sense the worker has: it
has no entry in `worker._handlers()`, so `run_job` returns and the loop moves
on, and `db.claim_next_job` does not offer it. There is no timer and no
default. The job sits there until a person presses SEARCH WITH THESE or CANCEL,
exactly as `ready_for_review` has always sat. It is in `db.IDLE`, so a cancel
ends it outright rather than setting a flag nothing will ever read (YTDL-1).

Two jobs skip the stop, both because there is nothing to review:

- **`term_scope='exact'`** has one term, the editor's own text, generated by
  nobody. Confirming what they just typed is a click for no information.
- **`auto_terms=true`** is the headless path (below). Nobody is watching a
  script's job to press the button for it.

### The translation

`job_terms.translation` is what the review prints in brackets. For a query
Claude wrote it is the `english_gloss` **that same call already produces** --
the same English sentence under the name the review speaks, so the feature
costs no extra AI turn and, deliberately, no change to `_TERM_SYSTEM`
(`tests/golden/` exists to prove that an editor who never touched a toggle
never had their search changed under them). It is `NULL` for a query that is
already English, which the SPA reads as "print no bracket after this one".

The **editor's own term** is the one row that can have no gloss of its own: it
is written before the model is asked anything. `worker._phase_generate_terms`
fills it in from the reply already in hand, matching on the query text, because
the model routinely echoes the editor's phrase back as one of its queries. When
it does not, the row simply has no bracket -- no second call is made for it.

### The ticks

`job_terms.enabled` defaults to 1, so terms begin all ticked, and
`db.unsearched_terms` reads nothing else: an unticked term is not searched late
or searched quietly, it is never looked at. `jobs.terms_total` is recounted
from the enabled ones both in `POST .../terms/continue` and at the top of
`_phase_search`, so a job resumed after a container restart counts up to a
total it can actually reach.

### The routes

```
POST /api/jobs/{id}/terms           {"enabled": [<term id | term text>, ...]}
  -> 200 {"ok": true, "enabled": 2, "total": 4}
  -> 409 {"detail": {"detail": "this job is searching, not waiting for you to
                                pick its search terms", "phase": "searching"}}
  -> 404 for another editor's job

POST /api/jobs/{id}/terms/continue  {}
  -> 200 {"ok": true, "phase": "searching", "terms": 2}
  -> 400 "tick at least one search term: a search with none of them would find
          nothing"
  -> 409 (as above) unless the phase is terms_review
```

The selection is the **whole set every time**, never a delta: the page knows
what it is showing and one post that says so cannot half-apply. Ids or the
query text are both accepted, because both are things a caller genuinely has.
UNTICK ALL is a legal thing to be looking at (`enabled: []` is accepted) and an
illegal thing to search (the continue is a 400, and the phase does not move).

Two routes and not one: ticking is a decision about the job, continuing spends
twenty minutes of YouTube requests. Folding them together would mean either a
round trip per checkbox on handlers that share one uvicorn worker with the
fleet status page, or a single call whose failure leaves nobody able to say
whether the ticks landed.

### The terms, as every JSON answer carries them

One shape, `db.term_dict`, used by `GET /api/jobs/{id}`, the manifest route and
the review:

```json
{"id": 7, "term": "藻礁 三接 爭議", "lang": "zh",
 "english_gloss": "algal reef third LNG terminal dispute",
 "translation": "algal reef third LNG terminal dispute",
 "enabled": true, "source": "claude", "searched": 0, "hits": 0, "videos": 0}
```

`translation` is `null` and `enabled` is `true` for a row from a database the
migration has not reached, which is what every term written before the review
actually was. The provenance `manifest.json` beside the clips carries
`translation` and `enabled` too: "why did this search not cover X" is answered
by the term the editor unticked, and nothing else would ever record it.

### The headless bypass

`POST /api/jobs {"auto_terms": true}` creates a job that goes straight from
`generating_terms` to `searching` with every term enabled. It is stored on the
row (`jobs.auto_terms`) rather than held in memory, for the reason
`shot_types`, `mode` and `max_candidates` are: a job that sat queued over a
container restart must resume as the caller submitted it. **The SPA never sends
it.** An editor who asked for a search is exactly who should see the queries it
is about to run.

### The page

`#terms`, above the review grid, shown only while the attached job is at
`terms_review`. Each row is `[x] <term> (translation)`, with the bracket only
when there is one and a dashed underline on the editor's own words; under them
`N of M terms`, `[ TICK ALL ]`, `[ UNTICK ALL ]` and `SEARCH WITH THESE`.

**The ticking is done in the browser.** `state.termsOn` is the set; the count
and the disabled state of the button come off it with no network in the way,
and the server is told once, on continue. SEARCH WITH THESE is disabled at zero
ticked, which is the same refusal the 400 above is, without the round trip.

## 2. The queue

### The rule

"One job per editor" has become "one job RUNNING per editor, the rest wait".

```python
db.BUSY = ('generating_terms', 'searching', 'enriching', 'filtering',
           'downloading')
```

`queued` is not busy (it *is* the waiting), and neither are `terms_review` and
`ready_for_review`: those are waiting for a **person**, and a person is not a
worker. That is the whole point -- a manifest nobody had looked at for a week
used to block every later search with a 409 (YTDL-25), and the small
[ CANCEL ] on the progress strip was the only way out.

`db.claim_next_job` is the only place that decides whose turn it is:

- a job in a BUSY phase is claimable (work already in flight comes first);
- a `queued` job is claimable when **its own editor** has no busy job. Another
  editor's running job never holds it back;
- a job under a live local-download lease stays invisible, unchanged
  (`docs/YTDL_LOCAL_DOWNLOAD.md` section 3).

Order: in-flight work, then the editor's own `queue_position`, then oldest
first. For a single job that is the `ORDER BY id` it always was.

### Creating

`POST /api/jobs` and `POST /api/jobs/urls` no longer 409. Every job is created
`queued` with a 1-based per-editor `queue_position`, and both answer:

```json
{"job_id": 41, "phase": "queued", "queue_position": 2, "queued_behind": 3}
```

`queued_behind` is counted, not stored: the editor's busy job (at most one)
plus every queued job in front of this one. 0 means it starts on the worker's
next tick. For a paste, the pre-existing `queued` key in the same answer is a
count of **clips** and has nothing to do with the queue.

The unique index `idx_jobs_one_active` is **dropped** by migration 012. It had
to be: a queued job is a non-terminal job, so with the index in place the queue
could never hold more than one thing. The double-clicked SEARCH it was created
for is no longer an error at all -- the loser queues behind the winner, which
is a job the editor can see and cancel, instead of an orphan that blocked them.

### Reading

```
GET /api/jobs/active
  -> {"job": {...the running job, or the head of the queue, or null...},
      "queue": [{"id": 42, "term": "offshore wind", "kind": "search",
                 "project_label": "2026/FF5/Energy Transition",
                 "phase": "queued", "position": 1,
                 "created_at": "2026-08-30T09:12:04+00:00"}, ...]}
```

The list is numbered by its ORDER, not by the stored positions: a queue with a
cancellation in the middle of it must read 1, 2, 3 to the person looking at it.
The running job is never also a queue row.

### Reordering and cancelling

```
POST /api/jobs/{id}/queue/move  {"position": 1}
  -> 200 {"ok": true, "queue": [...renumbered...]}
  -> 409 {"detail": {"detail": "this job is searching, not waiting in the
                                queue", "phase": "searching"}}
```

Positions are **clamped**, not validated: [ UP ] on the first row is a no-op an
editor will press, not an error worth a toast. The whole queue is renumbered
1..n in one transaction, because a scheme that rewrote only the moved row would
leave duplicate positions behind, which read as an arbitrary order the next
time anything sorts by them.

There is no cancel route here: `POST /api/jobs/{id}/cancel` already ends a
`queued` job outright (it is in `db.IDLE`).

### The page

`#queue`, under the running job and above Recent searches, hidden when empty.
One row per waiting job: position, term (or "pasted links"), destination
project, `[ UP ]`, `[ DOWN ]`, `[ CANCEL ]`. It is re-read from
`api/jobs/active` on load, after a create, after a move or cancel, and on a
poll where the attached job's phase MOVED -- not on every 1500 ms tick, because
the queue only changes when somebody presses something.

The search form no longer refuses while a job runs. A second search says
`queued behind 2 jobs: it starts when they finish`, and says nothing at all at
the front of the line.

## 3. What is stored

`migrations/012_terms_review_and_queue.sql` (v12):

| column | why |
| --- | --- |
| `job_terms.translation` | the bracket the review prints; NULL for English |
| `job_terms.enabled` | ticked, default 1 |
| `jobs.queue_position` | 1-based, per editor, read only while `queued` |
| `jobs.auto_terms` | skip the review (headless callers only) |
| *(dropped)* `idx_jobs_one_active` | the 409 this feature replaces |
| *(added)* `idx_jobs_queue` | `claim_next_job` asks "is this editor busy" per tick |

**No backfill, and none is possible.** Every term an existing database holds
WAS searched, which is what `enabled` defaults to; every job in it is terminal
or already running, so `queue_position` 0 is honest for all of them; and
`auto_terms` 0 is only reachable now that a stop exists.

Migration 003's already-applied predicate had to change with it. It used to be
"does `idx_jobs_one_active` exist", and 012 removes that index -- so on every
database past v12 it answered no, 003 re-created the index, and 012's own
predicate then read "not applied" and re-ran its `ALTER`s into a
`duplicate column name`. The predicate now also accepts "this database has
`jobs.queue_position`", i.e. it is past the point where that index existed.

## 4. What the local-download path did NOT need

Checked against `docs/YTDL_LOCAL_DOWNLOAD.md` and left alone:

- **the claim is still phase-gated.** `routes_fleet` refuses a claim unless the
  job's phase is `downloading`, so a queued job is not claimable by anyone's
  companion until its turn comes and the editor presses DOWNLOAD. Nothing in
  the queue widens that.
- **a leased job stays invisible to the loop.** The lease clause in
  `claim_next_job` is unchanged and now sits beside the queue clause; a job an
  editor's machine is downloading is BUSY for its own editor (it is in the
  `downloading` phase) and invisible to the worker, which is both of the
  properties it had before.
- **the reclaim, the grace period, the mode lock and the cancel** are
  untouched.

The one behaviour that did change on that side is `POST
/api/jobs/{id}/download` for a **finished** job: reviving it puts it straight
into `downloading` with no queue entry to wait in, so the one-job refusal still
applies there -- but against a BUSY job only. A search of that editor's parked
at `terms_review` or `ready_for_review` no longer refuses their retry, which
was YTDL-25's block turning up in the one place it was never about.
