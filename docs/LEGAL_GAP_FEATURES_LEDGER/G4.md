## What was built

### `ytdl/web/ytdlweb/db.py` (the SQL, appended at the end)

- `SUBJECT_MATCH`: where a person appears in the store. That is
  `jobs.created_by` or `claimed_by`, `job_terms` of the jobs they created,
  `job_videos.download_host`, `downloads.downloaded_by` and
  `attestations.username`. Every match is `COLLATE NOCASE`, because the
  dashboard lower-cases usernames. `download_host = 'server'` (the NAS
  worker's own mark) is never matched, even for an account called `server`.
- `subject_rows(c, username) -> {table: [row dict]}`. Read only. Nothing is
  excluded, because the store keeps no secrets.
- `forget_history(c, username) -> {table: deleted}`. Deletes the person's
  TERMINAL jobs only (`done`, `failed`, `cancelled`), together with their
  `job_terms`, `job_videos` and `job_video_terms`. The children are deleted
  explicitly, so the cascade pragma is not needed. It never deletes
  `downloads` (the dedupe ledger), attestations, running or parked jobs, or
  another person's job that this person's computer fetched.
- `forget_requester(c, username, pseudonym, machine_stand_in=None) -> counts`,
  in this order:
  1. It expires every live lease the person holds, with `expire_lease`, the
     same stop signal the cancel button uses. Their companion gets a 410 and
     the worker takes the job back. Another editor's job keeps running on the
     server.
  2. It cancels the person's unfinished jobs the way
     `POST /api/jobs/{id}/cancel` does: `cancel_now` for idle phases,
     otherwise `request_cancel` plus `expire_lease`.
  3. It deletes `job_terms` and `job_video_terms` for their finished jobs.
  4. It pseudonymises `jobs.created_by`, `jobs.claimed_by`,
     `job_videos.download_host`, `downloads.downloaded_by` and
     `attestations.username`, and the `created_machine` hostname through
     `machine_stand_in` (without one, it is set to NULL). Rows are kept. On an
     attestation (username, version) collision, one row is kept.

  Renaming `claimed_by` after the release is deliberate: the worker's reclaim
  (`worker._reclaim_local_job`) credits landed clips to `claimed_by`.
  The function is idempotent. A blank username or a blank pseudonym raises
  `ValueError`.

### `dashboard/src/ccsync_dashboard/ytdl.py` (appended wrappers)

(Superseded in part by the review round below: the wrappers now answer the
plan's bare shapes and raise on a store they cannot read.)

None of these is gated on `youtube_download`. A site that switched the feature
off still holds its records, and importing `ytdlweb.db` loads only stdlib
modules, never yt-dlp. A store file that does not exist is never created:
the result is `absent`. `ensure_schema` runs before any column is named, as
the mount does at boot, and a store newer than the code reports `error`.

- `subject_rows(username, *, db_path=None) -> {"status": "ok"|"absent"|"error", "detail", "tables"}`
- `forget_history(username, *, db_path=None) -> {"status", "detail", "counts"}`
- `forget_requester(username, conn=None, *, pseudonym=None, db_path=None) -> {"status", "detail", "pseudonym", "counts"}`
  - `conn` is the DASHBOARD connection. The stand-in comes from
    `db.pseudonym(conn, username)` and each hostname's from
    `db.machine_pseudonym`, so one person reads as one person in both
    stores.
  - With neither `conn` nor `pseudonym`, it returns `error` and rewrites
    nothing. It never makes up a name.
  - After a release or a cancel, it nudges the worker if that worker is
    loaded.
- `db_path` defaults to `ytdlweb.config.DB_PATH`, which comes from
  `YTDL_DATA_ROOT`.

## Departures from the plan, and why

1. **`forget_requester` rewrites `created_by` on every job the person created,
   not only finished ones.** Their unfinished jobs are cancelled first, so no
   live job belongs to anyone. A job still winding down would otherwise keep
   the real name for good.
2. **More columns than the plan lists are rewritten.** `job_videos.download_host`
   is pseudonymised on delete, and `jobs.created_machine` gets the machine
   stand-in. Both name the person or their computer (G0 departure 3 applies
   the same reasoning). `claimed_machine` is left alone: it is a
   companion-minted random id, not a name.
3. **`job_terms` of a job that is still winding down are kept until it
   stops.** The worker may be reading them. (Review round: they now go when
   the job reaches a terminal phase, through `set_job`, with no second call.)
4. **The wrappers return a status envelope instead of bare rows or counts.**
   This lets the export say "not included: the downloader's records could not
   be read" rather than presenting an empty list as complete.
5. **Known residual window, documented in the docstring.** A server download
   that is mid-clip when the cancel flag is set can finish that one clip and
   credit it from the worker's in-memory job row, under the real name.
   `counts["jobs_stopping"] > 0` flags this case. A second call after the job
   stops cleans it up.

## Review round (2026-09-25)

The adversarial reviewer raised eight points. I checked each one against the code and fixed all six that were real. Point 7 is accepted as wording only, and point 8 is fixed. Everything below is in G4's own files: `ytdl/web/ytdlweb/db.py`, `dashboard/src/ccsync_dashboard/ytdl.py` and `ytdl/web/tests/test_ytdl_subject.py`. No other group's file was edited.

**Contract decision (points 1 to 3).** G4 now follows the plan's contract (plan section 7.3). G3 and G2a had already been built to it, so G4 changed and they did not. G3 hand-off 3 is withdrawn.
- `subject_rows(u)` returns `{table: [rows]}`.
- `forget_history(u)` returns `{table: count}`.
- `forget_requester(u, conn=None, *, pseudonym=None, db_path=None)` returns `{"status": "ok"|"absent", "pseudonym", "counts"}`.
- A store that does not exist returns `{}` or `absent`, because it holds nothing.
- A store that exists but cannot be opened, read or written raises `ytdl.YtdlStoreError`. G3's `_ask` turns that into a `not_included` line. G3's erase route turns it into `not_done: ["ytdl"]`. G2a's `_forget_elsewhere` turns it into a delete warning.
- `STORE_ERROR` and the `detail` key are gone.

   - Tests:
     - `test_review_2_a_one_argument_delete_uses_the_mounted_dashboard_db` runs G2a's real `api._forget_elsewhere`. It checks that the job is renamed to the dashboard's stand-in, the lease is expired, the status is `ok` and there is no warning.
     - `test_review_2_with_no_way_to_make_a_stand_in_the_delete_warns` checks for the raise, a YouTube warning, and that nothing is renamed.
3. **Fixed: erase counts were dropped.** The cause was the same envelope.
   - Test: `test_review_3_erase_history_counts_reach_the_audit_shape` feeds the result through G3's real `_add_counts`. It checks for `ytdl.jobs` and `ytdl.job_terms`, and that there is no `ytdl.detail`.
   - An unreadable store now raises, so the erase route puts it in `not_done`.
4. **Fixed: the typed terms of a stopping job were left forever.** I did not add a second call, because nobody would make it.
   - `forget_requester` now flags a stopping job with `cancel_requested = FORGOTTEN_CANCEL` (2). The value is still truthy, so every existing reader still sees a cancel.
   - When that job reaches a terminal phase, `set_job` deletes its `job_video_terms` and `job_terms` in the same commit as the phase write. `set_job` is the path every terminal write takes; `run_job` writes `cancelled` through `set_phase`.
   - An ordinary cancel keeps its terms, as before.
   - There is no schema change.
   - Tests: `test_review_4_a_stopping_jobs_terms_go_when_it_stops` goes through the real `worker.run_job`. `test_review_4_an_ordinary_cancel_keeps_the_terms` is the control.
5. **Fixed: the lease expired before the rename.** `forget_requester` now does all its work in one transaction.
   - `expire_lease` and `cancel_now` were split into `_expire_lease_sql` / `_cancel_now_sql`, which do not commit. The public functions still commit, as they did.
   - The worker now sees either a live lease (the job is hidden) or the expiry together with the stand-in. It never sees an expired lease still under the real name.
   - Test: `test_review_5_no_commit_shows_an_expired_lease_under_the_real_name` uses a connection proxy that re-reads the store from a second connection after every commit. The test fails when step 1 goes back to `expire_lease`, which I checked by mutating the code.

   - When `db.ledger_add` gets a `job_id`, it now credits `COALESCE((SELECT created_by FROM jobs WHERE id=?), downloaded_by)`. That is the job's creator as stored at write time, not the in-memory row.

   - Test: `test_review_6_a_clip_finished_after_the_delete_is_credited_to_the_stand_in` passes the stale `created_by` the way the worker does and checks that the credit goes to the stand-in. It also checks the fallback when there is no `job_id`.
7. **Accepted as a wording point; no code change.** After a delete, what the person typed still survives in `jobs.term`, `jobs.term_dir` and `downloads.term`. Those values also name the clip folders on disk. The plan names only `job_terms`. The `forget_requester` docstring now says this. **G9 wording hand-off:** do not claim that a delete or an erase removes what the person searched for. The accurate claim is: "the list of search terms is removed. The search text stays on the job and download records, and in the folder names, under a stand-in name."

   - The person's own jobs are exported whole.
   - Test: `test_review_8_an_export_carries_nothing_of_another_persons_search`.
