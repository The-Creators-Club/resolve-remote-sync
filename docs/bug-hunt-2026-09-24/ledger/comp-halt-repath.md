## bug-comp-app-1 - A halt's paused project folders are unpaused by the next sequencer stop()/pause(), and a restart never re-pauses them
- Mechanism (as you traced it): as the finding says. `Sequencer.stop()` and `pause()` both end in `_unpause_all(self._last_selection)`, which never asked `_is_halted()`. So after `halt_all_sync` paused every folder, the next `stop()` (shutdown's `_stop_lanes`, which covers tray Quit, the self-upgrade hand-off and the Resolve-exit restart) or `pause()` (`toggle_pause`, `_root_pause_lanes`) released every selected project folder while `halt.active` was still true. The between-passes sweep and `_startup_unpause` also reach `_unpause_all`, so the one guard there covers every path. On restart the halt latch is read back, but `_start_lanes` only rewrote lane details: nothing re-paused. That matters because every build up to 0.9.77 released the folders in its own shutdown, so the first restart onto a fixed build finds them running. A fresh sequencer also knows no selection, so `halt_folder_ids()` alone would return only the asset libraries.
- Fix:
  - `companion/src/ccsync_companion/sync/sequencer.py`, `_unpause_all` (~1853): returns early when `self._is_halted()` is true. "Cannot tell" counts as halted. `release_for_halt` still works because `app.release_halt` clears the latch before it calls in.
  - `sync/sequencer.py`, new `halt_folder_ids_to_repause()` (~1088): returns `halt_folder_ids()` plus the valid, non-upload-only slugs and borrowed lenders from the cached `selection.json`. This is a read only: it does not adopt them as the known selection, so the release still goes through `_startup_unpause`'s ignores verification. It then filters to folders that are configured and still running (one `GET /rest/config/folders`), so a halt that held costs no config writes. If that read fails, it returns every id.
  - `companion/src/ccsync_companion/app.py`, new `_reassert_halt_pause()` (~7737): when `halt.active`, pauses each id the sequencer names. Falls back to `_pause_lane_c_folders(True)` for a sequencer double. Never raises. It is called at the top of `_start_lanes` (~6348), ahead of the tray-pause refusal, and at the top of `start()` (~9355). The `start()` call covers the config-problem, drive-out and not-signed-in branches, which never reach `_start_lanes`. `start()` is not a function either builder's findings name. The change is one call plus a comment.

## bug-comp-rclone-1 - A blocked repath is "finished" on the next pass by pointing Syncthing at the directory lane B or the structure clone created
- Mechanism (as you traced it): as the finding says. On a failed move, `reconcile` records the blocked event and leaves the folder paused. `_process_project` then carried on at the new rel: `_maybe_clone_structure` mkdirs `Projects/<new rel>` and lane B fills its `Proxy/`. On the next pass `_move_dir` saw a live source and an existing target and took the conflict branch. That branch returns True for ANY existing target, so the folder was re-pointed at the proxy-only directory and unpaused, the editor got a false "moved your copy", and Resolve was relinked to paths that do not exist. I also traced the second route the finding names. The EXDEV fallback `shutil.move` copies straight INTO the target, so a copy that fails part-way leaves a partial project there. That partial copy includes `.stfolder`, because a dot-directory is listed first and copied first, so it looks exactly like the real folder.
- Fix:
  - `sync/sequencer.py`, `_process_project` (~2143) plus a new `_repath_blocked()` (~2112): if the per-project reconcile did not repath the slug and the repath ledger holds a live blocked event for it, the turn is skipped (no clone, no lane A/B, no borrowed runs, no lane C turn). Nothing is created at the new path before the move happens. A ledger read that raises counts as "not blocked".
  - `sync/repath.py`, `_move_dir` conflict branch (~663): re-points only when the target carries Syncthing's `.stfolder` marker. Lane B excludes that marker and the clone never makes a dot-directory. A target made only of empty directories (what the clone leaves) is pruned with `os.rmdir`, deepest first, which cannot lose a file, and then the move proceeds. Any other occupied target is refused (return False) and `_target_occupied` is set.
  - `sync/repath.py`, `reconcile`:
    - When the target is occupied, the blocked note is the new `target_exists_note()`. Closing Resolve does not help in that case, so the usual note would be wrong. No em dash.
    - A folder no longer configured locally now clears its blocked event (`folder is None` branch, ~478). Without this, a stale event would skip the turn that contains the accept flow, forever.
  - `sync/repath.py`, `_default_move` EXDEV fallback: now `_copy_then_swap` (~166-230). It copies to `<dst>.ccsync-moving`, renames that onto the target only once the copy is whole, and then removes the source. A staging dir found at the start of an attempt is discarded. That is safe by construction: the source is removed only after the rename, so a leftover staging dir is a partial duplicate of an untouched source.
- Regression test:
  - `companion/tests/test_repath_blocked_turn.py::test_a_blocked_move_is_not_finished_by_the_lanes_next_pass` (real Sequencer and real ProjectRepather over tmp_path; the lane B double writes `Proxy/a.mov` the way rclone would). On HEAD, pass 1 runs lane B at the new path and creates `New/Proxy`. My fix leaves nothing at the new path, keeps pass 2 blocked, paused and pointed at the old path, and makes pass 3 (handle released) move the project and run the lanes.
  - `companion/tests/test_repath.py::test_a_target_the_lanes_built_is_not_taken_for_the_project`: the finding's own probe. On HEAD it returns `['s1']` and re-points.
  - `test_repath.py::test_an_empty_skeleton_at_the_target_is_cleared_and_the_move_made`: on HEAD it re-points without moving, so `cut.drp` is not at the new path.
  - `test_repath.py::test_a_failed_cross_volume_copy_leaves_nothing_at_the_target`: on HEAD the partial copy is left at `New`.
  - How I know they fail on HEAD: all four were run against the HEAD copies described above and failed. `test_a_blocked_event_for_a_folder_no_longer_here_does_not_hold_the_turn` is a supporting test for the new skip, not a regression test.
  - Changed existing test: `test_target_exists_conflict_skips_move_but_repoints` now puts `.stfolder` in the target, because the conflict re-point is now reserved for a target that is a Syncthing folder. It passes on both HEAD and the fix.
- Other tests run: same command and result as above (1164 passed). After the `folder is None` clear I re-ran `test_repath_blocked_turn`, `test_repath`, `test_sequencer` and `test_file_moves`: 182 passed.
- Skew / deploy order: companion-only, no wire change. The new blocked sentence travels the same way `repath_events` notes already do (tray, Settings, report), as free text.
- Behaviour change to note for KNOWN_BUGS: while a project's repath is blocked, lane A no longer uploads from it. It never uploaded from the old path anyway, because lane A ran at the new rel. The blocked sentence already says the project is not syncing. A target that holds files and has no `.stfolder` now needs a human to move it away, and the new sentence says so.
