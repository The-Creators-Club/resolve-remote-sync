# Extract of inventory section 11

## Items

### 11-001: Most of the dashboard needs a person signed in; a few things are open, and admin-only actions refuse everyone else.
- Where: accounts-privacy-legal / What each person may see and reach
- What: Everything the dashboard offers needs a signed-in person, except: signing in and out, asking who is signed in, the "is the dashboard up" check, the site description that installers read, a computer's own sign-in and reports, and the doors an editor's computer uses with its own credential (reading its sync plan, unticking its own project, fetching an update, reading the studio-wide stop, finding files, and taking, reporting on and finishing shared work). Those doors still check the computer's credential. An action reserved for admins refuses a signed-in non-admin with "admins only", and refuses someone not signed in with "log in first". A change made from a signed-in browser is accepted only when it comes from the dashboard's own pages, so another web page cannot act in a person's name.

### 11-002: An editor sees their own computers in full and only nameless totals for everyone else; an admin sees everything and can look at the fleet as one editor sees it.
- Where: accounts-privacy-legal / What each person may see and reach
- What: The project list, one project's page, transfers, who holds which media, and the per-computer fleet view are all narrowed to the viewer. A non-admin sees their own computers' rows; for the rest of the fleet they see only totals with no names (computers in total, how many are fine, how many are unhealthy, how many are out of date) and a count of rows hidden from them. Lists of computers whose downloads stopped themselves, computers that are halted, computers that are lost and computers whose reports are refused are trimmed to their own. The studio-wide stop is shown to everyone in full. A non-admin does not see the server's own health block, the release feed warning, the list of report parts the server does not understand, or the progress of a signing-key change. An admin sees everything and can narrow any of these views to one named editor.

### 11-003: A computer belonging to a removed, suspended or disabled person is refused everywhere it reaches the server, and is told why.
- Where: accounts-privacy-legal / Suspending, disabling and removing a person
- What: Whenever an editor's computer reaches the server (reporting, signing in, reading its plan, offering a file-access key and so on), it is refused when its person is:
  - removed from the dashboard (any sign-in method): told "this account was removed from the dashboard. Ask your admin to add it again if that was a mistake";
  - suspended by an admin (any sign-in method): told "this account is suspended on the dashboard. Ask your admin to press RESUME: your sync plan is untouched and comes straight back";
  - disabled (only on sites with the dashboard's own accounts): told "this account has been disabled on the dashboard. Ask your admin to turn it back on: nothing will sync until they do". On such a site a username with no account at all also counts as disabled, but only once at least one account has been created; a site that has created none yet refuses nobody this way.
  On sites where people sign in with NAS accounts or single sign-on, the "disabled" check does not apply (the account lives elsewhere); suspension covers it. The admin's fleet view and the refused-report alert show the short reason ("this account has been disabled", "this account is suspended", "this account was removed"). If the server cannot check because its own records are momentarily unreadable, the computer is let through. The b-roll, music and YouTube download parts refuse the same people: when a computer's sign-in was withdrawn, or its person is barred, those parts answer as if no sign-in was given. The app on the editor's computer tells the editor "this computer's sign-in was revoked: sign in again from the CC Sync tray" for a withdrawn sign-in.

### 11-004: A computer proves who it belongs to with a personal key, or with a studio-wide key an admin can switch off.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: Each editor's computer carries a credential that ties it to one person. It gets one automatically when the editor signs in from the app, or an admin can issue one by hand. There is also one studio-wide key that identifies nobody, accepted only while the admin has it switched on; a computer using it must also carry the editor's signed-in identity. A personal key belonging to someone else is refused with "this key belongs to a different editor". A computer with neither a matching identity nor a personal key is told to sign in from the app, or that its signing key was retired. A credential is either right or wrong; nothing a computer sends can make the server fail.
- Flag: several ways in: a personal key is obtained at the app's sign-in or issued by an admin; the studio-wide key is a second, older way for a computer to be let in

### 11-005: Resolve's scratch projects are ignored by the server.
- Where: resolve-on-the-editors-computer / Knowing which project is open
- What: Resolve projects named "Untitled Project" or "New Doc" (any letter case, extra spaces ignored), and those names followed only by a number ("New Doc 1", "Untitled Project (3)", "New Doc - 2", "New Doc [4]"), are treated as scratch. They are never matched to a project, never trigger the "this Resolve project is not mapped" prompt, never change what the dashboard says the computer is working on, and never count as the computer holding media. Names that merely start the same way, like "New Documentary" or "New Doc Final", are real projects.

### 11-006: The project list shows every project's health and each computer's progress in it.
- Where: dashboard / Projects
- What: For each project: its name and folder, a health status, how much is still needed in total, and how many editors are below 100%. A project whose folder was moved or lost its identity on the server shows as stopped with the reason. It shows how many folders it borrows from other projects are working and how many are not (broken, missing, or the lending project not active). The whole fleet gets one status, the worst of the projects, and whether the server's file sync is reachable. Projects named with slashes ("2026/CCT/Website Highlights") appear as a nested tree, each project shown by its last part, and the branch holding the open project opens by itself. For each computer in a project: its name and owner (or "unmapped" when the computer is not yet linked to a person), connected or not, when it last connected, completion percentage, files, bytes and deletions still needed, what it holds, speed, time left (only shown while something is actually moving), its status, when it last reported anything, and a sentence saying why its dot is not green when the computer went silent. Each direction of movement for that computer is shown separately with its state, a coloured chip and the chip's reason in words, how long it has been in that state, how many files are waiting, its last error, its last successful sync, the app's version, the project it is working on, bytes done of total, speed and time left.

### 11-007: One project's page adds what the server holds, its borrowed folders, and a total sync percentage per computer.
- Where: dashboard / Projects
- What: Besides everything in the list, a project's page shows whether it is active, what media the server holds for it, the folders it borrows from other projects (with every status) and the projects that borrow from it (working links only). Computers that report media for the project but do not sync it (for example a computer wired to the server) appear as "report only" rows with their media counts and a status. Each computer gets one total sync percentage covering proxies and the project's other files, against what the server has, rounded to one decimal; camera originals are left out. Before a computer has sent its list of files, its plain file-sync completion is shown instead.

### 11-008: The transfers view shows what is moving now, what is waiting, and the last 50 transfers that finished.
- Where: dashboard / Transfers and the queue
- What: Moving now: each file in flight with its editor, computer, direction, name, bytes done of total, percentage, speed and time left; for movement that is not tracked file by file, one row per project while it moves. When the server itself is still receiving files for a project, a row reads "<project>: N file(s) arriving at the server", with no editor named. The total fleet speed is shown and rows are sorted fastest first. History: the last 50 finished transfers with editor, computer, direction, name and time.

### 11-009: The queue shows, per person, computer and project, what is still owed, and never claims "nothing" when it cannot tell.
- Where: sync / What is owed
- What: The queue lists what is waiting to go up or come down for each person, computer and project, worked out from what the server has against what the computer says it has. For files the computer is missing from the project's general sync, the first 50 are listed and the list says when it was cut short. Only ticked projects can be queued, and an upload-only tick never queues anything coming down. Computers wired to the server, and people whose every computer is wired, never appear. A file already moving is not listed again as waiting. A row with nothing waiting is dropped, unless the computer's own list was cut short so that "nothing" really means "cannot tell". A just-ticked project shows a "preparing" row for each computer until there is something to count. An upload-only tick shows "preparing" until that computer's first list of files arrives; if the computer (or, for a tick not yet assigned to a computer, every computer it stands for) withholds its file list by a reporting switch, the row says the uploads are uncertain and not reported, never "nothing owed". A row on a computer that has said it cannot move (drive unplugged, halted, not signed in and so on) says it is held, and why. Totals give files queued (preparing rows not counted) and bytes queued.

### 11-010: For each project, an admin can see which media every computer holds and which clips in its Resolve project are offline.
- Where: dashboard / Projects
- What: For one project: what media the server holds, and for each person and computer: wired or not, how many originals and proxies it holds and their sizes, whether its list was cut short, a status that suits the computer's role, a "proxy only" badge, the bins of its Resolve project with each clip marked online or offline, and how many clips are offline. A computer that has sent its bins but not yet a disk report still appears, with zero counts.

### 11-011: The fleet view has one row for every computer that has ever reported, with its status and why.
- Where: dashboard / Each computer's state
- What: A computer keeps its row even after 30 silent days. Each row shows its directions of movement in a fixed order, a headline, and a status that is the worst of its directions and of whether it is still reporting, so a computer that stopped reporting stops being green. A direction stuck showing "syncing" for longer than that computer's own normal time turns into a stall. The row also shows: whether the computer is verified as its person's; how it reaches the server (for example relayed); safety stops in force (downloads that stopped themselves, halts); whether an admin's "resume proxy download" is still waiting to be picked up; disk colour and percentage (nothing at all when the computer never reported its disk); its clock, marked "AHEAD" or "SLOW" when off by at least the warning amount; whether diagnostics were asked for; whether the stall shown is still current; when and why the server last refused its report; wired or editing mode; whether the account is suspended; a summary of its sync plan; the studio-wide stop; b-roll and music indexing progress; the shared work it is doing now and what it is able to do; how much of its footage has proxies; YouTube import state; its operating system; and the app version running and the one current. Each row also names the reporting categories that computer withholds ("NOT REPORTED BY THIS COMPUTER") and its licence acceptance state.

### 11-012: Each computer gets one sentence saying why it is not syncing, plus warnings about clips that will never upload.
- Where: sync / Saying truthfully what the sync is doing
- What: The row gives one sentence for why the computer is not syncing, and each separate cause. Some reasons, such as being set to upload only, are shown as information, not as a fault. Added to it, also as information: "N clip(s) in the open project are outside the tree and will never upload", and "N clip(s) only on this computer in '<project>' [and M other project(s)], which it does not have open; they will never upload". "Idle, nothing owed" is claimed only when the server could actually count what this computer owes; never for a wired computer, a computer that never sent its file list, or one whose only answer is "cannot tell". That count stays at most about 15 seconds old and is redone as soon as anything it depends on changes.

### 11-013: A computer whose person has lent its graphics card shows a "volunteering" chip until the offer ends.
- Where: fleet-jobs / What a computer can honestly offer
- What: When a computer's own person has offered its graphics card for shared work until a time that has not yet passed, its row shows a "volunteering" chip with the end time (hours and minutes, in universal time). There is no control on the dashboard to make or end the offer.

### 11-014: A computer running a build different from the current one is flagged out of date.
- Where: releases-and-updates / Pushing updates and seeing who has what
- What: A computer is out of date when the version it runs differs from the current published build for its own operating system, whether older or newer (a computer that does not say which system it runs counts as Windows). One that reports no version is flagged "unknown build". One running a build the vendor has withdrawn shows the reason given for withdrawing it.

### 11-015: The fleet view also lists the fleet-wide trouble an admin must know about.
- Where: dashboard / Each computer's state
- What: Fleet-wide lists: computers whose proxy downloads stopped themselves (with the reason), computers halted (and over what), the studio-wide stop, computers whose reports are being refused (with the reason), "lost" computers (known but silent past the lost age, which keep their plan), parts of computers' reports this server does not understand (a sign the computers are newer than the server), how many computers are still signed in under a retired signing key (the count and up to 20 names; zero means a key change has finished), the release feed warning, and whether the server's own background checking is healthy. The release feed warning gives when the feed was last checked, how many days ago, the last error, "stale" when the feed has been read before and the last check is older than the stale limit (a feed never yet checked is not called stale), and whether every build on offer needs a newer server.

### 11-016: Anyone can ask whether the dashboard is up; a signed-in person or a computer gets a fuller health summary.
- Where: server-install-and-running / Health checks and alerts
- What: The check always answers, even when unhealthy, so installers and the macOS set-up wizard can use it to tell whether the dashboard is running. It is healthy when the server's file sync is reachable (or none is set up) and the server's background checking has not died. Anyone gets only healthy or not and the version. A signed-in person or a recognised computer also gets: exactly which build is running; whether the file sync is reachable; whether background checking is alive or has fallen behind; folder errors; when each kind of check last ran and whether it worked; refused share changes; per operating system, the current version, when it became current, how many computers there are, how many run it, how many are behind and how many are refusing it (counts only, no names), or "cannot tell"; computers seen per operating system; the release feed's health; free space on the server's data disk; counts of open errors and warnings and of open diagnoses (one error reported when they cannot be counted); the Timeline Cards state, its notes folder and whether its assistant features can run; and the state of each switchable part, "unknown" when never recorded. None of the parts can make the dashboard count as unhealthy.

### 11-017: Installers and editors' computers can read the site's description before anyone signs in, and it never contains a secret.
- Where: server-install-and-running / Settings and secrets
- What: The site description carries no secret, person, project, list of paths or key. Each value comes from the site settings an admin made, else from installation; blank means "this site was not told". It gives: the organisation's name, a short name (the full name when not set), a support contact, the product name (default "CC Sync") and a logo (blank means the product's own mark); the tree's name and the drive letter editors use, the server's share locations; what a computer needs to reach the server's files, including the server's own identity so the computer can verify it is talking to the right server; the address editors browse the dashboard at; the template folders a new project gets; the shared asset folders; the fixed list of video file kinds treated as originals (not configurable); the release feed's location (only when it is a secure address); the kind of NAS; the switches for YouTube downloads, the extra measures against YouTube's blocking (only ever on when downloads are on) and automatic updates, all off unless the site turns them on; the site's four reporting switches; and the b-roll indexing quality, "good" (a smaller model needing about 8 GB of graphics memory) or "best" (a larger one needing about 12 GB).

### 11-018: Asking for a project or a computer one may not see answers as if it did not exist.
- Where: accounts-privacy-legal / What each person may see and reach
- What: Any signed-in person may read the project list, one project, transfers, who holds what, the fleet view, and the list of files one computer is missing in one project (with how many it needs), each narrowed to what they may see. An unknown project is answered "unknown project '<name>'". Asking for the missing files of a computer that is not in the project, or that belongs to another editor when the asker is not an admin, is answered "device not in project", so an editor cannot even learn that another person's computer exists.

### 11-019: An admin can grant or withdraw one editor's access to one project.
- Where: accounts-privacy-legal / What each person may see and reach
- What: An admin can list the editors given access to a project, grant access to one more (the name is trimmed and lower-cased; an editor the dashboard does not know is refused with "unknown editor '<name>'"), and withdraw access (no check that the editor exists). On a site that controls access per project, this is the only way an editor wired to the server, who cannot tick, gets into a project. A change is recorded in the history and takes effect straight away. The project page offers the same control.

### 11-020: A person signs in to the dashboard with a username and password, and a failed sign-in never says which half was wrong.
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: Usernames are 1 to 64 characters, trimmed and lower-cased; passwords 1 to 256. Refusals, in this order:
  - the dashboard has no sign-in set up: "login not configured";
  - the site is set to secure connections only and the page was not opened securely: told to use the secure address (not counted as a failure);
  - on a single sign-on site, the password form works only for admins (break-glass); anyone else is told "bad username or password" (counted);
  - too many failures: "Too many sign-in attempts. Try again in <a minute | N minutes | about an hour>." (see the next item);
  - the server is momentarily too busy to check: "login busy: <reason>; try again";
  - a wrong password, or a person an admin removed (unless named in the site's admin list): "bad username or password" (counted).
  A successful sign-in clears that username's failures, starts a sign-in the server can withdraw later, and says who is signed in and whether they are an admin. A tool other than a browser can sign in the same way and then make changes.

### 11-021: Repeated failed sign-ins make a person wait, from a minute up to an hour.
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: Applies equally to the dashboard and to signing in from the app on an editor's computer. A person may fail 5 times per username, and one place on the network 40 times, within an hour. Past either limit the wait starts at 1 minute and doubles each time up to 1 hour, and the person is told how long to wait. A made-up username is held back exactly like a real one, so the wait does not reveal which names exist. A successful sign-in clears only that username's count, not the count for the place it came from.

### 11-022: A dashboard sign-in lasts up to 100 days, and a person is warned as its end nears.
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: A sign-in lasts at most 100 days, whether used or not. The dashboard can tell a signed-in person when their sign-in ends and how many days are left, so they are warned before it runs out; once it has, they are told "Your sign-in has expired. Sign in again." A person can sign out, which ends that sign-in on the server too. Anyone can ask who is signed in and whether they are an admin.

### 11-023: An editor signs the app on their computer in with their username and password, and the computer is then theirs.
- Where: editor-app / Signing in, the computer's identity and the licence
- What: The app sends the username and password, and the computer's name (cut to 48 characters), its operating system, its processor and its app version. The same limits on attempts apply as for the dashboard. Refusals and what the editor is told:
  - sign-in not set up on the server: "identity not configured";
  - server busy: "verify busy: <reason>; try again";
  - wrong password: "bad username or password";
  - on a site with the dashboard's own accounts: "'<name>' is not an account on this dashboard - ask an admin to create it on Settings, Users", or "'<name>' is not an editor on this dashboard - ask an admin to give the account the editor role";
  - on a site using NAS accounts: "'<name>' is not in the 'editors' group on the NAS. Ask an admin to add the account in Admin > Users", or "cannot confirm fleet membership right now: try again shortly" when the NAS cannot be asked;
  - a removed, suspended or disabled person: the sentence for that case.
  People named in the site's admin list always pass the membership check. On a site that uses NAS accounts or single sign-on but has no way to ask the NAS, membership is not checked at all and nobody is told. On success the computer gets a long-lived sign-in that works even straight after an admin withdrew the person's earlier ones. Unless the studio-wide key is on, it also gets its own personal key, labelled with the computer's name; signing in again on the same computer replaces that computer's previous key, and a person may hold at most 16 such keys, the least recently used beyond that being withdrawn. The answer also carries an update offer for that computer when one exists, or the reason an available build was held back from it.

### 11-024: A computer reads its own sync plan, and only its own person, that person's computers and admins may read it.
- Where: sync / A plan belongs to a computer
- What: A person's plan can be read by that person signed in, by an admin, or by one of that person's computers. A suspended, disabled or removed person's computers are refused, but the plan stays readable to an admin, so they can see what pressing RESUME will restore. Someone else is told "log in, or present" a credential. What the plan holds, for one named computer: every computer the person has; every remembered pairing of a Resolve project name with a project (with who set it and when); and each ticked project in queue order with its name, folder, position, whether it is active, whether it is full sync or upload only, the folders it borrows from other projects, and, for a full tick of an active project, the camera originals picked to come down to that computer. Asked without naming a computer, the answer is everything ticked on any of the person's computers.

### 11-025: Folders borrowed from another project come down with a full tick, never twice, and the app warns before the lender is removed.
- Where: sync / What syncs where
- What: A ticked project's borrowed folders are handed to the computer only when the link is working and only on a full tick. Each is named "<lending project>/<folder within it>". When the lending project is itself fully ticked on the same computer, the borrowed folder is already there and is not fetched separately, but the app uses the link to warn the editor before the lending project is removed. A borrowed folder inside one already handed out is dropped. A lending project that is only upload-only on that computer does not count as already there.

### 11-026: An editor or an admin ticks a project for a computer, for full sync or upload only.
- Where: dashboard / Ticking and unticking
- What: Ticking is done on the dashboard by the editor themself or an admin; an editor's computer cannot tick. The choice is full sync (the default) or upload only; ticking an already-ticked project the other way switches it. Refusals: "you can only change your own projects (admins excepted)"; "unknown or inactive project '<name>'"; "this account is wired to the server: it works directly off the NAS and syncs nothing, so projects cannot be ticked for it" when every computer of the person is wired; "'<editor>' has no computer named '<computer>'"; "'<computer>' is wired to the server: it works directly off the NAS and syncs nothing, so projects cannot be ticked for it". Ticking without naming a computer ticks it on every computer the person has, or, when they have none yet, holds it for their first computer to report. A tick is recorded in the history with where the project was ticked before and after (nothing is recorded when nothing changed), and sharing to the computer starts at once.

### 11-027: Ticking a project warns, without refusing, when its proxies would not fit comfortably on the computer.
- Where: sync / Disk space
- What: When the project's proxies plus 20 GB exceed the computer's free space, or the proxies are at least half of it, the tick goes ahead and the person is told "<project> is <size> of proxies. <computer> has <size> free.", followed by " That is more than will fit." when the proxies are larger than the free space. Nothing is said when either figure is unknown. When no computer was named, each of the person's computers is checked and up to three such sentences are shown.

### 11-028: An editor, an admin, or the editor's own computer can untick a project.
- Where: dashboard / Ticking and unticking
- What: The editor themself or an admin can untick from the dashboard, and the editor's own computer can untick its own project, so the app can take a project off the computer before deleting its copy. Without naming a computer, the project is removed from every computer of the person and from any tick held for a future computer. When a computer asks to untick a project that has no tick under its name but is still ticked on another of the person's computers, nothing is removed and it is told: "There is no tick for <project> under this computer's name (<computer>), but it is still ticked for another of your computers. Nothing was removed. If this computer was renamed, wait until the dashboard shows the new name, or untick it on the dashboard." A project ticked nowhere is simply fine. An untick is recorded in the history, naming the computer when a computer did it, and takes effect at once.

### 11-029: An editor picks camera originals to come down to one computer, from the dashboard or from inside Resolve.
- Where: sync / What syncs where
- What: The editor themself, an admin, or the editor's own computer (through a menu in Resolve) can add and remove picks, up to 5000 of each at once, files or whole folders. Picks are always for one computer: without one the person is told "say which computer: originals are picked for one computer at a time"; an unknown computer, or an unknown or inactive project, is refused by name. Each path must be inside the project and is refused, never repaired: a full path or drive letter ("'<p>' is an absolute path: name the file inside the project instead"), an empty one ("a pick needs a path inside the project"), a bad folder name, anything in a proxy folder ("'<p>' is inside a Proxy folder: proxies already come down on their own"), or the project's identity file ("the project marker is not footage"). Additions (never removals) are refused as a whole when the computer or person is wired ("<computer> is wired to the server: it works directly off the NAS, so every original of <project> is already there and nothing needs to come down."), when the project is not ticked there ("<project> is not ticked on <computer>, so nothing of it comes down there. Tick it for <computer> first, then choose its originals."), or when the tick is upload only ("<project> is set to upload only on <computer>, so nothing comes down to it. Switch it to full sync on the dashboard first."). Removals are applied before additions. Each change is recorded in the history with a count and the paths, under the editor's name even when the computer made it, and the person is told how many were added and removed and the total size now picked for that computer and project.

### 11-030: An admin moves a file or folder on the server, and every computer that has it follows.
- Where: proxies-and-file-moves / Moves that reach every computer
- What: Only an admin may move files ("only an admin can move files on the server"). The admin names something inside a project and where it goes: the same project or another, a folder (moved into it, keeping its name) or a full new path, or nothing for the destination project's top. Rules, each refused with its reason: no slashes inside a name, no names starting with "." and no "..", no control characters, nothing naming a proxy folder ("must not name a Proxy folder: proxies move with their originals"), never the project's identity file, nothing leading outside the projects tree ("path escapes the Projects tree"). Other refusals: the server's projects folder is not available ("the server's Projects folder is not mounted on this dashboard. Ask whoever installed this server to create or link the folder: it is a server-side step"); an unknown or inactive project at either end; "nothing at <project>/<path> on the server"; "<project>/<path> already exists: nothing was moved"; "a folder cannot be moved into itself"; "that is where it already is"; and when the server fails to move it, "the server could not move it: <error>", which is also recorded in the history. A move never overwrites anything. The computers that must follow are every computer with the project ticked (either way) and any computer whose file list says it holds the item; each receives the move the next time it reports. A change of letter case alone is a valid move.

### 11-031: When a single file is moved, its proxies move and are renamed with it.
- Where: proxies-and-file-moves / Moving footage through the product
- What: The file's proxies beside it (same name, any extension, letter case and accent spelling ignored) go to the proxy folder beside its new place and take its new name. A proxy that cannot follow (something already there, held open, unreadable) is listed and the move still counts; the result is "done", or "partial" with "these proxies did not move: ...". The admin is told what moved where, how many proxies moved and failed, and which computers must follow.

### 11-032: A move cut short on the server is finished or dropped on its own, and one that cannot be settled is shown to the admin.
- Where: proxies-and-file-moves / Moves that reach every computer
- What: A move is recorded as started before anything changes on disk and is offered to no computer until it is done. Whenever the server starts, and regularly while it runs, it looks at every unfinished move: if only the new place exists the move is completed ("completed after an interrupted move") and the computers are told; if only the old place exists the record is dropped, since nothing moved; if both or neither exist it stays unfinished, is offered to nobody, and is shown on the project page as a problem (what, from where to where, whether both exist, the two projects).

### 11-033: A move delivered to a computer that never answers expires, and an admin can send it to that computer again.
- Where: proxies-and-file-moves / Moves that reach every computer
- What: A move a computer received but never answered expires after a while; until it is sent again, that computer may upload the file again at its old path, and nobody is told except in the move list. A move not yet delivered never expires. An admin can list a project's moves and every move still waiting for computers, and can send an expired move again to one named computer; refused when there is no such move in the project, or with "that computer has already answered this move".

### 11-034: An admin can put a move back exactly as it was.
- Where: proxies-and-file-moves / Moves that reach every computer
- What: Undo makes the reverse move, restoring the exact original path and name, and every computer the original move reached is told as well. Before undoing a folder move the server tries to take a NAS snapshot, and goes ahead even if it cannot. Refusals: "no move <id> on this project"; "that move has already been put back"; "one of the computers could not apply this move, so its copy is still at the old path. Sort that computer out first, then put it back."; and any refusal a move would get (for example, something has since been created at the old place). The original move is then shown as undone and the undo is recorded in the history.

### 11-035: An admin, or an editor syncing a project, can make a folder of another project part of this one.
- Where: sync / What syncs where
- What: Only an admin or a signed-in editor who has the project ticked may change its shared folders ("only an admin or an editor syncing this project can change its shared folders"). The list travels with the borrowing project's own folder on the server, so it survives anything done to the dashboard, and the dashboard's view is refreshed straight after each change. Adding: the folder may be typed as the project's name path ("2026/FF5/..."); refused with "cannot share that folder: <reason>" when it is not a real folder of another project, and with "this project already shares 32 folders; remove one first" at the limit of 32. Adding one already listed changes nothing. Each entry records who added it and when. Removing takes it off the list. Both are refused when the server's projects folder is unavailable, the project is unknown or inactive, or "this project's folder marker does not carry its identity; repair the marker before editing its shared folders". Each link then shows as working, missing, "the lending project is not active on the dashboard", or the specific reason it is broken.

### 11-036: A Resolve project name is paired with a project once, by an admin or by an editor who has it open, and only an admin can change it.
- Where: resolve-on-the-editors-computer / Knowing which project is open
- What: Anyone signed in can see every pairing (Resolve project name, project, folder, how it was made, who made it, when). The first pairing for a name may be made by an admin, or by an editor only for a Resolve project one of their own computers has reported ("'<name>' is not a Resolve project any of your computers has reported. Open it in Resolve first, or ask an admin"). The first one wins: a second attempt is told "already mapped. Ask an admin to change it." Changing or removing a pairing is for admins only ("admins only: destination roots are fixed once set"); a removed pairing is worked out again from the next report. Pairing with an unknown or inactive project is refused by name. Resolve project names are up to 256 characters.

### 11-037: Each person has a panel of their own queue: their ticked projects in order with progress.
- Where: dashboard / Ticking and unticking
- What: For one person, or one of their computers: each ticked project in queue order with its name, position, full or upload-only, whether the project no longer exists, whether the computer is working on it right now, completion, files and bytes still needed, speed and time left, a status (green when nothing is known), and the borrowed folders it brings in. It also names every computer of the person (listed in the confirmation when unticking for the whole person), the Resolve project open now, the project it was matched to, and whether that pairing was made by the editor, an admin or worked out by the product. With a computer named, that computer's last report is used; otherwise the person's most recent one.

### 11-038: A list of projects not yet ticked is still prepared for the queue panel, but nothing shows it.
- Where: dashboard / Ticking and unticking
- What: The product still works out which projects a person has not ticked, for a picker that used to sit in the queue panel. Ticking moved to the project tree, and nothing shows that list any more.
- Flag: unreachable

### 11-039: Anyone signed in can create a project; it gets the site's template folders and is ready to tick at once.
- Where: dashboard / Projects
- What: The person names the project (1 to 128 characters) and the folder it goes in (default the top of the projects tree), and may pair a Resolve project with it. Refusals, each with its reason: the server's projects folder is unavailable; "parent folder does not exist"; "project name is required"; names with slashes, starting with "." or containing "..", or containing control characters; "cannot create a project inside another project (<path>)"; "that folder already contains a project (<path> [(+N more)]). Pick that one instead"; "that name produces an empty identifier. Use letters or numbers"; an archived project already there ("<path> is an archived project. An admin can put it back with "Unarchive" under "Archived projects" on the Sync plans page, and it keeps its folder, its files and its ticks"); "that folder is already a project with a different identity"; an existing ordinary folder of that name ("Projects/<path> already exists. Use "Use this folder" to point the project at it instead of creating another folder inside it"), unless the person chose to use it; "a different project already uses this identifier: <name>. Pick another name"; "could not create the folders on the NAS. Ask an admin to check the dashboard log" (the details, which name server paths, are kept from the person); and a Resolve project none of the person's computers has reported (checked before anything is made). The folder, the site's template subfolders and the project's identity file (recording who created it, keeping the first creator on a retry) are made, the project is active straight away and can be ticked, and the Resolve pairing is made if given (first one wins). Asking twice is harmless. On sites that control access per project, the new folder is closed to everyone but that project's group and the creator is given access. The creation is recorded in the history.

### 11-040: Anyone signed in can turn an existing folder into a project without changing its contents.
- Where: dashboard / Projects
- What: "Use this folder" makes an existing folder a project, adding no template folders. Refusals: the server's projects folder is unavailable; bad names; "pick a folder: the Projects root itself cannot be a project"; "folder does not exist"; "this folder is inside an existing project (<path>)"; the folder contains a project; "that folder name produces an empty identifier"; an archived project; "a different project already uses this identifier: <name>"; "could not write the project marker: <error>"; "this folder claims the identity of <project>, which still exists. Resolve the duplicate on the NAS first" (a project copied rather than moved); a Resolve project the person's computers have not reported. A folder that already carries a project identity keeps it, so a project moved on the NAS is picked up again at its new place. Unlike creating, using an existing folder is not recorded in the history.
- Flag: several ways in: creating a project and choosing to use an existing folder of that name does the same, but adds the template folders

### 11-041: An admin can archive a project, which deletes nothing, and bring it back.
- Where: dashboard / Projects
- What: Archiving keeps the folder, its files and every tick. The project leaves the tick lists, the assignments and the queue, and computers stop syncing it. On sites that control access per project, the project's group loses access while archived and gets it back on unarchive. Refusals: "no project called '<name>'"; "'<name>' is already archived"; "'<name>' is not archived". Both are recorded in the history, with the editors who have it ticked, and the admin is told who has it ticked.

### 11-042: The server refuses to stop sharing too many projects with computers at once until an admin approves the exact list.
- Where: sync / Safety stops
- What: When the server would stop sharing more project folders with computers in one go than a safety limit allows, it does none of them and shows the admin a banner with the list and its count. The admin can approve exactly that list ("APPLY THESE N REMOVALS"); the approval lasts one hour and covers only the folder-and-computer pairs shown. Refusals: "no share removals are waiting for approval"; "the list changed: N removal(s) are waiting now, not M. Reload and check them again."; "too many removals to approve one by one; raise the per-computer allowance under Settings, then Sharing safety, instead" (when the list was too long to show whole). The approval is recorded in the history with up to 50 of the pairs and takes effect at once.

### 11-043: An admin sets how many share removals each computer may have at once before the brake applies.
- Where: sync / Safety stops
- What: A whole number from 0 to 100 removals per computer at once (refused otherwise with "must be a whole number from 0 to 100"); 0 goes back to the single fixed limit. The setting records who set it, is recorded in the history with the old and new value, and takes effect at once.

### 11-044: An admin sees every person, computer, suspension, waiting key and unclaimed device on one view.
- Where: dashboard / People and computers
- What: The admin sees: how people sign in on this site (the dashboard's own accounts, NAS accounts, or single sign-on) and, on own-account sites, every account; every known computer with its owner, name, operating system, app version, when last seen, wired or editing, and how many projects are ticked on it; suspended people with each suspension's details; file-access keys offered by editors' set-up wizards and waiting for approval; when a NAS is set up, the NAS's editor accounts (name, full name, whether file sharing is on, whether it has a key, locked or not), never the server's own service account; computers that have appeared to the server's file sync but are not linked to a person, and ones waiting to be accepted, each with a suggested owner and computer when that computer already reported; the names a computer can be accepted under; and people the fleet knows who have no account (the only ones that can be cleaned up that way). When suspensions or waiting keys cannot be read right now, or the NAS or file sync cannot be asked, the view says so for that part only and shows the rest.

### 11-045: An admin accepts an unclaimed computer under its owner's name, and a malformed computer identity is refused.
- Where: dashboard / People and computers
- What: A computer identity typed in for acceptance is checked for its exact shape first and refused with an explanation that a malformed one could never connect and must be copied whole. Accepting it under a name the dashboard does not know is refused unless the admin ticks CREATE NEW EDITOR: "'<name>' is not an editor this dashboard knows. Pick the OWNER of this computer: one editor can own several computers, so a second computer takes the same username as the first. Tick CREATE NEW EDITOR if this really is a new person."

### 11-046: An admin creates an account or updates one.
- Where: accounts-privacy-legal / Who may sign in
- What: The admin gives a username (1 to 32 characters), and optionally a full name, a password (at least 12 characters), a file-access key, and on own-account sites a role (admin or editor, default editor). On own-account sites a blank password makes a random one, shown to the admin once and never again. On NAS-account sites: usernames must start with a letter and use only lowercase letters, digits, ".", "_" and "-"; a key that is not a valid public key is refused with a message saying so; a blank key is allowed only for a new account ("<name> already has an account. Leave the key blank only when creating a new one: to change this editor's key, paste the new key here"); the account is made or updated in the NAS's editors group; when the NAS cannot be reached or set up the admin is told so; setting a password there signs that person out of every browser and is recorded as a password reset. The person becomes a known editor and the view refreshes.

### 11-047: An admin resets a person's password, which signs that person out of every browser.
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: The new password must be at least 12 characters. On NAS-account sites the NAS refuses system accounts and anyone outside its editors group. The reset is recorded in the history (how it was done, nothing about the password). Every browser sign-in of that person ends, except the admin's own current one when they reset their own password, and the admin is told how many were ended.

### 11-048: On sites with the dashboard's own accounts, an admin can disable an account and turn it back on.
- Where: accounts-privacy-legal / Suspending, disabling and removing a person
- What: Only on own-account sites ("this action is only available" with the dashboard's own accounts). Refusals: "'<name>' is not a local account"; "you cannot disable the account you are signed in as - sign in as another admin to disable this one"; "this is the last enabled admin account - create another admin before disabling it". Disabling ends every browser sign-in of that person and withdraws every personal key of their computers, so those computers stop reporting. Turning it back on restores only the password, not the old sign-ins or keys. Both are recorded in the history and the admin is told how much was ended.

### 11-049: An admin can suspend a person, which stops their computers syncing but keeps their plan exactly, and resume them.
- Where: accounts-privacy-legal / Suspending, disabling and removing a person
- What: Works whatever the sign-in method. An optional reason (up to 255 characters) is shown on the person's row and in the history, never sent to the computer. While suspended, the person's computers are refused everywhere with the suspended sentence and the server stops sharing projects with them; their plan is kept untouched, so RESUME brings it back exactly. Nobody is signed out of the browser. Refusals: "not a valid username"; "you cannot suspend the account you are signed in as - sign in as another admin to suspend this one"; "'<name>' is not an editor this dashboard knows". Suspend and resume are recorded in the history.

### 11-050: An admin can remove a person from the whole product, and their computers are refused from then on.
- Where: accounts-privacy-legal / Suspending, disabling and removing a person
- What: Removes the person's account, every computer of theirs from the server's file sync together with its shares, their NAS account where the site uses one, and every record about them (computers, plans and so on), and marks them as removed so their computers are refused even where the account still exists on the NAS or the sign-on provider. If the file sync cannot be reached, nothing is removed and the admin is told the file sync could not be reached, so nothing was deleted, and to try again once it is up. If the NAS fails, the person's records stay ("<nas kind>: <error> - the account and the fleet records were left in place"). Then every key and sign-in is ended and deleted and their name is replaced with a stand-in in the YouTube download records and the client folders; each of these last steps may fail alone and is reported as a warning: "their revoked report tokens were kept; they are deleted 180 days after revocation", "their signed-out sessions were kept until they expire", "their name could not be removed from <YouTube requests | client folders>: the dashboard log names the reason". The history records the removal under a stand-in name, with counts. Refusals: "not a valid username"; "you cannot delete the account you are signed in as - sign in as another admin to remove this one"; the last enabled admin; "<nas kind>: <error> - nothing was deleted" when the NAS cannot be asked; "'<name>' is not an account or an editor this dashboard knows". A name the fleet knows but no account system has (a computer accepted under a name never set up, an account removed from the NAS by hand) can be removed too. The admin is told what was removed and any warnings.

### 11-051: An admin can forget one computer, which a still-signed-in app will register again.
- Where: dashboard / People and computers
- What: Removes the computer from the server's file sync with its shares first, then its records and its plan. If the file sync cannot be reached nothing is removed ("so the computer was not removed - try again once it is up"). An unknown computer is refused by name. It is recorded in the history. It does not withdraw anything: the admin is told that an app still running and signed in on that computer will register it again the next time it reports.

### 11-052: An editor's set-up wizard offers the computer's file-access key, which waits for an admin.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: The wizard sends the key it just made, the username and which computer made it (shown only). It must carry the editor's signed-in identity for that same username. Refusals: sign-in not set up on the server; "sign in from the installer or the companion tray first"; the removed, suspended or disabled sentence; a key that is not a valid key. The offer grants nothing until an admin approves it; it is recorded in the history, and the wizard is told it is waiting and given the key's fingerprint.

### 11-053: An admin approves or throws away a waiting file-access key.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: Approving adds the key to the person's account and takes it off the waiting list; the person becomes a known editor and the approval is recorded. On NAS-account sites the key is added beside the account's other keys, since each of a person's computers offers its own; the same key already there is not added twice. Where the NAS cannot show the existing keys, the approved key becomes the account's only key, and nobody is told. When the NAS fails the admin is told and the key keeps waiting. A key that is no longer waiting is refused ("no key waiting for <name> with that fingerprint"). Throwing an offer away withdraws nothing; the computer may offer again. On own-account sites an admin can also add a key to an account by hand (with a label) and remove one.
- Flag: differs: on NAS sites whose NAS cannot show existing keys, approving replaces every other key instead of adding one

### 11-054: An admin sees every browser sign-in and can sign a person out of all of them.
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: The admin can list every browser sign-in (each shown by a shortened identifier), which works even without a NAS. Signing a person out ends all their browser sign-ins and tells the admin how many; refused for a bad username, or when sign-ins are not being recorded.

### 11-055: An admin can withdraw every computer sign-in a person has, for example when a laptop was taken.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: Every sign-in issued to that person's computers so far stops working: their computers are refused on their next report and the app asks the editor to sign in again, which works at once. Nothing is deleted and no plan changes. It is recorded in the history.

### 11-056: An admin sees each computer key with the computers using it, issues new ones and withdraws them.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: The list shows every key in force with the computers whose last report used it, and how many computers still use the studio-wide key against personal ones, which tells the admin when it is safe to switch the studio-wide key off. Issuing a key for a person (username rules apply, label up to 64 characters) shows its secret once only. Withdrawing a key is never refused because it is in use; the admin is told who is affected: "Revoked. <A | A and B | A, B and N more> was using this token and will stop reporting within a minute. Give that editor a new token." or "Revoked. No computer's last report used this token, so nothing should stop reporting." An unknown key is refused ("no such live token").

### 11-057: An admin can stop syncing on every computer at once, with a reason every editor sees, for a set time.
- Where: dashboard / Stopping and resuming the fleet
- What: Anyone signed in, and any recognised computer, can see whether the studio-wide stop is on: its reason, who set it, when, when it ends, and how many times it was extended. An admin starts or releases it. The reason (at least 3 characters, up to 500) is shown in every editor's tray; without one the admin is told "say why: the reason is shown in every editor's tray (at least 3 characters)". It lasts 24 hours by default, any time above zero up to 720 hours (30 days), and ends by itself. "KEEP HALTED" moves only the end time, keeping the reason, who set it and when it began; asked after the stop already ended, it is refused with "Syncing already started again at <time>. To stop it again, give a reason." or "Nothing is stopped, so there is nothing to keep stopped. Stop syncing with a reason." Each computer learns of a start or release the next time it reports, so the stop survives a dashboard restart and reaches computers that were offline. An editor cannot release it from their computer.

### 11-058: An admin can push an update to one computer, including a build not yet offered to everyone.
- Where: releases-and-updates / Pushing updates and seeing who has what
- What: "UPDATE NOW" on an editor's behalf: the computer installs the named build the next time it reports, only if the signed offer it holds is that exact version and only when replacing the program would not cut off work in progress. Without a version, the current build for that computer's operating system is used. A build published but not yet current can be pushed, which offers it to that one computer only, as a trial. Refusals: an unknown computer; "no current companion package is published for that computer's platform"; "<version> is not in this channel for <platform>"; "<computer> kept crashing on <version> and rolled itself back, so it will not install that build again, not even from UPDATE NOW. Publish a fixed build and it is offered as usual." The admin is told whether a request was already waiting, whether the build is a trial build, and when it will apply: "on that computer's next report, usually within 30 s. It was last heard from <N s | N minutes | N hours | N days> ago"; or, when last heard from 24 hours or more ago, "when that computer next reports. It was last heard from ..., so this may sit for a while"; or, with no report on record, "when that computer next reports. Nothing on record says when it last did"; with ", as a targeted offer of a staged build" added for a trial build. A long-silent computer gets a warning, never a refusal.

### 11-059: On a server with no sign-in set up, a computer can read its plan with the studio-wide key alone.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: When the server has no sign-in secret set up, a computer can read its plan with the studio-wide key alone, without an editor's identity. Any real site has the secret set, so this never applies there.
- Flag: dev only
