## What was built

### `dashboard/src/ccsync_dashboard/subject_data.py` (new)

- `collect(conn, username, *, session_store=None, dashboard_version="")`
  returns `{generated_at, dashboard_version, subject, tables, not_included}`.
  - The dashboard database comes from G0's `db.fetch_subject_rows`, with the
    secret columns already dropped.
  - Sessions come from `SessionStore.subject_rows(username)` (G2a).
  - YouTube data comes from `ytdl.subject_rows(username)` (G4).
  - `client_shares.db` (`client_folders.created_by`,
    `client_folder_items.added_by`) is opened **read-only**, and so are the
    `ingest_batches` tables of `broll.db` and `music.db`
    (`editor`, `cancel_by`). The paths come from the mounted apps' own config,
    found through `sys.modules` only, as `alerts._broll_paths` does.
  - `tables` is flat. Dashboard tables use their own names; the other stores
    use `<store>.<table>` (for example `sessions.auth_sessions`, `ytdl.jobs`,
    `client_shares.client_folders`).
  - Columns called `token`, `token_hash`, `sid`, `sid_hash`, `password_hash`
    or `secret` are left out of the other stores' rows. A client folder's
    `token` is the credential for its public link.
  - `not_included` has the six sentences the plan lists (8.2). It also gets
    one sentence for each store that is not mounted, cannot be read, or whose
    helper is missing in this build. "Nothing" and "could not look" always
    read differently.
- `forget_shares(username, stand_in=None, *, conn=None, path=None)`
  pseudonymises `created_by` and `added_by` in `client_shares.db`. It does not
  touch the token, so the links keep working. It never raises and returns
  `{"ok", "client_folders", "client_folder_items"}` or `{"ok": False,
  "reason"}`.
- `counts(export)` and `to_json_bytes(export)`. BLOBs are written as base64.

### `dashboard/src/ccsync_dashboard/subject_data_api.py` (new)

- `POST /api/v1/admin/users/{username}/export` (admin only) and
  `POST /api/v1/me/export`.
  - `/me/export` takes the subject from `auth.get_session_user`, never from
    `Scope` or `?as=`.
  - A bad name gets 400. A person the dashboard knows nothing about gets 404
    (not an account and no `machines` row).
  - One export at a time per person, and at most 5 per person per hour. Both
    limits return 429 with `Retry-After`, and are held in memory on
    `app.state`.
  - The file is built in memory. Over 50 MB (`MAX_EXPORT_BYTES`) the route
    returns 413, and no audit row is written.
  - The response is
    `Content-Disposition: attachment; filename="ccsync-data-<user>-<date>.json"`
    with `Cache-Control: no-store`.
  - Each export writes a `user.export` audit row holding the per-table
    counts, the total rows and the byte size only.
- `POST /api/v1/admin/users/{username}/erase-history` (admin only).
  - It calls `db.purge_subject_history` and commits, **then**
    `SessionStore.purge_user(username, revoked_only=True)`, **then**
    `ytdl.forget_history(username)`, **then** writes the `user.erase_history`
    audit row: the counts from every store, plus `not_done`. Then it commits.
- `POST /partials/admin/users/erase-history` is the Users panel's twin. It
  re-renders `admin_users.html` with the result as its notice or error line,
  the same way `account_ui.partial_admin_user_display_name` does.
- None of these routes is CSRF-exempt. GET returns 405.

### `app.py`

One `from . import subject_data_api` and one `include_router` line, before
`ui.router`, beside the /account routers.

### Templates

- `partials/admin_users.html`: a `subject_buttons(name)` macro gives
  `[ EXPORT DATA ]` and `[ ERASE HISTORY ]`. It is used on local-account rows,
  NAS editor-account rows and "editors without an account" rows.
  - EXPORT is a plain `method="post"` form carrying the hidden `csrf` field,
    because a download cannot come back through htmx.
  - ERASE's `hx-confirm` is the plan's sentence: "This removes their past
    activity. Their computers keep reporting their current state unless you
    switch reporting off for them."
- `partials/account_you.html`: a "your data" row with `[ DOWNLOAD ]` and
  "Download everything the dashboard holds about you" (plain form, CSRF
  field).

## Departures from the plan, and why

1. **`forget_shares` takes a stand-in or the connection.** The plan's
   contract is `forget_shares(username)`, but the stand-in is an HMAC keyed on
   `meta['pseudonym_salt']`, which lives in the dashboard database. So the
   function needs either the stand-in or a connection to mint it from.
   Without either, it logs a warning and returns `{"ok": False}` rather than
   raising: a delete must finish. See hand-off 1.
2. **Triage run ids are not exported.** G0 found that no triage table can be
   tied to a username (G0 departure 1: `triage_replies.from_addr` is a site
   mailbox). The export instead names triage report bodies under
   `not_included`, as the plan says.
3. **The export and erase limits are keyed on the subject, not the admin.**
   The plan says "per user". Keying on the subject bounds how often one
   person's whole history is read, however many admins ask. An admin
   exporting several different people is not blocked.
4. **A 404 for a person the dashboard knows nothing about.** Without it, a
   typo would produce a valid-looking empty export, and an audit row about a
   person who never existed.
5. **Other groups' helpers are called through `getattr`.** Wave 1 builds
   them in parallel. When a helper is absent or raises, the export says so in
   `not_included`, and erase lists that store in `not_done` and in the panel
   notice ("Some stores could not be reached"). G2a's `subject_rows` and
   `purge_user` were already in the tree and match what this code expects
   (table -> rows, and table -> count). G4's dashboard-level
   `ytdl.subject_rows` and `ytdl.forget_history` were not yet in
   `dashboard/src/ccsync_dashboard/ytdl.py` when this was built.

## Review round (adversarial reviewer, 2026-09-25)

Each point was checked against the code (and G4's real helpers in
`dashboard/src/ccsync_dashboard/ytdl.py`) before any change. Files touched:
`subject_data.py`, `subject_data_api.py`, `tests/test_subject_data.py` only.

1. **Fixed.** `_ask` now unwraps G4's `{"status", "detail", "tables"}`
   envelope (`_is_envelope`). `ok` merges `tables`. `absent` or `error` puts
   the helper's own `detail` into `not_included`, so it no longer says
   "could not be read just now" on every export. The session store's bare
   table -> rows shape still works.
2. **Fixed.** `erase_history` reads G4's `{"status", "detail", "counts"}`.
   `error` adds `ytdl` to `not_done` and puts the detail in the log only,
   never in the audit row. `ok` and `absent` merge `counts`. `ytdl.detail: 0`
   no longer appears, and the real counts reach the audit row.
3. **Fixed on my side, hand-off owed.** `forget_shares` now raises
   `ForgetSharesFailed` when the name would stay: no stand-in and no
   connection, or the store could not be opened or written. G2a's `except`
   then records a warning. It still returns `{"ok": False}` when there is
   nothing to do (no client_shares.db on this dashboard).
4. **Real, outside my files: hand-off.** `created_by` is rewritten to the
   stand-in, as the plan says. What the public expired-link page shows is
   decided in `broll/web/app/client_folders.py`.
   - The free-text `contact`, `description` and item notes are the studio's
     words, and I do not rewrite them. `forget_shares`'s docstring now says
     so.
5. **Fixed.** An autouse fixture stubs `ytdl.subject_rows` and
   `ytdl.forget_history` with G4's real envelope, so no test opens
   `ytdl/web/data/ytdl.db`.
6. **Fixed.** `_known` also counts anyone about whom
   `db.fetch_subject_rows` or the session store's `subject_rows` returns a
   row. A 404 now means exactly "holds nothing". The NAS listing is not
   consulted: it would put a NAS round trip on every export. A NAS account
   with no rows anywhere really does have nothing here.
7. **Fixed.**
   - A stamp is added only after the file is built and audited
     (`_ExportGate.done`), so a 413 or a 500 no longer counts.
   - Stamps are bucketed by (subject, self or admin). Admins' exports cannot
     use up `/me/export`, and the cap still holds across admins.
   - `/me` gets its own 413 sentence (`EXPORT_TOO_LARGE_SELF`, "Ask an
     admin").
   - A refusal from a plain-form post (a 404, 413 or 429 with a
     form content type) is a small HTML page. It has the same status, the
     same sentence and a link back to `/account` or `/admin/users`. JSON
     callers still get JSON. 401 and 403 are re-raised unchanged.
8. **Fixed, partly by design.** `to_json_bytes(export, max_bytes=)` encodes
   through `JSONEncoder.iterencode` and raises `ExportTooLarge` once the
   output passes the cap, so the oversized string is never built.
   - The rows are still read whole by `collect`: G0's `fetch_subject_rows`
     returns lists. A row-level early stop would need a streaming registry
     read, which is G0's code.
   - `indent=1` is kept, because the file is meant to be readable.
9. **Fixed in my file.** `forget_shares(conn=...)` commits the salt write
   itself when `conn` had no transaction open before the call. A caller
   already in a transaction must commit it, and the docstring says so.
   Committing the salt inside `db.pseudonym_salt` is still worth doing for
   `ytdl.forget_requester` too (G0 hand-off below).
