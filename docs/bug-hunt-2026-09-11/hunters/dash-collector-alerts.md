### dash-collector-alerts-1 - CR-232 mails "this has cleared. No action is needed" about footage nobody has touched
- Severity: high
- Confidence: CONFIRMED
- Where: `dashboard/src/ccsync_dashboard/alerts.py:1783` (`_check_out_of_tree`, the `if project and not slug: continue`), with `dashboard/src/ccsync_dashboard/alerts.py:3728-3768` (`deliver`'s RECOVERED loop)
- What: 40f931a made `out_of_tree` return **no finding** for a machine whose currently-open Resolve project is not one of the tree's. But the alert ledger is keyed `(kind, subject)` and the subject is still `editor/machine`, so a subject that stops appearing in a scan is declared RECOVERED by `deliver` and a "cleared" message goes out. `_f`'s own docstring names this exact trap ("a subject that leaves the scan is declared RECOVERED, and 'this has cleared, no action is needed' ... is a worse lie than the daily mail") and offers `repeat=False` for it; the CR-232 change used `continue` instead.
- Failure scenario: ruskin's machine has 40 clips outside the tree in `Ruskin Pangolins` (a synced project) and the owner is alerted. Ruskin then opens `Wedding Video For Mum`. The next report re-latches `resolve_out_of_tree=40` (his own project has out-of-tree clips too) and sets `machine_state.resolve_project` to the personal name. The scan skips him, `deliver` sends "CC Sync: cleared - footage is outside the tree - ruskin/DESKTOP-LQQ41TC / This has cleared on its own or somebody fixed it. No action is needed." The 40 clips in the tree project are untouched, the ledger now says the condition is closed, and the same false recovery repeats every time he switches back and away. The weekly report also prints `ok - clips referenced from outside the tree` for that week.
- Evidence: reproduced against a real app + report ingest (scratchpad `t_cr232.py`): report `Ruskin Pangolins` -> `alerts.run_cycle` -> `_is_open("out_of_tree","jsmith/EDIT-PC")` is True; report `Wedding Video For Mum` -> second `run_cycle` returns `{'sent': 0, ..., 'recovered': 1, ...}`. `assert r2["recovered"] == 0` fails with `assert 1 == 0`. The existing CR-232 tests (`dashboard/tests/test_alerts.py:1650`) only assert `_out_of_tree(findings) == []` - they never call `deliver`, so the suite cannot catch this.
- Ledger: related to CR-232 (recorded FIXED 2026-09-10; this is the half the fix introduced)
- Suggested fix: do not drop the finding; emit it with `repeat=False` and a diagnosis saying the open project is not one this fleet syncs, or suppress it only for a subject that has never been raised. Either way the subject must stay in `seen` so no recovery is declared.

### dash-collector-alerts-2 - `sink_deliverable` calls a channel that has NEVER delivered anything "delivered something 3 hour(s) ago"
- Severity: high
- Confidence: CONFIRMED
- Where: `dashboard/src/ccsync_dashboard/alerts.py:581-584` (the `ok = 1` probe) against `dashboard/src/ccsync_dashboard/alerts.py:3869-3872` (`run_cycle` recording the no-sink weekly with `ok=True`)
- What: on a site with no sink, `run_cycle` deliberately records the weekly report in `alert_log` as `ok=1, detail="generated, not sent (no sink configured)"`. `sink_deliverable`'s "has anything actually been delivered" probe is `SELECT at FROM alert_log WHERE ok = 1` with **no** detail filter, while its failure probe *does* exclude `NO_SINK_DETAIL`. So the moment an admin configures SMTP or a webhook, the most recent `ok=1` row is that never-sent weekly and the helper answers `True`. It is the single shared answer for invariant 15 (`alerts_deliverable`), the protection panel's `alerts_sink` line and the Alerts page, so all three go green on an unproven channel.
- Failure scenario: a customer runs the vendor default (no sink) for a month; a Monday weekly is recorded ok=1 / "generated, not sent". The admin then types an SMTP host with a typo. Invariant 15 renders PROTECTED - "the smtp channel delivered something 3 hour(s) ago", the protection panel renders PROTECTED, and nothing tries a real send until the following Monday. This is the one check whose whole purpose is to prove the alarm can reach a person, and on a healthy fleet the weekly is the only thing ever sent, so the false green can stand for a week (and up to 30 days if the next weekly attempt is also missed).
- Evidence: scratchpad `t_sink.py` against a migrated DB - record the no-sink weekly, then `alerts.set_settings(..., alerts_sink="smtp", ...)`; `alerts.sink_deliverable(conn, LATER)` returns `(True, 'the smtp channel delivered something 3 hour(s) ago')`. The assertion `ok is False` fails.
- Ledger: new (DDIAG-16 / SYS-1 built this helper; the asymmetry is untested)
- Suggested fix: exclude the generated-not-sent rows from the `ok=1` probe the same way the `ok=0` probe excludes `NO_SINK_DETAIL` - record that weekly with an empty `sent_to` and add `AND sent_to <> ''` (or a `detail NOT LIKE 'generated, not sent%'`) to the `ok=1` query. Add a test for "sink configured after a no-sink weekly".

### dash-collector-alerts-3 - a collector that dies straight after a FAILED cycle is never "stale"; on a Syncthing-less deployment it can never be stale at all
- Severity: high
- Confidence: CONFIRMED
- Where: `dashboard/src/ccsync_dashboard/db.py:8596-8604` (`fetch_collector_status`), consumed by `dashboard/src/ccsync_dashboard/db.py:3808-3813` (`collector_health`) and `dashboard/src/ccsync_dashboard/alerts.py:1518` (`_check_collector_stale`)
- What: `stale` is only ever computed inside `if reachable and latest["finished_at"]`. `reachable` is `bool(latest["ok"])` of the newest non-Syncthing-free poll run. So if the last thing the collector managed was a **failed** cycle, `reachable` is False and `collector_stale` stays False permanently - the liveness question is never asked. Same when `latest is None`: a deployment with no `syncthing_url` only ever runs prune/invariants/alerts, so there is never a non-free poll run, `collector_stale` is False for ever and `syncthing_reachable` is False for ever.
- Failure scenario: the enforce cycle fails (Syncthing refuses, the NAS mount goes away), then the collector thread wedges or dies in a way `CollectorWatchdog` cannot recover (the watchdog disabled with `DASH_COLLECTOR_WATCHDOG_SECONDS=0`, or past its restart budget). Hours later the home page's "the server's collector has stopped" check is silent and the only alert is `nas_engine_down`, which sends the operator to check Syncthing on the NAS rather than to restart the container. The second shape is worse for a Syncthing-less site: `_check_nas_engine` raises `nas_engine_down` (an ERROR kind, re-mailed daily) for ever on a deployment that has no Syncthing by design, while `collector_stale` can never fire.
- Evidence: scratchpad `t_stale.py` - one `record_poll_run(conn, "enforce", OLD, OLD, False, ...)` six hours before `now`, then `fetch_collector_status(conn, now=NOW)` returns `syncthing_reachable=False, collector_stale=False`. `assert st["collector_stale"] is True` fails.
- Ledger: new
- Suggested fix: compute staleness from `MAX(finished_at)` over all poll runs (or over the kinds this deployment actually runs) independently of `ok`, and keep `reachable` as it is. Gate `_check_nas_engine` on `settings.syncthing_url` being set, so a Syncthing-less site gets silence rather than a permanent error.

### dash-collector-alerts-4 - `MAX_FINDINGS_PER_KIND` truncation silently turns into "recovered", and drops the overflow with no trace
- Severity: medium
- Confidence: CONFIRMED
- Where: `dashboard/src/ccsync_dashboard/alerts.py:2955` (`for finding in results[:MAX_FINDINGS_PER_KIND]`), with `dashboard/src/ccsync_dashboard/alerts.py:3734-3737` (`deliver`'s recovery loop)
- What: `scan` caps each kind at 40 findings with no marker, and `deliver` treats "not in this scan" as recovered. Any kind whose finding set both exceeds 40 and reorders between passes oscillates: subjects that fall out of the top 40 are mailed as cleared and re-raised next pass. `_check_notices` is the readiest trigger - it is `ORDER BY last_seen DESC LIMIT 40` over open error notices and `last_seen` is re-stamped every pass, so the ordering among ties is whatever SQLite returns. The invariant ledger has the same shape one layer down: `invariants.broken()` truncates to `INVARIANT_MAX_SUBJECTS = 20` and `run_cycle` then passes only those 20 to `db.clear_notices_of_kind`, so subject 21 onward has its `invariant_broken` notice CLOSED while the invariant is still broken on it.
- Failure scenario: a fleet with 45 machines gone quiet (a tailnet outage), or 45 open error notices. Every alerts cycle a handful of real problems are mailed as "cleared - no action is needed" and re-raised the next morning, and the ones permanently past the cap are invisible on the Alerts page and counted in the weekly report's "checked and found nothing wrong".
- Evidence: scratchpad `t_cap.py` calls `alerts.deliver` twice with 40 of 45 `machine_silent` findings, the second pass keeping a different 40; `result["recovered"] == 1`, so the assertion `recovered == 0` fails. The truncation itself is a plain read of `alerts.py:2955`; the clear-past-the-cap in invariants is `invariants.py:139` (`rows[:MAX_SUBJECTS]`) feeding `invariants.py:1221` (`clear_notices_of_kind(conn, "invariant_broken", broken_subjects)`).
- Ledger: new
- Suggested fix: when a kind overflows, emit a synthetic "and N more of the same on this fleet" finding, and make `deliver`'s recovery loop skip any kind that was truncated this pass - a capped kind has said nothing about the subjects it could not carry. Same for `invariants.run_cycle`: keep the stored subjects of a truncated verdict in `broken_subjects`.

### dash-collector-alerts-5 - `restore_into_quarantine` discards the walk-truncation flag the preview reports
- Severity: medium
- Confidence: CONFIRMED
- Where: `dashboard/src/ccsync_dashboard/recovery.py:369-370` (`snap_files, _cut = _walk(source)` / `live_files, _cut2 = _walk(live)`), against `dashboard/src/ccsync_dashboard/recovery.py:301-302` and `recovery.py:322` where `preview_restore` returns `"truncated"`
- What: `_walk` stops at `MAX_SCAN_FILES = 50_000` and reports that it did; the preview surfaces the flag, the restore throws it away. The function's own docstring says "a restore that silently stopped at row 300 would be the worst possible kind of half-recovery, one that looks complete" - and it then stops silently at row 50,000. Worse, when the live walk is the one truncated, every file it never reached is classified as missing from the live tree and re-copied into the quarantine directory, inflating the restore by up to the whole project.
- Failure scenario: an owner restores a project folder holding more than 50,000 files (a long-form doc tree with proxies and stills is this order). The result page says ok, names a file count and a directory, and the operator believes the lost material is back. It is not, and nothing in `result`, the audit row or the `_remember` history says the walk was cut short.
- Evidence: read of `recovery.py:259-283` (`_walk` returns `(found, truncated)` and returns early at the cap) and `recovery.py:369-370` (both flags bound to `_cut`/`_cut2` and never used again); `preview_restore` at `recovery.py:322` proves the flag exists and is meaningful.
- Ledger: new
- Suggested fix: refuse with a 409 when either walk is truncated, telling the operator to use the printed commands, or at minimum carry `"truncated": True` into `result`, the audit entry and the history so the page can say the restore is partial.

### dash-collector-alerts-6 - the "unhandled error" notice files the raw request PATH as its subject, unbounded and un-pruned
- Severity: medium
- Confidence: PLAUSIBLE
- Where: `dashboard/src/ccsync_dashboard/notices.py:948-972` (`record_server_error`, `subject = f"{path} ({type(exc).__name__})"`), called from `dashboard/src/ccsync_dashboard/app.py:1289`; `db.prune` (`dashboard/src/ccsync_dashboard/db.py:7876`) has no `DELETE FROM notices`
- What: the notice subject and body are built from `request.url.path` verbatim. `notices` is upserted on `(kind, subject)`, so the row count is bounded by the number of distinct paths that 500 - unbounded for any route with a path parameter. There is no retention on `notices` at all, so cleared rows and one-off `server_error` rows accumulate for the life of the deployment. A sharper concern: this product routes credentials in PATH segments (`/broll/share/<128-bit token>/...`); if such a request reaches this handler the credential is written to a table that is rendered on the home page, quoted into an `error`-severity alert by `_check_notices`, and travels in every database backup. `/broll/share` is served by a mounted sub-app that very likely handles its own 500s, which is why this is PLAUSIBLE - I did not prove whether a mounted sub-app's exception reaches the parent handler.
- Failure scenario: a client-preview link with a malformed token trips an exception inside the share routes; the token lands in `notices.subject`, on PROBLEMS THE SERVER FOUND, and in the next alert mail. Separately and independently: a polling page that 500s on `/api/v1/jobs/{id}/why` writes one permanent notice row per job id.
- Evidence: `app.py:1289` passes `request.url.path`; `record_server_error` interpolates it into both subject and body; `grep -n "DELETE FROM notices" db.py` returns nothing.
- Ledger: new
- Suggested fix: normalise the subject to the matched ROUTE template (`request.scope["route"].path`, falling back to the first two path segments) rather than the concrete path, and add a `notices` retention clause to `db.prune` for rows whose `cleared_at` is older than the audit window.

### dash-collector-alerts-7 - `_check_weekly_send` reads a 200-row window, so a failing alert channel silently "recovers"
- Severity: low
- Confidence: PLAUSIBLE
- Where: `dashboard/src/ccsync_dashboard/alerts.py:2000-2003` (`weekly = [r for r in db.fetch_alerts(ctx.conn, limit=200) if r.get("kind") == KIND_WEEKLY]`)
- What: this is the same cliff `bug-hunt-2026-09-03 dash-collector-4` fixed for `_open_subjects` (which now groups over the whole table), left in place here. `fetch_alerts` is capped at 500 by `db.py:6312` and ordered by id; once a week's other alert rows push the weekly row out of the 200-row window, the check returns `[]`, the subject leaves the scan, and `deliver` mails "cleared - the weekly report could not be sent" about a channel that is still broken.
- Failure scenario: a fleet with ~30 open conditions in digest mode writes one `alert_log` row per finding per cycle; 200 rows is then a few hours. The SMTP relay starts refusing on Monday, `weekly_send_failed` is raised, and by Monday afternoon it has been declared recovered - on the one check that tells you the alarm channel itself is dead.
- Evidence: read of `alerts.py:2000` and `db.py:6302-6313`; the docstring of `_open_subjects` (`alerts.py:3813-3824`) describes the identical defect and its fix, which was not applied here.
- Ledger: continuation of bug-hunt-2026-09-03 dash-collector-4 (recorded fixed for `_open_subjects` only)
- Suggested fix: query `alert_log` for `kind=KIND_WEEKLY` directly (`ORDER BY id DESC LIMIT 1`) rather than filtering a recency window.

### dash-collector-alerts-8 - `_check_feature_mounts` clears its notices for a mount that never recorded a verdict
- Severity: low
- Confidence: CONFIRMED
- Where: `dashboard/src/ccsync_dashboard/notices.py:670-694`, against `dashboard/src/ccsync_dashboard/mount_status.py:37-40` (`NAMES`)
- What: the check walks only the entries `mount_status.snapshot()` actually holds, then calls `clear_notices_of_kind(conn, "feature_not_mounted", open_names)`. A mount that is in `NAMES` but has no recorded verdict is neither reported nor kept - it is silently cleared. `mount_status.NAMES` exists precisely so "not mounted" can be told from "never recorded" (its own docstring says so) and this, its only reader, ignores it.
- Failure scenario: any boot path that stops recording one of the four (a future flag short-circuiting before `_record_mount`, a `mount_status.reset()` from a second `create_app` racing a collector cycle) leaves the topbar link missing with a previously-open `feature_not_mounted` notice quietly closed - the exact "the page vanished and nothing anywhere says why" this work package was written for.
- Evidence: read of the loop; `snapshot()` is a plain copy of `_STATE`, `NAMES` is never consulted, and `app.py:1439` is the only writer and it sits inside a bare `try`.
- Ledger: new
- Suggested fix: iterate `mount_status.NAMES`, treat a missing entry as "this server did not record a verdict for the X page - treat it as unchecked", and only clear notices for names that positively reported `mounted`.
