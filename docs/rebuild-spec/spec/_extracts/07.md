# Extract of inventory section 07

## Items

### 07-001: An editor sends a found b-roll clip, or just a range of it, from the b-roll page straight into the timeline open in Resolve on their own computer.
- Where: broll / Sending a clip to Resolve
- What: On the b-roll search page in the editor's own browser, the editor marks an in point and an out point on a clip and sends it to Resolve on the computer they are sitting at. Two placements are offered: at the end of the open timeline, or at the playhead. The clip is imported into Resolve's media pool and the chosen range placed on the timeline. The page is served by the server, so only the editor's own browser on that computer can reach that computer's Resolve: the page names the clip by its place in the archive, never by a path on any computer, and the app on the editor's computer works out where that clip lives there. What the editor is told:
  - an out point not after the in point: "out point must be after in point";
  - a placement this computer does not know (an older app): "unknown insert mode '<mode>' -- this companion may need an update";
  - Resolve's own refusals and the generic "the Resolve worker failed" when Resolve could not do it (the Resolve messages themselves are the ones in the Resolve section: no project, no timeline, Resolve did not answer).
  A Resolve that does not answer is given up on rather than left hanging the page.

### 07-002: The b-roll page can tell whether the app on this computer is present, which version it is, and whether Resolve is answering.
- Where: broll / Sending a clip to Resolve
- What: The page asks the app on the editor's computer for a quick self-test and learns: that it is the CC Sync app (not something else that happens to answer), its version, where the archive is on this computer, whether DaVinci Resolve answered (a Resolve that does not answer within 20 seconds counts as "no"), and the list of archive clips on this computer that are still being cut on their preview because the better editing copy could not be fetched (see 07-006).- Flag: undetermined: how the page shows these facts to the editor is outside this section.

### 07-003: A clip the editor sends to Resolve that is not on their computer yet is fetched on the spot, with progress, and then placed.
- Where: broll / Sending a clip to Resolve
- What: When the clip's file is not on this computer, the app downloads exactly that one file from the NAS to the place a full sync would have put it, and the page shows "syncing the clip to this computer: N%" (or without a percent when the size is not yet known), checking about every 1.5 seconds. As soon as the file is in place the same send carries on and the clip lands in Resolve; the editor does not press anything again. Pressing send again, or the page checking, joins the download already running rather than starting another. A download never leaves a half-written file under the clip's real name. A computer downloads at most two clips at once for an editor who is waiting; a third gets "not sent yet: this computer is already downloading as much as it will at once. This one starts as soon as a slot is free", and the page asks again by itself about every 1.5 seconds (nothing is queued on the computer). A failure reads "couldn't sync the clip from the NAS: <reason>", and the next send starts again from scratch. Quitting the app stops every such download ("cancelled -- the companion shut down").
- Flag: several ways in: the same one-file fetch serves b-roll clips, music tracks sent to Resolve, and YouTube originals the server downloaded ("pull this original to my computer").

### 07-004: Fetching a missing clip is refused, with the reason, when this computer cannot or must not receive it.
- Where: broll / Sending a clip to Resolve
- What: Automatic fetching happens only for the b-roll archive, only on a remote computer (never on the computer wired to the server, whose tree is the NAS itself), and only when the archive's location on this computer is the default one (an editor who points the archive at a folder of their own has switched automatic fetching off). Otherwise a missing file reads "file not found at <path> - is the share mounted?". Further refusals, each shown on the page:
  - this computer's sync settings are incomplete (no server named, no folder on the server, or no folder on this computer), each said in its own sentence naming which is missing, so the clip cannot be fetched;
  - the download tool cannot be used: "can't fetch the clip from the NAS -- <detail>";
  - the file would land outside this computer's tree: "that file is outside this computer's tree -- nothing was downloaded";
  - the tree is not there right now (an unplugged external drive, an unmounted macOS volume): "this computer's tree isn't mounted right now, so nothing can be downloaded into it -- reconnect the drive and try again". When the check cannot tell, the download goes ahead;
  - the download could not be started: "this computer could not start the download (<error>)".
- Flag: undetermined: a computer whose tree is the server's drive but which is not set as the wired computer is treated as wired when deciding what to place, yet can still start a download onto its own tree (see the Unsettled list).

### 07-005: The product decides on its own which copy of an archive clip lands in Resolve: the original, the preview, or the preview standing in for the original.
- Where: broll / Previews standing in for originals
- What: Every archive clip has a small browser preview (1080p) beside it, and an original that is judged too heavy to edit with also has a higher-quality editing copy. When the editor sends a clip, the product picks, in this order:
  1. The original is already on this computer: it is used. Nothing downloads.
  2. The server could not list the clip's folder, or this is the wired computer: the original is fetched.
  3. The archive has no original for this clip, or the editor sent the preview itself: the preview is fetched and used under its own name ("preview only").
  4. The original is light enough to edit with (or its weight is unknown and the server knows of no editing copy), or no preview exists: the original is fetched.
  5. The original is heavy and is in a format Resolve takes as an ordinary video file (MOV, MP4, M4V): the preview's picture is placed at the original's own name and place (a "stand-in"), so the clip in Resolve already points at where the original belongs, and the editing copy is fetched afterwards (07-006).
  6. The original is heavy and in any other format (camera raw such as Blackmagic RAW, RED or Canon Cinema RAW Light, or MXF, AVI, MKV, or no recognisable type): "preview only".
  Facts the server sends about the clip (which copies exist, whether the original is still uploading, its size and frame rate) guide the choice; anything wrong in them is ignored and never makes a send fail.
- Flag: undetermined: whether the editor is told, at the moment of sending, which of these they got (the page's own text is outside this section).

### 07-006: After a stand-in is placed, the product fetches the better editing copy in the background and attaches it in Resolve as the clip's proxy.
- Where: broll / Previews standing in for originals
- What: Once a stand-in has gone into Resolve, the editing copy is downloaded in the background, at most one at a time per computer and never making a waiting editor's clip wait, and then linked in Resolve as that clip's proxy, leaving the clip pointing at the original's place. If the editing copy has not arrived within an hour, it is given up ("the editing proxy did not finish downloading") and the clip keeps the preview. If the file arrived but Resolve could not take it (Resolve closed, another project open), the product tries again about every two minutes, up to 8 times; after that it stops until the editor sends that clip again, which starts the count afresh. A stand-in whose editing copy was given up is listed back to the page (07-002) "so the editor knows they are cutting on the preview, not the editing proxy". A clip whose editing copy is attached is never redone.
- Flag: undetermined: where the editor sees the given-up list; the inventory says the tray was meant to show it and that this is not built in this part.

### 07-007: The product remembers, on each computer, which archive files are really previews standing in for originals, and notices when the real original replaces one.
- Where: broll / Previews standing in for originals
- What: Each computer keeps a record of every stand-in it placed (which clip, which preview, which editing copy, the original's picture size, frame rate, length and start timecode, when placed, how big). It is written before the download starts, so a closed browser tab cannot leave an unrecorded stand-in, and removed again if the download is refused, fails or vanishes. A stand-in stops counting as one when a file of a different size is found in its place (the real original has arrived by sync); Resolve's clip then still carries the stand-in's picture size, which is how the relinking elsewhere knows to refresh it. When a download's result is unclear, the product reads the file's picture size: different from the original's means a stand-in landed; the same means the real original arrived (the record goes). A record whose file never appears within 6 hours is dropped. Records whose file has been gone for over 30 days are forgotten. Neither forgetting happens while the archive folder itself is missing, so an unplugged drive never wipes the record. Names are compared so that the same name spelt the macOS way and the Windows way, or in different letter case, is one file. A damaged record is treated as empty; clips placed before then will look like real originals.
- Flag: undetermined: a stand-in holds the preview's picture under the original's name, so a render made on that computer renders the preview. This is only written to the app's log; nobody is told.

### 07-008: The dashboard learns which archive clips each computer has stood a preview in for.
- Where: broll / Previews standing in for originals
- What: Each computer's regular report to the server lists the archive clips it has ever stood a preview in for, up to 200, each named once whatever its spelling. An empty list is sent as a positive "none here" rather than silence.
- Flag: undetermined: what the dashboard does with the list is outside this section.

### 07-009: An archive clip whose original is not on a remote computer is not counted as missing media in Resolve.
- Where: resolve-on-the-editors-computer / Missing clips, relinking and refreshing
- What: On a remote computer, an archive clip in Resolve whose original is offline is normal (only the clips sent to Resolve are fetched), so clips inside the b-roll archive, whether reached through this computer's tree or the server's drive, are left out of the count of missing media the editor is warned about.

### 07-010: Only the studio's own dashboard pages can make the app on an editor's computer do anything; everything else is refused.
- Where: whole-product / Safety in what the product does
- What: The app on the editor's computer answers only programs on the same computer, and only web pages served from the studio's dashboard address (as set on that computer or as the server last announced it, in either its plain or secure form). A page from any other site, a page with no origin, or a request that pretends to come from a different address name is refused. Reading (the self-test) works without a page; anything that changes something needs the dashboard page, or a program run by the computer's own user. Every refusal reads "this request was refused by the CC Sync companion" followed by advice to open the app's log, or to copy the app's diagnostics and send them to the admin; the reason itself is only in the log. If the dashboard address set on the computer does not match the address editors actually browse, every send to Resolve is refused this way: an admin or the editor fixes the address, or adds the extra address the dashboard is reached by (07-013). When the server announces a new address, the app follows it within about 30 seconds without a restart; a change made on the computer itself needs the app restarted.

### 07-011: A page can only name files inside the studio's libraries on this computer, never anything else on the disk.
- Where: whole-product / Safety in what the product does
- What: Every file a page asks about is named as a library (b-roll, music, projects, YouTube downloads) plus a place inside it. A name that climbs out of the library, starts from the disk's root or a drive letter, or follows a link out of it is refused with the reason. A library with no location on this computer reads "no mount configured for share '<library>'". Showing a file in the file manager never points the file manager at an application, installer package or similar macOS bundle.

### 07-012: Sending to Resolve can be switched off on a computer, and its absence never disturbs anything else.
- Where: editor-app / Settings, records and background work
- What: A setting on the computer turns the send-to-Resolve and library hand-off feature off (on by default). If another program already holds the way in that the feature needs, the feature is simply absent, the rest of the app (syncing above all) carries on, and the error is kept for the tray and the computer's report to the dashboard; it clears once the feature starts. The warning names the usual cause. Something unexpected inside a request is answered with "the companion failed to handle that request -- see its log"; a request is never left unanswered.
- Flag: undetermined: the usual cause the warning names is the retired standalone b-roll helper still running; a rebuild has no such helper.

### 07-013: Each computer keeps where each library lives on it, with sensible defaults, and a hand-written override.
- Where: editor-app / Settings, records and background work
- What: The b-roll archive defaults to "Assets/B-roll Archive" inside the computer's tree, music to "Assets/Music" and projects to "Projects". A person can set any library to another folder on that computer; doing so for the b-roll archive switches off fetching missing clips (07-004). On macOS a library with no location set is looked for as a mounted network volume of that name (or that name followed by -1 or -2). With no tree set there is no b-roll default. Changes are read when the app starts, so they need a restart. A plain-words explanation of these choices is written beside the settings the first time. A damaged settings file falls back to the defaults and never stops the app. Also settable on the computer: extra dashboard addresses to accept (none by default).
- Flag: undetermined: who is expected to edit these (the inventory describes a file on the computer, not a screen).

### 07-014: A developer can let any page on the same computer drive the app.
- Where: whole-product / Safety in what the product does
- What: A setting, off by default, accepts any page served from the computer itself on any port, so a developer can drive the app from a page they run locally.
- Flag: dev only

### 07-015: The YouTube page can stop the downloads this computer is running, and follow their progress.
- Where: youtube / Where a download runs, and saying so
- What: Through the app on the editor's computer, the YouTube page can ask whether this computer can download from YouTube itself, start a download the server defined (what to fetch, quality and destination all come from the server), follow this computer's downloads (all or one job), show a downloaded file in the folder, pull a server-downloaded original to this computer (07-003), and stop this computer's downloads (one job or all). Stopping answers "Stopped. The server will download the clips this computer did not finish." or "There was no download running on this computer." Quitting the app stops any YouTube download it was running.
- Flag: undetermined: what each of these does in detail is outside this section.

### 07-016: An editor brings new footage into the b-roll archive by dropping it on the b-roll page or picking it on their own computer, and their own computer does the work.
- Where: broll / Bringing new footage in
- What: The editor drops video files onto the b-roll page, or presses "choose from this computer", which opens the computer's own file or folder picker. Dropped files are copied into a holding folder on this computer; picked files are worked on where they are, never copied. Each file is then checked and fingerprinted so the server can say which are already in the archive. The page creates a batch on the server and hands it to this computer, which makes the previews and stills, describes every clip, uploads everything to the archive on the NAS, and the server makes each clip live. The same way in exists for music tracks (07-040). A folder picked is searched for the kinds of video accepted. A thumbnail is made on the computer for any clip the browser cannot show itself (10-bit footage, MXF), so every dropped clip has a picture in the drop grid.

### 07-017: Only these video kinds are accepted for the archive, and camera raw is not.
- Where: broll / Bringing new footage in
- What: Accepted: MP4, MOV, M4V, MXF, MTS and M2TS (AVCHD), AVI, MKV and WebM. Camera raw (Blackmagic RAW, RED, Canon Cinema RAW Light) is not accepted, because it cannot be decoded without Resolve. A file of another kind is refused on its own line ("<kind> is not a video this machine can index") while the rest of the drop goes ahead.

### 07-018: A drop is refused or trimmed, with the reason, when it is too big, has nowhere to go, or names files the editor did not pick.
- Where: broll / Bringing new footage in
- What: Refusals of the whole drop:
  - nothing offered: "no clips were offered";
  - more than 2,000 clips (music: 500 tracks): "that is N clips; 2000 is the most one batch can hold";
  - this computer has no synced tree: "this computer has no synced tree, so there is nowhere to stage the clips";
  - not enough room (07-033);
  - the holding folder cannot be made: "the companion could not create its staging folder -- <reason>".
  Refusals of single files (the rest still goes ahead): a kind not accepted; "no path was given for that clip"; "that file is not on this computer"; "that file could not be read"; "that is not a video this machine can index"; and "that file was not chosen on this computer: use the "choose from this computer" picker and pick it again". A page can only have files worked on in place if they lie inside a folder the editor actually chose in the computer's own picker; the last 32 chosen folders are remembered, across a restart of the app. The picker waits up to five minutes; closing it reads "cancelled"; it reports itself busy when another of the app's windows is open; any other failure reads "the file picker could not be opened on this computer".

### 07-019: Dropped files are copied safely to the computer, and a page that reconnects never sends a big file twice.
- Where: broll / Bringing new footage in
- What: A dropped file only takes its real name in the holding folder once every byte has arrived; a broken copy is deleted. A file already fully copied answers "that clip is already staged" and the page treats it as done. Messages: not enough room for this one file: "not enough space to stage this clip: it needs X GB and only Y GB is free (the floor is Z GB) -- free some space and drop it again"; the page sends more than it said: "this upload sent more than it declared -- nothing was kept"; the page stops mid-file: "the upload stopped before the whole file arrived"; the disk refuses: "the companion could not write the clip to its staging folder -- <reason>". Each file shows waiting, ready or failed ("the file is not there", "this file could not be read (<error>)"). Failed files can be retried, one, several or all; retrying re-checks picked files and clears a broken copy; retrying something not failed does nothing harmful.

### 07-020: Before a drop is indexed, the editor can see whether this computer can index at all, and why not.
- Where: broll / Describing and indexing clips
- What: The page asks the computer whether it can index, and is told yes, or every reason why not, in these words:
  - the computer's graphics hardware cannot run the description (or the specific reason, see 07-028);
  - the video tool the app needs is not on this computer yet and is fetched the first time a batch runs;
  - the tool that uploads to the NAS is not on this computer, "so indexed clips could not be uploaded to the NAS";
  - "this computer has no synced tree, so there is nowhere to stage the clips";
  - "only X GB free where the clips would be staged (the floor is Y GB)";
  - "this computer is already indexing a b-roll batch";
  - "nobody is signed in on this computer";
  - "b-roll indexing is switched off on this computer".
  It also learns the computer's graphics hardware and memory, which quality levels fit, which is recommended, what is already downloaded and how much a download would be, free space where clips are kept, and whether a batch is running. The answer is quick.
- Flag: undetermined: the second and third reasons name, in today's words, tools the present build chose; a rebuild says what is missing in its own words.

### 07-021: A batch is handed to one computer at a time, and the editor is told why a computer will not take it.
- Where: broll / Bringing new footage in
- What: A computer runs one batch at a time and holds it while it works; while it holds it nobody else can. Refusals when the page hands a batch over: "this computer is already indexing another batch"; indexing switched off on this computer; "this computer has no dashboard URL or token configured"; "nobody is signed in on this computer"; "those clips are no longer staged on this computer - drop them again"; "this computer could not reach the dashboard to claim the batch"; the server's own refusal ("the dashboard would not hand over this batch" by default); the quality level does not fit this computer's graphics hardware (the reason, and the batch stays offered so another of the editor's computers can take it once this one's hold expires); and "this computer has those clips staged, but the request did not say which drop: reload the page and try again". If the computer goes quiet its hold expires; if the server takes the batch away the computer stops all work on it at once without a message and keeps the dropped files.

### 07-022: A batch runs either now or only while the editor is away from the computer.
- Where: broll / Describing and indexing clips
- What: The page chooses: "now" (work at once) or "while I'm away" (work only while the editor has been away from keyboard and mouse for at least 5 minutes by default, and, by default, only while Resolve is closed). "Start now" from the tray or the page switches a waiting batch to working at once until it ends or is paused. The conditions are checked again between every step of every clip, so an editor coming back loses at most the step in progress, and the graphics memory used for describing is given back the moment work stops. When the computer cannot tell whether the editor is away, it counts them as present; when it cannot tell whether Resolve is open, it counts it as open.

### 07-023: The progress window and the page say exactly what a batch is waiting for.
- Where: broll / Describing and indexing clips
- What: The first reason that applies is shown, in this order:
  - switched off on this computer;
  - "waiting: the sync drive is not connected";
  - "paused" (by the editor, from the tray or page, or by the app's own pause);
  - "waiting: this computer's sync config needs fixing";
  - waiting for the video tool the app needs to be installed;
  - "fetching the local indexing model" (or the quality level does not fit, shown once as a warning);
  - nothing to do;
  - "waiting until you're away from the keyboard";
  - "waiting: DaVinci Resolve is open";
  - working.

### 07-024: While b-roll is being indexed, making proxies on that computer waits.
- Where: proxies-and-file-moves / Making proxies on editors' computers
- What: While a b-roll batch is working or downloading what it needs, this computer's proxy making stands aside and shows "indexing b-roll first". Music indexing never holds proxy making back.

### 07-025: A computer that is indexing stays awake and warns before shutting down.
- Where: editor-app / Starting, staying running and crashing
- What: While a batch is working or downloading what it needs, the computer is kept from sleeping and a shutdown is met with "still indexing <b-roll|music> (N <clip|track>(s) left)" or "still downloading the <kind> indexing model".

### 07-026: Each clip brought in gets a browser preview, an editing copy when it needs one, a poster, a hover strip and a description, and a bad result is never accepted.
- Where: broll / Previews made for the archive
- What: For each clip, in order:
  1. A 1080p browser preview that scrubs smoothly, carrying the source timecode. It is accepted only if it plays to at least 97% of the original's length and has exactly the original's number of frames, because Resolve refuses a proxy whose frame count differs. Otherwise the clip fails with "the proxy did not decode -- this clip was skipped" or "the proxy has N frames, the original has M - Resolve would refuse it".
  2. An editing copy, of the same kind as the project proxies the product makes, carrying the source timecode, only when the original is too heavy to edit with (an unknown weight counts as heavy). Camera raw never gets one here ("needs Resolve"); an original light enough gets none ("original is edit-weight"). If it cannot be made, the clip carries on without it.
  3. A poster frame taken 10% into the clip (640 pixels wide), a hover-scrub strip (one frame every 2 seconds, 240 pixels wide, up to 240 frames, spaced wider for longer clips) and a small thumbnail (160 pixels wide). A still that fails does not fail the clip.
  4. Frames for describing: one at every scene change, plus at the start if the first change is later than 4 seconds, and never more than 4 seconds apart, up to the end; a clip with no cuts still gets frames.
  5. The description (07-029).
  6. Upload (07-034).
  A step that runs too long fails (15 minutes for most steps, longer for long clips), for example a drive that went away or a file still being written. Each step is saved, so a restart resumes where it stopped.

### 07-027: A clip that cannot be done is tried twice and then left failed, and the rest of the batch carries on.
- Where: broll / Describing and indexing clips
- What: Each clip gets at most two tries. Messages a failed clip shows: "this clip could not be indexed: <error>"; "the source file is not on this computer any more"; after a restart, "the source file is no longer on this computer (the drive was unplugged, or it was moved)"; "the local model could not describe this clip (<error>)"; "the archive would not take this clip's description: <detail>" (the next try describes it again). The tray's status lists up to 20 failed clip names with their reasons.

### 07-028: Describing clips needs suitable graphics hardware on the computer, offers two quality levels, and says plainly when a computer cannot do it.
- Where: broll / Describing and indexing clips
- What: Describing never runs on the processor alone: a computer without suitable graphics hardware cannot index, and the batch can run on another computer instead. Two quality levels exist: Good (the default) and Best, which is "a little sharper on on-screen text and vocabulary" and about twice as slow, and needs more graphics memory. The product recommends the best level the computer can run. On Apple Silicon Macs the computer's shared memory is what counts. Refusals, shown on the page, as a tray notification and in the tray:
  - "Can't index b-roll: no usable GPU on this computer (<detail>). Indexing needs an NVIDIA GPU or Apple Silicon";
  - "Can't index b-roll: Best needs N GB VRAM, this GPU has M GB - choose Good" (Macs: "unified memory", "this Mac has");
  - "Can't index b-roll: Good needs N GB VRAM, this GPU has M GB - indexing needs a bigger GPU: this batch can run on another computer".
  The quality level used is recorded with each clip's description.
- Flag: undetermined: which hardware is "suitable", and the memory each level needs, follow from what describes the clips; today Good needs 8 GB of graphics memory (16 GB on Apple Silicon) at about 20 seconds a clip on a high-end gaming card, Best 12 GB (24 GB on Apple Silicon), and graphics cards that are not NVIDIA, and Intel Macs, cannot index.

### 07-029: Every clip is described shot by shot in searchable terms, with its on-screen text in the original script and in English.
- Where: broll / Describing and indexing clips
- What: The description of a clip is a list of shots plus themes:
  - A new shot starts whenever place, subject or camera set-up changes ("when in doubt, split"). Each shot's time runs from its first sampled frame to its last, so shot times are as precise as the sampling (07-026, at most 4 seconds apart). Neighbouring shots that are nearly the same (mostly the same objects and a closely matching description) are merged into one.
  - Each shot has a terse description: 8 to 20 words of nouns and noun phrases, no sentences, no "footage showing", keeping colour, time of day, camera position and counts. Shots with no searchable picture get exactly one label: newsreader (a studio anchor at a desk), title card, black frame, colour bars, station ident. Near spellings (news anchor, presenter, talking head, test pattern, titles, blank frame, channel ident and so on) are folded into these labels.
  - Each shot lists every visible object, most specific first and including the plain broader term (for example frigate, warship, navy ship), and names of people, places and organisations read from on-screen text, in both their original script and English.
  - Each shot carries burned-in text word for word in its original script (Chinese, Japanese and Korean never romanised): captions, lower thirds, channel names, dates, signs, banners, vehicle markings, name plates, stopping where the text becomes illegible and ignoring camera timecode, plus a short English rendering. It is transcribed even on newsreader and title shots.
  - Two to six theme tags summarise the clip (or each stretch of it).
  - Only what is visible is described: no narration, no story across frames, no guessed events or causes; uncertainty is hedged briefly ("possibly melons") or the look described instead. For example, red lights on vehicles are brake lights unless a light bar or livery shows; slow traffic is congestion, not an accident.
  - Description at most 220 characters, objects 300, each on-screen text 300, themes 160.

### 07-030: Each clip is flagged for poor exposure or focus from its pictures.
- Where: broll / Describing and indexing clips
- What: Measured from the clip's sampled frames: overexposed when at least 30% of frames are very bright on average or at least a quarter of their pixels are clipped white; underexposed when at least 30% of the frames that are not plain black are very dark; soft focus when the frames that are not black are, on the whole, blurred. The full set of quality flags a clip can carry is shaky, soft focus, overexposed, underexposed, noisy and rolling shutter; only the first three are worked out when describing on an editor's computer.

### 07-031: Each clip is filed under the studio's own category that fits it best, or none.
- Where: broll / Describing and indexing clips
- What: The product picks, from the list of categories the studio keeps on the server, the one whose name and description best match the clip's themes, descriptions and objects, in any language. When nothing fits well enough, no category is set.
- Flag: undetermined: the inventory could not tell whether the app as shipped matches by meaning across languages or only by shared words.

### 07-032: Indexing models are downloaded once, on demand, with their size announced, progress shown and the download resumable.
- Where: broll / Describing and indexing clips
- What: When a batch needs a quality level this computer does not yet have, the computer downloads it by itself, first showing a tray notification such as "Downloading the Good b-roll indexing model (3.9 GB). Right-click the tray icon to see progress." and afterwards "The b-roll indexing model is ready. Indexing starts now." The progress window shows "Downloading <name>: 61% at 38 MB/s, about 1 min left" (time phrases: "almost done", "about N sec left", "about N min left", "about Hh Mm left"). Nothing is downloaded for a level this computer cannot run. A download interrupted (even by quitting) resumes where it left off ("the download was stopped - it will resume where it left off"). Refusals and outcomes: not enough disk space: "Not enough disk space for the Good model: needs about X GB free at <folder>, has Y GB - free some space and try again" (a disk that cannot be measured is not a refusal); a download that fails its integrity check is deleted and fetched again ("the model download's checksum did not match. The file was deleted and will be fetched again"); any other failure: "the b-roll model could not be downloaded: <error>"; success: "<Good|Best> is ready". Downloads come only from a short fixed list of trusted sources, over a secure connection; anything else is refused. Today the levels are downloads of about 3.3 GB and 6.2 GB.
- Flag: undetermined: the inventory notes a promise of "never a surprise 3.9 GB download", but the computer starts the download as soon as a batch needs it with only a notification; any consent step would be on the page.

### 07-033: Dropped clips are only kept while there is room, and the editor is told exactly what is taking the space.
- Where: broll / Bringing new footage in
- What: The computer always keeps a floor of free space where dropped clips are held (20 GB by default; a setting on the computer). A drop that would eat into the floor is refused with "Not enough space where the clips would be staged (<folder>): X GB free, and this drop needs Y GB on top of the Z GB floor", followed by whichever applies: "N GB of that drive is finished b-roll staging: open Settings from the tray icon and use CLEAR FINISHED STAGING"; "N GB of that drive is b-roll staging that was never indexed: open the b-roll page and index or re-drop it, and it is cleared automatically after 7 days"; "Free some space and it will continue"; and "N GB more is b-roll staging kept on this computer because the archive does not have those files yet; it is released once they reach it". A disk that cannot be measured never refuses.
- Flag: differs: the computer checks free space at four moments with different rules (when the page asks whether it can index: the floor only; when a drop is offered: the floor plus the whole drop; when each file arrives: the floor plus that file; before a model download: the model plus room to unpack it), so a computer can say yes and then refuse.

### 07-034: Results go up to the archive one file at a time, cheapest first, so a clip is searchable before its original has finished uploading.
- Where: broll / Bringing new footage in
- What: For each clip the poster, hover strip, preview, editing copy (if made) and the original are uploaded to the archive on the NAS, one file at a time so it never crowds the computer's sync. A clip shows on the dashboard once its stills land, plays once its preview lands, and goes live on its previews while a large original is still uploading. Each file is checked on the NAS after upload; a file that arrived at the wrong size is sent again ("<file> arrived at N bytes, not M -- it will be sent again"). A file that fails is sent again up to 3 times, then the clip fails with the reason. If the NAS cannot be reached (sync settings incomplete), uploading waits and tries again every few seconds without counting a failure. The server must confirm it has every file; if it says some are missing they are sent again, up to 3 times, then "the archive never saw these files: <up to 3 names>". Other refusals: "the archive refused this clip (HTTP N)" at once, or "the archive would not take this clip (HTTP N)" after 3 tries. An upload interrupted part way restarts that file from the beginning. Whether originals are uploaded at all is a setting of the batch, on by default.
- Flag: undetermined: who sets whether originals are uploaded, and where (it arrives with the batch from the server).

### 07-035: Once a clip is live, its preview and editing copy are already in place on the computer that brought it in.
- Where: broll / Sending a clip to Resolve
- What: When the server confirms a clip is live, the computer that indexed it puts the preview and editing copy into its own copy of the archive, so sending that clip to Resolve from that computer needs no download. A file already there is left alone.

### 07-036: A live clip whose original never reached the archive stays usable, and the only copy of its original is kept.
- Where: broll / Bringing new footage in
- What: If a clip is already live on its previews and then its original fails to upload, the clip stays live and its dropped file is kept on the computer (never cleaned away) until a later retry gets the original up. At the end of the batch the server is told how many originals failed and up to 10 of their names. The warning that the original "has to be uploaded again" is otherwise only written to the app's log; whether anyone sees it depends on the server.

### 07-037: The editor can pause, resume, start now, cancel, and pause or resume uploads, from the page or the tray.
- Where: broll / Bringing new footage in
- What: The same actions from both places: pause (also ends "start now"), resume, start now (work at once and unpause), cancel, pause uploads, resume uploads. Pausing uploads lets the file in flight finish. Cancelling stops all work on the batch at once (a stuck step is forced to stop after 5 seconds), tells the server "cancelled on this computer", and keeps the dropped files for the usual keeping time. An admin or the editor can also cancel a batch, or pause and resume its uploads, from the dashboard; the computer follows within about 30 seconds ("cancelled from the dashboard").
- Flag: several ways in: the page in the browser, the tray, and the dashboard.

### 07-038: A progress window opens when a batch starts working and says what is happening.
- Where: editor-app / Windows, dialogs and notifications
- What: Opened once per batch when work starts; if the editor closes it, it stays closed. Title "INDEXING B-ROLL" or "INDEXING MUSIC". It shows the model download headline while downloading (07-032); the current clip, its step and percent; done, total and failed counts in clips or tracks; time remaining; and a note (the current warning, or what it is waiting for, 07-023; for music, "Waiting for the computer that is wired to the server: N tracks still on this computer."). Buttons: Cancel, Pause or Resume, and Start now (only while waiting for the editor to be away or for Resolve to close). It shows the batch as finished when every item is done, failed or left for the wired computer. Each new warning also appears once as a tray notification. The page in the browser shows the same progress, checking about every 1.5 seconds, including uploads (how many queued, done, failed, paused, and the current file's size, speed and time left).

### 07-039: A batch survives the app or the computer restarting.
- Where: broll / Bringing new footage in
- What: After a restart the computer picks up its batch where it stopped, asks the server to confirm it still holds it (trying again if the server cannot be reached), and re-sends any uploads that were under way. A file that has gone in the meantime fails with "the source file is no longer on this computer (the drive was unplugged, or it was moved)".

### 07-040: Music tracks are brought into the library the same way, on the editor's computer.
- Where: music / Adding tracks to the library
- What: Dropping or picking tracks works as for b-roll (07-016 to 07-039) with these differences: accepted kinds are WAV, MP3, FLAC, AAC, M4A, OGG, AIFF/AIF and Opus (OGG is converted on the computer before upload); at most 500 tracks a drop; at most 537 MB a file ("that track is N MB and the library takes at most 537 MB per file"); no graphics hardware needed and no quality level; the analysis needed is a download of about 280 MB; it never holds proxy making back. Its refusal sentences say "tracks" and "the library" ("so indexed tracks could not be uploaded to the library", "this computer is already indexing a music batch", "music indexing is switched off on this computer"). A track this computer could not analyse is left for the computer wired to the server, and the window says how many are waiting for it. Music has its own on/off switch on each computer.
- Flag: differs: the free-space floor for music is 2 GB when the page asks and when each file arrives, but 20 GB when the drop is offered, unless set on the computer.

### 07-041: Dropped files are cleaned away after a week, and an editor can clear finished ones at once.
- Where: broll / Bringing new footage in
- What: Files held for a finished batch are deleted 7 days after the batch ended (a setting on the computer; 0 means as soon as it ends). Files dropped but never indexed are deleted once they and the newest file among them are older than that. Never deleted: the batch being worked on, files left for the computer wired to the server, and originals the archive does not have yet. A control in the app's settings on the computer, CLEAR FINISHED STAGING, removes finished drops at once (never unindexed or held ones) and says how many were kept back. A folder that cannot be deleted yet (a file still open on Windows) is tried again shortly.

### 07-042: The dashboard sees each computer's indexing progress and how much space its held files take.
- Where: broll / Bringing new footage in
- What: Each computer's regular report to the server carries its batch's state, what it is waiting for, done, failed and total counts, the current clip's name and percent, the quality level, now or while-away, whether it is uploading or uploads are paused, the model download percent and any warning (nothing when there is no batch and no warning); and the space its held files take, how many drops, the oldest, split into finished, never indexed and held.
- Flag: undetermined: how the dashboard shows these is outside this section.

### 07-043: Settings on each computer for bringing footage in.
- Where: editor-app / Settings, records and background work
- What: Each computer has, separately for b-roll and for music: indexing on or off (on by default); how long the editor must be away before while-away work starts (5 minutes by default, following the computer's proxy-making setting); whether while-away work also waits for Resolve to close (on); the free-space floor (07-033, 07-040); where dropped files are held (inside the archive folder on the computer by default; meant to be moved on the wired computer, whose tree is the NAS); and how long finished drops are kept (7 days).
- Flag: undetermined: who may change these, and from where (the inventory describes settings held on the computer).
