## dash-release-jobs-1
- Verdict: CONFIRMED
- Duplicate of: none
- Reasoning: The hunter is right on both halves. `consume_restart_request` decides from `read_state(settings)`, which is `_read_json(update_state_path(...))` - a pure disk read with no in-memory fallback - so `request_restart`'s now-best-effort write is the ONLY carrier of the intent, and swallowing it loses the decision the fix exists to preserve. The second half is the stronger one: `apply` at :1471 and `rollback` at :1558 both call `_set_state(step="restarting", ...)` unguarded one line before `request_restart`, so on the same read-only or full `/data` the OSError escapes there, `start_apply._run`'s generic `except` routes it to `_fail_state` (best effort, silent), `_signal_restart()` never fires at all, and the process goes on serving the OLD code while `current.json` already names the new tree - CR-285S's own failure shape, moved one line earlier. One correction to the hunter's failure scenario for the `finish_restart` half: the dashboard service carries `restart: unless-stopped` in all three compose files, and docker restarts a container that exits 0, so that half is a reboot with an outage rather than "old code until a human restarts"; the :1471 half has no such safety net because the process never exits.
- Evidence: scratchpad script against the dashboard venv (`_write_json` -> `OSError(30)`, `_signal_restart`/`_exit_process` stubbed): `request_restart` printed the healer's warning, `calls == ['SIGTERM']`, `finish_restart -> False`, no `exit 75`, and the on-disk state still `step: idle, in_progress: False`. `dashboard/deploy/run.sh:520` exits with `rc` unless it is 75.
- Fix note: the hunter's fix is right and cheap - a module-level flag OR'd into `consume_restart_request`, plus `best_effort=True` on the two pre-`request_restart` `_set_state` calls. The in-memory flag must not be consulted across a re-exec; `PROCESS_NONCE` already exists for that. A fix should also add a case that drives `apply`/`rollback` with a writer that starts failing PART WAY (the hunter's coverage note is right that no existing case does), and `dashboard/tests/test_bug_hunt_2026_09_18_dashboard_mediums.py:460-477` is the test that currently passes on the half-fix - it asserts only that `_signal_restart` fired.

## dash-release-jobs-2
- Verdict: REFUTED
- Duplicate of: none
- Reasoning: The finding's premise - "editing `git_dirty` needs no key: only the ability to serve the feed's static JSON" - is false. `git_sha`/`git_dirty` are outside the per-RECORD Ed25519 signature, but `repair_provenance` is only ever called from `check_now` with `_valid_records(channel, ...)` of a channel returned by `fetch_and_verify_channel`, which fetches the detached `channel.json.sig` and runs `verify_channel_signature` over `canonical_channel_bytes(channel)` - `json.dumps` of the WHOLE parsed document, advisory fields included - against `DASH_RELEASE_PUBKEYS`, and never returns a channel that failed. Flipping `git_dirty` on any record therefore invalidates the channel signature and the whole poll is rejected with `channel signature invalid`. An attacker holding the offline release key does not need this write path. The narrower surviving worry (a locally published `-AllowDirty` row being cleared) additionally needs the vendor feed to carry a record with that build's exact sha256, or `sha_conflict` skips the row - and `publish_latest` only publishes green CI bytes, which are not the bytes `ship.cmd -AllowDirty` built.
- Evidence: `release_feed.py:121-159` (`canonical_channel_bytes` / `verify_channel_signature`), `:391-432` (`fetch_and_verify_channel`, "NEVER returns a channel that failed signature verification"), `:818-822` (the only `repair_provenance` call site), `:1187-1201` (`sha_conflict`). `grep` shows `repair_provenance` has exactly one caller.
- Fix note: no fix needed. If one is wanted anyway, the hunter's `published_by == FEED_PUBLISHER` gate is the wrong one and CR-285AA's own ledger entry says why: the Packages page's [ PUBLISH ] button stamps an admin username, so that gate would stop the repair working at all. The one-shot `meta` marker alternative would work but buys nothing over the channel signature. The same false premise sits in the CR-285AA ledger entry and in the code comment at `release_feed.py:765-783`; both overstate what a feed host can do, and that comment is worth correcting whether or not anything else changes.

## server-tools-3
- Verdict: CONFIRMED
- Duplicate of: none
- Reasoning: All three `subprocess.run` calls in `run_piplicenses` (`tools/gen_notices.py:160`, `:163-166`, `:170`) pass `text=True` with no `encoding`, so they decode by `locale.getpreferredencoding(False)` - cp1252 on this rig - while the same fix pass added `encoding="utf-8", errors="replace"` to `server/check_health.py` and the four bench runners, and while `gen_notices.py` itself was the most heavily edited file in the territory (+100 lines). `--with-license-file` pulls whole licence TEXTS through that pipe, which is the most likely place for a non-ASCII byte to arrive. The escape is real: `UnicodeDecodeError` is a `ValueError` but neither a `RuntimeError` nor a `json.JSONDecodeError`, so `collect()`'s `except (RuntimeError, json.JSONDecodeError)` at :196 does not catch it and it leaves `main()` as a traceback. The consequence is loud rather than silent (the notices file simply cannot be regenerated, and `gen_notices.py --check` is a CI step), which is why I would not rate it higher than medium, but it is a genuine latent break of the one document that must exist before a build is conveyed to a customer.
- Evidence: dashboard venv on this rig: `locale.getpreferredencoding(False)` -> `cp1252`; `'母'.encode('utf-8').decode('cp1252')` -> `UnicodeDecodeError: 'charmap' codec can't decode byte 0x8d`; `isinstance(exc, ValueError)` -> True, and `issubclass(json.JSONDecodeError, ValueError)` -> True. `git diff --stat` confirms check_health.py and the four bench runners got `encoding="utf-8", errors="replace"` in this same pass.
- Fix note: the suggested fix is right and self-contained. Widening the `except` to `ValueError` is the important half (it subsumes `json.JSONDecodeError`), and `errors="replace"` keeps a stray byte from failing the run at all. Nothing pins the current behaviour: `tools/tests/test_gen_notices.py` stubs at a higher level and does not assert the subprocess kwargs. Worth doing at the same time: `tools/publish_latest.py:82` has the identical unencoded `subprocess.run` over git output (the hunter's own out-of-territory note), and a test that greps `tools/*.py` for `text=True` without `encoding=` would keep this from being a hand-written list, the failure mode server-tools-4 reports for the bench half.
