# Extract of inventory section 12

## Items

### 12-001: An admin can stop all syncing on every computer at once, giving a reason every editor sees.
- Where: sync / Studio-wide stops and the editor's pause
- What: Only an admin may stop syncing studio-wide. A reason is required: at least 3 characters after trimming, up to 500. If it is shorter the admin is told "say why: the reason is shown in every editor's tray (at least 3 characters)" and nothing stops. The stop records the reason, who set it and when, and it ends by itself after a chosen number of hours: 24 by default, more than 0 and at most 720 (30 days). Each editor's computer learns of the stop, and of its release, the next time it checks in with the server, normally within about 30 seconds, and the reason is shown in every editor's tray. A stop is studio-wide only; there is no way here to stop one computer. A stop whose end time has passed reads as not stopped (and as having expired). If the stored stop cannot be read, the product treats syncing as not stopped.

### 12-002: An admin can keep a studio-wide stop going longer, and is told plainly when there is nothing to keep stopped.
- Where: sync / Studio-wide stops and the editor's pause
- What: While a stop is active, "keep it stopped" moves its end time to the chosen number of hours from now (24 by default, at most 720) and keeps the original reason, the person who set it and the start time; each extension is counted and shown. If no stop is active and no reason of at least 3 characters is given, the admin is refused with "Syncing already started again at <time in the studio's time zone>. To stop it again, give a reason." or, if nothing was ever stopped, "Nothing is stopped, so there is nothing to keep stopped. Stop syncing with a reason." Pressing it with a real reason after the stop expired starts a fresh stop.

### 12-003: An admin can start syncing again everywhere without giving a reason.
- Where: sync / Studio-wide stops and the editor's pause
- What: Releasing a studio-wide stop needs no reason. Every computer resumes on its next check-in with the server, normally within about 30 seconds.

### 12-004: Anyone signed in, and every editor's computer, can see whether syncing is stopped studio-wide; the last 20 stops are kept as history.
- Where: sync / Studio-wide stops and the editor's pause
- What: The current state shows whether syncing is stopped, whether a stop expired, the reason, who set it, when, when it ends, and how many times it was extended. Anyone signed in may see it; a person not signed in is refused with "log in first". Every stop, extension and release is added to a history of the last 20 (who, when, which action, the reason, the end time) and to the studio's record of admin actions.

### 12-005: When an admin asks one computer to do something, the admin is told when it will happen and how recently that computer was heard from.
- Where: dashboard / Each computer's state
- What: Requests aimed at one computer (update now, resume proxy download, ask this computer why) are held on the server and reach the computer when it next checks in. Each answer to the admin names the editor and computer and says when it will apply:
  - no check-in on record: "when that computer next reports. Nothing on record says when it last did";
  - last heard from 24 hours ago or more: "when that computer next reports. It was last heard from <age>, so this may sit for a while";
  - otherwise: "on that computer's next report, usually within 30 s. It was last heard from <age>".
  - For a pushed build that is not yet the studio's current one it adds ", as a targeted offer of a staged build".
  Ages read "N s ago" under 90 seconds, "N minutes ago" under 90 minutes, "N hours ago" under 48 hours, otherwise "N days ago". A computer heard from 24 hours ago or more, or never, is marked as silent. A silent computer is warned about, never a reason to refuse. The admin is also told whether the same request was already waiting from an earlier click.

### 12-006: An admin can tell one computer to install a particular build now.
- Where: releases-and-updates / Pushing updates and seeing who has what
- What: Only an admin. The admin may name a version (up to 32 characters); with none named, the computer's platform's current build is used. Refusals, each with its sentence:
  - the computer is not known: "no computer '<machine>' for '<editor>'";
  - no version named and nothing current for that platform: "no current companion package is published for that computer's platform";
  - the named version is not published for that platform: "<version> is not in this channel for <platform>";
  - the named version is the one this computer kept crashing on and rolled itself back from: "<machine> kept crashing on <version> and rolled itself back, so it will not install that build again, not even from UPDATE NOW. Publish a fixed build and it is offered as usual." (A version with a local-build suffix counts as the same version.)
  A published build that is not yet current may be pushed: this is how a new build is tried on exactly one computer first. The push records who asked, when and which version the computer was on, and clears any earlier verdict that the computer could not be offered a build. The admin is told whether the build was a staged one, plus the delivery wording in 12-005. A push that has waited 14 days is dropped.

### 12-007: A pushed build installs only when the computer can safely take it.
- Where: releases-and-updates / Installing an update on an editor's computer
- What: Nothing is installed from the server's side. The computer takes the pushed build only if the signed offer it holds is exactly that version, the version is not below the lowest version that computer has promised never to go under, and replacing the app would not interrupt work in progress. If the computer cannot be offered the pushed build, it is not sent; the computer is given the reason (by default "the update you were sent cannot be installed on this computer"), the computer is no longer treated as about to update, and the push stays waiting and is sent as soon as the build becomes offerable. A push is finished once the computer reports that version or a later one; a push backwards (a rollback) is finished only when the computer reports exactly that version.

### 12-008: An admin can withdraw a pushed update before it is taken.
- Where: releases-and-updates / Pushing updates and seeing who has what
- What: Only an admin. Always succeeds, even when nothing was waiting. Withdrawing also ends the one-computer offer of a staged build to that computer.

### 12-009: An admin can forget a computer, removing it and everything recorded about it.
- Where: dashboard / People and computers
- What: Only an admin. Unknown computer: refused. The computer is first removed from the server's file sharing, together with every folder shared with it; if the server's file sharing cannot be reached, the admin is told that it could not be reached, so the computer was not removed, and to try again once it is up; nothing is removed. Then the computer's entry, its sync plan and its status are deleted, and the admin is told how many of each were removed. The admin is also told: "a companion still running and signed in on this computer will register it again on its next report". Forgetting is not taking access away: the person keeps their account and their sign-in.

### 12-010: An admin can restart a computer's stopped proxy download on the editor's behalf.
- Where: sync / Safety stops
- What: Only an admin. Proxy downloading stops itself when the server stops looking like the tree it was or when one pass would delete too much; normally only a person restarts it. The admin can do so remotely. Refusals: unknown computer; and, when the computer's last check-in does not show proxy download stopped (including a computer too old to say), "that computer's last report does not show proxy download stopped, so there is nothing to resume. Wait for its next report and try again." The request is used once: on the computer's next check-in it is sent, unless that check-in shows the download is no longer stopped, in which case it is dropped. The admin gets the delivery wording in 12-005. The admin may withdraw a waiting restart; withdrawing always succeeds.

### 12-011: An admin can copy one computer's sync plan onto another computer belonging to the same person.
- Where: sync / A plan belongs to a computer
- What: Only an admin. The target computer's ticked projects are replaced by the source computer's, in the same order and with the same mode for each project (full sync or upload only). Refusals, each with its sentence:
  - unknown target or source computer for that person;
  - "source and target are the same computer";
  - the whole account works directly off the NAS: "this account is wired to the server: it works directly off the NAS and syncs nothing, so projects cannot be ticked for it";
  - the target works directly off the NAS: "'<machine>' is wired to the server: it works directly off the NAS and syncs nothing, so a plan cannot be copied onto it";
  - the source works directly off the NAS: "'<source>' is wired to the server: it works directly off the NAS and holds no plan, so there is nothing to copy from it";
  - the source has nothing ticked: "<source> has no projects ticked - copying it would empty <target>."
  Every project added or removed is recorded as its own tick or untick, marked as a copy from the source, so the computer's plan history shows it and each one can be undone. A project removed this way gets the same 60-second grace before it stops being shared that a hand untick gets. The admin is told how many projects the target now holds and which were added and removed. The change takes effect soon after.

### 12-012: An admin can approve a computer that has asked to join the server's file sharing and name the editor who owns it.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: Only an admin. A computer waiting to join is approved under an editor's username (1 to 32 characters). One editor may own several computers, so a second computer takes the same username as the first. Refusals, each with its sentence:
  - the server's file-sharing address is not set up: the admin is told it is not configured;
  - "username must be a valid TrueNAS-style username";
  - the computer's identifier is not well formed (letter case does not matter): the admin is told it is not a valid identifier, what the expected shape is, to copy it whole, and that "Adding a malformed ID creates a device entry that can never connect.";
  - the username is not an editor the dashboard knows and "create new editor" is not ticked: "'<name>' is not an editor this dashboard knows. Pick the OWNER of this computer: one editor can own several computers, so a second computer takes the same username as the first. Tick CREATE NEW EDITOR if this really is a new person.";
  - the file sharing itself refuses: its own error is shown.
  On success the editor becomes a known editor, the approval is recorded among admin actions, and the list of people and computers is redrawn.

### 12-013: The studio's server holds published builds of the editor app and of the installer, for Windows and for macOS, with one current build of each.
- Where: releases-and-updates / Offering an update to a computer
- What: There are two kinds of build: the app on the editor's computer (offered to computers as an update) and the installer (what a new editor downloads to set up). Each kind exists for Windows and for macOS. For each kind and platform exactly one build is current; any other published build is staged. The file name a person downloads is chosen by the server from the kind, platform and version, never taken from what was uploaded. On macOS the installer is either the set-up wizard app or a script run in Terminal, depending on what was published.

### 12-014: An admin sees every published build and which computers are behind.
- Where: releases-and-updates / Pushing updates and seeing who has what
- What: Only an admin. For each build: kind, version, platform, file name, checksum, size, when and by whom published, whether it is current or staged and since when, whether its file is still on the server, whether it is signed and whether the program itself is code-signed, the lowest version every computer that sees it will promise never to go below, which dashboard version it needs (and whether this dashboard is too old for it), which processor it was made for, the source revision and whether it was built from unsaved changes, the publisher's one line of what changed, whether it was recalled and why, whether it was ever current (making it current again is a rollback), its trial status (how many computers ran it, for how long, crashes), and how many computers last reported running it. For installers that count is always "cannot tell", because no computer says which installer set it up.
  Also shown: the current version per platform; every computer whose app is out of date, with its version, last check-in, any pushed version and why that push cannot be sent, its last attempt to update (version, attempts, last error, when, the version it rolled back from), any offer it is refusing, and whether the current build is the one it crashed on and fled; every reporting computer grouped by platform, for picking one computer to push to (a computer that never said its platform counts as Windows); every processor kind that computers report and the current build does not cover, with how many computers; the recalled builds; how far each platform has adopted the current build and which computers refuse their offer; the trial length; free and total space on the server's data disk (or that it cannot be measured); and the dashboard's version.

### 12-015: An admin can publish a new build, and the server refuses anything it cannot trust or store.
- Where: releases-and-updates / Making and publishing a release
- What: Only an admin. A build arrives with its version, checksum, signature, its "never go below" version and its publish time, plus optionally whether it should become current, the dashboard version it needs, the processor it is for and a line of what changed (the line is shown in the editor's update dialog). Refusals before anything is received:
  - platform not Windows or macOS, kind not app or installer, version not three dotted numbers ("version must look like 1.2.3"), checksum malformed;
  - this dashboard has no release key to check signatures with: "this dashboard has no release public key configured, so it cannot verify a build and will not publish one. ...";
  - no signature: "unsigned publish REFUSED: no signature. ...";
  - the "never go below" version or the publish time missing or malformed;
  - the version is already published for that platform: the admin is told to raise the version number and rebuild;
  - not enough free space: the data disk must have at least three times the build's size plus 256 MiB free, and the admin is told "not enough free space on the data volume: N MiB free, this publish needs about M MiB. Old builds are pruned on publish (current plus the two newest are kept); free some space and try again." When free space cannot be measured there is no refusal.
  Refusals after receiving: larger than 200 MiB ("package body too large"); empty or not matching its checksum (the admin is told the checksum did not match or the upload was empty: "the upload was corrupted, and nothing was published"); a "never go below" version above the build's own version (every computer that saw the offer would then refuse it; nothing is published); a signature that does not check out against the dashboard's release keys ("release signature REJECTED (...)"). A transfer cut off midway leaves nothing behind, and two uploads at once cannot spoil each other. The publish is recorded among admin actions.

### 12-016: Publishing with "make it current" makes the build current only if the release gate allows it; otherwise it is published staged.
- Where: releases-and-updates / Trying a build on one computer first
- What: When an admin publishes and asks for the build to become current, the release gate in 12-018 decides, with no override. If the gate refuses, the build is published but staged, and the admin is told "published and STAGED: push it to one computer, let it soak, then MAKE CURRENT." followed by the gate's reason. At publish time the trial period is skipped when nothing is current yet or when the new build is not newer than the current one.

### 12-017: Old builds are cleared away when a new one is published.
- Where: releases-and-updates / Making and publishing a release
- What: By default, publishing removes every non-current build of that kind and platform except the two newest, so the current build plus two others remain. The publisher can choose not to clear old builds.

### 12-018: An admin can make a published build the current one, subject to a release gate that explains every refusal.
- Where: releases-and-updates / Trying a build on one computer first
- What: Only an admin. For the app, current means what every computer is offered; for the installer, what a new editor downloads. The gate, in order:
  - no such build: refused;
  - the build was recalled by the vendor: "<kind> <version> was RECALLED by the vendor[: reason]. It cannot be made current. Roll the fleet back to a build that was not recalled." No override;
  - the build needs a newer dashboard (or its stated need cannot be read): "<kind> <version> needs dashboard <x> and this dashboard is <y>. Update the dashboard first, then make this build current." No override;
  - the build has no signature: the admin is told that computers check signatures, so making it current stops every computer in the studio from updating, silently; the message points to where a signed build can be had (the vendor's available builds when the studio takes them, otherwise the studio's own release tool) and ends "To make it current anyway, type the version number (<v>) into the confirmation box.";
  - a build that was current before passes (it is a rollback);
  - the trial period (12-019) applies to the app only, never to the installer.
  An override is given by typing the build's version number into a confirmation box; asking for an override without typing it correctly is refused with "to override the soak gate, type the version number (<v>) into the confirmation box. Nothing changed." Every change of current build is recorded among admin actions, including whether it was overridden.

### 12-019: A new app build must run on at least one computer for a trial period before it can become current.
- Where: releases-and-updates / Trying a build on one computer first
- What: A staged app build may become current only after at least one computer has run it for the trial period: 30 minutes by default, set per studio, and 0 turns the trial off. Every refusal starts "<v> has not soaked yet:" and ends "Make it current anyway by confirming the override." and says which of these holds: no computer has reported running it yet ("Push it to one computer first, leave it for N min, then make it current."); some computers had to roll themselves back off it after crashing repeatedly; computers crashed since they started running it; crashes on record cannot be dated, or no computer reported its crash count; or not enough minutes have passed yet. Typing the version number overrides it.

### 12-020: An admin can roll every computer on one build back to another build.
- Where: releases-and-updates / Rolling back and withdrawing a build
- What: Only an admin, for the app only, and for any build, recalled or not. Every computer whose last check-in says it runs the chosen build on that platform is asked to install the build named to go back to, on its next check-in; by default that is the platform's current build. Refusals:
  - nothing current and nothing named: "no current <kind> package is published for that platform, so there is nothing to roll back to";
  - going back to the same build: "<v> is what those computers are already running.", and the admin is asked to pick the build to put them back on;
  - the installer: "a <kind> build cannot be rolled back across the fleet: no computer reports which <kind> it was set up with, so there is nobody to ask. Make the older <kind> current instead, and it is what new installs download.";
  - the build to go back to is not published, or was recalled too ("<to> was recalled too. Pick a build that was not.").
  When the build being left is the current one, the studio's current build is first switched to the one gone back to, through the release gate with no override. If the gate refuses, the current build stays as it is, the admin is shown the gate's reason, and the computers are still asked. When the current build did change, the admin is told which build stopped being current and which computers run something newer than the one gone back to (they will now be offered a downgrade). The admin is told which computers were asked. Recorded among admin actions.

### 12-021: An admin can delete a build that is not current; it is kept in a trash for 30 days.
- Where: releases-and-updates / Rolling back and withdrawing a build
- What: Only an admin. Refused when the build does not exist, and when it is current: "cannot delete the current version. Make another version current first". The build's file is moved to a trash on the server and kept for 30 days from the deletion, after which it is deleted for good. If it cannot be moved to the trash, the admin is told "could not move <file> to the trash folder (...). Nothing was deleted: the package row is still here and so are its bytes." A file already missing is not an error. There is no way to restore a trashed build from the dashboard. Recorded among admin actions with where the file went.

### 12-022: Anyone signed in, and every editor's computer, can download a published build, including "the current one" by name.
- Where: releases-and-updates / Installing an update on an editor's computer
- What: A person signed in to the dashboard or a computer with the studio's credentials may download any published build, or ask for "current" (any letter case) to get the current build of that kind and platform. Refusals: neither a signed-in person nor a computer with credentials (told to log in); a computer whose person's account is removed, suspended or disabled is refused with the account sentence in 12-025; nothing current ("no current <platform> <kind> package is published"); unknown version; the build's file missing from the server ("package file missing on server"). The download carries its checksum, version and signature details, so the macOS first-install script, which cannot check a signature itself, can still check the file is whole and refuse a channel that is not signed.

### 12-023: Each computer is offered the build it should run, or told why not.
- Where: releases-and-updates / Offering an update to a computer
- What: A computer is offered a build only when it has said its platform (Windows or macOS) and the version it runs, and that version differs from the build to offer. "Differs", not "is older": a rollback made current is offered exactly like an update. The build offered is the platform's current one, except for a computer with a pushed build waiting, which is offered the pushed version even when it is staged. The offer carries the build's details and the publisher's line of what changed. The offer is held back, and the computer is given the reason instead, when:
  - this computer kept crashing on that build and rolled itself back, and it is not an admin's push: "this computer kept crashing on that build and rolled itself back, so it is not offered again" (lasts until the computer runs that version or a newer one);
  - the build was recalled: "that build was recalled by the vendor";
  - the build needs a newer dashboard: "that build needs a newer dashboard than this one";
  - the build and the computer both state their processor kind and they differ, unless the build is made for both Mac processor kinds: "that build was made for a different processor than this computer". A build or a computer that does not state one is offered as usual.

### 12-024: Each editor's computer checks in with the server about every 30 seconds, and anything asked of it arrives on its next check-in.
- Where: dashboard / Reports from computers
- What: Each editor's computer sends its state to the server about every 30 seconds. Anything an admin or a person asks of one computer reaches it when that computer next checks in, normally within about 30 seconds; a computer that is off gets it when it comes back. Everything the dashboard shows about a computer is measured from when the server received its check-in, not from that computer's own clock. Something a check-in does not mention is usually left as it was, rather than read as empty.

### 12-025: A computer is heard only while its editor is signed in on it and the editor's account is in good standing, and a refused computer is marked on the dashboard.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: A computer must present the studio's credentials and the identity its editor got by signing in at the tray. Each refusal tells the computer why:
  - no identity: told an identity is required, and to sign in from the tray (its "Sign in" item) to get one;
  - identity taken away by an admin: told it was revoked, and to sign in again from the tray;
  - identity cannot be checked any more (the server's signing secret changed): told it is invalid or expired, and to sign in again from the tray;
  - identity or credential belongs to a different editor than the one reporting: refused, saying so;
  - bad or missing credentials: refused, saying so.
  When the person's account was removed, suspended or disabled, the computer is refused with:
  - removed: "this account was removed from the dashboard. Ask your admin to add it again if that was a mistake";
  - suspended: "this account is suspended on the dashboard. Ask your admin to press RESUME: your sync plan is untouched and comes straight back";
  - disabled: "this account has been disabled on the dashboard. Ask your admin to turn it back on: nothing will sync until they do".
  An identity never expires by itself. If the account check itself fails, the computer is heard. Each refusal marks the computer on the dashboard with "report refused at <time>" and a plain reason (for example "no computer identity token was sent", "its computer identity token was revoked by an admin", "its computer identity token cannot be verified (the dashboard's session secret has changed)", "its computer identity token belongs to a different editor", or the account reason). Nothing else from a refused check-in is kept. The mark clears on the next accepted check-in.

### 12-026: During a change of the server's signing secret, computers signed in under the old one keep working, and the dashboard knows which ones still use it.
- Where: accounts-privacy-legal / How secrets and keys are kept
- What: An identity made with the previous signing secret is still accepted during a changeover. The dashboard records which computers still use the old one, so an admin can tell when it is safe to retire it. Once it is retired, those editors must sign in again at the tray.

### 12-027: For people building the product, check-ins can be accepted without any credentials.
- Where: whole-product / Requests, logs and outside programs
- What: Only when the server is deliberately run in its insecure development mode can it be told to accept check-ins with no credentials. Without development mode that option is ignored and the server says so when it starts.
- Flag: dev only

### 12-028: A very large check-in is trimmed rather than refused, keeping the editor's most important projects.
- Where: dashboard / Reports from computers
- What: A check-in is never refused for being too long in its lists: the server keeps the first 64 projects of the editor's disk listing and of the Resolve bin listing, the first 64 waiting items, the first 4,000 originals and 4,000 proxies per project (the project is then marked as cut short), and the first 4,000 clips per Resolve project. The computer's own order is kept, so its most important projects survive. Every text, list and number in a check-in is cut to its limit rather than refused. The computer is told what was cut. A whole check-in larger than 8 MiB is refused.

### 12-029: When computers run a newer app than the dashboard understands, the home page says so.
- Where: dashboard / Problems the server finds
- What: Information in a check-in that the dashboard does not recognise is accepted and set aside, never a reason to refuse the check-in. The dashboard keeps track of it, and a banner on the home page tells the admin that computers are reporting things this dashboard does not read, which means the dashboard has fallen behind the computers. A part of a check-in that cannot be read at all is dropped and the rest is kept.

### 12-030: Information a studio or a computer has chosen to withhold is removed on arrival, and what was held before is deleted.
- Where: accounts-privacy-legal / What the product records about a person
- What: Four kinds of information can be withheld: the names of Resolve projects (withholding these withholds the Resolve bin trees too), the lists of files on the editor's disk (and the clip lists and paths in the health reports), the Resolve bin trees, and how long the keyboard and mouse have been idle. They can be withheld by the whole studio, or by one computer for itself; both together apply. A computer that does not say its own choice this time keeps its last stated choice. Every withheld item is removed before anything is kept. The records of Resolve changes a computer can undo stay listed, with their project names masked. If the withheld items cannot be removed cleanly, that whole part of the check-in is dropped; if even that fails, the check-in is refused. When a computer starts withholding a kind of information, everything the dashboard held of that kind for that computer is deleted. Each computer's choice is recorded.

### 12-031: The dashboard records how each computer reaches it and warns when the connection is unencrypted over the public internet.
- Where: dashboard / Security of pages
- What: For each computer the dashboard records whether it connects unencrypted over the public internet, unencrypted over the studio's own network or private network, or encrypted. It records a change when one happens, and raises a warning only for an unencrypted connection over the public internet.

### 12-032: The dashboard records which version of the licence each computer accepted, and when.
- Where: accounts-privacy-legal / The licence a person accepts
- What: Each computer reports the licence version it accepted, when, and a fingerprint of the exact text. The dashboard keeps it, and a check-in that does not mention it leaves the record as it was.

### 12-033: The dashboard shows what each computer's sync is doing right now, file by file.
- Where: sync / Saying truthfully what the sync is doing
- What: For each of a computer's sync activities the dashboard shows its state (idle, syncing, error or paused), how many files are waiting and moving, its last error (up to 2,000 characters), when it last synced, a short detail line, the project it is on, bytes done and total, speed, time left, and how long it has been in that state, together with a marker that changes whenever real work happens (so a stuck activity can be told from a busy one). The live list of files moving (up to 256: name, direction, bytes done and total, percentage, speed, time left, project) is replaced by each check-in, and finished files are added to the transfer history (name, direction, which activity, when).

### 12-034: The dashboard learns which Resolve project is open on each computer and which tree project it belongs to.
- Where: resolve-on-the-editors-computer / Knowing which project is open
- What: Scratch projects are ignored: a name of "untitled project" or "new doc", optionally followed by a number (for example "New Doc 1", "Untitled Project (3)"), whatever its letter case and spacing. A Resolve project already matched to a tree project uses that match. Otherwise the product matches it by itself only when confident: at least two meaningful words in common with an active project's name, or the Resolve name equal to the last part of the project's folder. It does not match when a folder in the projects tree that is not a registered project matches as well, or when the tree cannot be read. A match made this way is kept for good, and only an admin can change it afterwards. With no match, the editor's computer is told, so it can ask the editor to pick the folder.

### 12-035: Each computer says whether it works directly off the NAS or syncs, and the dashboard keeps its last word.
- Where: sync / Wired or remote
- What: The computer's own check-in says whether it is wired (works directly off the NAS and syncs nothing) or an editing computer that syncs. A check-in that does not say keeps the stored answer.

### 12-036: The dashboard knows what each computer holds on its own disk, project by project.
- Where: sync / What is owed
- What: For each project on the editor's disk: how many originals and proxies, their total size, whether the list was cut short, and when sent, the list of files with their sizes. A folder on the disk is matched to its project by name, with names compared so that a Mac's spelling of accented letters matches the same name from Windows or the NAS. A folder with no registered project still gets its own entry. When a full file list arrives it replaces the computer's earlier list for that project.

### 12-037: The dashboard keeps each computer's Resolve bin layout for projects matched to the tree.
- Where: resolve-on-the-editors-computer / Bins, clip sorting and imports
- What: For each Resolve project that has a match to a tree project, the dashboard keeps each clip's bin, name, file path, kind and whether its file is present, replacing that computer's earlier layout for that project. Scratch projects and unmatched projects are not kept.

### 12-038: The dashboard shows how each computer's connection to other machines is doing and how many unfinished uploads it left on the server.
- Where: sync / Speed and routes
- What: For each computer: how many of its connections to other machines are direct and how many go through a relay, and how many unfinished uploads from it are lying on the server and their total size. A check-in that does not mention these leaves the last values.

### 12-039: The dashboard shows each computer's safety stops and its own pause.
- Where: sync / Safety stops
- What: For each computer the dashboard shows whether proxy download has stopped itself, why and when; whether that computer has stopped syncing and whether the stop is its own or the studio's, with the reason; how many files the editor's local trash holds and their size; how many uploads were never sent because the server already holds a file of the same name at a different size (never replaced), and under which project this was measured; and the lowest free space at which proxy download parks itself. When a computer stops reporting one of these problems, it disappears from the dashboard at once.

### 12-040: The dashboard shows each computer's free disk space, kept until the next measurement.
- Where: sync / Disk space
- What: Free and total space where the computer syncs to, free space on its system disk, and when they were measured. A check-in without a measurement leaves the last one shown rather than blanking it.

### 12-041: The dashboard shows why nothing is moving on a computer, and whether something got stuck.
- Where: sync / Stuck, slow and fair transfers
- What: The computer's own answer to "why is nothing moving" (a reason, a detail and since when) is shown. Also: the last sync activity the computer found stuck, for how long, and whether it had to be stopped; how often the computer turns from project to project, which sets how long the dashboard waits before calling something stuck; how many times the app's background work had to be restarted in the last 24 hours, the latest one and its error; whether the file-sharing part of the app is down, since when, how many times a restart was tried, the last error and whether anything is still trying (yes, no or cannot tell); how many shared folders have no filter written (and the first 10 names); and how many sync conflicts it holds.

### 12-042: The dashboard shows how many times the app crashed on a computer.
- Where: editor-app / Starting, staying running and crashing
- What: The count of crash records on that computer and the name of the newest one.

### 12-043: When an editor deletes a project's local copy before it caught up, nobody is told.
- Where: sync / Deletions and removing a project
- What: When an editor deletes a project's copy from their computer although it still had uploads owed, the computer reports it (up to 8 at once, with how many uploads were owed and why). The server only writes it to its own log; nobody is told and the dashboard does not show it.

### 12-044: The dashboard shows Resolve's media health on each computer.
- Where: resolve-on-the-editors-computer / Missing clips, relinking and refreshing
- What: For each computer: how many clips point outside the shared tree, how many through a wrong drive or path, how many are missing, how many were set aside, when the last scan ran, and the projects not opened on the dashboard whose clips exist only on that computer (up to 20, with counts). The detail behind it is also kept: whether Resolve is connected, which project is open, whether a call to Resolve has been stuck and for how long, up to 50 missing clips, up to 50 clips refused because their path is not the shared one, proxy attach results, proxies missing, the stills check, and stand-ins still owed. When the computer stops sending it, the detail is cleared.

### 12-045: The dashboard shows project folders on an editor's disk that are not where the tree says, and footage dropped in but not filed.
- Where: sync / Project folders on an editor's computer
- What: For each computer: how many project folders on its disk are not in the tree and their size; how many project folders are not where the tree says they should be; and how much footage was dropped in on that computer but not yet filed.

### 12-046: The dashboard shows whether each computer's "Send to Resolve" helper is listening.
- Where: broll / Sending a clip to Resolve
- What: For each computer: whether the local helper that takes "Send to Resolve" clicks from the browser is on, listening, on which port, its error if any, and since when. This is what to look at when a person's "Send to Resolve" does nothing.

### 12-047: The dashboard shows whether each computer can download from YouTube and whether its downloads reached Resolve.
- Where: youtube / Reaching the editor and Resolve
- What: Each computer's verdict on its YouTube download tools is kept and feeds two alert checks. Clips it downloaded that never reached Resolve are shown in the per-computer view: a state (for example fine, no matching project, Resolve closed, sync drive missing, paused), the reason, how many are waiting, and when. Both clear when the computer stops sending them.

### 12-048: The server knows which archive clips each computer holds a stand-in proxy for, and tells every computer which ones exist across the studio.
- Where: broll / Previews standing in for originals
- What: Each computer reports up to 200 archive clips for which it holds a preview standing in for the original; a full list replaces its earlier one, and a check-in without one changes nothing. On every check-in the computer is told every archive clip any computer in the studio holds a stand-in for (an empty list means none).

### 12-049: Each computer answers the file moves an admin made on the server, and the admin sees each answer.
- Where: proxies-and-file-moves / Following a move on an editor's computer
- What: Every move an admin made on the server that a computer must follow is sent with each check-in until that computer answers, including moves recorded under the computer's previous name. Answers (up to 64 at once) say done, failed, trying again, blocked, or "not synced here" (the computer put its copy in the trash because it does not sync the project the file moved to; this is final), with a detail line, how many attempts, and whether the file moved on disk but Resolve is not yet pointed at it. While a computer is still working on a move, it keeps being sent. A move answered in one check-in is not sent back in the reply to it.

### 12-050: Each computer reports the Resolve clip-path changes it can undo, and answers undo requests.
- Where: resolve-on-the-editors-computer / Fixing media: copying in, rehearsals and undo
- What: A computer lists the changes it made to clip paths in Resolve projects (up to 20: project, when started, how many clips, where they came from); each list replaces the last. Answers to undo requests (up to 16 at once) say done, failed, trying again, or waiting because no project is open in Resolve, with a detail and attempts. Answers are matched even when the computer was renamed.

### 12-051: An admin can see a computer's undoable Resolve changes and undo one on that computer.
- Where: resolve-on-the-editors-computer / Fixing media: copying in, rehearsals and undo
- What: Only an admin. The admin sees what the computer last reported it can undo, and every undo asked of it with a sentence for its state: waiting ("waiting: no project open in Resolve, will resume when one is"), trying again ("retrying on this computer's next report"), done, failed (each with the computer's own detail when it gave one), or no answer yet ("waiting for that computer to report"). Asking for an undo is refused when the computer has not reported that change: "that computer has not reported a change called '<id>'. Its list is refreshed every time it reports: reload and try again." The request is sent on every check-in until answered. The computer refuses it while a different project is open in Resolve.

### 12-052: Each computer tells the server what heavy work it can do and whether it is free.
- Where: fleet-jobs / What a computer can honestly offer
- What: Each check-in can say: whether it has a graphics card, its name and memory, a hardware video encoder, the video tools, transcription and its details, the assistant, up to 16 shared drives it can reach, processor count, how long the keyboard and mouse have been idle ("cannot tell" counts as not idle), load, whether it takes shared work at all, its idle threshold, which kinds of work it takes (none listed means all), until when it volunteers, whether Resolve is running and which project, the state of its connection for Timeline Cards (connected, state, timeline, version, since when, a detail line, last contact), and why it takes no shared work on its own (reason and detail). Each one replaces the last; a check-in without it leaves the last. A computer that never said what it can do is offered no work that has a requirement.

### 12-053: The dashboard shows how far each computer's own proxy making has got.
- Where: proxies-and-file-moves / Making proxies on editors' computers
- What: For each computer: how many proxies are missing, the state of its proxy making, and how many are left. A check-in without it leaves the last values.

### 12-054: The dashboard shows each computer's local b-roll and music indexing and any warning, and can ask it to stop a batch.
- Where: broll / Describing and indexing clips
- What: For b-roll and for music separately, the dashboard shows whether a local indexing batch is running on that computer, which batch, its state, done, total, failed, the current clip or track, the percentage, the quality level (b-roll only) and any warning, for example not enough graphics memory, shown even when nothing runs. A check-in without it shows "not indexing" and keeps the rest. Batches someone asked that computer to stop (up to 16 of each) are sent with its next check-in. If the b-roll or music part is off or cannot be read, no stop is sent.

### 12-055: A computer's own settings are shown on its owner's account page, and a change asked from there reaches it on its next check-in.
- Where: accounts-privacy-legal / What each person may see and reach
- What: Each computer reports which settings may be changed from the dashboard (only whether it takes shared work and which kinds; whether it is wired or remote can never be asked for), how long it volunteers, how often it reminds about an unplugged sync drive, its YouTube status (downloads on, sign-in enabled, terms accepted, signed in), which settings are waiting for a restart of the app, and its answer to the last request. A request for a change is sent on every check-in until answered and the first delivery time is recorded. It is held back, still waiting, if it asks for a setting that computer does not accept; a computer that never said what it accepts is judged against the settings that may ever be asked for. An answer of "applied" or "refused" ends the request; any other answer leaves it waiting. When the computer cannot say whether a restart is waiting, the dashboard shows that it cannot tell.

### 12-056: A renamed computer keeps its plan, and a copied disk running on two computers is caught and explained.
- Where: sync / Computers joining and changing
- What: Each computer has an identity of its own that survives a change of its name. When a computer reports under a new name with the identity an older entry of the same person carries:
  - if the older entry checked in within the last 5 minutes, both are treated as live computers (one disk was copied onto another): nothing moves, and the home page shows "Two computers are reporting the same identity: ... This happens when one computer's disk was copied onto another one ..." with the fix: on the newer computer, quit CC Sync, delete the computer's identity record in that user's home folder and start CC Sync again, wait five minutes, then remove the old entry with "Forget" on the sync status page;
  - if the older entry has been quiet for 5 minutes or more, the new name takes over the old one's plan and records, and the duplicate warning is cleared;
  - if the new name already has a plan of its own, nothing moves.
  When a computer reports a file-sharing identity that another of the same person's entries held, it is taken off the other entry, because one identity is one computer.

### 12-057: The home page warns when the server is slow to record check-ins.
- Where: dashboard / Speed under load
- What: When recording a check-in holds the server's records busy for more than 5 seconds at a stretch, a problem is shown on the home page.

### 12-058: An editor's computer sends the server a plain-text account of its own state, and the admin can read it.
- Where: dashboard / Reports from computers
- What: The account describes the computer: who it is, its sign-in state, its sync folder, configuration problems, what its sync is doing, its connection to Resolve, and so on. It is sent when the editor presses the tray's button, when a sync activity hits an error, or when an admin asks (12-059). The same sign-in and account checks as a check-in apply (removed, suspended or disabled accounts are refused with the account sentence; a missing identity is told to sign in from the tray). Text longer than 256 KiB is cut, never refused. If the studio withholds a kind of information that this computer does not take out of its own account (including a computer that never said), the account is not kept; in its place the admin reads "(not stored: this site withholds <categories>, and this computer's companion is too old to take those out of its bundle. Update the companion on this computer to see its bundles again.)". Accounts are kept 30 days. An admin can read them all for one person or one computer, or the newest for every computer. Each one received is recorded among admin actions.

### 12-059: An admin can ask one computer "why", and get its account back.
- Where: dashboard / Each computer's state
- What: Only an admin. Unknown computer: "no computer '<machine>' for '<editor>'". The ask is sent on every check-in until that computer's account arrives, then stops. The admin is told whether an earlier ask is still unanswered, plus the delivery wording in 12-005.

### 12-060: An admin can see every alert open now, every kind of alert, and the last 200 sent.
- Where: dashboard / Alerts by mail
- What: Only an admin. Opening it runs every check afresh and shows the problems found now with counts; every kind of alert with its severity, title and what it means; the kinds grouped, each with whether it is sent; the alert settings (a password is never shown, only whether one is set and where it came from); and the last 200 alerts sent.

### 12-061: An admin can send a test alert and preview this week's report.
- Where: dashboard / Alerts by mail
- What: Only an admin. The test sends "This is a test of the CC Sync alert channel. Nothing is wrong." through the configured way of sending, every time it is pressed (never held back as a repeat), and shows what happened. The preview shows the subject and the body of this week's report exactly as it would be sent.

### 12-062: An admin can see what is protected and plan a recovery, even when the NAS is down.
- Where: server-install-and-running / Snapshots, restoring and the server's disk
- What: Only an admin. The admin sees what is protected now, what can have gone wrong, and the plan for a chosen problem. It answers even when the NAS is down, saying what it could not find out. Refusals come with their own sentences.

### 12-063: An admin can preview and restore a project from a server snapshot, never over the live project.
- Where: server-install-and-running / Snapshots, restoring and the server's disk
- What: Only an admin. A preview shows what restoring that project from that snapshot would bring back. A restore puts the project into a separate dated folder in the tree, beside the project and never over it; the admin may choose to also bring back files that changed since the snapshot. There is no way to overwrite the live project.

### 12-064: An admin can rehearse a restore, and only a successful rehearsal is shown as the last one.
- Where: server-install-and-running / Snapshots, restoring and the server's disk
- What: Only an admin. A rehearsal restores from a chosen snapshot into a scratch place. Only a successful rehearsal records its date on the protection overview.

### 12-065: Heavy work is shared out across the studio's computers, with a limit on how many of each kind run at once.
- Where: fleet-jobs / Load on the NAS and the computers
- What: Kinds of work: transcription, small proxies for Timeline Cards, sound taken out of a clip, waveforms, bringing in a camera card, copying a drive, and updating the record of where every copy is. Files a job uses are named by shared place and position within it, so each computer finds them wherever its drives are. Studio-wide limits on how many run at once: transcription 2, drive copies 2, every other kind 4; the operator can change them. Two computers can never hold the same job, and claims at the same moment cannot exceed a limit.

### 12-066: An admin can queue a piece of work, aim it at one computer, and make it run now.
- Where: fleet-jobs / Choosing who runs what
- What: Only an admin. A job has a kind, what it works on, what it needs, a priority from -100 to 100 (higher first, 0 by default), optionally one computer it must run on, and optionally "run now", which skips waiting for the computer to be idle, the rest after a failure and the ranking grace, but nothing else. When nothing is said about what a job needs, the standard needs for its kind are filled in (the media kinds need the video tools and the places the job names). For the proxy, sound and waveform kinds, an output name that is not a plain file name is refused, and the admin is told the name is not a plain file name: it cannot be a dot name or hold a '/' or a control character, on any computer. The admin is shown, for every computer, whether it can run the job and why not. A kind that does not exist and a computer that does not exist are accepted without a warning.

### 12-067: An admin can list the jobs, see the queue and the limits, and see whether the server itself can take work the computers gave up on.
- Where: fleet-jobs / Failures, retries and the queue
- What: Only an admin. Jobs can be listed by state and kind (200 by default). The queue view shows how many are waiting, running and taken over by the server, how many of each kind run against its limit, and whether the server can take over work the computers gave up on, with the reason when it cannot ("no executor is configured"). Each job can be opened, along with, per computer, why it can or cannot run there.

### 12-068: An admin or an editor's computer can see which computers a job could be aimed at.
- Where: fleet-jobs / When a computer counts as free and able
- What: An admin, or a signed-in computer; a signed-in person who is not an admin is refused "admins only". For every computer: whose it is, its name, whether it is wired, whether it is online (checked in within the last 24 hours), when it last checked in, whether it takes shared work (no if it never said what it can do), which kinds (none listed means all), what it has (graphics card and memory, hardware encoder, video tools, transcription, processors, shared drives), how long it has been idle ("cannot tell" when unknown) and the job it holds now. Online computers first, then by name. No credentials, file-sharing identities, paths or project names are shown.

### 12-069: An admin can cancel a job; one already running is stopped by the computer running it.
- Where: fleet-jobs / Stopping and cancelling
- What: Only an admin. A waiting job ends at once as failed, "cancelled by <admin>", and is never tried again. A job a computer is running, or the server has taken over, is asked to stop: the computer is told on its next check-in and stops its work, and the server stops its own; the job is not marked finished until the work has actually stopped. Refusals: no such job; "this job is already <state>" for a finished one. The admin is told whether it ended or a stop was asked.

### 12-070: An admin can try a finished job again as a new job.
- Where: fleet-jobs / Failures, retries and the queue
- What: Only an admin. The same work is queued again under a new number, with the same kind, inputs, needs, priority, "run now" and target, marked as a retry of the old one; the old one is left as it was. Refusals: no such job; "job #N is <state> and has not finished, so there is nothing to try again yet. Cancel it first."; "job #M is already a new attempt at job #N and it is still on the queue." The admin is shown who can run the new one.

### 12-071: An editor's computer takes work only when offered it, keeps hold of it only while it keeps working, and hands back the result.
- Where: fleet-jobs / Failures, retries and the queue
- What: On each check-in a computer is offered up to 8 jobs it may take, chosen from what it can do right now; jobs an admin said to run now are marked; jobs it holds that an admin cancelled are named; and it is told how deep the studio's queue is (waiting, running, taken over by the server, and the age of the oldest waiting job) so it can ask less often. It takes one job, checked against what it can do at that moment. It must keep saying it is still working (with an optional note and progress); a job not heard about for 5 minutes is taken away and queued again, handed to the server, or given up, and a computer told "this job is no longer yours" stops. When it finishes it says whether it worked; a failure that may succeed elsewhere is queued again until the kind's number of attempts runs out, then handed to the server if the server can do that kind (transcription never is), otherwise given up. A failure that is the job's own fault is not tried again. A computer that failed rests for 2 minutes before being offered more. A computer whose person's account is removed, suspended or disabled cannot take work or keep it, but may still hand back a result. Finished jobs are kept 30 days.

### 12-072: An editor's computer about to give up on files that vanished can ask the server whether they were moved.
- Where: proxies-and-file-moves / Moves made by hand on the NAS
- What: A signed-in computer asks about files by name and exact size only, at most 2,000 at a time (more is refused: "ask about at most 2000 files at a time - this asked about N."). The server answers from its last inventory of the tree without looking at the disk: for each file every place in an active project where a file of that name and size sits (it never picks one), names compared so a Mac's spelling matches. It also says how old the inventory is, which projects could not be read last time and were left out, and when no inventory has ever been taken, that the answer is "not known" rather than "not found".
