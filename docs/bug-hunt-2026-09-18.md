## Two things that affect the ship pipeline today

- **CI on `main` will be red on the next push** (`ytdl-web-1`, high,
  reproduced by the orchestrator): `ytdl/web/tests/test_api.py:470`
  monkeypatches the running yt-dlp to the literal `2026.08.27` and asserts
  it is not stale against a 21-day limit computed from `date.today()`. It
  held until 2026-09-17 (the last green run) and fails from 2026-09-18 for
  ever. The `ytdl/web -- pytest` step has no `continue-on-error`, and
  `tools/publish_latest.py` publishes only the newest GREEN run, so the
  vendor feed cannot take any commit made after yesterday until this one
  line is fixed. The fix is to derive the fresh date from the clock.
- **The companion suite spends about eleven minutes on one leaked thread**
  (`comp-music-ytdl-jobs-2`, medium): a `test_ytdlp_manager.py` test starts a
  real `YtDlpManager` with `sidecar_tools` unstubbed; its thread holds
  `sidecar_tools._work_lock` through real GitHub I/O, and a later test blocks
  on that lock. The verifier corrected the culprit to
  `test_start_runs_ensure_on_its_own_thread_and_stop_ends_it` (line 929),
  not the test the hunter cited.

## The ten that matter most

In the order a fix pass should take them. Six of the ten are in code that
shipped to the whole fleet on 2026-09-17; three are in the hand-moves
feature (CR-268, dashboard 0.7.45+ / companion 0.9.73+); one is the CI red
above.

1. **`comp-sync-1` = `dash-api-1` - lane B puts a deleted file back at the
   exact path it just trashed it from, every pass, for ever, and disarms
   the breaker while doing it** (high, CONFIRMED both ends, reproduced
   against the real lane). CR-268b's `_relocate_trashed` treats "the
   server's inventory holds one place for this (basename, size)" as "it was
   moved there" and never checks whether that place is the path the file
   was just trashed FROM. `nas_media` is the last completed walk (up to
   `interval_inventory` old, and arbitrarily old when the walk is failing:
   DASH-5's collapse refusal keeps the stale rows and never advances
   `tree_sig`, and `locate.py` reads them with no reference to
   `nas_inventory_state.last_error`). So a file genuinely deleted on the NAS
   is restored from `.ccsync-trash` to its own path on every lane B pass,
   the deletion never lands, and because every restore is counted as a
   relocation that `LaneBBreaker._discount_relocations` subtracts, a NAS
   folder wiped by accident raises nothing. `HAND_MOVES_ON_THE_SERVER.md`
   §4a says "found ELSEWHERE"; the code does not implement the word.
   Fix both ends: drop any place equal to the trashed-from path in the
   companion, and exclude projects whose inventory is flagged unreadable or
   stale from the locate join, carrying the excluded slugs in the answer.
2. **`res-companion-2` - lane B's hand-move follow leaves Resolve pointing
   at the old path, and the detection command that follows answers "nothing
   at the old path" instead of relinking** (high). CR-268's lane B renames
   the local copy itself, with no `file_moves` intent row and no relink;
   minutes later the v53 detection delivers the same move as a command,
   `apply_move` finds the source gone, the resume branch needs an intent row
   lane B never wrote, it returns `ok` with `paths=None`, and `app.py` skips
   the relink and records the move as done. Every clip under a hand-moved
   folder is Media Offline in that editor's Resolve while the MOVES history
   says the machine followed. The verifier notes lane B only relocates
   `**/Proxy/**`, so part of the harm predates CR-268; what is new is that
   resumable evidence exists and is ignored.
3. **`comp-broll-tiers-1` = `res-companion-1` - a stand-in whose download
   finishes after the page stops polling is never ledgered** (high, one
   line, one fix). On `fetch_standin` the 1080p preview is written to the
   ORIGINAL's local path by an asynchronous rclone job, but the ledger row is
   written only by the request that observes `state == "done"`. Close the
   tab, background it, switch to Resolve after the "syncing 40%" toast, and
   the file lands under a 6K name with no ledger entry: the next Send to
   Resolve takes the import-original path, `broll_fetch` calls the original
   present for ever, the relink pass never learns the geometry is the
   stand-in's, and a render on that machine renders 1080p H.264 under a 6K
   name. `test_broll_insert_tiers.py:288` pins the gap with `assert
   broll_standins.all() == []`. Record the intent BEFORE the fetch starts.
4. **`comp-resolve-1` - the stand-in geometry refresh never runs:
   `replace_clip` short-circuits on its own path and reports success**
   (high, reproduced independently by the verifier). Phase 3's mechanism is
   `ReplaceClip(<the same path>)` to make Resolve re-read a changed file;
   `apply_relinks` calls `resolve_bridge.replace_clip`, which returns
   `Already linked` whenever the requested path equals the clip's own, which
   for a refresh is always true. Nothing is re-read, `refreshed += 1` is
   counted, and the same ops are planned every 120 s pass, each burning one
   `allow_automatic` grant, so the 8-per-day budget is spent in about two
   hours and genuine proxy relinks are held for the rest of the day. The
   verifier warns that a `force=` flag alone also makes the success test
   vacuous and writes a no-op undo entry: both need a decision.
5. **`comp-resolve-2` = `res-companion-3` - the geometry check ffprobes
   every archive clip, whole file, on every 120 s pass** (high).
   `_geometry_disagrees` runs `ffprobe -count_packets` (a full demux) on
   every in-tree archive clip whose original is present and is not a
   ledgered stand-in, cached per pass only. On a wired rig with the archive
   on P:, fifty 2 GB clips is ~100 GB over SMB every two minutes, serialised
   on the media-tree thread, with a 60 s timeout per clip; the lane
   watchdog then restarts the thread mid-probe, so neither the library walk
   nor the relink ever completes. Ask the cheap question first (the ledger's
   `is_stale`, which nothing calls; a header-only probe) and persist the
   verdict per (path, size, mtime). Note `proxy-tiers-4` (medium): the
   wired rig has no working signal at all that a clip was born from a
   stand-in, because the ledger is per-machine state about an event on
   another machine, so items 4 and 5 are two halves of "goal 2 of the plan
   has no mechanism that works", while CR-281 records it as built.
6. **`dash-api-2` = `dash-db-3` = `dash-core-2` - the database-busy handler
   does a blocking 5 s write on the event loop, under exactly the contention
   it is reporting, and usually records nothing** (high; three hunters found
   it, one rated it medium and the verifier upgraded it). The `4aaca6a`
   handler is `async def`, so on a `--workers 1` container the busy branch's
   synchronous second connection, INSERT and commit block the whole loop for
   another busy timeout and then raise `database is locked` themselves,
   swallowed. One heavy report holding the lock for 20 s makes the dashboard
   unresponsive for every companion and tab, and the `db_busy` notice the
   rework exists to write is the one that does not get written. `db.connect`
   already takes `busy_ms`, so the fix is small: record off the loop with a
   short timeout, or coalesce in memory and let the collector flush.
7. **`res-fleet-1` - the engine pool left the pinned-job executor unstarted
   on every boot, and jobs still get pinned into a queue nothing drains**
   (high). `PinnedExecutor.start()` was un-gated for the lazy pool, but its
   caller in `app.py:736` still reads `if executor.available():`, which at
   boot asks a pool with no engines and gets `None`. The thread is never
   created and `release_pinned_jobs()` never runs; `jobs.can_pin` asks the
   same object later, after an editor has opened an episode, and answers
   true. A spent `proxy-480p` job goes `pinned` with no worker, is not
   `abandoned`, and the DDIAG-6 check cannot see it (its shapes need "not
   mounted" or a non-empty `claimed_machine`). The boot log line "fleet jobs
   are never pinned here: Timeline Cards is not mounted" is also untrue.
8. **`dash-cards-1` - an agent whose editor is in no episode long-polls in
   a hot loop** (high). Phase 1a made `/cards/agent/pending` answer a note
   IMMEDIATELY when `_routed` finds no engine for that editor, but the
   companion's `pull_loop` has no sleep of its own; its pacing was always
   the server's 25 s hold. Every companion with the cards role on, from
   every container restart until somebody opens an episode, issues that GET
   continuously, each one a full fleet-credential check on the single-worker
   dashboard. Before the pool this path raised and the loop's backoff caught
   it; the pool turned the exception into a 200. Honour `wait` on the
   refusal path (dashboard-only); `dash-cards-8` = `wire-3` is the honest-
   signal half (a discarded push reads as healthy) and needs a companion
   release.
9. **`wire-1` - a non-409 refusal of `/items/{uid}/uploaded` wedges the
   item in `uploading` for ever** (high). `_pump_uploads` handles 200 and
   409 and logs everything else; the item stays `uploading` with all rels
   landed, so every pump re-POSTs the identical body with no attempt
   counter while the batch lease is heartbeated. This week added the first
   non-409 refusal of that route (`400 wrong_edit_proxy`, whose own comment
   says "no retry can make this right") and the companion cannot see it. A
   500 or 503 wedges identically, which is why `wire-2` (medium: the
   mounted b-roll app answers 500 where the parent answers 503 for a busy
   database) must not be fixed on its own, or a 503 the companion treats as
   terminal just moves the loss.
10. **`ytdl-web-1` - the ytdl/web suite is red from today on a hard-coded
    date, and red CI blocks the vendor feed** (high; above).
