## comp-music-ytdl-jobs-4
- Verdict: CONFIRMED (low)
- Duplicate of: none (security.md's cookie finding is about the Cards carry-on cookie's `secure` flag, a different file)
- Reasoning: `install_text` (`ytdl_cookies.py:199-201`) really is `tmp.write_text(text)` -> `secretfile.harden(tmp)` -> `os.replace`, so a live Google session exists on disk under the inherited ACL for the duration of the write. One correction to the hunter's framing: the comment says harden happens "before the rename", and it does - the comment is literally true; what is not true is the conclusion it draws ("so the secret is never briefly world-readable"). `secretfile.py` exposes only `harden(path)`, so there is no atomic create-then-write helper today, confirming the rest of the evidence. Low is right: the window is milliseconds, the file lives in the user's own `~/.ccsync`, and an attacker with read access to that directory has the hardened file a moment later anyway on posix (the ACL case on Windows is the one with real residue).
- Evidence: read `install_text` and `secretfile.py`'s three functions (`_windows_owner`, `_harden_windows`, `harden`).
- Fix note: the suggested `os.open(..., O_CREAT|O_EXCL|O_WRONLY, 0o600)` is right on posix but is a no-op on Windows, where the mode argument is ignored - the Windows half has to be create-empty, `secretfile.harden(tmp)`, then write, which is what the fix text says. `O_EXCL` also changes behaviour when a stale `.new` file exists from a killed write, so the fix must unlink it first or the install starts failing with FileExistsError. Same pattern should be applied wherever else a secret is staged this way (`cli_tools` / `<data>/secrets` are the dashboard's own, out of this file's scope).

## res-fleet-1
- Verdict: CONFIRMED
- Duplicate of: none (no dash-cards, dash-core or dash-release-jobs finding covers the boot gate; tally grep for "pinned" returns only this row)
- Reasoning: every link in the chain checks out. `mount_cards` sets `app.state.cards_engine = None` unconditionally (`cards.py:568`) and builds an EMPTY `EnginePool` (`cards.py:637`); `engine_provider`'s closure (`cards.py:326-331`) asks `pool.any_engine()`, which returns None until an episode is opened, then falls back to that same `None`. So at lifespan `executor.available()` (`cards_exec.py:166-170`, `callable(getattr(self.engine, ENGINE_METHOD, None))`) is False on every boot, and `app.py:735-752` therefore never calls `executor.start()` and never runs `db.release_pinned_jobs()`. `PinnedExecutor.start()` itself was correctly un-gated for the pool (`if not self.available() and not callable(self._engine_src): return` - the provider is callable, so it would run), which makes this a half-applied fix. `jobs.can_pin` (`jobs.py:467-480`) asks `available()` at pin time, by which point an engine exists, so rows really do go to `pinned` with no worker. High is right: rule 5 in CLAUDE.md says a job pinned into a queue nothing drains is worse than an abandoned one, and this is exactly that, silently, on every current image.
- Evidence: `grep -n "pinned_executor"` over the dashboard package finds one writer/starter (`app.py:735/751`) and readers only (`api.py`, `ui.py`, `jobs.py`); `grep -rn "release_pinned_jobs"` finds the definition and that one call site behind the same gate. `dashboard/tests/test_cards_pool.py:197` tests `any_engine()` in isolation and no dashboard test touches `create_app`'s lifespan wiring, which is why a green gate missed it.
- Fix note: the suggested fix is right - call `executor.start()` unconditionally when Cards is configured and move the boot `release_pinned_jobs()` out from behind `available()`. Two other files must move with it: `cards_exec.why_not()` (it answers "Timeline Cards is not mounted in this dashboard" for a mounted-but-empty pool, which is what makes the boot log line actively misleading), and a new test in `dashboard/tests/test_jobs_pinning.py` or `test_cards_pool.py` that drives the lifespan, since nothing pins the wiring. Do not instead gate `can_pin` harder: that would re-abandon jobs on a container where an engine is one click away, which is the regression `engine_provider` was written to avoid.

What survives is real but smaller: up to a fortnight of `reason_code=upgrading` on a machine that cannot take the build, with no reason anywhere and a push that keeps riding every reply.
- Evidence: `grep -rn "clear_machine_update_request"` -> `api.py:5264` (the DELETE route), `api.py:9484` (machine reported the version), `ui.py:4019` (admin cancel) - plus the expiry above, which the hunter's grep missed because the writer is named `expire_*`. `grep -n "update_request" alerts.py` is indeed empty, so the "nothing says why" half stands; `_check_upgrade_refused` (`alerts.py:2569`) only sees refusals the companion REPORTED, which this machine never sends.

The second half ("let the scheduler stop treating a push older than N hours as upgrading") is redundant with `MACHINE_UPDATE_REQUEST_MAX_AGE_DAYS` and would need `db.expire_machine_update_requests`' constant reconsidered rather than a second timer. A fix touches `api.py` (the report block must ask `_upgrade_info` before emitting), `alerts.ALERT_KINDS` (a new kind needs its writer registered with it - the resilience sweep's own first bug), and `dashboard/tests/test_report_endpoint.py`, which pins the current "request exists -> command emitted" shape.
