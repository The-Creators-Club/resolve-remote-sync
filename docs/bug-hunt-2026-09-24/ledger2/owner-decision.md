## bug-broll-3 - posters/sprites keyed by videos.id while the base rig and the live dashboard mint ids independently
- Status: DEFERRED (needs the owner's decision; nothing built)
- Verified as: re-read at HEAD 4462a2a. `broll/web/app/ingest_batches.py:160-161` (ItemFiles names the stills `posters|sprites/{video_id}.jpg`) and `:822-831` (claim mints the id with a plain AUTOINCREMENT insert on the live DB). `companion/src/ccsync_companion/broll_ingest.py:2900-2905` builds its upload plan as `posters/{video_id}.jpg` / `sprites/{video_id}.jpg` from the claim's video_id itself, not from a server-advertised path. `broll/web/app/routes_media.py` `poster()` / `sprite()` serve `<posters|sprites>/{id}.jpg` with no per-row path, unlike `_proxy_path`, which reads `videos.archive_path` first. `server/broll_drain.py` APPLY: "never with their old id", re-inserts every drained clip at `cur.lastrowid`, renames nothing. Verifier med-07 CONFIRMED. The broll ledger (ledger2/broll.md) deferred it for the same reason.
- The decision, in plain terms: when an editor drags clips into the b-roll page, the server gives each clip a number, and the clip's thumbnail and scrub strip are saved under that number. The base rig numbers ITS new clips from the same starting point, and the publish step renumbers the dragged-in clips without moving their thumbnails. Result: dragged-in clips show another clip's thumbnail, or none, after the base rig indexes and publishes. Pick one of these:
  - (A) Recommended. Dragged-in clips get numbers from a separate block the base rig never uses (from 1,000,000,000), and the publish step KEEPS such a number instead of renumbering, since it can never clash with a base-rig clip. Thumbnails then never need moving. Clips dragged in before this change still have low numbers, so the publish step also renames their two thumbnail files once when it renumbers them (the rename is only needed for those old clips). Cost: server-side only (broll claim + server/broll_drain.py), no companion release, no change for editors. Bonus: a companion that is still uploading a clip while a publish runs keeps posting to the right number, which the renumbering breaks today.
  - (B) Rename-only: keep today's numbering and make the publish step rename `posters|sprites/<old>.jpg` to the new number. Not safe alone (the broll builder's point): the base rig and the dashboard still collide on the same numbers before a publish, and build_archive overwrites one clip's thumbnail with another's.
  - (C) Name thumbnails by content (hash, or a digest of share + path) and store that name on the clip's row. Fixes the root cause, but the companion hard-codes the file name, so it needs a companion release, a server that accepts both names while old companions are in the field, the base rig's indexer and build_archive changed to match, and a one-off rename of the whole existing archive's stills. Largest change, most risk.
- What building (A) means, for whoever builds it:
  - broll (`broll/web/app/ingest_batches.py` claim): insert with an explicit id `max(FLEET_ID_BASE, (SELECT max(id) FROM videos WHERE id >= FLEET_ID_BASE) + 1)` instead of AUTOINCREMENT. Constant shared with the drain. `routes_ingest.py:72` (the dormant `db.mode: api` HttpBackend insert) would then continue AUTOINCREMENT from the fleet block because sqlite_sequence follows the max; it must mint below FLEET_ID_BASE explicitly, or be documented as part of bug-broll-2's fix.
  - release-tools (`server/broll_drain.py` APPLY): for a bundle video whose id is >= FLEET_ID_BASE and free in the newly published file, insert WITH that id (vmap[old] = old). For one below it (legacy fleet clips), keep today's re-mint and rename `posters/<old>.jpg` and `sprites/<old>.jpg` to the new id. The APPLY program runs inside the container, which sees the archive root, so the rename happens there, after the transaction commits (a rolled-back merge must not have moved files), and it must be idempotent (skip when the target already exists and the source does not) because a bundle may be applied twice. Refuse (and report) if the published file ever holds an id >= FLEET_ID_BASE, because that means the base rig pulled fleet rows and the two blocks are no longer disjoint.
  - build_archive: no change needed; the base rig never writes a still at a fleet-block id.
  - Skew / deploy order: server-only. Companion 0.9.77/0.9.78 take whatever video_id the claim returns and upload to `posters/{id}.jpg`, so a large id is transparent to them (check that no companion or JS path narrows it, e.g. a 32-bit field; JSON and Python ints are fine). Deploy the dashboard image first, then the base-rig tools before the next publish.
