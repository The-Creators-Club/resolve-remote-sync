## bug-comp-core-1 - A crash-loop revert does not stop the machine re-installing the build it just fled
- Mechanism (as you traced it): as the finding says. `revert_to_previous_build` wrote only `reverted_from` / `reverted_at` / `reverted_announced` into `state/upgrade_attempts.json`. `_note_report_accepted` clears that marker after the restored build's first accepted report. The per-version attempt counters were already empty, because vX cleared them by starting (`_load_upgrade_state`: record.version == VERSION). So `_upgrade_attempt_blocked(vX)` answered "" on both unattended paths (`_maybe_auto_update` and `_apply_pushed_update`). The dashboard kept offering vX, and a standing push rode every report, so the restored build reinstalled vX on its first reply. One more thing: `_on_upgrade_available` also put up an "Update available: vX" balloon right beside the "the last update kept crashing" one, which invites the click that restarts the loop.
- Fix: a separate, durable "fled" marker in the attempts ledger, `crash_looped` / `crash_looped_at` (`upgrade.CRASH_LOOPED_KEYS`). `note_reverted_from` writes it, and neither of the existing clears touches it: `clear_reverted_from` pops only the revert keys, `clear_upgrade_attempts` pops only the counters, and `note_upgrade_attempt` carries the keys across a version change. `upgrade.crash_looped_on(record, version)` matches only that exact version. `upgrade.clear_crash_looped` runs when the machine comes up ON the fled version (a person installed it by hand). `app._upgrade_attempt_blocked` returns "crash-looped" for the fled version (logged once per version), which gates both the auto-update and the pushed-update paths. A newer version is still taken, as with REL-8. `_on_upgrade_available` skips the balloon for the fled version, but the tray menu's manual Update is NOT gated, so a person can still choose it. Files: companion/src/ccsync_companion/upgrade.py (CRASH_LOOPED_KEYS near ATTEMPTS_FILENAME; note_upgrade_attempt key carry; note_reverted_from, crash_looped_on, clear_crash_looped), companion/src/ccsync_companion/app.py (`__init__` `_crash_looped_block_logged`; `_load_upgrade_state`; `_upgrade_attempt_blocked`; `_on_upgrade_available` toast).

  - `api._upgrade_info` withholds the offer when the build is this machine's stored `upgrade_reverted_from`. The check is `_fled_here`, an exact string or equal numeric version (so "+dirty" matches), and it fails open on a sqlite error. It only applies where a machine is named (the report reply, not /verify). The reason goes to `upgrade_none_reason` as `FLED_BUILD_REASON`. That existing optional key already rides the reply and every build in the field ignores it or shows it as a sentence.
  - The refusal does NOT apply to a targeted push (`pushed_here`): a push that exists after the revert is an admin choosing that build again.
  - `db.store_upgrade_state` withdraws any standing push of exactly the fled version when a report carries `reverted_from`, and logs `machine.update_push_withdrawn` to the audit ledger. The companion sends that marker once per revert, so this runs once per incident. Any push of that version that exists afterwards was made after the revert.
  - The [ UPDATE NOW ] emitter needed no change of its own: `_machine_can_be_offered` asks `_upgrade_info`, and the pre-revert push is gone before the emitter runs (the store is at api.py ~9438, the emitter at ~9700 of the same request).
  - A newer version is a different string, so it is offered as usual. Other machines are unaffected.
  - Settings > Packages: `outdated_machines[].fled_current` (computed from the guard's revert and the platform's current version). The row says "Not offered to this computer: it kept crashing on X and rolled itself back. UPDATE NOW sends it anyway. A newer build is offered as usual."
