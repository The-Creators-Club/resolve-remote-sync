### dash-core-1 - the Synology backend still follows redirects, so a 307 replays the DSM admin password
- Where: `dashboard/src/ccsync_dashboard/nas/synology.py:321-330`
  (`SynologyClient._http`), against `nas/truenas.py:112-137`, which does it
  right.
- What: CR-111 put `allow_redirects=False` plus an explicit 3xx refusal on the
  OIDC token POST and on every TrueNAS request, and CLAUDE.md states the
  invariant as "no dashboard call follows a redirect". The Synology backend was
  missed. Every DSM credential this dashboard holds rides in a POST BODY:
  `_ensure_session` posts `passwd=<DASH_NAS_PW>`, `_request` puts `_sid` and
  `SynoToken` in the body, `set_known_password` a freshly set editor password.
  `requests` strips `Authorization` across a host change but never a form body,
  and a 307/308 preserves method and body verbatim; `_json` only rejects a
  non-2xx AFTER the chain has resolved.
- Verified: measured, not argued. The verifier stood up two loopback servers,
  one 307ing to the other, and called them in exactly `_http`'s shape
  (requests 2.34.2): `body replayed:
  api=SYNO.API.Auth&method=login&account=dsm-admin&passwd=SUPER-SECRET&...`,
  `X-SYNO-TOKEN: tok-123`, `Authorization: None` - the stripped header is
  precisely why the body is the exposure.
- Why the suite is green: `tests/test_synology_client.py` stubs `_http` or the
  session entirely; nothing anywhere asserts `allow_redirects`.
- Fix: copy `nas/truenas.py:127-136` verbatim into `_http` -
  `allow_redirects=False` plus a `NasError` naming the status and the
  `Location` and saying nothing was sent on. It must go in `_http`, not
  `_json`, because `_json` only sees the resolved response. Ship the same
  one-liner in `syncthing_client._request` (dash-core-2) in the same change.

### server-tools-1 - `ship.ps1 -EmitKindExtras` fails OPEN when the dashboard reports an empty rollout
- Where: `tools/ship.ps1:540-570` (step 0a), against
  `dashboard/src/ccsync_dashboard/api.py:1499` (`_rollout_block`) and
  `db.py:4199` (`rollout_status`).
- What: the gate that is supposed to make `-EmitKindExtras` impossible until
  the whole fleet is on 0.9.55+ guards with
  `if ($null -eq $health -or $null -eq $health.rollout)`, and in PowerShell
  `$null -eq @()` is `$false`. An empty JSON array walks past the refusal, the
  `foreach` body never runs, `$stragglers.Count` is 0, and the script prints
  "every reporting computer is on 0.9.55 or newer" having checked nothing -
  while its own comment says an unparseable answer must be FALSE.
  `_rollout_block` returns `[]` on ANY exception with HTTP 200, so the fail-open
  path is reachable from a dashboard-side fault the operator cannot see. A
  second, narrower hole: the loop iterates CHANNELS, and `rollout_status` builds
  one channel per `(kind, platform)` with a CURRENT build, so a platform with
  real machines and no current package is invisible even when the array is not
  empty - the leso-Mac-on-0.9.2 shape exactly.
- Verified: `$h = '{"rollout": [], "version": "0.7.42"}' | ConvertFrom-Json` ->
  `isnull: False, count: 0, stragglers: 0`; `('{"version":"0.7.42"}' |
  ConvertFrom-Json).rollout -eq $null -> True`. The consequence is a signed
  record carrying `requires_dashboard`/`arch` that every companion below 0.9.55
  fails the signature check on and refuses permanently - no over-the-air
  recovery, a reinstall at that desk.
- Why the suite is green: `tools/tests/test_release_scripts.py` exercises
  `-EmitKindExtras` but never with an empty rollout array.
- Fix: `if ($null -eq $health -or @($health.rollout).Count -eq 0)`. The
  wire-level half matters more: `_rollout_block` must return `null` (or a
  distinguishable shape) on the exception path so "computed, nothing current"
  and "could not compute" stop sharing one representation. Do not fix only the
  PowerShell side, or an empty array refuses a legitimately fresh site and the
  refusal gets papered over with a flag the first time it bites.

### dash-collector-alerts-1 / res-fleet-3 - CR-232 mails "this has cleared. No action is needed" about footage nobody has touched
- Where: `dashboard/src/ccsync_dashboard/alerts.py:1783` (`_check_out_of_tree`,
  the `if project and not slug: continue` added at HEAD commit 40f931a),
  interacting with `alerts.py:3728-3768` (`deliver`'s RECOVERED loop) and
  `_open_subjects` at `:3809`.
- What: yesterday's commit made `out_of_tree` return no finding for a machine
  whose open Resolve project is not one of the tree's. The alert ledger is
  keyed `(kind, subject)` and the subject is still `editor/machine`, so a
  subject that stops appearing in a scan is declared RECOVERED and a "cleared"
  message goes out - and the recovery pass writes the ledger row that CLOSES
  the condition, so the next scan that does see the project raises it as NEW
  and the weekly report counts the week as clean. `_f`'s own docstring names
  this trap and offers `repeat=False` for it; the CR-232 change used `continue`.
- Verified: reproduced against a real app and report ingest - report
  `Ruskin Pangolins`, `run_cycle`, the subject is open; report
  `Wedding Video For Mum`, second `run_cycle` -> `{'recovered': 1}`. The
  verifier tried three escape routes (the `continue` precedes the append to
  `seen`; the recovery pass skips only kinds whose CHECK failed, and
  `out_of_tree` returned cleanly; `_open_subjects` groups over the whole
  `alert_log`) and none of them holds. On a machine whose editor moves between
  a fleet project and a personal one this flaps once per switch.
- Why the suite is green: the CR-232 cases at `tests/test_alerts.py:1650`
  assert `_out_of_tree(findings) == []` and never call `deliver`.
- Fix: the subject must stay in `seen`. `repeat=False` alone is not enough if
  it is implemented as "emit but do not send" - whatever path is chosen must
  add the subject to `seen` before any `continue`. The cleanest variant is to
  suppress only for a subject that has never been raised, which keeps CR-232's
  intent (silence for personal projects) without ever closing an open row.

### dash-collector-alerts-2 - `sink_deliverable` calls a channel that has NEVER delivered anything "delivered something 3 hour(s) ago"
- Where: `dashboard/src/ccsync_dashboard/alerts.py:581-584` (the `ok = 1`
  probe) against `alerts.py:3869-3872` (`run_cycle` recording the no-sink
  weekly with `ok=True`).
- What: on a site with no sink, `run_cycle` deliberately records the weekly
  report as `ok=1, detail="generated, not sent (no sink configured)"`.
  `sink_deliverable`'s "has anything actually been delivered" probe is
  `SELECT at FROM alert_log WHERE ok = 1` with no detail filter, while its
  failure probe DOES exclude `NO_SINK_DETAIL`. So the moment an admin
  configures SMTP or a webhook, the most recent `ok=1` row is that never-sent
  weekly and the helper answers True. It is the single shared answer for
  invariant 15 (`alerts_deliverable`), the protection panel's `alerts_sink`
  line and the Alerts page, so all three go green on an unproven channel - the
  one check whose whole purpose is to prove the alarm can reach a person.
- Verified: reproduced twice independently against a migrated DB. Record the
  no-sink weekly, then `set_settings(alerts_sink="smtp", ...)`:
  `sink_deliverable` -> `(True, 'the smtp channel delivered something 3 hour(s)
  ago')`. On a healthy fleet the weekly is the only thing ever sent, so the
  false green stands for a week, and up to 30 days if the next weekly is also
  missed.
- Why the suite is green: the five existing `sink_deliverable` cases never
  change the sink after a no-sink weekly has been recorded.
- Fix: record the no-sink weekly with an empty `sent_to` and add
  `AND sent_to <> ''` to the `ok=1` probe. Prefer that to a `detail LIKE`
  filter: the detail string is user-facing prose that will be reworded, and a
  green/red gate keyed on prose rots silently. The `ok=1` probe has no `kind`
  filter either, and must keep none - a HEARTBEAT row is legitimate evidence.

### broll-2 - the `client_shares.db` v1 -> v2 migration cannot run twice, and one interrupted run 500s every client link for ever
- Where: `broll/web/app/client_folders.py:150-170` (`ensure_schema`), reached
  per request from `get_shares_db` (`:213`) and at boot from
  `dashboard/src/ccsync_dashboard/broll.py:552` (`_init_broll_storage`).
- What: the v1 -> v2 step is `ALTER TABLE ... ADD COLUMN hash` ->
  `_backfill_hashes()` -> `PRAGMA user_version = 2` -> `commit()`. In CPython's
  sqlite3 the ALTER is DDL and commits immediately, while `user_version` is only
  written after the backfill, so there is a window - the whole backfill, one
  unindexed UPDATE per hashed `videos` row (broll-6) - in which the file has the
  column and still reports version 1. Any second entry re-runs the ALTER and
  raises `OperationalError: duplicate column name: hash`, which nothing catches:
  it escapes `get_shares_db` as a 500 on every client-folder route and every
  public `/broll/share/<token>/...` link, and at boot it sends the mount
  DEGRADED. Nothing self-heals; the cure is hand-editing `PRAGMA user_version`
  on the NAS.
- Verified: both hunter and verifier built a real v1 ledger with the ALTER
  already applied and drove the real module at it - `in_transaction after ALTER:
  False`, a second connection sees the column, `user_version still: 1`,
  `ensure_schema RAISED: OperationalError duplicate column name: hash`. The
  verifier knocked down the concurrency trigger (the boot call at broll.py:552
  serialises the normal upgrade) and left three that stand: a container killed
  or OOM-ed during the backfill, a deployment whose `_init_broll_storage` raised
  earlier, and the bare `broll/web` app run without the dashboard shim.
- Why the suite is green:
  `test_a_v1_ledger_gains_the_hash_column_and_is_backfilled`
  (`tests/test_client_folders.py:349-374`) drops the column and resets
  `user_version` in the same commit, so it never constructs the half-migrated
  file.
- Fix: test for the column with `PRAGMA table_info(client_folder_items)` rather
  than trusting `user_version` alone, and take `BEGIN IMMEDIATE` around the
  whole version==1 branch. Catching `OperationalError` on the message text is
  the weaker second choice - the message is not API. A `try/except` around
  `ensure_schema()` in `get_shares_db` is worth adding on its own merits (one
  bad ledger must not take the public share door out) but it must not swallow
  the deliberately fatal "newer user_version" RuntimeError. CLAUDE.md's rule
  that `publish_db.py` must never be able to take a customer's client links
  with it is the reason this is a high.

### music-1 - `allocate_name`'s collision loop has no ceiling, and both of its "taken?" helpers answer TAKEN on error
- Where: `music/web/musicweb/ingest_batches.py:236-242`, with
  `_taken_by_a_track` at `:281-296` and `_taken_on_disk` at `:265-278`.
- What: the loop's only exit is "no reserved name, nothing on disk, nothing in
  `tracks`", and both predicates deliberately return True on any error ("a query
  that cannot run counts as TAKEN, which is the harmless direction"). That
  reasoning holds only for a TRANSIENT error. For a persistent one every
  candidate answers TAKEN, `i` increments without bound, and the loop never
  returns - an infinite tight loop on a uvicorn threadpool thread, in the single
  worker process that "tells everyone whether their footage is syncing". The
  companion's HTTP timeout fires and it RETRIES, so every retry of every item
  adds another spinning thread; nothing logs, nothing times out server-side, and
  only a container restart clears it.
- Verified: the hunter reproduced it with a connection whose `tracks` query
  raises `database is locked` (`alive after 3s: True`). The verifier refuted
  that scenario's ROUTE-level reachability (an unreadable DB 500s earlier, in
  `_leaseholder_or_410`) and then found a better trigger that needs no database
  fault at all: `pathlib.Path.exists()` swallows only ENOENT/ENOTDIR/EBADF, so
  an EACCES or EIO from `stat()` propagates and `_taken_on_disk`'s
  `except OSError: return True` turns it into "taken" for every candidate. A
  music root the container's uid can stat but not traverse - the bind-mount
  ownership failure - passes `share_root_ready` whenever the index has no
  `tracks` rows yet (a fresh customer deployment) and then spins:
  `gate: (True, '')`, `_taken_on_disk('theme.mp3'): True`, `allocate_name still
  running after 4 s: True`.
- Why the suite is green: `test_ingest_batches.py` only exercises the happy
  collision path; no test drives `allocate_name` with a failing connection or a
  failing filesystem.
- Fix: cap the loop (`for i in range(2, 1000)`) and raise
  `HTTPException(503, ...)` on fall-through. Keep the two helpers returning True
  rather than raising - their contract was pinned by the 2026-09-03 music-3 fix
  - and let the cap produce the 503. This MUST land with music-2's
  companion-side classification, or the new 503 is consumed as a permanent
  track failure by every companion in the fleet.

### comp-broll-music-1 - an artifact whose local file is gone is declared as an upload but never queued, and the item, the batch and the machine wedge for ever
- Where: `companion/src/ccsync_companion/broll_ingest.py:2467-2487`
  (`_enqueue_uploads`) and `:2552-2578` (`_pump_uploads`); the same shape in
  `music_ingest.py:465-496`.
- What: `_enqueue_uploads` writes `item["uploads"] = {rel: kind for every rel in
  the plan}` and then skips the `queue.enqueue` for any rel whose local file is
  missing. `_pump_uploads` only acts on a missing rel that is ALSO in
  `queue.failures()`. A rel that was never enqueued can never land and can never
  fail, so the branch `continue`s on every tick: `upload_attempts` never
  increments, `_fail_item` is never reached, the item stays `ITEM_UPLOADING`,
  `_next_item` skips it by design, and `_maybe_finish` counts it as outstanding
  for ever and never calls `release`. The batch is never released, the heartbeat
  keeps renewing its lease so no other machine can take it, and every later drop
  on that machine gets `run()`'s 409 "this computer is already indexing another
  batch".
- Verified: both hunter and verifier reproduced it against the real
  `BrollIngestor` with the repo's own fakes, deleting `local_path` between
  describe and enqueue: four rels declared, three queued, `after 20 pumps ->
  batch held: True, stage: uploading, upload_attempts: None, released: []`. The
  verifier attacked the "something rescues it" axis and could not find one -
  `MAX_ITEM_ATTEMPTS`/`MAX_UPLOAD_ATTEMPTS` are unreachable from this state and
  `_requeue_after_restart` re-declares and re-skips the same rel - and corrected
  one fact: the dashboard's CANCEL does reach the heartbeat and frees the
  machine at the cost of the whole batch, so there is a manual escape hatch but
  not a recovery. The trigger is ordinary: a camera card indexed in place and
  unplugged, an external staging drive removed, a poster ffmpeg that produced
  nothing.
- Why the suite is green: `FakeQueue` models the failure ledger and the one-way
  stop latch, but not "it was never handed over at all".
- Fix: put a rel into `item["uploads"]` only once its `queue.enqueue` actually
  happened, and fail the item when a REQUIRED local file (the original, or
  music's single audio file) is gone. Both `broll_ingest.py` and
  `music_ingest.py` must change together. Add the belt in `_pump_uploads` too -
  a rel in neither `landed` nor `failures` for N ticks counts as a failure -
  because it closes comp-broll-music-7's dead-worker shape as well.

### dash-api-3 - [ ROLL THE FLEET BACK ] has never applied anything, and then the channel argues with it
- Where: `dashboard/src/ccsync_dashboard/api.py:6114` (`roll_fleet_back`) and
  `:6174` (`api_roll_fleet_back`), against `:8799` (the report handler's clear
  rule) and `:5493` (`_upgrade_info`); the htmx twin is `ui.py:3593`.
- What: the hunter found that `roll_fleet_back` queues a per-machine update
  request and never un-currents `from_version`, so once a machine reports the
  rolled-back build the push clears and `_upgrade_info` offers the recalled
  build again - with `auto_update` on, re-installing it unattended inside a
  minute. The verifier found the route is broken one step EARLIER and worse:
  the report handler clears a pending push when the machine reports a version
  at or past the requested one (the dash-core-6 widening), and a rollback by
  definition asks for a version BELOW what the machine is running, so
  `_version_at_least("0.9.66", "0.9.64")` is True on the very next report and
  the request is retired before `commands.upgrade` is ever emitted. This is why
  it was upgraded to high: REL-16's headline operation is a no-op with a green
  toast on every fleet.
- Verified: end to end through the app - `roll -> 200 ['jsmith/EDIT-PC']
  pending: 0.9.64`, `REPORT#1 commands.upgrade: None`, `pending after report#1:
  (cleared)`, and a machine that took 0.9.64 by hand is offered 0.9.66 again on
  report #3.
- Why the suite is green:
  `test_sweep_2026_09_04_says_what_it_knows.py:346` and
  `test_release_channel.py:495` both stop at "the request was queued" and never
  report afterwards.
- Fix: two halves, both needed. The clear rule has to learn the push's
  direction - record the version the machine was on at push time (a column
  beside `update_requested_version` in `machines`, so db.py, schema.sql, a
  migration step and `db.request_machine_update`) and clear on "at or past" only
  for an upgrade, on exact match for a downgrade. And make the fan-out and the
  channel state one operation: when `from_version` is current, make
  `to_version` current first, or refuse with a sentence telling the admin to do
  it. A guard added to `api_roll_fleet_back` only covers one door; `ui.py:3593`
  calls `roll_fleet_back` directly.

### install-onboard-1 - the macOS "installer is on a mounted volume" guard refuses every frozen wizard run from the home folder
- Where: `onboarding/steps.py:3305-3325` (`installer_on_forbidden_drive`, the
  darwin branch) with `_default_is_mount` at `:2128`; caller
  `onboarding/onboard.py:1137`.
- What: the darwin branch walks from `posixpath.dirname(sys.executable)` up to
  `/` and returns True at the first directory `os.path.ismount` calls a mount
  point. On macOS 10.15+ the user's data lives on a separate APFS volume reached
  through firmlinks, so `lstat('/Users').st_dev` is the Data volume's while
  `lstat('/Users/..').st_dev` is the sealed System volume's - which is exactly

  (`weekly_due`) and `:716-747` (`heartbeat_due`), both calling
  `db.last_alert_at(..., ok_only=False)`; the send itself at `:3868-3879` with
  `dedup=False`. `last_alert_at`'s own docstring says `ok_only` exists "because a
  send that FAILED has told nobody: suppressing the retry on the strength of it
  would be the dedup silencing the alert outright" - and both schedules pass
  False, so an `ok=0` row satisfies the slot exactly as a success does and the
  week's report is GONE, not late, against `weekly_due`'s own stated intent ("a
  container down for the whole of Monday still sends it on Tuesday"). Downgraded
  because neither half is silent in the dangerous direction: a failed weekly
  raises `weekly_send_failed` (SEV_ERROR), which stands open on the Alerts page
  and is mailed the moment the sink recovers, so what is lost is one summary
  email; and a missed heartbeat is a dead-man's switch failing towards alarm.
  Fix: `ok_only=True` in both - but ship it with a per-slot attempt ceiling or a
  backoff keyed on the last `ok=0` row, because `weekly_due` then stays True and
  `run_cycle` attempts an SMTP send on EVERY collector cycle until the next slot,
  each blocking the collector thread for the socket timeout.
- **res-fleet-5** - low (v, from medium), CONFIRMED (mechanism and reachability)
  - `collector.py:1424-1436` (the `for editor in plan_editors:` fallback in
  `_run_enforce`), fed by `db.fetch_all_selections(sync_modes=(SYNC_MODE_FULL,))`
  and filtered only by `base_only_editors` and `suspended_editors`, while the
  per-machine path immediately above is filtered by `base_machines` and by the
  FULL-mode `fetch_machine_selections`. The two routes into `desired` are
  filtered at different granularities: the fallback is per PERSON and adds EVERY
  device of a ticked editor that no machine row claims, so a machine whose tick
  is upload-only, or that is wired, is protected from it only by having reported
  a `syncthing_device_id`. Downgraded because the companion self-reports its
  device id on a refresh cycle, so a regenerated identity is re-mapped within a
  report or two; the durable shape needs a machine whose Syncthing is up and
  approved while its companion cannot read `myID`. Fix: the hunter's suggestion
  is a NO-OP as written - a known device id is already in `mapped_device_ids` and
  already excluded, and an unmapped device is by construction unattributable to a
  machine, so no per-machine predicate can reach it. What works: narrow the
  fallback to editors who have NO machine-mapped device at all (the "dashboard
  upgraded ahead of the companion" case it was written for), or keep it and emit
  the once-per-(editor, device) warning, which is the safe half and matches
  `_warned_unknown_editor` beside it.
- **res-fleet-6** - low, CONFIRMED - `collector.py:1443-1483` (`removals`
  computed from `actual`, which came from `cfg = self.client.config()` at
  `:1184`) versus `:1514-1533` (`_enforce_loop`, which re-reads
  `live = self.client.get_folder(slug)` and keeps only `existing` entries that
  are in `desired`). The blast-radius brake is computed against the snapshot
  taken at the top of the pass while the write is applied against a fresh
  per-folder read, so any device that entered a folder between the two reads - an
  admin approving a pending device through the Syncthing GUI,
  `_ensure_shared_folders` creating and sharing - is silently dropped by the loop
  without ever being counted by `enforce_max_share_removals`, recorded in
  `record_enforce_plan` or named in the "REFUSING n share removal(s)" log. The
  window is one HTTP round trip per folder and the next cycle usually re-adds a
  legitimate share, which is why it is low - but it is a hole in a brake whose
  whole job is that no unshare happens uncounted. Fix: compute the removal set
  for a folder from `live` inside `_enforce_loop`, and refuse rather than
  silently apply a folder whose fresh read disagrees with the planned `actual`.

## Cross-cutting patterns

Nine shapes account for most of the 131. A fix pass that only patches the sites
will meet them again.

1. **A fix that landed on one side of a wire, or in one of two callers.** The
   single commonest shape, and it is always the SECOND caller that is wrong:
   comp-resolve-2 (RES-15 taught `popup` about `dry_run` and not
   `consolidate`), comp-app-1 (APP-6 reproduced one of `_start_lanes`' six

   The rule the codebase already knows - "a path from a URL is checked in ONE
   place or in none of them" - generalises: put the predicate in one function
   both callers use, rather than reproducing it.
2. **An unverified state reported as a good one.** `sink_deliverable` calling a
   never-used channel proven (dash-collector-alerts-2), run.sh writing `ok: true`
