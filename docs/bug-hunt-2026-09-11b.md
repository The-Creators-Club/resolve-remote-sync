### wire-2 - `sync_guard.repath_events[].at` is a float on the companion and a string in the model: every report from a 0.9.71 machine that has had a project renamed is 422'd
- Where: `companion/src/ccsync_companion/sync/repath.py:243` (`"at": float(self._now())`) via `app.py:5050-5063` and `:6416-6418` into `guard["repath_events"]`, against `dashboard/src/ccsync_dashboard/api.py:7267` (`RepathEventIn.at: str | None`).
- What: comp-sync-4 (CR-234) put the repath ledger's events on the wire and declared `at` a string; the producer writes an epoch float. `_BoundedSectionIn`'s before-validator truncates and clamps, it does not coerce, and pydantic v2 does not coerce float to str; `sync_guard` is deliberately not one of ReportIn's tolerant sections, so the whole report fails validation.
- Failure: an admin renames a project on the server; the 0.9.71 companion repaths the folder and records an event; from that moment every 30 s report from that machine is 422'd for the life of the ledger entry. The machine goes dark on the fleet grid, and because the report reply is the only channel back it stops receiving `commands.halt`, `commands.upgrade`, file moves and the lane B resume.
- Reproduced by the orchestrator: `api.RepathEventIn(old='a', new='b', at=1757577000.5, relinked=True)` -> `Input should be a valid string [type=string_type, input_value=1757577000.5, input_type=float]`. The companion regression test for comp-sync-4 invents an ISO-string `at` the producer never writes.
- Fix: `at: float | str | None` on `RepathEventIn` (the way `TrashIn.oldest` is a float epoch) on the dashboard, deployed BEFORE any 0.9.71 companion, plus a test that feeds `repath.Ledger.record(...)`'s actual output through `ReportIn`. This is why 0.9.71 is held.

### res-companion-1 / wire-1 - the crash-resume for an interrupted file move is unreachable, and the crash now ends as a PERMANENT failed move
- Where: `companion/src/ccsync_companion/app.py:7522-7540` (the ledger gate in `_apply_file_moves`) against `file_moves.py:243-262` (`apply_move`'s new resume arm) and `:518-530` (`record_intent`); dashboard `db.py:5555-5572` (`mark_file_move_applied`) and `api.py:8411` (`FileMoveResultIn.state`).
- What: the res-companion-1 fix writes an `applying` intent row before the first filesystem call and teaches `apply_move` to finish the job on redelivery. But `_apply_file_moves` never calls `apply_move` again for that move: it short-circuits on the ledger row because `retry_due()` is False for every state except `retryable`, answers `ok=False, state=None` (it only maps `blocked`), and a missing `state` means "answered, stop asking" to the dashboard, which stamps `applied_at` and retires the command.
- Failure: the tray is killed between `src.replace(dest)` and `record()` (CR-93 abort, reboot, upgrade swap). On the next start the redelivery is answered as failed with an internal state name as the detail; the project page shows that machine FAILED for ever; the `applying` row stays, and because its state is in `recent_excludes`'s unresolved set the old path is excluded from lane A permanently. The kill-before-the-rename variant is worse: the move is never applied locally, the server is told it failed and stops asking, and the editor's copy diverges silently. Both regression tests miss it - one calls `apply_move` directly, the other monkeypatches it away. comp-sync-b-2 adds that the intent row is written with `relink_pending=True` before the file has moved, so a kill between the row and the rename lets `_relink_pending_moves` repoint Resolve clips at a path that does not exist.
- Fix: treat `STATE_APPLYING` like a due retry in `_apply_file_moves` (fall through to `apply_move`), answer `state="retrying"` until it resolves, and drive `_apply_file_moves` twice across a simulated kill in the test.

## Cross-cutting patterns

1. **Half a wire.** Six findings are a fix that landed on one process and not the other: comp-app-1 (companion answered `retrying`, dashboard still expires), res-companion-1 / wire-1 (companion learned `applying`, dashboard's vocabulary did not and the companion never reaches its own resume), dash-db-1 / res-fleet-1 (fleet route passes `from_version`, the per-machine doors do not), comp-broll-music-1 (page sends `staging_id: null`, companion needs it), music-1 (b-roll's guard grown the same morning, not ported), dash-release-jobs-3 / wire-4 (tunnel dropped the fallback older companions rely on). The rule for the next fix pass: a finding with a `Where:` on both sides of a wire is ONE builder's, never two, and the hand-off ledger must name the field.
2. **A type on the wire that no test ever produced.** wire-2's regression test invents an ISO string; the producer writes a float. Every wire test should feed the producer's real output through the receiver's model.
3. **A latch set in one thread and cleared in another** (comp-sync-b-1) and **a thread revived by its own restart fix** (dash-release-jobs-1, twice). The resilience sweep's "supervisor for every thread" rule needs its corollary: a supervisor must own a generation, never a bare flag.
4. **A gate with a new door.** dash-api-1 (roll-back bypasses `make_current_refusal`), security-1 (`_refuse_barred_account` stops at api.py), music-2 (button drawn where b-roll hides it). The docstrings already listed the doors; the fixes did not read them.
5. **A fix whose test cannot fail where it runs.** tests-1 (`ntpath.ismount`), dash-core-2 (asserts a constant), comp-app-3 (the ceiling tests pass on the backoff), comp-ui-3 (every supervisor test uses a timestamp that round-trips exactly). The macOS runner runs the companion and onboarding suites and went red once tonight already; the local gate does not run them on a Mac at all.
6. **A "green while dead" that a same-day fix created.** comp-sync-b-1 (lane B stalled, lane not red), dash-collector-alerts-1 (healthy collector reported stopped), dash-mounts-ui-b-1 (a mount that is gone reported healthy), res-fleet-3 (a refused tree never reverted, nothing says so).
