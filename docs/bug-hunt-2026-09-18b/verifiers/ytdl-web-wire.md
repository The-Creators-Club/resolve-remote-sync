# verdicts - ytdl-web-wire

## wire-2
- Verdict: CONFIRMED (and under-rated here: the same defect is filed as a HIGH)
- Duplicate of: comp-app-1 ("the remembered dashboard version is never forgotten, so a dashboard rollback 422s every report from that machine")
- Reasoning: `_note_dashboard_version` (companion/src/ccsync_companion/app.py:1331-1346) writes `app._dashboard_version` only inside `if version:` and has no `else`, so a reply with no `dashboard_version` leaves the last remembered value standing - the exact opposite of its own docstring ("an ABSENT `dashboard_version` means a dashboard older than the one that started sending it, which is the safe reading"). `_dashboard_knows_state_word` then stays latched open, and both senders of the word (app.py:8095 the ledger re-answer, app.py:8173 the fresh 4b answer) put `not_synced_here` on the wire. On a 0.7.49 dashboard that word is not in `FileMoveResultIn.state`'s Literal and `file_moves_applied` is not in `_TOLERANT_SECTIONS` (api.py:8606, which lists only proxy_coverage / youtube_import / broll_ingest / music_ingest / capabilities), so the whole report 422s; the move is never recorded applied, so it is redelivered, and the ledger arm re-answers with the same word every 30 s until the tray restarts. The 0.7.50 validator's own docstring says it "CANNOT HELP A DASHBOARD OLDER THAN THIS BUILD", which is precisely this case. I could not refute reachability: an image-mode rollback is a documented first-class operation, and `_dashboard_version` is in-memory only, so nothing else clears it.
- Evidence: read both halves; `grep -n "_dashboard_knows_state_word\|not_synced_here" companion/src/ccsync_companion/app.py` -> the gate has exactly two call sites, both senders; `_TOLERANT_SECTIONS` read at api.py:8603-8612 (file_moves_applied absent); `git show HEAD:dashboard/.../api.py` Literal has no `not_synced_here`.
- Fix note: the hunter's fix (clear, or timestamp, the remembered version when a well-formed reply carries no `dashboard_version`) is right and costs one probe report. Prefer the timestamped form: "well-formed reply" must mean a 200 report reply, not any dict, or a 4xx/5xx body would clear it and re-latch it next tick. A fix must also be reconciled with whatever the comp-app-1 builder lands in the same lines (they were unfixed when I read them), and with the companion test that pins the latch (grep `_note_dashboard_version` under companion/tests before editing).

## wire-3
- Verdict: CONFIRMED
- Duplicate of: comp-resolve-4 ("the fleet's stand-in hint is treated as conclusive about THIS machine"); wire-4 / dash-api-5 / comp-resolve-8 are the neighbouring empty-list defect, not this one
- Reasoning: `db.standins_known` (dashboard/src/ccsync_dashboard/db.py:8869-8886) is `SELECT archive_rel ... FROM broll_standins GROUP BY archive_rel ORDER BY last_seen DESC LIMIT ?` - no `editor`, no `machine`, no rel filter, no `last_seen` bound - while both sides' comments (api.py:9859-9862, proxy_relink.py:425-427) describe "the rels this machine listed" and "among the archive clips this machine listed". The call site (api.py:9870) passes only `conn`, so no intersection with the report's own `standins_placed` is possible. On the companion, `fleet_says_standin` True short-circuits `_geometry_disagrees` at proxy_relink.py:560-572 BEFORE `header_frames_fn` and before the packet count, and the caller turns that into a real ReplaceClip refresh; `apply_relinks`' own comment at :1035-1043 names the harm ("each one spending one of the 8 allow_automatic grants a day, so genuine proxy relinks are rate-limited out for the rest of it"). The wired rig holding the genuine original at a rel some remote editor once stood in for is exactly the case the feature is aimed at, so the false positive is not exotic. `_GEOMETRY_VERDICTS` is module state, so the verdict is re-learned after every companion restart; that bounds the waste per process, not per day.
- Evidence: read both SQL statements and both readers; `record_standins_placed` (db.py:8845-8867) and `standins_known` share no predicate; no age column is consulted; `_fleet_key` -> `broll_standins.archive_rel_of` is a plain NFC archive rel, i.e. fleet-global by construction.
- Fix note: the suggested fix is right in direction, but "pass the machine's own `standins_placed`" is the wrong intersection for the case the feature exists for - the wired rig's own ledger is empty for exactly these clips, which is why the fleet answer was added. The correct shape is the hunter's cheapest variant: keep the fleet True as a HINT that permits the header estimate instead of replacing it, plus a `last_seen` bound and exclusion of the asking `(editor, machine)`'s own rows. A fix touches db.py (`standins_known` signature), api.py (the call site), proxy_relink.py (the arm at :560-572) and the companion/dashboard tests that pin "True is conclusive, no probe".

## ytdl-web-1
- Verdict: CONFIRMED
- Duplicate of: none
- Reasoning: `poll()` calls `loadManifest` at exactly one site (app.js:1255) inside `if (job.phase !== 'failed')`, and the only other manifest fill is the per-tick fetch gated on `job.phase === 'downloading'` (app.js:1233-1237); `attach()` sets `state.manifest = null` (app.js:1182). `renderRetry`'s new `pending` count (app.js:1419) therefore reads an empty array in the exact state CR-286K is written for. The reload case is deterministic (hash re-attach onto a failed job: manifest null, pending 0, stalled false, button hidden). The live case is no better: the manifest the page holds was fetched at `ready_for_review`, when rows are `dl_state='none'` (db.py:699 inserts `none`; `mark_pending` only moves them to `pending` at the press), so `pending` is 0 there too unless a poll tick happened to catch phase `downloading` before the worker failed the job - which is the race the finding names. CR-286K's own ledger text (docs/bug-hunt-2026-09-18/ledger/webapps-tools.md:175) states the manifest half of the mechanism and then fixes only the offer expression.
- Evidence: read app.js 1170-1275 and 1400-1445; `grep -n "loadManifest\|state.manifest" ytdl/web/static/app.js` -> the three fill sites above; the regression test at tests/test_bug_hunt_2026_09_18_webapps_tools.py:158-165 is a source grep over `renderRetry` for the string `dl_state === 'pending'`, so it passes with the behaviour absent.
- Fix note: of the two suggestions, carry `dl_pending` on `/api/jobs/{id}` (routes_api's job payload / `db.job_dict` or the poll's counts) so `renderRetry` needs no manifest at all - it survives a 404 manifest and the reload path alike. The tolerant `loadManifest` in the failed branch also works but must not `schedulePoll()` on failure (polling is deliberately stopped there). Any fix must also replace the source-grep test with one that drives `renderRetry`'s inputs, or ytdl-web-6 stays true.

## ytdl-web-2
- Verdict: CONFIRMED
- Duplicate of: none
- Reasoning: `estimated_bytes` (routes_api.py:1407-1416) sums `r['duration']`, and a pasted row has only `video_id`/`url` (`parse_url_list`, routes_api.py:874-884), written verbatim by `create_url_job`; a `KIND_URLS` job goes straight to `downloading` with no enrich phase, so nothing fills a duration later. Both the press guard (`_refuse_if_full`, routes_api.py:1518-1568) and the worker backstop (`_no_room_note`, worker.py:1570-1593) therefore always collapse to the flat `UNKNOWN_ESTIMATE_FLOOR` of 2 GB for a paste, regardless of 1 link or 40. The ledger entry CR-286L claims to have closed "40 links into a project with 6 GB left"; it has not. The fix is real for a nearly-full disk, so this is a partial fix, not a no-op - but the scenario it advertises is still accepted on both the press and the executor.
- Evidence: run from ytdl/web with the dashboard venv: `estimated_bytes([{'video_id':..,'url':..}]*40, '1080p')` -> `0`; `need` -> 2,000,000,000; `6 GB >= need` -> True, i.e. no 409. Both new tests monkeypatch free space to 10**8 bytes, below the flat floor, so they pass with the estimate hard-coded to 0.
- Fix note: the suggested per-clip floor is right (`max(UNKNOWN_ESTIMATE_FLOOR, len(rows) * PER_CLIP_FLOOR)`), but keep it in ONE place - both callers compute `need` themselves, so put the floor in a helper both use, or worker.py:1576-1581 keeps the old number. Watch the failure direction: a per-clip floor makes the check able to refuse a download that would have fit, so pick the floor from the lowest realistic rung (`BYTES_PER_SECOND['1080p']` x a conservative clip length) rather than from `best`. New test: 40 rows, 6 GB free, expect the 409.

## ytdl-web-4
- Verdict: DOWNGRADED to low
- Duplicate of: none (ytdl-web-5 is the ordering half of the same gate)
- Reasoning: the mechanism is exactly as described - `tree_missing_note` is now consulted unconditionally at worker.py:1668-1685 and fails the job, where before `_refuse_if_the_tree_is_gone` only chose the wording of a refusal already decided on free space - but the stated failure scenario ("a project ticked on the dashboard whose folder has not been made on the NAS yet") does not survive checking. ytdl's project list is read straight from the dashboard's `projects` table (projects.py `_SQL`/`_ALL_SQL`, `active = 1`), and rows get there either from the collector walking the tree or from the create route, which `target.mkdir(parents=True)`s the folder at api.py:3621 BEFORE `_register_project` writes the row; adopt takes an existing folder. The CR-90 half is also already handled: `_named_under_the_root` NFC-normalises both sides segment by segment, so an NFD label matches. `tree_is_gone` returns False for a traversal refusal, an unreadable/absent root and any OSError, so a false positive requires the project folder to genuinely not exist. What remains is real but small: in that state the job now fails hard with a sentence that blames a lost share and points at an admin, where it used to create the folder and proceed. That is a wrong-cause wording defect plus a behaviour change, not the outage the medium rating implies.
- Evidence: read `tree_is_gone` / `_named_under_the_root` / `_refuse_if_the_tree_is_gone` (routes_api.py:1570-1670) and the new gate at worker.py:1665-1690; `grep -n "INSERT INTO projects" dashboard/src/ccsync_dashboard/db.py` -> one writer, `upsert_project`, whose callers are the collector and `_register_project`; api.py:3615-3630 mkdirs the project (and template subfolders) before registering.
- Fix note: do not add the "root contains at least one entry" test the hunter suggests - a populated tree with one deleted project folder still answers "gone", and an empty but healthy root would then disarm the guard entirely. Casefolding `_named_under_the_root` is also the wrong direction on a case-sensitive dataset (two projects differing only in case would alias). The cheap correct change is wording: when the ROOT is readable and has siblings, say "this project's folder is not in the tree" rather than "the server has lost the share", and keep the hard refusal. ytdl-web-5's reordering (the gate above `ensure_outdir`) should land with it, since both touch the same block.
