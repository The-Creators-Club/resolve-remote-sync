## Findings

### comp-core-1 — the companion installs a signed record without ever checking that it is a companion record for THIS platform and arch
- Severity: high
- Confidence: CONFIRMED
- Where: `companion/src/ccsync_companion/upgrade.py:1000` (`parse_upgrade`), `:1225` (`_accept_offer`), `:1310` (`download_and_verify`), `:1495` (`_apply_inner`); second side `dashboard/src/ccsync_dashboard/api.py:4728-4750` (`_upgrade_info`)
- What: `release_pubkey.py`'s whole stated purpose is that the signature covers `kind`, `platform` and (optionally) `arch` so that "a Mac handed a Windows exe, or an onboard installer offered as a companion self-upgrade" is impossible, and that "an offline signing key removes the dashboard from the trust chain entirely". But nothing on the companion side ever compares those fields to itself. `_accept_offer` checks only (a) the ed25519 signature, (b) `min_version > version` self-contradiction, (c) the persisted downgrade floor. `download_and_verify` adds origin pinning and transport. `_apply_inner` then renames whatever came down over the running exe. `grep -n '"kind"\|platform_key()\|arch_key()' upgrade.py` returns only the two *definitions* and the `record_fields(info.get("kind"), …)` call in `parse_upgrade` — i.e. `kind`/`platform`/`arch` are canonicalised for verification and then discarded. The only enforcement lives in `api._upgrade_info`, which is the party the signature was introduced to distrust (its own comment: "kind='companion' explicitly: the fleet must never be offered the onboarding installer as a self-upgrade -- upgrade.py would rename it over the running companion exe").
- Failure scenario: a dashboard that is compromised, rolled back, or simply buggy answers `/api/v1/report` with `upgrade` = the *genuinely signed* `onboard`/windows record (it is in the same `companion_packages` table, published by the same key, and `publish_latest.py` signs both kinds). `verify_offer` passes, the floor passes, `same_origin` passes (same host), the sha256 matches the signed hash. The companion renames `ccsync-companion.exe` to `.old`, moves `onboard.exe` into its place and launches it. `onboard.exe` does not exit within `CHILD_TAKEOVER_GRACE_SECONDS` (2 s) — it puts a wizard window up — so no rollback happens; the parent calls `request_shutdown()`. `keep_old_exe_until_healthy` on the *next* start never runs because there is no next companion start, but the Run-key autostart now launches the wizard at every logon and the machine has no companion at all. Same shape with a signed macOS record served to a Windows box (exec fails, rollback fires, then retries on the REL-8 backoff for 8 attempts) or an arm64 record to an Intel Mac (REL-16's exact symptom, which the ledger fixed dashboard-side only).
- Evidence: read of `_accept_offer` (upgrade.py:1225-1265) — three checks, none about kind/platform/arch; `grep -n '"kind"\|platform_key()\|arch_key()' upgrade.py` -> lines 145, 729, 1029 only; `release_pubkey.py:15-18` states the intent; `api.py:4728` states that the dashboard is the only enforcer. `parse_upgrade` already carries `kind` and `platform` through into `info`, so the data is in hand at the decision point.
- Ledger: new (adjacent to REL-16 / REL-4, both recorded as dashboard-half fixes; this is the missing client half)
- Suggested fix: in `_accept_offer`, after the signature verifies, refuse unless `str(info.get("kind")) == "companion"`, `str(info.get("platform")) == platform_key()`, and (when the record carries one) `info["arch"]` matches `arch_key()` or `universal2`. Refuse before `note_floor` too, so a foreign record cannot raise this machine's downgrade floor.

### comp-core-2 — macOS has no relaunch-after-abort net, and the code that declines to give it one says launchd will, which the installer deliberately made false
- Severity: medium
- Confidence: CONFIRMED
- Where: `companion/src/ccsync_companion/supervisor.py:325` (`spawn_for`'s `platform != "win32"` early return) and `:319-321` (its docstring: "frozen win32 builds only -- a source run has nothing to relaunch, and macOS has launchd"); second side `installer/macos_bootstrap.sh:2366-2392`
- What: `spawn_for` returns None on every non-Windows platform on the stated grounds that launchd covers macOS. The LaunchAgent the installer writes has `RunAtLoad` and, deliberately and with a comment saying so, **no `KeepAlive`** (and `macos_bootstrap.sh:2353` treats the *presence* of KeepAlive as a plist that must be rewritten). So on a Mac nothing whatsoever relaunches a companion that dies without reaching `shutdown()` — the precise gap CR-93's supervisor exists to close — and `crash_report.start_supervisor` reports the absence at DEBUG ("not started (source run, not Windows, or CCSYNC_NO_SUPERVISOR set)"), so there is no INFO/WARNING line on a Mac saying the machine is unprotected.
- Failure scenario: leso's Mac hits any native abort (a Tcl_Panic on the Tk dialog path, a fusionscript segfault, an OOM kill). The tray disappears; launchd does nothing because there is no KeepAlive; the machine syncs nothing until the next logon. The next start does write the `UncleanExit` crash report, so the evidence exists — but hours late, exactly the 47-minute/3-hour outage CR-93 was written up from.
- Evidence: `supervisor.py:325` `if not (sys.platform if platform is None else platform) == "win32": return None`; `installer/macos_bootstrap.sh:2366` "NO KeepAlive, deliberately"; `upgrade.py:1622-1624` states the same fact from the other direction ("the LaunchAgent is RunAtLoad-only with no KeepAlive, so nothing else will ever bring the new build up if this spawn dies with us"). `crash_report.start_supervisor` logs the None case with `log.debug`.
- Ledger: new (CR-93's fix is recorded as Windows-only without the macOS gap being stated)
- Suggested fix: either port the supervisor to POSIX (`waitpid`/`kill(pid,0)` in place of the two ctypes helpers — `decide()`, the marker, the history and `_detached_popen` are already platform-neutral), or, at minimum, correct the docstring and raise the "no supervisor on this platform" line to INFO/WARNING so a Mac's log says it is unprotected.

### comp-core-3 — on macOS a project whose rel path carries a diacritic is reported to the dashboard TWICE, once without its file list
- Severity: medium
- Confidence: PLAUSIBLE
- Where: `companion/src/ccsync_companion/manifest.py:136` + `:157` (`scan_local_manifest`); called into `companion/src/ccsync_companion/fixer.py:392-409` (`list_project_dirs`, out of territory); consumed at `dashboard/src/ccsync_dashboard/api.py:7513-7525`
- What: `list_project_dirs` builds a `set[str]` from two sources that spell Unicode differently — the local `os.walk` (macOS listdir hands back **NFD**) and `extra_rels`, which is `sequencer.rel_to_slug.keys()`, i.e. the dashboard's **NFC** selection. Its membership test for `extra_rels` is `(projects_dir / …).is_dir()`, which succeeds on APFS/HFS+ because those filesystems are normalisation-insensitive for lookups — so both spellings of the same directory land in the set as distinct strings. `scan_local_manifest` then walks both (both walks succeed, again because of APFS) and emits two `local_manifest` keys with identical rollups. `include_files = project_rel in selected_rels` is an exact string test, so only the NFC copy gets `originals`/`proxies`; the NFD copy is rollup-only. This is CR-90's mechanism at the *project-rel* level; CR-90's fix (`db.media_rel_key`) normalises `editor_media.rel_path` (per-file paths) but the project key goes through `_slug_for_rel`, not through it.
- Failure scenario: a Mac editor holds `Projects/2026/Français/Été` (any year/series/project component with a diacritic). The heavy report carries two keys for it; the dashboard writes two `editor_media_project` rows, so the fleet grid double-counts that project's originals and bytes and shows a phantom project that is not in anyone's plan. Both also consume slots against `MAX_PROJECTS`/`MAX_REPORT_PROJECTS = 64`, so on a base rig two real projects fall off the report instead.
- Evidence: `fixer.py:392` `rels: set[str] = set()`; `:401` `rels.add(rel.as_posix())` (walked, NFD on a Mac); `:406-409` `rels.add(extra)` (dashboard, NFC) guarded only by `is_dir()`; `manifest.py:157` `include_files = selected_rels is not None and project_rel in selected_rels`. Not verified on real macOS hardware (no Mac in this session) — hence PLAUSIBLE; the NFC/NFD premise is the one CR-90 measured live on `leso liaoshaoxuandeMacBook-Pro.local`, and no `unicodedata` import exists anywhere in `manifest.py` or `fixer.py`.
- Ledger: related to CR-90 (recorded FIXED at the dashboard's per-file write chokepoints only; this path was not covered)
- Suggested fix: fold both sides through `rclone_lane.nfc_key()` (the helper SYNC-3 already added) when unioning in `list_project_dirs` and when testing `project_rel in selected_rels` — comparison only, never for the path that is walked.

### comp-core-4 — a crash-loop revert exits without clearing the run marker, so the restored build files the deliberate rollback as an UncleanExit crash
- Severity: low
- Confidence: CONFIRMED
- Where: `companion/src/ccsync_companion/app.py:8785-8789` (`run()`'s crash-loop early return) vs `app.py:8527` (`crash_report.mark_clean_exit` inside `shutdown()`), `crash_report.py:610-640` (`install_native`)
- What: when `note_version_start` reports `crash_loop` and `_revert_crashing_build()` succeeds, `CompanionApp.run()` returns immediately ("Nothing has been started yet, so returning IS the shutdown") — before its `try/finally`, so `shutdown()` and therefore `mark_clean_exit()` never run. The run marker written by `crash_report.install_native` for this pid stays on disk. The restored build takes the single-instance slot after this process has exited, so `_pid_is_alive(previous_pid)` is False and the marker is not read as a hand-off: `_report_unclean_exit` writes an `UncleanExit` crash report describing a rollback the companion performed on purpose.
- Failure scenario: a build reverts itself after three fast starts; the admin opens the crash reports and sees an extra `UncleanExit` for the reverting process alongside the real ones, and the `sync_guard.upgrade.reverted_from` telemetry is duplicated by a crash file that names no fault. The supervisor is not fooled (the process exits 0, which is in `DELIBERATE_EXIT_CODES`), so this is noise rather than a relaunch loop.
- Evidence: `app.py:8785` `if start_record.get("crash_loop") and self._revert_crashing_build(): … return`; `revert_to_previous_build` is passed `request_shutdown=self._stop_event.set`, which sets an event and does not call `shutdown()`; `mark_clean_exit` is only ever called from `CompanionApp.shutdown()` (single call site, `grep -n mark_clean_exit app.py` -> 8527).
- Ledger: new
- Suggested fix: call `crash_report.mark_clean_exit(self.config)` (and `upgrade_mod.note_clean_shutdown` is *not* wanted here) immediately before the `return` on the revert path.

### comp-core-5 — a schema-relative update URL without a leading slash is never resolved against the dashboard, and is refused as a download failure
- Severity: low
- Confidence: CONFIRMED
- Where: `companion/src/ccsync_companion/upgrade.py:504-507` (`same_origin`) and `:1339-1345` (`download_and_verify`)
- What: `same_origin` returns True for any URL with neither scheme nor netloc — including `"api/v1/companion/package/windows/0.9.65"` — but the resolution step immediately below only handles the absolute-path case (`if url.startswith("/"): url = base + url`). A path-relative URL therefore reaches `self._http_open` unresolved, where urllib raises `ValueError: unknown url type`, which the handler files as `ERROR_DOWNLOAD` and REL-8 then counts as a failed attempt (10 min -> 1 h -> 6 h -> give up after 8), so a formatting slip in the offer looks exactly like an AV quarantine.
- Failure scenario: a future dashboard (or a hand-published record) serves `url` without the leading `/`; every companion reports `last_error: download-failed` and eventually `attempts >= 8`, and the Packages page shows an unreachable fleet with no clue that the URL was the problem.
- Evidence: `same_origin`'s `if not parsed.scheme and not parsed.netloc: return True  # relative -- resolved against dashboard_url below`; the resolution below is guarded on `startswith("/")` only.
- Ledger: new
- Suggested fix: resolve with `urllib.parse.urljoin(base + "/", url)` for any relative URL rather than string-concatenating only the absolute-path case, or refuse a relative URL that does not start with `/` with an explicit `ERROR_REFUSED` and a log line naming it.

## Coverage note

Not covered: `consolidate.py` (skimmed only), most of `watcher.py` (the classification loop and its debounce/ignore bookkeeping), `paths.py`, the bulk of `config.py`'s `validate_config` (~300 lines of key-by-key checks) and `set_value`/backup rotation, `ed25519.py`'s arithmetic (I did not audit the field/scalar implementation for constant-time or edge-case correctness — a bad `verify` there would be the single worst bug in this territory), and roughly 80% of `app.py` outside the report/upgrade/shutdown paths named above.

What the suite does not cover, specifically:
- `tests/test_upgrade.py` exercises signature verification, the floor, transport, origin and the swap/rollback, but has **no test that an offer of the wrong `kind`/`platform`/`arch` is refused** — because the code has no such rule (finding 1). A test asserting the current behaviour would pass while the invariant in `release_pubkey.py`'s docstring is false.
- `tests/test_supervisor.py` drives `decide()`/`main()` with injected waiters and never asserts anything about platform coverage, so finding 2 is invisible to it.
- `tests/test_manifest.py` uses ASCII project rels throughout; there is no NFC/NFD fixture in the companion suite outside `test_rclone_lane.py` (SYNC-3), so finding 3 has no guard.
- Nothing in the suite asserts that the run marker is gone after a crash-loop revert (finding 4).
- `test_no_em_dash.py` passes; I found no em dash in user-visible copy in this territory.

Verified-good (checked, no defect found): `effective_mode()` reads `config["mode"]` only, per CR-88; `site.feature_enabled` fails closed on every arm and `FEATURE_KEYS` is a real whitelist rebuilt by `normalise()` (`cards_agent` is gated by companion config, not by the site manifest, so the 0.9.3 `auto_update` shape is not repeated); `parse_version`/`compare_to_running` handle two-digit minors correctly (`(0,9,64) < (0,10,0)`); `auto_update` refuses anything not `VERSION_NEWER`; `note_floor` is monotonic and `_min_version_above_own` implements CR-52; `idle.seconds_idle` and `capabilities._idle_seconds` hold "None means cannot tell means not idle" on every path, including the 45 s capability cache which deliberately re-reads `idle_seconds`/`resolve`/`cards_agent`/`volunteer_until` on a hit; `supervisor.decide` correctly stands down on a self-upgrade (marker pid mismatch), a Quit (no marker) and `Stop-Process` (0xFFFFFFFF), and caps at 3/hour; `mark_clean_exit` refuses to delete another pid's marker; `_replaced_pid()` pops `CCSYNC_REPLACES_PID` before `start_supervisor` runs, so a relaunched companion does not inherit a stale predecessor claim; `default_http_post` refuses redirects on every dashboard call; no credential reaches a log line in `identity.py`/`reporter.py`/`upgrade.py`.
