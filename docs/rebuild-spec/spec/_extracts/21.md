# Extract of inventory section 21

## Items

### 21-001: The person looking after the server can check the whole server side in one go and see what passes, what fails and what is merely slow.
- Where: server-install-and-running / Health checks and alerts
- What: One check covers everything the server needs, and reports one pass or fail per part plus warnings that never count as failures. The count of failures is the verdict (none means all good), and the run ends with "N of M checks passed" and, when there were warnings, a line saying nothing is broken but something is slow, with each listed. A check that itself cannot run is reported as that check failing, with the reason, and the remaining checks still run. What is checked:
  - the shared Resolve project database on the NAS answers on the network (skipped, and said so, for a studio that does not use one); this proves it is reachable, not that a login works;
  - the NAS is signed in to the studio's private network, with its private addresses listed; then each other computer on that network is listed as offline, as reached directly, or as relayed. A relayed computer is a warning: every byte to it is passed through a relay, and the person is told to check that the network lets the direct path through in both directions;
  - the path from the person's own computer to the NAS is direct or relayed (a warning when relayed; skipped, and said so, when it cannot be read; never a failure);
  - the part of the server that keeps project folders in step with editors' computers answers, and lists the project folders it holds;
  - the project tree's top folder exists on the NAS (and on Synology, that the editors' access to it is in place, or a warning when it cannot tell);
  - the editors' group exists and has members, listing them ("exists but has no members yet" is a failure);
  - on Synology, that the settings for transfers to editors are within what DSM's built-in secure file-transfer server can serve (see 21-030);
  - the dashboard answers and says it is healthy; with the server's own credential supplied, also that the dashboard can see the part that keeps project folders in step, because without it the dashboard's view of that part and the setting up of new projects go stale.
  Each network check gives up after a few seconds (about 5 to 15). Computer names in other alphabets are shown as well as the screen can, never by stopping the check. A preview mode says what each check would do and checks nothing.
- Flag: several ways in: the same health of the dashboard is also checked at the end of every install or update (21-023), from the NAS's side rather than from the person's computer.

### 21-002: The dashboard on the NAS reports its own health to the NAS, so the NAS's own app list shows whether it is healthy.
- Where: server-install-and-running / Health checks and alerts
- What: The NAS asks the dashboard about once a minute whether it is healthy, allows it about two minutes to start before counting, gives each answer about ten seconds, and shows it unhealthy after three failures in a row.

### 21-003: On TrueNAS the dashboard holds a limited key for the NAS, never the NAS administrator's password.
- Where: server-install-and-running / Connections and credentials
- What: The person setting up the server creates a key on TrueNAS that the dashboard uses to manage editors' accounts and permissions, so that the administrator's password is never stored inside the dashboard on the NAS.
  - The key acts as a named, dedicated account that can do only what the dashboard needs (manage accounts and set permissions). Making it act as the administrator itself is refused unless the person deliberately asks for that, and then they are warned that the key has administrator-equivalent rights.
  - Before the key is made, the person is always told the risk that remains: even the dedicated account can reset any account's password and keys and change permissions anywhere; the key's value is only that the administrator password is not on the server, that it can be revoked by its name, and that its account can be watched. They are shown exactly which actions the key allows.
  - The person creates the dedicated account and its rights themselves in TrueNAS; the product does not.
  - The key is shown once ("TrueNAS stores it hashed and will not show it again"), with the lines to paste for the install, and a reminder of where to revoke it. It is written down nowhere.
  - The key is labelled by name in TrueNAS; a new name for each rotation lets the old key be deleted by name.
  - If TrueNAS refuses every way of making the key, the person is told not to guess and to read the NAS's own documentation. If a key was made but its value did not come back, they are told to delete it and try again.
  - On Synology this is refused with the explanation that DSM has no such keys.
  - Installing or updating the server on TrueNAS refuses without such a key, unless the studio has explicitly allowed the password to be stored; then it says that the dashboard will hold the administrator password, and how to make a key instead. With a key it says that the password is not stored.

### 21-004: On Synology the dashboard holds the password of a dedicated account.
- Where: server-install-and-running / Connections and credentials
- What: Because DSM has no keys of its own, the dashboard on a Synology holds the password of the account named for it; the person is told at every install that this should be a dedicated account that is not an administrator. Every secret the dashboard needs on a Synology is kept in a file only the NAS's administrator can read, never in the description of the app itself; a preview names the secrets without their values.

### 21-005: Secrets are never shown or left lying about without the person being told.
- Where: server-install-and-running / Settings and secrets
- What: Typing a secret directly into a command gets a warning that it may be kept in the command history. Every preview of an install masks secrets. A secret the product generates or creates for the person (a key, a password) is shown once, with that said. The connection from the dashboard to the NAS checks the NAS's certificate: when checking is switched off the person is advised to pin the certificate's fingerprint, and a pinned one is named at install.

### 21-006: The administrative web page of the server's folder-syncing service is locked behind a login.
- Where: server-install-and-running / Connections and credentials
- What: Any administrative web page the server exposes for keeping folders in step must require a login, because anyone who can reach an unlocked one is its administrator.
  - The person can ask for a report only: it shows the address, the user (or "none, unauthenticated") and whether insecure access is allowed; with no login it warns that anyone who can reach the address is an administrator, and counts as a failure.
  - Locking it sets a user (a default name is offered) and a password (generated, 28 letters and digits, unless one is given), turns insecure access off, and can restrict the address it listens on. It replaces any existing login.
  - The login is shown once and also saved in a file on the person's computer that only they can read, with a warning heading.
  - Everything that already talked to the service keeps working; its access key is not changed.
  - When the service needs a restart for the change to take hold, the person is told to restart it, and where.
  - A wrong access key and a wrong address are told apart: "a 403 means the key is wrong; a connection error means this is not the page".
  - When installing an editor's computer locks it instead, the rules are gentler: an existing login with insecure access off is left alone; when only insecure access is on, it is turned off and the existing login kept; the login file is written before the change and removed again if the change fails; and it never stops the install.
- Flag: differs: the person's own action always replaces an existing login; the one run while installing keeps it.

### 21-007: The project tree and the dashboard's own records are snapshotted on a schedule, and the person can see that this is so.
- Where: server-install-and-running / Snapshots, restoring and the server's disk
- What: The person can set up point-in-time snapshots for two things: the whole project tree, and the dashboard's own data (the studio's projects, people, computers and what each computer syncs). Each covers everything beneath it.
  - Hourly snapshots on the hour, kept 24 hours; daily snapshots at 03:10, kept 30 days. Both keep periods can be changed.
  - Setting up shows what would be done first and changes nothing until confirmed.
  - The report names the kind of NAS, the two places, and for each: either "NO snapshots found: this has no point-in-time behind it today", or how many there are and the newest with its time.
  - A listing-only mode also asks the NAS, without changing anything, whether each place can be scheduled at all; any that cannot is named with the reason, followed by "Backups are NOT fully configured", and counts as a failure.
  - Each schedule either succeeds, fails, or needs a step the person must click themselves (for example on DSM without its snapshot package). Any failure or manual step is listed and the run ends "Backups are NOT fully configured"; a clean run ends by asking the person to check again within the hour that snapshots are appearing.
  - The person can also take an immediate snapshot of both places under a name they give.
  - With no place given for the dashboard's data, the person is told that the dashboard's records then have no snapshot behind them.
  - Every install or update warns when either place has no snapshot schedule ("no snapshot floor"), and says how to check again.

### 21-008: Before anything risky and sweeping on the NAS, a snapshot is taken first.
- Where: server-install-and-running / Snapshots, restoring and the server's disk
- What: Before an install, an update, a re-creation of the dashboard, or any change of ownership that walks a whole folder tree, a snapshot of what is about to change is taken. By default this is best effort: if it cannot be made the person is warned and the work goes on. The person can ask for it to be required, and then the work stops before anything changes if no snapshot could be taken. Every such run ends by saying whether the snapshot was taken.

### 21-009: Before a destructive change the person must type the NAS's name, and every change says which NAS it is about to touch.
- Where: server-install-and-running / Installing on a NAS
- What: Every operation that changes the NAS first shows which NAS, which studio settings and which project tree it is about to work on. Re-creating the dashboard, re-applying ownership across a whole tree, and revoking an editor's access additionally ask the person to type the NAS's name to confirm (for example "About to DELETE and re-create the dashboard app; its data is not deleted"). This can be skipped deliberately; with no one to answer and no such skip, the operation is refused. A plain update never asks.

### 21-010: Every operation on the NAS can be previewed first, and says plainly when nothing was changed.
- Where: server-install-and-running / Installing on a NAS
- What: Every server operation has a preview that shows what it would do (including what it would run on the NAS) and changes nothing, ending with a line saying nothing was changed and how to apply it. Some operations preview by default and need a deliberate confirmation to act (publishing a search index, setting up snapshots, converting editors' access, revoking an editor's access); the rest act by default. Every refusal before a change says "nothing was changed" or "the NAS is untouched" in its own words.
- Flag: differs: which operations preview by default and which act by default is not consistent.

### 21-011: The person can create or repair an editor's account on the NAS.
- Where: accounts-privacy-legal / Who may sign in
- What: An editor's NAS account is what their computer uses for transfers and for the network drive. Creating it again for an existing editor repairs it in place; that is the supported repair.
  - The username must start with a letter and use only lowercase letters, digits, dot, underscore and hyphen, at most 31 characters; otherwise it is refused. Capitals are turned to lowercase and the person is told.
  - The editor's public key is required. A file that is not readable is refused; one that does not look like a key gets a warning and the work goes on.
  - The account is put in the editors' group (created if missing), given a home folder under the studio's homes folder, and allowed onto the network drive.
  - Afterwards the account is read back and checked for the key, the network drive and the group. Any gap is listed, and the person is told password login will not be turned off until it is fixed; this counts as a failure.
  - The home folder is made private to the editor, and the NAS's login service is asked whether it will accept it. A home that is blank, the root of the disk, or one of the system's shared folders is never touched; the person is told to fix the account's home and run again. If the home is not acceptable, the person is warned that the editor's transfers will fail with "unable to authenticate" until it is fixed (this does not count as a failure).
  - Password login is turned off where the NAS allows it: on TrueNAS an account with network-drive access cannot have it turned off, so login stays key-only through the login service's own setting, and the person is told; on Synology the platform manages it, and the person is told.
  - The person is given the connection details to put on the editor's computer (the NAS's private address, the username, the port, and where the key lives).
  - A preview shows all of this without reading the key or changing anything.

### 21-012: A studio can restrict editors to transfers only, with no login to the NAS itself.
- Where: accounts-privacy-legal / Who may sign in
- What: A studio can choose that editors' accounts may only transfer files and never log in to the NAS. New accounts then get no login, and the NAS's login service is set for the editors' group to allow file transfer only, with no password login (the person is told when it was installed, already correct, or must be added by hand).
  - Existing editors can be converted. This is report-only until confirmed, and refused unless the studio has chosen transfer-only (the person is told to set that first). The report lists every editor, marking those who would change, and warns that the dashboard must be updated so editors' computers learn of it, and that until each computer picks up the change its transfers report errors.
  - Applying it converts each account and reports each one; it ends "All editors are transfer-only. Update the dashboard so editors' computers learn of it."

### 21-013: The person can revoke an editor's access when they leave, and optionally lock the account.
- Where: accounts-privacy-legal / Suspending, disabling and removing a person
- What: Revoking removes the editor's key from their NAS account. Locking as well disables the account, which stops their network drive and their dashboard sign-in too.
  - The account is looked up first; a name with no account is refused.
  - It is report-only until confirmed, and then asks the person to type the NAS's name.
  - The person is told that this alone does not stop the editor's computer receiving project folders, which must also be stopped in the dashboard, and reminded to delete the key from the editor's computer.

### 21-014: With per-project access, an editor reaches only the projects they have been added to.
- Where: accounts-privacy-legal / What each person may see and reach
- What: A studio can choose per-project access (the default for a new studio): each project belongs to its own group, and an editor must be added to each project's group to reach it. Otherwise every editor reaches every project, and asking for per-project access only says so. Adding an editor to a project reports each one; a bad project name, a missing account or a failed change is a warning. Folders above a project are protected so that editors cannot remove or rename what is not theirs. Ticking a project for an editor's computer in the dashboard does NOT add the editor to that project's group yet; every install reminds the person to add each editor to each project by hand. On Synology per-project groups are only partly set up and must be finished in DSM's own user and file pages; the person is told so.
- Flag: undetermined: whether the gap between ticking and access is meant to stay.

### 21-015: The person can accept a new editor's computer for syncing and tie it to that editor.
- Where: sync / Computers joining and changing
- What: An editor's computer asks to join and the person accepts it by its device identity, naming it with the editor's NAS username.
  - An identity of the wrong shape is refused, with an example of the right shape and its length (63 characters).
  - The name must be the editor's username, not the computer's name, because the dashboard matches the computer to the editor by it and then shares that editor's ticked projects with it. With no name, or a name that does not look like a username, the person is told the computer will be unmapped and the dashboard will not manage what it receives. A username is honoured only if the dashboard already knows that editor.
  - The person is told whether the computer was found waiting; either way, the work goes on.
  - A computer already accepted is not added again; a different name renames it (a failed rename is a warning).
  - It ends by saying that the next step is ticking the editor's projects in the dashboard. Repeating it changes nothing.

### 21-016: A project can still be shared with a computer by hand, though the dashboard undoes it.
- Where: sync / What syncs where
- What: While accepting a computer, the person can also share one project folder with it by hand. They are told that the dashboard decides what each mapped editor's computer receives and may undo a hand-made share. Sharing it again when already shared changes nothing.
- Flag: dormant: kept from an older way of working, outside the normal steps.

### 21-017: The person can set up a project's synced folder on the server by hand.
- Where: sync / What syncs where
- What: For one project (given by its path at any depth under the projects folder), the server's synced folder is created or, deliberately, reconfigured.
  - Its identity comes, in order: from one the person gives; from the project's own identity on disk (which wins); or, only for a project with no identity, from its path, with advice to give the project a permanent identity.
  - Refused, with nothing changed: a project whose identity record exists but cannot be read (told to repair it or give the identity); an identity that cannot be read at all because the NAS cannot be reached or refuses (three ways out listed); a bad path or identity.
  - Refused: the identity already belongs to a folder somewhere else (both places are named, with the explanation that two different names can turn into one identity), unless the person deliberately moves it. Also refused, even when forced: another identity already points at this exact place, which is what a moved project looks like; the person is told to use that identity.
  - Behaviour of every synced project folder that a person meets: a deletion an editor makes is never carried to the server; a file replaced or deleted on the server is kept as an earlier version, thinned out over time and kept up to a year; changes are noticed as they happen and everything is re-checked hourly; half-finished downloads never travel. Reconfiguring keeps which computers it is shared with, and always re-applies the list of what never travels, so an existing folder picks up a changed list.
- Flag: built twice: the dashboard also creates these folders itself.

### 21-018: The person can create a new project's folder tree on the NAS.
- Where: server-install-and-running / Installing on a NAS
- What: A project is created at year / series / project under the projects folder, or at any depth; names with spaces are fine.
  - Inside it the standard folders are made (each reported as created or already there): AE, Audio/Music, Audio/Voiceover, B-roll, Interviewees, Render in Place, Subs, Youtube. A studio can replace this list. Proxy folders are not made.
  - Refused before anything is created, with "Nothing was created": the target is inside an existing project, or already contains a project two or more levels down (the one found is named).
  - The project is given a permanent identity, derived from its path and shown, only if it has none; an existing identity is always kept.
  - Ownership and permissions are re-applied over the whole project every time, for the editors' group (on TrueNAS group-writable with new files taking the group; on Synology through inherited access entries).
  - A snapshot of the tree is taken first and the person types the NAS's name to confirm.

### 21-019: A project's identity survives its folder being renamed or moved, and is changed only deliberately.
- Where: server-install-and-running / Installing on a NAS
- What: Each project carries a permanent identity on disk, which every dashboard record and the project's synced folder are keyed on. The person can give an existing folder an identity (adopting it) or repair a moved project. Re-writing the same identity says "identity unchanged". Changing it is refused unless forced, with the explanation of what is keyed on it and the suggestion to keep the old one. Any other information in the identity record is kept. If the existing record cannot be read, no new one is written over it. A missing project folder is refused.

### 21-020: The person can replace the live b-roll or music search index on the server with a newly built one, safely.
- Where: broll / Replacing the search index
- What: A newly built search index is published onto the server without disturbing the one the dashboard has open, and the previous one is kept. Nothing on the server moves until confirmed; the preview does every check first. In order, the person is told or refused:
  - the new index is checked for damage on the person's computer first; damaged: "Nothing was sent; the live index is untouched";
  - newer than what the deployed dashboard understands: refused, "Update the dashboard first, then publish";
  - older than the live one: refused for b-roll (the running dashboard would never update it and every new upload of footage would fail); allowed for music, which updates it itself. Either refusal can be overridden deliberately;
  - more than 10% fewer clips, segments or descriptions (b-roll) or tracks, windows or tags (music) than live: each shrinking part is listed with before, after and percentage, and it is refused unless the person says the shrink is intended (for example a prune). The threshold can be changed. If the live counts cannot be read the person is told the shrink check was skipped, normal for a first publish;
  - the copy on the server is checked to be complete and checked for damage again before it goes live; any failure leaves the live index untouched;
  - success names the new index and its size and where the previous one is kept, and how to roll back.
  The live index is only ever replaced in one step, never copied over, so a failure at any point leaves it in place.
- Flag: differs: b-roll refuses an older index and keeps what exists only on the server (21-021); music does neither.

### 21-021: Clips that arrived on the server since the b-roll index was built are kept when it is replaced.
- Where: broll / Replacing the search index
- What: Footage the editors brought into the archive through the server since the new index was built exists only in the live index. Publishing first saves those clips, with their descriptions and search data, the batches they arrived in, and which share and folder they belong to, then puts them back into the new index once it is live. A clip already in the new index is left as published; others are added, links between duplicates follow, and search results refresh. The person is told how many clips, batches and items were saved and put back. If they cannot be saved, the publish is refused (unless the person accepts the loss). If they cannot be put back, the person is told the new index is live but those clips are not in it yet, nothing is lost, and the exact step to put them back; putting them back can be repeated safely and either completes or changes nothing. The saved set is kept on the server.
- Flag: undetermined: what happens to footage that starts arriving between the save and the switch.

### 21-022: The person can roll a search index back to the previous one.
- Where: broll / Replacing the search index
- What: Rolling back puts back the newest previous index, or one the person names, and keeps the current one aside as rolled back. Refused with nothing changed: naming something that is not an index, the folder cannot be listed (told to name the previous one), or there is nothing to roll back to. The music page notices the swap by itself; for b-roll the person is told to restart the dashboard if the page does not pick it up. Every previous index and every saved set of server-only clips stays on the server; nothing removes them.
- Flag: undetermined: whether the b-roll page picks up a rolled-back index without a restart.

### 21-023: Installing and updating the server is one action, and re-running it is the update.
- Where: server-install-and-running / Updates, restarts and rollbacks
- What: One action installs the dashboard on the NAS with all its parts (b-roll, music, YouTube downloads, Timeline Cards with its editor, the Footage Sorter) or updates it. The code it replaced stays on the NAS as the way back. The dashboard's data is never deleted, even when the app is re-created.
  - A plain update only restarts the dashboard on the new code. Changes to how it is published (addresses, port, settings it starts with) need a full re-creation, which asks for confirmation; the person is told this after every plain update. A plain restart keeps the vendor build it was on; moving to a new one is asked for explicitly or done from the NAS's own app page.
  - After the restart it checks that the dashboard started properly and answers healthy on the expected version; a failure counts as a failed update. The person can ask that a dashboard that does not come back healthy is put back to the previous code and restarted.
  - A restart that fails tells the person to restart the app from the NAS's own app page.
  - A first install ends with the port and the next steps: open the dashboard on the NAS's private address, check its health, then point each editor's computer at it.
  - The NAS can be told not to download the vendor build itself, for a studio with no internet on the NAS.

### 21-024: An install refuses, before touching the NAS, whatever would leave it broken.
- Where: server-install-and-running / Installing on a NAS
- What: Each of these stops the install with the NAS untouched, and a preview reports them as "would fail" and carries on:
  - the folder chosen for the app does not have the shape this kind of NAS expects. The person can override this, and is then warned that the app's code folder there will be moved aside (not deleted) and its data left alone;
  - transfer settings the NAS cannot serve (see 21-030);
  - the project tree is not set;
  - the b-roll part is on but its upload secret is weak: under 24 characters, or a placeholder such as "changeme", "password", "token", "test", "none" (the person is told how to generate one, or to switch b-roll off);
  - on TrueNAS, no limited key (21-003); an unusable certificate rule (21-005); admins that cannot be worked out;
  - on TrueNAS, the service account the studio configured does not match the NAS's real accounts (a warning only when the NAS cannot answer);
  - on Synology, the share holding the tree is missing or unusable ("everything below depends on it").
  A part whose code is missing from the build is not a refusal: the install goes on without it, the dashboard shows that part as absent and hides its menu entry.

### 21-025: An install creates the shared folders every part needs, with the editors' group able to write.
- Where: server-install-and-running / Installing on a NAS
- What: Each install makes sure these exist on the NAS: the tree's top folder and Projects (on Synology), a shared Assets folder with the studio's shared libraries (by default LUTs and Stills, changeable per studio), the b-roll archive with folders for its previews, and the music library under Assets. On TrueNAS they belong to the service account with the editors' group able to write, and new files take the group; on Synology they are created and take the share's access entries. A failure for the shared libraries is a note that the shared LUTs and Stills may not appear; a failure for the b-roll archive or music library stops the install. Every app folder is created on every studio, whether or not its part is used, so the dashboard always starts.

### 21-026: On Synology an install grants the editors' group file transfer and runs the dashboard as the NAS's real accounts.
- Where: server-install-and-running / Installing on a NAS
- What: On Synology the install grants the editors' group secure file transfer (if this fails, the person is warned that editors' transfers will fail with "channel closed", and the install goes on), and reads the editors' group and service account from the NAS itself to run the dashboard as them, saying which. The heavy extras (about 1.4 GB of music search data and the video tools) are not sent to a Synology unless asked for.

### 21-027: Music search data is sent to the server only when it is missing there, unless asked otherwise.
- Where: music / Keeping the library's data whole
- What: An install sends the music search pieces the NAS lacks: the index, the text-search model (about 482 MB) and the music previews (about 906 MB). The person can send all, none, or chosen pieces. They are told what will be sent and the total, or that nothing needs sending; pieces missing on their own computer are noted. With no music data at all they are told the music page will open empty and search will fail.

### 21-028: The install tells the person when a part is half set up.
- Where: server-install-and-running / Settings and secrets
- What: Notes, never refusals, at install:
  - YouTube downloads on with no assistant key: the YouTube page will report that it has no working key until one is set;
  - YouTube's anti-blocking extras on without YouTube downloads: nothing is set up for them;
  - Timeline Cards' editor asked for while Timeline Cards is not going out: the editor stays off; Timeline Cards on with no place for its data: it will serve nothing; a media folder without a mapping, or the reverse: neither does anything;
  - the Footage Sorter: switched on with no pool; cloud-state or backup folders that are not full paths on the NAS, or set without a pool; a cloud-state folder inside the pool (not used); no source or destination folders; any folder outside the pool, because a move between disks would fail.
  The parts each studio switches on are carried into the dashboard at install.
- Flag: dormant: YouTube anti-blocking, assistants run as programs on the NAS, and unattended updates are off unless a studio turns them on.

### 21-029: The Footage Sorter's backup folder and time zone are set up at install.
- Where: footage-sorter-and-camera-cards / Backed up and safe to format
- What: When the studio names a backup folder, it and its two inner folders are created only if missing, owned by the named person with the editors' group; an existing folder is left alone (an empty one owned by the system is given that owner). The Sorter's daily jobs run at 04:00 and 04:30 in the studio's time zone: taken from the studio's settings, else read from the NAS; if neither is known the person is told the jobs will run on universal time.

### 21-030: DSM's built-in file-transfer server cannot serve large transfer windows.
- Where: server-install-and-running / NAS speed, load and clock
- What: Fact about Synology: DSM's own secure file-transfer server cannot serve transfers that use large pieces or many at once. Transfers to and from editors on a Synology must stay within 64 KiB pieces and 16 at a time. Settings above that are refused at install and fail the health check, which tells the person the values to use, to update, and to fetch again any proxy over 514 MiB that came down under the wrong settings.

### 21-031: Facts about each kind of NAS that the person setting up meets.
- Where: server-install-and-running / Installing on a NAS
- What:
  | | TrueNAS | Synology (DSM) |
  |---|---|---|
  | Limited keys for the dashboard | yes, labelled by name, shown once | none; a dedicated account's password |
  | Turning off password login for an account with network-drive access | refused by TrueNAS; key-only through the login service | managed by the platform |

  | Folder permissions | owner, group and group-writable with inherited group | inherited access entries from the share |

### 21-032: The dashboard's recovery page can read the NAS's snapshots when the install can find them.
- Where: server-install-and-running / Snapshots, restoring and the server's disk
- What: At first install or re-creation, the install looks for where the NAS keeps the project tree's snapshots and, when the NAS confirms that place exists, lets the dashboard read it (read-only) for its recovery page. When none is found the person is told the recovery page can only print commands, and how to name the place. When one is found they are told how to check the dashboard really sees snapshots there, because an empty view makes the recovery page report every project missing.

### 21-033: The Resolve shared project database on the NAS gets a password once, which each editor enters once.
- Where: resolve-on-the-editors-computer / Project libraries and projects
- What: On a Synology install, the shared Resolve project database's password is generated once and kept on the person's computer; an existing database is re-keyed to it when it starts. The person is told it must be entered once in each editor's Resolve database entry, and that the database is only reachable on the studio's local network and private network addresses. A studio can say it does not use the shared database.

### 21-034: The person is told exactly which version of Timeline Cards and the Footage Sorter went onto the server.
- Where: releases-and-updates / The server updating itself
- What: Each install names the version of Timeline Cards and of the Footage Sorter it put on the server, and whether newer work exists that was not sent. Uncommitted or new files are listed (the first six and a count) as not being in this install. An install that would leave an empty part, or names a version that does not exist, is refused before anything moves. A record of what went out is kept on the server and on the person's computer.
- Flag: dev only: this belongs to the vendor building from working copies, not to a studio installing the vendor's build.
