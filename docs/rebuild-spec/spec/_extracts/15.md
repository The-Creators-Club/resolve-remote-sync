# Extract of inventory section 15

## Items

### 15-001: An admin chooses where the server's alerts go: nowhere, by e-mail, or posted to another service.
- Where: dashboard / Alerts by mail
- What: An admin sets the alert destination for the whole site: none (the default), e-mail, or a web address of another service that each message is posted to (a subject and a text). Any other choice is refused, with a message naming the three that are allowed. These settings are never handed to editors' computers or their installers. With no destination set, problems are still found and still shown on the dashboard and in its count of open problems; they are written down and nobody is told.

### 15-002: For e-mail alerts the admin gives the mail server, its port, a sign-in, a sender and one or more recipients.
- Where: dashboard / Alerts by mail
- What: Settings for e-mail: the outgoing mail server's host name (no default); its port (default 587; must be between 1 and 65535, refused with "must be a port number between 1 and 65535"; may be left blank); the sign-in name; the sender address; one or more recipient addresses separated by commas or semicolons; whether the connection is encrypted (on by default; off sends unencrypted); and whether the mail server's certificate and name are checked (on by default; off is an explicit choice for a studio's own internal mail server with its own certificate). A certificate that fails the check never falls back to sending unchecked; the admin is told "the certificate <host> presented could not be verified (...). If this is your own mail server with its own certificate, turn off 'Verify the mail server's certificate' on this page."

### 15-003: The mail password is entered once, never shown back, and can be supplied at install instead.
- Where: dashboard / Alerts by mail
- What: The admin types the mail account's password. It is kept apart from the other settings and readable only by the server. A blank password is refused ("the password is blank"), as is one over 400 characters or one containing control characters ("the password contains control characters, paste it again"). If it cannot be saved, the admin is told which folder on the server must be writable. Clearing it deletes it. The page only ever shows whether a password is set, where it came from, and a mask (its first 3 and last 4 characters; under 12 characters, only "..."). A password supplied when the server was installed overrides the typed one, and the page says the value came from the deployment.
- Flag: several ways in: typed by an admin on the dashboard, or supplied when the server is installed (the installed one wins).

### 15-004: A destination web address for alerts must be encrypted, and is shown masked.
- Where: dashboard / Alerts by mail
- What: The address another service receives alerts at must start with https://, or the save is refused: "the webhook URL must start with https:// (an alert body names your editors and computers)". It is checked again each time a message is sent. The page shows it masked after its site part ("https://host/..."), because the rest of the address works as a password; saving the form back with the mask unchanged keeps the stored address. Only the site part is ever recorded in the history of what was sent. The server never follows a redirect from that address.

### 15-005: An admin sets the time zone the alert schedules run in.
- Where: dashboard / Alerts by mail
- What: The weekly report, the daily "still here" message and the daily server check run in the site's time zone. An admin types a standard time zone name; an unknown one is refused: "'X' is not a time zone this server knows (use a name such as Europe/London)". Left blank, it follows the site's general time zone if one is set, otherwise UTC. If the server cannot use the zone at run time it quietly falls back to UTC for the schedules (nobody is told).

### 15-006: Every alert setting is checked before any is saved, and one bad field changes nothing.
- Where: dashboard / Alerts by mail
- What: A save is all or nothing: every field is checked first. Every value is refused if it contains control characters ("must not contain control characters") or is over 400 characters. Yes/no settings take on, off or blank (blank means off). A setting the server does not know is refused ("'X' is not an alert setting").

### 15-007: When an alert destination is set for the first time, everything already open is sent as a catch-up.
- Where: dashboard / Alerts by mail
- What: Problems found while no destination was set are not lost. When the admin first sets a destination, every problem still open is raised again on the next check, and the next combined message opens "CC Sync: here is everything currently open (N)" and says it is the catch-up, not N new faults.

### 15-008: An admin can switch off individual kinds of alert without switching off the check.
- Where: dashboard / Alerts by mail
- What: The admin sees every kind of alert, grouped as: editors' computers; sharing and studio-wide controls; this server; updates; projects and footage; shared work; YouTube downloads; b-roll; and can switch any of them off. A kind added by a later version is on until switched off. A switched-off kind is still checked and still shown among the open problems, in the weekly report and in the count of open problems; only the message is withheld. Switching it back on sends a still-true problem as new. An open problem of a switched-off kind that clears is closed without a message. Switching a kind off also silences "that check could not run" for it; "the whole scan failed" is always sent. A name that is not a kind of alert is refused ("not an alert kind: ...").

### 15-009: The product tells the admin whether the alert channel is actually working.
- Where: dashboard / Alerts by mail
- What: The channel is shown as working (green) only when a destination is set, it has delivered something to someone in the last 30 days, and the most recent failure is older than the last success. Otherwise it is shown red with one of: "no mail server and no webhook is set, so nothing this server finds is ever sent to anybody"; "the e-mail channel is set up and has never managed to send anything: ..."; "the e-mail channel is set up but nothing has ever been sent through it"; "the last message this server tried to send did not go out: ..."; "nothing has been delivered through the e-mail channel since YYYY-MM-DD". Green reads "the e-mail channel delivered something N hour(s) ago" (the channel is named by what it is: e-mail or the other service). After each check the server's status also says how many alerts were sent, that some could not be delivered, that the channel is slow ("S of T alert(s) sent this check; the alert channel is slow"), or, with no destination, "N alert(s) were written down here and nobody was told: no alert channel is set up". This same fact is one of the facts re-checked on a schedule (15-096) and also stands as a problem on the dashboard while no destination is set (15-078).
- Flag: several ways in: the channel status, a standing problem on the dashboard, and the re-checked fact all say the same thing.

### 15-010: An admin can send a test message through the alert channel.
- Where: dashboard / Alerts by mail
- What: There is a "Send a test" control for the alert destination; many fix lines point the admin at it to time the channel or prove it works. A successful test also clears the "weekly report could not be sent" alert.
- Flag: undetermined: the control and its wording are not described in this part, only referred to.

### 15-011: The server checks for problems about every ten minutes, with or without a destination.
- Where: dashboard / Problems the server finds
- What: About every ten minutes the server checks every kind of problem it knows, then sends what is owed, then sends the weekly report and the daily "still here" message if they are due, then starts the daily server check if it is due. It checks whether or not a destination is set. The number of open problems (serious and less serious) from the last check is shown on every dashboard page and in the server's public health answer.

### 15-012: A check that cannot run is reported as unchecked, never as fine.
- Where: whole-product / Could not check, refusals and nothing silent
- What: If one kind of check fails, that is itself a serious problem, "a health check could not run", naming the check: "The check for '<what>' could not run, so this server does not know whether that is all right. Treat it as unchecked, not as fine." Fix: send the server's own log from the NAS to support. If the server cannot even read its own state, one problem is raised for "the whole scan": "This server could not read its own state to check whether anything is wrong, so nothing below has been checked." On such a check no open problem is declared cleared. A check that starts working again is declared cleared.

### 15-013: No more than 40 problems of one kind are listed at once, and the rest are counted.
- Where: dashboard / Problems the server finds
- What: Each kind lists at most 40 problems per check. Beyond that one more entry, "and more of the same", says: "There are N of these and this server shows the first 40. The other M are real and are not listed here." Fix: "Open the dashboard and work through the list: something fleet-wide is usually behind this many at once." Problems not listed because of the cap are never treated as cleared.

### 15-014: A serious problem is mailed once a day while it lasts; a lesser one is mailed once.
- Where: dashboard / Alerts by mail
- What: Each kind of problem is either serious (an error) or something to look at (a warning). A serious problem is sent when first found and then once a day for as long as it stays true. A warning is sent once and not again until it has cleared and come back. Some problems are said once only while they stay true (named on the kinds that do this). A failed send counts as sent for this rule, so a broken channel is not retried every ten minutes.

### 15-015: When a problem goes away, the people told about it are told it cleared.
- Where: dashboard / Alerts by mail
- What: An open problem that a working, uncapped check no longer finds is declared cleared, with the message subject "CC Sync: cleared - <title> - <subject>" and body "This has cleared on its own or somebody fixed it. No action is needed." Whether a problem is open survives a server restart. When a computer stops reporting what a check looks at, an open problem about it is closed without any message ("closed without a message: that computer no longer reports what this checks").

### 15-016: Each alert message says what is wrong, what to do, and the technical detail.
- Where: dashboard / Alerts by mail
- What: When messages are sent one per problem, the subject is "CC Sync: <title> - <subject>" and the body is the diagnosis, then "What to do: <fix>", then "Detail: <technical line>", then "Open the CC Sync dashboard for the full picture." A body is cut at 60,000 characters. Wherever a text says "send us ...", the site's support contact is added when the site has one; this holds for alerts, combined messages, the weekly report and the server check.

### 15-017: By e-mail, everything one check finds goes out as one combined message.
- Where: dashboard / Alerts by mail
- What: By default e-mail gets one combined message per check and another service gets one message per problem; an admin can force either way. The combined message's subject, in order of priority: the catch-up ("CC Sync: here is everything currently open (N)"); new problems ("CC Sync: 1 new problem: <title>" or "CC Sync: N new problem(s)"); only repeats ("CC Sync: still not fixed after D day(s): <first two headlines> and K more"); only clearances ("CC Sync: cleared - <headline>" or "CC Sync: N problem(s) cleared"). The body lists serious problems before warnings. New problems appear in full under "PROBLEM:" (serious) or "TO LOOK AT:" (warning). Repeats are one line each under "STILL NOT FIXED" with "(open for D day(s))", then "The full description of each of these went out when it was first found. Nothing about them has changed." Clearances appear under "CLEARED:". Then "Still open from before: N (see the HEALTH page)" when warnings or say-once problems are still open. Days open count from the first alert after the last time it cleared, at least 1.

### 15-018: Sending alerts never holds up the server; what cannot be sent in time waits for the next check.
- Where: dashboard / Alerts by mail
- What: One check spends at most two minutes sending, and each single message gives up after 20 seconds. Anything not sent in time is sent at the next check (a combined message goes whole or not at all). When that happens a standing warning is shown: "Sending this server's alerts took longer than the 120 seconds one check is allowed, so N of them were left for the next check. ..." with the fix "On Settings, Alerts: press "Send a test" and time it. ...". It clears on the first check that sends everything. No failure to deliver ever stops the server checking.

### 15-019: A failure to deliver is named in plain words.
- Where: dashboard / Alerts by mail
- What: Failures shown in the history of what was sent: for another service, "no webhook URL is set", "the webhook URL must be https", "the webhook answered HTTP N", "could not reach the webhook (...)"; for e-mail, "no mail server is set", "e-mail needs a sender address and at least one recipient", the certificate message (15-002), "the mail server refused the sign-in" (the mail server's own reply is never repeated, since it can carry the password), "could not send through <host> (...)". With no destination, each message is recorded as not delivered because none is set.

### 15-020: A weekly report on the whole studio goes out every Monday at 08:00.
- Where: dashboard / Alerts by mail
- What: On by default; an admin can switch it off. Sent Monday at 08:00 in the site's time zone, staying at 08:00 across daylight-saving changes. If the server was down all Monday it is sent when it comes back, and a restart never sends it twice. A failed send is retried after 10 minutes, then an hour, then 6 hours. With no destination it is still put together and recorded as made but not sent, which is not a failure. Subject: "CC Sync weekly: N computer(s), E problem(s), W thing(s) to look at". Body, in order: "Fleet health for the week ending <now>." and "N computer(s) reporting."; "PROBLEMS (n)" and "THINGS TO LOOK AT (n)" with every open problem's diagnosis, fix and detail, or "none."; "BUILDS": how many computers run each version ("<version>: 6 of 8 computers"), then each out-of-date or unknown computer ("<who> has been on <build> for <span>; current for <platform> is <version>"); "WHAT CHANGED THIS WEEK (n entries)": up to 40 lines from the history of changes, then "... and N more on the TIMELINE page." or "nothing."; "ALERTS SENT THIS WEEK": up to 50, failures marked "(SEND FAILED: ...)"; "JOBS: q queued, r running, a abandoned this week"; the standing list of what is protected, or "WHAT IS PROTECTED: this section could not be read this week. Treat it as unchecked, not as fine."; "RECOVERABLE FILES IN .ccsync-trash" with each computer's size and file count of recoverable deleted files; "CHECKED AND FOUND NOTHING WRONG (k of N)" with "ok - <what>" per clean check, then "COULD NOT BE CHECKED (n)"; "NOT SENT AS ALERTS (n, switched off on Settings, Alerts; still checked and listed above)" with "off - <what>" per switched-off kind; and the closing line "This report is composed from what the dashboard already knows. Anything it could not read is named above rather than left out."

### 15-021: The weekly report would list bytes moved per computer, but never does.
- Where: dashboard / Alerts by mail
- What: A section of the weekly report giving how much data each kind of transfer moved per computer exists only on paper; the product does not record that figure, so it never prints.
- Flag: unreachable

### 15-022: An admin can ask for a daily "still here" message so that silence means the server is down.
- Where: dashboard / Alerts by mail
- What: Off by default; only sent when a destination is set. Once per calendar day in the site's time zone, retried after 10 minutes, an hour, 6 hours if it fails. Subject "CC Sync: all quiet - N computer(s), E problem(s)" when nothing serious is open, otherwise "CC Sync: still here - ...". The body explains "IF THESE STOP ARRIVING, THE SERVER ITSELF IS DOWN", lists computers known, problems open and things to look at, and says how to turn it off (on the dashboard, alert settings, the daily "still here" message). It is never itself a problem, never "cleared", never among the open problems.

### 15-023: An admin can see what was sent, message by message.
- Where: dashboard / Alerts by mail
- What: The history of what was sent is grouped by the message each problem went out in, with a count of problems in each message and whether all of them were delivered. The dashboard also lists everything currently open.
- Flag: undetermined: the screens themselves are not in this part, only what they group and count.

### 15-024: Admins are told when a computer has gone quiet for a day.
- Where: dashboard / Problems the server finds
- What: Serious. Raised when a computer has never reported, or last reported 24 hours or more ago. "<who> has not been in touch since <age>. Everything this dashboard shows for that computer is frozen at that moment, so a green row there means nothing right now." Fix: "Ask that editor to check the CC Sync tray icon is running and that the computer is on and online. If that computer is gone for good, open Sync status and press "Forget" on its row so this stops." After 14 days of silence it is said once more and no longer daily; it stays open, and the standing problem for a long-gone computer (15-084) takes over.

### 15-025: Admins are told when a computer has been showing a problem for an hour and nothing more specific explains it.
- Where: dashboard / Problems the server finds
- What: Serious, "a computer is not syncing". Raised when a computer has been shown red for an hour or more and no other kind of problem named it in the same check. The text is the computer's own "why" sentence (15-110), or "<who> has been showing a problem for <duration> and this dashboard cannot say which. It is not syncing normally.", followed by " Nothing more specific could be worked out from what that computer has reported." Fix: "Open that computer's row on the Sync status page and press "Ask this computer why", then send us the diagnostics it returns."

### 15-026: Admins are told when proxy download has stopped itself on a computer.
- Where: sync / Safety stops
- What: Serious, "proxy download stopped itself". Raised when a computer reports that its download safety stop has tripped. "Proxy download has stopped itself on <who>, <age>. Until somebody clears it, that computer gets no new proxies, so the editor cannot see anyone else's footage. Uploads from it are still running and nothing has been deleted." Fix: press "Resume" on that computer's row, after checking the server looks right.

### 15-027: Admins are told when a computer has stopped its own downloads because its drive is nearly full.
- Where: sync / Disk space
- What: Serious, "a computer stopped its own downloads for space". Raised when the computer reports it stopped proxy download for lack of space. "<who> has stopped its own proxy download because the drive is nearly full (X free). ..." Fix: clear space, or untick a project.

### 15-028: Admins are told when a computer's sync drive is running out of space.
- Where: sync / Disk space
- What: Serious, "a computer is running out of space". Raised when the computer's drive is in the red by the disk rule (15-108, using the computer's own stopping point), the computer is not a wired machine, and (when known) it holds at least one project ticked for full sync. "<who> has X free on its sync drive (P percent). Proxy download fills a drive file by file, and the recoverable-files bin cannot be cleared while the brake is on, so this ends with that editor unable to work."

### 15-029: Admins are told when syncing has been down on a computer for an hour.
- Where: sync / Saying truthfully what the sync is doing
- What: Serious, "syncing is down on a computer". Raised when the computer has reported its syncing down for an hour or more; never for wired machines. "Syncing on <who> has been down for <duration>. ..." Fix: quit and restart CC Sync from the tray, and send diagnostics if it happens again. The detail names how many times the computer tried to restart it and the last error.

### 15-030: Admins are told when a transfer on a computer is stuck.
- Where: sync / Stuck, slow and fair transfers
- What: Serious, "a sync transfer is stuck". Raised when a computer reports a transfer stuck and it is still stuck (15-107). The text is the computer's "why" sentence plus "A drive that has stopped answering reads exactly like this, and the other transfers on that computer wait behind it." Fix: restart CC Sync and check the drive opens.

### 15-031: Admins are told when a kind of transfer on a computer has been failing for an hour.
- Where: sync / Saying truthfully what the sync is doing
- What: Serious, "a sync transfer has been failing". Raised when any kind of transfer on a computer has been in a failed state for an hour or more; the subject names the computer and the kind of transfer. "<kind of transfer> on <who> has been failing for <duration>. ..."

### 15-032: Admins are told when the server is turning a running computer away.
- Where: dashboard / Reports from computers
- What: Serious, "a computer is being turned away". Raised when the server has refused a computer's reports. "<who> IS running and IS trying to report, and this server is turning it away (<age>). ..." Fix: "Ask that editor to click Sign in on the CC Sync tray on that computer."

### 15-033: Admins are told when a computer's clock is five minutes or more out.
- Where: sync / Clocks and file age
- What: Serious, "a computer's clock is wrong". Raised when a computer's clock is 5 minutes or more ahead of or behind the server's. The text explains that proxy download only takes files past a minimum age, so a clock this far out makes it transfer nothing at all while reporting no error. Fix: turn on setting the time automatically on that computer.

### 15-034: Admins are told when a shared folder on a computer has no filter, so originals would travel both ways.
- Where: sync / Files that must never sync
- What: Warning, "a shared folder has no filter". Raised when a computer reports shared folders with no filter keeping originals out, unless every one of them was ticked for that computer within the last 30 minutes (a fresh tick is unfiltered for a short while by design). "N shared folder(s) on <who> has/have no ignore filter written yet. Without it, that computer will carry camera originals in both directions over the internet instead of proxies only."

### 15-035: Admins are told when the app on a computer keeps restarting its work or has crashed.
- Where: editor-app / Starting, staying running and crashing
- What: Two warnings. "CC Sync keeps restarting itself": the app restarted parts of its own work 3 or more times in 24 hours; fix: use the app's diagnostics button and send the result. "background tasks have crashed": the computer has any crash reports.

### 15-036: Admins are told when a file move was never confirmed by a computer.
- Where: proxies-and-file-moves / Moves that reach every computer
- What: Warning, "a file move was never confirmed". One entry per computer and old path whose move request ran out unconfirmed (first 40), subject "<computer> <old path>". Fix: run "Move on the server and on every computer" again once that computer is online. Moves owed by computers the server no longer has are grouped as one entry, "computers this server no longer has".

### 15-037: Admins are told when "Send to Resolve" cannot work on a computer.
- Where: editor-app / Telling the editor what is wrong
- What: Warning, "Send to Resolve cannot work on a computer". Raised when the computer reports that the local connection the browser pages use to reach it is switched on but could not be opened, usually because something else on that computer holds it. Fix: quit whatever holds it (an old b-roll helper, a leftover process), then restart the CC Sync tray.

### 15-038: Admins are told when a computer reaches the dashboard unencrypted over the internet.
- Where: accounts-privacy-legal / How secrets and keys are kept
- What: Serious, "a computer reaches this dashboard unencrypted over the internet". Raised when a computer's last report arrived unencrypted from a public internet address. Unencrypted over the studio's own network or private network is never raised. It repeats daily only while that computer has reported in the last 24 hours; otherwise it is said once. Fix: serve the dashboard encrypted on the private network, set the encrypted address in the tray, update CC Sync, or forget that computer.

### 15-039: Admins are told while a studio-wide stop is on, and when one ran out by itself.
- Where: sync / Studio-wide stops and the editor's pause
- What: Warning, "syncing is stopped for the whole fleet", while an admin's studio-wide stop is in force and not expired; fix: "Start syncing again" or "Keep it stopped". Warning, "a fleet-wide stop expired by itself", for 24 hours after a stop's expiry time.

### 15-040: Admins are told when the server refused a sharing change that would unshare too many computers at once.
- Where: sync / Safety stops
- What: Serious, "a sharing change was refused". Raised when the server held back a change that would stop sharing folders with too many computers at once. The standing problem says how many removals were held back over the limit and lists the folders, with the fix: check no computer was renamed or removed, then press "Apply these removals", or raise the per-computer allowance under the sharing safety settings. While the hold is in place, each computer still being sent a project nobody has ticked for it is listed as its own warning (up to 20): "This computer is still being sent a project that nobody has ticked for it...". All of these clear when the hold clears.
- Flag: built twice: both a mailed alert and a standing problem say this, with different wording.

### 15-041: Admins are told when the server refused to mark many projects gone at once.
- Where: sync / Deletions and removing a project
- What: Serious, "a mass project deactivation was refused". Raised when too many projects disappeared from the server's tree at once; N projects looked deleted in one check, over the limit, so none were marked gone.
- Flag: built twice: both a mailed alert and a standing problem.

### 15-042: Admins are told when a sharing change is waiting to be applied.
- Where: sync / Safety stops
- What: Warning, "a sharing change is held". Raised when there is a worked-out sharing change with at least one folder to add or remove that has not been applied. An empty change raises nothing.

### 15-043: Admins are told when computers are still on an old sign-in key a week after it was changed.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: Warning, "computers are still on the old sign-in key". Raised when computers still identify with a replaced server key 7 days or more after it was replaced.

### 15-044: Admins are told when the server's own syncing is not answering.
- Where: server-install-and-running / Health checks and alerts
- What: Serious, "the server's syncing is not answering". Raised when the server cannot reach its own syncing; shown as a standing problem too, cleared when it answers again and left as it was when the server cannot tell. Not raised on a site that has no such syncing.
- Flag: built twice: a mailed alert and a standing problem.

### 15-045: Admins are told when the server's own data space is running out.
- Where: server-install-and-running / Snapshots, restoring and the server's disk
- What: Two checks on the dashboard's own data space. Serious, "the server is running out of space", mailed, when under 10 percent is free; if free space cannot be read, the check counts as one that could not run. Serious standing problem when under 2 GB is free, or free space cannot be measured ("That is not the same as knowing it is fine."); fix: delete old builds from the published packages, or enlarge the volume.
- Flag: differs: one check fires at under 10 percent, the other at under 2 GB, with different wording.

### 15-046: Admins are told when the project tree on the server is missing or empty.
- Where: server-install-and-running / Shares that go away, and checks that cannot run
- What: Raised as serious in three places with three wordings. The mailed alert, "the project tree is missing": the projects folder "is not there at all" or "is there but completely empty"; not raised when no projects folder is configured. The standing problem: the folder cannot be read (naming the system's error), is not there, or is empty, "which normally means the storage is not mounted... Nothing has been marked as deleted."; it clears for every path once the folder is healthy. The re-checked fact: the tree is readable and not empty (empty counts as broken); when fine it says how many top-level entries there are and how many are projects. While the tree is not healthy, nothing is marked deleted.
- Flag: built twice: three checks of one fact, each with its own wording.

### 15-047: Admins are told when a project's file figures could not be refreshed.
- Where: dashboard / Projects
- What: Serious standing problem, one per project, raised when the server was refused while listing a project's files: "The figures on that project's page are the last good ones". The fix mentions "Move on the server and on every computer" if the project was renamed. Only checked when the projects folder itself is healthy.

### 15-048: Every serious standing problem is also mailed.
- Where: dashboard / Alerts by mail
- What: "the server found a problem": each open serious standing problem is mailed (the most recent 200 are looked at, at most 40 listed), subject "<kind>: <subject>", text the problem's own text plus "(first seen <age>)", fix the problem's own fix. A problem that also has its own mailed alert therefore goes out twice.
- Flag: built twice: see the question on double mailing.

### 15-049: Admins are told when the server's own background work has stopped, was restarted, is failing or is late.
- Where: server-install-and-running / Health checks and alerts
- What: Serious, "the server's background work has stopped", when it has not started its regular work recently (on a site without the server's own syncing: twice the shortest interval, never less than 3 minutes). Serious, "the server restarted its background work", when the server had to restart it (an event, said when it happens). Serious, "a server background job is failing", per piece of work whose last run failed; the standing problem says for how long ("The '<job>' job has been failing <for about N hour(s)>: <meaning>. The server reported: <error, 200 characters>") and what it means for people, said in the rebuild by effect: new and moved project folders are not being set up for syncing (fix: look at the other problems, a stray project marker is the usual cause, otherwise restart); the server cannot read its own syncing; projects ticked or unticked on the dashboard are not reaching the editors' computers (fix: untick and re-tick one project); the server's own file list is not being refreshed (fix: check the projects folder is mounted); old history is not being cleared out (fix: check free space); the re-checked facts are not being re-checked; anything else: "Restart the dashboard". Cleared when the work next succeeds. Warning, "a server background job is late", when work that last succeeded has not finished within its expected time plus one alert interval; the history-clearing work has its own wording about deleting history on the privacy schedule. While the background work is stopped or that work is failing, an open "late" problem is held quiet.

### 15-050: Admins are told when the server cannot write to its own records.

No report for 6 hours or more: red, "this computer has been silent for 6 hours or more"; 15 minutes or more: amber, "... silent for 15 minutes or more". Busy but no data moved for more than 30 minutes, timed by the server's own clock: red, "syncing, no progress for N min"; when the computer cannot say whether data moved, no verdict. Syncing: amber. Otherwise green. A stuck transfer the computer reported stops counting as stuck when that report is over 24 hours old or that kind of transfer has since finished a sync.

### 15-108: A computer's drive is coloured by its free space, and the dashboard says when a computer has probably stopped downloading.
- Where: sync / Disk space
- What: Red when under 5 percent free or under the computer's stopping point (20 GB, or the figure the computer reports); amber when under 10 percent or under 50 GB; otherwise green. A computer that reports nothing about its drive gets no colour at all, never a reassuring green. A computer is taken to have stopped proxy download when its free space is under its own reported stopping point, or under 20 GB if it reported none. No free-space figure never counts as stopped.

### 15-109: Ticking a project for a computer warns when its proxies may not fit, but never refuses.
- Where: dashboard / Ticking and unticking
- What: When the project's proxy size and the computer's free space are both known, a warning is shown unless the proxies plus 20 GB fit and the proxies are under half the free space: "<project> is <size> of proxies. <computer> has <free> free.", plus "That is more than will fit." when they are larger than the free space. The tick is never refused.

### 15-110: Each computer gets one plain sentence saying why it is not syncing, or none.
- Where: sync / Saying truthfully what the sync is doing
- What: One sentence per computer, shown on the studio's overview, on the editor's own view and in diagnostics. No reason found is not shown as "all good"; there is simply no sentence. The computer's own reason wins, except a stuck transfer the server can see has recovered. Otherwise the server works one out. The reasons, highest first, and their sentences:
  - not signed in: "Not syncing: this computer is not signed in"
  - licence not accepted (from the computer): "Not syncing: the licence agreement has not been accepted on this computer yet"
  - clock 60 seconds or more out: "Not syncing: this computer's clock is <duration> out from the server, so proxy download transfers nothing"
  - drive missing: "Not syncing: the sync drive is not there on this computer"
  - drive not answering: "Not syncing: the sync drive is mapped but not answering, so nothing can be read or written"
  - drive pointing at the wrong place: "Not syncing: the sync drive is pointing at the wrong place"
  - out of space, when the computer said so: "Not downloading proxies: proxy download stopped itself, the drive has <free> free"; when the server is guessing from the 20 GB default: "Proxy download has probably stopped itself: the drive has <free> free, under the 20 GB this computer's build stops at unless it was set otherwise on that computer"
  - studio-wide stop: "Not syncing: syncing is stopped by your admin for the whole fleet"
  - stopped on this computer: "Not syncing: syncing is stopped on this computer"
  - paused (from the computer): "Not syncing: syncing is paused on this computer"
  - download safety stop: "Not downloading proxies: proxy download stopped itself and needs a person to check the server"
  - nothing ticked (information, never a fault; not for wired machines): "Nothing ticked for this computer"
  - shared folders unfiltered: "Not syncing safely: N shared folder(s) on this computer has/have no ignore filter yet"
  - upload only (information): "Nothing to download: this project is upload-only on this computer"
  - stuck: "Not syncing: <upload / proxy download / folder sync> has been busy for <duration> with nothing moving"
  - syncing down (not for wired machines): "Not syncing: syncing on this computer is down"
  - cannot reach the server (from the computer): "Not syncing: this computer cannot reach the server"
  - a reason from a newer app: "Not syncing: this computer reported a reason this dashboard is too old to explain"
  The computer's own detail is added in brackets unless it only repeats the sentence, is over 120 characters, or the reason is "nothing ticked". If another separately fixable cause is also true (studio-wide stop, stopped here, paused, safety stop, out of space), it is added as ". Also: <sentence>"; at most two causes are shown.

### 15-111: Files waiting to move are marked on hold, with the reason, only when the computer says that kind of transfer is held.
- Where: dashboard / Transfers and the queue
- What: A file waiting in the queue is shown on hold, with the reason sentence and since when, only when the computer itself reported a reason that holds that kind of transfer. Not signed in, licence not accepted, drive missing, not answering or misplaced, studio-wide stop, stopped here, paused and offline hold every kind; a wrong clock, a full drive and the download safety stop hold proxy download only; syncing down holds shared folders only. A stuck transfer never marks a hold.

### 15-112: Every "send us the diagnostics" line tells the person exactly where to copy them.
- Where: editor-app / Telling the editor what is wrong
- What: Wherever the product asks for a computer's diagnostics, it names the one place in the app's settings where the editor copies diagnostics for their admin.

### 15-113: Each computer's row leads with one headline, and counts its further notes.
- Where: dashboard / Each computer's state
- What: First match wins: a fault sentence, red; a stale report: with nothing ticked, muted "Nothing ticked for this computer. Last report <date time> UTC", otherwise "Not heard from since <date time> UTC" (or "Not heard from this computer for 15 minutes or more"), amber until 6 hours, then red; the app out of date, amber, "Out of date: running X, current is Y"; a kind of transfer red, red, "<Kind> has stopped: <reason>"; an information sentence, muted; syncing, muted "Syncing"; otherwise muted "Idle between checks, N file(s) still to move", "Idle, nothing owed" (only when the count of files owed is known) or "Idle". Beside the folded details, a count of further notes: N crashes; the drive is filling up (drive not green); N clips outside the tree; N projects not open with clips only on this computer; N stray project folders; a project folder has moved; N sync conflicts; a shared folder has no filter yet; an update keeps failing; this computer is being refused; N files it will not upload; a lot of footage in the local recoverable-files bin (over 5 GB); footage waiting in the drop folder; the fast upload is failing or dropped files; N clips need proxies; Timeline Cards' link to Resolve on this computer is not running; N YouTube clips waiting for Resolve, or the YouTube import gave up; N clips with neither the original nor a proxy on this computer; Resolve has stopped answering a call.

### 15-114: A computer that withholds a kind of report shows a grey chip saying so, and is never marked at fault for it.
- Where: accounts-privacy-legal / What the product records about a person
- What: For each kind of report a computer does not send, a grey chip "NOT REPORTED BY THIS COMPUTER" with the kind: "OPEN RESOLVE PROJECT", "FILE LIST", "RESOLVE BINS", "IDLE TIME". Its hover text says the computer's own privacy switch or the site's is off, and "Sync is not affected, and nothing here is a fault." It never changes any colour, headline, note or alert.

### 15-115: Each computer shows which licence it accepted.
- Where: accounts-privacy-legal / The licence a person accepts
- What: Compared with the licence version this dashboard hands out: the same, green "Licence X accepted"; different, amber "Older licence accepted"; nothing reported, grey "Not reported"; when the dashboard has no licence of its own, shown without colour. Shown on the studio's overview and on the person's own account page.

### 15-116: An admin can switch on a daily server check in which the assistant reads everything open and mails what needs a person.
- Where: dashboard / The daily server check
- What: Off by default; an admin switches it on in the alert settings. The assistant reviews everything the dashboard knows to be open, stuck or failing, and the result is mailed to the alert recipients with numbered suggested actions that a reply can carry out. It runs at chosen hours of the day in the site's time zone: default 06:00 and 18:00, at most 4 a day ("at most 4 checks a day"; hours 0 to 23, repeats removed, sorted; a blank field saves the default, never "never"). If the server was down at that hour, it runs when it comes back; a restart never runs it twice; a failed send is retried after 10 minutes, then an hour, then 6 hours. It never runs while switched off or with no alert destination. Only one runs at a time: a second is refused with "a server check is already running" or "a server check has been running since <time>"; one that has been running for more than 90 minutes is taken as dead and does not block. It never holds up the server's other work.
- Flag: dormant

### 15-117: An admin can run the server check now.
- Where: dashboard / The daily server check
- What: A "run now" control starts a check whatever the schedule. Refused with "the server check is off. Turn it on and save first." or "no alert channel is set up, so the report would go nowhere." It also starts looking for replies at once.

### 15-118: The server check tells the admin when the assistant is not available to it.
- Where: dashboard / The daily server check
- What: The check needs the assistant to be available on the server: switched on for the site and set up in the assistant settings, or, on the vendor's standard build, the site's own key for the assistant. When it is not, the admin is told why in plain words (switched off on this server, not set up on this server, or no key entered, each naming the assistant settings), and the check sends its fallback report instead (15-123). The assistant gets no stored sign-in, only what the check needs.

### 15-119: In the server check, the assistant can only read, and never sees a secret.
- Where: dashboard / The daily server check
- What: The assistant may read and search but never change, run or fetch anything. It is given a snapshot of: the open standing problems (200), the alerts of the last 48 hours (500), the counts of open problems, the state of every re-checked fact, the state of the server's background work, every computer's row, live transfers and the queue, open shared work (500, with counts by kind and state), the published packages, and the actions offered by the previous check and what became of them. It may also read the product's own workings when it needs to. A part that cannot be read is marked as such. Nothing from the site's settings or stored secrets is given; any field named like a password, token, secret or key, and any value that looks like a key, is blanked before the snapshot is written. It has 20 minutes to answer.

### 15-120: The server check lists only what needs a person, most important first, and never calls an empty computer a problem.
- Where: dashboard / The daily server check
- What: The assistant is told: list what needs a person, most important first, each with evidence and a suggested action; do not list what is fine; a computer with no projects ticked is never a problem; say all clear when nothing needs a person; suggest actions only from the fixed list of actions (15-130); a fault in the product's own code is a finding with a ready-to-paste instruction for fixing it, never an action; plain text, no em dashes. At most 30 findings and 20 actions are kept; each finding is serious, a warning or for information (a warning if unclear); each text is cut at 4,000 characters; em dashes are replaced with " - "; "all clear" only when there are no findings.

### 15-121: An action is offered in the server check only if it is on the list and makes sense right now.
- Where: dashboard / The daily server check
- What: Each proposed action needs a number from 1 to 99, not used twice, must be one of the fixed actions with exactly its details, and must pass that action's own check against the present state. Duplicates are dropped. Proposals that fail are listed under "Suggested but not offered:" with the reason.

### 15-122: The server check's e-mail reads as a short list of what needs the admin and what a reply can do.
- Where: dashboard / The daily server check
- What: Subject "[CC Sync] Server check: <the assistant's subject, or 'all clear' / 'what needs you'>". Body: the headline, or "All clear: nothing on the server or the fleet needs a person."; "WHAT NEEDS YOU" with numbered findings "[SEVERITY] title", "Evidence:", "Suggested:", "Actions: [n]", and a ready-to-paste instruction for fixing the product's code where there is one; "ACTIONS A REPLY CAN CARRY OUT" with "[n] <action> - <why>"; the actions not offered; then either 'To carry any of these out, reply to this email, e.g. "do 1 and 3".' and "Reference: CCT-<code>   (valid until <local time>, each action runs once)", or, with replies off, "Replies are switched off on this server (Settings, Alerts, SERVER CHECK: reply address), so these can only be done on the dashboard.", or "Nothing in this check can be done by reply." The reference is random and valid for 48 hours; the server keeps only a fingerprint of it, and its own copy of the e-mail shows only the last four characters. Replies are directed to the reply address only when actions were offered and replies are on. The e-mail is recorded in the history of what was sent.

### 15-123: The server check always reports, even when the assistant could not run.
- Where: dashboard / The daily server check
- What: When the analysis cannot run (the assistant is not available, did not answer within 20 minutes, could not start, failed, or gave no usable answer), a fallback is sent: subject "[CC Sync] Server check: the analysis could not run"; the body names the reason, then what the dashboard itself can say: open standing problems (up to 40, by kind and subject), "Computers not syncing:" with each fault sentence, and "Background jobs failing:", then "This message is sent because the check always reports. If these stop arriving, the server check itself is broken." If the check itself fails: subject "[CC Sync] Server check: the check failed", body "The server check failed before it could finish: <error> ... Nothing was changed. The next check will try again."

### 15-124: The admin sees the server check's state, and past checks are kept for 60 days.
- Where: dashboard / The daily server check
- What: The settings show: whether the check is on, whether the assistant is available to it and why not, the incoming mail server used for replies, whether replies are on, the time zone, the last check (when, ok / fallback / failed, whether the e-mail went, detail), "running since" when one is running, and the result of the last look for replies. A past check's report can be shown as text (subject plus the masked body, or a one-line status). Each check is recorded with its offered actions. Offered actions whose reference has run out are marked expired. Checks, their actions and replies older than 60 days are deleted.

### 15-125: An admin can let replies to the server check carry out its actions, by giving a reply address.
- Where: dashboard / The daily server check
- What: Replies are on only when the check is on, a reply address is set (one plain e-mail address; blank turns replies off, and the report is still sent) and alerts go by e-mail. The server reads replies with the same mail account it sends from. The incoming mail server can be typed, or left blank to be worked out from the outgoing one's name (the usual naming of a provider's incoming and outgoing servers, which for Gmail is known); if it cannot be worked out, the admin is told "replies cannot be read: the incoming mail server, the mail user or the mail password is not set". A reply is picked up within about two minutes; replies from the last two days are considered, read or unread. The certificate check follows the alert e-mail setting. A failure to read is shown as "could not read the inbox (<kind>: <server message>)".

### 15-126: Only a genuine reply from an alert recipient, carrying a current reference, is acted on.
- Where: dashboard / The daily server check
- What: Each reply is handled once. A message not actually addressed to the reply address is skipped and left as it was. It is refused when: the sender is not one of the alert recipients; the receiving mail provider did not vouch that the message really came from the sender's domain (for Gmail, only Google's own verdict counts), unless the sender is the mailbox account itself and the identical message is in that account's sent mail, with no explicit failed verdict; or it carries no reference from a check, or one older than 48 hours ("the reference in the reply has expired (a check's actions can be chosen for 48 hours)", "the reply carries no reference (CCT-...) from a check this server sent"). An accepted reply is recorded before anything is done, so a crash never acts twice. Handled replies are marked read.

### 15-127: A refused reply is never answered by e-mail; the admin is told on the dashboard instead.
- Where: dashboard / The daily server check
- What: A warning standing problem, named by the failed test: "A reply to the server check email from <who> was not acted on: <reason>. Nothing was changed, and no answer was sent, because answering a forged sender sends mail to whoever it pretended to be." Fixes: reply from an address among the alert recipients; the mail provider did not vouch for the message, so use the dashboard's own buttons; reply to the most recent check e-mail within 48 hours. It closes itself when a later reply from the same sender is acted on, or after 7 days.

### 15-128: A reply can say "all", "none", or the numbers to do, or ask in its own words.
- Where: dashboard / The daily server check
- What: Only the reply's own words count (the quoted original and signature are ignored), at most 4,000 characters. "all", "do all", "all of them" means every offered action; "none" or "nothing" means none; a list of numbers such as "1, 3", "do 1 and 3", "1 & 2" means those. Anything else is read by the assistant, with no tools, in up to 3 minutes, to find which numbers to do or skip and what is unclear. If the assistant is not available: "the reply is not a list of numbers, and the assistant is not available to read it (...)". Each chosen action runs once, in order, and each action can run only once across all replies; outcomes are done, refused (its check said no now), failed, "not done again", or "not understood" (not offered).

### 15-129: An accepted reply gets a confirmation saying what was done.
- Where: dashboard / The daily server check
- What: Subject "Re: <original subject>"; "What your reply asked for:" then "[n] <action>: done / refused / failed / not done again / not understood - <detail>", or "Your reply did not choose any of the offered actions, so nothing was changed."; "Not clear from your reply: ..."; "Note: ..."; "Nothing else was changed."; how to carry out another; and the reference line again. Recorded in the history of what was sent.

### 15-130: The actions a reply can carry out are the dashboard's own buttons, each re-checked when chosen.
- Where: dashboard / The daily server check
- What: Each action is checked when offered and again when chosen; a failed check is a refusal with the reason. Each does exactly what the matching dashboard button does and is recorded in the history of changes as done by the server check on behalf of the sender. Details are limited to 128 characters, without control characters; editor names are taken in lower case.

  | Action | Refused when |
  |---|---|
  | Push the current app build to a computer ("asked <who> to update to X on its next report") | no such computer, no current build for its platform, or it already runs it |
  | Withdraw a pushed update for a computer | no such computer, or no update waiting |
  | Resume proxy download on a computer | no such computer, or its last report does not show download stopped itself |
  | Start syncing again everywhere (release the studio-wide stop) | no studio-wide stop in force |
  | Keep syncing stopped everywhere, for 24 hours from the reply (keeps its reason and start) | no studio-wide stop in force |
  | Cancel a piece of shared work by number (it stops at that computer's next report, or, for work the server took over, when the server next checks it) | no such work, or already finished |
  | Dismiss a standing problem by number ("it comes back by itself if the condition is still true") | no open problem with that number |
  | Ask a computer for its diagnostics | (no refusal described) |
  | Ask the server's background work to run now | the server's background work is not running |

  Approving a computer waiting to join is deliberately not possible by reply.
