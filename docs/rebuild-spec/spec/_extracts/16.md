# Extract of inventory section 16

## Items

### 16-001: What the dashboard shows about sync and the NAS is kept fresh on its own, each kind of fact on its own clock.
- Where: dashboard / Pages that refresh and answer clicks
- What: Without anyone pressing anything, the server keeps its picture of the studio current. Which computers are connected, and from where, is at most about 15 seconds old. How far each computer is through each project, and which files it still lacks, is at most about a minute old. The list of projects and computers known to the NAS is at most about two minutes old. A folder newly marked as a project on the NAS is set up within about five minutes. The count of video files on the NAS for a project that changed is at most about 15 minutes old (a brand-new project is counted within seconds of being found). The protection panel is re-evaluated about every 15 minutes, the server's own alert checks run about every 10 minutes, and old records are cleaned up about once an hour. When the server starts, all of this is gathered straight away rather than after the first wait.

### 16-002: Ticking or unticking a project for a computer takes effect within about five seconds, not at the next routine refresh.
- Where: sync / What syncs where
- What: When an editor or an admin ticks a project (or makes another change that affects sharing), the server applies the change to the NAS's sharing within about five seconds and refreshes the connection and progress figures at the same moment, so the person sees the effect almost at once. Without a nudge like this, sharing is checked against the ticks about every minute anyway, so a change made any other way is also applied within about a minute.

### 16-003: The server's health panel shows, for each kind of background work, when it last ran, whether it worked, and a short note.
- Where: server-install-and-running / Health checks and alerts
- What: Every kind of work the server does on its own records its start and end time, success or failure with the error text, and an optional note. A job that worked but only did part of what it should says so in the note ("partial: ..." or "skipped: ..."), for example "partial: N folder(s) left for the next cycle", "refused N share removal(s)", "kept N project inventory(ies): the walk collapsed", "N move(s) detected on the server", "N safety mechanism(s) missing", or the number of open problems. One kind of work failing never stops the others: its half-done changes are thrown away and the rest carries on. A failed kind of work is tried again no sooner than normal, and after repeated failures it waits longer each time, never more than five minutes between tries; one success puts it back to normal. If the server cannot open its own records at all, it keeps trying every five seconds, forever, and nobody is told except through the server's log.

### 16-004: Background work that runs slowly is shown as a problem the server found, and the problem closes itself once it is fast again.
- Where: dashboard / Problems the server finds
- What: When one kind of background work takes longer than a set threshold, a problem card opens naming that work. The next time the same work finishes under the threshold the card closes on its own, including after a server restart.
- Flag: undetermined: the exact threshold and the card's wording are not given

### 16-005: The server notices when its own background work has stopped or hung, restarts it, and reports each restart in its alerts.
- Where: server-install-and-running / Health checks and alerts
- What: The server watches that its background work is still alive and still moving. If it has died without being stopped on purpose, a replacement is started (never two at once). Each restart is counted and reported by the next alert check. Work deliberately stopped (at shut-down) never counts as dead; at shut-down the server waits up to ten seconds for it to finish.

### 16-006: Parts that need the NAS's file sharing or the project tree simply show nothing when the server was not given them, and the health panel does not call that a failure.
- Where: server-install-and-running / Shares that go away, and checks that cannot run
- What: When the server has not been connected to the NAS's sharing of project files, everything that depends on it (setting up projects, sharing, connections, progress, missing files) is recorded as a quiet success that did nothing. When the project tree on the NAS is not available to the server, setting up projects and counting video files are recorded the same way. Retention, the protection panel and the alert checks run regardless. A configured project folder that does not exist fails with "the Projects folder does not exist" and the path.

### 16-007: A one-off command runs the main gathering jobs once and prints whether each worked.
- Where: server-install-and-running / Health checks and alerts
- What: A person building the product can run the setting-up, picture, connections, progress and missing-files jobs once from a command line. It prints each job as ok or FAILED, then how many projects, computers, progress figures and missing-file lists it now holds, and exits with the number that failed. It refuses at once when the server has not been told where the NAS's file sharing answers.
- Flag: dev only

### 16-008: An optional part that comes alive or breaks is noticed within seconds without restarting the server.
- Where: server-install-and-running / Health checks and alerts
- What: After every round of background work (every few seconds) the server re-checks whether each optional part (b-roll, music, Timeline Cards and the like) is available, and records any change. The change of state is only written to the server's log; nobody is told by this check.

### 16-009: A folder on the NAS becomes a project because it carries the product's project identity mark, and it is set up for syncing on its own within about five minutes, shared with no computer until someone ticks it.
- Where: sync / What syncs where
- What: The server looks through the project tree on the NAS, up to eight folder levels deep, skipping hidden folders (names starting with a dot), never treating the top of the tree itself as a project, and not looking inside a folder that is already a project. Every folder carrying a valid identity mark is a project; the identity in the mark (lowercase letters a to z, digits and hyphens only) is the project's permanent identity, and it is also the last part of the project page's address. A mark with any other identity is ignored. A newly marked folder is set up for syncing under that identity and shared with nobody until ticked. The project's name as shown is its path inside the project tree, and the server corrects the shown name whenever the folder's path changes.

### 16-010: A damaged identity mark is shown as a problem with the exact repair, and the folder is not a project until it is fixed.
- Where: dashboard / Problems the server finds
- What: When a folder's identity mark cannot be read, the folder is skipped and a warning card opens: "The folder <folder> on the server has a damaged CCSync marker file, so it is not a project as far as this dashboard is concerned: nobody can tick it and nothing in it syncs." If the server already knows that folder under some identity, the repair text says to replace the mark with one carrying that identity, and that the server usually writes a fresh mark by itself within a few minutes. Otherwise it says to copy a working mark and set the identity to the project's own (the last part of its project page address), or to delete the damaged file if the folder was never a project. The card closes on its own once the mark reads again.

### 16-011: The server puts back a project's missing identity mark by itself, but only where it is certain which project the folder is.
- Where: sync / Safety stops
- What: When a folder the server already syncs as a project has lost its identity mark, the server writes a fresh one carrying the identity it knows, within about five minutes. It refuses (and leaves the folder alone) when the folder does not show signs of really being the synced folder, or when some other folder in the tree already claims that identity. A refusal or a failed write is only written to the server's log; nobody is told. A mark the server writes keeps everything else that was in it (such as borrowed-folder declarations) and records who wrote it and when. It is written whole in one step, so an editor's computer never receives a half-written or temporary mark.

### 16-012: Within a project, every file that is not video and not a proxy is kept in step between the NAS and every computer that takes the project in full; a fixed list of files never travels that way, and the server puts that list back if anyone changes it.
- Where: sync / Files that must never sync
- What: Files such as edit projects, sound, graphics and documents are kept the same on the NAS and on each computer with a full tick. These never travel that way: video files of every camera and editing format the product knows (Blackmagic RAW, QuickTime, MPEG-4, MXF, AVI, AVCHD transport streams, Matroska, RED, Canon Cinema RAW, MPEG-1 and 2, Windows Media, WebM and Insta360 360-degree files, matched without regard to letter case); unfinished transfers; YouTube downloads still in progress; and any folder named Proxy (any case). How video originals and proxies travel is described with the footage sync. Every few minutes the server compares each project's list with the correct one and puts the correct one back if it differs.

### 16-013: Deleting a file on an editor's computer never deletes it on the NAS, and a file deleted or replaced on the NAS is kept for a year.
- Where: sync / Deletions and removing a project
- What: For the files kept in step within a project, a delete made on an editor's computer is never applied to the NAS's copy. On the NAS, an older or deleted copy of such a file is kept in the project's deleted-files folder for up to one year, thinning out over time, and the server puts these keep-for-a-year settings back if they are changed on any project.

### 16-014: Moving or renaming a project folder on the NAS by hand is followed: the project, its ticks and its history carry on at the new place.
- Where: proxies-and-file-moves / Moves made by hand on the NAS
- What: Within about five minutes of a project folder being moved or renamed on the NAS, the server points the project at the new place and updates its shown name; every tick and all its history survive, because they belong to the project's identity, not its path. The server refuses to follow (and checks again every few minutes) when: the old folder still exists, so the new one is a copy; the new folder does not look like a finished copy of the synced folder (an interrupted or still-running copy); the new folder holds fewer than half the video files (originals and proxies together) last counted for the project; or the project's current place is somewhere the server cannot see, in which case it must be fixed by hand. A refusal is only written to the server's log; nobody is told.

### 16-015: The server refuses to set up a project that sits inside another project, contains other projects, or points at a folder another sync setup already serves, and says why.
- Where: dashboard / Problems the server finds
- What: Each refusal opens an error card:
  - Inside another project: "The folder <folder> on the server is marked as a project, but it sits INSIDE another project (<parent>). Projects cannot be inside each other, so this one is not being set up and nothing in it syncs on its own." The repair: delete the inner mark, or move the folder out beside the parent.
  - Containing projects (looked for up to eight levels down, skipping hidden folders): "The folder <folder> on the server is marked as a project, but it CONTAINS N project(s) (...). Setting it up would hide them, so the dashboard has refused, and those projects are missing from this dashboard until it is sorted out." The repair: delete the outer folder's mark.
  - Two sync setups for one folder: "Two sync folders point at the same directory on the server (<folder>): this project's own (<identity>) and another one (<other>). Only one of them is the folder editors are connected to, so work saved through the other one goes nowhere." The repair: remove the stray one on the server; nothing is deleted from disk by doing so.
  Each card closes on its own once the cause is gone.

### 16-016: A project folder copied rather than moved (two folders with one identity) is never guessed at: the server says so and keeps or stops syncing accordingly.
- Where: dashboard / Problems the server finds
- What: When two or more folders carry the same identity, an error card opens: "Two folders on the server both claim to be the same project (...). That happens when a project folder is COPIED rather than moved, because the copy brings the project's identity file with it." If one of them is the folder the project already lives at, the card adds "The dashboard is working with the one it already knew and ignoring the other." and syncing continues from it. Otherwise it adds "The dashboard cannot tell which one is real, so it is leaving both alone and this project is not syncing." The repair: delete the identity mark inside the copy, or delete the copy. The card closes on its own once only one folder is left.

### 16-017: A project that cannot be set up for syncing is shown as a problem of its own, and every other project carries on.
- Where: dashboard / Problems the server finds
- What: Each project is set up on its own. One that fails opens an error card: "The project folder <folder> could not be set up for syncing: <the error, cut to 200 characters>. Until this clears, nothing in that project reaches anybody." The repair tells the admin to look at the other problems first, and otherwise to check that the NAS's file sharing is running. The card closes on its own when the project sets up. The health panel counts how many projects failed.

### 16-018: The server never removes a project's sync setup by itself, and a project that disappears from the NAS's sharing is put out of the active list only a few at a time.
- Where: sync / Deletions and removing a project
- What: A project whose folder has vanished is left as it is; nothing is deleted. A project the NAS no longer shares is marked inactive in the dashboard, but when many would go inactive at once the server refuses (it notes "refused deactivating N project(s)" on the health panel) and nobody else is told.
- Flag: undetermined: how many count as too many

### 16-019: Every editor computer receives the studio's shared asset libraries (by default the LUT library and the Resolve stills gallery) without anyone ticking anything.
- Where: resolve-on-the-editors-computer / Colour look-up tables (LUTs)
- What: By default two libraries are shared: the LUTs folder ("LUT library") and the stills folder ("Resolve gallery"), both under the tree's Assets folder. They are set up on the NAS by the server if missing and every editor computer the server can link to a known editor receives them, except the computers of suspended editors. They are not projects: they cannot be ticked, never appear among projects and are never counted. A site can replace the list with its own folders under Assets (the change is picked up within seconds); an entry with no letter or digit, or one that would clash with an earlier one, is left out, and nobody is told. A library already set up somewhere other than where the site says is left alone; this is only written to the server's log. When the libraries cannot be set up, an error card opens: "The shared asset libraries (the LUT library) could not be set up: <error>. Editors will see their LUTs missing in Resolve." The repair: check the NAS's file sharing, then the site's shared-folder setting. It closes itself on the next success. Within a library, video, unfinished transfers and operating-system clutter files (Mac folder records, Windows thumbnail caches and folder settings, temporary files) never travel, and the server puts this list back if it changes.

### 16-020: A new project is created with a standard set of folders, which a site can change.
- Where: dashboard / Projects
- What: By default a new project gets these folders: AE, Audio/Music, Audio/Voiceover, B-roll, Interviewees, Render in Place, Subs, Youtube. A site can give its own list; a blank list means the default, and any attempt to climb out of the project folder in a name is dropped.

### 16-021: The dashboard can list folders in the project tree that are not projects yet.
- Where: dashboard / Projects
- What: The server can list folders up to three levels down in the project tree that are not a project, are not inside one and do not contain one, skipping hidden folders. When the tree cannot be read, the answer is "cannot tell", never an empty list.

### 16-022: A computer receives its projects only once it has been approved on the NAS, and until then its projects are simply not shared.
- Where: sync / Computers joining and changing
- What: When a computer reports itself to the dashboard but has not yet been approved on the NAS, the server cannot share anything with it and skips it; projects are shared with it from the first refresh after approval (within about a minute). This part of the product only writes that to the server's log. The list of computers waiting for approval is handed to the server's own problem checks; when it cannot be read it is treated as unknown, never as "nobody waiting". Approving a computer adds it under the given name (or renames it if it is already known) and shares nothing by itself.

### 16-023: Each project is shared with exactly the computers that should take it in full, and with no others the server manages.
- Where: sync / What syncs where
- What: The NAS always keeps its own copy. A computer receives a project when a full tick for that project (or for a project that borrows a folder from it) is on that very computer. These receive nothing: a computer with an upload-only tick for the project; a computer set to wired (and every computer of a person who only has wired computers); every computer of a suspended editor; any computer for an archived project (an archived project's ticks count for nothing, and so do those of an archived project that borrows from it). A computer running an older version of the app that has not said which computer it is receives every project its person has ticked in full. Computers the server cannot link to any known person are never touched: what they have is left as it is. Only who receives each project is ever changed this way; the project itself is not.

### 16-024: Unticking is held back for a few seconds so that Undo costs nothing.
- Where: sync / A plan belongs to a computer
- What: Removing a computer from a project is not applied while the tick was changed only seconds ago (the Undo window on the fleet view), so unticking and pressing Undo never stops or restarts anything. Adding is never delayed.
- Flag: undetermined: the length of the Undo window

### 16-025: The server refuses to take many projects away from computers in one go unless an admin caused it on purpose, shows the refusal, and lets an admin approve it.
- Where: sync / Safety stops
- What: Each project taken from one computer counts as one removal. Removals an admin clearly caused do not count: those of an archived project, those of a suspended editor's computers, those backed by a recorded untick made recently, and those an admin approved by name from the refusal. If the rest exceed the limit, they are all held back while additions and the approved removals still go ahead, and a banner shows what was refused. The limit is three, or, if larger, a site setting "removals allowed per computer" (default 0, meaning the three applies) multiplied by the number of editor computers. An admin approval is used up as soon as any approved removal is applied. A refresh with nothing refused clears the banner.
- Flag: undetermined: how recent a recorded untick must be

### 16-026: The dashboard can show which sharing changes are waiting to be made.
- Where: dashboard / Ticking and unticking
- What: For each project, what the server wants (which computers should receive it) and what the NAS currently does are recorded before any change is made, so the dashboard can show the changes still pending. Computers the NAS shares a project with that the server did not know of are kept. When the NAS refuses a change for one project, the others still go ahead and the health panel says "applied A of B folder(s)" with the first error.

### 16-027: On a fresh server that takes over a NAS already sharing projects, each existing share becomes a tick once.
- Where: sync / Computers joining and changing
- What: The first time a server with no ticks recorded meets projects already shared with editors' computers, each of those shares becomes a tick for that editor, on that computer if known, or on the person's not-yet-assigned plan if not. This can only add ticks, never take a share away. It waits (and says "seed deferred" on the health panel) until at least one project and at least one computer it can link to a person are seen.

### 16-028: A computer named like a person the dashboard does not know is left alone.
- Where: sync / Computers joining and changing
- What: A computer is linked to a person only when its name matches an editor the dashboard knows (on a brand-new dashboard that knows no editors yet, any name shaped like a username counts). A computer whose name looks like a username but matches no known editor is treated as nobody's, and its shares are left alone. This is only written to the server's log; nobody is told. The same is true when an older app's computer is being shared projects by person rather than by computer.

### 16-029: The dashboard knows how many video files, originals and proxies each project has on the NAS, and how big they are.
- Where: dashboard / Projects
- What: For each active project the server lists every video file (the same formats as in 16-012) with its size and date. A file inside any folder named Proxy (any case) counts as a proxy, every other as an original. A newly found project is counted within seconds; after that a project is only re-counted when something in it changed, and at most eight changed projects are counted every 15 minutes, the rest following in turn. This count is what shows each project's proxy size before a tick, what the moves on the NAS are recognised from, and what the editor's app is answered from when it asks where a file went.

### 16-030: A project tree that looks unmounted, or a count that suddenly collapses, never wipes what the dashboard knows about a project.
- Where: server-install-and-running / Shares that go away, and checks that cannot run
- What: When the project tree on the NAS appears completely empty, the count is skipped and the health panel says "skipped: the Projects tree looks unmounted (0 entries)". When a project that had files suddenly counts as nearly empty, the previous count is kept. A project whose folder is missing is recorded as missing on the NAS, and one with no video and no sign of being a synced folder is recorded as looking unmounted, not empty.
- Flag: undetermined: what counts as a collapsed count

### 16-031: A video file or folder moved by hand on the NAS is recognised, and every computer holding it follows: each moves its own copy and relinks Resolve, so nothing uploads the old path again.
- Where: proxies-and-file-moves / Moves made by hand on the NAS
- What: Within about 15 minutes of the change being counted, the server recognises a move: the same video file (same name, size and modification time) gone from exactly one place and present at exactly one other place, within a project or between projects. Names spelled differently by a Mac and by Windows still match. A whole folder whose every file moved to the matching place under one new folder, with nothing left behind, is recorded as one folder move (a folder renamed in place counts too; a folder named Proxy is never recorded as a moved folder). Proxies in the Proxy folder beside an original that moved to the Proxy folder beside its new place go with the original's move. A move seen in two halves at different times is still paired, as long as the file is now only at its new place and the disappearance was seen no later than the arrival; a file that comes back to where it was cancels it. The move is recorded as already done on the server, by "detected on the server", and every computer holding the file at the old place is told to follow. Nothing on the NAS is touched by this.

### 16-032: Some changes on the NAS are deliberately not taken as moves.
- Where: proxies-and-file-moves / Moves made by hand on the NAS
- What: Each of these stays a plain disappearance and arrival: a file whose size or date could not be read; a file that disappeared from two places or appeared in two places (ambiguous); a file that only disappeared (a deletion); a proxy that moved without its original; a file that, when seen arriving, is also still somewhere else (a copy). The same move is not recorded twice within a day.

### 16-033: Each recognised move is shown as an information card, and an unusually large batch of moves is capped and said so.
- Where: dashboard / Problems the server finds
- What: For each recognised move an information card opens: "N file(s) were moved on the server, by hand, from <old place>. K computer(s) are following: each moves its own copy and relinks Resolve, so nothing re-uploads the old path." Its repair text: "Nothing to do; the computers follow on their own. If this was not a move, open the project page's MOVES history." At most 500 moves are taken in one count; beyond that the first 500 (by project and path) are recorded, the rest dropped, and a card says moves were dropped. When not every project could be read, the "moves made by hand" check is not marked as checked, so its status goes stale rather than looking fine.
- Flag: undetermined: the wording of the "moves dropped" card

### 16-034: The dashboard shows each project's progress on each computer, the project's own state on the NAS, and what editors are still sending up.
- Where: sync / Saying truthfully what the sync is doing
- What: About every minute, for every project, the server records the project's state on the NAS and any error (so a stopped or broken project shows), its total files and size, and what is still on its way up to the NAS from editors. For each computer that receives the project it records the percentage complete, how many files and bytes are still owed and how many deletions are pending. A figure the server could not get is left out, never shown as 0%. On a studio with very many projects, some figures may be up to about two minutes old; until refreshed, a project keeps its last known figures. Progress for a project no longer shared with a computer is removed.

### 16-035: For each computer still behind on a project, the dashboard can list the files it still lacks, up to 600.
- Where: sync / What is owed
- What: About every minute, for each project and computer that is not complete, the server fetches the names (and sizes where known) of the files that computer still needs, up to 600. The list is marked as cut short when more are owed than were listed. It is cleared once the computer reaches 100% with nothing owed.

### 16-036: Files finished arriving on the NAS from editors appear in the transfer history.
- Where: dashboard / Transfers and the queue
- What: Each file within a project that finishes arriving on the NAS is added to the transfer history as an upload, named by the project and file. It is credited to an editor only when exactly one editor's computer receives that project; otherwise to nobody. If this cannot be read, nothing is said and nothing else is affected.

### 16-037: Old records are cleared out about once an hour, and expired sign-ins are removed.
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: About every hour the server clears records past their keeping period and removes sign-in sessions that have expired.
- Flag: undetermined: how long each kind of record is kept

### 16-038: Shared work a computer stopped answering for is taken back about every hour; work out of retries is done by the server itself where it can, otherwise given up visibly.
- Where: fleet-jobs / Failures, retries and the queue
- What: When a computer's hold on a piece of shared work has expired, the server takes it back. A piece of work that has used up its retries is run by the server itself when the server can do that kind of work, and is otherwise marked as abandoned. A computer that just failed a piece of work waits two minutes before being offered more.

### 16-039: A project can borrow a folder that lives inside another project, and every computer with a full tick of the borrower then receives the lending project.
- Where: sync / What syncs where
- What: A project's identity mark may declare folders it borrows from other projects, each as a path inside the project tree. Any computer with a full tick of the borrowing project receives the lending project as well; limiting what of it is actually brought down is the editor's app's job. Declarations are re-read about every five minutes and the mark on the NAS is always the truth. At most 128 declarations are read and at most 32 are used per project; past 32, one line says "too many includes (limit 32); N ignored". Repeated declarations, and ones inside another declaration of the same project, are dropped. When the links cannot be worked out a warning card opens: "A shared-folder link between projects could not be resolved: <error>. The borrowed folder will not appear in the project that borrows it." with the repair "check the borrowing project's shared folder links"; it closes itself on the next success.

### 16-040: Each borrowed folder is shown as working, missing, refused or from an inactive project, with the reason in words.
- Where: sync / What syncs where
- What: A borrowed-folder link is in one of four states: ok, missing, invalid, lender-inactive. It is refused (invalid) with these reasons: "empty path"; "absolute paths cannot be shared; declare a tree-relative Projects/ path"; "empty or dot path segment"; "segment ... starts with '.'"; "control character in path"; "segment ... contains ':' (declare a tree-relative path, not a drive path)"; "path segment over 255 bytes"; "only folders inside a project can be shared (the path must start with Projects/)"; "that is a whole project; tick both projects instead"; "cannot share a Proxy folder; share its parent instead"; "not inside a project"; "that folder is inside this project already"; "the lending project's marker is unreadable"; "contains a project (<folder>)"; "path escapes the Projects tree" (a shortcut that leads outside the tree). It is missing with "folder not found on the server" or "folder could not be read on the server", and still names the lending project. It is lender-inactive with "the lending project is not active on the dashboard". When the lending project has been moved, the link keeps working through the lender's new place and says "declared path is stale; the folder moved to Projects/<new>. Update the declaration when convenient."; the declaration itself is never rewritten.

### 16-041: When files vanish from an editor's computer, its app can ask the server where else on the NAS a file of the same name and size now sits.
- Where: sync / Safety stops
- What: The server answers, for up to 2000 files at a time, every place on the NAS a video file of that name and size is, from its latest count of the NAS (it does not look at the disk). Names spelled differently by a Mac and by Windows still match. Inactive projects, and projects whose last count failed, are left out. The answer says whether the NAS has ever been counted at all (if not, "not found" means "not known"), how old the count behind it is, and which projects could not be read. Several matches are all returned; the server does not choose.

### 16-042: An admin can see and change which computer syncs which project, for any person, from one grid.
- Where: dashboard / Ticking and unticking
- What: Only an admin may use it. The admin chooses a person, then one of that person's computers or all of them; the grid appears once both are chosen. If there is only one editor, or a person has only one computer, it is chosen already. A person with no computer shows one choice, "no computer yet". The rows are every active project by name; the columns are the chosen computers. Each cell shows whether the project is ticked on that computer and whether the tick is upload-only. Ticking here is exactly the same as the editor ticking it themself. Each computer's column also lists the person's other computers, to copy a plan from.
- Flag: several ways in: the editor's own ticking and this admin grid

### 16-043: Beside the grid the admin sees what is needed to tick wisely: each person's status, which computers cannot be ticked, sizes and free space, and which projects are archived.
- Where: dashboard / Ticking and unticking
- What: Shown with the grid: each person's worst status across their computers (green, amber or red; empty if never reported); which people have only wired computers, and which computers are wired, whose cells cannot be ticked; each project's proxy size on the NAS and each computer's free disk, so a tick that would not fit is warned about before it is made (a project never counted shows nothing, meaning "cannot say"); the archived projects (with a warning, when the list could not be read because the server was busy, rather than claiming none is archived); how many people tick each project, for the archive confirmation; and the number of computers in the whole studio.

### 16-044: A studio can choose to let each editor reach on the NAS only the projects they work on.
- Where: accounts-privacy-legal / What each person may see and reach
- What: When the site turns this on, each project gets its own access group on the NAS. An editor is in the group of every project they have ticked on any of their computers (full or upload-only) that is not archived, plus every project an admin granted them; grants are the only way in for editors who only have wired computers. ### 16-051: An admin can restore a project's missing files from a snapshot into a new folder beside the projects, which overwrites nothing and is never sent to any editor.
- Where: server-install-and-running / Snapshots, restoring and the server's disk
- What: The files missing from the project, and with the option "also bring back the ones that are there but different" also the changed ones, are copied out of the snapshot into a new hidden folder at the top of the project tree, named with the date and time and holding a folder with the project's name, at the same places inside. That folder is not a project and is not synced to anyone. Nothing existing is overwritten, deleted or given a new owner, and file dates are kept. The restore is recorded (when, who, project, snapshot, how many files, size, where, failures) in a history of the last 20 restores, and in the audit trail. N file(s) are there with different contents. Nothing was changed.").

### 16-052: The server can rehearse a restore by itself: it brings one file back from a snapshot and checks it is byte for byte the same.
- Where: server-install-and-running / Snapshots, restoring and the server's disk
- What: From the newest snapshot (or one named), the first file between 1 byte and 64 MB is copied to a scratch place, compared with the original byte for byte, and the copy deleted (scratch left by an interrupted rehearsal is cleared first). The result reads "restored one file out of this snapshot and it came back byte for byte" or "the file that came back is NOT the file in the snapshot". A good result records today as the restore date on the protection panel; a bad one records nothing there. Every rehearsal is kept in a history of the last 20 and in the audit trail. Refusals: no snapshots visible ("this server cannot rehearse a restore: <reason>"); the snapshot holds no project tree where expected; no file small enough ("under 64 MB"); a copy error.

### 16-066: On Synology, the dashboard manages editor accounts through DSM and installs sign-in keys itself, with the NAS's own rules and pitfalls spelled out.
- Where: server-install-and-running / Installing on a NAS
- What: Facts and behaviour on Synology DSM 7.2 or later:
  - DSM must offer the web interfaces for sign-in, users, groups, group membership, user homes, secure file transfer and shared folders in the expected versions, or everything is refused with "this DSM does not offer the web API shapes CC Sync provisions with: ... Provision editors in DSM's Control Panel instead ..."; a box that does not answer that question is "... this does not look like a DSM 7 box".

  - Deleting an editor always warns that DSM deletes the account's home folder with it.
