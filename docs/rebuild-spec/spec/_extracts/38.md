# Extract of inventory section 38

## Items

### 38-001: The Footage Sorter on a single computer asks nobody to sign in; the one inside the dashboard knows who is asking.
- Where: accounts-privacy-legal / What each person may see and reach
- What: In its stand-alone form the Footage Sorter is a program on one Windows computer, reachable only from that same computer, and anyone using that computer can do everything in it: no sign-in, no roles. When the Sorter is opened through the dashboard instead, it sits behind the dashboard's sign-in and knows who is asking.
- Flag: differs: the stand-alone form has no notion of who is using it; the dashboard form does.

### 38-002: The Sorter never moves, renames or deletes footage on its own; it only plans.
- Where: footage-sorter-and-camera-cards / Moving footage on the NAS
- What: Sorting clips into folders only records an intention. No file in the source folders or in the studio's final folder tree is moved, renamed, overwritten or deleted by the Sorter itself. The only things it makes there are empty folders that a card copy is about to land in, and the one note described in 38-073. Footage is moved only by the separate mover (38-028 to 38-031), started by a person, or (in the dashboard form) by an admin on the server.
- Flag: differs: in the stand-alone form a person runs the mover by hand on the Windows computer; in the dashboard form an admin starts the moves on the server itself.

### 38-003: Every change to the sorting plan is kept as a dated copy.
- Where: footage-sorter-and-camera-cards / Sorting into shoots, people and cameras
- What: The plan (which clip goes to which folder, which calendar event points at which folder, which folders are planned, which shoots are dismissed) is saved after every edit, and each save also keeps a dated copy of the whole plan. The newest 200 copies are kept; older ones are deleted. Nobody is offered a way to restore one from the Sorter itself.

### 38-004: The folders the Sorter works with.
- Where: footage-sorter-and-camera-cards / The sorter page
- What: The Sorter works with three kinds of folder:
  - **source folders**: where footage arrives (camera dumps); there can be several;
  - **the final tree**: the studio's finished folder structure (on this studio, the project drive);
  - **the staging folder**: where a camera card is copied when it is not sorted straight into the final tree; when none is set it is the first source folder.
  The final tree is always browsed too, so footage already sorted stays visible and can still be sorted again. Without a final tree set, the folder tree is empty and exporting a move plan, auditing and final-mode card copies are refused, and the person is told no final tree is set.

### 38-005: A person can add or remove a source folder, with clear refusals.
- Where: footage-sorter-and-camera-cards / The sorter page
- What: Anyone using the Sorter can add or remove a source folder. Quotes around a pasted path are stripped, and comparisons ignore letter case. Refusals, each with its message: no folder given; "give the full path, starting at the drive"; "no such folder"; "that is a file, not a folder"; "that sits inside the destination"; "already a source root"; "already covered by <folder>" (it is inside an existing source folder); "that contains the existing root <folder>"; on removal, "not a source root" and "that is the only source root" (the last one cannot be removed).

### 38-006: Settings of the Sorter, by what they do.
- Where: footage-sorter-and-camera-cards / The sorter page
- What: Settings and their defaults:
  - the studio's time zone, used for every recording time and calendar time: UTC+8, as a fixed offset with no daylight saving;
  - the earliest date of calendar events fetched: 1 April 2026;
  - how often the calendar is refetched: every 15 minutes (5 minutes to one day allowed);
  - which of the studio's calendars are read: the account's main calendar;
  - per-day, per-camera time folders (38-024): off, with the camera labels A-CAM (Sony FX3), B-CAM (other Sony), BMCC (Blackmagic), DRONE, AUDIO;
  - whether a card copy brings the camera's proxies along: on, into a subfolder named "proxy";
  - spare room a card copy must leave on the target drive: 256 MB;
  - whether a card copy that could not be verified may count as done: off;
  - what happens when an incoming card file has the name of a different file already there: keep both (the incoming one is renamed); the alternative is to skip the incoming file;
  - how often the crew card list is refreshed: every 15 minutes;
  - the names given to card serial numbers (38-053).
  Only the calendar choice, refresh interval and start date, the source folders and the card names can be changed from the Sorter's own screens; the rest are set when the Sorter is set up.
- Flag: undetermined: the stand-alone form has no screen for most settings; whether the rebuild wants them on a screen is the owner's call.

### 38-007: A person can rescan the footage, and sees the scan's progress and warnings.
- Where: footage-sorter-and-camera-cards / The sorter page
- What: A scan reads every source folder plus the final tree and lists every clip. Only one scan runs at a time; asking again while one runs says it is running and shows the previous count. While it runs the page shows a live clip count; afterwards the clip count, total size, when it started and finished, any error, up to 50 warnings (a source folder that is unavailable or is not a folder, a folder that could not be read), and a one-line account of footage found moved by hand (38-014). A scan never changes footage. After each scan the Sorter also catches up on moves the mover has made (38-031) and notes which known copies are no longer where they were.

### 38-008: Folders and files the scan always ignores.
- Where: footage-sorter-and-camera-cards / Telling recordings apart
- What: A scan skips recycle bins, the operating systems' housekeeping folders (Windows system volume information, macOS index, trash and event folders, lost-and-found), macOS archive leftovers, any hidden folder (name starting with a dot), the duplicates quarantine folder (38-086), and the Sorter's own program folder. It skips the files Windows and macOS leave in folders (thumbnail caches, folder settings, macOS resource-fork companions whose names start with "._", sync tool databases).

### 38-009: The Sorter decides on its own that a numbered run of frames is one clip.
- Where: footage-sorter-and-camera-cards / Telling recordings apart
- What: A folder holding a numbered run of at least 3 frames with the same name pattern, in EXR, PNG, TIFF or DPX, becomes one clip (an image sequence). The whole folder is the clip and is always moved as one folder. Its recording time is a date found in its path with the time of day of its oldest file, else the oldest file's time. An image sequence is never matched to a look-alike clip (38-013).

### 38-010: The Sorter decides on its own which files make up one clip and which is the main file.
- Where: footage-sorter-and-camera-cards / Telling recordings apart
- What: Files in one folder that share a name (ignoring the extension) are one clip. The main file is chosen by type: video first (Blackmagic RAW, RED, MXF, MOV, MP4, M4V, AVCHD, AVI, MKV, MPEG, WMV), then raw stills, then other stills, then sound. A JPEG beside a raw still is its companion. Files in a folder called "proxy" or "proxies" (at any depth below it) join the clip of the same name as its proxy, with Sony's two-digit proxy suffix ignored for the match; a proxy with no matching clip becomes a clip of its own. Other files beside a main file join it as companion, metadata or other files (Blackmagic companion files, LUTs, Sony XML and housekeeping files, subtitles), with Sony's metadata suffix ignored for the match. A group with no recognisable type takes its first file by name as the main file. Each clip is one of video, sound, still or other, from its main file.

### 38-011: The Sorter decides on its own which camera a clip came from.
- Where: footage-sorter-and-camera-cards / Telling recordings apart
- What: A clip's camera is decided from, in order: a folder in its path named B-CAM or A-CAM; a path mentioning Blackmagic (or its camera names); a file name containing FX3; a Blackmagic RAW file; a file name starting "DJI_" (a drone); otherwise "other". For time folders (38-025) the camera model a Sony camera wrote into its own metadata beats the folder name.

### 38-012: The Sorter decides on its own when each clip was recorded.
- Where: footage-sorter-and-camera-cards / Clocks and file dates
- What: Recording time is taken from, in order of trust:
  1. a Blackmagic file name (camera letter, reel, month-day-hour-minute, clip number) gives month, day, hour and minute; the year comes from a date in the path, else a year in the path, else the file's modified time, moved back a year if that would put the shot more than 30 days after the file was written;
  2. the Sony camera's own metadata file, which also gives the duration, the recording's unique id and the camera model;
  3. a date in the file name or path, with the time of day from the modified time; if the modified time falls on a different day than the name says, the video's own creation time is read instead;
  4. the file's modified time.
  A sound recorder stamps a file when it closes it, so when a WAV's time came from its modified time, its start is moved back by its length. Every time is shown in the studio's time zone (38-006).

### 38-013: A clip keeps its identity when it is copied or moved.
- Where: footage-sorter-and-camera-cards / The record of every copy
- What: The Sorter recognises the same recording wherever a copy of it lands, so assignments and backup records follow it. In order of trust: a Sony clip by the unique recording id its camera wrote; an image sequence by its folder name, file count and total size; anything else (Blackmagic, drone, sound, stills) by its name (case ignored), the main file's size and the recording day. A weaker "look-alike" link pairs two clips with the same name and recording day (for example an FX3 recording to both card slots at once, whose ids differ slightly); it only counts when the main file sizes also match, and is never used on its own.

### 38-014: Footage moved by hand outside the Sorter is noticed after a scan, and the plan follows it.
- Where: footage-sorter-and-camera-cards / Moving footage on the NAS
- What: After every scan, without touching any file, the Sorter works out what happened to clips that were moved or renamed by hand:
  - a clip found at exactly one new place keeps its assignment ("re-keyed"); none found is "gone", several is "ambiguous", and both are left untouched;
  - a clip now inside the folder it was assigned to (or a time folder of it) is marked done ("found in place");
  - a clip already done that a person then moved elsewhere in the final tree: the hand move wins, and its assigned folder becomes where it now is ("moved by hand, adopted"); if another copy is still in the assigned folder it is counted as a duplicate and left alone; a clip never yet moved is left for the next move plan;
  - when every clip of one folder went to the same other folder and none is left behind, it is a whole-folder move: planned folders, placeholders, calendar links and assignments under it are renamed to match, and the mover's checks follow the folder to its new place.
  The person is shown one line, for example "3 re-keyed, 2 found in place, 1 moved by hand, adopted, 1 folder move(s): A -> B, 1 duplicate copies left alone, 4 gone, 1 ambiguous".

### 38-015: An operator can also re-attach orphaned assignments by hand.
- Where: footage-sorter-and-camera-cards / Moving footage on the NAS
- What: A separate operator tool finds assignments whose clip no longer appears in the scan, looks the recording up in the record of copies, and re-attaches the assignment to its current final copy, only when that copy is in the scan and has no assignment of its own. It prints counts (total, still fine, re-attachable, no identity, no final copy, already taken, not in the scan) and up to 10 examples, and warns that a rescan including the final tree is needed first, or those stay orphaned, when some point at footage the scan does not hold. It is a dry run unless asked to apply; applying keeps a backup copy of the plan first and asks for the Sorter to be restarted or rescanned.
- Flag: built twice: the automatic follow-up after every scan (38-014) does the same job.

### 38-016: Folder names are cleaned and impossible names refused.
- Where: footage-sorter-and-camera-cards / Sorting into shoots, people and cameras
- What: Every folder name a person gives is cleaned the same way: backslashes become slashes, empty parts are dropped, trailing dots and spaces are removed from each part (Windows would drop them silently). Refused as invalid: an empty name, a drive letter or network path, a part made only of dots, a part containing < > : " | ? * or a control character, and a part whose name before its first dot is a name Windows reserves (CON, PRN, AUX, NUL, COM1 to COM9, LPT1 to LPT9).

### 38-017: A person can assign clips to a folder, or take them back.
- Where: footage-sorter-and-camera-cards / Sorting into shoots, people and cameras
- What: Any number of clips can be assigned to one folder of the final tree, in one of two ways: **keep the card's layout** (each file keeps its path below its source folder) or **the studio's convention** (38-026). Assigning again replaces the earlier choice; unassigning returns clips to unsorted. Refusals: no clips chosen; an invalid folder name (38-016). Each change shows at once the time folders it would produce (38-024).

### 38-018: A person can plan folders before any footage exists, including greyed-out placeholders.
- Where: footage-sorter-and-camera-cards / Sorting into shoots, people and cameras
- What: A planned folder appears in the folder tree, marked as planned, before it exists on disk, and is created by the next move (even empty, so an episode's skeleton gets made). Many can be planned at once (duplicates ignoring case are skipped, invalid names listed back). A folder can instead be planned as a **placeholder**: shown greyed out in the tree but not created on disk until a clip is assigned into it.

### 38-019: A person can take a folder out of the plan; a folder on disk is never deleted.
- Where: footage-sorter-and-camera-cards / Sorting into shoots, people and cameras
- What: Removing a folder takes it and everything beneath it out of the plan: planned folders, placeholders, assignments into it (those clips go back to unsorted; no file is touched) and calendar links to it. A preview first shows how many planned folders, clips and calendar links it would undo, and whether the folder exists on disk with how many files (counted up to 2000). A folder that only exists on disk is refused: "This app never deletes inside the final tree: remove it in Explorer, then reload." A folder nothing refers to: "nothing here to remove".

### 38-020: A person can move or rename a folder in the plan, but never one that holds footage on disk.
- Where: footage-sorter-and-camera-cards / Sorting into shoots, people and cameras
- What: A planned folder can be renamed or moved under another parent (or to the top of the final tree), carrying its planned subfolders, placeholders, assignments and calendar links with it. Refusals, in order: not a usable folder name; "a folder cannot be moved inside itself"; the folder holds files on disk ("This app never moves anything inside the final tree: move it in Explorer, then reload", files counted up to 2000); "is not a folder this app can move" (nothing refers to it and it is not on disk); "already exists" (a planned folder of that name); "already exists on disk and is not empty". An empty folder on disk may be moved in the plan; the empty original is reported as left on disk, not deleted. Moving a folder onto itself does nothing and says so.

### 38-024: Per-day, per-camera time folders, when switched on.
- Where: footage-sorter-and-camera-cards / Sorting into shoots, people and cameras
- What: With time folders on (off by default), each assigned folder gets one subfolder per day and camera, named "<YYYY-MM-DD> <HH.mm>-<HH.mm> <camera label>", for example "2026-08-09 08.54-15.06 A-CAM" (a dot instead of a colon, which Windows forbids). The range runs from the earliest to the latest recording time of those clips that day. No time folder is made for: the "keep the card's layout" choice, image sequences, stills, other files, clips with no recording time, clips with no camera label; those land straight in the assigned folder. An existing time folder is reused and never renamed: if one for the same day and camera already holds any of these clips, its name stays even when the new range is wider, and the person is warned "range widened: <fresh name> reused <existing name>". A folder with exactly the new name that holds none of these clips belongs to another shoot, so the new one becomes " (2)", " (3)" and so on. Before anything is moved the person sees, per assigned folder, each time folder it implies with its clips, size, whether it already exists and which existing one it merges into. What is on disk is re-read at least every 30 seconds, and at once after a move plan, a card copy, a scan or an audit.

### 38-025: The Sorter decides on its own which camera label a clip's time folder gets.
- Where: footage-sorter-and-camera-cards / Sorting into shoots, people and cameras
- What: Sound clips get the sound label. Stills, image sequences and other files get none. A Sony model that is an FX3 (but not an FX30) gets A-CAM; other Sony cinema, mirrorless, camcorder and compact models get B-CAM; Blackmagic RAW or a Blackmagic camera gets BMCC; a file name starting "DJI_" gets DRONE; a camera folder named A-CAM or FX3 gets A-CAM, one named B-CAM gets B-CAM; anything else gets no label (and so no time folder).

### 38-026: A person can export a move plan, and is told what it holds before anything moves.
- Where: footage-sorter-and-camera-cards / Moving footage on the NAS
- What: Exporting builds the list of moves for every assignment not yet done whose clip is in the last scan. Where each file goes:
  - an image sequence moves as one whole folder;
  - "keep the card's layout": each file keeps its path below its source folder;
  - "the studio's convention": main files go straight into the folder; proxies (from a folder named proxy or proxies, or a Sony card's proxy folder) go into a "Proxy" subfolder, keeping any deeper path; a Blackmagic companion file stays beside its clip;
  - with time folders on, into the time folder under the assigned folder.
  Every planned folder is included even with nothing in it (so an episode skeleton is made empty), except placeholders, which wait for a clip. Clips that are only on a camera card in a reader are left to the card copy, and assigned clips that are neither scanned nor on a card are reported as missing. The person is told the number of moves and folders, total size, collisions, files already in place, duplicates, missing clips and the time folders.

### 38-027: A move plan leaves out what is already in place and flags what clashes.
- Where: footage-sorter-and-camera-cards / Moving footage on the NAS
- What: Before the plan is written, the export removes moves whose destination already holds the identical file (same size; for files of 64 MB or less also the same content), and keeps only one of two identical files headed for the same place (the same card staged twice), reporting both lists. Anything not identical (a different file already at the destination, or two different files for one name) is a **collision**: it is reported and the mover will refuse it.

### 38-028: A person rehearses the moves first, and nothing moves until the rehearsal is clean.
- Where: footage-sorter-and-camera-cards / Moving footage on the NAS
- What: The mover is run by a person on the Windows computer, by default as a rehearsal that moves nothing. It checks every planned move: both paths are complete and clean, source and destination differ, a folder is not moved into itself, every destination is inside the final tree, no two moves share a source or a destination, the source exists with exactly the planned size (a folder's size counted the way the scan counts it), the destination does not exist ("COLLISION - dst already exists"), and the destination's parent is not a file. It shows files and folders to move, moves already done, total size and folders to be created (first 25 of each list on screen, all in a saved report). A clean rehearsal ends "RESULT: CLEAN - every source exists with the expected size and no destination path is occupied." and allows the real move of exactly that plan for the next 60 minutes. Otherwise "RESULT: N PROBLEM(S) - nothing may be moved." with up to 50 problems listed. Paths may hold brackets, spaces, Chinese characters and be very long. A missing, empty or unreadable plan stops it with "MOVER ABORTED ... Nothing was deleted or overwritten."

### 38-029: The real move never deletes or overwrites, stops on the first error, and resumes where it stopped.
- Where: footage-sorter-and-camera-cards / Moving footage on the NAS
- What: The real move is refused unless a clean rehearsal of exactly the same plan is under 60 minutes old (and not dated in the future): "REFUSED - no valid dry-run gate" with the reason, the rehearsal to run, and "Nothing was moved." It then re-checks every pending move, and refuses outright if anything fails ("NOTHING was moved"). It creates every planned folder (so a folders-only skeleton is still made), then moves one item at a time, checking just before each that the destination is still free and the source still there, and just after that the destination exists with the right size. The first error stops the run: "RESULT: STOPPED ON FIRST ERROR" with the failed item, the reason, how many were completed, skipped and not attempted, what is still to move, and "Nothing was deleted or overwritten. Fix the cause, re-run the dry-run, then run again: already-moved items are skipped." Every move is recorded as it happens, so a crash loses nothing: moves already done are skipped next time, and a move interrupted after the file arrived is recognised as done. It never copies, never overwrites, never deletes, and never removes emptied source folders (they are listed "REPORTED ONLY, nothing is deleted"). Progress is shown every 25 moves. Success: "RESULT: OK - N item(s) moved"; a plan with nothing left: "Nothing left to move - the plan is already complete."

### 38-030: A person can verify every move ever made, and gets a list of where everything went.
- Where: footage-sorter-and-camera-cards / Moving footage on the NAS
- What: Verifying checks every move ever recorded (or only this plan's, or only those since a given point): each destination must exist with the recorded size and its source must be gone ("dst MISSING", "size mismatch", "src STILL EXISTS after move"). A file the mover later moved again is followed (up to 64 times), and a file under a folder later moved by hand (38-014) is checked at its new place; both count as verified. It always rewrites a spreadsheet-readable list of every original path and where it went, which shows Chinese names correctly in a spreadsheet program. It ends "RESULT: ALL VERIFIED - every moved item is at its destination with the expected size and no source remains." or "RESULT: N PROBLEM(S)", lists source folders now empty, and saves a report. With nothing ever moved: "No journal found - nothing has been moved yet."

### 38-031: Once footage has moved, the Sorter learns it by itself.
- Where: footage-sorter-and-camera-cards / The record of every copy
- What: When the Sorter starts, after every scan, and when a person asks, it reads what the mover has done: each moved clip's staging copy becomes a final copy in the record of copies (keeping whether it was verified) and its assignment is marked done. Only the main file's move changes where a clip is recorded.

### 38-032: The Sorter keeps a record of every place a copy of every clip has been seen, and never forgets one.
- Where: footage-sorter-and-camera-cards / The record of every copy
- What: For each recording the Sorter records every known copy, each as one of: on a card, in staging, in the final tree, or elsewhere (a path in both the final tree and staging counts as final). Each copy notes when it was last seen, whether it is still there, how it was learnt (scan, card copy, move), whether it was verified and when, and whether it is damaged. Nothing is ever removed: a copy no longer found is marked absent and keeps its last-seen time. A rescan refreshes details but never erases a known one; where a recording first came from (card serial and name, card kind, session, first seen) is set once. A verified copy stores the content's fingerprint; if a later verified copy disagrees it is replaced (nobody is told). A record that cannot be read starts empty.

### 38-033: Each clip shows how safe it is.
- Where: footage-sorter-and-camera-cards / Backed up and safe to format
- What: Each clip on screen carries its backup state, from present, undamaged copies only: **final, verified**, **final**, **staging**, or none. A clip the Sorter cannot find under its own identity may borrow the state of a look-alike (same name, same day, same main file size; the safer one wins), and the screen says the state came from a look-alike. Each clip also shows where it sits now: in the final tree, in staging, on a card, or elsewhere.

### 38-034: A person can look a clip up in the record of copies.
- Where: footage-sorter-and-camera-cards / The record of every copy
- What: The record can be searched by a clip on screen, by any path a copy is known at, or by name (letter case ignored, at most 50 results), and each result shows its copies and backup state. A summary shows how many recordings and copies are known, copies per place, and how many recordings have a verified final copy.

### 38-035: A person can audit the whole final tree into the record of copies.
- Where: footage-sorter-and-camera-cards / The record of every copy
- What: An audit reads the whole final tree in the background and records every clip found there as a final copy. Only one runs at a time (asking again shows the running one). Its progress shows start and finish, clips so far, clips linked, and any error. Refused when no final tree is set.

### 38-036: Clips show thumbnails, made by themselves.
- Where: footage-sorter-and-camera-cards / Thumbnails and hover filmstrips
- What: Each clip gets a thumbnail 320 pixels wide, kept for a day by the browser. It is taken from, in order: a playable proxy, a playable main file, a still's JPEG companion, an image, any playable file; for an image sequence, its first frame. A video thumbnail is the frame at 1 second, else the first frame. Sound, Blackmagic RAW without a proxy and project files get none. While one is being made the page shows it pending and asks again; a thumbnail clicked on jumps the queue. A thumbnail that failed stays missing until the Sorter restarts. A card being copied is never read for thumbnails (they stay pending), and on a Sony card the camera's own thumbnails are used straight away.

### 38-037: A person can play a clip in the browser.
- Where: footage-sorter-and-camera-cards / The sorter page
- What: A clip can be played (and scrubbed) in the browser: the proxy when there is one, else the main file, else any playable file (MP4, M4V, MOV, MKV, WebM, WAV, MP3, M4A, AAC, FLAC, OGG). Refusals: "card is being copied" (a card is not read while it is copied); "no playable file for this clip"; "file unavailable".

### 38-040: A person can connect the studio's Google calendar, read-only.

### 38-041: Calendar events are fetched by themselves and survive going offline.
- Where: footage-sorter-and-camera-cards / Sorting into shoots, people and cameras
- What: While connected, events are refetched every 15 minutes (setting, at least 5), and on request. Events from the start date (default 1 April 2026) to one year later are read from each chosen calendar; repeating events are shown as their single occurrences; cancelled and undated events are dropped; an all-day event runs from midnight of its first day to midnight after its last. If a fetch fails, the error is shown and the last events are used, so the Sorter keeps working offline.

### 38-042: Without Google, events can come from an exported calendar file.

Times without a zone are taken as the studio's time zone; date-only events are all-day. ### 38-043: The Sorter decides on its own whether a shoot is b-roll or an interview.

### 38-044: The Sorter decides on its own which folder a calendar event belongs to.
- Where: footage-sorter-and-camera-cards / Sorting into shoots, people and cameras
- What: From the studio's list of episodes, its naming rules, and the roster (38-047), in order of trust:
  1. the first rule whose pattern matches the title: a rule can skip the event, force the kind, rename the interviewees branch, name the episode, or send it to a folder outside the episode tree;
  2. an episode's alias found in the title (leftmost, then longest);
  3. a roster name in the title (Chinese name, the given name alone for 3-4 character names, the English name and each English word of 4+ letters other than titles, English as whole words): with an episode known a person in that episode is preferred; with none, only a name in exactly one episode decides it;
  4. for interviews only, an existing interviewee folder whose first word appears in the title (longest wins).
  The folder is "<episode>/B-roll/<subject>" or "<episode>/Interviewees/<subject>". The subject is the person's folder name "<Chinese> <English>" when a person was found, else the title with alias and the words interview, broll, filming, online removed; characters Windows forbids become spaces. An existing folder in the same place whose name equals, starts with, or is the start of the subject is reused (the shortest). A b-roll event with no subject goes into the episode's B-roll folder; an interview with no subject is not placed. Each placed event shows the reason ("route /.../", "title matches /.../", "\"<name>\" is in the <episode> roster", "\"<name>\" already has a folder in <episode>"). ### 38-045: The person is told why an event got no folder.

### 38-046: The Sorter suggests which shoot each clip belongs to, from the calendar.
- Where: footage-sorter-and-camera-cards / Sorting into shoots, people and cameras
- What: Only events with a folder (linked or worked out) suggest anything. **High** confidence: the clip was recorded from 1 hour before the event's start to 2 hours after its end. **Low**: the nearest event with a folder on the same day. Among candidates a timed event beats an all-day one, then the closest, then the shorter, then the earlier. ### 38-047: An admin can build the roster of who appears in which episode from the planning sheet.

### 38-048: An operator can have recordings listened to for names and self-introductions.
- Where: footage-sorter-and-camera-cards / Placing sound recordings
- What: A tool run by hand listens to sound clips (by default only unassigned ones; optionally all, a number, or only those under chosen folders) and notes who is named on them. Clips with an identical copy elsewhere go last, otherwise smallest first. It listens in 5-minute windows and stops at the first roster name or self-introduction, unless asked to listen to the whole file; a cap on how far in can be set. It is resumable: work is kept after each window, a clip already heard is not heard again unless asked, and a file that moved (same name, size, and length within 1 second) reuses what was heard. Missing files and files under 5 seconds are skipped. A roster person's Chinese name (3+ syllables) matches when heard with the same sounds, even written with other characters; an English name matches whole, or by two of its parts of 5+ letters; a single usable part is a weak "partial" match; a name in two episodes is marked ambiguous. Self-introductions are recognised from "我是", "我叫", "這位是", "我們今天訪問", "my name is", "i am called" followed by a name. Each finding keeps the quote and its time. It never assigns anything.
- Flag: differs: run by hand; the rebuild's footage-in runs on its own.

### 38-049: The Sorter decides on its own whose interview a sound recording is, and shows its evidence.
- Where: footage-sorter-and-camera-cards / Placing sound recordings
- What: Each sound clip that has been listened to is scored against several kinds of evidence, each proposing a folder with a score (the same folder proposed twice gets the higher score plus 0.08, at most 1):
  - an identical file (same name and size) already filed: 0.92 in an interviewee folder ("An identical file is already filed here"), else 0.3;
  - what was said matching an interview transcript in the studio's transcript archive (compared in runs of 4 words or Chinese characters; a match needs at least 6 % of runs and 25 runs shared): 0.85 (up to 0.95 at 25 % and 120 runs), 0.55 at 12 % and 60 runs, else 0.3; evidence "<n>% of what was said is in the transcript of <name> (<episode>)", noting whether the folder came from the roster, two folders carry that name, or no folder carries it;
  - a roster name heard: 0.72 (0.35 for part of an English name); a name in two episodes gives a folderless 0.4;
  - a self-introduction: 0.6 with a folder, 0.3 without ("Said: ...");
  - the calendar suggestion: 0.7 if high, else 0.35.
  The interviewee folder for a transcript match is the folder whose name contains the person's Chinese name, or two English name parts, or one distinctive English part of 4+ letters that is not a common Taiwanese surname. Confidence: high at 0.75 or more, medium at 0.45, else low. Each clip shows ranked candidate folders with evidence, the main language heard, how much was listened to, where the clip is filed now, its assignment, and **disagrees** when a high-confidence candidate backed by a copy or a transcript points elsewhere than where it is filed and no identical copy sits where it is. Nothing is assigned; the person decides.

### 38-050: A sound suggestion is offered only where the calendar says nothing.
- Where: footage-sorter-and-camera-cards / Placing sound recordings
- What: A sound suggestion (shown with a note symbol) is offered for a sound clip that is not assigned, has no calendar suggestion, whose top candidate has a folder and is not low confidence, and that is either filed nowhere or filed where the sound confidently disagrees. It shows high or low, a summary, the moment something was heard and what, and a reason (at most 300 characters).

### 38-051: A person can open what was heard on one recording, and see its copies.
- Where: footage-sorter-and-camera-cards / Placing sound recordings
- What: For one sound clip the person sees its full scoring and what was heard: how much was listened to, its length, whether it was taken from a moved copy, and each window's start, length, language and lines with times to a tenth of a second. The copies of a sound clip (other sound clips with the same name and size and, where known, length within 2 seconds) are listed with where each is and whether it is assigned. An overview shows the transcript archive's size, the last listening run, how many sound clips there are, and per clip its top candidate (score to two decimals), disagreement, and whether a name or introduction was heard. New transcripts in the archive are picked up within about a minute.

### 38-052: The crew record on their phones which cards they used, and the Sorter keeps a copy.
- Where: footage-sorter-and-camera-cards / Backed up and safe to format
- What: The crew record on their phones which camera cards they used on which day, on the studio's own card tracker site. The Sorter keeps a copy so its card report works offline, refreshes it every 15 minutes (and on request), and tells the site one thing back: a card is "backed up" or "used". Without the tracker's access key the card list is still read but not the usage days, and the status says so. Each refresh gives up after 20 seconds; a failure leaves the last copy in place and is shown in the status (not authorised, not set up, or another error). The status shows the site, whether it is set up, last refresh, last error, number of cards, usage rows and the serial names.

### 38-053: A person can name a card by its serial number.
- Where: footage-sorter-and-camera-cards / Recognising cards and drives
- What: A card in a reader is known by its volume serial; a person names it with the label written on it, which must look like 1 to 4 letters, a hyphen and 1 to 3 digits (for example SD-1); the serial must be 2 to 40 letters, digits, hyphens or underscores. Both are upper-cased; an empty name removes it; naming a serial again replaces the old name. If that card is in a reader, its size is learnt for later guesses. Any finished copy of that card is checked again at once, so a card named after its copy finished is marked backed up straight away.

### 38-054: The Sorter guesses which card a freshly formatted card is.
- Where: footage-sorter-and-camera-cards / Recognising cards and drives
- What: Cameras give a card a new serial at every format, and some USB readers report their own, so for an unnamed serial the Sorter ranks the studio's cards: a Blackmagic RAW card can only be a CF card, a Sony card only an SD card, drone and sound either; inactive cards and cards already in another reader are excluded, as is a card whose learnt size differs by more than 2 %. Score: +2 if the crew recorded that card used on a day this footage was shot ("used <days>"), +1 if it is marked used rather than backed up ("marked used"); "same size" is noted. One card is suggested only when the top score is at least 2 and nothing ties; the full list is shown too.

### 38-055: A card is marked backed up by itself once every clip on it has a copy.
- Where: footage-sorter-and-camera-cards / Backed up and safe to format
- What: When a card's copy finishes, and the card is named and every clip on it has a known copy, the tracker site is told the card is backed up. Otherwise nobody is told on screen; the reason ("not mapped to a card label", or "stays marked used: N of M clips have no copy yet") is only written to the Sorter's log. A person can also mark one or more cards backed up or used by hand. Refusals: no cards given; a tracker that is not set up, refuses the key, or fails.

### 38-056: A person sees a card report: every card, every shooting day, and what is unaccounted for.
- Where: footage-sorter-and-camera-cards / Backed up and safe to format
- What: The report shows:
  - the studio's cards in order (family, then number): backed up or not, active, last change and by whom, last used, serials named to it;
  - shooting days, newest first: each card used that day, who recorded it, its backed-up state, and the footage known to have come off it that day (clip count, the folders it landed in with time folders and proxy folders folded into their parent, staged and final copy counts); days before the calendar start date are not compared;
  - each day's calendar events (dismissed shoots left out) with their folders, events with a folder first, then timed, then all-day, then repeating all-day; a day's likely event (the only one with a folder, "strong", or failing that the only timed one, "weak"); an event spanning days appears on each (at most 60);
  - **unrecorded**: footage that came off a named card on a day the crew did not record that card;
  - **unmapped serials**: serials seen on copied clips that have no name yet, with volume label, kind, clip count, last seen, the last 4 days, and a hint (CF for Blackmagic RAW, SD for Sony), most recent first.

### 38-057: A card is recognised by what is on it, never by its drive letter.
- Where: footage-sorter-and-camera-cards / Recognising cards and drives
- What: The Sorter decides on its own what kind of card it is, from its content, first match wins:
  1. **Sony**: the camera's clip folder (PRIVATE, M4ROOT, CLIP) exists, even empty; stills in the card's DCIM folder are taken too;
  2. **drone**: DCIM holds a folder named three digits plus MEDIA (for example 100MEDIA) with MP4 or MOV files;
  3. **Blackmagic RAW**: a BRAW file in the card's top folder (macOS "._" companions ignored); the whole card is read;
  4. **sound recorder**: WAV files in the top folder whose names match the studio's recorder patterns (a DJI Wireless PRO name, or six digits, underscore, three digits).
  On a Sony or drone card, matching recorder WAVs in the top folder are taken too. A card image mounted as a folder can be given instead of a drive letter. Nothing recognisable: "nothing recognisable on <drive> (no Sony/BRAW/DJI/audio structure)". The volume serial, label and size are read on Windows; elsewhere they stay empty.

### 38-058: On Windows, inserting a card opens the Sorter on that card by itself.
- Where: footage-sorter-and-camera-cards / Recognising cards and drives
- What: A watcher in the Windows notification area starts at sign-in (only one can run: "Auto Backup Utility is already running (see the system tray).") and starts the Sorter if it is not running. Every 3 seconds, unless paused, it looks at every removable and internal drive for a card it recognises (38-057). A card is noticed when it appears or its contents change; a card sitting still never fires again; a card pulled and put back always fires; a card already handled and left in the reader at sign-in is not processed again. On a card:
  - if a Sorter tab is open, every open tab switches to that card, and the notice says "<what> - showing in the sorter." (<what> is "Card on K:", "Drone clips on K:", "Blackmagic BRAW on K:" or "Loose audio on K:");
  - if none is open, it opens one on that card: "<what> - opening the sorter...". A tab that is just opening or reconnecting (within 30 seconds of being asked for, or 10 seconds of the last tab dropping) is waited for rather than opening a second;
  - "<what> - the sorter did not recognise it." (warning);
  - the Sorter cannot be reached: "<what> - but the sorter server is not running and could not be started." (error) and the card is tried again; or, with the old field copy switched on (the default), the old field copy starts instead (38-074 to 38-077), with "<what> - sorter unreachable, starting the old backup...".
  Removing a card is reported too. If the Sorter restarts, every card still in a reader is re-registered quietly, nothing opened. Its notes older than 60 days are deleted at start.
- Flag: differs: the watcher only recognises drone footage in the first numbered media folder (100MEDIA), while the Sorter accepts any.

### 38-060: Each inserted card is shown with its state, and the same card coming back is recognised.
- Where: footage-sorter-and-camera-cards / Recognising cards and drives
- What: Each card shows: drive, kind, serial, label, camera (up to two camera models seen on it, else the kind), state, clip count, size, when it was inserted and read, any error, warnings, damage counts, copy progress, capacity, which studio card it is and the guess. States: **scanning**, **ready**, **planned**, **copying**, **done**, **error**, **ejected** (the card was pulled). A card is read in the background; its clips appear when ready. There is one entry per card: reporting a card already being read, planned or copied returns that one. When the same card comes back (same serial, or same drive letter without one) after it was pulled, finished or failed, the old entry disappears (so its clips are never listed twice) and the new one keeps the old one's assignments. Closing a card (dismissing it) forgets its assignments; a pulled card keeps them, since it may come back. Closing is refused while it copies ("a copy is running for this card"). Rescanning is refused while it copies, and when the drive no longer holds a recognisable card ("<drive> no longer holds a recognisable card"). Clips the record of copies already knows a backup of are marked with that state on the card.
- Flag: undetermined: the stand-alone Sorter forgets every card when it restarts and relies on the watcher re-reporting them; whether the rebuild should remember cards across a restart is open.

### 38-061: Sony cards: proxies, housekeeping files and the camera's thumbnails; drones with unset clocks.
- Where: footage-sorter-and-camera-cards / What cameras and recorders write
- What: On a Sony card, the camera's proxies (in its proxy folder, named after the clip plus S and two digits) are attached to their clips, and the camera's own thumbnails (named after the clip plus T and two digits) become the clips' thumbnails. Housekeeping-only groups (BIM, BIN, SMI, PPN, TXT, DAT, IND or XML files with no footage) are dropped. A drone clip dated before 2020 is flagged as having a wrong date (the drone's clock was not set).

### 38-062: Every clip on a card is health-checked before the card can be copied, while it is still unformatted.
- Where: footage-sorter-and-camera-cards / Damaged and unfinished recordings
- What: Before a card is ready, each clip's main file (MP4, MOV, M4V, MXF, BRAW, R3D, Canon RAW, WAV, broadcast WAV, Sony unfinished RSV) is checked with a few small reads, one at a time; stills and image sequences are not. A clip is **damaged**, **suspect** or fine. The person is told, in these words:
  - "The file is 0 bytes." (damaged);
  - first MiB all zeros: "Reads as nothing but zeros (<size>). The camera never committed this clip; the footage may still be on the card, but only a raw image of the whole card can get it back. Don't format the card." or, when data exists later, "The first MiB is zeros (the header is gone). Data from about <size> before the end. Image the card before formatting it." (damaged);
  - a Sony unfinished recording: "An unfinished Sony recording (RSV, <size>): the camera never turned it into an MP4. Put the card back in the same camera and let it recover the clip; failing that, it can be rebuilt using a healthy clip from the same camera and settings. Keep the RSV either way." (damaged);
  - cut short: "Cut short: the '<box>' box claims <size> but the file ends <size> before that (<size> on disk)." plus, if it has no index either, that it will not open and the rebuild advice (damaged);
  - no index: "No index (moov box): it won't open. " plus the rebuild advice, plus, when the end is zeros, " The last <size> (<n>%) are zeros: the recording was cut off, and that part exists only on the card." (damaged);
  - the rebuild advice: for Blackmagic RAW, that the common repair tools do not handle BRAW, a BRAW recovery tool or service rebuilds the index from the frames using a healthy clip from the same camera and settings, "Keep this file exactly as it is."; otherwise that a repair tool can rebuild it using a healthy clip from the same camera and settings;
  - other video over 2 MiB ending in a zero MiB: "The last <size> are zeros: the recording may have been cut off." (suspect);
  - "Could not read the file: <error>" (damaged);
  - Sony only: "No M01.XML: the camera never closed this clip normally." or "The M01.XML is 0 bytes: the camera never closed this clip normally (it was likely rebuilt by the camera's recover function)." (suspect); "No proxy, although the other clips on this card have one." (suspect).
  Proxies get the same checks, always only suspect, prefixed "Proxy: ". Sizes read as GB with one decimal from 1 GB, else whole MB.

### 38-063: Every copy from a card is checked again, and damage the copy introduced fails the copy.
- Where: footage-sorter-and-camera-cards / Checking a copy
- What: After each part of a card copy, what landed gets the same checks, plus: "The copied <part> is not there: <path>", "The copied <part> is N bytes; the card's is M." (damaged for a main file, suspect otherwise), and "The copied M01.XML is 0 bytes although the card's is not." A problem the card's own file does not have counts as introduced by the copy (if the card is already gone, its earlier verdict stands in). A damaged copy is recorded as damaged and never counts as a backup, and damage the copy introduced fails the copy with "the copy of <clip> is damaged but the card's is not (<problems>): delete <path> and copy it again". Clips skipped as already present are checked too, because "present" only meant the same name and size.

### 38-064: A person plans a card copy, choosing final or staging.
- Where: footage-sorter-and-camera-cards / Copying a card
- What: Two kinds of copy:
  - **final**: only the clips assigned to folders, each to its place in the final tree;
  - **staging**: every clip (or the ones ticked) to the staging folder, always into per-day, per-camera time folders; clips that cannot have one (stills, no time, unknown camera) go into a folder named "<day> <card label, serial or drive> loose".
  Refused while the card is still being read ("still scanning the card"), and when the target folder is not set. In a final copy, unassigned clips are split into "unassigned but backed up" (a final copy of the right size exists; no warning) and "unassigned" (a wipe would lose them). Each destination folder is a group showing counts and sizes per state, with clips to copy first, then clashes, then skips. Proxies come along unless switched off for this copy. A destination path longer than 240 characters warns "long path (<n>): <path>". The target drive must hold the bytes to copy plus 256 MB to spare, else the plan is not OK: "not enough free space on <root>: need N + M margin, have F" (unknown free space counts as enough).

### 38-065: The Sorter decides on its own, clip by clip, whether a card clip needs copying.
- Where: footage-sorter-and-camera-cards / Copying a card
- What: Judged from the main file at its planned destination:
  - nothing there: **copy**;
  - the same recording there (known from the record of copies, or for Sony from its recording id) but smaller: **copy** to finish a partial copy (only the difference counts toward space);
  - the same recording there, not smaller: **skip**;
  - a different or unknown clip of the same size: **skip**;
  - a different size: **clash**; the incoming file is then renamed (or skipped, per the setting);
  - an image sequence whose folder name is taken: **clash**, never merged blind;
  - nothing there, but the same recording already sits at another final place with the same size: **elsewhere**: offered but **not ticked by default** and not counted toward space; it may offer linking instead of copying (38-073).

### 38-066: A plan goes stale when assignments change.
- Where: footage-sorter-and-camera-cards / Copying a card
- What: A card copy runs the plan the person reviewed, and only that. If the plan was replaced, or any assignment of its clips changed since it was made, the copy is refused: "that plan is stale: plan again" or "assignments changed since the plan was made: plan again". A copy with no plan: "plan first".

### 38-067: A person starts a card copy, and the copy is verified against the card.
- Where: footage-sorter-and-camera-cards / Copying a card
- What: Starting a copy (optionally only the ticked clips) puts the card in **copying**. Every file is copied and then verified against the card's content. Refusals: "a copy is already running for this card"; copying is not possible on this computer (with the reason); verification is switched off on this computer (unless unverified copies are allowed, 38-006). In a final copy the person may choose to stage the unassigned clips in the same run. Copies of one card run one after another; different cards copy side by side, and a card pulled and put back waits for its earlier copy. Main files go before their proxy folder. A file whose planned name differs from its name on the card is not copied, and nobody is told. Progress per destination: files done, verified, failed, bytes; the state shows **verifying** once copying is finished and checking runs. Clips skipped as present are recorded as copies at once.
- Flag: differs: a quick "stage this card now" copy skips the review and does not apply the copying-not-possible and verification-off refusals.

### 38-068: How a card copy ends, and what the person is told.
- Where: footage-sorter-and-camera-cards / Checking a copy
- What: Each destination ends **done** (every file copied and verified), **done, unverified** (finished but some files not verified, or completion could only be confirmed by name and size), or **failed** (files missing or of the wrong size, or the copy failed). Unverified does not fail the copy but is shown as "some unverified". If a copy shows no sign of starting within 2 minutes, stops for 1 minute, or is copied but not verified within 3 minutes, the Sorter stops waiting and checks the destination by name and size itself; there is no overall time limit. **Cancel** lets the current folder finish and starts nothing more (remaining ones show cancelled); pulling the card also stops further folders. The copy ends **cancelled** (card back to ready), **error** (the first error is shown, or "copy failed"), or **done**; a pulled card stays ejected. A main file that did not land shows "not copied" with the reason. Each copied main file is recorded in the record of copies with the card's serial, label and kind as its origin; every completed folder is added to a lasting copy history (source, destination, size, verified, fingerprint, renamed name).

### 38-069: After a card copy, the plan follows the footage.
- Where: footage-sorter-and-camera-cards / Copying a card
- What: A clip copied in a final copy is marked done in the plan. A clip copied to staging keeps its assignment on its staged copy, so the next scan shows it assigned and the next move plan takes it to its folder.

### 38-070: Card copies are only trusted when verified, and the card watcher installs itself to start at sign-in.
- Where: footage-sorter-and-camera-cards / Installing the card watcher
- What: On Windows, an installer that can be run again sets the computer up so every card copy is verified against the card and copies run one at a time, puts the card watcher in the Startup folder so it starts at sign-in (clearing a "disabled in Task Manager" mark if one is set), and reports whether the A-CAM and B-CAM target folders exist. It ends "Install complete." and can remove the startup entry again. The Sorter warns when card copies cannot be verified on this computer (and refuses them, 38-067), and when copies can then only be checked by presence and size.

### 38-071: Facts about the studio's cameras and cards the Sorter relies on.
- Where: footage-sorter-and-camera-cards / What cameras and recorders write
- What: A Sony card keeps clips, proxies and thumbnails in separate folders under PRIVATE, M4ROOT, and writes a metadata XML per clip holding the recording time with its zone, duration, a unique recording id and the camera model; an FX3 recording to both card slots gives two clips whose ids differ slightly. A drone keeps clips under DCIM in numbered MEDIA folders and its clock may be unset (dates before 2020). A Blackmagic camera writes BRAW files to the card's top folder with month, day, hour and minute in the name and the clip number after a C, proxies in a Proxy folder, and macOS companion files on the card carry creation dates. A sound recorder stamps a WAV when it closes it, and an unclosed WAV's header may be wrong (the bytes on disk count). A camera gives a card a new volume serial at every format, and some USB readers report their own serial.

### 38-072: Open Sorter tabs follow cards as they arrive, leave and copy.
- Where: footage-sorter-and-camera-cards / The sorter page
- What: Every open Sorter tab is kept up to date with cards as they arrive, leave and copy, and reconnects within about 2 seconds if the link drops. A card the watcher opens is shown straight away in the tab.
- Flag: undetermined: what the card view itself shows is in another section.

### 38-073: Instead of copying, a person can link an existing folder into another CC Sync project.
- Where: sync / What syncs where
- What: When a card clip is "elsewhere" (the same recording, same size, already sits in the final tree), and that existing copy's folder (or the folder above a Proxy folder) lies inside one CC Sync project while the planned destination lies inside a different one, the person is offered **link folder** instead of copying. Clicking it adds that folder to the borrowing project's list of included folders, with a note "clip <name> already final here; folder linked instead of copied", who added it and when, so the footage syncs with that project without a second copy. Everything is worked out from the reviewed plan, never from what the browser sends. Already linked: nothing changes and the person is told. Refusals: "unknown clip in this plan"; "this clip is not filed elsewhere on the destination"; "the existing copy is not inside another ccsync project"; the folder is the project's own top folder ("tick both projects instead"); the project's marker cannot be read ("fix it first") or has no project identity ("refusing to edit it"); a stale plan. The answer names the lending and borrowing projects.
- Flag: differs: offered only in the stand-alone Sorter; the dashboard form answers that this is "not here".

### 38-074: Old field copy: Sony cards.
- Where: footage-sorter-and-camera-cards / Copying a card
- What: When the Sorter cannot be reached (and the old field copy is on, the default), or when run by hand on Windows, a Sony card is copied into the A-CAM or B-CAM transfer folder, not into the final tree. An FX3 clip goes to A-CAM, any other or unknown model to B-CAM; proxies come along into "proxy". Clips are grouped by camera and day into "<target>, <date> <label>, <HH.mm-HH.mm>" (a day folder, then one time-range folder per card); a folder already holding one of this card's recordings is reused, else a new one (" (2)" if taken). A neighbouring folder where at least half the start times match but ids differ is flagged as a probable **dual record**, and the person chooses "Write to NEW folder" or "MERGE into". Each clip shows **MISSING - will copy**, **PARTIAL - will complete (+size)**, **already backed up**, or **DIFFERS +/-size - likely same footage** (within 2 MB) / **likely a DIFFERENT take**; missing and partial are ticked, "differs" unticked (ticked when nobody is there to answer). A plan window "Auto Backup - K:" shows the card, clip count and selection, one entry per destination (with "[WILL SKIP: ...]" for a missing target or too little space), each opening a clip chooser with **All**, **None**, **Only missing**, **OK**, **Cancel**; buttons **Back up selected** and **Cancel**. Each clip is re-checked before copying; a same-name different clip is renamed, skipped, or put in a per-card subfolder by setting. Messages: copying not possible, "No clips found on K:", "Backup of K: cancelled.", "Backup complete (K:)" or "Backup finished with issues (K:)" with one line per group. If its window cannot be drawn it falls back to a plain yes/no question, and if that fails too it goes ahead as if yes was pressed. A rehearsal mode copies nothing. Notices show for 10 seconds; each run keeps a log.
- Flag: differs: copies into transfer folders with its own windows and folder layout (day folder, then time range), without the Sorter's plan, record of copies or health check.

### 38-075: Old field copy: Blackmagic cards.
- Where: footage-sorter-and-camera-cards / Copying a card
- What: BRAW files in the card's top folder are copied to the A-CAM target into "<date> BMCC", then a time-range folder; an existing time folder holding one of the clip names is reused. Clips up to a given clip number can be left out. The time comes from the file name, with the year from the macOS companion file's creation date, else the file's year. Every BRAW already anywhere under the target with the same name and size is "already backed up elsewhere" and never copied. States: **MISSING - will copy**, **DIFFERS - will re-copy**, **already in this folder** (or "media present - proxy will copy"), **already backed up elsewhere**. Window "Blackmagic footage - H:" per date, a chooser with **All**, **None**, **Only new**, **OK**, **Cancel**, shown even when nothing is new. Messages: the A-CAM target not found, "Nothing to copy from H: (already backed up).", "No clips selected from H: - nothing copied.", "Blackmagic backup of H: cancelled.", "Not enough free space on target (X free).", "Blackmagic backup complete (H:)", "Blackmagic backup finished with issues (H:)".
- Flag: differs: see 38-074.

### 38-076: Old field copy: sound recorders and drones.
- Where: footage-sorter-and-camera-cards / Placing sound recordings
- What: **Recorder WAVs** are each placed by their recording interval (end = file time, start = end minus length) into every A-CAM day folder of that date, inside each time-range folder it overlaps, else the day folder itself; a day with no folder is skipped ("no FF-A-CAM folder for <date>"): sound never creates day folders. Each destination is new, re-copy (different size) or skip. Window "Loose audio - R:" with **Copy audio now** / **Cancel**, no chooser. **Drone clips** (dated by file time) go into the B-CAM day folder of that date; with none, a new "<date> B-CAM" folder is proposed ("NEW FOLDER") and made; a date before 2020 is skipped ("bogus timestamp (<date>) - drone clock not set", "SKIPPED - can't route"). Window "Drone footage - H:" with **Copy drone now** / **Cancel**. Each says "Nothing to copy ...", "... cancelled.", a free-space error, "... complete" or "... finished with issues". An admin can also place recorder files by hand from a list of recovered recording times: matched files into overlapping time folders of their day, date-only ones into the day folder, the rest listed as not placed; that one shows nothing on screen and only writes a log.
- Flag: differs: see 38-074.

### 38-077: The old field copy can be switched off.
- Where: footage-sorter-and-camera-cards / Copying a card
- What: Whether the watcher falls back to the old field copy when the Sorter cannot be reached is a setting, on by default though meant only as a transition aid. With it off, the person is told the Sorter could not be started and the card is tried again.
- Flag: dormant: kept on by default, though described as something to turn off.

### 38-078: The NAS is backed up off site every night, and on demand.
- Where: server-install-and-running / Off-site backup
- What: The studio's project tree, the editing program's database backups and the Footage Sorter's own snapshots are backed up to an off-site storage box. It runs by itself each night at 04:15 (time and on/off settable; on by default; a missing or broken schedule means the defaults), and whenever someone asks for a run now from the Sorter. Only one run at a time. A run that fails is not retried that night. Upload speed is limited to 12 MB/s from 08:00 and 30 MB/s from 23:00, so working hours are not swamped. A run that finds nothing changed makes no new snapshot. What a person can see: running, OK or failed with the time and a message ("started (manual|nightly)", "complete (...)", "backup failed (...)"), live progress while running, the last run's start, finish and result, and the final summary. After a good run the full file list of the new snapshot is kept so it can be browsed. Daily logs are kept 60 days.

### 38-079: Old backup snapshots are thinned weekly, and deletions stay restorable for a while.
- Where: server-install-and-running / Off-site backup
- What: Once a week (the first successful run on a Sunday) old snapshots are thinned to keep 24 hourly, 30 daily, 12 weekly and 24 monthly. A file deleted on the NAS is not deleted off site at once: it stays restorable from older snapshots for that long.

### 38-080: The online record of copies answers only callers holding its key.
- Where: footage-sorter-and-camera-cards / The record of every copy
- What: An online record of every copy of every footage file, reported by every copying tool, sits on the studio's own web site. Every question except "are you working" needs its key; a wrong one: "bad token"; when it is not set up, it says so. Requests are limited to 5,000 items per list. Every change is numbered, so a client can keep a mirror and ask "what changed since".

### 38-081: What the online record tracks, and when two copies are one file.
- Where: footage-sorter-and-camera-cards / The record of every copy
- What: Only footage main files are tracked (camera video and raw formats, sound recordings, raw stills, 360-camera files); never anything in a Proxy folder, a Blackmagic companion file, an FX3 proxy, a macOS "._" file or a temporary file; anything else in a report is silently skipped. Two copies are one file when name (case ignored) and size match and, where both are known, modified times are within 3 seconds. Each place is a card, a studio drive ("ours"), a client drive, the NAS, a laptop, or unknown; any other kind is refused. Copies are never deleted from the record: one no longer found is marked missing since a time, and can later be answered as moved or deleted, but stays.
- Flag: differs: the Sorter's own record of copies (38-032) recognises a recording differently (by camera recording id, or name, size and day).

### 38-082: Reports of what changed on a drive are refused when the listing looks wrong.
- Where: footage-sorter-and-camera-cards / The record of every copy
- What: A drive's changes (added, gone, back) or a full listing can be reported. Added files are recorded as seen; gone ones are marked missing; back ones present again. If something would be marked gone, the drive had more than 100 live copies under the folders reported on, and the new total is under 80 % of that, nothing changes: "suspect listing: N files where M were; nothing changed (a half-mounted drive or a scan during chkdsk?)". A finished full listing cannot be finished again ("that scan is finished").

### 38-083: When files disappear, the person is asked where they went.
- Where: footage-sorter-and-camera-cards / The record of every copy
- What: Missing files still on the same drive (same path with a new size, or same name and size at another path) are linked to that copy and need no question. For the rest, one question per folder: "these files left <folder> on <drive>: where did they go?", with file count and size, and a suggested drive when one other drive holds a live copy of every file in it. Open questions are listed largest first. Answers: **deleted** (marks them deleted); **moved** to a named, known drive (links each to its copy there; any not yet seen there wait, and the question closes by itself when that drive's next scan or copy supplies them); **within** (moved or replaced on the same drive; closes when none are left). A question whose files all turn up again closes itself, "found again". Refusals: an unknown answer, an unknown drive, "already answered".

### 38-084: A person can ask where any files are, and whether they are safe.
- Where: footage-sorter-and-camera-cards / Backed up and safe to format
- What: For any list of files (name, size, time) the record answers every copy (drive, label, kind, path, how verified, missing) and a verdict: **at home** (a live copy on the NAS); **safe** (at home, or live copies on at least two of studio drives, the NAS or laptops); **on a laptop**; **laptop-only** (on a laptop and on no studio drive or NAS); and how many drives count. Missing copies count for nothing.

### 38-085: A daily mail lists footage that is not at home.
- Where: footage-sorter-and-camera-cards / Backed up and safe to format
- What: A report lists everything with no live copy on the NAS, grouped: **only on a laptop** first, then **on drives we own, not at home**, then **only on drives that are not ours (client drives, cards)**, by folder and where it sits, largest first, with total size and file count, plus "Where did these go? N folders no longer where they were:" with each one's probable drive. Every day at 08:00 studio time it is mailed to the owner, sender "Backups", subject "[backups] Not at home: <size>" plus " · ⚠ <size> only on a laptop" and " · N to answer". Nothing is sent when there is nothing to report, or when mail is not set up (and then nobody is told).

### 38-086: An operator can check footage already on disk for dead clips.
- Where: footage-sorter-and-camera-cards / Damaged and unfinished recordings
- What: A tool walks any folders given (skipping recycle bins, system folders, caches, proxy, Sony proxy and thumbnail folders, quarantine folders and macOS companions) and runs the card health check (38-062) on every footage file, plus: a Sony-named MP4 whose metadata XML beside it is 0 bytes is suspect. It prints each damaged and suspect file with its problems (fine ones too if asked), progress every 200 files, and "N files checked in X s: D damaged, S to check", and can save the results. It never changes footage, and its exit tells a caller whether anything was damaged.
- Flag: built twice: the same checks run on every card (38-062).

### 38-087: An admin can take a raw image of a whole camera card before reusing it.
- Where: footage-sorter-and-camera-cards / Damaged and unfinished recordings
- What: On Windows, run as administrator, a tool copies a card sector by sector into one image file, so a clip the health check flagged can be recovered later after the card is reused. Refusals (each says so and nothing is written): no drive given; not run as administrator; no partition has that letter; the drive is on the system disk; not enough room (needs the card's size plus 1 GB; not checked on a network path). The image is named from the card's label and serial and the time, in a default card-images folder, never overwriting, with a details file beside it (drive, label, file system, serial, model, connection, size, bytes read, complete or not, the image's fingerprint, unreadable ranges, start and finish). It reads in 8 MB blocks; a block that fails is re-read sector by sector and unreadable sectors are written as zeros and listed. Progress every 2 seconds shows done, total, speed and time left. It ends "Done: <size> in <time>", the fingerprint, the unreadable ranges if any, and "Recover from the image, not the card". A short read says how much was read. It can also image an ordinary file, for testing.

### 38-088: An operator can plan every episode's folder skeleton at once.
- Where: footage-sorter-and-camera-cards / Sorting into shoots, people and cameras
- What: From the studio's episode list and its standard subfolders, every episode folder and every standard subfolder is added to the plan as planned folders (38-018). It reports "<n> episodes x <m> folders = <k> planned folders", how many were new, any rejected names, and that they are created on disk by the next move. A rehearsal lists them and sends nothing. If the Sorter is not running it says so.

### 38-089: An operator can plan a folder for every interviewee on the roster.
- Where: footage-sorter-and-camera-cards / Sorting into shoots, people and cameras
- What: Every person on the roster gets a placeholder folder "<Chinese> <English>" in their episode's Interviewees folder (shown greyed out, not created until a clip lands). The episode's Interviewees folder is the one that already holds clips (shortest path wins), else any such folder (flagged "nothing is filed here, check this"), else the standard place; one can be pinned per episode. A person already filed under that episode (a folder holding clips whose path contains their Chinese name, or English name of 5+ characters) is left alone; a near-identical existing folder is reused. It reports people, already filed, to plan, skipped rows, folders per episode, "N folder(s) still empty - held as placeholders: shown greyed out in the tree, and NOT created on disk until a clip lands in one.", and "No assignment was touched." It needs the roster (an empty one is refused) and the episode list. A rehearsal sends nothing.

### 38-090: An operator can set verified duplicate copies aside into a quarantine folder.
- Where: footage-sorter-and-camera-cards / Writing duplicates aside
- What: A tool finds redundant copies in the staging folder and the final tree from a fresh move plan: files already at their destination, two identical sources for one destination, and clashes (the destination holds a different copy, or several sources). Which copy stays is decided by the studio's preference lists (some folders always kept, some lose ties); a chain of "kept" copies that loops, or anything outside the two folders, is refused. It then verifies each candidate against the copy that stays: identical content; else identical picture and sound streams; else, if smaller, a strict beginning of the kept one (a card that stopped early); else a metadata file whose footage verified. Anything not verified stays put with the reason. The verification can be resumed. Only then, and only when asked to act, are verified copies moved (never deleted) into a quarantine folder, keeping their path; it refuses when the source is gone or changed size, the kept copy is gone ("refusing to quarantine the only copy"; a kept copy the mover has since moved still counts), or the quarantine path is taken. The first error stops the run. It reports "moved N file(s), X GB; skipped M". A person empties the quarantine by hand. Scans ignore the quarantine folder.
- Flag: built twice: the move-plan export already leaves out the same duplicates (38-027).

### 38-091: Screenshots of every Sorter view can be made from sample data.
- Where: footage-sorter-and-camera-cards / The sorter page
- What: A tool opens the Sorter with built-in sample data (400 clips) and saves pictures of 18 fixed views at desk size (1440 by 900) and phone size (390 by 844, touch), with reduced motion and fresh local storage each time.
- Flag: dev only
