## The three CI reds on main at 3c7cf8e, 2026-09-11

The local gate was green on the same code and GitHub's `CI` workflow (run
34583384353) was red in three steps, so all three were environment-specific by
construction. None of them is: two are races or spellings this rig happened to
win, and the third is a licence verdict the gate could not read here at all.
The same three steps are red on every `CI` run back to 2026-09-07 (34145011883)
at least, so "CI is red" had stopped naming anything.

---

### 1. `linux :: dashboard -- pytest`: `test_not_checked_is_its_own_band_and_never_ok`

**Root cause: a race with the real collector thread, not a platform
difference.** `test_health_page.py`'s `env` fixture enters `TestClient(app)`,
which starts the Collector; `protection`, `invariants` and `alerts` are all in
`SYNCTHING_FREE_KINDS`, so the first cycle runs immediately on its own
connection and STORES verdicts. `protection.page_view` reads only the stored
picture, so whether the test's "nothing on a fresh server has been checked"
premise holds depends on who got there first. A pass that gets in finds three
genuinely BROKEN lines on a fresh, unconfigured server (no restore drill
recorded, no alerts sink, no `DASH_RELEASE_PUBKEYS`) and those rows arrive on
the health page in the `error` band, not `unknown`.

Measured on this rig with the file alone: **2 of 5 runs failed** before the
fix, which is what "green locally" was worth. CI's Linux runner simply lost it
every time.

The code is right (a real BROKEN verdict must show as an error), so the fix is
the fixture, in the shape `test_alerts.py` and `test_invariants.py` already
use for the identical reason -- `test_invariants.py`'s own comment records the
same sentence about CI's Linux runner from 2026-08-29. Stop the collector
(`stop()` joins its thread, so nothing writes after it), then reset to the
baseline the tests describe: `invariant_results`, `notices`, and the
`protection_results` meta key. A second `stop()` cannot close the gap between
thread start and the fixture body, so the reset is the point.

Changed: `dashboard/tests/test_health_page.py` (fixture only).

### 2. `linux :: licence gate (dashboard-container)`

**Root cause: `dashboard/requirements.lock` was compiled without
`pyproject.toml`'s `cards` extra**, so the four packages the container
installs for the mounted Timeline Cards page -- `psycopg2-binary`, `zstandard`
(2026-08-31, commit f31676b) and `zhconv`, `pypinyin` (a13a65e, the same day)
-- were in `dashboard/deploy/requirements.lock` and in no venv CI scans.
`check_licenses.py` reads the container target's licences out of
`dashboard/.venv` and the three web venvs because the container's venv has no
local twin, so all four came back `UNSCANNED`, which is a FAIL under
`--strict`.

Fixed as a lock bump, per `docs/RELEASE.md` "Refreshing the lockfiles": the
lock regenerated with `--extra cards` added to the exact command in its own
header. Only those four lines change; every other pin is preserved. The extras
table in `docs/RELEASE.md` now lists `cards`, with a caveat bullet saying why
an extra left off that command is a licence verdict nobody can see.

**What was hiding behind the four `UNSCANNED` lines**, once the gate could
read them:

| package | metadata licence | verdict |
|---|---|---|
| `pypinyin` 0.55.0 | MIT | clean |
| `zstandard` 0.25.0 | (BSD, no copyleft string) | clean |
| `psycopg2-binary` 2.9.13 | `LGPL with exceptions` | allowlisted, see below |
| `zhconv` 1.4.3 | **GPLv2+** | **dropped from the container** |

`psycopg2-binary` is allowlisted with a `reason` that mirrors paramiko's
entry line for line, because the shipping posture is identical (pip-installed,
importable, nothing statically linked, replaceable by the customer's own
build) and psycopg2 additionally carries its own linking exception. It is
imported only by the mounted cards page's project-library route, on a site
that sets `DASH_CARDS_ENABLED`. Like every entry in that file it is a claim a
lawyer should read, and `docs/legal/THIRD_PARTY_NOTICES.md` still owes it the
notice, the licence text and a written offer of source.

**`zhconv` 1.4.3 is GPLv2+, and the answer was to DROP IT, not to excuse it**
(owner's decision, 2026-09-11). It was in the BASE `deploy/requirements.txt`,
i.e. installed in every customer's container, vendor build included -- the
case `tools/license_allowlist.toml`'s header says the default answer to is
"replace it or stop shipping it", and the case
`bgutil-ytdlp-pot-provider` was split out of the base lock for on 2026-08-17.
GPL is not LGPL: the dynamic-linking posture paramiko and psycopg2 rest on
does not carry over to a plain GPL library a shipped program imports.

**Nothing in the container ever needed it.** Timeline Cards'
`multicam_pipeline/cards/text.py` imports zhconv inside a `try` and falls back
to its own Simplified/Traditional char map in `multicam_pipeline/zh_fold.py`,
whose header names this exact deployment ("No new dependency. opencc and
zhconv are not in the dashboard"), and that repo's `tests/test_zh_fold.py`
covers "the container's case" with neither package installed. So the removal
costs the page nothing; the base rig keeps zhconv through the Cards repo's own
`requirements.txt`, which is untouched.

Removed from `dashboard/pyproject.toml`'s `cards` extra and from
`dashboard/deploy/requirements.txt` (both with a comment saying why, and "do
not put it back"), and both locks regenerated with their own header commands:
`dashboard/deploy/requirements.lock` loses exactly the three zhconv lines and
nothing else, and `dashboard/requirements.lock` gains only
`psycopg2-binary`, `zstandard` and `pypinyin`. `docs/RELEASE.md` carries the
one-paragraph why under the extras table.

Changed: `dashboard/pyproject.toml`, `dashboard/deploy/requirements.txt`,
`dashboard/deploy/requirements.lock`, `dashboard/requirements.lock`,
`tools/license_allowlist.toml`, `docs/RELEASE.md`.

### 3. `windows :: installer -- powershell suites`: `Test-BinDirLeftovers.ps1`

**Root cause: 8.3 short paths.** A hosted Windows runner's `$env:TEMP` is
`C:\Users\RUNNER~1\AppData\Local\Temp`; the `FullName` `Get-ChildItem` reports
is always the long form (`runneradmin`). Seven cases compared one spelling
against the other. `alex` needs no 8.3 name, so this rig could never see it.

Both halves were wrong and both are fixed:

- `installer/windows_uninstall.ps1`'s `Get-BinDirLeftovers` compared its
  `$expected` list (built from the `$BinDir` and `$SelfPath` it was handed)
  against `Get-ChildItem`'s `FullName` as plain strings. Handed a short-form
  bin dir it excused nothing, so the running uninstaller and the
  `drive_mapping.ps1` it dot-sources were reported as leftovers on a perfectly
  clean uninstall -- a warning on every run, which is the exact failure the
  function's own DESCRIPTION says it exists to avoid. Both sides now go
  through one normaliser (`Get-Item ... .FullName`, falling back to
  `[IO.Path]::GetFullPath`, falling back to the string; it never throws,
  because the uninstall is over by the time it is asked).
- `installer/tests/Test-BinDirLeftovers.ps1` built its expectations from raw
  `$env:TEMP`. It resolves `$TempRoot` once now and both sandboxes hang off
  it, so the expectations are in the same spelling as the answers.

Verified by re-running the suite with `$env:TEMP` pointed at a real 8.3 path
(`...\shortpathprobe\LONGDI~1`), which reproduces the runner's condition on
this machine: 23/23 pass there and 23/23 unchanged with the normal TEMP.

Changed: `installer/windows_uninstall.ps1`,
`installer/tests/Test-BinDirLeftovers.ps1`.
