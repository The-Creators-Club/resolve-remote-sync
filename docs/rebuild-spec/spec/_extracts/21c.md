# Extract of inventory section 21c

## Items

### 21c-001: On TrueNAS the install checks that the account the server runs as has the same numbers on the NAS as the site's settings say, and names the fix when it does not.
- Where: server-install-and-running / Connections and credentials
- What: The server writes the studio's tree as the account the editors' share is owned by (by default named "broll", user number 3000, group number 3001, in the group "editors"). Before installing, the product reads the account's and the editors' group's real numbers on the NAS. When they differ from what the server would run as, the person is told each difference ("is user N on this NAS but the server would run as M", likewise for the group) and told to set those numbers in the site's settings. When the numbers cannot be read, the person is warned that the install goes ahead unchecked. A rehearsal skips the check.
- Flag: undetermined: whether a difference stops the install or is only reported

### 21c-002: A server set to update itself from the vendor must be given the vendor's public key, and an install that would leave it unable to accept any update is refused.
- Where: releases-and-updates / Signing and trust
- What: Before anything on the NAS changes, the install checks the keys the server will trust for updates. Refused, with the reason:
  - a value that is not a valid public key: the person is told the server would quietly ignore it, so every publish would fail and every vendor release would be refused; that the value is the vendor's 44-character public key; and not to generate a random value in its place;
  - no key at all: the person is told the server checks every update against these keys before running it, so with none no update could ever apply and publishing would fail. The fix is to set the vendor's key, or to tell the install to use the vendor's own defaults.
  The person is warned that a customer must never make their own key: a key of their own rejects every vendor release and cuts the site off from the vendor's updates. A rehearsal that passes says the key is set.

### 21c-003: A customer's install can take the vendor's own update key and release feed automatically.
- Where: releases-and-updates / Customer sites and the vendor's release feed
- What: With one switch on the installer's side, the server is given the vendor's built-in public key(s) when none is supplied, and the vendor's release feed when the site names none; the server is also marked as a customer site. A key or feed the site supplies always wins. Off by default.

### 21c-004: Installing a server with no release feed is allowed, with a warning that it will never be offered updates.
- Where: releases-and-updates / Customer sites and the vendor's release feed
- What: When no release feed is set, the person installing is warned that the vendor feed is off: the server makes no call to it and the updates screen offers no update. It is still a valid way to run, and the person is told to set the feed if updating itself is why they are installing this way. The site chooses how vendor releases are taken: by hand, staged for trying, or made current.

### 21c-005: The person installing is told when the version of the server they named can change under them, or does not exist yet.
- Where: server-install-and-running / Updates, restarts and rollbacks
- What: Naming the server's version by a movable label rather than a fixed one draws a note that the label can change and a suggestion to pin the exact one. Naming the general label for the first major version draws a note that it exists only once that version is released, and to use the newest test build's label or its exact identity until then.

### 21c-006: The install tells the person whether over-the-air updates built here will be accepted by the server they are installing.
- Where: releases-and-updates / The server updating itself
- What: Before installing, the person is shown the identity of the runtime the server should carry and how to read it from the running server afterwards. After it starts, the person is shown the runtime identity the server actually carries. If they differ, it is not an error, but the person is told that update bundles built for the other runtime will be refused as a change of runtime, and the updates screen will say "runtime update" instead of offering a button. A server that carries no runtime identity at all is a failure: the person is told the server is older than this and must be rebuilt or fetched again. When the expected identity cannot be worked out, the person is told the server's value will be shown without comparing it.

### 21c-007: After every install the product waits for the server to answer as the version just installed, and says plainly whether it is serving.
- Where: server-install-and-running / Updates, restarts and rollbacks
- What: The product asks the server, from inside the NAS, whether it is healthy and which version it is, about every 5 seconds for up to 150 seconds (a slow NAS can stretch this to about three and a half minutes). It passes only when the server answers as the version just installed (or, when the install did not change the server's own software, as the version that was serving before). On success the person is told "the dashboard is SERVING" with its version. On failure they are told the server did not answer as the expected version within 150 seconds and why (it answered as another version, could not be asked, or answered nothing readable); that nothing was deleted and the replaced version is still on the NAS; the exact one-line command that puts the previous version back and restarts the server; and to read the server's own log. A failed check fails the whole install, which also stops a new version of the editors' app being published against a server that is down. A rehearsal says what it would check and passes.

### 21c-008: The person installing can ask for a failed install to be put back automatically.
- Where: server-install-and-running / Updates, restarts and rollbacks
- What: Off by default; without it the person is told the option exists. When on and the server does not come up, the product sets the failed version aside (renamed with the date and time, never deleted), puts back the version this install replaced, restarts the server, and checks again for up to 150 seconds, accepting any version. The person is told either that the server answers again and "this deploy is UNDONE, not finished", or that it still does not answer and the fault is not this install's. The install still counts as failed. If this install replaced nothing, the automatic put-back refuses and the person is told to restore the newest kept version by hand. If the put-back itself fails, the person is told where the failed version may now be, to fix it by hand, and not to install again until the server answers.

### 21c-009: When the server is run as the vendor's ready-made build, the install says which code it is running and gives different put-back advice.
- Where: server-install-and-running / Updates, restarts and rollbacks
- What: About 10 seconds after the server starts, the person is told whether it is running the code it was built with or an update applied over the air on top of it, and then the live version and whether it is healthy. If it cannot tell which code is running, or the server does not answer, the person is told it failed, and the advice is to install again using the other way of running the server. This check never puts anything back on its own.
- Flag: differs: here the advice is to reinstall the other way; after a failed health check the advice is to put the previous version back (21c-007, 21c-008)

### 21c-010: Fetching the server's software onto the NAS can take up to 15 minutes, and a failure explains the likely cause rather than stopping the install.
- Where: server-install-and-running / Installing on a NAS
- What: Same on TrueNAS and Synology. The person is told when it was fetched. On failure they are told the three usual causes: the software was already loaded onto the NAS by hand (expected, fine); the NAS has no route to the internet; or the version named does not exist (try the newest test build).

### 21c-011: The server's own logs are capped so they cannot fill the NAS.
- Where: server-install-and-running / Snapshots, restoring and the server's disk
- What: Each part of the server running on the NAS keeps at most about 100 MB of log (five files of 20 MB), the oldest dropped first.

### 21c-012: When the dashboard's address is secure, sign-in is only ever carried over secure connections, and the server believes visitors' addresses only from machines the site trusts.
- Where: dashboard / Security of pages
- What: If the dashboard's address starts with https, the sign-in cookie is marked secure; otherwise it follows whether each request arrived securely. The visitor address the server records (for sign-in limits and records) is taken from a forwarding machine only when that machine is trusted: by default only the NAS itself and the server's own address on the studio's private network; a site can name its own list.

### 21c-013: Which archive folders count as the studio's own footage is a site setting; blank means the whole archive browses as downloaded footage.
- Where: broll / How the archive is laid out
- What: A site lists the archive folders that hold the studio's own shoots. If the list is blank, everything browses as downloaded footage. A site whose settings say nothing at all about the b-roll archive gets one older site's own project folder as its default, a fallback kept from before the setting existed.
- Flag: differs: a blank setting and a missing one behave differently

### 21c-014: On Synology the speed settings for editors' file transfers are limited by what Synology's file-transfer server can carry, and a value over the limit is refused, never lowered.
- Where: sync / Facts about the NAS and the operating systems
- What: Synology's file-transfer server silently cuts short any download larger than 514 MiB when pieces bigger than 64 KiB are asked for. So on Synology a piece size above 64 KiB is refused, saying exactly that; a value that is not a size is refused with an example ("64Ki"); and more than 16 transfers at once is refused. Blank values become 64 KiB and 16. These are checked before anything moves. On TrueNAS no limit applies and the values pass through unchanged.
- Flag: differs: Synology has limits, TrueNAS none

### 21c-015: The server publishes the site's identity and layout to every editor's computer.
- Where: server-install-and-running / Settings and secrets
- What: Set once in the site's settings and handed to every editor's app and every page:
  - the studio's name and its short name (blank short name: the full name is used); a support contact (blank: the vendor's); the product name; a brand logo (blank: the product's own mark);
  - the release feed (blank: off) and how vendor releases are taken (by hand, staged, or current);
  - the tree's name, the folders a new project starts with, and the shared asset folders;
  - the b-roll archive's default collection and its label, and the folder holding the studio's own shoots;
  - the drive letter editors see the tree on (default P:), the tree's location on the NAS, and its Windows network path;
  - where editors' computers transfer files to (host, and port, default 22), the NAS's key that their computers check (left blank when the site has turned that check off), the transfer speed values, and whether editors have only file transfer;
  - whether each project is private to its own people or shared by all editors, and where projects live;
  - the server's own sync identity and the dashboard's address.

### 21c-016: The server on the NAS checks the NAS's certificate the same way the installer did.
- Where: server-install-and-running / Connections and credentials
- What: Unless the site says otherwise, the server is given the fingerprint of the NAS's certificate recorded at install (TrueNAS's web port, or Synology's own management port), so it refuses a changed certificate. A site may instead turn checking off or name its own rule; that passes through unchanged. A rehearsal shows which fingerprint would be used without contacting the NAS. A description of the server written for pasting by hand carries only the site's own setting, which can be blank.

### 21c-017: The dashboard's admins must be named, and must not be the NAS's administrator account.
- Where: accounts-privacy-legal / Who may sign in
- What: Installing refuses when no dashboard admin is named, telling the person to name an editor account, not the NAS administrator. It also refuses when the list names the NAS administrator (letter case ignored), telling the person to use a separate account. A site can turn both refusals off with an old opt-out in its settings, in which case the NAS administrator is the admin. Names are comma-separated; spaces and blanks are dropped.
- Flag: differs: a legacy opt-out lets the NAS administrator be the dashboard admin

### 21c-018: On TrueNAS the server never holds the NAS administrator's password: it is given a limited key instead, and an install without one is refused.
- Where: server-install-and-running / Connections and credentials
- What: On TrueNAS, installing without a limited access key refuses, saying the server no longer holds the NAS administrator's password, and gives the step that makes a key for the server's own account. A site can turn this refusal off with an old opt-out. Synology has no such keys, so on Synology the server keeps the password and is never refused here.
- Flag: differs: TrueNAS uses a key; Synology must hold the administrator's password

### 21c-019: Whether computers may still report with the one key shared by the whole studio is a site setting, off by default.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: Each computer normally proves who it is with its own key. A site can allow the older single studio-wide key as well (meant only while moving computers over); off by default. The installer can also set it directly.

### 21c-020: The server answers only on the addresses it is given, restarts on its own, and its health is visible on the NAS.
- Where: server-install-and-running / Health checks and alerts
- What: The server answers on its address on the studio's network and on the private network, never on every address; the default port is 8480. The location of the studio's tree must be set, and a missing one is refused naming where to set it. The server restarts on its own after a crash or a NAS restart unless someone stopped it. The NAS checks every minute that the server answers healthy, allows it two minutes to start, and marks it unhealthy after three failed checks in a row.

### 21c-021: Which parts are switched on reaches the server from the site's settings, with their defaults.
- Where: server-install-and-running / Settings and secrets
- What: Defaults when a site says nothing: b-roll on; YouTube downloads off; YouTube's blocking workaround off (and on only when YouTube downloads are also on); the assistant through a program installed on the NAS off; the studio-wide lock on that off; automatic updates of editors' apps off. Music has no switch of its own: it is on when installed. YouTube downloads are always tried on the requesting editor's own computer first. A site can also stop the people page checking each editor's sign-in key on the NAS every time it is shown (on by default), which makes the page faster.
- Flag: dormant: the YouTube blocking workaround is off for everyone by default

### 21c-022: On Synology several site choices and parts never reach the server.
- Where: server-install-and-running / Installing on a NAS
- What: A Synology server is always installed with YouTube downloads, the YouTube blocking workaround, the assistant through an installed program, its studio-wide lock and automatic updates of editors' apps switched OFF, whatever the site's settings say. It is also not given access to Timeline Cards' notes and media, the camera card pool, the snapshot folder, the YouTube script runtime or the Timeline Cards editor's runtime, and does not get the YouTube blocking workaround's helper. The snapshot details are still passed, so the server may believe a snapshot folder exists that it cannot reach. TrueNAS passes all of these through.
- Flag: differs: Synology sites lose these features; TrueNAS sites keep them

### 21c-023: A description of the server can be produced for installing it by hand, with every secret left as a placeholder to fill in.
- Where: server-install-and-running / Installing on a NAS
- What: The description carries placeholders for eight secrets: the sync key, the computers' report key, the session secret, the b-roll intake key, the assistant's key, the Timeline Cards key and the NAS administrator's password (under two names). Its addresses can be overridden when the server is started. Producing it is refused if the product would leave any value unfilled.

### 21c-024: The server can also run the shared project library for Resolve, which refuses Resolve's well-known default password.
- Where: resolve-on-the-editors-computer / Project libraries and projects
- What: Off unless asked for. It answers only on the studio's network and private-network addresses, on port 5432 by default. It refuses to start with an empty password or Resolve's default ("DaVinci", either case), telling the person to set a long random one. On an existing library it first sets the password to the one given; if it cannot, it refuses to start and says so.

### 21c-025: The server can also run its own copy of the sync service, switched off unless started on purpose.
- Where: server-install-and-running / Installing on a NAS
- What: When started, it needs the sync key (and refuses without it), its control page is reachable only from the NAS itself, and it serves the whole tree. It restarts on its own unless stopped and its log is capped like the server's.
- Flag: dormant

### 21c-026: A rehearsal never shows a secret, and a real install refuses when a required secret is missing.
- Where: server-install-and-running / Settings and secrets
- What: In a rehearsal each secret is shown only as "not shown" when set or "unset" when not. A real install requires the sync key, the computers' report key and the session secret, refusing when any is missing; the b-roll intake key must already have passed the strength rule; and the NAS administrator's password is taken from whichever is set for that kind of NAS. Secrets are checked against their real values before anything is masked.

### 21c-027: Publishing the music library's data to the server sends only what is missing by default, or exactly what the person names.
- Where: music / Keeping the library's data whole
- What: The library's data comes in three pieces: the index of tracks, the part of the search model that reads typed searches, and the track previews. By default only pieces the server does not already have (missing or empty) are sent; if the server cannot be asked, everything is sent. The person can instead send all three, a named set every time (which is how a new index is published), or nothing. An unknown piece name is refused listing the accepted ones. Sizes are shown in B, KB, MB and GB (1024-based, one decimal). A rehearsal shows the full first-time plan.

### 21c-028: A new music index replaces the old one whole only after it has been checked, and the old one is always kept.
- Where: music / Keeping the library's data whole
- What: If there is no index to send, the person is told nothing was installed. If the indexing computer still holds changes not yet written into the index file, the person is warned that only the file is sent, and to close the indexer or flush its changes first; this does not stop the install. The new index is sent to a holding place, checked by size, checked again once copied into position, and only then swapped in; the previous index is renamed with the date and time and never deleted. If the transfer, the check or the swap fails, the person is told the installed index is untouched (or was put back). On success the person is told its size and where the previous index was kept. A rehearsal says what would be sent.
