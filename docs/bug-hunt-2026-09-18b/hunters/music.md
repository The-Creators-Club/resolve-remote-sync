## Findings

### music-1 - the cancel wedge CR-286/music-1 names is still reachable on the OTHER branch of the same `if`
- Severity: medium
- Confidence: CONFIRMED
- Where: `music/web/musicweb/routes_batches.py:198-206` (the `else` path, line 206) and `music/web/musicweb/ingest_batches.py:614-619` (`cancel`), against `ingest_batches.py:670-675` (`expire_stale_leases`); b-roll twin `broll/web/app/routes_batches.py:193`.
- What: the fix makes the *finalise* branch correct (sweep first, ask `lease_live`), but the branch it deliberately keeps - a cancel delivered to a machine holding a LIVE lease - still calls `ingest_batches.cancel()`, which sets `lease_expires_at = NULL` while leaving `state = 'running'`. That is bit-for-bit the wedge the fix's own comment describes: `expire_stale_leases`'s predicate is `state IN ('claimed','running') AND lease_expires_at IS NOT NULL AND lease_expires_at < ?`, so a NULL lease is outside every sweep for ever, and `claim` answers 410 (`cancel_requested`) to anyone who tries. Only the companion that was asked to stop can move the row - and the orphaned-companion case (owner, 2026-08-18) is exactly when it cannot.
- Failure scenario: editor clicks CANCEL on a batch this machine is really indexing; the companion is killed (crash, `Stop-Process`, power cut, the tray's own upgrade) before its next heartbeat. Row: `state='running'`, `cancel_requested=1`, `lease_expires_at=NULL`, `finished_at=NULL`. No sweep can reach it, no claim can take it, the panel shows it cancelling for ever, and (because of the music-3 fix in the same pass) `reserved_names` keeps every `dest_name` that batch holds reserved for ever, so every later drop of `Theme.wav` is previewed and allocated as `Theme (2).wav`. The only escape is the editor guessing to press CANCEL a second time.
- Evidence: `grep -n "UPDATE ingest_batches" music/web/musicweb/*.py` gives every writer of the row; the only ones that can leave `running`+NULL are `claim`/`heartbeat`/`release`/`retry_failed` (all need a live companion) and the cancel route's own second click. The new test `test_a_cancel_never_leaves_a_row_no_sweep_can_reach` pins only the dead-lease branch - it calls `_running_with_a_dead_lease` first - so it passes while the live-lease branch still produces the state its own name forbids.
- Ledger: CR-286 music-1 does not fix the whole of music-1 (the live-lease half).
- Suggested fix: in the request-not-kill branch do not null the lease; instead leave the existing expiry in place (the 410-on-next-call effect is already provided by `cancel_requested`, which `claim` and `heartbeat` both check), so the sweep can still reap the row if the companion never answers. Alternatively record `cancel_requested_at` and let `expire_stale_leases` finalise a `running` batch whose cancel is older than one lease period.

### music-2 - a cancel disarms the retry-failed guard, so two of an editor's machines can index the same tracks
- Severity: medium
- Confidence: CONFIRMED
- Where: `music/web/musicweb/routes_batches.py:237-246` (`retry-failed`, the `lease_live` guard) against `music/web/musicweb/ingest_batches.py:614-619` (`cancel`).
- What: `cancel()` nulls `lease_expires_at` under a leaseholder that is still working (it learns about the cancel only on its next heartbeat). `lease_live()` reads that column and nothing else, so immediately after a cancel the retry-failed route's "a batch a machine is STILL HOLDING is refused" guard - the music-1 (2026-09-11b) fix, whose docstring is right above it - passes. `retry_failed` then resets `cancel_requested = 0`, `state = 'queued'`, so the still-running companion is never told to stop at all, and another machine can claim the same batch.
- Failure scenario: batch running on Razer with 3 failed items; editor cancels, then (same page, seconds later, before Razer heartbeats) presses TRY THE FAILED TRACKS AGAIN. The route allows it, `cancel_requested` is cleared so Razer keeps embedding and uploading, the leso Mac claims the batch and indexes the same tracks into the same library - the exact "two computers indexing the same tracks into the same library until the first one's next per-item POST is 410'd" the guard exists to prevent, except here nothing 410s because the batch is alive again.
- Evidence: source reading of the three functions; `lease_live` is purely `_parse_iso(batch['lease_expires_at']) > now` (`ingest_batches.py:156`), and `cancel`'s UPDATE sets that column to NULL while leaving `state`. No test covers cancel-then-retry: the new suite's cancel tests never call retry-failed, and `test_ingest_batches.py`'s retry tests never cancel first.
- Ledger: related to CR-286 music-1 (the same `cancel()` behaviour); a live regression of music-1 (2026-09-11b) through a path that fix did not consider.
- Suggested fix: make the retry-failed guard ask "is a machine still holding this" rather than "is the lease column live" - refuse when `state in ('claimed','running') and not batch['finished_at']`, or have `cancel()` leave the lease alone (see music-1's suggested fix, which closes both).

### music-3 - the retry toast now reports a browser/network error as if it were the companion's answer, and drops the one actionable sentence
- Severity: medium
- Confidence: CONFIRMED
- Where: `music/web/static/ingest.js:1392-1421` (`miRetryFailed`'s new `refused` path and `miRefusalText` at 1328).
- What: the music-2 fix replaced a bare `catch { }` with `refused = miRefusalText(e)` for EVERY exception, but `miRefusalText` falls through to `e.message` whenever the thrown error is not a 409 with a body. The two commonest dispatch failures are not refusals in words at all: the tray is not running (fetch rejects, `e.message === 'Failed to fetch'`, no `.status`) and the companion is too old for `/music/ingest/*` (404, `e.message === 'the CC Sync tray returned HTTP 404'` - the app's own generic string, since the 404 has no JSON body). Both now print as the reason this computer did not pick the tracks up, and the fallback sentence that tells the editor what to DO ("Open this page on the computer that has the tracks and press take over") is only shown when nothing was thrown - i.e. never on this path.
- Failure scenario: an editor opens the panel on their laptop to retry a batch whose audio is staged on the studio rig (the case the fallback sentence was written for; the laptop's tray answers 404 because it is on 0.9.71). Toast: "3 tracks back in the queue, but this computer did not pick them up: the CC Sync tray returned HTTP 404." They are told a raw HTTP code instead of "go to the computer that has the tracks", and `MI_TOO_OLD`, which the page already knows, is never shown.
- Evidence: `miLoopback` (`ingest.js:412-418`) builds the message as `parsed.message || parsed.detail || 'the CC Sync tray returned HTTP <n>'`; `miRefusalText` returns `e.message` for any status other than 409-without-body. The new node test only drives 409s with bodies, so it cannot see this.
- Ledger: CR-286 music-2 opens a neighbour (new).
- Suggested fix: set `refused` only when the companion actually spoke - `if (e.body && (e.body.reason || e.body.message)) refused = miRefusalText(e);` - and keep the old fallback sentence (plus `MI_TOO_OLD` on a 404) otherwise.

### music-4 - `--dry-run` counts the files it cannot decode but never names them, and its byte totals no longer match the real run's
- Severity: low
- Confidence: CONFIRMED
- Where: `music/indexer/make_proxies.py:150-160` (the new `if not info:` branch) against `music/indexer/music_index/proxies.py:325-336` (`build_all`) and `make_proxies.py:68-96` (`report`).
- What: the new branch does `summary[proxies.FAILED] += 1` but does not append to `summary['failures']`, which is the list `report()` iterates to print `    <id> <name>: <err>`. The real run appends every FAILED and MISSING with a reason. So the estimate now says "failed 7" and prints nothing about which seven, over a library of hundreds - the operator cannot act on it. Secondly, the branch adds the source size to `after_bytes` (and `before_bytes` was already added above), while the real run's FAILED path contributes 0 to both, so the dry run's "preview bytes before/after" and its ratio no longer describe the same arithmetic the real run reports.
- Failure scenario: `python make_proxies.py --dry-run` over the library after a bad copy leaves a handful of truncated `.aac`; the operator sees a failure count with no filenames and has to run the full encode to find out which files to re-fetch. (Pre-existing for the dry run's MISSING branch, which has the same omission.)
- Evidence: `report()` loops `for tid, path, err in summary['failures']`; `new_summary()` seeds `'failures': []`; neither dry-run branch appends. `build_all` appends for both FAILED and MISSING.
- Ledger: CR-286 music-4 is incomplete (new).
- Suggested fix: append `(tid, str(src), 'no decodable audio stream')` in the new branch (and `'source not found'` in the MISSING branch), and add 0 rather than `before` to `after_bytes` so the two runs' totals agree.

### music-5 - the page now sends a staging id that may be stale, which walks straight past CR-253A's guard
- Severity: low
- Confidence: PLAUSIBLE
- Where: `music/web/static/ingest.js:1303-1320` and `:1341-1342` (`miTakeOver` now forwards `mi.stagingId` where it used to send `''`), against `companion/src/ccsync_companion/broll_ingest.py:1802` (`if not staging_id and items and not any(i.get("local_path") ...)`).
- What: the companion's guard keys on "the request named no staging id", but the condition that actually matters is "no item resolved to a local path while this machine holds the files". regression-1 widened the set of dispatches that carry an id, so a request carrying a STALE id (the staging entry was pruned by retention or by the tray's CLEAR FINISHED STAGING - `prune_staging`, `broll_ingest.py:3630`) now bypasses the guard instead of tripping it: every item is built with `local_path: ""`, `_crunch_item` fails each one, and `MAX_ITEM_ATTEMPTS` are burned before the batch is released failed.
- Failure scenario: a batch finishes with failures; days later retention prunes its staging folder while the panel is still open (`mi.stagingId` unchanged); the editor presses take over or retry; the companion accepts the claim with an id it no longer holds and spends the batch's whole attempt budget on items with no source, instead of answering the 409 the page now knows how to correct.
- Evidence: `_item_from_manifest` resolves `local_path` only from `self._staging.get(staging_id)`, and `_staging_holding` (which would find the files under another id) is called only inside the `not staging_id` branch. `prune_staging` pops entries from `_staging` while nothing invalidates the page's copy of the id.
- Ledger: related to CR-286 regression-1 / CR-253A (new).
- Suggested fix: on the companion, run the `_staging_holding` check whenever no item resolved a local path, whatever the request said, and answer the same 409 with the id actually held (the page's new retry then corrects it in one hop).
