# Extract of inventory section 17

## Items

### 17-001: The server makes its own secret credentials on first start and keeps them, so the person installing has nothing to type
- Where: server-install-and-running / Settings and secrets
- What: The server needs five secret credentials of its own: one that keeps people and computers signed in, one the studio's computers report with, one the b-roll indexing hands its results in with, one that controls syncing on the server, and one that lets the server's file-transfer service trust the server. Any of them the person installing did not supply is made at random on first start and kept on the server's own disk, readable only by the server, and the same value is used at every later start. A value the installer supplies always wins over a kept one. Values are never shown or written anywhere a person reads. Saving is done so that a failed save never destroys the good copy and never leaves an empty one.

### 17-002: The server refuses to start when it made a secret it could not keep, and says what each lost secret would cost
- Where: server-install-and-running / Settings and secrets
- What: If a freshly made secret could not be saved (an empty saved copy counts as not saved), the server refuses to start rather than run with a secret that changes at every start. The message names each one with its cost: every computer and every browser would be signed out the next time the server restarts; the computers in the fleet would stop being able to report; b-roll indexing would stop being accepted; the server would lose control of its own syncing; the file-transfer service would stop trusting the server. It tells the installer to fix who owns the server's data folder on the NAS, or to supply the value themselves.

### 17-003: The server refuses to start with a weak secret the installer supplied
- Where: server-install-and-running / Settings and secrets
- What: A secret the installer supplied is refused at start if it is under 24 characters, a placeholder, or has too little variety. This covers the sign-in secret, the shared computer credential, any retired sign-in secret still being honoured, and (when b-roll is switched on) the b-roll indexing credential, where the message also offers switching b-roll off. The message names what is weak and tells the installer how to generate a strong value and redeploy. Only secrets that are present are checked.

### 17-004: The server refuses to start with a sign-in set-up that would lock everyone out
- Where: server-install-and-running / Settings and secrets
- What: Start-up is refused, with a message that names the problem and ends "Fix it and redeploy.", when: the chosen sign-in method is not one of the three offered ("Left as it is, every password would be refused"); https-only sign-in is forced while the server has no https address and no trusted front end; single sign-on is chosen but the identity provider's address or the dashboard's registration with it is missing, or the provider's address is not https (plain is allowed only to the same machine); sign-in by NAS account is chosen but no NAS address is given ("no password can ever be checked and nobody could sign in", offering the dashboard's own accounts or the NAS address as the fix).

### 17-005: The server refuses to start if the studio's projects folder is named anything but "Projects"
- Where: server-install-and-running / Installing on a NAS
- What: The installer is told the server only supports a tree whose projects live in a folder called "Projects". The same refusal meets an admin who pastes settings naming another projects folder.
- Flag: undetermined: no install is known to set another name, so the refusal may be reachable only by hand

### 17-006: A development hatch lets the server start despite every refusal
- Where: server-install-and-running / Settings and secrets
- What: One install-time switch, meant only for testing, skips every start-up refusal (weak secrets, unsaved secrets, the projects folder name), keeps a browser signed in even after its sign-in was ended on the server, and allows computers to report with no credential at all. It is announced loudly at every start, and the messages that mention it say never to do it on a real installation.
- Flag: dev only

### 17-007: Some start-up warnings reach nobody but the server's log
- Where: whole-product / Could not check, refusals and nothing silent
- What: At start the server notices, but only writes to its own log (nobody is told on any screen): an admin named in the admin list who has no account (dashboard's own accounts only); computers still reporting with the old shared credential, which will be refused when that credential is turned off; NAS details missing, so editor sign-in and the admin's user management will not work ("The dashboard still runs"); retired sign-in secrets still being honoured, with the advice to remove them once no computer uses them; the locked build holding a stored "allow sign-in-based assistant tools" setting that it ignores.

### 17-008: Problems in the server's own set-up are shown on the home page at start
- Where: dashboard / Problems the server finds
- What: Each start checks the server's set-up and puts what it finds on the home page's list of problems the server found, for example a secret that was typed with quotes or spaces around it.

### 17-009: A file rename on the server cut off by the server stopping is finished or set aside at the next start
- Where: proxies-and-file-moves / Moves that reach every computer
- What: If the server went down part-way through moving a file on the NAS, the next start either completes that move or sets the half-moved file aside safely, so nothing is left in two places or lost.

### 17-010: The dashboard's title carries the studio's name and the product's name
- Where: whole-product / Windows, text and names
- What: The dashboard's title reads "<studio's name> - <product name> Dashboard", or "CC Sync Dashboard" when no studio name is set. The product name defaults to CC Sync.

### 17-011: The server keeps its own background work running, and says so on the home page when it had to step in
- Where: server-install-and-running / Health checks and alerts
- What: The work that keeps the fleet picture up to date is watched about every 30 seconds. If it has stopped, the server restarts it and puts a warning on the problems list: "The background job thread stopped and had to be restarted (N time(s) since this server last started). While it was down, nothing about the fleet was being updated." with the advice "If this keeps happening, restart the dashboard and send the server log to support." After three such restarts, on the fourth stop, or if it is alive but has made no progress for 15 minutes, the whole server restarts itself. If the server cannot tell, it assumes all is well.

### 17-012: A server update that will not start is rolled back by itself
- Where: releases-and-updates / The server updating itself
- What: After an over-the-air update of the server's code, two failed starts in a row put the previous code back at the next start. A start that hangs before it is healthy is caught too. A staged code update that asks for a restart is applied when the server stops.

### 17-013: Open cut lists are saved before the server stops
- Where: cards-editor / Opening episodes and keeping the editor running
- What: When the server is stopped or restarted, the Timeline Cards editor is stopped first and saves every open cut list before anything else goes down.

### 17-014: A switchable part that is broken or absent never stops the dashboard, and gets no menu entry
- Where: dashboard / Overview, menus and finding things
- What: Each switchable part (b-roll, music, YouTube downloads, Timeline Cards, the Footage Sorter) is one of: working, absent, or working badly. Only a working part appears in the dashboard's navigation. A part that is not working is named on the health checks and the problems list, and the dashboard still starts. With b-roll switched off the health check says "the b-roll platform is switched off on this server". The Timeline Cards editor, when its own parts are missing, shows a page that says so. A part's pages can never take over a dashboard page's address.

### 17-015: The Footage Sorter's pages wait until its data is loaded after a start
- Where: footage-sorter-and-camera-cards / The sorter page
- What: After the server starts, the Sorter loads its data in the background; a request made before it is ready waits rather than failing. If loading fails quickly, the Sorter is reported absent.

### 17-016: An unexpected error says only "internal error", and the admin sees it on the problems list
- Where: whole-product / Could not check, refusals and nothing silent
- What: Any unexpected error answers "internal error" with nothing from the error itself, and is recorded on the home page's problems list, one row per kind of error on each page. When the dashboard's data is momentarily locked, the answer is "the dashboard's database is busy; try again", the browser is told to retry in 30 seconds, and a separate "database busy" warning is recorded. Errors in every switchable part except the old Timeline Cards page are answered and recorded the same way.

### 17-017: Everything needs a signed-in browser except a short list of open doors
- Where: accounts-privacy-legal / What each person may see and reach
- What: Every page and every piece of data needs a signed-in person, except:
  - the sign-in page and signing in and out, and asking "who am I";
  - the set-up wizard page and the parts of it open before the first admin exists (see 17-063);
  - the server's health answer and the studio's public description (studio name, drive letter, addresses, which parts are on), which installers and the app on editors' computers read;
  - what a phone needs to install the dashboard or Timeline Cards as an app (icons, app description, the offline page), read only;
  - a client folder link in b-roll and a shared folder link in the Footage Sorter, where the link itself is the credential;
  - the YouTube downloader's description of itself for the app on editors' computers, readable by anyone by design.
  There are no public pages describing the server's programming interface.

### 17-018: A visitor who is not signed in is sent to sign in and brought back afterwards
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: Opening a page without a sign-in goes to the sign-in page and, after signing in, back to the page asked for (with its query). A part of a page refreshing itself after the sign-in has ended sends the whole browser to the sign-in page, returning afterwards to the page that part belongs to. A data request is answered "Your sign-in has expired. Sign in again." (in the switchable parts, "login required").

### 17-019: The studio's computers and services reach only their own work with their own credentials
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: The app on an editor's computer uses its computer's credential, not a browser sign-in, for its own work: reporting, fetching its sync plan, downloading updates, reading (never setting) a studio-wide stop, claiming and reporting shared work (proxies, transcription, YouTube jobs, b-roll and music imports, the Footage Sorter's card reports), Timeline Cards' link to Resolve, and finding files. A bad or missing credential is refused before anything the computer sent is read. The b-roll indexing hands in its results with its own credential, and the studio website's gear page asks what a photo shows with its own credential. Nothing a computer credential reaches can be reached by a browser without signing in.

### 17-020: How large a single upload or request may be
- Where: dashboard / Security of pages
- What: A music file dropped in to the library may be up to 512 MB. A companion build an admin publishes may be up to 200 MB. A computer's report may be up to 8 MB. Any other form or request may be up to 4 MB. Anything larger is refused at once with "request body too large (max N bytes)".

### 17-021: A dashboard page drawn by an older version reloads itself when used, and nothing done on it is saved
- Where: dashboard / Pages that refresh and answer clicks
- What: After the dashboard is updated, the first click on a page an older version drew reloads the page instead of acting, so a change made on an out-of-date page is never saved. This does not apply inside the switchable parts.

### 17-022: An action that did not come from the dashboard's own page is refused
- Where: dashboard / Security of pages
- What: A change sent to the dashboard by another web site, or from a page whose sign-in has changed since it was drawn, is refused: "missing or bad CSRF token: reload the page and try again" on the dashboard, and "this request came from another site" in Timeline Cards. The cure in both cases is reloading the page.

### 17-023: The studio chooses one of three ways for people to sign in
- Where: accounts-privacy-legal / Who may sign in
- What: Set by the person installing the server: people sign in with their NAS account and password (the default), with the studio's own single sign-on provider, or with accounts the dashboard keeps itself. Whatever the choice, the people named as admins at install time can always sign in with a password (the way back in if single sign-on fails).

### 17-024: Signing in with a NAS account checks the password against the NAS
- Where: accounts-privacy-legal / Who may sign in
- What: The NAS is asked within 10 seconds whether the name and password are good. A NAS that would let the person in only as a guest or anonymously counts as a refusal. When four sign-ins are already being checked, a fifth waits up to 2 seconds and is then told the server is busy. An empty name or password is always refused.

### 17-025: Signing in over plain http is refused when the dashboard is set to https only
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: Set by the installer: whether a browser's sign-in is marked as https-only. By default it is marked https-only exactly when the visit came over https; it can be forced on or off. Forced on, signing in over plain http is refused with "this dashboard is configured for https only: use the https URL", and this does not count as a failed sign-in.

### 17-026: A person an admin deleted cannot sign in, and a suspended person still can
- Where: accounts-privacy-legal / Suspending, disabling and removing a person
- What: A person an admin has deleted cannot start a browser sign-in (unless named in the install-time admin list). A suspended, not deleted, person can still sign in to the browser. If the server cannot read who was deleted, it lets the person in.

### 17-027: Too many wrong passwords block sign-in for a while, and the person is told how long
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: Failures are counted per account name (5 allowed) and per visitor's address (40 allowed). Reaching either limit blocks sign-in for 1 minute, doubling with each further failure (1, 2, 4 minutes ...) up to 1 hour; the longer of the two waits applies. A failure older than an hour stops counting. The person sees "Too many sign-in attempts. Try again in a minute / N minutes / about an hour." (rounded up to the minute; 45 minutes or more reads "about an hour"). The counts survive a restart of the server. A successful sign-in clears the account's count but not the address's, which ages out by itself. Every failure is recorded with the name and address, never the password.

### 17-028: Which front ends the server believes about a visitor's address
- Where: server-install-and-running / Connections and credentials
- What: Set by the installer: the front ends (proxies) allowed to tell the server the real visitor's address; by default only the server's own machine. A visitor's address decides the sign-in limit in 17-027 and is what the account page shows. When a front end that is not trusted passes addresses along, they are ignored and every person coming through it counts as one visitor, which is written to the server's log once and told to nobody. A trusted front end's word on whether the visit was https is believed too.

### 17-029: A browser stays signed in for 100 days
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: A sign-in ends 100 days after it was made, whatever the use, or after 100 days without any use, whichever comes first. Because the two are equal, a phone used offline for weeks is not signed out. Both lengths can be changed by the installer; there is no "never expires" (zero or nonsense falls back to 100 days). Every page knows when its sign-in will end, which is what lets it warn the person beforehand.

### 17-030: A person can see and end their own sign-ins, and an admin can end anyone's
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: Each sign-in records when it was made, when it was last used (kept to within about a minute), the visitor's address and the browser. The browser is shown as a short description such as "Chrome, Windows" (programs like command-line tools and the product's own app are named as such; "Unknown browser" when nothing is recognised), never the raw browser text. A person can:
  - sign out, which ends the sign-in on the server at once;
  - sign out every other browser, keeping this one;
  - end one particular other sign-in of their own; ending the browser they are using this way is refused.
  An admin can end any person's sign-ins and sees every live sign-in across the studio, up to 200 at a time. Ended or expired sign-ins disappear from the server 7 days after they were ended, or once past the 100-day limit.

### 17-031: A person can export or erase what the server holds about their sign-ins
- Where: accounts-privacy-legal / What the product records about a person
- What: A person's data export includes their sign-ins (when, last used, address, browser) and their failed-sign-in count. "Erase history" removes only sign-ins that have already ended and the failed-sign-in count, unless that count is blocking sign-in right now; live sign-ins are kept. "Delete" removes every sign-in and the count. Failure counts kept per address are never part of a person's export.

### 17-032: An editor's computer stays signed in until someone ends it
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: When an editor signs in on the app on their computer, that computer is signed in with no end date. Ending a person's computer sign-ins makes every computer signed in before that moment sign in again; a computer signed in afterwards is not affected. If the server cannot read whether a person's computers were signed out, it accepts them. When the server's sign-in secret is changed, computers signed in with the old one keep working until it is retired, and the dashboard counts the computers still owing their editor one "Sign in..." click. A computer's sign-in and a browser's can never stand in for each other.

### 17-033: Whether the old shared computer credential is still accepted
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: Set by the installer: whether computers may still report with the one credential the whole studio once shared, beside each editor's own. On a new installation it is not accepted. While it is accepted, computers using it are listed in the server's log with advice to give them their own credential and then turn it off; nobody is told on a screen.
- Flag: dormant

### 17-034: Who is an admin, and what an admin sees that an editor does not
- Where: accounts-privacy-legal / What each person may see and reach
- What: An admin is anyone named in the admin list set at install time (or in the set-up wizard), on every sign-in method; with the dashboard's own accounts, an account with the admin role that is not disabled is an admin too. A person's account page can show where their admin power comes from (the admin list, or their account's role). An editor only ever sees their own data. An admin sees the whole studio and may look at the dashboard as one editor sees it. A person may change an editor's settings if it is themselves or they are an admin.

### 17-035: A password the dashboard sets must be at least 12 characters
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: Any password set through the dashboard is refused under 12 characters ("password must be at least 12 characters"). Passwords that already exist are never checked against this.

### 17-036: Signing in through the studio's single sign-on provider
- Where: accounts-privacy-legal / Who may sign in
- What: The sign-in button sends the person to the studio's provider and back to the page they wanted (only a page on this dashboard; anything else returns to the home page). The round trip must finish within 10 minutes. On the way back the person can be told:
  - "this sign-in expired or did not start here: try again";
  - "bad sign-in state: try again";
  - "the identity provider refused this sign-in" (the provider's own reason is not shown);
  - "no authorization code in the callback";
  - that the provider's answer could not be checked ("the identity provider's answer could not be verified"), or a short reason when the provider pointed the sign-in somewhere else;
  - that the account name the provider gave is not usable here;
  - "this account was removed from the dashboard - ask your admin".
  When the provider cannot be reached: "the identity provider is unreachable. An admin can sign in at" the password sign-in page. When single sign-on is chosen but not fully set up, both steps answer with the first thing missing. The account name from the provider must start with a letter and hold only letters, digits, dot, dash and underscore, up to 32 characters, with no "@", "/" or backslash; it is lower-cased.

### 17-037: Who single sign-on lets into the studio
- Where: accounts-privacy-legal / Who may sign in
- What: A person coming from the provider is let in if they are an admin, if the provider marks them with one of the admin values, or if they belong to one of the allowed groups. When allowed groups are set and none match: "this account is not a member of the group allowed to use this dashboard - ask your admin". With no allowed groups, the person must already be known to the dashboard (has ticked a project, has a computer that reported, is a known editor, or has an account), otherwise "this account is not part of this fleet - ask your admin to add it". While the dashboard knows no editors at all, or cannot read who it knows, anyone the provider vouches for is let in.

### 17-038: Under single sign-on, the provider's admin mark does not make anyone an admin
- Where: accounts-privacy-legal / What each person may see and reach
- What: A person the provider marks as an admin gets past the membership check and nothing more; they are not an admin anywhere in the dashboard. Only the admin list (and, with the dashboard's own accounts, the admin role) makes an admin. The set-up wizard says so when such a mark is configured.

### 17-039: Under single sign-on, only admins may use the password form
- Where: accounts-privacy-legal / Who may sign in
- What: The password sign-in stays available as the way back in when single sign-on is broken, but only for admins; their password is checked against the NAS. Anyone else is refused "bad username or password", and it counts as a failed sign-in.

### 17-040: The single sign-on settings
- Where: accounts-privacy-legal / Who may sign in
- What: Set by the installer: the provider's address (must be https, plain only on the same machine); the dashboard's registration with the provider and its secret (optional); which details are asked of the provider (default the person's name, profile and e-mail); which of the provider's details is the account name (default the person's preferred user name); which detail and which values mark an admin; which detail lists groups and which groups are allowed (none means "must already be known"); and the address the provider returns to (default worked out from the visit). The provider's answer must be signed in a way only the provider could sign, and the dashboard's secret is never sent anywhere the provider did not name.

### 17-041: Accounts the dashboard keeps itself
- Where: accounts-privacy-legal / Who may sign in
- What: With the dashboard's own accounts, each account is an admin or an editor. An account name starts with a lower-case letter and holds lower-case letters, digits, ".", "_" and "-", up to 32 characters (typed names are trimmed and lower-cased). Creating one is refused with "username must start with a letter and contain only lowercase letters, digits, '.', '_', '-'", "role must be one of ('admin', 'editor')", "password must be at least 12 characters", or "'<name>' already exists". Setting a password is refused for a name that is not an account ("'<name>' is not a local account") or a short password. A disabled account cannot sign in and is not an admin; from outside, a disabled or unknown account looks the same as a wrong password. Passwords are kept only in a form that cannot be read back.

### 17-042: An admin can disable, re-enable or delete an account, but never their own or the last admin
- Where: accounts-privacy-legal / Suspending, disabling and removing a person
- What: Disabling is refused for the account you are signed in as ("you cannot disable the account you are signed in as - sign in as another admin to disable this one") and for the last enabled admin ("this is the last enabled admin account - create another admin before disabling it"); deleting has the same two refusals in "delete" wording. Deleting an account removes the account and its file-transfer keys but keeps the person's history in the studio: their ticks, their computers and what they did.

### 17-043: Each account can hold the keys its computers use for file transfer
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: With the dashboard's own accounts, each account holds the public keys its computers present to the server's file-transfer service. A key must look like a standard public key; adding the same key again only refreshes its label and date; a key is removed by its fingerprint, and removing one that is not there is not an error. A comment at the end of a key does not change which key it is.

### 17-044: A "must change password" mark can be set on an account but nothing acts on it
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: Setting a password can mark the account as having to change it, but nothing in the dashboard asks the person to.
- Flag: unreachable

### 17-045: The studio's name, short name, product name and mark
- Where: dashboard / Settings and setup
- What: An admin sets the studio's name (blank by default; used in the dashboard's title and branding), a short name (blank; for tight spots such as the tray icon's tooltip), the product's name (default CC Sync) and the mark shown on editors' computers (default the product's own mark; otherwise a mark shipped with the app or a picture on the editor's computer).

### 17-046: Where the studio's support requests go
- Where: dashboard / Settings and setup
- What: An admin sets a support contact. Left blank, the vendor's support address is used. Help text in the product that says to send something to "us" or to "support" has "Support: <address>" added (never twice). The settings and the settings export show only the studio's own value, never the vendor's.

### 17-047: The drive letter, tree name and server folder every computer builds its paths from, locked once computers exist
- Where: dashboard / Settings and setup
- What: An admin sets the drive letter (or, for a Mac-style tree, an absolute folder) editors' computers see the studio's tree at (default P:\), the tree's name, and where the tree lives on the server. The drive letter must look like "P:" or "P:\" (the backslash is added) or an absolute folder with no "..", and may not be blank ("must be a Windows drive letter like 'P:\\' or a POSIX absolute path like '/mnt/tree'"). Once any computer has registered or reported, changing any of the three is refused, because every installer and app builds its paths from them; the message says to plan every computer's move first and that only the person installing can unlock the change on purpose. Saving the value a setting already has is not a change.

### 17-048: The folders laid down in every new project, and the shared libraries every computer gets
- Where: dashboard / Settings and setup
- What: An admin sets the list of folders made in every new project, and the list of shared libraries (for example colour look-up tables) synced to every computer; both have sensible defaults. Each entry must be a folder under the tree, not an absolute one, with no drive letter and no ".." ("must stay under the tree root: '..' is not allowed"). A shared library's name needs at least one letter A-Z or digit 0-9, and two names that would be confused for the same library are refused ("rename one of them").

### 17-049: The dashboard's address published to editors, and values filled in by themselves
- Where: dashboard / Settings and setup
- What: An admin sets the address editors' computers and browsers use to reach the dashboard. That address, the server's sync identity and the server's file-transfer address are filled in by the server itself where it can learn them, and shown greyed out in settings when a live value exists.

### 17-050: Which kind of NAS the studio has
- Where: server-install-and-running / Installing on a NAS
- What: An admin (or the installer, or the wizard) says whether the NAS is a TrueNAS or a Synology; TrueNAS is the default. Blank or any other kind is refused with the list of kinds offered.

### 17-051: The studio-wide switches for optional behaviour
- Where: dashboard / Settings and setup
- What: An admin turns each on or off; all are off by default:
  - YouTube downloads;
  - YouTube's extra measures against being blocked (meaningful only with downloads on);
  - letting the server use an assistant tool signed in with a subscription and installed on the server, instead of a paid key; and keeping that tool updated by itself;
  - editors' computers installing any newer offered build with nobody clicking.
  A switch set in the dashboard wins over the install-time value. A switch the server cannot read, or does not know, counts as off.

### 17-052: The vendor's locked build never allows the subscription-signed assistant tools
- Where: whole-product / The assistant
- What: In the build the vendor ships to customers, the assistant tools signed in with a subscription, their set-up, their automatic updating and the server's own read-only problem-triage by the assistant are off whatever a site has stored, unless the person installing explicitly unlocks them. Where such a feature would be, the person reads that those tools are not available in this build and to use a paid key with one of the assistant services instead.
- Flag: differs: the studio's own build can unlock what the vendor's build cannot

### 17-053: How well new b-roll clips are described when the studio describes them on its own machine
- Where: broll / Describing and indexing clips
- What: An admin picks "good" (the default) or "best" for describing b-roll clips on the studio's own computer; anything else is refused.

### 17-054: The studio's Android app identity
- Where: dashboard / Phones and the installed app
- What: An admin may give the identity of the studio's Android app (its package name and certificate fingerprints), which lets an Android phone open dashboard links in that app. Blank means no Android app. A package name must have two or more dot-separated parts each starting with a letter or underscore; each fingerprint must be 32 pairs of hex digits separated by colons (a leading "SHA256:" is accepted, case does not matter, duplicates are dropped). Only an admin in the dashboard can set these.

### 17-055: What editors' computers report about their editors, switched off for the whole studio
- Where: accounts-privacy-legal / What the product records about a person
- What: An admin can switch off, for the whole studio, four kinds of report from editors' computers: which Resolve project is open, what media sits on the computer, the computer's own file list, and whether the editor is at the keyboard. All four are reported by default. Switching off which Resolve project is open also switches off what media sits on the computer. Switching one off deletes, for every computer at once, what the server already held of it, and the confirmation (for a save, an import or an undo) says which categories will be switched off and so deleted. These switches must be exactly on or off; blank is refused. The studio's choice is applied at every start of the server too, and if the server cannot read the stored choice it keeps the last one applied rather than quietly reporting again.

### 17-056: Saving settings checks the whole form first
- Where: dashboard / Settings and setup
- What: Every value is trimmed, and text holding control characters is refused. Whole numbers may be blank but not negative ("must not be negative", "'x' is not a whole number"). An unknown setting is "not a recognised site setting". The whole form is checked before anything is written, so one bad field changes nothing; the reason is shown. Each setting records when and by whom it was last changed, and a setting can be cleared back to its default. Only an admin may read or change these settings ("log in first", "admins only").

### 17-057: Settings changes can be looked back on and the last one undone
- Where: dashboard / Settings and setup
- What: The history lists each recorded change's time, who made it, how (save, import or undo) and how many settings it touched, never the values. A plain save is recorded when it changes the tree settings or a reporting switch; an import is recorded whenever it changed something. An admin can undo the newest change, which puts the earlier values back through all the same checks; it is refused when nothing is recorded ("no site setting change is recorded to undo"), when someone saved since the admin looked ("the newest change is no longer the one you confirmed (someone saved since): reload the page"), or when the change kept no values. The undo is itself recorded, so it can be undone. Before undoing, the admin is told which reporting categories the undo would switch off.

### 17-058: The studio's settings can be exported as text and imported by pasting
- Where: dashboard / Settings and setup
- What: An admin can export the settings the dashboard holds as a plain-text settings file (the same shape the server's install reads), and import one by pasting (up to 65,536 characters). Before importing, a preview lists every change and which reporting categories it would switch off, and writes nothing. Settings the dashboard does not hold are ignored silently; text with none it recognises is refused ("no recognised [section] keys found in that text"); text that cannot be read is refused with the reason; a projects folder named other than "Projects" is refused. An import goes through every check a save does.

### 17-059: Install-time studio settings are copied in once, then the dashboard's values rule
- Where: server-install-and-running / Settings and secrets
- What: The first time the server starts with studio settings given at install time, they are copied into the dashboard. From then on the dashboard's values win, and changing the install-time value does nothing; the change must be made in the dashboard. An installation that gave none at install time is configured in the dashboard from the start.

### 17-060: The studio describes itself once in a settings file the install reads
- Where: server-install-and-running / Installing on a NAS
- What: The person installing writes one settings file describing the site (the NAS, the tree, the network, the sync, the studio's name, updates, b-roll, Timeline Cards, the Footage Sorter, the switches). It never holds a password, key or credential: those stay with the person installing. The install turns it into the server's settings, and the same file can be pasted into the dashboard's import (17-058), which takes only what the dashboard holds. The file also carries two deliberate escape hatches for the installer: allowing the NAS's admin password to be kept on the server, and allowing the NAS's admin account to be a dashboard admin.

### 17-061: Settings the person installing sets for the server
- Where: server-install-and-running / Settings and secrets
- What: Set only at install time (not in the dashboard), each by its effect:
  - the port the dashboard listens on (default 8480) and where published builds are kept;
  - where the server sees the studio's projects; when given, any new project folder on the server is made syncable by itself within about five minutes;
  - whether syncing between computers may use only the studio's private network (off by default) and, when given, the server's private-network address, offered to computers first;
  - whether the server protects its own sync administration page with a password when it finds none (on by default);
  - the NAS's address, admin account, key or password, and how its certificate is trusted (by default the first one seen is remembered and a different one refused later; it can be pinned or checked against the usual authorities);
  - whether each project gets its own group of people on the NAS (default one shared group), and which NAS account the server itself runs as, which is hidden from lists of editors;
  - the vendor's update feed and signing keys (17-064), how often the feed is checked (daily by default) and what to do with what it finds (17-065);
  - whether b-roll, Timeline Cards, the Timeline Cards editor and the Footage Sorter are on, and where their data is.

### 17-062: A safety stop when the server would stop sharing projects with several computers at once
- Where: sync / Safety stops
- What: When the server's own bookkeeping would stop sharing project folders with more than 3 computers in one go, it refuses those removals and still makes any additions. The limit is set by the person installing.

### 17-063: Before any account exists, anyone may start the set-up; after that, only an admin
- Where: server-install-and-running / Installing on a NAS
- What: With the dashboard's own accounts and no account yet, anyone who opens the set-up wizard may read the task list, read and accept the licence, and create the first admin, which signs that browser in at once. Creation is refused when the studio does not use the dashboard's own accounts, when an admin already exists ("an admin account already exists"; two people submitting at once cannot both succeed), or with the account rule that failed. Any other step answers "create the admin account first (step 2), then this step opens". Once an account exists, or when the studio signs in by NAS account or single sign-on, every part of the wizard needs a signed-in admin ("log in first", "admins only"), and the wizard never offers to create an account. Creating the first admin is recorded with the visitor's address.

### 17-064: Updates are trusted only when signed with the vendor's key
- Where: releases-and-updates / Signing and trust
- What: The server accepts only builds signed with a signing key it holds. The build the vendor ships to customers already holds the vendor's key and the vendor's update feed; an installer who deliberately sets either to empty gets none. A value that is not a real key counts as no key. The server can tell whether every key it holds is the vendor's, which lets other pages say the matching private key is the vendor's and not something the studio must back up.

### 17-065: What the server does with new builds on the vendor's feed
- Where: releases-and-updates / Customer sites and the vendor's release feed
- What: Set by the installer, default "manual": new builds on the vendor's feed are only shown to the admin to publish ("manual"), published but not offered yet ("stage"), or published and offered to every computer ("current"). The feed is checked about once a day, and on demand from the wizard. A staged build cannot be made current until it has run for 30 minutes without crashing on at least one computer; the admin can change or turn off that wait.

### 17-066: Shared work: how much of each kind the studio runs at once, and how long a computer rests after a failure
- Where: fleet-jobs / Failures, retries and the queue
- What: Set by the installer: a studio-wide limit on how many pieces of each kind of shared work run at the same time (at least 1), and how long a computer is passed over after one of its pieces of work failed (default 2 minutes; 0 turns it off).

### 17-067: How fresh the dashboard's picture of the studio is
- Where: dashboard / Each computer's state
- What: Which computers are connected is refreshed about every 15 seconds. A tick or untick reaches the server's sharing within about a minute, and sync progress is refreshed about every minute. A new project folder is made syncable within about five minutes. Each project's file inventory is refreshed about every 15 minutes. The server checks for problems to alert about about every 10 minutes and runs its deeper checks about every 15 minutes. Old records are cleared about hourly. With syncing on the server not configured, none of the sync picture updates but housekeeping still happens.

### 17-068: Each computer's reports are classed by how safely they arrived
- Where: server-install-and-running / Connections and credentials
- What: For each computer the server notes whether its reports arrive over https, over plain http inside the studio's own network (including the private network and the same machine), or over plain http across the public internet; only a change is recorded. An admin's settings view shows how many computers are in each class. When the server cannot tell, or a name cannot be looked up within a second, it counts as inside the studio's network.

### 17-069: The set-up wizard is a list of tasks, each with a check, an optional action and a state
- Where: server-install-and-running / Installing on a NAS
- What: Setting up a new studio is a list of tasks. Each shows a title, a description, a check button (which only looks and reports, changing nothing), sometimes an action button, and its state: to do, ok, warning, failed or skipped, with a one-line detail and when it was last checked. States are kept, so restarting the server mid-way resumes where the admin was. A task's check or action that breaks shows as failed "internal error: ..." rather than an error page, and one task cannot be checked twice at once. Required tasks cannot be skipped ("... is required and cannot be skipped"); skipping an optional one shows "skipped by admin" and stays skipped even if it is checked later. Until every required task is satisfied the dashboard sends an admin to the wizard and its navigation carries a set-up badge. The same list stays available to an admin among the settings afterwards.
- Flag: several ways in: the first-run wizard and the admin's settings show the same task list

### 17-070: The "Done" task waits until the required tasks and three protections are dealt with
- Where: server-install-and-running / Installing on a NAS
- What: "Done" ("Everything required is configured.") stays to do, showing "waiting on: <task titles>", until every required task is satisfied and each of the signing key for updates, protecting the data and who to tell is ok or has been skipped. The order of tasks is: licence, admin account, your studio, storage check, secrets, syncing on the server, done (all required), then the optional ones: connect to the private network, connect to the NAS, protect your data, editors, software for editors, signing key for updates, who should we tell.

### 17-071: Wizard task: accept the licence
- Where: accounts-privacy-legal / The licence a person accepts
- What: "Welcome, EULA" (required): "Read and accept the license agreement." The page shows the licence text and a box to tick. States: "accepted v<version>" (ok); "awaiting acceptance of v<version>" (to do), so a new licence version needs a new acceptance; "no licence agreement is included in this build, so nothing has been accepted" (warning, which counts as satisfied only while the build truly has no licence, re-checked every time); "could not read EULA: ..." (failed). A licence added to the build after the server started is found later without a restart.

### 17-072: Wizard task: the admin account
- Where: server-install-and-running / Installing on a NAS
- What: "Create your admin account" (required, no action button): "A local account for you. No NAS credential is involved." With the dashboard's own accounts it is ok ("admin account: <names>") once any account exists (made with the first-admin form, 17-063), else "no admin account yet". With NAS sign-in or single sign-on, the task carries a box for the admin names and is ok as "admins are NAS accounts (<kind of NAS>): <names>" or "admins are your identity provider: <names>"; with none it asks the admin to type the account names that may administer the dashboard, adding under single sign-on that the provider's admin mark is only noted at sign-in and makes nobody an admin. Each name is 1 to 64 letters, digits, ".", "_", "@", "\" or "-", several separated by commas, at least one required ("enter at least one account name").

### 17-073: Wizard task: your studio
- Where: server-install-and-running / Installing on a NAS
- What: "Your studio" (required, no action button): "Name, tree name, drive letter and the project template." Ok as "<studio name> / <tree name>" once the studio's name, the tree name, the drive letter and the folders for every new project all have values; otherwise "not set: <which>". The values are the same settings as 17-045, 17-047 and 17-048.

### 17-074: Wizard task: the storage check
- Where: server-install-and-running / Installing on a NAS
- What: "Storage check" (required, button "DO IT"): "Confirm the tree is writable and lay down the shared asset folders." The check reports the projects folder as not available to the server, as "not yet probed: click Do it", or as "writable; <free space> free". The action writes, reads back and removes a small test file in the projects folder, then creates any missing shared library folders (never changing who owns anything): "writable; <free> free; created N shared asset folder(s)". Failures: "could not write/read/delete a probe file: ...", and for a permission refusal it names the account the server runs as and who owns the folder, and says to make a dedicated NAS account, give it to the server and redeploy; "writable, but could not create <folders> under <root> - check the mount's ownership"; or that the projects folder is not available to the server at all and must be added before redeploying. When the server cannot see the tree beside the projects folder it says the shared libraries live beside Projects on the NAS, outside its view.

### 17-075: Wizard task: the secrets
- Where: server-install-and-running / Settings and secrets
- What: "Secrets" (required, button "DO IT"), described as the credentials for sign-in, computer reports, b-roll indexing and the server's file transfer. Ok as "all five secrets present", else "not yet generated: <which>". The action makes and keeps the missing ones and says "generated N just now. Press RESTART SERVER on this row to load them"; this task has a restart button.

### 17-076: Wizard task: syncing on the server
- Where: server-install-and-running / Installing on a NAS
- What: Required, button "DO IT": confirms the server's own syncing answers. With no address for it: "no sync engine address is set: type it in the box on this row and save" (the box takes a full http or https address with no user name or password in it, and suggests the one shipped with the server). The check (5 seconds at most) says unreachable (failed), reachable but with no identity (warning), or ok with the first 7 characters of its identity; it becomes a warning when the sync administration page has no password ("anyone on your network can reach it. This server sets one itself on its next cycle, or now with the button on this row"). The action checks again, puts a password on that page if it has none, and records the server's sync identity for editors if none was recorded.

### 17-077: Wizard task: connect the server to the studio's private network and publish the dashboard on it
- Where: server-install-and-running / Connections and credentials
- What: "Connect to your private network" (optional, button "SIGN IN OR PUBLISH"): sign the server into the studio's private network. When the server carries its own private-network connection:
  - not signed in: the server is not signed in yet, with a link to open to add it to the network, or, with no link yet, a note to press the button;
  - signed in and published with https: ok, "signed in as <name>, published at <address>", or ok when the dashboard's address is already a private-network address;
  - its key expires within 14 days: warning "... its key expires in N day(s). When it does every editor loses the server at once.", with the steps in the network's own admin console to turn key expiry off for this server; a later expiry date is shown as a note;
  - not published: to do, saying https certificates are off for the network, or the publishing settings could not be read, or that nothing publishes the dashboard on the network, so no editor can reach it (it listens on the NAS itself only), each with the by-hand command.
  Without its own connection: no dashboard address yet is to do; an address on the private network is ok; any other address is to do, advising publishing on the private network "so editors need no VPN of their own".
  The button publishes the dashboard with https on the private network when signed in, or fetches a sign-in link (waiting up to about 5 seconds) and says "open <link> and sign in, then press CHECK on this task"; it never reports success by itself. Refusals: the network service did not answer, is not running, has https certificates off (with where in the network's admin console to turn them on, then press this again; "so no editor could connect"), publishing settings unreadable, publishing not turned on for the network (follow the link in the message once), or the server has no name on the network yet. Publishing records the published address as the dashboard's address if none was set.

### 17-078: The dashboard is put back on the private network by itself if it goes missing
- Where: server-install-and-running / Connections and credentials
- What: About once a minute, a server that is signed in to the private network checks that the dashboard is still published there and publishes it again if not. An existing publication, including one an admin made by hand, is never overwritten. The last repair (when, whether it worked, why not) is remembered for display. The server's alert checks see the network state, the key's expiry and whether the dashboard is published, and treat an unreadable answer as not checked.

### 17-079: Wizard task: connect to the NAS
- Where: server-install-and-running / Connections and credentials
- What: "Connect to your NAS" (optional, no action button): described as a one-time admin credential for snapshots and the editors' accounts on the NAS. The task carries a form: kind of NAS (TrueNAS or Synology), the NAS's address (name or IP with optional port, "with no http:// in front"), for TrueNAS an API key and the account it was made for, for Synology the admin account and password, and the NAS certificate fingerprint (blank remembers the first certificate seen and refuses a different one later; a fingerprint pins it; "1" checks it against the usual authorities; there is no way to turn checking off here). Refusals: a TrueNAS given a password ("a TrueNAS NAS is connected with an API key, never the admin password..."), a key without its account, and a NAS admin account that is also a dashboard admin ("Make a separate sign-in for the dashboard admin, so a stolen dashboard login is not the key to the whole NAS."). The check asks the NAS within 3 seconds: "<kind> <version> at <name> answered" (with a support note when the TrueNAS version is outside the supported range), or failed with the NAS's refusal in one line of at most 100 characters; with nothing stored it asks for the details.

### 17-080: Wizard task: protect your data
- Where: server-install-and-running / Snapshots, restoring and the server's disk
- What: "Protect your data" (optional, no action button): "Schedule NAS snapshots or export a /data backup." Ok when the NAS has any scheduled snapshot task ("N periodic snapshot task(s) on the NAS", with the newest backup), or when only a backup of the server's own data under 7 days old exists (saying there is no snapshot schedule and why); otherwise to do, pointing to the backup instructions. On Synology it says snapshot schedules cannot be read.

### 17-081: Wizard task: editors
- Where: server-install-and-running / Installing on a NAS
- What: "Editors" (optional, no action button): "Add your first editor." Ok as "N editor(s): <first five names>, and N more", counting every person the dashboard knows (and enabled editor accounts with the dashboard's own accounts); otherwise "no editors yet", pointing to where users are added.

### 17-082: Wizard task: software for editors
- Where: releases-and-updates / Customer sites and the vendor's release feed
- What: "Software for editors" (optional, button "CHECK NOW"): "Publish the current companion build for Windows and macOS." Ok as "windows <version> current, macos <version> current"; a warning when only one platform has a current build ("<platform>: none published"); to do when neither does, pointing to publishing one from the vendor's builds; failed when the server cannot read its builds. The task carries a box for the vendor update feed's address (must be https). The button checks the vendor's feed now under the studio's feed choice (17-065) and adds "published from the vendor feed: <versions>", "the vendor feed has nothing this dashboard does not already hold", or a warning that the check failed; with no feed address it says there is nothing to check for.

### 17-083: Wizard task: the signing key for updates
- Where: releases-and-updates / Signing and trust
- What: "Signing key for updates" (optional, no action button): "The key this server checks every CC Sync build against." Ok as "the vendor's signing key is pinned: this server only accepts builds the vendor signed", or "N release signing key(s) configured" (the key itself is never shown). With none: "no release signing key: this server refuses every build until this server holds the vendor's public signing key, so your editors' computers can never be updated from here. Do not make a key of your own: paste the vendor's in the box on this row and save ... Skipping means updates wait until you do". A pasted value that is not a key is refused ("it should be 44 characters of letters and digits ending in =").

### 17-084: Wizard task: who should we tell
- Where: dashboard / Alerts by mail
- What: "Who should we tell?" (optional, button "SAVE A DESTINATION"): "This server checks dozens of things about your fleet every few minutes. It needs somewhere to send what it finds. With nobody to tell, the first anyone hears of a stopped sync is an editor asking." States: "nobody is being told" (to do, asking for an e-mail address or a web address to post to); a warning when e-mail or posting was chosen without its address, when there is an address but no mail server ("open Settings, then ALERTS and fill in the mail server"), or a mail account without its password; ok as "alerts go to <address> through <mail server>" or "alerts go to <masked web address>". Every ok adds whether the daily "still here" message is on, or that with it off nothing tells you if the server itself goes down. The admin gives one e-mail address (up to 320 characters, an "@" not at either end) or one web address (up to 1,024 characters), not both ("pick one: ..."), and may turn the daily message on or off; an e-mail address also becomes the sender if none is set. A test button sends "This is a test of the CC Sync alert channel. Nothing is wrong." even if one was just sent, and says where it went.
- Flag: several ways in: the wizard's short form and the full alert settings

### 17-085: Saving a wizard form restarts the server, and secrets typed there are never shown back
- Where: server-install-and-running / Settings and secrets
- What: Only a signed-in admin can save a wizard task's form. After saving, the server restarts by itself about 1.5 seconds later, after the answer reaches the browser, so the new value is in force on the next start. A secret field never shows its value, only whether one is set; leaving it blank keeps what is stored, while blanking a plain field clears it; a secret over 400 characters or holding control characters is refused. A value the person installing set on the server always wins over one typed in the wizard. Each form notes which install-time settings it stands in for. Refusals: "this step has nothing to fill in here", "not a setting of this step: ...", "nothing to save", "could not store the setting (...)", and field errors prefixed with the field's label.

### 17-086: An admin can restart the server from the wizard
- Where: server-install-and-running / Updates, restarts and rollbacks
- What: A restart button (on the secrets task) restarts the server about 1.5 seconds after it is pressed. The restart is recorded in the admin's audit trail.

### 17-087: Settings changes are recorded in the audit trail without their values
- Where: dashboard / Settings and setup
- What: Every save of studio settings, import, undo, wizard form save and restart is recorded with who did it and which settings it touched, never the values; a saved alert destination is recorded by its type only, never the address.
