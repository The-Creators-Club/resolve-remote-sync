# P4a: phase 4, first half (group `settings-fleet`): Site and Packages

Builder P4a, 2026-09-25, worktree branch `ui-port`. This run picked up where an
earlier P4a run stopped: the earlier run had written the Site page, its
Android partial, `static/cc/site_settings.js`, `static/cc/settings_fleet.css`,
`ai_providers.PROVIDER_HELP` and `ever_current` on the package view. This run
checked that work, then built Packages, the registry rows and the tests. Nothing
is committed and no version was bumped.

## Built

**Site** (`/admin/settings`; bench `design/site.html`)
- `templates/cc/admin_settings.html`: five tabs (studio and tree, features, ai
  providers, export and history, android). They only switch which panel shows.
  `#settings-form` wraps only the studio-and-tree and features panels, and
  every field keeps its `site_store.KEYS` name (`indexer_model_tier`). The AI
  section, `#settings-import-form`, `#android-form` and `#ui-groups-form` sit
  beside `#settings-form`, never inside it. The field hints are the classic
  words. The advanced connection fields are behind a `<details data-key>`.
  Import and undo ask through their own `<dialog id="site-ask">`.
- `templates/cc/partials/android_settings.html`: the Android window's body.
  Both android.py routes swap it back.
- `static/cc/site_settings.js`: a fork of the classic file, which stays frozen.
  The write half is unchanged: same routes, same bodies, same serialisation.
  The render half is rewritten:
  - only providers that are set up are listed, each with a manage menu
  - "add new" opens a picker, then a short wizard (API key: get, paste, test;
    CLI: allow, install, sign in, test)
  - a who_answers window, and a pin select
  - the "how to get a key" copy comes from the API's `help`
    (`ai_providers.PROVIDER_HELP`)
- `static/cc/settings_fleet.css`: the few extra rules that Site and Packages
  need on top of components.css.

**Packages** (`/admin/packages`; bench `design/packages.html`)
- `templates/cc/admin_packages.html`:
  - the page keeps classic's 30 s innerHTML poll, on a plain wrapper
  - a `this_dashboard` window whose body loads once, by a load trigger, and is
    never polled
  - scripts: `cc/dashboard_update.js`, plus the shared `confirms.js` for the
    feed policy select
- `templates/cc/partials/admin_packages.html`:
  - the whole context comes from `_packages_and_feed`
  - `.admin-packages-box` is a plain div that holds the windows: currently
    served, rollout, from the vendor, other versions held (with
    `data-key="pkg-other"` kept), out of date computers. This is 3.1's keeper
    fallback, and every form still targets `closest .admin-packages-box`.
  - chips become tags, and nothing is bracketed
  - every served row gains a **roll back to** select (`name=version`, POST
    `packages/current`). It lists only the builds a plain MAKE CURRENT accepts.
  - every held build keeps its own row with all of these: canary line, push to
    one computer, make current, the typed override (with the unsigned
    `hx-confirm` only when the build is unsigned), delete, and the CR-335
    `error_for` refusal
  - the delete question now says "trash on this server for 30 days"
  - every form that asks for confirmation has a `data-confirm-key`, so the
    confirm still works after the poll replaces the form
  - fixed-width keys with busy text laid over them (`form.htmx-request`), so
    nothing shifts
- `templates/cc/partials/admin_dashboard_update.html`: the body of the
  `this_dashboard` window.
  - `#dashboard-update` holds no oob fragment
  - two select-plus-key pairs:
    - older bundle on the feed: `data-dashupd-apply` + `data-dashupd-older="1"`
    - tree or image rollback: `data-dashupd-rollback`, with
      `#dashupd-restore-db` and `#dashupd-schema` kept
- `static/cc/dashboard_update.js`: a fork of the classic file, which stays
  frozen.
  - clicks are matched with `closest()`, and classes are set with `classList`
  - `data-dashupd-for` copies each select's value onto its key
  - `reloadPanel()` sends the page's `hx-headers` (CSRF and the `X-CC-UI` set)
  - `HX-Refresh` reloads the page instead of swapping an empty body in
  - a 409 carrying `X-CC-UI-Want` shows the reload line and keeps the panel
  - the rollback confirms are still native `window.confirm` (3.2, wave 5)
  - `window.ccsyncDashUpdate` is exposed as a test seam
- `src/ccsync_dashboard/ui_packages.py` (new): the Jinja global
  `pkg_rollback_choices(rows, current)`. It lists held builds of the same kind
  and platform that are older than current, not recalled, not blocked on the
  dashboard version, signed and present on disk. A companion build also needs
  `ever_current` or a finished soak. It mirrors
  `package_store.make_current_refusal`. `app.py` imports it with one line,
  next to the ui_health router.

**Registry**: five rows in `ui_variant.TEMPLATE_GROUPS` under "phase 4, first
half (P4a)".

**Shared fix (small)**: `templates/cc/shell.html`'s `#cc-confirm` had no
`data-cc-confirm-q` / `-ok` / `-cancel` attributes. `cc.js` looks for exactly
those, so every `hx-confirm` on a terminal page would have thrown a TypeError
after `preventDefault`, and nothing would have been sent. I added the three
attributes and made no other change.
