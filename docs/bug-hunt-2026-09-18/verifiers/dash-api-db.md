## dash-api-1
- Verdict: CONFIRMED (high)
- Duplicate of: comp-sync-1 (the companion side of the same wire: "lane B puts a file back at the exact path it just trashed it from, forever, while the server's inventory is stale"). Same defect, two ends; whoever fixes it must fix both.
- Reasoning: I could not refute the mechanism. `db.replace_nas_media` (db.py:8395-8443) returns False on a collapse, leaves `nas_media` untouched, writes `nas_inventory_state.last_error` and deliberately does NOT update `tree_sig`, so the stale rows persist across every subsequent cycle. `locate()` (locate.py:79-102) joins `nas_media` to `projects` on `active=1` only, and `_has_been_walked` is explicitly documented as "a row in `nas_media` is the evidence, not a row in `nas_inventory_state`" - which is right for the never-walked case and wrong for the refused case. On the consuming side `rclone_lane._relocate_trashed` (:3974-4045) adds every located file to `_server_relocated_keys` before deciding what to do with it, and `_count_relocations` (:4150-4193) subtracts that set from the deletion count in both arms, including the arm where the remote listing failed. So the breaker is disarmed by the same stale answer that drives the restore. The `locator` is constructed unconditionally in `app.py:2335`, and the whole fleet is on 0.9.74, so this is live behaviour, not a dormant path.
- Evidence: read `replace_nas_media`'s refusal branch (it updates only `walked_at`/`last_error`), the locate query, and both companion call sites. The one mitigation I found and the hunter did not cite: DASH-5's self-diagnosis half (KNOWN_BUGS ~line 6208) writes an `inventory_refused` error notice per active project with a non-empty `last_error`, so the operator IS told the walk was refused - but nothing on the locate path or the companion path reads that state, so the churn and the disarmed breaker stand exactly as described. `tests/test_locate.py` has no refused-inventory case, confirmed by reading it.
- Fix note: the suggested fix (exclude projects whose `last_error` is non-empty, and carry the excluded slugs back) is right and is the minimal one. Files a fix must touch: `dashboard/src/ccsync_dashboard/locate.py`, the locate route's response model in `api.py` if the excluded-slug list is added to the JSON, `companion/src/ccsync_companion/sync/server_locate.py` (`LocateAnswer` would have to carry and log the new field - and must keep working against a dashboard that does not send it), and `dashboard/tests/test_locate.py`. Note the `walked_at` staleness half of the suggestion is the weaker half: a project whose `tree_sig` is unchanged is legitimately not re-walked, so an age test on `walked_at` alone would exclude healthy projects. Gate on `last_error` first.

## dash-api-2
- Verdict: CONFIRMED (high)
- Duplicate of: dash-db-3 and dash-core-2 (three hunters found the same handler). dash-api-2 is the strongest statement of it - the other two describe the extra lock wait, this one describes the event-loop block, which is the part that makes it high rather than medium.
- Reasoning: `unhandled_error` is `async def` (app.py:1318), so it executes on the event loop of a `--workers 1` container, and the busy branch calls `db.connect(settings.db_path)` + `notices.record_db_busy` + `conn.commit()` synchronously, with no `run_in_threadpool`. `db.connect` (db.py:~690) sets `timeout=busy_ms/1000` and `PRAGMA busy_timeout=5000` from `BUSY_TIMEOUT_MS = 5000`, so the worst case is a 5 s stall of the whole loop - and the precondition for reaching this branch is that somebody has held the write lock for at least 5 s already, which is precisely when that stall is most likely to be paid in full. The `except Exception` around it (app.py:1373) swallows the resulting `database is locked`, so the notice the 2026-09-17 rework exists to produce is the one that is lost under sustained contention. I could not find any escape hatch: no threadpool, no short timeout, no in-memory coalescing.
- Evidence: read the handler and `connect`. The hunter's 5.4 s measurement is consistent with `timeout=5.0` plus the pragmas in `connect` (which themselves touch the database). `tests/test_db_busy_2026_09_17.py` injects the OperationalError from a hand-registered route on an idle database, so nothing in the suite measures the contended case - confirmed by reading the file.
- Fix note: the suggested fix is right and cheap: `db.connect` already takes `busy_ms` as a keyword (`def connect(path, *, busy_ms=BUSY_TIMEOUT_MS)`), so `db.connect(settings.db_path, busy_ms=250)` needs no signature change, and wrapping the record in `run_in_threadpool` gets it off the loop. A fix must touch `app.py`'s `record_server_error` branch one hunk down for the same reason (out of territory here, claimed by dash-core) and should add a test that holds a real `BEGIN IMMEDIATE` on a second connection rather than injecting the exception.

## dash-api-4
- Verdict: CONFIRMED (low)
- Duplicate of: dash-mounts-ui-5 ("a lane a machine never reported is drawn in the same quiet colour as a healthy one") - same defect, same two files.
- Reasoning: verified both sides. `health.lane_strip` (health.py:877-883) fills a missing lane with `{"state": "not reported", "chip": GREEN, "reported": False}`, and `fleet_grid.html:207` renders `class="chip lane {{ "quiet" if lane.chip == "green" else lane.chip }}"` - `lane.reported` appears nowhere in the template. So a lane that never arrived is styled identically to a healthy one, and the `reported` flag is dead data. This is the "green while dead" shape the product's own conventions argue against, but it is genuinely low: a machine that has stopped reporting ENTIRELY is still caught by the row headline and the silence chips, so the reachable case is the narrower one of a single lane section going missing from an otherwise-live report.
- Evidence: read `lane_strip` and the template hunk verbatim; `reported` has no reader in `dashboard/templates`.
- Fix note: the suggested fix is right and is the smaller of the two options - have the template read `lane.reported`, because changing `chip` to amber in `lane_strip` would also change what the note/headline counters downstream see if any of them key off chip colour. `test_fleet_grid_declutter_2026_09_11.py` pins the order and the green-is-quiet rule and would not break; a fix should add the not-reported case there.

## dash-api-5
- Verdict: CONFIRMED (low)
- Duplicate of: none
- Reasoning: everything checked out and one part is worse than the hunter thought. `SkippedExistsIn.subpath` (api.py:7239) is declared with a comment saying nothing reads it, and nothing does - it is absent from the `machine_state` upsert (api.py:7838) and from `db.py:7185`. The stored figure is one per MACHINE while the scan is per subpath (`rclone_lane._refresh_size_mismatches(subpath)`, :3040), and `ui.py:324-327` states it of the whole computer. The "never clears" half is narrower than claimed: a later scan that finds nothing still reports `count: 0` (the report dict is truthy even at zero, so `out["skipped_exists"]` is sent at rclone_lane.py:4342) and `COALESCE(0, ...)` writes the zero. But the reverse is the stronger bug and the hunter missed it: on a machine syncing several projects, each project's scan OVERWRITES the single number, so project Y's zero hides project X's four - the count is not just mis-scoped, it is racy between scopes. The failure scenario as written (project untied, no further scan, count frozen) also holds.
- Evidence: read the companion's `_refresh_size_mismatches` and the report assembly at rclone_lane.py:4342; read the upsert and the copy. `grep -n subpath api.py` finds no reader.
- Fix note: the suggested fix is right, and the honest version is to store the count keyed by subpath (or to store the samples' scope alongside) rather than to clear on scope change. Any fix touches `api.py` (the model and the upsert), `db.py` (the `machine_state` columns and therefore a migration), `ui.py`'s sentence, and the tray copy in `companion/tray.py` only if the wire shape changes - the companion already sends `subpath`, so the dashboard can be fixed alone.

## dash-api-6
- Verdict: CONFIRMED (low)
- Duplicate of: none
- Reasoning: the ordering claim is factually right - `package_store.store_verified_package` does `os.replace(part_path, dest_dir / filename)` (package_store.py:458) and only then `db.insert_companion_package`, with the commit later still. I checked the route for the guard the hunter assumed: `api_publish_package` 409s on `db.get_package(conn, platform, version, kind) is not None` (api.py:6180) BEFORE the body is streamed, so two overlapping publishes of the same version both pass that check and only the loser's INSERT hits the `UNIQUE (kind, platform, version)` constraint - after its bytes are already at the served filename. The ship's DASH-3 note shows this exact overlap (Ctrl-C a stalled publish, re-run while uvicorn drains the first) is a real operational shape. What keeps it low: the damage needs DIFFERENT bytes for the same version, i.e. a rebuild of an unbumped version, and the resulting failure is loud (the companion's sha check refuses the download) rather than silent.
- Evidence: read the route from the 409 check through the streaming/hashing block to the `run_in_threadpool` call, and `store_verified_package` end to end. The per-request `uuid4` staging name means the two uploads no longer corrupt each other's bytes - only the final placement races.
- Fix note: "move the file after the insert, before the commit" is the right shape and keeps the DASH-3 reasoning intact. Note that the gate one hunk below the insert ("THE FLIP, GATED", REL-1) can raise AFTER the insert, so the placement must sit between the insert and that gate, or the refusal leaves a placed file with a rolled-back row - the same class of hole moved one line. `dashboard/tests/` has no test for the failed-insert-after-replace path; a fix should add one.

## dash-db-1
- Verdict: CONFIRMED (medium)
- Duplicate of: dash-collector-alerts-4 ("the new 'slow write' notice blames the collector for holding a write lock the collector deliberately does not hold") - same defect, same line.
- Reasoning: `Collector._timed` (collector.py:469-501) starts `time.monotonic()` before `fn(conn)` and measures the entire runner - `_run_inventory`'s SSH walk, `_run_enforce`'s and `_run_connections`' Syncthing round trips - then treats `elapsed > BUSY_TIMEOUT_MS/1000` as evidence the poll "held the database's write lock". Almost none of that elapsed time is inside a write transaction; `_timed` itself commits before the measurement is even evaluated. The irony the hunter names is real: the same test file (`test_db_write_locks.py`) exists specifically to pin that the collector does NOT hold the lock over network calls, and the new branch then reports it as if it did. The unclearable half checks out too: `db.notice` NULLs `cleared_at` on every re-assert by design, and there is no `clear_notices_of_kind` for `slow_write` anywhere (`grep -n "slow_write" db.py ui.py` returns nothing at all).
- Evidence: read `_timed` verbatim; confirmed `SLOW_POLL_SECONDS = 1.0` at collector.py:117 and `BUSY_TIMEOUT_MS = 5000` at db.py:686. The two `record_slow_write` tests call the function directly and `test_a_slow_poll_says_so_in_the_log` monkeypatches `SLOW_POLL_SECONDS` to -1.0 with a zero-cost runner, so the 5 s branch is never entered - verified by reading test_db_write_locks.py:280-292.
- Fix note: the suggested fix is right, and the "give it its own wording" half is the safer one to land first - re-timing only the committing section means threading a clock through every runner. A fix must also touch `notices.record_slow_write`'s body and fix line (the wording is the wrong claim, not just the trigger), and `api.py:9405`'s caller, which measures a real write and is the one honest user of the function today. Whatever lands should add the clearing writer dash-db-2's fix will want anyway.

## dash-db-2
- Verdict: CONFIRMED (medium)
- Duplicate of: dash-collector-alerts-5 ("`db_busy` and `slow_write` are notice kinds with a writer but no registry row") - same defect.
- Reasoning: reproduced by inspection rather than by AST: `grep -n "db_busy\|slow_write" db.py ui.py api.py` finds NOTHING in db.py or ui.py, so neither kind is in `NOTICE_KINDS` (db.py:3165-3325) and neither has a `notice_href` case. `ui.py:1848-1852` takes a health row's title from `{k["kind"]: k["what"]}` built out of `db.notice_kinds()` with `or n.get("kind")` as the fallback, so a contention notice renders with the literal title `db_busy`. The WHAT THE SERVER CHECKS panel is built from the same registry, so database contention is a condition the server does check and never lists - the mirror image of the false-[ OK ] problem the registry was built for, exactly as the hunter says.
- Evidence: the greps above plus a read of `notice_kinds()`, `notice_href()` and the `add(...)` call in ui.py's health rows.
- Fix note: the suggested fix is right and small. Two cautions: `NOTICE_KINDS` rows drive `notice_check_times` / `[ NOT CHECKED ]`, so registering a kind whose writer only fires under contention will render as NOT CHECKED on a healthy fleet unless `_mark_notice_checked` is called on the happy path too - register the kind WITH its check-time writer, which is CLAUDE.md's own rule. And the proposed generic test would immediately fail for any kind written outside `ccsync_dashboard/*.py`, so scope the AST sweep to that package as the hunter did.

## dash-db-3
- Verdict: CONFIRMED (medium as filed; the correct severity is high)
- Duplicate of: dash-api-2 (same handler, same lines) and dash-core-2. I judged the severity under dash-api-2: the extra lock wait this finding describes is real, but the event-loop block dash-api-2 identified is the larger cost, so the merged finding should be filed high.
- Reasoning: everything asserted is true of the code. The handler is entered only because a request exhausted its 5 s busy timeout, and its response is to open a second connection at the same default `BUSY_TIMEOUT_MS` and take the write lock (`db.notice` upsert plus `conn.commit()` in `notices.record_db_busy`, notices.py:1130-1150). The client's worst case doubles, the extra waiter lands on the one route (`/api/v1/report`) the rework was written for, and the `except Exception` at app.py:1373 swallows the second `database is locked` - so the record is destroyed by the very condition it documents. I found no rate limit, no short-circuit and no in-memory path.
- Evidence: read `record_db_busy` (it ends in `conn.commit()`), the handler, and `db.connect`'s default. `test_the_handler_answers_a_locked_database_503_with_retry_after` drives an idle database, so the contended case is untested.
- Fix note: `db.connect` already accepts `busy_ms`, so the short-timeout fix is a one-word change; the queue-and-let-the-collector-drain option is better but needs a place to hold the events across a recreate, which is the thing the rework was trying to avoid. Fix this and dash-api-2 as one change, and take `record_server_error` (one hunk below, dash-core's territory) with it.

## dash-db-4
- Verdict: CONFIRMED (low)
- Duplicate of: none
- Reasoning: `file_move_target_machines` (db.py:5496-5500) binds `media_key + "/%"` into `rel_path LIKE ?` with no `ESCAPE`, and `_` is a single-character wildcard, so a directory move of `Gold_Card_Meetup` matches any sibling of the same length differing only where an underscore sits. I confirmed there is no `ESCAPE` clause anywhere in db.py. The consequence really is bounded: this list drives `commands.file_moves`, and the companion's "already where the server has it" / not-found arms answer harmlessly (the hunter's own coverage note establishes this, and I agree), so the visible damage is a wrong per-machine progress row. Over-matching, not under-matching, which is the safe direction. Low is the right severity.
- Evidence: read the statement and the surrounding docstring; `grep -n "ESCAPE" db.py` returns nothing.
- Fix note: the suggested fix is correct; escape `\`, `%` and `_` in that order and add `ESCAPE '\'`. Anything else that builds a prefix LIKE on a path should be checked in the same change - db.py:9445 is the only other one and documents itself as a prefilter with an exact re-check, so it is fine as is. A test should use a real underscore-bearing project name (`Gold_Card_Meetup`), which is what the fleet actually holds.

## dash-db-5
- Verdict: CONFIRMED (low)
- Duplicate of: dash-mounts-ui-3 ("the Assignments computer picker offers the unassigned bucket to a person who HAS computers, and choosing it renders 'this'...") - same defect, and that hunter reached the rendered page too.
- Reasoning: the two halves disagree exactly as described. `_machine_options` (assignments.py:171-184) returns early with the bucket when the person has no machines, and otherwise APPENDS the bucket whenever `db.selections_for_machine(conn, editor, db.ANY_MACHINE)` is non-empty - its own docstring says it must never invent a bucket option beside real computers, and then it does, on exactly the condition the docstring calls out as the legacy shape. The column loop (assignments.py:95-108) emits a `machine=""` column only under `if not machines: ... continue`, so filtering to `machine=""` for a person with machines leaves the column list empty. The hunter's scratch reproduction against the real app matches what the code says.
- Evidence: read both functions verbatim; the docstring at :175-178 is itself evidence that the appended option contradicts the intent.
- Fix note: of the two options offered, "emit the bucket column whenever bucket rows exist" is the honest one but changes what an admin sees on every affected person's grid and may interact with the tick-writing routes (a tick written into a `machine=""` column for a person who HAS machines is the shape `db.selections_for_machine` only honours for a machine with no plan, so the column would have to be read-only or the write path would have to refuse). The narrower fix - offer the option only when the person has no registered machine - matches the column loop and cannot create a new write shape. `test_admin_assignments.py` covers only the no-machines case and would not break either way; a fix should add the both-shapes case.
