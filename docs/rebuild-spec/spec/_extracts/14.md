# Extract of inventory section 14

## Items

### 14-001: The dashboard's pages need nothing from the internet to display properly.
- Where: whole-product / Requests, logs and outside programs
- What: Every font, script and icon a dashboard page uses is served by the studio's own server. A studio whose network has no internet access still sees complete, correctly drawn pages. No page reaches out to a third party while a person reads it.

### 14-002: The dashboard can be installed on a phone or desktop as an app that opens in its own window.
- Where: dashboard / Phones and the installed app
- What: The dashboard offers itself as an installable app named "CC Sync" with the description "The fleet dashboard: who is syncing, what is transferring, what is wrong." Installed, it opens on the dashboard's front page in its own window with no browser bars (or minimal ones where the device insists), in any orientation, with proper icons for phones, including ones a phone may crop to a circle or rounded square. Where the browser offers installation (Chrome-family browsers), an "install this app" button is shown; pressing it opens the browser's own install dialog once and the button goes away. Nothing is shown when the dashboard is already running as an installed app or the browser makes no offer (Safari, Firefox). Installation and the offline page (14-003) are only available when the dashboard is reached over https (or on the same computer); over plain http on the studio's network nothing is offered and nothing is said.
- Flag: undetermined: the inventory could not confirm that the pages actually carry the place where the install button goes, so the button may never appear.

### 14-003: When the server cannot be reached, a dashboard page says so instead of showing a browser error, and nothing personal is kept on the device.
- Where: dashboard / Phones and the installed app
- What: Opening a dashboard page always asks the server first. Only when the server cannot be reached at all is a saved "offline" page shown (or, if even that is missing, a bare "offline"). The device keeps only the dashboard's general files (pages' styling, scripts, icons and the offline page) so they appear at once; each is refreshed quietly in the background and a failed refresh never turns a working file into an error. Nothing that depends on who is asking (any data, any panel, sign-in, the b-roll, music, YouTube and Timeline Cards apps) is ever stored on the device; it always comes from the server. Each new dashboard release replaces what the device holds, so an old copy never outlives an update.

### 14-004: Dashboard pages keep themselves current, refresh at once when a person returns to them, and refresh less often on phones.
- Where: dashboard / Pages that refresh and answer clicks
- What: Panels on a page refresh themselves on a timer. On a touch device (phone, tablet), a panel that refreshes every 2 seconds on a desk refreshes every 10 seconds instead, and one that refreshes every 5 seconds refreshes every 15 seconds; slower panels are unchanged. While the tab or app is in the background nothing is fetched at all; the moment it is shown again every panel refreshes once at once, so what a person sees on returning is current rather than minutes old.
- Flag: undetermined: the refresh interval of each individual panel is not given in this section.

### 14-005: A page that has stopped updating says so plainly, with the reason, until it recovers.
- Where: dashboard / Pages that refresh and answer clicks
- What: When a page's exchanges with the server start failing, a warning fixed at the bottom of the page reads "THIS PAGE HAS STOPPED UPDATING (last update <N seconds / minutes / hours ago>). Nothing below is current." followed by the reason:
  - session ended: "Your session has ended. Reload the page and sign in again."
  - refused to this account: "The server refused this to your account (403)[: <server's reason>]. Reload the page; if you were signed out, sign in again."
  - any other error: "The server answered <status>. Reload the page to try again."
  - server unreachable: "The server could not be reached. Reload the page to try again."
  - no answer in time: "The server did not answer in time. Reload the page to try again."
  The warning never covers anything on the page. It disappears by itself the moment any exchange with the server succeeds. Text from the server is always shown as plain text.

### 14-006: A refused change is shown next to the control that asked for it, not as an outage.
- Where: whole-product / Could not check, refusals and nothing silent
- What: When a button, form or switch that changes something is refused by the server (other than because the person is signed out), the page does not show the "stopped updating" warning. Instead a short note appears directly above the control used, and is scrolled into view: "Not allowed: <server's reason>" (or "Not allowed: this account cannot do that.") when the account may not do it; otherwise "Refused: <server's reason>" (or "Refused: the server answered <status> and gave no reason."). A tick box that was flipped goes back to what the server still holds. Using the same control again removes the old note first. Likewise, when a press redraws a panel that carries an error or an outcome message (for example a test mail that went out or failed), that message is moved to directly above the control that was pressed and scrolled to the middle of the screen; an error wins over an outcome. When several forms on a page do the same kind of thing, the message goes beside the one actually used. For a form taller than half the screen, the message goes above its last button instead. Timed refreshes never move a message; only presses do.

### 14-007: Timed refreshes never wipe what a person is in the middle of doing.
- Where: dashboard / Pages that refresh and answer clicks
- What: A panel is not refreshed by the timer (the refresh is skipped, and the next one runs as normal) while: the person's typing cursor is in one of its text boxes or drop-downs; it holds a field the person has changed and not yet sent (for up to 5 minutes after the last change); a change it sent is still waiting for an answer (up to 5 minutes); a folder browser opened from it is open (up to 5 minutes); or a pop-over of it is open. The same holds for the refresh that happens on returning to the tab. Fold-out rows that a person opened in a refreshing list stay open across refreshes, and closed ones stay closed. While a confirmation question is open (14-010), no refresh happens at all.

### 14-008: Every status mark and control explains itself on hover, on keyboard focus and on a tap.
- Where: whole-product / Wording
- What: Every control and every status mark (chip, tag, light) carries a short explanation.
  - With a mouse, hovering shows it after a quarter of a second, beside the element and kept on screen; the pointer may move onto it.
  - With a keyboard, explained marks can be reached with Tab; focusing shows the explanation at once (after nearly a second for buttons, so tabbing along a row of buttons does not cover the next one); Escape hides it; it follows its control while the page scrolls.
  - On a touch screen, every control with an explanation has a small "?" beside it that opens an explanation sheet with the control's name and text; tapping a status mark itself also opens the sheet. Enter or Space opens it from the keyboard. Tapping the sheet, tapping elsewhere or Escape closes it.
  The explanation is also given to screen readers.
- Flag: built twice: two separate ways of opening the same explanation sheet exist (tapping a mark, and the "?" button), and both behave the same.

### 14-009: Every page remembers where the person was on it.
- Where: dashboard / Overview, menus and finding things
- What: For each dashboard page (not the b-roll, music, YouTube or Timeline Cards apps), the browser remembers the scroll position, which fold-out sections were open (up to 100), which sections the person folded away, and the last tab chosen. A page showing a particular person, computer, project, kind or view is remembered separately from the plain page; search text does not make a separate memory. The memory survives the phone closing an installed app, and is ignored after 8 hours. On returning, sections are re-opened and the page scrolls back once its panels have loaded (waiting up to 3 seconds, then going to the remembered heading). It does not restore when the address points at a particular place, when the browser restored the page itself (Back/Forward), or once the person scrolls, touches, types or clicks first. There is no visible cue, and nothing happens where the browser blocks storage. Folded sections stay folded across refreshes.

### 14-010: A question before an action is never answered by accident, and nothing is sent if the page changed meanwhile.
- Where: whole-product / Safety in what the product does
- What: Any action that asks first shows the question with OK and Cancel, with Cancel chosen by default. Cancel or Escape sends nothing and puts back any tick box that had already flipped. While the question is open the page does not refresh. If the control was redrawn while the question was open, it is found again and the action is sent once; if it can no longer be found, the dialog says "This changed while you were reading; nothing was sent." with only a close option.
- Flag: differs: some questions appear in the page's own dialog and some in the browser's own confirm box; they behave the same apart from how they look and the default focus.

### 14-011: An answer, error or one-time secret is never hidden inside a folded section.
- Where: dashboard / Pages that refresh and answer clicks
- What: A person can fold sections of a page away, and the choice is kept. A folded section opens by itself (without changing the remembered choice) when: an answer to something the person did lands in it, a link points inside it, an error, result or refusal lands in it, a one-time secret is shown in it, or a settings save refuses a field in it. An answer that appears in a separate place is scrolled into view and given keyboard focus, unless it came from a timed refresh.

### 14-012: A link can point at any place on a page, and opening it takes the person there.
- Where: dashboard / Overview, menus and finding things
- What: Following a link to a particular part of a page opens whatever holds it (a tab, a folded section, a fold-out) and scrolls to it, on load and whenever the link changes; clicking the same link again does it again. A link naming a fold-out section on the overview opens it once; folding it again is respected by later refreshes. Tabs can be moved between with the arrow keys, Home and End. There are no single-key shortcuts on dashboard pages other than "/" for a find box.

### 14-013: A find box filters the projects list as the person types, in any script.
- Where: dashboard / Overview, menus and finding things
- What: Above the list of projects a find box filters project rows by name as the person types, ignoring case and treating accented letters written either way as the same. Nothing is filtered while an input method (Zhuyin, Pinyin and the like) is still composing; the filter applies when composition ends. Groups with no match are hidden; groups with a match open while filtering and close again when the box is cleared (only those it opened). "No match" is shown when nothing matches. The filter and the typed text survive the list refreshing. Pressing "/" outside a text box puts the cursor in the find box.

### 14-014: Copy buttons put a value on the clipboard and say whether it worked.
- Where: whole-product / Wording
- What: Wherever a value is meant to be copied (one-time passwords, fresh computer sign-in keys, checksums, device ids), a Copy button copies it. The button reads "Copied" for 2 seconds. If copying is impossible but the value can be selected, it is left selected and the button reads "Selected: press Ctrl+C" (the same wording on a Mac); otherwise "Could not copy". Copying works over plain http as well as https.

### 14-015: Dashboard pages respect accessibility settings and stay usable by keyboard and touch.
- Where: whole-product / The look
- What: Every focused control shows a clear focus outline. Nothing blinks or pulses forever: warning lights, a loading episode and a saving tick box blink a few times and stop. With the operating system's reduce-motion setting on, all animation and transitions are off. With Windows high contrast on, marks whose meaning is otherwise only colour get borders and the current page is outlined and underlined. On a touch screen every button, tab, tick box, field and list row is at least 44 pixels tall. On a phone, text is never smaller than 12 pixels, text boxes are large enough that an iPhone does not zoom in on them, long names wrap rather than widening the page, and wide tables and code scroll inside themselves. Pages do not jump when an answer arrives (result lines keep their space) and buttons keep their width while their label changes to a busy word during a request. The pages are always dark, including the browser's own drop-downs and scroll bars.

### 14-016: A person is warned two weeks before their sign-in runs out, so offline use keeps working.
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: Once a browser's sign-in has 14 days or less to run, a non-blocking note appears at the top of each page: "Your sign-in expires in <N days | less than a day>. Sign in again now so this phone/computer keeps working offline for another 100 days." "Sign in again" renews the sign-in while it is still live and returns to the same page. "Not now" hides it until the next calendar day. The note is shown only while the device is online, and checks the real expiry with the server (a saved page may carry an old one).

### 14-017: The admin can confirm before letting every new vendor build reach the whole studio unapproved.
- Where: releases-and-updates / Customer sites and the vendor's release feed
- What: When an admin chooses the policy that publishes new builds from the vendor automatically AND makes them current, they are first asked: "Publish new builds automatically AND make them current? Every editor's computer will take each new build from the vendor feed without anyone approving it first. Choose 'stage' if you want to test a build before the fleet gets it." Cancel puts the previous policy back and changes nothing; any other policy is applied at once.

### 14-018: An admin can update the dashboard, or roll it back, from the dashboard itself, and watch it come back.
- Where: releases-and-updates / The server updating itself
- What: For a newer version, the admin is asked "Update this dashboard to <version>? It will be offline for about ten seconds while it restarts. The databases are backed up first." For an older version on the vendor's feed (chosen from a list; the button stays disabled until one is chosen): "Roll this dashboard back to <version>? It will be offline for about ten seconds while it restarts. The databases are backed up first and stay as they are: they are not taken back to an older copy." A rollback to an earlier installed state can also restore the databases from a chosen backup; the question then says that everything recorded since that backup is discarded. Without restoring, it says "The databases are NOT restored: use a backup for that.", and when the databases are already in a newer form than the older version reads, it says to tick the restore box "or this will be refused". Only one update runs at a time. Progress reads "starting the update", then "working: <step>[, <message>]", then "restarting: the dashboard is offline for about ten seconds"; the page reloads by itself once the new version answers. After 3 minutes without it: "the dashboard has not come back yet. It may still be restarting: reload this page in a minute, or check the server's logs." A failed update shows its error; a refused one shows "Not applied: <reason>" and, if another update was already running, keeps following that one. Opening the page while an update is running picks up the progress.

### 14-019: First-run set-up is a checklist of steps, each saying where it stands and what failed.
- Where: server-install-and-running / Installing on a NAS
- What: The set-up page shows every step with its state: done, check this, failed, to do, skipped (or not listed), and highlights the first unfinished one. Errors appear inside the step that failed and are scrolled to; older errors are cleared first. Steps:
  - Licence: the licence text is shown ("(no EULA shipped in this build)" when none, and it cannot be accepted); the accept button works only once the accept box is ticked; accepting shows "accepted (<detail>)".
  - First admin: a name and password form, "Makes the first admin account and signs you in with it." It is replaced by "not available in this build", "an admin account already exists" or "could not check: ..." as the case is.
  - Your studio: the organisation's name and short name, the name of the project tree, the drive letter editors see it as, and the template folders; when signed in, prefilled from the current settings (never over typed text). Only changed, non-blank fields are saved; "nothing changed" or "saved".
  - Alert destination: an email address, a web address to post alerts to, and a "daily still-here message" choice; a test button shows "sending...", then "test sent to <where>." or "the test could not be sent: <detail>".
  - A checklist of remaining tasks, each with title ("(optional)" where so), state and detail, and "(you chose to skip this on <date>)" where an earlier skip no longer applies. The "done" row links each outstanding step. Each row offers "check" ("Looks again at how this step stands. Changes nothing."), the task's own action when it can run, "skip" (or "skip, I understand" for a step that gates completion) on optional steps, and "restart server" where the task needs one. A task needing values shows a form in its row (fixed choices as drop-downs, secrets hidden with "set; leave blank to keep it" when one is set) with "save and restart": "Saved. The server is restarting and this page reloads by itself." A fold-out for an operator shows how to set the same values when installing the server by hand.
  - After a restart, the page reloads by itself once the server answers healthy.

### 14-020: An admin changes the site's settings in one form, sees who changed what, and can undo the last change.
- Where: dashboard / Settings and setup
- What: Saving sends the whole settings form; settings the product works out for itself are shown but not editable. Each save says "saving...", then "saved at HH:MM:SS" (local clock) or "could not save: <reason>"; a refusal naming a setting opens the place holding it. The last five site-setting changes are listed, each as "<what was done> by <person>", how long ago (exact time on hover) and how many settings, with the total recorded ("No site setting changes recorded yet." when none). "Undo the last change" asks "Put back the <n> setting(s) changed by <person> <ago> (<exact time>)?" and undoes exactly that change, never a newer one made meanwhile; it is disabled until the history has loaded. Admins only.

### 14-021: An admin can import a whole settings file, seeing what it would change before it is applied.
- Where: dashboard / Settings and setup
- What: An admin pastes the text of a site settings file. Pasting nothing is refused ("could not import", asking for the settings file first). The product first works out the differences without applying them: "Nothing in that text differs from the current settings. Nothing was changed." or "This will change <n> setting(s), including <setting> from <old or (blank)> to <new or (blank)>, ... [, and <k> more]. Apply it?" (the first three named). Applying reloads the page; a failure says "could not import: <reason>". Imports appear in the change history and can be undone like a save.

### 14-022: Switching off a kind of reporting asks first, because what is held is deleted for good.
- Where: accounts-privacy-legal / What the product records about a person
- What: When a save, an import or an undo would switch off one of the site's reporting categories (14-055), the admin is first asked: "Stop every computer reporting: <names>? What this dashboard holds about it/them is deleted for every computer now, for good. Sync is not affected." with the button "Stop reporting". Turning one back on is not asked.

### 14-023: An admin is told how many computers reach the dashboard over plain http.
- Where: server-install-and-running / Connections and credentials
- What: Beside the site settings, information only: "<n> computer(s) reach(es) this dashboard over plain http on your network or tailnet. Serving it over https is recommended." and "<n> ... over plain http from the internet: see the alerts on the home page." Nothing is shown when there are none.

### 14-024: An admin chooses which assistant service answers the product's questions, and sees who answers each feature.
- Where: whole-product / The assistant
- What: Several assistant services can be set up, of two kinds: a key billed per use, or a program installed on the server and signed in with a subscription. They sit in a fixed order; the first one that is available answers, unless an admin pins one ("auto: first available in the order", or a pinned service; a pinned service that is not set up is listed as "(not set up)"). A refused pin puts the choice back and says "could not pin: <reason>". The panel says, per feature, who answers and why:
  - YouTube downloads (search terms, then relevance): the chosen service, or "no usable AI provider" with the reason.
  - Timeline Cards (semantic search, summaries): the same answer when it is a service of the family Timeline Cards was written for; otherwise "refused", with the advice to add or pin one of that family; "nothing to answer" when none is set up.
  - The server's own check (14-028): whether it can run, and on what.
  The header says "pinned to <service>", "pinned, not available" or "auto: first available". The list of set-up services shows "<n> of <total> set up · in order"; each row gives its rank, name, kind, a state (available, not configured, not installed, not signed in, disabled by site, unknown; each explained), the last test ("testing...", "test ok, <s>s" or "test failed, <s>s"), the key masked and whether it was set by whoever deployed the server or stored on it, or for a program its location, version and "signed in as <account>", and what it is used for, standing by for, or not used for and why. With none set up: "No AI provider is set up.", saying that the YouTube downloader cannot search, Timeline Cards' assistant features do not work and the server check mails a plain summary, and that adding a key takes a minute. "+ add new" lists the services not yet set up ("<n> more you can set up: <names>", or "All five providers are set up."), each with what it is and what it needs. Per service a menu offers: Test (one real call, timed), Pin as preferred / Unpin, and the actions in 14-025 and 14-026. Admins only. A failure to read the panel says "could not read the AI providers: <reason>".
- Flag: several ways in: the site-wide switch allowing installed programs (14-026) can be set from the panel's own tick box, by accepting the notice inside the set-up steps, and from the site settings form.

### 14-025: An admin adds a pay-per-use assistant key in three guided steps.
- Where: whole-product / The assistant
- What: Steps "get a key", "paste it", "test". Step 1 shows the service's own instructions, a link to its site in a new tab, what is needed, and a note that any spending limit is set on the service's side. Step 2 is a hidden key box with "Save key"; a blank key ("the key is blank") or one containing a space ("the key contains a space: paste the key alone, with no 'Bearer' prefix") is refused before sending. Saved: "Stored as <masked>." It is explained that the key is stored on the server readable only by the dashboard and never shown again except masked. Next is allowed only after a save. Step 3, "Test key", makes one real call and shows OK or FAILED with seconds, then where the service sits in the order and whether it now answers ("It answers from now on" or "<X> still answers first"), and, for a service of another family, "Timeline Cards will not use it". A stored key can be replaced (straight to step 2) or removed ("Remove the stored <name> key from this server? The YouTube downloader will fall back to the next available provider."). A key set by whoever deployed the server cannot be changed or removed here, and the panel says so. Back, cancel ("Closes this without going further. Anything already saved stays saved.") and Next or Finish are always offered; what was typed survives redraws.

### 14-026: An admin can install and sign in a subscription assistant program on the server, after accepting a notice.
- Where: whole-product / The assistant
- What: Steps "allow cli tools", "install", "sign in", "test", starting at the first unfinished one; a note says when this server cannot run the program.
  - Allow: a terms notice and a tick box; Next only when ticked, and pressing it switches on, for the whole site, the use of installed programs. The same switch has a tick box under the list ("allowed for this site", or "not allowed", noting that adding one shows the notice and asks first); switching it off closes any open set-up.
  - Install (or Update, or Try again): "From <publisher>, checked against its published sha256 before anything runs. It goes into this server's data folder and nowhere else." Progress "<step>: <MiB> of <MiB> (<n>%)" with a meter; then "installed: <version>", "interrupted: ..." or an error. Where the publisher gave no checksum, the installed state carries a note that the received file's checksum was recorded instead. A fold-out "installed it yourself? type its full path" lets an admin name a copy already on the server ("blank = search PATH"); a named copy wins over the installed one.
  - Sign in: an account-type choice where the program offers one (subscription, or per-use console), a button opening the publisher's own sign-in page in a new tab, a one-time code to type there, a box to paste back a code from that page (blank refused "that code is blank"), "waiting for the sign-in to finish (<n>s left)" and a cancel button. Once signed in: "Signed in as <account>." with a sign-out button. A hint names the command to sign in on the server itself instead.
  - Test and finish: version, signed in or not, a Test button, and its place in the order.
  Afterwards, per program: sign out, or "Finish setting up: sign in"; Update (only if installed here); "Use my own copy" or "Change its path"; Remove (only if installed here: "Remove <name> and its sign-in from this server? The YouTube downloader will fall back to the next available provider."). When the site has switched installed programs off, the row only says to switch them on.
- Flag: dormant: off in the vendor's build until a site switches it on; some builds leave it out entirely (see 14-028).

### 14-027: Timeline Cards' assistant features run only on the assistant family they were written for.
- Where: whole-product / The assistant
- What: When the service that would answer is of another family, Timeline Cards' semantic search and summaries are refused, and the admin's panel says why and what to do (add or pin a service of that family). The YouTube downloader works with any service.

### 14-028: The server's own assistant-written check runs only on a program installed on the server.
- Where: server-install-and-running / Health checks and alerts
- What: The admin's panel says whether the server's periodic check (which mails a report of what it found) can run: "always <program>, whatever the order or the pin say" when the subscription program is working; a warning that its runs fail and mail a plain summary until it is signed in when installed but not signed in; "cannot run" when installed programs are off for the site; otherwise "cannot run: <program> is not set up on this server". On a build that leaves installed programs out, there are no program rows, no switch and no notice; instead one optional line lets the admin type the path of a copy they installed themselves ("path saved", or "blank: the server looks for it on its PATH"), and the check then runs only on a pay-per-use key, never a subscription sign-in.
- Flag: differs: builds that include installed programs and builds that leave them out offer different set-ups for this check.

### 14-029: An admin ticks and unticks projects for every person's computers in one grid.
- Where: dashboard / Ticking and unticking
- What: The grid shows one tick box per project per computer of each person. Choosing a person fills the computer choice with "choose a computer…", "every computer" (only when the person has more than one) and each computer; a person with one computer has it chosen already, and the computer choice is unavailable until a person is chosen. A filter box hides projects whose name does not contain the typed text. Ticking makes a full tick; unticking removes the tick. A cell for a person whose computer has never reported applies to the person as a whole (every computer, or the not-yet-assigned plan). Each cell has an upload-only qualifier: turning it on ticks the project as upload-only (ticking it if needed); turning it off returns it to a full tick; it never unticks. While saving, the box is unavailable and pulses briefly. A failure puts the box back and shows a note that stays until clicked ("click to dismiss"): "could not tick <project> on <computer>: <reason>" or "could not set upload-only for ..."; a success shows a short note for 4 seconds. If the admin's sign-in has ended, the browser goes to sign-in and returns to the grid afterwards, and any column action in progress stops.

### 14-030: A computer wired to the server cannot be given a new sync tick.
- Where: sync / Wired or remote
- What: Once a wired computer's ticked project is unticked in the admin grid, its box locks with the explanation "<computer> is wired to the NAS: it works directly off the tree, so a new sync cannot be ticked here". Wired computers are also offered no project to add on a person's own account page (14-041).

### 14-031: Before a project is ticked onto a computer that may not have room for it, the person is warned and may go ahead.
- Where: sync / Disk space
- What: When both the project's proxy size on the server and the computer's last reported free space are known, and the project would leave less than 20 GB free or would take half or more of the free space, ticking it asks "<project> is <size> of proxies. <computer> has <free> free.[ That is more than will fit.] Sync it there anyway?". Cancel unticks it again; nothing is refused. The same warning is given when switching an upload-only tick to a full one, on a person's own account page and in the admin grid. Ticking a whole column first gives the warning for the column total ("<n> projects (<k> of them measured) are <size> of proxies...").
- Flag: built twice: the account page's warning and the admin grid's warning are worked out separately and are meant to agree.

### 14-032: An admin can tick or untick a whole column at once, and stop it part way.
- Where: dashboard / Ticking and unticking
- What: ALL ticks (full) and NONE unticks every project in one computer's column that differs, one after another. NONE first asks "Untick all <n> projects for <person[ on computer]>? Their copies stay on disk. Nothing new comes down and proxy sync stops for all of them." While it runs the button shows "done/total"; pressing it again stops after the change in flight ("click to stop after the change that is in flight"). At the end: "ticked all for ..." / "unticked all for ...", "stopped after i of n for ...", or a note that stays until dismissed: "[stopped after i of n. ]<f> of <n> change(s) failed: <first six names>[, and <k> more]".

### 14-033: An admin can copy one computer's sync plan onto another computer of the same person.
- Where: sync / A plan belongs to a computer
- What: For each computer, the admin can choose another computer of the same person to copy from; the plan is replaced by the other's. If the source has nothing ticked it is refused before anything is sent: "<source> has no projects ticked. Copying it would leave <target> with nothing." Otherwise the admin is asked "Replace <target>'s <n> project(s) with <source>'s <m>?" followed by either "<target> stops syncing <k> of them: <names>..." or "Nothing is removed from <target>." The page then reloads; a failure says "could not copy the plan: <reason>".

### 14-034: The Timeline Cards episode list can be sorted, filtered, searched and folded, and remembers how it was left.
- Where: cards-editor / Opening episodes and keeping the editor running
- What: The list of episodes works without any of the following too (folders fold, buttons work, alphabetical order).
  - Sort: last opened (the default; by when this person opened it, then by when anyone did), date last modified, largest, or A to Z. Episodes within each folder, and the folders themselves (by their newest or largest content), are re-ordered; ties and A to Z use natural, case-insensitive name order.
  - View: folders, or a flat list of every episode (folding controls are hidden in the flat list).
  - Year: only one year's episodes, or all; a remembered year no longer present falls back to all; the "recent" tiles follow the year too.
  - Search: every word typed must appear (ignoring case) in the episode's searchable text; matching letters of the name are highlighted; folders holding a match open and the others close and hide, and clearing the search returns folders to the person's own choices. Folder counts read "N of M" while filtered; the total reads "N episode(s)" or "N of M episodes"; a "nothing matches" note shows when nothing is left; a clear button appears while searching. The recent tiles stay visible, dimmed, during a search.
  - Keys: "/" (outside a text box) jumps to the search; Escape in the search clears it; Enter opens the episode when exactly one is left.
  - Unfold all, fold all, and a reset that clears the year and the search.
  - Folder sizes are the sum of their episodes (B, KB, MB, GB, TB, by 1024), with a "+" when any episode's size is unknown.
  - Sort, view, year and each folder's open or closed state are remembered on the device; the search text only for the tab.

### 14-035: An episode that is opening is watched, and the person is taken into it once it is ready.
- Where: cards-editor / Opening episodes and keeping the editor running
- What: While any episode in the list shows "loading", the list checks with the server about every 3 seconds (not while the tab is hidden; after a failure it waits longer, up to 15 seconds). When any episode's state changes, the list redraws. When the person was waiting for a particular episode and it is now ready, the browser goes straight into it, and Back does not return to the waiting list.

### 14-036: The episode list shows which cut lists are saved on this device and opens them with no network.
- Where: cards-editor / Working offline, connections and several devices
- What: The episode list shows, for each episode, whether a cut list of it is saved on this device:
  - "downloaded" (explanation: "A cut list of this episode is saved on this device and opens with no network.") with one "open <file>" button per saved cut list; its explanation names the file and "N edit(s) wait to sync" when there are unsent edits.
  - "downloaded, page not saved" (explanation: "...open the episode once with a connection.") with no button, when the cut list is saved but the editor itself is not.
  An "on this device" list at the top, newest first, reads "N cut list(s) open offline" and per copy "<episode>: <file>", the number of cuts, "N edit(s) waiting to sync", "saved <local date/time>", and either "its episode is not in this list" or "the episode page is not saved: open the episode once with a connection". It is shown only when at least one copy exists. Opening a copy opens the editor on it; online, with the episode not yet open on the server, it opens the episode the ordinary way instead. Saved cut lists are matched to episodes by where they came from on the server. Visiting the list while online saves what is needed for the next launch to work with no network.

### 14-037: A person can choose to work offline, and is told plainly when the server is unreachable.
- Where: cards-editor / Working offline, connections and several devices
- What: "work offline" (explanation: "Use the cut lists downloaded on this device even with the server up, as on a plane. Nothing goes to the server until you go back online.") switches the episode list and the editor on this device to offline; "go back online" switches back. Offline, the list shows an "offline" warning:
  - not by choice: "The server cannot be reached. This is the episode list as of <date/time or 'your last visit'>. Cut lists marked downloaded open from this device and sync when the server is back. Opening or closing anything else needs the server." with a "try the server again" link.
  - by choice: "You are working offline by choice. Cut lists marked downloaded open from this device, and their edits wait here until you go back online. Opening or closing anything else needs the server." with "go back online".
  Every open and close button is unavailable, explained "Needs the server, which cannot be reached." Where Timeline Cards runs as a desktop app on the person's computer, the app follows the same choice.

### 14-038: Anyone signed in can read the product's help documents inside the dashboard.
- Where: dashboard / Help pages
- What: A reader shows the product's documentation. Opening help with no document named opens the customer guide to how the product works. An index groups documents by folder (the main documents first, then each subfolder alphabetically; within a group the guide first, labelled "the customer explainer", then by name), each entry showing the document's own title. The index never lists a document the reader may not open.

### 14-039: Help documents are shown safely, with a contents list and links that work between them.
- Where: dashboard / Help pages
- What: Licence texts are shown exactly as written. Other documents are shown formatted: headings (each with a stable link address made from its words, leaving out any section number, so "4.1 Your sync plan" is linked as "your-sync-plan"; repeated headings numbered -2, -3), a contents list of the second- and third-level headings, paragraphs, lists (one level of nesting; numbered steps separated by blank lines stay one list), code blocks, tables (scrolling sideways when wide), rules, code, bold, italic and links. In the glossary, every term has its own link address so other pages can link to one term. Web, mail, in-site and in-page links work; a link to another document opens it in the reader, keeping the section; a link of any other kind, or to something that is not a document, is shown as plain text with the target in brackets. No markup written inside a document is ever passed through to the page. The page title is the document's title. Only documents inside the help folder can ever be opened, whatever address is typed.

### 14-040: Every person signed in has their own account page, always about themselves.

- What: Anyone signed in can open their own account page; it is always about the signed-in person, and no address can make it show someone else. Not signed in: "Sign in first." For each computer: Windows or Mac, wired or remote, its app version and whether it is up to date ("up to date" when it matches the current one or no current one is known), when it last reported, whether it is live, why it is in its state, its licence line and which reporting categories it withholds, its sync plan (each project, full or upload-only), its shared-work facts (14-048), the settings it last reported (14-050) and any pending request (14-049). Each computer's part refreshes on its own, and disappears if the computer stops being the person's. The same information can be fetched by a script for the signed-in person.

### 14-041: A person can add a project to one of their own remote computers from their account page.
- Where: dashboard / Ticking and unticking
- What: Under each of the person's remote computers, a list of active projects not yet in that computer's plan, with one button per mode (full sync or upload only). Choosing full for a project that may not fit first gives the warning in 14-031. Upload-only rows in the plan carry the same warning for switching to full. Wired computers offer neither. The computer's part refreshes when done.

### 14-042: A person can choose a display name that others see instead of their sign-in name.
- Where: accounts-privacy-legal / Who may sign in
- What: A display name is only a label shown to other people; records of who did what, sessions and sync plans always use the sign-in name. A person sets or clears their own; an admin can set or clear anyone's. Clearing (empty text): "Cleared. Other people now see your sign-in name." Unchanged text changes nothing. Spacing is tidied and equivalent Unicode spellings are made one. Refusals: only spaces: "A name cannot be empty. To go back to your sign-in name, clear the box and save."; over 64 characters: "A name can be at most 64 characters."; invisible or control characters: "A name cannot contain invisible or control characters."; the name of someone else (their sign-in name or display name): "Someone else already goes by that name. Pick another." A person may use their own sign-in name. Success: "Saved. Other people now see <name>." For an admin setting another's: "<username> is now shown as <name>." or "<username> is shown by their sign-in name again."; unknown person: "There is no account called <username>."; a non-admin trying: refused. Every change is recorded with the name before and after. A change shows everywhere at once; elsewhere names may take up to 30 seconds to update, and if display names cannot be read, sign-in names are shown.

### 14-043: A person can change their own password from their account page.
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: The form asks for the current password, the new one, and the new one again, with a "show passwords" choice for all three. Under the new password a count reads "0 of <min> characters", "<n> of <min> characters: <k> more to go" or "<n> characters: long enough"; under the repeat, "type it again", "the two match" or "the two do not match yet". Checks, in this order, with nothing changed on any refusal:
  1. A site where people sign in with their organisation's account: "You sign in with your organisation's account, so there is no password here to change. Change it where your organisation looks after its accounts." A sign-in method the dashboard cannot change passwords for: "This dashboard does not know how to change passwords for its sign-in method. Ask your admin. Nothing changed."
  2. "The two new passwords are not the same. Nothing changed."
  3. "The new password needs at least <n> characters. Nothing changed." (the same minimum as everywhere).
  4. "The new password is the same as the current one. Nothing changed."
  5. Too many wrong tries: the same wait as the sign-in page, which wrong current passwords here count towards.
  6. An admin named in the server's configuration with no account the dashboard keeps: "<user> is not an account this dashboard keeps a password for. Ask another admin, or change it where that account lives."
  7. The current password is checked as at sign-in: "The server is busy checking other sign-ins. Try again in a minute. Nothing changed." or "That is not your current password, so nothing changed. Several wrong tries in a row make this form wait, like the sign-in page."; a right one clears the wrong-try count.
  Anything over 1024 characters: "A password must be text of at most 1024 characters. Nothing changed." A typed password is never shown back.
- Flag: several ways in: the length and match checks are made both before sending and by the server, with the same words.

### 14-044: For people who sign in with their NAS account, changing the password changes it on the NAS.
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: Where the dashboard keeps its own accounts, its stored password is replaced. Where people sign in with their account on the NAS, the NAS password is changed. Refusals, nothing changed: no NAS access set up: "This dashboard holds no server credential, so it cannot change server passwords. Ask your admin."; NAS unreachable: "Could not reach the server, so nothing changed. Try again in a minute."; an account the dashboard may not manage (not an editor on the NAS): "The server does not let this dashboard change the password of <user>. Change it in the NAS's own settings, or ask your admin."; the NAS refuses: "The server refused the change, so nothing changed. Try again, or ask your admin." The NAS's own error text is never shown to the person.

### 14-045: After a password change, every other browser of that person is signed out and this one stays in.
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: The change is recorded (how they sign in and how many other sign-ins existed, never the password or its length). This browser gets a fresh sign-in, and every other browser signed in as the person is signed out. Computers' sync sign-ins are not affected. The account page then confirms the change and how many other browsers were signed out; when that number is unknown it says the password changed but it cannot say whether other browsers were signed out. If the fresh sign-in cannot be made, other browsers are still signed out and this one keeps its old sign-in.

### 14-046: A person can see every browser signed in as them and sign out any other.
- Where: accounts-privacy-legal / Passwords, sessions and failed sign-ins
- What: The account page lists the person's live sign-ins: a short handle, network address, browser description, when it signed in, when last seen, and which one is this browser, with a count of the others. Signing out one other browser: "Signed that browser out."; refused when the handle is not on the list ("That is not a browser on this list."), already signed out ("That browser is already signed out."), ambiguous ("Two browsers match that; use sign out the others instead.") or this browser ("That is this browser. Use Sign out instead."). "Sign out the others": "Signed out <n> other browser(s). This one stays signed in." or "No other browser was signed in." Another person's sign-in can never be touched this way. Each sign-out is recorded. When the server keeps no record of sign-ins: "Signed-in browsers are not being recorded on this server."

### 14-047: A person can see the sync keys their computers use, without being able to change them.
- Where: accounts-privacy-legal / How a computer proves who it belongs to
- What: The account page lists the person's sync keys (the key each of their computers uses to move files to and from the server): keys waiting for an admin's approval (fingerprint, computer, when submitted) and approved keys (fingerprint, computer, a comment up to 64 characters, when added). The key itself is never shown. It says whether a key is needed: not needed only when every one of the person's computers is wired to the server; a person with no computers yet needs one. The list arrives a moment after the page so a slow NAS never holds the page up. Where people sign in with their NAS account, approved keys are read from the NAS; on a NAS that cannot show key text (Synology), the page says keys exist but cannot be listed; if the NAS cannot be asked: "The server could not be asked which keys are approved just now." Where people sign in with their organisation's account, no approved keys are shown. Adding, approving and removing keys is for an admin only, elsewhere.

### 14-048: A person can see whether each of their computers is taking shared work, and what it is doing.
- Where: fleet-jobs / What a computer can honestly offer
- What: For each computer: "Not taking work: not heard from" (a lost computer), "Not taking work: switched off on this computer", the computer's own reason why not, "Taking fleet work" (wired), "Taking fleet work while nobody is using it" (remote), or "not reported". How long nobody has used it: wired computers "no wait (a computer wired to the server is exempt)"; otherwise "<n> s with nobody using it" under a minute, "<n> min with nobody using it", or "not reported". The work running now: "<label>[ on <file>][, <n>%]". The graphics card's name and memory when reported.

### 14-049: A person can ask one of their computers to take or stop taking shared work, and which kinds.
- Where: fleet-jobs / What a computer can honestly offer
- What: Only two things can be asked from the dashboard: whether shared work may use the computer, and which kinds of work it takes: "Transcribe audio (uses the graphics card)", "Make small preview copies of video", "Pull the audio out of video", "Draw audio waveforms" ("every kind" ticks all). Each change asks only for what it changed. The ask reaches the computer the next time it reports and takes effect the next time the app starts there. Who: the computer's owner or an admin ("Only the person this computer belongs to, or an admin, can change it."). Refusals: an unknown computer ("<person> has no computer called <computer>."); anything else, including wired or remote, which can never be asked ("Only these can be changed from here: whether the fleet may use the computer, and which kinds of work it takes."); unticking the last kind (refused before sending: "That is the last kind of work this computer takes. Untick Let the fleet use this computer instead."); an unknown kind; a computer that has never reported ("<computer> has not reported yet."); a computer whose app is too old ("<computer>'s CCSync is too old to change this from here. Update it, or change it in its tray: Settings, FLEET JOBS."). In those last two cases the controls are replaced by the sentence. When it already works that way: "Nothing to ask: it already works that way." One ask per computer can wait at a time; a pending ask can be withdrawn ("Withdrawn. Nothing is asked of it now." or "There was nothing waiting to withdraw."). The tick boxes show what the computer WILL do: a pending ask, else what is saved there awaiting a restart, else what is running. The state under each computer:
  - "Asked <ago>. <computer> gets it the next time it reports in."
  - "Sent to <computer> <ago>. Waiting for its answer."
  - "<computer> could not save it yet and will try again: <detail>"
  - "<computer> saved it. It takes effect the next time CCSync starts there."
  - "In effect." (for 10 minutes after the answer, then nothing)
  - "<computer> refused: <detail>"
  - "<computer> did not report in for 14 days, so the request was dropped."
  - nothing, when withdrawn or none.
- Flag: several ways in: the same two settings are also changed on the computer itself, in its own settings window.

### 14-050: A person can see, read-only, other settings each computer last reported, and where to change them.
- Where: editor-app / Settings, records and background work
- What: Blank when not reported: how long a computer lends itself to shared work ("<n> min"; change it on the computer, in its settings); for remote computers, the reminder about a pulled sync drive ("the first warning only", or "every <n> min"; changed on the computer); and, only when the site has YouTube downloads on, the YouTube terms ("accepted" / "not accepted", plus "downloads off on this computer") and the YouTube sign-in ("signed in", "signed in, needs a refresh", "expired: sign in again", "not signed in", "not used on this computer"), changed on the computer.

### 14-051: Any person can download everything the dashboard holds about them; an admin can do it for anyone.
- Where: accounts-privacy-legal / What the product records about a person
- What: A person downloads their own data (always their own; nothing can change whose). An admin can download anyone's; a non-admin trying for someone else: "Only an admin can do this for another person."; an impossible name: "That is not a user name this dashboard can hold."; nobody known by that name: "This dashboard holds nothing about <username>." A person counts as known if they have an account, are named as an admin, have a display name, a computer, any record naming them, or any sign-in record. The download is a single readable data file named for the person and the date, containing when it was made, the dashboard version, whose data it is, every record naming the person (secrets left out), and a "not included" list. It gathers: every dashboard record naming the person; their sign-ins and failed sign-ins; their YouTube requests, downloads and rights confirmations; client folders they made and clips they added to them; b-roll and music indexing batches they started or cancelled. Names are matched ignoring case. Sign-in secrets, password fingerprints and client-link secrets are never included (a client link's secret is the link itself). "Not included" always lists, in plain words: files on the person's own computers; files on the storage server and the server's own records of what each computer holds; the text of the server's mailed check reports (kept 60 days); Timeline Cards' working records (kept per episode); records of failed sign-ins kept by network address; snapshots of the dashboard's storage. It adds a sentence for each store that could not be read ("<what>: not available on this dashboard, so it could not be read.", "<what>: could not be read just now.", "<what>: this dashboard version cannot read them yet.", or the store's own reason). Every export is recorded with counts only, never the data. It can only be started by a deliberate press, never by opening a link.

### 14-052: Exports of a person's data are limited in number and size.
- Where: accounts-privacy-legal / What the product records about a person
- What: Per person: one export at a time ("An export of <username>'s data is already being made. Try again when it has finished."); at most 5 handed over per hour, counted separately for the person's own and for admins' ("<username>'s data has been exported <n> times in the last hour. Try again later."); at most 50 MB (for an admin: "The export of <username>'s data is larger than 50 MB, so it was not made. Erase their history first, or ask for a copy by other means."; for the person: "Your data is larger than 50 MB, so the file was not made. Ask an admin for a copy by other means."). The counts start afresh when the server restarts. A refusal from a page is shown as a short page with the sentence and a "Go back" link.

### 14-053: An admin can erase a person's past history while keeping their account and computers.
- Where: accounts-privacy-legal / What the product records about a person
- What: Admins only ("Only an admin can do this for another person."), with the same name checks as the export. It removes the past records about the person (never current state), their ended sign-ins (live ones stay) and their YouTube history. A store that cannot be reached is skipped and named, and the rest still runs. The admin is told "Erased <n> past record(s) about <username>. Their account and their computers' current state are unchanged.", adding " Some stores could not be reached; press it again later." when anything was skipped. The erasure is recorded with counts per kind of record and what was skipped.

### 14-054: When a person is deleted, their name on client folders is replaced by a stand-in and the client links keep working.
- Where: accounts-privacy-legal / Suspending, disabling and removing a person
- What: Every client folder the person made and every clip they added to one is relabelled with a stand-in name for that person (always the same stand-in for the same person). Client links keep working. Free text typed into a folder (contact, description, notes) is not changed. If it cannot be done, the deletion is reported to the admin as failed for client folders. B-roll and music indexing records are not relabelled (they are replaced whole when an index is next published).

### 14-055: Four kinds of report data can be withheld, by a computer or for the whole site, and the server never keeps them.
- Where: accounts-privacy-legal / What the product records about a person
- What: A site can switch off, or a computer can withhold, these kinds of report data; the server removes them from every incoming report, whatever app version sent it, before anything is kept:
  - Which Resolve project is open: removes the open project, the projects with clips only on that computer, and the project names in the record of changes made to Resolve. Changes made to Resolve can still be listed, but with project names replaced by "<project>" or "(detail withheld: this computer does not report project names)". Switching this off also switches off the project's media list (below).
  - The list of files on the computer: removes it, the names of missing clips and refused paths in the Resolve check, the names of files in sync conflicts (the count stays), stray and moved project folders (they read as "not reported"), and example names of files skipped because they already existed (counts stay).
  - The project's media list in Resolve.
  - How long since someone used the computer: removed, so shared-work idle times read as "not reported".
  Never removed, because sync or the person's own action needs them: names of files transferring, finished transfers, applied file moves, and the timeline a Timeline Cards hand-over is working in. A report that cannot be cleaned is refused rather than kept with withheld data in it.
- Flag: undetermined: an app version that does not understand withheld project names may no longer be able to undo a Resolve change from the dashboard.
