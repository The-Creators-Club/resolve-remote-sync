# Bug hunt 2026-09-03 (full-repo sweep, orchestrated fleet)

Sixth fleet hunt. Seventeen module-scoped hunters (every tracked source file
in the repo, one disjoint territory each) followed by five adversarial
verifiers told to REFUTE every high and medium finding in their area. All
hunters were briefed on CLAUDE.md, SPEC.md, the KNOWN_BUGS ledger (through
CR-101) and the three prior hunt archives, so nothing below re-reports a
resolved item; where a finding is the missing half of a recorded fix it says

0.7.27, installer 1.0.38), clean except for an uncommitted edit to
`docs/DOCKER.md`. 22 agents, roughly 4.4M tokens, about 45 minutes wall clock.
Read-only throughout: no hunter or verifier changed a file in the repo.

**Tally: 84 findings. After verification: 9 high, 27 medium, 48 low.**
43 of the 84 (every high and medium) went through the verifier wave: 0
refuted, 8 downgraded (2 high to medium, 6 medium to low), 0 upgraded,
several PLAUSIBLE raised to CONFIRMED by reproduction. Every territory's

which is a statement about what the suites do not cover: not one of the 84

### dash-mounts-ui-1 - `assignments.js` does not parse; every tick on the admin assignments page is a silent no-op
- Where: `dashboard/static/assignments.js:89-91`
- What: the UX-1 capacity confirm (commit `55fdfa7`, 2026-08-28) has two raw
  newlines inside a double-quoted string literal. `node --check` fails at
  line 89. The whole file is one IIFE, so nothing in it runs: the `change`
  listener that writes a tick, the upload-only qualifier, `[ ALL ]` /
  `[ NONE ]`, copy-from, the CR-95 wired re-lock, the filter. The checkbox
  flips visually and no request is made and no error is shown.
- Verified: `node --check` run by both hunter and verifier; the Dockerfile
  copies `dashboard/static` verbatim with no build step; per-commit blob
  check shows `097745f OK -> 55fdfa7 BROKEN -> 0407b57 BROKEN`, so it has
  shipped in every dashboard from 0.7.17 through the live 0.7.27.
- Why the suite is green: nothing in `dashboard/tests` parses or executes
  JavaScript; `test_admin_assignments.py` asserts server-rendered attributes.
- Fix: `sentence + "\n\nSync it there anyway?"`. Add a syntax gate over
  `static/*.js` (a `node --check` that skips cleanly when node is absent,
  plus the dependency-free "no quoted literal spans a newline" scan as a
  belt).

### ytdl-web-2 - the DOWNLOAD button re-validates the destination with the narrow rule, so a widened job can be created but never downloaded
- Where: `ytdl/web/ytdlweb/routes_api.py:517` (`start_download`), against
  the create sites at `:456` and `:774`
- What: creation passes `machine=req.machine, local=req.local` into
  `projects.resolve_project`; `start_download` calls it with neither, i.e.
  the pre-CR-72 narrow rule. The create-time flags are persisted nowhere
  (no `local`/`machine` column in `schema.sql` or any migration), so no
  correct answer is reachable from that function. Because
  `YTDL_LOCAL_DOWNLOAD` ships OFF, the SPA posts `local: false`, half 1 of
  CR-96 widens every editor's create, and DOWNLOAD (and RETRY) then answer
  `409 "<project> is no longer a project you sync"`, which is false.
- Verified: reproduced end to end by hunter and verifier with the real app;
  needs no companion, no flag, no mixed account.
- Ledger: regression of CR-96 (both halves).
- Fix: persist the create-time `local`/`machine` on the job row (migration,
  defaults = pre-widening values) and pass them back in. Do NOT re-derive
  from the current request: trusting a client-supplied `local=false` here
  would let any editor download into any active project. Missing test:
  create -> `ready_for_review` -> DOWNLOAD for a widened project.

### ytdl-web-1 - the SPA never sends `machine` on a job POST, so the picker offers projects that SEARCH / GET LINKS refuse
- Where: `ytdl/web/static/app.js:1913` (`runSearch`) and `:1972` (`runUrls`)
- What: `loadProjects` puts `&machine=<hostname>` on the GET (CR-96 half 2)
  but neither POST body carries `machine`, so `NewJob.machine` is `None`,
  `_wired(user, None)` is False and the server falls back to the ticked
  list. On a mixed wired/remote account standing at the wired rig, the

- Verified: reproduced with the CR-96 test fixture. The CR-96 test pins "a
  picker offering what the POST then refuses is the worse bug" by calling

  is exactly the seam the defect lives in.
- Fix: add `machine` next to `local` on both payloads (omit when unknown,
  never `''`); extend the picker test to assert the POST body. Pair with
  ytdl-web-2 or the widened job still dies at DOWNLOAD.

### comp-resolve-1 - two concurrent media-pool edits silently lose undo-journal entries
- Where: `companion/src/ccsync_companion/resolve_journal.py:401-433`
  (`record`), `_write` at `:351`
- What: `record()` takes `_lock` only inside `open_session()`, then does an
  unlocked read-append-write of the whole journal file, and every writer
  shares one `.tmp` name. Both call sites (`replace_clip` at
  resolve_bridge.py:2213, `link_proxy_media` at `:2310`) are OUTSIDE
  `_bridge_call`, so `_API_LOCK` does not serialise them. The write failure
  is swallowed at `log.debug`.
- Verified: 8 threads x 20 records into one project: hunter saw 5 of 160
  survive, verifier 8 of 160. Real colliding writers: FIX ALL (tray
  thread), the 120 s proxy-relink pass, the watcher's automatic canonical
  relink, the b-roll `/insert` canonicaliser.
- Consequence: tray or dashboard UNDO reports success while the clips whose
  entries were lost keep the rewritten path, with no "skipped" count.
- Fix: hold `_lock` across the read-append-write; give `_write` a
  per-thread tmp name (on Windows the shared tmp is a second, separate
  failure); raise the swallowed write failure to WARNING.

### comp-core-1 - the companion installs a signed record without checking that it is a companion record for THIS platform
- Where: `companion/src/ccsync_companion/upgrade.py:1225` (`_accept_offer`),
  `:1310`, `:1495`; the sole enforcer today is
  `dashboard/src/ccsync_dashboard/api.py:4728` (`_upgrade_info`)
- What: `release_pubkey.py` says the signature covers `kind`, `platform`
  and `arch` so "a Mac handed a Windows exe, or an onboard installer
  offered as a companion self-upgrade" is impossible and the dashboard is
  "removed from the trust chain". The companion canonicalises those fields
  for verification and then discards them: `_accept_offer` checks the
  signature, the CR-52 self-contradiction and the downgrade floor, nothing
  else. A genuinely signed `onboard` record (same table, same key) served as
  `upgrade` passes every check and is renamed over the running companion;
  `onboard.exe` puts up a wizard, does not exit inside the 2 s takeover
  grace, so no rollback fires and the Run key now launches the wizard at
  every logon.
- Verified: grep shows `kind`/`platform_key()`/`arch_key()` used only at the
  definitions and the `record_fields` call. Realistic impact is denial of
  service plus a wizard on autostart, not arbitrary code (an unsigned build
  still cannot be produced), but the module's stated invariant is false.
- Ledger: the missing client half of REL-16 / REL-4 (both recorded as
  dashboard-half fixes).
- Fix: in `_accept_offer`, after the signature verifies and BEFORE
  `note_floor`, refuse unless `kind == "companion"` and `platform ==
  platform_key()`. The `arch` half is a policy decision, not a patch:
  `OPTIONAL_KIND_EXTRA_FIELDS` deliberately says arch is enforced
  dashboard-side, and a client arch test must treat a missing `arch` and
  `universal2` as passing or every pre-wave record is refused.

### comp-ui-1 - two tray dialogs build a `tk.Tk()` root outside `ui_dispatch`, orphaning a pinned Tcl interpreter per click
- Where: `companion/src/ccsync_companion/tray.py:977`
  (`_install_youtube_cookies`) and `:1088` (`_show_youtube_terms_dialog`);
  the correct pattern is `popup._tk_pick` (popup.py:2225)
- What: both run on a `_spawn` worker thread and call `tk.Tk()` directly,
  then `root.destroy()`. They are the only two `tk.Tk()` sites in the
  package not wrapped in `ui_dispatch.dispatch`, and neither calls
  `release_root()`. The CR-93 guard pins every interpreter at birth; the
  only release paths are `dispatch()`'s reclaim and `release_root()`, so the
  record becomes a permanent orphan (about 1.8 MB each; `PINNED_WARN_AT=8`
  then logs an ERROR naming no holder). On macOS the same code builds
  Tk-Aqua off the main thread beside the dispatcher's own root, which is
  the CR-93 abort shape. The docstring six lines above the `tk.Tk()` says
  "not one of this process's Tk roots".
- Verified: reproduced from the venv (`pinned after worker exited: 1`,
  `held by: <none>`; same body under `dispatch` + `release_root`: 0). Every
  test of both functions passes the `picker=`/`confirm=` seam, mocking away
  the broken branch.
- Fix: wrap each body in `dispatch(fn)` with `release_root(root, ...)` in a
  `finally`, as `_tk_pick` does; correct the docstrings. Caution on "take
  `_popup_active_lock` too": `_show_update_dialog` already holds it, so
  check the callers first or it deadlocks. Add an AST guard to
  `test_tk_interpreter_hygiene.py`: every `tk.Tk()` in the package must be
  inside a function passed to `ui_dispatch.dispatch`.

### comp-ytdl-jobs-1 - one failed heartbeat HTTP call destroys a running whisper job
- Where: `companion/src/ccsync_companion/jobs_runner.py:509` (`_heartbeat`),
  caught by `_run_child`'s catch-all at `:884`
- What: `_heartbeat` has zero transport-failure tolerance. A single raised
  call (a 3 s dashboard restart, a tailnet blip) propagates into
  `_run_child`'s `except Exception`, which terminates the child and posts
  the job failed with `retryable=True`. The dashboard counts an attempt
  AND puts a 120 s cooldown on the machine that did the work; three such
  events and the job is `abandoned`. The module docstring's "miss ten in a
  row before it is treated as gone" is not implemented. Both siblings in
  this repo got it right (`ytdl_executor.FleetClient._call` retries;
  `DownloadJob._heartbeat_loop` swallows anything but a 410).
- Verified: probe with a `request_fn` raising on `/heartbeat` only:
  `proc.returncode=-15`, job failed, one HTTP call. This is CR-31's shape
  reproduced in a module written after CR-31 was fixed.
- Fix: a raised transport failure returns True (keep going); only a real
  410 returns False. If a consecutive-failure counter is added it must
  exceed `JOB_LEASE_SECONDS / HEARTBEAT_SECONDS` or it reintroduces the
  same premature kill more slowly. Same fix covers comp-ytdl-jobs-2 below.

### dash-api-1 - `DASH_SESSION_SECRET` rotation is wired into `/report` only; selection, untick, diagnostics and every fleet-job gate reject a retired-key identity

  `/heartbeat`, `/result` 403 (a held job can never finish; its lease
  expires and it re-queues). Per-editor `cce1.` tokens do not save

- Verified: live `TestClient` run by hunter and verifier with an identity
  minted on the old key: report 200, selection 401, diagnostics 401,

- Ledger: incomplete fix of DASH-2.
- Fix: `auth.read_identity_token_ex(settings, identity)[0]` at all four
